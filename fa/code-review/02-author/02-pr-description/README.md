# شرح PR، شواهد و خودبازبینی

**زبان:** فارسی · [English](../../../../en/code-review/02-author/02-pr-description/README.md)

> مسیر: [فصل ۲ — آماده‌سازی نویسنده](../README.md) · [فهرست دوره](../../README.md)

## آموزش

شرح PR باید مسئله، راه‌حل، دامنه، تصمیم‌های مهم، تست‌ها، ریسک و نوع بازخورد درخواستی را روشن کند. لینک issue، تصویر UI، نمونهٔ ورودی/خروجی و تغییر config را در صورت نیاز بگذار؛ دادهٔ محرمانه یا secret را در تصویر و log وارد نکن.

خودبازبینی یعنی diff نهایی را مانند فردی بخوانی که در پیاده‌سازی حاضر نبوده. فایل تصادفی، debug log، حذف ناخواسته، test ضعیف، docs منسوخ و ناسازگاری با معیار پذیرش را پیدا کن. بررسی حافظه‌ای کافی نیست؛ تمرکز روی diff نهایی باشد.

شرح باید حقیقت‌گو باشد: اگر benchmark یا integration test اجرا نشده، آن را ادعا نکن. trade-off و ابهام را توضیح بده تا reviewer بتواند سؤال درست بپرسد. مستندات feature، API، تنظیمات و runbook هم با تغییر هماهنگ شوند.

پیش از درخواست review، استانداردهای کدنویسی تیم و معماری موجود را رعایت کرده‌ای؟ تغییر را در محیط توسعهٔ مناسب آزموده‌ای؟ عنوان، توضیحات، لینک issue، تصویر بی‌خطر و تنظیمات لازم را اضافه کرده‌ای؟ پرسش‌ها و ریسک‌های حل‌نشده را یادداشت کن؛ انتظار نداشته باش reviewer آن‌ها را از diff حدس بزند.

## روند پیشنهادی

1. چه مسئله‌ای و برای چه کسی حل می‌شود؟
2. راه‌حل و بخش‌های تغییرکرده چیست؟
3. چه تستی اجرا شد و نتیجه چه بود؟
4. ریسک، rollout و rollback چیست؟
5. diff نهایی و docs را از ابتدا بازبینی کن.

## مثال کاربردی

در PR cache بنویس: «کلید قبلی بین tenantها مشترک بود؛ tenant به کلید افزوده شد. تست جداسازی اضافه است. cache قدیمی تا TTL می‌ماند؛ لطفاً invalidation و سازگاری deploy را هم بررسی کنید.» این شرح reviewer را به ریسک اصلی راهنمایی می‌کند.

## خطاهای رایج

شرح «fix bug» کافی نیست؛ تست اجرا نشده را سبز معرفی نکن؛ screenshot بدون توضیح نگذار؛ پرسش مهم را بیرون PR نگه ندار؛ خودبازبینی را با اجرای formatter یکی ندان.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** شرح مناسب PR کدام است؟

   1. فقط اسم branch
   2. مسئله، راه‌حل و شواهد اعتبارسنجی
   3. تعداد ساعت کار
   4. متن مبهم fix

**پاسخ:** 2 — زمینه کمک می‌کند diff درست خوانده شود.

### پرسش 2

**سؤال:** خودبازبینی روی چه چیزی انجام می‌شود؟

   1. حافظهٔ نویسنده
   2. diff نهایی از دید reviewer تازه
   3. فقط تست
   4. کد پس از merge

**پاسخ:** 2 — diff نهایی ممکن است خطاهای ساده را آشکار کند.

### پرسش 3

**سؤال:** اگر integration test اجرا نشده چه می‌نویسیم؟

   1. سبز است
   2. اجرا نشده و دلیل/محدودیت چیست
   3. شرح را حذف می‌کنیم
   4. تست را از CI برمی‌داریم

**پاسخ:** 2 — شفافیت ریسک را قابل مدیریت می‌کند.

### پرسش 4

**سؤال:** کدام درخواست review بهتر است؟

   1. همه‌چیز را چک کن
   2. migration و rollback روی دادهٔ قبلی را بررسی کن
   3. فقط سریع approve کن
   4. هرچه خواستی تغییر بده

**پاسخ:** 2 — درخواست دقیق توجه را هدایت می‌کند.

## آموزش عمیق: به reviewer زمینه و شواهد بده

### شرحی که در شش ماه هم قابل‌فهم باشد

شرح PR بخشی از تاریخچهٔ تصمیم مهندسی است. نویسنده هنگام ساخت کد می‌داند چرا این راه را انتخاب کرده؛ نفر بعدی فقط diff را می‌بیند. بنابراین شرح باید پاسخ دهد: **چه تغییری؟ چرا؟ چطور اعتبارسنجی شد؟ چه ریسکی باقی است؟** جملهٔ «fix bug» هیچ‌کدام از این پاسخ‌ها را نمی‌دهد.

از قالب زیر استفاده کن و بخش بی‌ربط را حذف کن:

<pre dir="ltr"><code>## What
...

## Why
...

## How to verify
- ...

## Risks and rollout
- ...

## Reviewer focus
- ...</code></pre>

**What** نتیجهٔ قابل‌مشاهده را خلاصه می‌کند. **Why** issue یا نیاز محصول را به آن وصل می‌کند. **How to verify** دستور تست یا شواهدی مانند screenshot و benchmark را می‌آورد. **Risks and rollout** اثر جانبی، migration و بازگشت را توضیح می‌دهد. **Reviewer focus** سؤال‌هایی را مشخص می‌کند که نویسنده واقعاً برایشان نظر می‌خواهد. قالب جای فکر را نمی‌گیرد؛ متن باید برای PR واقعی انتخاب شود.

### خودبازبینی از دید نفر تازه

بعد از پایان پیاده‌سازی، چند دقیقه از کد خارج شو و diff را دوباره باز کن:

1. عنوان و شرح را با نیازمندی مقایسه کن؛ آیا هر دو همان مسئله را می‌گویند؟
2. فهرست فایل‌ها را مرور کن؛ فایل موقت، log دیباگ، secret، خروجی build یا تغییر ناخواسته‌ای هست؟
3. هر بخش diff را بخوان؛ آیا می‌توانی توضیح بدهی چرا تغییر لازم است؟
4. تست و مستندات را ببین؛ تست چیزی را assert می‌کند؟ راهنمایی قدیمی نشده؟
5. دستورات تست را اجرا و نتیجهٔ واقعی را ثبت کن.
6. مواردی را که هنوز مطمئن نیستی، به‌عنوان سؤال یا محدودیت بنویس.

خودبازبینی اجرای دوبارهٔ formatter نیست. formatter فقط شکل را تغییر می‌دهد، درحالی‌که self-review دنبال خطای مفهومی، فایل ناخواسته، تغییر ناقص و ادعای بی‌شاهد است.

### مثال: تغییر تنظیم cache

**شرح مبهم:** «cache fix شد.»  
**شرح قابل‌بررسی:** «پاسخ cache بین tenantها مشترک می‌شد؛ tenant فعلی به کلید cache اضافه شد. تست جدید جداسازی دو tenant را می‌سنجد؛ unit tests اجرا شدند. cacheهای قبلی تا پایان TTL باقی می‌مانند. لطفاً invalidation، مهاجرت rolling و امکان برگشت نسخهٔ قبلی را بررسی کنید.»

شرح دوم هم «چه» و هم «چرا» را می‌گوید، evidence را محدود به واقعیت نگه می‌دارد و reviewer را به risk اصلی راهنمایی می‌کند.

### تمرین

برای یک تغییر فرضی که صفحهٔ جست‌وجو را pagination می‌کند، قالب بالا را پر کن. پاسخ باید بگوید sort پایدار چگونه حفظ می‌شود، چه تستی صفحهٔ آخر/خالی را می‌سنجد، آیا API قدیمی سازگار می‌ماند و اگر deploy نیمه‌کاره شد چه رفتاری رخ می‌دهد. اگر اطلاعاتی را نمی‌دانی، آن را سؤال بنویس نه فرض.

### تسلط یعنی بتوانی…

- شرح را طوری بنویسی که تغییر را بدون خواندن همهٔ فایل‌ها معرفی کند؛
- ادعاهای تست و benchmark را دقیق و قابل‌ردیابی نگه داری؛
- سؤال review را به ریسک اصلی وصل کنی؛
- diff را از نگاه هم‌تیمی‌ای بخوانی که در پیاده‌سازی حضور نداشته است.
