## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

مدل دامنه مفاهیم، رفتار، روابط و محدودیت‌های مسئله را در زبان نرم‌افزار بازنمایی می‌کند؛ باید با قواعد واقعی کسب‌وکار هماهنگ بماند.

## مثال کاربردی

`Order` جمع مبلغ، وضعیت مجاز و شرط لغو را مدیریت می‌کند، نه فقط فیلدها را.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «برنامه‌نویسی شیءگرا» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** مدل‌سازی همهٔ جزئیات شرکت را به نرم‌افزار تحمیل نکن؛ محدودهٔ use case مهم است.
- **بازبینی:** مدل دادهٔ دیتابیس را بی‌فکر به عنوان مدل دامنه نپذیر.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: مدل دامنه مفاهیم، رفتار، روابط و محدودیت‌های مسئله را در زبان نرم‌افزار بازنمایی می‌کند؛ باید با قواعد واقعی کسب‌وکار هماهنگ بماند.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: `Order` جمع مبلغ، وضعیت مجاز و شرط لغو را مدیریت می‌کند، نه فقط فیلدها را.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: مدل‌سازی همهٔ جزئیات شرکت را به نرم‌افزار تحمیل نکن؛ محدودهٔ use case مهم است.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: مدل دادهٔ دیتابیس را بی‌فکر به عنوان مدل دامنه نپذیر.

## آموزش تکمیلی مستقل

### ۴. طراحی مدل‌محور و زبان مشترک

Domain model، schema ذخیره‌سازی نیست. آن، مفهوم‌ها، رفتارها، روابط و قواعد دنیای مسئله را به زبان نرم‌افزار بیان می‌کند. برای کشف آن، به جای شروع از کلاس‌ها با متخصص دامنه دربارهٔ جریان واقعی کار، استثناها، تصمیم‌های انسانی و پیامدها گفتگو کن.

#### زبان مشترک (Ubiquitous Language)

واژهٔ مشترک باید در مکالمه، کد، API، آزمون و مستندات معنای سازگار داشته باشد. «لغو سفارش»، «بازپرداخت پول» و «مرجوعی کالا» سه عمل مختلف‌اند. اگر همه را cancel بنامیم، سیستم نمی‌تواند به‌خوبی وضعیت ارسال، پول و موجودی را مدیریت کند.

یک واژه‌نامهٔ کوتاه بساز اما آن را به سند مرده تبدیل نکن. مثال و counterexample اضافه کن؛ اگر دو بخش کسب‌وکار یک واژه را با معناهای متفاوت به کار می‌برند، bounded context جدا را بررسی کن و ترجمهٔ میان contextها را صریح بساز.

#### Domain model غنی و مدل بی‌رفتار

مدل غنی state و قواعد را نزدیک هم نگه می‌دارد؛ مفید است وقتی invariantهای مهم یا پرتغییر داریم. مدل بی‌رفتار عمدتاً داده است و عملیات در serviceها قرار می‌گیرد؛ برای CRUD ساده، گزارش یا انتقال داده ممکن است کم‌هزینه و درست باشد.

مدل بی‌رفتار وقتی آسیب می‌زند که:
- یک قاعده در چند handler تکرار شود؛
- caller state را بخواند، تصمیم بگیرد و setter بزند؛
- transition نامعتبر از چند مسیر ممکن باشد؛
- سرویس‌های متعدد برای یک مفهوم نتایج متفاوت تولید کنند.

در چنین شرایطی مالک invariant را پیدا کن و رفتار را به آن منتقل کن. برچسب anti-pattern را کورکورانه به هر data record نزن؛ پیچیدگی واقعی را بسنج.

#### Entity، value و class variant

Entity با identity پایدار و lifecycle خود شناخته می‌شود؛ ایمیل مشتری عوض شود، CustomerId همان است. Value object بر اساس مقدار معنا دارد؛ Money(100, USD) با Money(100, USD) برابر است، اما 100 USD با 100 EUR برابر نیست. value object معمولاً تغییرناپذیر است و invariant را هنگام ساخت می‌گیرد.

حالت‌ها و variantها را طوری مدل کن که ترکیب نامعتبر کم شود. دو Boolean می‌توانند چهار ترکیب بسازند که شاید فقط یکی مجاز باشد. enum، tagged union، subclass یا composition را بر اساس تعداد حالت‌ها، رفتار مستقل و جهت تغییر انتخاب کن؛ کلاس بیشتر همیشه مدل بهتر نیست.

## نمونهٔ کد مرحله‌ای

مدل دامنه state و invariantهای مفاهیم مسئله را نگه می‌دارد؛ schema دیتابیس فقط یکی از شیوه‌های ذخیره‌سازی آن است. مقدارها و انتقال‌های معتبر را از گفت‌وگو با متخصص دامنه استخراج کن و مدل را با مثال‌های واقعی بررسی کن.
**تمرین با پاسخ:** آیا دو سفارش با شناسهٔ یکسان ولی مبلغ متفاوت یک entity واحدند؟ شناسه هویت را تعیین می‌کند، اما تغییر مبلغ باید از قاعدهٔ معتبر دامنه عبور کند.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا تصمیم طراحی روشن بماند.

~~~csharp
public sealed class Order
{
    public OrderId Id { get; }
    public Money Total { get; private set; }
    public OrderStatus Status { get; private set; }

    public void AddLine(Product product, Quantity quantity)
    {
        if (Status != OrderStatus.Draft) throw new InvalidOperationException();
        Total += product.Price * quantity.Value;
    }
}
~~~
