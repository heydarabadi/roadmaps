# فصل 01: کد تمیز — Clean Code


> **زبان:** [نسخهٔ انگلیسی](../../en/01/clean-code/README.md)

## هدف یادگیری

- کد تمیز یعنی کاهش هزینهٔ فهم و تغییر؛ معیار آن سلیقه یا کوتاهی خط نیست، بلکه این است که هم‌تیمی بتواند رفتار کد را با اطمینان دنبال و اصلاح کند.
- بتوانی میان مسئله، الگو و هزینهٔ عملیاتی تمایز بگذاری.
- برای یک تصمیم، مثال، مبادله و معیار بازبینی بنویسی.

## ایدهٔ مرکزی فصل

کد تمیز یعنی کاهش هزینهٔ فهم و تغییر؛ معیار آن سلیقه یا کوتاهی خط نیست، بلکه این است که هم‌تیمی بتواند رفتار کد را با اطمینان دنبال و اصلاح کند. این فصل را همراه با فصل‌های مجاور بخوان: طراحی شیء و اصول، کیفیت کد را درون جزء بهتر می‌کنند؛ سبک و الگوی معماری رابطهٔ چند جزء و مرزهای استقرار را شکل می‌دهند؛ الگوهای سازمانی اغلب درون این مرزها اجرا می‌شوند.

## نقشهٔ مفهومی و درس‌های مستقل

- [یکنواختی — Be consistent](topics/consistency/README.md) — قراردادهای مشترک برای نام‌گذاری، قالب، خطاها و ساختار فایل، هزینهٔ جابه‌جایی ذهنی را پایین می‌آورند؛ قواعد باید خودکار یا دست‌کم روشن باشند.
- [نام معنادار به‌جای توضیح اضافی — Meaningful names over comments](topics/meaningful-names/README.md) — نام باید نیت و واحد دامنه را روشن کند؛ توضیح متنی وقتی لازم است که دلیل یا محدودیت غیرآشکار باشد، نه برای شرح خود کد.
- [تورفتگی و سبک کد — Indentation and Code Style](topics/indentation-style/README.md) — قالب‌بندی یکنواخت بلوک‌ها و عبارت‌ها ساختار منطقی را در نگاه اول نشان می‌دهد و اختلاف‌های بی‌ارزش را از بازبینی حذف می‌کند.
- [کوچک نگه‌داشتن تابع، کلاس و فایل — Keep methods, classes, and files small](topics/small-units/README.md) — واحد کوچک باید یک دلیل مشخص برای تغییر داشته باشد و جزئیات نامرتبط را پشت رابط محدود پنهان کند؛ «کوچک» هدف مستقل نیست.
- [تابع خالص — Pure functions](topics/pure-functions/README.md) — تابع خالص خروجی‌اش فقط به ورودی وابسته است و بیرون از خود اثر قابل مشاهده ندارد؛ چنین تابعی آسان‌تر تست، cache و موازی می‌شود.
- [کاهش پیچیدگی دوری — Minimize cyclomatic complexity](topics/cyclomatic-complexity/README.md) — کاهش مسیرهای تصمیم‌گیری در یک واحد، تعداد حالت‌هایی را کم می‌کند که باید فهمیده و آزموده شوند؛ با نام‌گذاری، guard clause و استخراج قواعد مرتبط کمک بگیر.
- [پرهیز از null و boolean مبهم — Avoid passing nulls and booleans](topics/avoid-null-booleans/README.md) — ورودی اختیاری یا حالت رفتاری مبهم را با نوع معنادار، گزینهٔ صریح یا چند عملیات نام‌دار مدل کن تا فراخواننده نیتش را نشان دهد.
- [فاصله‌دادن منطق دامنه از فریم‌ورک — Keep framework code distant](topics/framework-distance/README.md) — منطق مرکزی را از annotation، API و چرخهٔ عمر چارچوب جدا نگه دار تا تغییر ابزار و آزمون واحدهای دامنه ارزان‌تر باشد.
- [انتخاب سازهٔ زبانی درست — Use the right constructs](topics/right-constructs/README.md) — از قابلیت خود زبان برای بیان دقیق قصد استفاده کن؛ نوع‌ها، enumها، ساختارهای کنترل و مجموعه‌ها وقتی به‌درستی انتخاب شوند خطاهای نامعتبر را محدود می‌کنند.
- [آزمون سریع و مستقل — Tests should be fast and independent](topics/fast-independent-tests/README.md) — آزمون قابل اعتماد باید نتیجه‌اش به ترتیب اجرا، ساعت، شبکه یا دادهٔ باقی‌مانده وابسته نباشد؛ آزمون‌های کند را در سطح مناسب و با مرز روشن قرار بده.
- [سازمان‌دهی بر پایهٔ نقش/عامل — Organize code by the actor it belongs to](topics/organize-by-actor/README.md) — گروه‌بندی بر اساس کسی که نیازمندی را تغییر می‌دهد، محل یافتن قواعد را برای تیم و بازبین قابل پیش‌بینی می‌کند؛ منظور می‌تواند نقش کسب‌وکار یا capability باشد.
- [جداسازی فرمان و پرس‌وجو (CQS) — Command-query separation](topics/command-query-separation/README.md) — یک عملیات یا وضعیت را تغییر دهد یا نتیجه برگرداند؛ جداکردن این دو رفتار قرارداد تابع و آزمون را شفاف می‌کند، اما لزوماً به دو سرویس یا دو پایگاه داده نیاز ندارد.
- [سادگی و بازآرایی پیوسته — Keep it simple and refactor often](topics/simple-refactor/README.md) — طراحی را با نیاز فعلی حل کن، کد تکراری و پیچیده را پس از فهم رفتار مرحله‌ای بازآرایی کن و با آزمون مرز رفتار را نگه دار.

## توضیح یکپارچهٔ فصل

برای هر تصمیم سه سؤال را جواب بده: **چه چیزی تغییر می‌کند؟ چه کسی مالک قاعده/داده است؟ و کدام ویژگی کیفی اهمیت دارد؟** سپس سطح راه‌حل را انتخاب کن: تابع و نوع، مرز ماژول، سرویس، صف یا مدل داده. این ترتیب کمک می‌کند نام الگو جای شناخت مسئله را نگیرد.

هر فایل موضوعی اکنون یک درس مستقل با توضیح مرحله‌ای، نمونهٔ کد، محدودیت، تمرین و آزمون پاسخ‌دار است. مسیر پیشنهادی از قراردادهای خوانایی آغاز می‌شود، به مرز و پیچیدگی می‌رسد، سپس آزمون و بازآرایی را به چرخهٔ روزانه وصل می‌کند. برای مقایسه، نمونهٔ زیر عمداً یک مسئلهٔ مشترک را با چند سطح طراحی نشان می‌دهد: در فروشگاه، قانون لغو سفارش یک قاعدهٔ دامنه‌ای است؛ جداکردن آن از کنترلر مرز درون‌برنامه‌ای می‌سازد؛ اگر تیم و چرخهٔ انتشار مستقل شوند شاید component کافی باشد؛ اگر داده و بار و مالکیت مستقل باشند جداسازی سرویس بررسی می‌شود. هر مرحله نیازمند شاهد تازه است و مرحلهٔ بعدی را خودکار توجیه نمی‌کند.

## مطالعهٔ موردی و تجربهٔ صنعتی مستند

Shopify در نوشتهٔ مهندسی خود دربارهٔ ماژولارکردن یک کدبیس Rails بزرگ توضیح می‌دهد که مرزهای روشن، مالکیت اجزا و آزمون‌های کوچک‌تر به فهم‌پذیری و سرعت تغییر کمک می‌کنند. این نمونه نشان می‌دهد خوانایی فقط ویژگی یک تابع نیست و به سازمان‌دهی تیم و مخزن هم وابسته است.

- [Shopify؛ Deconstructing the Monolith](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity) — گزارش/منبع اصلی یا مرجع مرتبط با تجربهٔ مستند.
- [Shopify؛ Under Deconstruction](https://shopify.engineering/shopify-monolith) — گزارش/منبع اصلی یا مرجع مرتبط با تجربهٔ مستند.

**روش خواندن مطالعهٔ موردی:** مسئلهٔ اولیه، محدودیت workload، گزینه‌های ردشده، هزینهٔ ارتباط و پیامد بعدی را استخراج کن. عدد یا تصمیم گزارش‌شده را به کل شرکت و همهٔ سامانه‌ها تعمیم نده.

## نمونهٔ کد یا قرارداد

```python
from decimal import Decimal

def subtotal(lines):
    return sum((line.quantity * line.unit_price for line in lines), Decimal("0"))
```

تابع محاسبه فقط از ورودی‌ها استفاده می‌کند و اثر جانبی ندارد؛ نوشتن تست آن ساده است.

## دام‌ها و سوءبرداشت‌ها

- الگو را از روی ترند انتخاب‌کردن، پیش از شناخت فشار طراحی.
- یک ساختار را همه‌جا تحمیل‌کردن؛ حتی وقتی پیچیدگی دامنه و چرخهٔ تغییر متفاوت است.
- نمونهٔ واقعی یک سازمان را بدون workload، تیم، هزینه و تاریخچه کپی‌کردن.
- بهینه‌سازی برای شاخص ساده‌ای مثل تعداد کلاس، سرویس یا خط کد به‌جای هدف محصول.

## کوییز جامع فصل با پاسخ‌نامه

۱. تابع مالیات هم زمان جاری را می‌خواند، هم نرخ را از دیتابیس می‌گیرد و هم نتیجه را ذخیره می‌کند. چگونه بازطراحی می‌کنی؟
   - پاسخ: ورودی‌های متغیر مثل زمان و نرخ را بیرون گرد می‌آورم؛ محاسبه را تابعی خالص نگه می‌دارم؛ ذخیره‌سازی را در use case یا adapter می‌گذارم. آزمون مرز زمانی و rounding لازم است.
۲. فراخوانی process(order, true, null) را واضح کن.
   - پاسخ: اول معنای true و null را کشف می‌کنم؛ حالت‌ها را با نام پارامتر، enum/Option یا operationهای جدا بیان می‌کنم. در قرارداد JSON، absent و null را جدا تعریف می‌کنم.
۳. آیا باید همهٔ تابع‌ها زیر ده خط باشند؟
   - پاسخ: خیر؛ اندازه معیار قطعی نیست. انسجام، سطح انتزاع، دلایل تغییر، مسیرهای تصمیم و آزمون‌پذیری را می‌سنجم.
۴. یک آزمون وقتی جدا اجرا می‌شود پاس است و در suite شکست می‌خورد. چه می‌کنی؟
   - پاسخ: shared state، ترتیب اجرا، دادهٔ باقی‌مانده، ساعت، randomness، concurrency و cleanup را بررسی و علت وابستگی را حذف می‌کنم.
۵. آیا کد تکراری را همیشه به تابع مشترک منتقل می‌کنی؟
   - پاسخ: نه؛ بررسی می‌کنم آیا تکه‌ها یک قاعده و actor و مسیر تغییر مشترک دارند. شباهت نحوی به‌تنهایی دلیل یکی‌کردن نیست.
۶. چرا تغییر قالب‌بندی را از refactor رفتاری جدا نگه می‌داریم؟
   - پاسخ: تا reviewer تغییر منطقی را پیدا کند، blame دقیق بماند و بازگشت تغییر هدفمند باشد.
## تمرین عملی

یک سیستم کوچک فروش، رزرو یا صدور فاکتور انتخاب کن. برای سه نیازمندی پرتغییر، نقشهٔ مسئولیت‌ها را بکش؛ یک قرارداد و آزمون بنویس؛ سپس توضیح بده چرا فعلاً از مرز انتخاب‌شده استفاده می‌کنی و چه نشانه‌ای باعث می‌شود آن را تغییر بدهی. تمرین را با [قالب ADR](https://adr.github.io/) ثبت کن.
