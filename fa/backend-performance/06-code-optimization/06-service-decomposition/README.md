# ۶.۶ — تجزیهٔ سرویس و اثر آن بر کارایی

**زبان:** فارسی · [English version](../../../../en/backend-performance/06-code-optimization/06-service-decomposition/README.md)


تجزیه یعنی جابه‌جا کردن بخشی از رفتار به یک مرز مستقل، معمولاً فرایند یا سرویس جدا. انگیزه می‌تواند مقیاس مستقل، جداسازی مصرف منابع یا مالکیت روشن باشد. **Microservices راه‌حل پیش‌فرض کارایی نیست**؛ مرز شبکه هزینهٔ Serialization، رفت‌وبرگشت، خطای جزئی و عملیات را اضافه می‌کند.

**هدف یادگیری:** بیان دلیل قابل‌اندازه‌گیری برای استخراج، محاسبهٔ هزینهٔ مرز، تشخیص distributed monolith و طراحی مهاجرت محدود. پیش‌نیاز: [مسیر بحرانی](../04-critical-paths/README.md)، HTTP و صف. بررسی منابع: **۲۰۲۶-۱۱-۱۰**.

## پیش‌نیازهای همین درس

فرایند (Process) برنامه‌ای در حال اجرا با منابع و فضای اجرایی خودش است. ماژول مرز کد داخل یک فرایند دارد؛ سرویس مستقل مرز شبکه و شکست جداگانه نیز دارد. صف کار را برای مصرف بعدی نگه می‌دارد. یک hop یعنی عبور درخواست از یک مرز ارتباطی دیگر و معمولاً زمان شبکه، encode/decode و امکان خطای تازه به مسیر اضافه می‌کند. «مونولیت توزیع‌شده» حالتی است که اجزا جدا deploy شده‌اند ولی برای تغییر یا پاسخ به فراخوانی‌های هم‌زمان و هماهنگ وابسته می‌مانند؛ مرز فرایند به‌تنهایی استقلال معماری نمی‌آورد.

## مدل ذهنی: مرز منطقی در برابر مرز اجرا

| گزینه | فایدهٔ محتمل | هزینه و محدودیت |
| --- | --- | --- |
| ماژول در همان برنامه | مرز کد و رابط روشن، فراخوانی محلی | مقیاس و Failure domain عمدتاً مشترک |
| Worker جدا | جداسازی کار سنگین/قابل‌تأخیر | صف، ذخیرهٔ پایدار و تأخیر تکمیل |
| سرویس مستقل | مقیاس و rollout مستقل | شبکه، قرارداد نسخه و عملیات بیشتر |

راهنمای رسمی [Azure Microservices](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/microservices) مزیت مقیاس مستقل و چالش پیچیدگی، ارتباط و سازگاری داده را کنار هم شرح می‌دهد. مرز مناسب از رفتار، داده و الگوی تغییر می‌آید؛ هر تابع یا جدول لازم نیست سرویس جدا شود. اگر چند سرویس فقط با استقرار هم‌زمان و تراکنش سراسری کار می‌کنند، استقلال وعده‌داده‌شده به دست نیامده است.

1. با Profile ثابت کنید کدام بخش برای بقیه صف یا رقابت می‌سازد؛ مشکل کندی یک Query با تعداد سرویس حل نمی‌شود.
2. ابتدا مرز ماژول و قرارداد داده را روشن کنید. امکان محدود کردن concurrency یا استفاده از worker در همان Stack را بسنجید.
3. سود مقیاس/جداسازی را با hop، Serialization، retry، اتصال، observability و هزینهٔ تیم مقایسه کنید.
4. مالک داده، سازگاری، idempotency و نسخهٔ قرارداد را مشخص کنید؛ دسترسی مستقیم همهٔ سرویس‌ها به جداول یکدیگر استقلال را ضعیف می‌کند.
5. یک مسیر محدود را مرحله‌ای استخراج کنید و بار/صحت را مقایسه کنید. shadow خواندن می‌تواند مفید باشد؛ shadow نوشتن بدون کنترل side effect خطر تکرار عمل دارد.

## مثال حل‌شده: گزارش سنگین کنار checkout

**مدل آموزشی:** برنامهٔ واحد ۱۰۰ درخواست checkout/s با ۵ ms CPU و ۱۰ گزارش/s با ۲۰۰ ms CPU دارد. تقاضای CPU به‌ترتیب ۰٫۵ و ۲ CPU-second/s، در مجموع ۲٫۵ است. ظرفیت اختصاص‌یافته ۲ core است؛ در عمل باید صف، سهم زمان و overhead هم بررسی شود. محدودیت ظرفیت را با افزودن یک hop شبکه رفع نمی‌کنیم.

گزینهٔ اول محدود کردن گزارش، بهینه‌سازی الگوریتم یا اجرای worker با سهم منابع جداست. گزینهٔ دوم استخراج گزارش برای مقیاس مستقل است؛ همچنان تقریباً همان ۲ CPU-second/s محاسبه لازم است، اما فشار از منابع checkout جدا می‌شود. اگر خروجی گزارش لازم نیست هم‌زمان برگردد، قرارداد `202 Accepted` و وضعیت Job می‌تواند انتظار را از پاسخ تعاملی بردارد؛ این به معنی تکمیل گزارش در لحظهٔ پذیرش نیست.

برای یک مسیر همگام دیگر، فرض کنید یک فراخوانی محلی ۵ ms است. استخراج آن با هزینهٔ افزودهٔ فرضی ۶ ms برای شبکه و encode/decode، حتی با ثابت ماندن محاسبه، آن بخش را به ۱۱ ms می‌رساند. این عدد اندازه‌گیری واقعی نیست؛ مدل نشان می‌دهد استقلال استقرار ممکن است با افزایش latency همراه شود. آن را برای همان محیط بسنجید.

## تمرین و انتظار

برای سرویس فروش فرضی سه قابلیت «checkout»، «ساخت گزارش ماهانه» و «دریافت نام مشتری» را روی کاغذ رسم کنید. نرخ، CPU، وابستگی داده‌ای و نیاز همگام هرکدام را بنویسید. سپس سه طراحی ماژول، worker و سرویس جدا را مقایسه کنید. **راه‌حل نمونه:** از اعداد مثال، checkout برابر <span dir="ltr">100 × 5 ms = 0.5 CPU-second/s</span> و گزارش برابر <span dir="ltr">10 × 200 ms = 2 CPU-second/s</span> است. گزارش <span dir="ltr">2 / (0.5 + 2) = 80%</span> تقاضای CPU این دو را می‌سازد، پس ابتدا محدودکردن سهم منابع یا Worker جدا را می‌سنجیم؛ سرویس جدا تنها وقتی لازم است که مقیاس یا rollout مستقل ارزش هزینهٔ شبکه و عملیات را داشته باشد. دریافت نام برای ۱۰۰ آیتم، اگر جداگانه فراخوانی شود، ۱۰۰ hop می‌سازد؛ یک Batch یا واکشی محلی/ترکیبی را مقایسه کنید. این محاسبه فرضی است و انتخاب نهایی به بار واقعی وابسته است.

## شاهد واقعی

در **۶ مارس ۲۰۲۳** [Discord](https://discord.com/blog/how-discord-stores-trillions-of-messages) data serviceهایی میان API monolith و DB قرار داد تا درخواست‌های هم‌زمانِ یک داده را ادغام کند؛ routing هم‌کلید نیز به این هدف کمک کرد. هدف مشخص، محافظت از DB در برابر ترافیک داغ بود. این نمونه شاهد استخراج هدفمند است و سود عمومی هر تجزیه‌ای را ثابت نمی‌کند؛ مهاجرت DB و تغییرات دیگر هم در داستان حضور دارند.

## شکست‌ها و علائم

| شکست | علامت عملیاتی | اقدام |
| --- | --- | --- |
| مرز بسیار ریز | Trace پر از hop کوتاه و سریال | رابط درشت‌تر و Batching متناسب |
| DB مشترکِ گلوگاه | تعداد سرویس بیشتر، DB همچنان اشباع | برنامهٔ داده و Query را اصلاح کن |
| Retry در همهٔ لایه‌ها | amplification هنگام اختلال | مالک Retry و بودجهٔ مشترک |
| استقرار وابسته | هر تغییر نیاز به rollout هم‌زمان دارد | قرارداد سازگار و مالکیت روشن |
| نبود Trace/مالک on-call | علت تأخیر نامشخص | observability و مسئولیت پیش از استخراج |
| side effect دوگانه در مهاجرت | پرداخت/اعلان تکراری | کنترل مسیر نوشتن و dedup پایدار |

تجزیه هزینهٔ پایهٔ چند فرایند، deployment و اتصال را نیز بالا می‌برد. برای تیم کوچک یا بار کم، ماژول روشن در برنامهٔ واحد می‌تواند هزینه و زمان تغییر کمتری داشته باشد. برای workload ناهمگون با شواهد رقابت منابع، استقلال مقیاس می‌تواند مفید باشد؛ این تصمیم با نتیجهٔ بار و عملیات سنجیده می‌شود.

### چک‌لیست عملیاتی

- [ ] محدودیتی که مرز جدید حل می‌کند با Metric/Profile ثبت شده است.
- [ ] گزینهٔ ماژول، محدودیت هم‌زمانی و worker مقایسه شده‌اند.
- [ ] hopها، قرارداد، مالک داده و سازگاری روشن‌اند.
- [ ] Deadline، cancellation، idempotency و خطای جزئی طراحی شده‌اند.
- [ ] هزینهٔ اتصال، حافظهٔ پایه، استقرار، Trace و on-call برآورد شده است.
- [ ] rollout محدود، بررسی صحت و بازگشت بدون side effect تکراری ممکن است.

## آزمون

1. آیا جدا کردن سرویس همان محاسبه را خودبه‌خود کم می‌کند؟
2. تفاوت مرز ماژول و مرز فرایند چیست؟
3. چرا دریافت جداگانهٔ هر فیلد از سرویس دیگر می‌تواند کند باشد؟
4. اگر DB گلوگاه است و همهٔ سرویس‌ها همان Query را می‌فرستند، چه اتفاقی محتمل است؟
5. پاسخ `202` برای گزارش چه چیزی را تضمین نمی‌کند؟
6. چه چیزی استخراج Discord را به تصمیم قابل‌فهمی تبدیل می‌کند؟

### پاسخ تشریحی

1. خیر؛ ممکن است همان کار با overhead بیشتر انجام شود. سود می‌تواند جداسازی ظرفیت باشد، نه کاهش کار.
2. ماژول مرز منطقی در همان اجرا دارد؛ فرایند جدا هزینهٔ ارتباط، شکست مستقل و عملیات اضافه می‌کند.
3. تعداد رفت‌وبرگشت و Serialization افزایش می‌یابد؛ تأخیرهای کوچک در زنجیره جمع می‌شوند.
4. DB همچنان اشباع می‌ماند و هم‌زمانی بیشتر ممکن است وضعیت را بدتر کند؛ باید بار و Query اصلاح شوند.
5. تکمیل موفق در لحظهٔ پاسخ را تضمین نمی‌کند؛ پذیرش باید با ذخیرهٔ Job و قرارداد وضعیت تعریف شود.
6. محدودیت روشنِ ترافیک داغ و سازوکار مشخصِ coalescing/routing؛ نام Microservices به‌تنهایی دلیل نیست.

## جمع‌بندی

استخراج سرویس فقط وقتی توجیه دارد که محدودیت مشخصی مثل رقابت منابع یا نیاز به مقیاس مستقل را حل کند. ماژول و Worker را با همان معیار بسنجید؛ hop، داده، Deadline، idempotency و مالکیت عملیات هزینه‌های مرز مستقل‌اند. پذیرش کار پس‌زمینه را با تکمیل آن یکی نگیرید.

- [English: Azure Microservices Architecture](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/microservices): کاربردها، هزینه‌ها و انتخاب مرز.

- [English: Martin Fowler, Microservices](https://martinfowler.com/articles/microservices.html): انگیزه‌های تفکیک و هزینهٔ مرزها در تجربهٔ تیم‌ها؛ مقالهٔ تحلیلی است، نه استاندارد یا نتیجهٔ اندازه‌گیری‌شده برای این سناریو.

- [English: Discord message storage](https://discord.com/blog/how-discord-stores-trillions-of-messages): استخراج لایهٔ داده با هدف کاهش فشار DB؛ همراه تغییرات دیگر.
