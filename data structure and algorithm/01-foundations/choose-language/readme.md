# انتخاب زبان برای تمرین

> مسیر: [فصل ۱ — پایه‌ها و تحلیل الگوریتم](../readme.md) · پیش‌نیاز پیشنهادی: فصل ۱ و مبانی برنامه‌نویسی · [English](readme.en.md)

## پیش‌نیازها و نقشهٔ ذهنی

هیچ زبان خاصی لازم نیست. ابتدا مفهوم را به‌عنوان یک قرارداد ببین، سپس نمایش حافظه و عملیات را دنبال کن. هدف حفظ‌کردن نام نیست؛ باید بتوانی برای یک ورودی کوچک، state را بعد از هر گام بنویسی.

## ایده از پایه

ایدهٔ الگوریتم مستقل از syntax است؛ برای یادگیری یک زبان تمرین ثابت انتخاب کن تا انرژی روی حل مسئله بماند. معیار، محبوبیت جهانی نیست: آیا کد را می‌توانی اجرا، debug و با collectionهای اصلی پیاده کنی؟

## مدل، قرارداد و ناوردا

زبان را با هدف انتخاب کن: آموزش و نمونه‌سازی (Python)، کنترل و STL (C++), ecosystem سازمانی (Java/C#)، سادگی backend/concurrency (Go)، وب (JavaScript)، memory safety systems (Rust)، اسکریپت خوانا (Ruby). محیط مسابقه/دانشگاه یا تیم ممکن است زبان مشخص بخواهد.

ناوردا (invariant) جمله‌ای است که در تمام مراحل الگوریتم باید درست بماند. نوشتن آن پیش از کدنویسی، هم به اثبات درستی کمک می‌کند و هم خطاهای مرزی را آشکار می‌سازد.

## الگوریتم یا عملیات گام‌به‌گام

انتخاب عملی: ۱) اگر دوره/کار زبان مقرر دارد، همان. ۲) syntax پایه را یاد بگیر. ۳) API array/list, map/set, stack/queue و heap را تمرین کن. ۴) چند هفته ثابت بمان. ۵) complexity، integer range، equality و mutation را از مستندات همان نسخه بررسی کن.

در پیاده‌سازی واقعی، قرارداد ورودی/خروجی را دقیق تعریف کن: رفتار ورودی تهی، مقدار تکراری، عنصر پیدا‌نشده و ظرفیت تمام‌شده باید روشن باشد.

## اجرای حل‌شده با ردگیری

برای BFS، Python با deque و C# با Queue هر دو الگوریتم یکسان دارند؛ ساختار صف API متفاوت است. زمان الگوریتم O(V+E) است ولی `list.pop(0)` پایتون یا `Array.RemoveAt(0)` انتخاب ساختاری نامناسب می‌تواند پیاده‌سازی را کند کند.

برای تمرین، جدولی با ستون‌های «گام»، «اندیس/اشاره‌گر»، «بخش فعال»، «تغییر state» و «دلیل» بساز. این روش به‌خصوص برای الگوریتم‌های درجا و تقسیم‌و‌غلبه جلوی پرش ذهنی را می‌گیرد.

## چرا درست است؟

منطق مسئله باید از semantics زبان جدا بماند؛ ترجمهٔ الگوریتم بین زبان‌ها، قراردادهای null, overflow, mutation, comparator و integer division را حفظ کند.

اثبات معمولاً سه بخش دارد: (۱) آغاز—ناوردا پیش از نخستین گام درست است؛ (۲) نگهداری—هر گام آن را حفظ می‌کند؛ (۳) پایان—شرط توقف همراه invariant جواب موردنیاز را نتیجه می‌دهد. اگر یکی از این سه بخش نامشخص است، هنوز درک الگوریتم کامل نشده است.

## تحلیل زمان و حافظه

زبان compile/interpreted عامل ثابت مهم است، اما معمولاً مرتبهٔ رشد و انتخاب structure اهمیت بیشتری دارند. برای algorithm challenge پیچیدگی کتابخانه و runtime، memory limit و نوع عدد را بررسی کن.

در Big-O ورودی را تعریف کن (مثلاً n تعداد عناصر)، نوع حالت را نام ببر (بهترین/میانگین/بدترین)، و فضای کمکی را از حافظهٔ خود ورودی جدا کن. مرتبهٔ رشد زمان واقعی بر حسب ثانیه نیست؛ cache، تخصیص حافظه و ثابت‌های پیاده‌سازی هم اثر دارند.

## کاربرد واقعی و انتخاب مناسب

مصاحبه و یادگیری با یک زبان؛ کار صنعتی با language/toolchain تیم؛ prototype با زبان بیان‌پذیر؛ systems programming با memory control. زبان مناسب وابسته به هدف است.

پیش از انتخاب بپرس: چه عملیاتی پرتکرارند؟ آیا ترتیب مهم است؟ دادهٔ ورودی چه اندازه است؟ آیا محدودیت حافظه، latency بدترین‌حالت یا thread-safety داریم؟ ساختار خوب برای workload نامناسب می‌تواند انتخاب بدی باشد.

## خطاهای رایج و edge caseها

هر هفته زبان عوض نکن؛ زبان «سریع» الگوریتم غلط را نجات نمی‌دهد. APIهای مختلف یک نام ممکن است performance متفاوت داشته باشند. road map زنده تغییر می‌کند؛ گره‌های آن پیشنهاد هستند، نه الزام.

حالت‌های مرزی را جداگانه بررسی کن: ورودی خالی، یک عضو، همهٔ اعضا برابر، هدف غایب، حداقل/حداکثر مقدار و اندازهٔ بزرگ. سرریز عدد صحیح در محاسبهٔ اندیس/ظرفیت نیز بسته به زبان مهم است.

## تمرین‌های مرحله‌ای

۱) هدف را از بین دانشگاه/مصاحبه/پروژه انتخاب و زبان را با دلیل بنویس. ۲) BFS و min-heap را در زبان منتخب پیدا/پیاده کن. ۳) complexity عملیات اصلی collectionها را در مستندات ثبت کن.

برای هر تمرین، اول پاسخ ساده و درست بنویس، بعد پیچیدگی را حساب کن، سپس edge case اضافه کن. تمرین را با دست‌کم یک ورودی کوچک ردگیری کن و خروجی را با انتظار مستقل مقایسه کن.

## آزمون جامع با پاسخ تشریحی

ابتدا پاسخ‌ها را نخوان؛ جواب را با استدلال بنویس، سپس توضیح را مقایسه کن.

1. **پرسش:** آیا زبان، ایدهٔ الگوریتم را عوض می‌کند؟
   **پاسخ تشریحی:** نه؛ semantics/API پیاده‌سازی را عوض می‌کند.
2. **پرسش:** چند structure باید بلد باشی؟
   **پاسخ تشریحی:** array/list، map/set، stack/queue و priority queue.
3. **پرسش:** چرا زبان ثابت؟
   **پاسخ تشریحی:** کاهش بار syntax و تمرکز روی reasoning.
4. **پرسش:** چه هزینهٔ API مهم است؟
   **پاسخ تشریحی:** مثلاً حذف اول Array ممکن است O(n) باشد.
5. **پرسش:** زبان انتخابی باید بر چه بنا شود؟
   **پاسخ تشریحی:** هدف، دسترسی به runtime و توان debug/تمرین.

## راهنمای بازگویی از حافظه

بدون نگاه به متن، ایده، پیش‌شرط، invariant، یک ردگیری واقعی، پیچیدگی، edge case و یک کاربرد را در چند دقیقه روی کاغذ توضیح بده. اگر فقط pseudocode را حفظی می‌نویسی اما دلیل درستی یا محدودیت‌ها را نمی‌دانی، یک بار دیگر بخش‌های invariant و خطاها را مرور کن.
