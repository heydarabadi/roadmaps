# انتخاب بازبین و برنامهٔ بررسی

**زبان:** فارسی · [English](../../en/03-reviewer/02-reviewer-selection/README.md)

> مسیر: [فصل ۳ — آماده‌سازی بازبین](../README.md) · [فهرست دوره](../../README.md)

## آموزش

بهترین reviewer کسی است که دربارهٔ تغییر مشخص تخصص داشته باشد و بتواند در زمان معقول پاسخ دهد. گاهی backend، database، security یا product designer هرکدام بخشی را بررسی می‌کنند. CODEOWNERS و approval rules کمک می‌کنند مالکیت و حوزهٔ تخصص معلوم باشد، اما خودشان صحت منطق را تضمین نمی‌کنند.

Reviewer پیش از شروع، سطح بررسی و سؤال‌های مهم را مشخص کند. برای typo ممکن است بررسی کوتاه کافی باشد؛ migration، auth یا dependency جدید باید عمیق‌تر ارزیابی شوند. اگر وقت نداری، زود دریافت را تایید و زمان/جایگزین اعلام کن. Pair programming یا گفت‌وگوی هم‌زمان برای طراحی مبهم مفید است، ولی نتیجهٔ تصمیم مهم را در PR ثبت کن.

تیم باید review را در برنامهٔ کاری جا بدهد، نه این‌که آن را کار اضافه‌ای بداند که هیچ‌وقت فرصت ندارد.

review بخش ناآشنای codebase می‌تواند دانش بین تیمی را پخش کند، به شرط آن‌که بازبین متخصص در موضوع حساس حاضر باشد و هدف یادگیری با مسئولیت امنیت/کیفیت اشتباه نشود. نویسنده می‌تواند پیش از پایان توسعه هم برای طرح یا قسمت مبهم feedback بخواهد؛ این کار معمولاً از انتظار برای PR کامل کم‌هزینه‌تر است.

## روند پیشنهادی

1. فایل‌ها و حوزه‌های تغییریافته را شناسایی کن.
2. یک reviewer اصلی و متخصصان لازم را انتخاب کن.
3. checklist متناسب با تغییر بساز.
4. در صورت کمبود وقت یا دانش زود اطلاع بده.
5. بحث هم‌زمان را با خلاصهٔ تصمیم ثبت‌شده تمام کن.

## مثال کاربردی

تغییر migration ممکن است به backend reviewer و database owner نیاز داشته باشد. یک نفر روی رفتار query تمرکز می‌کند و دیگری هزینه و ایمنی migration را می‌سنجد.

## خطاهای رایج

reviewerهای زیاد را پیش‌فرض نکن؛ CODEOWNERS قدیمی را قطعی ندان؛ PR را بی‌خبر معطل نگذار؛ review را فقط پس از پایان همهٔ کارها برنامه‌ریزی نکن.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** reviewer خوب چه ویژگی دارد؟

   1. عنوان شغلی بالا
   2. تخصص مرتبط و امکان پاسخ به‌موقع
   3. همیشه مدیر
   4. فقط صاحب CODEOWNERS حتی اگر unavailable باشد

**پاسخ:** 2 — ارتباط تخصص و دسترس‌پذیری مهم است.

### پرسش 2

**سؤال:** CODEOWNERS چه می‌کند؟

   1. تضمین کیفیت
   2. کمک به درخواست review/approval از مالکین
   3. جایگزین تست
   4. تصمیم خودکار طراحی

**پاسخ:** 2 — مالکیت مسیر review را هدایت می‌کند.

### پرسش 3

**سؤال:** اگر review کامل نمی‌شود چه باید کرد؟

   1. سکوت
   2. زمان یا reviewer جایگزین را زود اعلام کرد
   3. approve حدسی
   4. تا آخر هفته صبر کرد

**پاسخ:** 2 — شفافیت از صف نامعلوم جلوگیری می‌کند.

### پرسش 4

**سؤال:** Pair review چه زمانی کمک می‌کند؟

   1. برای حذف مستندات
   2. برای رفع ابهام پیچیده با گفت‌وگوی زنده
   3. برای دورزدن policy
   4. برای تغییر همهٔ کد

**پاسخ:** 2 — تعامل هم‌زمان می‌تواند چرخهٔ فهم را کوتاه کند.

## آموزش عمیق: چه کسی و با چه عمقی review کند؟

### انتخاب بازبین

reviewer را بر مبنای خطر و دانش مرتبط انتخاب کن، نه فقط سلسله‌مراتب سازمانی. برای تغییر backend ممکن است owner همان سرویس مناسب باشد؛ برای migration، متخصص دیتابیس؛ برای مجوز یا cryptography، security reviewer؛ برای رفتار UI، طراح محصول. گاهی یک بازبین اصلی، یک حوزه را پوشش می‌دهد و متخصص دوم فقط قسمت محدود خود را می‌بیند.

سه پرسش برای انتخاب:

1. چه کسی می‌تواند دربارهٔ رفتار و معماری این بخش قضاوت کند؟
2. کدام تخصص برای خطر مشخص لازم است؟
3. چه کسی می‌تواند در زمان معقول پاسخ دهد؟

CODEOWNERS و قواعد approval مسیریابی را کمک می‌کنند، اما مالکیت فایل ضمانت کیفیت نیست. فایل CODEOWNERS ممکن است قدیمی باشد، owner در دسترس نباشد یا تغییر از چند حوزه عبور کند. اگر reviewer اصلی متخصص نیست، باید این محدودیت را به رسمیت بشناسد و کمک بخواهد، نه این‌که approve را به‌جای دانش استفاده کند.

### تعیین عمق

برای اصلاح املایی، diff، pipeline و نمایش نهایی ممکن است کافی باشد. برای تغییر authentication، schema یا پردازش پول، معیار review باید شامل منطق، تست منفی، compatibility، اثر deploy، امنیت و راه بازگشت شود. depth از blast radius، حساسیت و برگشت‌پذیری می‌آید؛ نه از این‌که نویسنده تازه‌کار یا ارشد است.

عمق بیش‌ازحد هم هزینه دارد. اگر هر تغییر trivial چند approval و چک‌لیست صدبندی بخواهد، تیم فرایند را دور می‌زند. تعیین سطح یعنی وقت reviewer را روی جاهایی بگذاریم که خطای احتمالی واقعاً پیامد دارد.

### تقسیم review، pair و cross-learning

اگر چند حوزه درگیرند، comment را صاحب همان حوزه بررسی کند؛ review همه‌چیز را به یک نفر نسپار. Pair یا جلسهٔ کوتاه برای ابهام معماری مفید است و feedback زودهنگام می‌تواند جهت غلط را پیش از PR کامل پیدا کند. اما خروجی تصمیم مهم را در PR یا design record ثبت کن تا بعداً قابل‌ردیابی باشد. آشناشدن با بخش ناآشنا فرصت یادگیری است، ولی به معنی واگذاری کنترل امنیتی به فرد بی‌تخصص نیست.

### مثال و تصمیم

PR یک dependency جدید به سرویس حساس اضافه می‌کند، query دیتابیس را عوض می‌کند و صفحهٔ جدیدی می‌سازد. بازبین backend می‌سنجد الگوی سرویس رعایت شده؛ database owner هزینه و migration را؛ security مسئولیت dependency و ورودی‌ها را؛ طراح/مالک محصول تجربهٔ خطا را. اگر تیم کوچک است، همهٔ نقش‌ها شاید جدا نباشند؛ نام خطرها و پوشش هرکدام را در checklist بنویس.

### تمرین

برای PRی که JWT validation، migration و UI دارد، نقش reviewer اصلی و دو تخصص مکمل را انتخاب کن. بنویس هر نفر چه یک یا دو سؤال مشخصی را جواب می‌دهد. پاسخ خوب «سه senior» نیست؛ پاسخ خوب حوزه و تصمیم هر نفر را نام می‌برد.

### زمان پاسخ و رفتار تیم

اگر review را کامل نمی‌کنی، زود receipt بده، زمان تقریبی یا جایگزین اعلام کن. سکوت باعث می‌شود نویسنده نداند آیا PR دیده شده یا باید دنبال متخصص دیگری بگردد. زمان پاسخ باید توافق تیم باشد، نه الزام ساختگی برای approve سریع.
