# لایهٔ کاربرد و Microservices

## هدف یادگیری

- مسئله‌ای را که این مفهوم حل می‌کند تعریف کنی.
- برای یک سامانهٔ نمونه انتخاب را با trade-off توضیح بدهی.
- رفتار سیستم را هنگام اختلال پیش‌بینی کنی.

## ایدهٔ مرکزی

لایهٔ application use caseها را هماهنگ می‌کند؛ microservice مالکیت مستقل می‌سازد ولی هزینهٔ شبکه و عملیات را زیاد می‌کند.

## نقشهٔ مفهومی

نیاز کسب‌وکار ← قرارداد بار/کیفیت ← انتخاب الگو ← نقطهٔ شکست ← مشاهده و بازیابی

## توضیح کامل

مرز سرویس را از دامنه و ownership تیم تعیین کن، نه تعداد خط کد. قرارداد و استقرار مستقل لازم‌اند؛ هر فراخوانی دوردست timeout، retry، ورژن ناسازگار و failure جزئی می‌آورد. Modular monolith گزینهٔ شروع خوبی است: مرزها داخل کد روشن، امکان جداسازی آینده حفظ می‌شود.

## درس گام‌به‌گام

### معماری monolith و microservice

Monolith یک برنامه است که معمولاً با یک artifact و فرایند یا deployment منتشر می‌شود. Monolith می‌تواند ماژولار باشد: مرزهای داخلی، interfaceها و مالکیت داده مشخص‌اند. Microservice یک قابلیت دامنه‌ای را در واحدی جداگانه اجرا و معمولاً مستقل deploy/scale می‌کند. تفاوت اصلی تعداد processها نیست؛ ownership، deployment، داده و failure boundary است.

سرویس مستقل می‌تواند با زبان/مقیاس مناسب خودش کار کند و تیم را از هماهنگی انتشار جدا کند. در مقابل، شبکه را وارد هر call می‌کند: latency، timeout، authentication، retry، version skew، tracing، deploy و incident response. تراکنش سادهٔ چند جدول ممکن است به saga، outbox، compensation و eventual consistency تبدیل شود. بنابراین microservice یک ابزار سازمان‌دهی سیستم و تیم است، نه صرفاً راه افزایش سرعت برنامه.

### مرز را از دامنه پیدا کن

به business capability و تغییرهایی که باهم انجام می‌شوند نگاه کن. در فروشگاه، کاتالوگ، سفارش، پرداخت و ارسال ممکن است مرزهای مناسبی باشند؛ اما اگر همیشه برای یک عملیات به‌صورت اتمیک باهم تغییر می‌کنند و یک تیم کوچک نگهداری‌شان می‌کند، جداسازی زودهنگام هزینه دارد. Bounded contextهای دامنه کمک می‌کنند معنای «مشتری»، «قیمت» و «سفارش» بین تیم‌ها مبهم نشود.

### دادهٔ هر سرویس و قرارداد

هر سرویس باید مالک write model خود باشد. دسترسی مستقیم همهٔ سرویس‌ها به یک schema، coupling پنهان می‌سازد؛ تغییر ستون می‌تواند چند deploy را هم‌زمان نیازمند کند. برای خواندن از دادهٔ سرویس دیگر، API یا event مصرف کن و freshness/consistency را مشخص کن. قرارداد باید versioned، محدود، قابل مشاهده و امن باشد. consumerها باید با فیلدهای افزوده و تغییرهای تدریجی سازگار بمانند.

### ارتباط همگام و ناهمگام

فراخوانی همگام برای نتیجهٔ فوری ساده است، اما dependency زنجیره‌ای می‌سازد. اگر API به سه سرویس با latencyهای 100، 150 و 200ms صدا بزند، پاسخ حداقل جمع زمان‌ها به‌علاوهٔ شبکه و queue است و هر خرابی می‌تواند مسیر را خراب کند. پیام ناهمگام coupling زمانی را کم و burst را جذب می‌کند، اما نتیجه دیرتر می‌رسد، تکرار و ترتیب مهم می‌شود و debugging نیاز به correlation id دارد.

### تراکنش بین سرویس‌ها

یک دیتابیس محلی می‌تواند چند تغییر را در transaction اتمیک انجام دهد. وقتی مراحل بین سرویس‌ها پخش‌اند، distributed transaction پیچیدگی و وابستگی قوی می‌آورد. Saga هر گام پایدار را انجام می‌دهد و در خطا عمل جبرانی دارد؛ جبران الزاماً اثر بیرونی را حذف نمی‌کند (مثلاً refund با bank transfer برگشت خودکار نیست). Outbox کمک می‌کند write محلی و انتشار event از هم جدا نشوند.

### چه زمانی جداسازی ارزش دارد؟

نشانهٔ مفید: تیم‌ها مرتباً برای release هم قفل می‌شوند؛ یک قابلیت بار یا SLO بسیار متفاوت دارد؛ مالکیت و مدل داده‌اش مستقل است؛ شکستش باید از بقیه ایزوله شود. نشانهٔ خطر: تیم کوچک، دامنهٔ ناپایدار، deployment و observability ضعیف یا DB مشترک با دسترسی آزاد. مسیر کم‌ریسک غالباً modular monolith، آزمون مرزها و جداسازی تدریجی با Strangler است.

### حداقل‌های عملیات سرویس

هر سرویس health/readiness، metrics، logs و traces، identity سرویس‌به‌سرویس، timeout/deadline، محدودیت connection و runbook می‌خواهد. قرارداد versioning و deploy باید rolling upgrade را تحمل کند. خطای یک سرویس را به‌صورت failure جزئی در نظر بگیر؛ فرض نکن همهٔ سرویس‌ها باهم بالا و پایین می‌شوند.

## مثال عملی

جداکردن سفارش از پرداخت ممکن است یک تراکنش ساده را به saga و consistency نهایی تبدیل کند؛ جداسازی را با نیاز انتشار یا scale توجیه کن.

## تجربهٔ عملی و تصمیم‌های معماری

نمونهٔ مهندسی برای مطالعه: [Netflix TechBlog](https://netflixtechblog.com/)

نمونهٔ عمومی معماری در مقیاس بالا: [Uber Engineering Tech Stack](https://www.uber.com/us/en/blog/tech-stack-part-one-foundation/) توضیح می‌دهد که رشد از monolith به سرویس‌های متعدد، discovery، routing و telemetry را به دغدغه‌های اصلی تبدیل کرد.

چندتیمه و scale متفاوت: microservice؛ تیم کوچک یا دامنهٔ نامعلوم: monolith ماژولار.

| تصمیم | چه زمانی مناسب است | کجا پرریسک می‌شود |
| --- | --- | --- |
| راه‌حل ساده | بار و دامنه محدود، رفتار قابل‌اندازه‌گیری | نیاز اثبات‌شدهٔ چندمنطقه‌ای یا حد ظرفیت |
| الگوی توزیع‌شده | نیاز روشن به جداسازی، ظرفیت یا دوام | پیچیدگی عملیاتی از سود بیشتر شود |

## دام‌ها و سوءبرداشت‌ها

- database مشترک وابسته؛ سرویس‌های ریز؛ نبود tracing؛ آغاز با Kubernetes پیش از مرز دامنه.
- عددهای مثال آموزشی‌اند؛ SLO و ظرفیت نهایی را از دادهٔ واقعی تعیین کن.

## آزمون کوتاه

1. کدام هزینه‌ها با microservice می‌آیند؟
2. چرا modular monolith شروع معقولی است؟
3. مرز سرویس را با چه شاهدی توجیه می‌کنی؟

### پاسخ‌نامهٔ فشرده

1. شبکه، failure جزئی، versioning، tracing، deploy، امنیت و هماهنگی داده/تراکنش.
2. مرز ماژول‌های روشن و dependency کنترل‌شده را با هزینهٔ کمتر از شبکه می‌دهد؛ می‌توان بعداً جداسازی کرد.
3. ownership دامنه/تیم مستقل، cadence انتشار متفاوت یا الگوی scale/خرابی قابل تفکیک.

## تمرین

برای یک فروشگاه اینترنتی، مسیر درخواست این مفهوم را رسم کن. منبع حقیقت، مرز شبکه، رفتار شکست، دادهٔ حساس، معیار پایش و راه بازگشت را مشخص کن. سپس یک آزمون خرابی بنویس که بتواند فرض اصلی را رد کند.

## خلاصه

لایهٔ application use caseها را هماهنگ می‌کند؛ microservice مالکیت مستقل می‌سازد ولی هزینهٔ شبکه و عملیات را زیاد می‌کند. پیش از پیاده‌سازی رفتار عادی، حالت اختلال و معیار موفقیت را ثبت کن.
