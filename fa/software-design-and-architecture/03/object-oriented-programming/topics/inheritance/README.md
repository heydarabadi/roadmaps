## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

وراثت رفتار و نوع را از نوع پایه می‌گستراند و رابطهٔ «نوعی از» را بیان می‌کند؛ زیرنوع باید در جای پایه رفتار درست داشته باشد.

## مثال کاربردی

`PremiumMember` فقط وقتی از `Member` ارث ببرد که همهٔ عملیات مورد انتظار عضو عادی را حفظ کند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «برنامه‌نویسی شیءگرا» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** وراثت coupling و شکنندگی کلاس پایه می‌آورد؛ ترکیب و delegation اغلب منعطف‌ترند.
- **بازبینی:** وراثت را فقط برای reuse کد به کار نبر.

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: وراثت رفتار و نوع را از نوع پایه می‌گستراند و رابطهٔ «نوعی از» را بیان می‌کند؛ زیرنوع باید در جای پایه رفتار درست داشته باشد.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: `PremiumMember` فقط وقتی از `Member` ارث ببرد که همهٔ عملیات مورد انتظار عضو عادی را حفظ کند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: وراثت coupling و شکنندگی کلاس پایه می‌آورد؛ ترکیب و delegation اغلب منعطف‌ترند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: وراثت را فقط برای reuse کد به کار نبر.

## آموزش تکمیلی مستقل

#### وراثت (Inheritance)

وراثت می‌تواند type relation، reuse behavior و polymorphism بدهد؛ ولی «برای reuse» دلیل کافی نیست. رابطهٔ زیرنوع باید از دید مصرف‌کننده درست باشد: هرجا نوع پایه استفاده می‌شود، subtype هم باید قرارداد رفتاری را حفظ کند.

اگر subtype یک operation پایه را غیرفعال می‌کند، پیش‌شرط قوی‌تری می‌خواهد یا معنی نتیجه را عوض می‌کند، آن subtype احتمالاً جایگزین معتبر نیست. subclass به implementation پایه، ترتیب hookها و protected API وابسته می‌شود؛ تغییر base class می‌تواند وارثانی را بشکند که مالکیتشان دست تیم دیگری است.

نمونهٔ مستند تحلیلی: مربع از نظر ریاضی نوعی مستطیل است، اما object مستطیلی که عرض و ارتفاعش مستقل تغییر می‌کنند با مربع قابل‌جایگزینی نیست. اشتراک مفهومی همیشه قرارداد زیرنوعی درست نمی‌سازد.

برای رفتارهایی که به چند محور مستقل تغییر می‌کنند، composition مناسب‌تر است: سفارش یک DiscountPolicy می‌گیرد، نه اینکه برای هر ترکیب نوع مشتری و کمپین subclass تازه بسازیم.

## نمونهٔ کد مرحله‌ای

ارث‌بری رابطهٔ «نوعی از» است، نه راه پیش‌فرض برای reuse. زیرکلاس باید قرارداد پایه را حفظ کند و در هر جایی که پایه پذیرفته می‌شود درست کار کند. اگر subclass عملیات مهم را غیرفعال یا شرط تازه‌ای را تحمیل می‌کند، composition یا دو نوع مستقل مناسب‌تر است.
**تمرین با پاسخ:** آیا Square باید از Rectangle ارث ببرد؟ اگر مستقل بودن width و height بخشی از قرارداد Rectangle است، نه؛ تغییر یک ضلع square invariant دیگری می‌خواهد.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا تصمیم طراحی روشن بماند.

~~~csharp
public abstract class Shape
{
    public abstract decimal Area();
}

public sealed class Circle(decimal radius) : Shape
{
    public override decimal Area() => Math.PI * radius * radius;
}
~~~
