# ۶.۵ — انتخاب زبان و Runtime با اندازه‌گیری

**زبان:** فارسی · [English version](../../../../en/backend-performance/06-code-optimization/05-language-and-runtime-choices/README.md)


زبان و Runtime بر مدیریت حافظه، زمان‌بندی، کتابخانه‌ها و هزینهٔ توسعه اثر دارند. انتخابشان یک تصمیم مهندسی برای workload مشخص است. **Go و Rust گزینه‌اند**؛ هیچ‌کدام توصیهٔ عمومی برای سریع شدن همهٔ Backendها نیستند. ابتدا Profile و مسیر بحرانی را پیدا کنید، سپس محدودیت قابل‌انتساب به Runtime را بررسی کنید.

**هدف یادگیری:** جدا کردن محدودیت CPU/GC/I/O، طراحی مقایسهٔ منصفانه، سنجش هزینهٔ مهاجرت و انتخاب آزمایش محدود. پیش‌نیاز: [Profiling](../02-application-profiling/README.md) و [Critical paths](../04-critical-paths/README.md). بررسی منابع: **۲۰۲۶-۱۱-۱۰**.

## پیش‌نیازهای همین درس

Runtime برنامه را اجرا و مدیریت می‌کند؛ Garbage Collection (GC) حافظهٔ اشیای دیگرقابل‌دسترسی را بازیابی می‌کند، درحالی‌که JIT هنگام اجرا کد را بهینه می‌کند و ممکن است warmup بخواهد. در مدل Ownership، هر مقدار مالک و قواعد مشخصی برای قرض‌گرفتن دارد؛ این مدل می‌تواند برخی خطاهای حافظه را پیش از اجرا رد کند، اما کار CPU و انتظار I/O را حذف نمی‌کند. CPU-time زمان پردازنده و wall time زمان سپری‌شدهٔ درخواست است؛ زمان انتظار DB در اولی به همان مقدار شمرده نمی‌شود. این تفاوت برای تشخیص این‌که تغییر Runtime واقعاً کدام هزینه را هدف می‌گیرد، ضروری است.

## چه چیزی را مقایسه می‌کنیم؟

| شاهد موجود | فرضیهٔ قابل‌بررسی | گزینه‌های پیش از بازنویسی |
| --- | --- | --- |
| CPU در الگوریتم/Serialization | کد یا پیاده‌سازی داغ گران است | الگوریتم، کتابخانه، حذف تبدیل تکراری |
| Allocation و GC قابل‌توجه | ساخت اشیای موقت هزینه دارد | کاهش تخصیص، عمر داده و تنظیم سنجیده |
| انتظار DB غالب | Runtime بخش کوچک زمان است | Query، Pool، Batching، locality |
| حلقهٔ رویداد اشباع | کار CPU یا زمان‌بندی نامناسب | محدودیت کار، worker و fairness |
| نیاز به کنترل حافظه/latency خاص | مدل حافظه ممکن است مناسب نباشد | نمونهٔ محدود در مسیر اثبات‌شده |

در Go، GC هزینهٔ CPU و حافظه دارد و تنظیم آن مبادله ایجاد می‌کند؛ راهنمای رسمی [Go GC](https://go.dev/doc/gc-guide) توضیح می‌دهد چرا مصرف تخصیص و حافظهٔ زنده اهمیت دارند. پیش‌فرض یا مقدار یک تیم را برای بار دیگر کپی نکنید. در Rust، Ownership امکان تضمین‌های ایمنی حافظه بدون GC را می‌دهد؛ این رفتار در [کتاب رسمی Rust](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html) آمده است. نبود GC به معنای نبود تخصیص، قفل، صف یا latency بد نیست.

Runtimeهای دارای JIT ممکن است به warmup حساس باشند؛ build توسعه و release رفتار یکسان ندارند. مدل هم‌زمانی نیز به‌تنهایی throughput را تضمین نمی‌کند: کار CPU همچنان ظرفیت محدود دارد و async انتظار را سازمان می‌دهد، نه اینکه کار لازم را حذف کند.

## مثال حل‌شده: سقف سود مهاجرت

در یک درخواست **فرضی** ۲۵۰ ms، کار برنامه ۲۵ ms و انتظار وابستگی‌ها ۲۲۵ ms است. اگر نمونهٔ بازنویسی همان کار را در ۵ ms انجام دهد و همهٔ هزینه‌های دیگر ثابت بمانند، زمان کل ۲۳۰ ms است: فقط ۲۰ ms کاهش، حدود ۸٪. پنج برابر سریع شدن بخش محاسبه به معنای پنج برابر شدن کل سرویس نیست.

در مقابل، اگر هدف هزینهٔ CPU باشد، همان کاهش ممکن است با نرخ بالای درخواست ارزشمند باشد. برای ۱۰۰۰ درخواست/s، صرفه‌جویی ۲۰ ms CPU در هر درخواست، در مدل ایده‌آل ۲۰ CPU-second/s است؛ این فقط وقتی درست است که ۲۵ و ۵ ms واقعاً **CPU-time** باشند، نه زمان دیواری. هزینهٔ شبکهٔ مرز جدید، کتابخانه و Serialization را از آن کم کنید.

نسخهٔ فعلی را با تنظیم معقول خودش مقایسه کنید. Bench کردن Hash متفاوت، حذف اعتبارسنجی یا پاسخ ناقص مقایسهٔ زبان نیست. مجموعهٔ نماینده باید ورودی کوچک/بزرگ، کش سرد/گرم، رقابت و کار بلندمدت داشته باشد. Microbenchmark تابع فقط برای همان تابع شاهد است.

## تمرین و انتظار

برای نمونهٔ بالا، دو پیشنهاد بسازید: بهبود برنامه از ۲۵ به ۵ ms و کاهش انتظار از ۲۲۵ به ۱۵۰ ms. هزینهٔ تخمینی هر پیشنهاد را به نفرروز و خطر تغییر قرارداد ثبت کنید. **راه‌حل:** پیشنهاد اول <span dir="ltr">25 − 5 = 20 ms</span> از ۲۵۰ کم می‌کند، پس زمان ۲۳۰ ms است؛ پیشنهاد دوم <span dir="ltr">225 − 150 = 75 ms</span> کم می‌کند و زمان ۱۷۵ ms می‌شود. برای هدف latency، دومی در مدل <span dir="ltr">75 − 20 = 55 ms</span> سود بیشتر دارد. اگر ۲۵ و ۵ ms، CPU-time باشند، پیشنهاد اول صرفه‌جویی ۲۰ CPU-ms در هر درخواست می‌دهد؛ اگر wall time باشند، این صرفه‌جویی CPU را نمی‌توان نتیجه گرفت. سپس یک یادداشت تصمیم کوتاه بنویسید: فرضیه، معیار موفقیت، محدودهٔ آزمایش و شرط بازگشت.

## شواهد واقعی و حد تعمیم

در گزارش **۲۰۲۳** [ذخیرهٔ پیام Discord](https://discord.com/blog/how-discord-stores-trillions-of-messages)، Rust انتخاب data serviceها بود، اما تغییر معماری، کنترل ترافیک و ادغام درخواست‌ها نیز همراه آن بودند. نمی‌توان کل نتیجه را صرفاً به زبان نسبت داد. گزارش **۲۰۲۶** [Discord Voice](https://discord.com/blog/how-we-moved-discord-voice-to-the-edge) نیز مشکل starvation در سرویس Rust را شرح می‌دهد؛ درست بودن انتخاب زبان جای تحلیل زمان‌بندی را نمی‌گیرد.

## تناسب و هزینهٔ تصمیم

Go می‌تواند با ابزار و مدل اجرای مناسب نیاز یک تیم را برآورده کند؛ Rust ممکن است برای کنترل حافظه و مسیرهای حساس مناسب باشد. مهارت تیم، Driver، کتابخانهٔ پروتکل، ابزار مشاهده‌پذیری، زمان build، پاسخ‌گویی on-call و قابلیت استخدام جزو هزینه‌اند. انتخاب حفظ Stack موجود نیز می‌تواند نتیجهٔ درست اندازه‌گیری باشد. اگر تنها یک Kernel محاسباتی محدودیت دارد، مهاجرت همان بخش یا استفاده از کتابخانهٔ مناسب را با بازنویسی کل سرویس مقایسه کنید؛ FFI یا سرویس جدا خودش هزینه دارد.

| شکست | علامت | اقدام |
| --- | --- | --- |
| نسبت دادن انتظار DB به زبان | CPU پایین و latency ثابت | مسیر انتظار را اول اصلاح کن |
| Bench نابرابر | خروجی/مجوز/دقت متفاوت | semantics و شرایط برابر |
| حذف GC و فراموشی retention | RSS همچنان رشد دارد | عمر داده، Cache و صف را بررسی کن |
| بازنویسی بزرگ بدون بازگشت | رگرسیون و ناتوانی rollout | مسیر محدود، canary و نسخهٔ قبلی |
| تیم ناآشنا با Runtime | زمان رفع رخداد طولانی | آموزش، ابزار و مالکیت عملیاتی |

### چک‌لیست عملیاتی

- [ ] شاهد Profile نشان می‌دهد کدام هزینه به Runtime مرتبط است.
- [ ] الگوریتم، I/O و کار تکراری پیش از مهاجرت بررسی شده‌اند.
- [ ] صحت، quota، build و warmup در مقایسه همسان‌اند.
- [ ] CPU، RSS، tail، خطا و هزینهٔ کار موفق سنجیده می‌شوند.
- [ ] هزینهٔ کتابخانه، آموزش، نگه‌داری و on-call برآورد شده است.
- [ ] آزمایش محدود و مسیر Rollback وجود دارد؛ انتخاب زبان نتیجهٔ شواهد است.

## آزمون

1. پنج برابر سریع شدن ۱۰٪ از زمان، چرا کل پاسخ را پنج برابر سریع نمی‌کند؟
2. نبود GC چه چیزی را تضمین نمی‌کند؟
3. چرا build توسعه را نباید با build بهینهٔ زبان دیگر مقایسه کرد؟
4. در سرویس با ۹۰٪ انتظار DB، نخست چه چیزی را بررسی می‌کنید؟
5. آیا کاهش latency همیشه همان کاهش هزینهٔ CPU است؟
6. از تجربهٔ Discord چه ادعایی دربارهٔ Rust نمی‌توان کرد؟

### پاسخ تشریحی

1. ۹۰٪ دست‌نخورده می‌ماند؛ در مدل ثابت زمان جدید `0.9+0.1/5=0.92` برابر قبلی است.
2. نبود Allocation، contention، retention یا starvation را تضمین نمی‌کند؛ این مشکلات مستقل‌اند.
3. تنظیم کامپایل و ابزار تشخیصی اثر بزرگی دارند و مقایسهٔ نابرابر را به زبان نسبت می‌دهند.
4. Trace انتظار، Query، Pool، رفت‌وبرگشت و locality؛ مهاجرت زبان فقط بخش کمی را هدف می‌گیرد مگر شاهد دیگری باشد.
5. خیر؛ انتظار می‌تواند زمان دیواری را زیاد کند بدون CPU مشابه، و موازی‌سازی هم ممکن است منابع بیشتری بخواهد.
6. اینکه Rust به‌تنهایی علت همهٔ بهبودها یا درمان عمومی Backend است؛ چند تغییر هم‌زمان و شرایط خاص وجود داشت.

## جمع‌بندی

پیش از مهاجرت زبان، محدودیت را با Profile به CPU، حافظه، I/O یا زمان‌بندی نسبت دهید؛ الگوریتم و کار تکراری را هم بررسی کنید. مقایسه باید خروجی، بار، quota و build هم‌ارز داشته باشد. تصمیم را بر اساس latency، CPU، خطا و هزینهٔ توان نگه‌داری بگیرید، نه نام زبان.

## منابع تکمیلی اختیاری

برای فهم این درس یا حل تمرین، بازکردن پیوندهای زیر لازم نیست؛ آن‌ها برای مطالعهٔ بیشتر و بررسی رفتار مستند ابزارها هستند.

- [فارسی: Profiling و مدل Runtime در Go فارسی](https://book.gofarsi.ir/chapter-4/profiling/): توضیح تخصیص، GC و زمان‌بند برای بررسی فرضیهٔ محدودیت Runtime؛ درصدهای نمونهٔ مقاله را مقدار ثابت همهٔ برنامه‌های Go فرض نکنید. این منبع مقایسهٔ مستقیم زبان‌ها نیست؛ مقایسه باید با بار خودتان انجام شود.
- [English: Go GC Guide](https://go.dev/doc/gc-guide): مبادلهٔ حافظه/CPU و رفتار GC در Go.
- [English: Rust Ownership](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html): تعریف رسمی مدل حافظه، بدون ادعای برتری عمومی.
- [English: HotSpot Garbage Collection tuning guide](https://docs.oracle.com/en/java/javase/26/gctuning/index.html): اهداف و مصالحه‌های GC در JVM؛ گزینه‌های نسخهٔ Java 26 را به Runtimeهای دیگر تعمیم ندهید.
- [English: .NET performance and allocation guidance](https://learn.microsoft.com/en-us/dotnet/csharp/advanced-topics/performance/): توصیه به اندازه‌گیری مسیر داغ و ارزیابی Allocation/کپی در C#؛ راهکارهای زبان و Runtime آن Stack-specific هستند.
- [English: Discord message storage](https://discord.com/blog/how-discord-stores-trillions-of-messages): تصمیم Rust در یک زمینهٔ واقعی و همراه تغییرات معماری.
