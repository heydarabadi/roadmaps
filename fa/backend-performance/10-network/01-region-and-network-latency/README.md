# ۱۰.۱ — انتخاب منطقه و تأخیر شبکه

**زبان:** فارسی · [نسخهٔ انگلیسی](../../../../en/backend-performance/10-network/01-region-and-network-latency/README.md)  

**هدف یادگیری:** RTT را از ظرفیت لینک و زمان سرور جدا کنید، مسیر وابستگی را محاسبه کنید و محل برنامه/داده را با توزیع واقعی کاربران بسنجید. پیش‌نیاز: HTTP و Trace. بررسی منابع: **۲۰۲۶-۱۱-۱۱**؛ عددها آموزشی و اجرا‌نشده‌اند.

## مدل ذهنی و روش کار

درخواست از کاربر به API و سپس به DB، Cache یا سرویس دیگر می‌رود. نزدیکی جغرافیایی می‌تواند زمان انتشار را کم کند، اما Routing، Peering، ازدحام و صف هم اثر دارند. یک Region نزدیک روی نقشه الزاماً بهترین مسیر شبکه را ندارد. RTT نیز زمان یک‌طرفه نیست؛ نصف آن بدون فرض تقارن، اندازه‌گیری دقیق یک‌طرفه نمی‌دهد.

| اندازه‌گیری | چه چیزی می‌گوید؟ | محدودیت |
| --- | --- | --- |
| RTT مسیر | رفت‌وبرگشت در شرایط نمونه | Ping/ICMP ممکن است رفتار HTTP را نمایندگی نکند |
| DNS/Connect/TLS | هزینه کشف و آماده‌سازی اتصال | اتصال گرم این هزینه را برای هر درخواست تکرار نمی‌کند |
| TTFB از دید کاربر | زمان تا اولین بایت پاسخ | شبکه، صف و پردازش می‌توانند ترکیب شوند |
| زمان بدنه و Throughput | هزینه تحویل حجم پاسخ | loss، ظرفیت و کندی مصرف‌کننده مهم‌اند |
| Trace وابستگی | hopهای سریال و انتظار پایین‌دست | مرز ابزارگذاری و زمان خارج Trace را بررسی کنید |

۱. سهم کاربران، ISP/منطقه و Routeهای حساس را بنویسید. ۲. چند پنجره شامل اوج و اختلال را نمونه بگیرید. ۳. API، DB و تماس‌های بین‌منطقه‌ای را روی مسیر پاسخ رسم کنید. ۴. هم‌مکانی، کاهش call و کش مجاز را پیش از تکثیر سراسری مقایسه کنید. ۵. با ترافیک محدود، p95/p99، خطا و هزینه را بسنجید؛ درصدک‌های مناطق را میانگین نگیرید و آن را p95 کل ننامید.

## آموزش پایه: تأخیر از چه تکه‌هایی ساخته می‌شود؟

برای یک پاسخ ساده می‌توان مسیر را این‌طور تجزیه کرد:

<div dir="ltr" align="left">

```text
user
  -> [DNS, if needed]
  -> [TCP/TLS setup, if a new connection is needed]
  -> network to API
  -> API queue + processing
  -> serial calls to DB/cache/other services
  -> response transfer to user
```

</div>

براکت‌دارها ممکن است با اتصال گرم یا کش DNS تکرار نشوند. **Propagation** زمان حرکت سیگنال در مسیر است؛ **queueing** انتظار پشت کارهای دیگر؛ **processing** کار برنامه/پایگاه داده؛ **serialization** زمان تبدیل/ارسال بایت‌ها. برای شاخه‌های وابسته، زمان‌ها روی مسیر بحرانی جمع می‌شوند؛ برای دو شاخهٔ واقعاً مستقل که هم‌زمان آغاز شوند، زمان پایان تقریباً برابر شاخهٔ کندتر است، نه جمع کامل آن‌ها.

RTT و Bandwidth دو مسئلهٔ جدا را توصیف می‌کنند. RTT زیاد روی تماس‌های کوچک و سریال هزینهٔ رفت‌وبرگشت می‌سازد. Bandwidth محدود روی بدنهٔ بزرگ زمان ارسال می‌سازد. تقریبِ زمان انتقال، `body_bytes / effective_bytes_per_second` است؛ برای نمونه 512 KiB روی نرخ مؤثر 10 MiB/s حدود 50 ms طول می‌کشد، جدا از تأخیر شروع و انتظار شبکه. پس افزایش Bandwidth الزاماً یک call سریال DB را حذف نمی‌کند.

حتی پیش از شلوغی، فاصله یک کف تقریبی ایجاد می‌کند: سیگنال در فیبر بسیار کندتر از خلأ حرکت می‌کند و مسیر کابل از خط مستقیم طولانی‌تر است؛ در نتیجه، کم‌کردن چند صد یا چند هزار کیلومتر مسیر می‌تواند روی RTT اثر بگذارد. این فقط حد فیزیکی ذهنی است؛ route، تجهیزات، صف، peering و مسیر برگشت عدد واقعی را تعیین می‌کنند. «هم‌منطقه» را اندازه بگیرید، با نقشه تضمین نکنید.

## مثال حل‌شده: API نزدیک، DB دور

مدل **فرضی** اتصال گرم، بدنه کوچک و سه call سریال DB دارد. پردازش کل ثابت ۲۰ ms است؛ هیچ صف، handshake یا هم‌پوشانی نداریم:

</div>

```text
Layout A: user -> API RTT 80 ms; API -> DB RTT 2 ms
response = 80 + 3*2 + 20 = 106 ms

Layout B: user -> API RTT 20 ms; API -> DB RTT 70 ms
response = 20 + 3*70 + 20 = 250 ms
```

<div dir="rtl" align="right">

در این مدل، نزدیک‌تر کردن فقط API زمان را ۱۴۴ ms بیشتر می‌کند؛ DB دور سه بار در مسیر است. این جمع ساده پیش‌بینی دقیق اینترنت نیست. اگر وابستگی‌ها مستقل باشند، هم‌پوشانی طبق [مسیر بحرانی](../../06-code-optimization/04-critical-paths/README.md) مدل دیگری دارد. پاسخ بزرگ نیز زمان انتقال اضافه می‌کند؛ ۱ MiB روی نرخ مؤثر ثابت ۲ MiB/s حدود ۰٫۵ ثانیه برای بدنه می‌خواهد، جدا از انتظار شروع.

**چطور عدد را بخوانیم؟** در Layout A، شبکهٔ کاربر 80 ms، سه رفت‌وبرگشت DB روی‌هم `3×2=6 ms` و پردازش 20 ms است؛ جمع `106 ms`. در Layout B، کاربر 20 ms صرف می‌کند، اما DB سه بار `3×70=210 ms` می‌گیرد؛ با 20 ms پردازش می‌شود `250 ms`. سود 60 ms نزدیک‌تر شدن کاربر از هزینهٔ اضافی 204 ms برای سه call DB کمتر است؛ پس جای کاربر/API به‌تنهایی معیار انتخاب region نیست.

## کاربرد و مصالحه

برای کاربران متمرکز، هم‌مکانی برنامه و داده اغلب نامزد بررسی است. کاربران جهانی ممکن است به لبه، خواندن محلی یا چند منطقه نیاز داشته باشند، با هزینه replication، کهنگی، عملیات و failover. داده را فقط برای کم کردن RTT تکثیر نکنید؛ الزامات محل نگه‌داری، مجوز، سازگاری و بازیابی را تعریف کنید. تماس بین منطقه و خروج داده می‌تواند هزینه مالی نیز داشته باشد. خرابی یک منطقه نباید به routing به نود ناسالم یا هجوم ناگهانی به مقصد باقی‌مانده منجر شود.

## تمرین و انتظار

در Layout B، DB را هم‌منطقه و RTT آن را ۲ ms کنید؛ سپس یک سرویس پرداخت سریال با RTT برابر ۹۰ ms اضافه کنید. **انتظار:** مدل اول `20+6+20=46 ms` و با پرداخت `136 ms` است. اکنون گلوگاه تازه را مشخص کنید. برای تصمیم واقعی، حداقل دو گروه کاربر و دو بازه بار را مقایسه کنید؛ نتیجه تمرین معیار تضمینی سرویس نیست.

**حل تمرین:** پس از جابه‌جایی DB، سه تماس DB در مجموع `3×2=6 ms` می‌شوند؛ همراه شبکهٔ کاربر `20 ms` و پردازش `20 ms`، زمان `46 ms` است. پرداخت سریال 90 ms به critical path اضافه می‌شود، پس `46+90=136 ms`. اکنون پرداخت بزرگ‌ترین جزء مدل است؛ کم‌کردن RTT دیتابیس بیشتر سود کمتری می‌دهد تا اندازه‌گیری/کاهش انتظار پرداخت. اگر پرداخت و DB واقعاً مستقل بودند و هم‌زمان شروع می‌شدند، 90 ms را به‌جای جمع با DB، در شاخهٔ موازی مدل می‌کردیم.

## شاهد عمومی و حدود آن

گزارش **۹ ژوئن ۲۰۲۶** [Discord Voice at the Edge](https://discord.com/blog/how-we-moved-discord-voice-to-the-edge) نشان می‌دهد پوشش جغرافیایی بیشتر به‌تنهایی کافی نبود: مسیریابی تماس و مشکلات زمان‌بندی برنامه/زیرساخت هم بر نتیجه اثر داشتند. این تجربه مربوط به رسانه بلادرنگ روی UDP و زیرساخت مشخص است؛ اعداد آن هدف HTTP API ما نیستند. سناریوی DB بالا فرضی و مستقل از این گزارش است.

## شکست‌ها، علائم و چک‌لیست

TTFB بد فقط در یک ISP، تماس‌های cross-region روی Trace، افزایش egress، و tail بد در اوج، مسیرهای بررسی‌اند. میانگین سالم ممکن است گروه کوچکی از کاربران دور را پنهان کند؛ یک آزمون از لپ‌تاپ نویسنده جای توزیع کاربران را نمی‌گیرد.

- [ ] کاربر، API، DB و وابستگی‌های سریال مکان و RTT مشخص دارند.
- [ ] اتصال سرد/گرم و پاسخ کوچک/بزرگ جدا بررسی شده‌اند.
- [ ] نمونه‌های اوج و تفکیک منطقه/ISP کنار هزینه ثبت می‌شوند.
- [ ] سازگاری، محل داده، failover و ظرفیت مقصد جایگزین تعریف شده‌اند.
- [ ] معیار کاربر با Trace داخلی و زمان خارج Trace تطبیق داده می‌شود.

## خودآزمایی

۱. آیا RTT همان زمان یک‌طرفه است؟

۲. چرا API نزدیک‌تر در مثال کندتر شد؟

۳. چرا افزایش Bandwidth، سه call سریال کوچک را لزوماً سریع نمی‌کند؟

۴. آیا Ping خوب، TTFB خوب را ثابت می‌کند؟

۵. تکثیر داده در چند منطقه چه تعهدی اضافه می‌کند؟

۶. پس از هم‌مکانی DB، چرا باید دوباره Trace بگیریم؟

### پاسخ با دلیل

۱. خیر؛ رفت‌وبرگشت است و مسیر/تأخیر دو جهت الزاماً برابر نیست.

۲. کاهش ۶۰ ms در سمت کاربر با افزایش `3*(70-2)=204 ms` در DB جبران و بیشتر شد.

۳. برای پیام کوچک، انتظار رفت‌وبرگشت غالب است؛ ظرفیت بایت بیشتر تعداد وابستگی‌های سریال را حذف نمی‌کند.

۴. خیر؛ پروتکل، صف، handshake و پردازش API هم اثر دارند و مسیر/اولویت ICMP ممکن است متفاوت باشد.

۵. replication، تازگی، تعارض/مالکیت write، هزینه و بازیابی؛ خواندن محلی بدون قرارداد صحت کافی نیست.

۶. محدودیت می‌تواند به وابستگی دیگری مانند پرداخت منتقل شود؛ خط مبنا پس از تغییر باید تازه شود.
