# فصل 08: الگوهای معماری — Architectural Patterns


> **زبان:** [نسخهٔ انگلیسی](../../../../en/software-design-and-architecture/08/architectural-patterns/README.md)

> [ورود به درس کامل الگوهای معماری](lessons.md) — DDD، MVC، Microservices، CQRS، Event Sourcing، messaging و سایر گره‌های نقشه‌راه.

## هدف یادگیری

- الگوی معماری ساختار داخلی یا همکاری اجزا را برای نیروی تکرارشونده پیشنهاد می‌کند. سطح الگو، واحد انتخاب و هزینه‌اش با سبک معماری فرق دارد.
- بتوانی میان مسئله، الگو و هزینهٔ عملیاتی تمایز بگذاری.
- برای یک تصمیم، مثال، مبادله و معیار بازبینی بنویسی.

## ایدهٔ مرکزی فصل

الگوی معماری ساختار داخلی یا همکاری اجزا را برای نیروی تکرارشونده پیشنهاد می‌کند. سطح الگو، واحد انتخاب و هزینه‌اش با سبک معماری فرق دارد. این فصل را همراه با فصل‌های مجاور بخوان: طراحی شیء و اصول، کیفیت کد را درون جزء بهتر می‌کنند؛ سبک و الگوی معماری رابطهٔ چند جزء و مرزهای استقرار را شکل می‌دهند؛ الگوهای سازمانی اغلب درون این مرزها اجرا می‌شوند.

## نقشهٔ مفهومی و درس‌های مستقل

- [طراحی دامنه‌محور — Domain-Driven Design (DDD)](topics/domain-driven-design/README.md) — DDD فرایند و الگوهایی برای فهم دامنهٔ پیچیده است: زبان مشترک، bounded context، context map و مدل دامنهٔ دارای قواعد.
- [الگوی Model-View-Controller — Model-View-Controller (MVC)](topics/mvc/README.md) — MVC مسئولیت مدل، نمایش و کنترل ورودی را تفکیک می‌کند تا UI و منطق از هم جدا شوند؛ شکل دقیق MVC در frameworkها فرق می‌کند.
- [مایکروسرویس‌ها — Microservices](topics/microservices/README.md) — سامانه از سرویس‌های مستقل قابل‌استقرار پیرامون قابلیت‌های کسب‌وکار ساخته می‌شود؛ داده و تغییر هر سرویس تا حدی خودمختار است.
- [الگوی تخته‌سیاه — Blackboard Pattern](topics/blackboard/README.md) — چند منبع دانش روی فضای دادهٔ مشترک کار می‌کنند و کنترل‌کننده تصمیم می‌گیرد کدام جزء در گام بعد پیشرفت ایجاد کند؛ برای مسئله‌های راه‌حل‌تدریجی مناسب است.
- [الگوی ریزهسته — Microkernel Pattern](topics/microkernel/README.md) — هستهٔ کوچک قابلیت‌های پایدار را فراهم می‌کند و pluginها ویژگی‌های قابل تعویض را اضافه می‌کنند؛ قرارداد extension نقطهٔ حیاتی است.
- [معماری serverless — Serverless Architecture](topics/serverless/README.md) — کد به صورت function یا سرویس مدیریت‌شده اجرا می‌شود و بخشی از provisioning و مقیاس‌پذیری به provider سپرده می‌شود؛ مالکیت عملیات حذف نمی‌شود.
- [صف پیام و جریان رویداد — Message Queues and Streams](topics/queues-streams/README.md) — Queue کار را برای مصرف‌کننده نگه می‌دارد؛ stream سابقهٔ مرتب‌شده‌ای از رخدادها برای چند مصرف‌کننده می‌دهد. مدل retention و offset با هدف فرق می‌کند.
- [ثبت رویدادمحور — Event Sourcing](topics/event-sourcing/README.md) — وضعیت فعلی از دنبالهٔ تغییرناپذیر رویدادهای دامنه بازسازی می‌شود؛ audit و بازسازی projection مزیت‌اند.
- [معماری سرویس‌گرا (SOA) — Service-Oriented Architecture (SOA)](topics/soa/README.md) — SOA قابلیت‌های سازمان را در سرویس‌های قابل همکاری و قراردادی عرضه می‌کند؛ معمولاً با تمرکز بر یکپارچه‌سازی سامانه‌های سازمانی و قابلیت استفادهٔ مجدد.
- [تفکیک مسئولیت فرمان و پرس‌وجو — Command Query Responsibility Segregation (CQRS)](topics/cqrs/README.md) — مدل نوشتن که قواعد تغییر state را اجرا می‌کند از مدل خواندن جداست؛ در شکل ساده هر دو می‌توانند در یک سرویس و یک دیتابیس باشند.

## توضیح یکپارچهٔ فصل

برای هر تصمیم سه سؤال را جواب بده: **چه چیزی تغییر می‌کند؟ چه کسی مالک قاعده/داده است؟ و کدام ویژگی کیفی اهمیت دارد؟** سپس سطح راه‌حل را انتخاب کن: تابع و نوع، مرز ماژول، سرویس، صف یا مدل داده. این ترتیب کمک می‌کند نام الگو جای شناخت مسئله را نگیرد.

توضیح‌ها و مثال‌های هر مفهوم در فایل مستقل بالا آمده‌اند. برای مقایسه، نمونهٔ زیر عمداً یک مسئلهٔ مشترک را با چند سطح طراحی نشان می‌دهد: در فروشگاه، قانون لغو سفارش یک قاعدهٔ دامنه‌ای است؛ جداکردن آن از کنترلر مرز درون‌برنامه‌ای می‌سازد؛ اگر تیم و چرخهٔ انتشار مستقل شوند شاید component کافی باشد؛ اگر داده و بار و مالکیت مستقل باشند جداسازی سرویس بررسی می‌شود. هر مرحله نیازمند شاهد تازه است و مرحلهٔ بعدی را خودکار توجیه نمی‌کند.

## مطالعهٔ موردی و تجربهٔ صنعتی مستند

مستند Microsoft دربارهٔ eShopOnContainers یک نمونهٔ آموزشی برای DDD/CQRS داخل سرویس سفارش است و تأکید می‌کند که این الگوها را نباید برای همهٔ سرویس‌ها تحمیل کرد. مقالهٔ Fowler نیز CQRS را برای بسیاری از سیستم‌ها پیچیده‌تر از نیاز می‌داند. این‌ها نمونهٔ آموزشی و نظرهای مرجع‌اند، نه ادعای اینکه تمام سامانه‌های سازمانی باید چنین باشند.

- [Microsoft؛ CQRS و DDD در eShopOnContainers](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/apply-simplified-microservice-cqrs-ddd-patterns) — گزارش/منبع اصلی یا مرجع مرتبط با تجربهٔ مستند.
- [Martin Fowler؛ CQRS](https://martinfowler.com/bliki/CQRS.html) — گزارش/منبع اصلی یا مرجع مرتبط با تجربهٔ مستند.
- [Microsoft؛ معماری‌های مختلف در مایکروسرویس](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/multi-container-microservice-net-applications/microservice-application-design) — گزارش/منبع اصلی یا مرجع مرتبط با تجربهٔ مستند.

**روش خواندن مطالعهٔ موردی:** مسئلهٔ اولیه، محدودیت workload، گزینه‌های ردشده، هزینهٔ ارتباط و پیامد بعدی را استخراج کن. عدد یا تصمیم گزارش‌شده را به کل شرکت و همهٔ سامانه‌ها تعمیم نده.

## نمونهٔ کد یا قرارداد

```python
def place_order(command, order_repository):
    order = Order.from_command(command)
    order_repository.save(order)
    return order.id

def get_order_summary(query, read_store):
    return read_store.find_summary(query.order_id)
```

تفکیک مفهومی فرمان و پرس‌وجو را نشان می‌دهد؛ این مثال نیازمند دو پایگاه داده یا دو سرویس نیست.

## نمونهٔ تصمیم معماری

| پرسش | نمونهٔ پاسخ |
| --- | --- |
| نیاز یا فشار چیست؟ | تغییر مکرر قواعد سفارش و نیاز به بررسی مستقل آن‌ها. |
| ساده‌ترین گزینه چیست؟ | یک ماژول منسجم در برنامهٔ موجود با قرارداد داخلی و آزمون. |
| چه چیزی نتیجه را عوض می‌کند؟ | نیاز واقعی به استقرار مستقل، مقیاس متفاوت، امنیت یا مالکیت تیمی مستقل. |
| چگونه می‌سنجیم؟ | زمان تغییر، اثر انتشار، خطاهای مرزی، سربار ارتباط/عملیات و نیازهای محصول. |

## دام‌ها و سوءبرداشت‌ها

- الگو را از روی ترند انتخاب‌کردن، پیش از شناخت فشار طراحی.
- یک ساختار را همه‌جا تحمیل‌کردن؛ حتی وقتی پیچیدگی دامنه و چرخهٔ تغییر متفاوت است.
- نمونهٔ واقعی یک سازمان را بدون workload، تیم، هزینه و تاریخچه کپی‌کردن.
- بهینه‌سازی برای شاخص ساده‌ای مثل تعداد کلاس، سرویس یا خط کد به‌جای هدف محصول.

## کوییز جامع فصل با پاسخ‌نامه

1. مفهوم اصلی این فصل را چگونه برای یک سامانهٔ سفارش توضیح می‌دهی؟ از یکی از موضوع‌ها نام ببر و مسئله‌اش را بیان کن.
   - پاسخ/معیار ارزیابی: الگوی معماری ساختار داخلی یا همکاری اجزا را برای نیروی تکرارشونده پیشنهاد می‌کند. سطح الگو، واحد انتخاب و هزینه‌اش با سبک معماری فرق دارد.
2. در سناریویی که فروش، بازپرداخت و اعتبار مشتری را به contextهای روشن تقسیم می‌کنیم، چون واژه‌ها و مالکیت قواعد متفاوت‌اند. چه trade-offی را پیش از انتخاب می‌سنجی؟
   - پاسخ/معیار ارزیابی: DDD فرایند و الگوهایی برای فهم دامنهٔ پیچیده است: زبان مشترک، bounded context، context map و مدل دامنهٔ دارای قواعد. نیازمند همکاری متخصص دامنه است و هزینهٔ مدل‌سازی دارد.
3. یک مورد از این فصل را انتخاب کن که ممکن است over-engineering شود؛ چه نشانه‌ای باعث می‌شود آن را حذف یا ساده کنی؟
   - پاسخ/معیار ارزیابی: وقتی abstraction یا عملیات/نگهداری از نیاز مشاهده‌شده بیشتر می‌شود، ساده‌سازی را انتخاب کن؛ YAGNI و دادهٔ واقعی را راهنما بگیر.
4. برای یکی از تصمیم‌های فصل، چه آزمون یا سنجه‌ای نشان می‌دهد طراحی بهبود یافته است?
   - پاسخ/معیار ارزیابی: آزمون‌های رفتار/قرارداد، زمان تغییر، نرخ خطا، latency یا هزینه را با توجه به هدف انتخاب کن و قبل/بعد را مقایسه کن.
5. کدام بخش سناریوی مستند فصل را می‌توان به مسئلهٔ خودت تعمیم داد و کدام بخش وابسته به زمینهٔ همان شرکت است?
   - پاسخ/معیار ارزیابی: اصل مسئله و trade-off را تعمیم بده؛ فناوری، بار و ساختار سازمانی شرکت را بدون شواهد کپی نکن.
6. رابط یا مرزی را طراحی کن که تغییر یک مسئولیت را از بقیه جدا کند؛ توضیح بده این مرز کدام نوع coupling را کم می‌کند.
   - پاسخ/معیار ارزیابی: مدل نوشتن که قواعد تغییر state را اجرا می‌کند از مدل خواندن جداست؛ در شکل ساده هر دو می‌توانند در یک سرویس و یک دیتابیس باشند.

## تمرین عملی

یک سیستم کوچک فروش، رزرو یا صدور فاکتور انتخاب کن. برای سه نیازمندی پرتغییر، نقشهٔ مسئولیت‌ها را بکش؛ یک قرارداد و آزمون بنویس؛ سپس توضیح بده چرا فعلاً از مرز انتخاب‌شده استفاده می‌کنی و چه نشانه‌ای باعث می‌شود آن را تغییر بدهی. تمرین را با [قالب ADR](https://adr.github.io/) ثبت کن.
