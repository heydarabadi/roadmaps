# مسیر مطالعه و تسلط

**زبان:** فارسی · [English](../en/11-study-path/README.md)

این برنامه برای خودآموزی طراحی شده است. پیشنهاد پایه: روزانه ۴۵ تا ۷۵ دقیقه، پنج روز در هفته؛ اگر زمان کمتری داری، تمرین‌ها را حذف نکن و تعداد روزها را بیشتر کن.

## پیش‌نیازها

برای فهم مثال‌ها لازم نیست در زبان خاصی متخصص باشی، اما این مفاهیم را بشناس:

- کد در فایل‌ها و تابع‌ها سازمان‌دهی می‌شود؛
- یک درخواست از ورودی تا منطق برنامه و ذخیره/پاسخ حرکت می‌کند؛
- Git تغییرها را در commit و branch نگه می‌دارد؛
- تست یک انتظار را بررسی می‌کند؛
- API میان دو جزء سیستم قرارداد می‌سازد؛
- authentication و database را در حد آشنایی می‌شناسی.

### خودارزیابی آغازین

اگر نمی‌توانی به پرسش‌ها جواب دهی، اول همان مفهوم را در مخزن خودت پیدا و با مثال کوچک تمرین کن:

1. diff تغییرات staged و unstaged چه تفاوتی دارند؟
2. تستی که فقط mock را صدا می‌زند چه چیزی را ثابت می‌کند؟
3. احراز هویت با مجوزدهی چه فرقی دارد؟
4. migration چگونه با سرویس قدیمیِ در حال اجرا تداخل می‌کند؟
5. کدام تست‌ها و CI برای آخرین commit اجرا شده‌اند، چطور می‌فهمی؟

پاسخ ندادن نشانهٔ ناتوانی نیست؛ فهرست پیش‌نیازهای یادگیری توست.

## برنامهٔ چهار هفته‌ای

### هفتهٔ ۱: فهم PR و کار نویسنده

- **روز ۱:** فصل مبانی را بخوان؛ تفاوت review، تست، lint و QA را با مثال خودت بنویس.
- **روز ۲:** چرخهٔ review را دنبال کن؛ یک PR بسته‌شده را از شرح تا merge بخوان.
- **روز ۳:** یک تغییر فرضی را به دو PR متمرکز تقسیم کن؛ دلیل هر مرز را بنویس.
- **روز ۴:** قالب شرح PR را برای feature کوچک پر کن؛ تست و risk را دقیق بنویس.
- **روز ۵:** self-review انجام بده؛ diff را بدون اتکا به حافظه بخوان و فایل‌های تصادفی را بیاب.

### هفتهٔ ۲: دیدگاه بازبین و آزمون

- **روز ۱:** نیازمندی و مسیر دادهٔ یک PR را ترسیم کن.
- **روز ۲:** سه حالت مرزی، دو failure mode و یک invariant پیدا کن.
- **روز ۳:** یک تست را بخوان؛ توضیح بده assertion چه regressionی را می‌شکند.
- **روز ۴:** security review ساده انجام بده: identity، permission، source و sink را دنبال کن.
- **روز ۵:** performance و operations را با query، timeout یا cache مثال بزن.

### هفتهٔ ۳: گفت‌وگو، اصلاح و ادغام

- **روز ۱:** پنج کامنت تند یا مبهم بنویس و آن‌ها را به observation + impact + ask بازنویسی کن.
- **روز ۲:** findingها را blocker، suggestion، question یا nit طبقه‌بندی کن.
- **روز ۳:** برای سه comment پاسخ نویسنده بنویس؛ یکی را با دلیل نپذیر.
- **روز ۴:** diff پیش و پس از اصلاح را مقایسه کن؛ بگو کدام approvalها به revision جدید مربوط‌اند.
- **روز ۵:** پیش از merge چک‌لیست required checks، owners، rollout و rollback را اجرا کن.

### هفتهٔ ۴: پروژهٔ واقعی و بازنگری

- **روز ۱:** یک مخزن کوچک عمومی و فعال پیدا کن؛ ابتدا contribution guide آن را بخوان.
- **روز ۲:** یک PR کوچک را فقط برای فهم هدف و دامنه مطالعه کن.
- **روز ۳:** تست‌ها و edge caseها را بررسی کن؛ سه سؤال بنویس ولی هنوز کامنت منتشر نکن.
- **روز ۴:** یافته‌ها را با reviewهای موجود و مستندات پروژه مقایسه کن؛ فرض‌ها را اصلاح کن.
- **روز ۵:** یک review تمرینی با یک blocker، یک سؤال، یک suggestion و یک نکتهٔ مثبت بنویس؛ اگر آماده بودی قوانین پروژه را برای مشارکت واقعی دنبال کن.

## مرور فاصله‌دار

پس از هر فصل، همان روز یک یادداشت کوتاه بساز؛ یک روز بعد checklist را بدون نگاه‌کردن بازگو کن؛ سه روز بعد سناریو را روی PR دیگری اجرا کن؛ هفتهٔ بعد فقط مواردی را که دشوار بودند دوباره بخوان. هدف حفظ جمله‌ها نیست؛ تشخیص خطر و انتخاب شاهد است.

## درجه‌بندی تسلط

| سطح | توانایی مشاهده‌شده |
|---|---|
| ۰ — آشنایی | اصطلاح را می‌بیند اما هنوز نمی‌تواند مثال بزند |
| ۱ — با راهنما | با checklist می‌تواند سؤال‌های اولیه مطرح کند |
| ۲ — مستقل | finding را با رفتار، اثر و شواهد توضیح می‌دهد |
| ۳ — پیشرفته | ریسک‌های بین‌سیستمی، trade-off و محدودیت evidence را می‌سنجد |
| ۴ — راهبر تیم | policy قابل‌عمل، گیت‌های خودکار و فرایند بهبود را طراحی می‌کند |

لازم نیست هر موضوع در سطح ۴ باشد. reviewer خوب هم می‌داند چه چیزی را نمی‌داند و چه زمانی باید متخصص مناسب را وارد کند.

## چه زمانی پیشرفت را بسنجی؟

با تعداد کامنت‌ها خودت را نسنج. نمونه‌ای از reviewها بردار و بپرس: آیا مسئلهٔ درست پیدا شد؟ آیا کامنت actionable بود؟ آیا نظر اختیاری merge را بی‌دلیل متوقف نکرد؟ آیا نویسنده فهمید چه تستی لازم است؟ آیا موردی از security/compatibility جا افتاد؟ یادداشت کیفیت به رشد کمک می‌کند، نه quota.
