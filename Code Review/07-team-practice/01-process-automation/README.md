# Definition of Done، اتوماسیون و سلامت جریان

**زبان:** فارسی · [English](../../en/07-team-practice/01-process-automation/README.md)

> مسیر: [فصل ۷ — تیم، تجربه و تمرین](../README.md) · [فهرست دوره](../../README.md)

## آموزش

فرایند تیم باید purpose، مسئولیت، تعریف Done، موارد blocker، زمان پاسخ و روش حل اختلاف را روشن کند. نیازها متناسب با تغییرند: migration شاید برنامهٔ rollback و تایید DB owner بخواهد؛ تغییر متن شاید تصویر و تست UI بخواهد. review باید در workload جا داشته باشد و فرصت یادگیری و آشنایی بین حوزه‌ها ایجاد کند.

تیم مشارکت در review را تشویق کند، بازبینی را اولویت کاری بداند و انتظار turnaround روشن داشته باشد. جلسه‌های دوره‌ای کوتاه برای دیدن الگوهای تکراری، بازبینی فرایند و حل اختلاف مفیدند. کیفیت feedback و کمک به یادگیری را به رسمیت بشناس؛ تعداد کامنت را پاداش نده. نویسنده هم می‌تواند پیش از پایان کار feedback زودهنگام بخواهد.

formatter، lint، build، تست، dependency review، SAST و secret scanning را خودکار کن. هشدار باید قابل‌فهم و قابل‌حل باشد، وگرنه تیم بی‌تفاوت یا دورزن می‌شود. CODEOWNERS، required checks و bypassها را دوره‌ای نگه‌داری کن. AI/bot را دستیار بدان؛ یافته را با کد راستی‌آزمایی کن.

شاخص‌هایی مانند زمان اولین پاسخ، صف review، rework و بار بین افراد سرنخ‌اند، نه KPI فردی. تعداد کامنت یا سرعت approve می‌تواند رفتار غلط تشویق کند. برای فهم bottleneck، نوع PR و کیفیت را نیز نمونه‌برداری کن.

## روند پیشنهادی

1. Definition of Done و policy را شفاف بنویس.
2. قواعد مکانیکی را با CI خودکار کن.
3. ownership، bypass و هشدارهای flaky را بازبینی کن.
4. زمان پاسخ و review load را در تیم پایش کن.
5. روندهای تکراری را به اقدام دارای owner تبدیل کن.

## مثال کاربردی

صف review طولانی است. به‌جای الزام approve در یک ساعت، تیم می‌بیند بیشتر PRهای DB منتظر یک متخصص‌اند؛ دانش را پخش و reviewer دوم آموزش می‌دهد، هم‌زمان flaky test را اصلاح می‌کند.

## خطاهای رایج

چک‌باکس بی‌معنا نساز؛ تعداد comment را KPI نکن؛ همهٔ هشدارها را blocking نکن؛ AI را مرجع نهایی فرض نکن؛ میانگین زمان را تمام داستان ندان.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** چه چیزی را به CI بسپاریم؟

   1. قضاوت معماری کامل
   2. قواعد deterministic مانند lint و format
   3. نیاز کاربر
   4. trade-off محصول

**پاسخ:** 2 — تکرارپذیری، اتوماسیون را مناسب می‌کند.

### پرسش 2

**سؤال:** چرا comment count معیار ضعیفی است؟

   1. نمی‌توان آن را شمرد
   2. ممکن است nit و کامنت بی‌ارزش را تشویق کند
   3. فقط تیم کوچک دارد
   4. review کامنت ندارد

**پاسخ:** 2 — حجم مساوی ارزش نیست.

### پرسش 3

**سؤال:** با افزایش latency چه می‌کنیم؟

   1. فوراً توبیخ می‌کنیم
   2. نوع صف و علت را بررسی می‌کنیم
   3. همهٔ approvals را حذف می‌کنیم
   4. بدون تست merge می‌کنیم

**پاسخ:** 2 — علت ممکن است تمرکز دانش یا flaky CI باشد.

### پرسش 4

**سؤال:** خروجی AI review را چگونه مصرف کنیم؟

   1. بدون دیدن merge کنیم
   2. فرضیه بدانیم و مستقل بررسی کنیم
   3. همیشه نادیده بگیریم
   4. فقط تعدادش را گزارش کنیم

**پاسخ:** 2 — مدل ممکن است زمینه و semantics را از دست بدهد.

## آموزش عمیق: سیاست خوب، رفتار درست را آسان می‌کند

### تعریف Done متناسب با ریسک

تیم باید روشن کند چه چیزی برای ادغام لازم است؛ برای مثال build و tests موفق، بازبینی یک همتا، update مستندات متأثر و تعیین تکلیف هشدارهای امنیتی. جزئیات می‌تواند بر اساس نوع تغییر فرق کند:

- تغییر UI: تست رفتار و تصویر/ویدئوی بی‌دادهٔ محرمانه؛
- migration: بررسی سازگاری نسخه‌ها، حجم اجرا و راه بازیابی؛
- dependency: علت استفاده، منبع، license و تغییر lockfile؛
- auth/security: بازبینی متخصص و تست دسترسی مثبت/منفی؛
- متن یا typo: scope کوچک و بررسی خروجی، نه فرم سنگین انتشار.

Definition of Done باید به تیم کمک کند چیزی را فراموش نکند؛ نباید checkboxهایی بسازد که همه بدون نگاه‌کردن تیک بزنند. هر بند باید owner یا شواهد قابل‌دیدن داشته باشد.

### کجا اتوماسیون کنیم؟

**مناسب:** formatting، lint، build، تست‌های تکرارپذیر، secret scan، dependency advisory و برخی قواعد مجوز. **مناسب نیست به‌تنهایی:** آیا feature نیاز محصول را حل می‌کند؟ آیا مجوز به object درست وصل است؟ آیا مهاجرت برای بازار/tenant خاص امن است؟ bot ممکن است پیشنهاد بدهد، اما context را reviewer باید تأیید کند.

کیفیت گیت‌ها را هم نگه‌داری کن: flaky test را مالک‌دار کن؛ false positive را مستند کن؛ درگاه امنیتی را بدون فرایند رسیدگی blocking نکن؛ CODEOWNERS و bypass مجاز را دوره‌ای بازبینی کن. اگر ابزار خطای نامفهوم می‌دهد، توسعه‌دهنده آن را دور می‌زند و کنترل بی‌اثر می‌شود.

### سلامت جریان و شاخص‌ها

زمان تا اولین پاسخ، زمان انتظار در صف، round tripها، اندازهٔ تغییر و بار review می‌توانند bottleneck را نشان دهند. آن‌ها را کنار کیفیت، rework و incident تفسیر کن. میانگین review time ممکن است PR ساده و migration پرخطر را مخلوط کند. تعداد comment یا سرعت approve را KPI فردی نکن؛ این شاخص‌ها nit یا تایید سطحی را پاداش می‌دهند.

جلسهٔ دوره‌ای کوتاه بررسی کند: کدام هشدارها پرتکرارند؟ دانش در یک نفر متمرکز شده؟ آیا نویسنده می‌تواند پیش از پایان کار طرح را نشان دهد؟ چه قانونی چند بار محل اختلاف بوده؟ هر اقدام بهبود باید owner، زمان و روش سنجش داشته باشد. فرصت یادگیری در حوزهٔ ناآشنا را ایجاد کن، ولی کنترل حساس را بی‌متخصص رها نکن.

### نمونهٔ توافق تیمی

این متن را متناسب با تیم تغییر بده:

<pre dir="ltr"><code>برای merge:
- CI مربوط به آخرین revision سبز باشد.
- یک reviewer واجد دانش مرتبط بررسی کند.
- تغییرات auth، schema و dependency مالک حوزه داشته باشند.
- blockerها حل شده باشند؛ suggestion اختیاری بتواند در issue پیگیری شود.
- author تغییر تازه را اعلام کند و reviewer در صورت تغییر رفتار re-review کند.
- برای تغییر پراثر، metric، rollout و rollback در شرح ثبت شوند.
زمان اولین پاسخ را در توافق تیم تعیین می‌کنیم و اگر reviewer در دسترس نیست، جایگزین معرفی می‌شود.</code></pre>

این فقط الگو است. برای پروژهٔ کوچک ممکن است بیش از حد سنگین باشد؛ برای سیستم حساس، کنترل‌های بیشتری لازم است.

### تمرین

فرایند فعلی‌ات سه بار PR را به‌خاطر اختلاف style نگه داشته. یک تغییر سیستمی پیشنهاد بده. پاسخ مناسب می‌تواند style guide روشن، formatter در CI، تصمیم دربارهٔ فایل‌های قدیمی و تعریف nit باشد؛ نه افزودن approval یا تنبیه reviewer.
