# پاسخ نویسنده و اصلاح

**زبان:** فارسی · [English](../../en/06-follow-up/01-address-feedback/README.md)

> مسیر: [فصل ۶ — پاسخ، تایید و ادغام](../README.md) · [فهرست دوره](../../README.md)

## آموزش

برای هر comment وضعیت را روشن کن: انجام شد، سؤال دارم، یا انجام نمی‌دهم چون… . اصلاح را در commit قابل‌دیدن بفرست و کوتاه بگو چه رفتاری تغییر کرد. اگر پیشنهاد را نمی‌پذیری، دلیل و شواهد ارائه کن؛ سکوت، reviewer را وادار به حدس می‌کند.

پیش از اصلاح، علت comment را بفهم. حذف retry شاید تست را سبز کند اما ریشهٔ دوبار پرداخت را حل نکند؛ idempotency یا transaction مناسب‌تر است. پس از تغییر، تست و docs مربوط را دوباره اجرا یا بررسی کن. resolveکردن thread ابزار هماهنگی است، نه اثبات حل مسئله.

برای دور بعد، reviewer را از push جدید باخبر کن و تست‌های مرتبط را نام ببر. پیشنهاد اختیاری را می‌توان با دلیل نپذیرفت، اما blocker حل‌نشده باید بماند تا تصمیم مسئول مشخص شود.

## روند پیشنهادی

1. feedback را فهرست و blockerها را جلو بینداز.
2. به هر مورد پاسخ یا تغییر مشخص بده.
3. دلیل رد پیشنهاد را با معیار توضیح بده.
4. تست/docs را بعد از اصلاح بازبینی کن.
5. reviewer را برای revision تازه مطلع کن.

## مثال کاربردی

reviewer خطر retry دوباره را می‌گوید؛ نویسنده قرارداد را روشن، idempotency key اضافه، تست درخواست تکراری اجرا و شمارهٔ commit را در پاسخ می‌گذارد.

## خطاهای رایج

فقط done نگو؛ thread حل‌نشده را پنهانی resolve نکن؛ آزمون مربوط را بعد از اصلاح فراموش نکن؛ سکوت را مخالفت یا موافقت فرض نکن.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** اگر پیشنهاد را اجرا نمی‌کنی چه باید کرد؟

   1. سکوت
   2. توضیح دلیل و شواهد
   3. resolve بی‌شرح
   4. بحث شخصی

**پاسخ:** 2 — پاسخ روشن ادامهٔ review را ممکن می‌کند.

### پرسش 2

**سؤال:** resolve کردن thread چه چیزی را ثابت نمی‌کند؟

   1. وضعیت رابط کاربری تغییر کرد
   2. رفتار واقعاً درست شده است
   3. کامنت وجود داشت
   4. کسی آن را بست

**پاسخ:** 2 — ابزار به‌تنهایی صحت را اثبات نمی‌کند.

### پرسش 3

**سؤال:** چرا باید علت feedback را بفهمی؟

   1. برای کاهش commitها
   2. برای رفع ریشهٔ ایراد
   3. برای حذف تست
   4. برای تغییر موضوع

**پاسخ:** 2 — اصلاح سطحی ممکن است مشکل واقعی را باقی بگذارد.

### پرسش 4

**سؤال:** پس از push چه اطلاعاتی مفید است؟

   1. هیچ
   2. تغییر، تست اجراشده و درخواست re-review
   3. تعداد خطوط
   4. emoji

**پاسخ:** 2 — reviewer می‌تواند دور بعد را هدفمند کند.

## آموزش عمیق: بازخورد را به تغییر قابل‌ردیابی تبدیل کن

### قبل از پاسخ، کامنت را بفهم

برای هر نظر، این چهار مورد را مشخص کن:

1. بازبین به چه رفتار یا خطری اشاره کرده؟
2. آیا این الزام، پیشنهاد یا سؤال است؟
3. چه بخشی از کد/نیازمندی شاهد را تأیید می‌کند؟
4. آیا اصلاح، تست یا توضیح لازم است؟

اگر واژه‌ای مثل «بهتر» یا «ایمن‌تر» مبهم است، پیش از تغییر بپرس کدام invariant یا سناریو مطرح است. اجرای پیشنهاد بدون فهم قصد، ممکن است خطای تازه بسازد.

### پاسخ‌هایی که فرایند را جلو می‌برند

- اصلاح شد: «کلید idempotency به transaction اضافه شد؛ تست retry در commit تازه آمده.»
- نیازمند clarification: «آیا منظور شما retry از client است یا اجرای مجدد job؟ دو مسیر ضمانت متفاوت دارند.»
- پیشنهاد اختیاری رد می‌شود: «در این مسیر حجم داده محدود به ۲۰ مورد است؛ benchmark را گذاشتم. برای refactor جدا issue ثبت می‌کنم تا دامنهٔ PR فعلی نرود.»
- comment با شواهد نادرست است: «من آزمایش کردم این branch قبل از فراخوانی DB با role فعلی برمی‌گردد؛ تست در این فایل رفتار را پوشش می‌دهد. اگر سناریوی دیگری مدنظر است لطفاً مشخص کن.»

حتی اگر با نظر مخالفی، آرام و به رفتار پاسخ بده. پاسخ شخصی یا سکوت، راه را برای نتیجه‌گیری غلط باز می‌کند. نظر reviewer هم ممکن است با شواهد تغییر کند.

### حل مجموعه‌ای از commentها

1. blockerها را اولویت بده.
2. commentهای وابسته را کنار هم بگذار؛ ممکن است یک تغییر چند مورد را حل کند.
3. اصلاح را در diff روشن و منطقی انجام بده؛ تغییرهای نامرتبط را اضافه نکن.
4. تست‌های مرتبط را بعد از تغییر اجرا کن و نتیجه را ثبت کن.
5. thread را طبق policy تیم resolve کن؛ اگر مسئله حل نشده، آن را باز نگه دار.
6. وقتی آماده‌ای، reviewer را دوباره درخواست کن و محدودهٔ revision را بگو.

resolved کردن thread وضعیت گفتگو را می‌بندد؛ correctness را اثبات نمی‌کند. بازبین باید نتیجهٔ تغییر را ببیند.

### مثال کامل

کامنت: «دو درخواست هم‌زمان می‌توانند هر دو موجودی را بخوانند و یک کالا را بفروشند.» نویسنده ابتدا روشن می‌کند آیا سفارش باید در موجودی صفر رد شود. سپس قید atomic در DB و تست رقابت اضافه می‌کند، تست را روی آخرین revision اجرا می‌کند، در پاسخ نام تست و فایل را می‌آورد و reviewer را re-request می‌کند. فقط افزودن if در برنامه، بدون قید اتمیک، ممکن است race را حل نکند.

### تمرین

برای comment «این error handling خوب نیست» بنویس چه clarificationی می‌خواهی و چه پاسخ قابل‌قبولی می‌دهی. نمونه: «کدام failure mode مدنظر است: timeout، پاسخ 4xx یا دادهٔ ناقص؟ فعلاً timeout retry می‌شود اما خطای دائمی به caller منتقل می‌شود؛ اگر نگرانی شما افشای جزئیات است، پاسخ عمومی را جدا می‌کنم و علت را امن log می‌کنم.»
