# Big-Theta: کران تنگ

> مسیر: [فصل ۱ — پایه‌ها و تحلیل الگوریتم](../readme.md) · پیش‌نیاز پیشنهادی: فصل ۱ و مبانی برنامه‌نویسی · [English](readme.en.md)

## پیش‌نیازها و نقشهٔ ذهنی

Big-O، Omega و تابع هزینه. ابتدا مفهوم را به‌عنوان یک قرارداد ببین، سپس نمایش حافظه و عملیات را دنبال کن. هدف حفظ‌کردن نام نیست؛ باید بتوانی برای یک ورودی کوچک، state را بعد از هر گام بنویسی.

## ایده از پایه

Θ(g(n)) توصیف دقیق نرخ رشد مجانبی است: تابع هزینه هم از بالا و هم پایین با g(n) تا ضریب ثابت محدود می‌شود. اگر T(n)=Θ(n log n)، می‌دانیم رشدش در همان مرتبه است، نه صرفاً از آن بیشتر نمی‌شود.

## مدل، قرارداد و ناوردا

ثابت‌های مثبت c₁,c₂ و n₀ وجود دارند که برای همهٔ n≥n₀: c₁g(n)≤T(n)≤c₂g(n). بنابراین Θ(g)=O(g)∩Ω(g). این تعریف روی تابع nonnegative هزینه اعمال می‌شود.

ناوردا (invariant) جمله‌ای است که در تمام مراحل الگوریتم باید درست بماند. نوشتن آن پیش از کدنویسی، هم به اثبات درستی کمک می‌کند و هم خطاهای مرزی را آشکار می‌سازد.

## الگوریتم یا عملیات گام‌به‌گام

برای T(n)=4n²+10n+3: از بالا برای n بزرگ ≤C n²؛ از پایین ≥4n²؛ پس Θ(n²). برای جست‌وجوی خطی worst-case Θ(n) است، اما بهترین حالت O(1) و worst upper/lower را جدا می‌گوییم.

در پیاده‌سازی واقعی، قرارداد ورودی/خروجی را دقیق تعریف کن: رفتار ورودی تهی، مقدار تکراری، عنصر پیدا‌نشده و ظرفیت تمام‌شده باید روشن باشد.

## اجرای حل‌شده با ردگیری

T(n)=n log n + 7n. نسبت T/(n log n)=1+7/log n به 1 میل می‌کند؛ بنابراین دو طرف با n log n هم‌مرتبه‌اند و Θ(n log n).

برای تمرین، جدولی با ستون‌های «گام»، «اندیس/اشاره‌گر»، «بخش فعال»، «تغییر state» و «دلیل» بساز. این روش به‌خصوص برای الگوریتم‌های درجا و تقسیم‌و‌غلبه جلوی پرش ذهنی را می‌گیرد.

## چرا درست است؟

کران پایین/بالا باید هر دو برای همهٔ n کافی بزرگ و با quantifier درست ثابت شوند؛ یک مثال خاص، Θ را اثبات نمی‌کند. برای الگوریتم، function cost و worst/average case را مشخص کن.

اثبات معمولاً سه بخش دارد: (۱) آغاز—ناوردا پیش از نخستین گام درست است؛ (۲) نگهداری—هر گام آن را حفظ می‌کند؛ (۳) پایان—شرط توقف همراه invariant جواب موردنیاز را نتیجه می‌دهد. اگر یکی از این سه بخش نامشخص است، هنوز درک الگوریتم کامل نشده است.

## تحلیل زمان و حافظه

Θ notation برای tight bound مفید است، اما نمی‌گوید تابع دقیقاً برابر g است. Θ(n) می‌تواند 2n و 1000n را هر دو شامل شود. constants در benchmark واقعی همچنان مهم‌اند.

در Big-O ورودی را تعریف کن (مثلاً n تعداد عناصر)، نوع حالت را نام ببر (بهترین/میانگین/بدترین)، و فضای کمکی را از حافظهٔ خود ورودی جدا کن. مرتبهٔ رشد زمان واقعی بر حسب ثانیه نیست؛ cache، تخصیص حافظه و ثابت‌های پیاده‌سازی هم اثر دارند.

## کاربرد واقعی و انتخاب مناسب

تحلیل دقیق sorting مانند merge sort Θ(n log n)، پیمایش Θ(n) و عملیات tree براساس ارتفاع. زبان مصاحبه‌ای «O(n)» اغلب منظور worst upper است، پس برای دقت tight bound را بنویس.

پیش از انتخاب بپرس: چه عملیاتی پرتکرارند؟ آیا ترتیب مهم است؟ دادهٔ ورودی چه اندازه است؟ آیا محدودیت حافظه، latency بدترین‌حالت یا thread-safety داریم؟ ساختار خوب برای workload نامناسب می‌تواند انتخاب بدی باشد.

## خطاهای رایج و edge caseها

از بدترین‌حالت O(n) نمی‌توان نتیجه گرفت Θ(n) مگر lower bound هم ثابت باشد. Θ(n²) و O(n²) تفاوت assertion دارند.

حالت‌های مرزی را جداگانه بررسی کن: ورودی خالی، یک عضو، همهٔ اعضا برابر، هدف غایب، حداقل/حداکثر مقدار و اندازهٔ بزرگ. سرریز عدد صحیح در محاسبهٔ اندیس/ظرفیت نیز بسته به زبان مهم است.

## تمرین‌های مرحله‌ای

۱) Θ bound عبارت 3n³−8n را ثابت کن. ۲) برای linear search بهترین و بدترین tight bound را بنویس. ۳) آیا T=n² برای nهای مثبت در Θ(n³) است؟ کران را بررسی کن.

برای هر تمرین، اول پاسخ ساده و درست بنویس، بعد پیچیدگی را حساب کن، سپس edge case اضافه کن. تمرین را با دست‌کم یک ورودی کوچک ردگیری کن و خروجی را با انتظار مستقل مقایسه کن.

## آزمون جامع با پاسخ تشریحی

ابتدا پاسخ‌ها را نخوان؛ جواب را با استدلال بنویس، سپس توضیح را مقایسه کن.

1. **پرسش:** Θ چه چیزی را ترکیب می‌کند؟
   **پاسخ تشریحی:** کران بالا O و پایین Ω.
2. **پرسش:** چرا یک نمونه کافی نیست؟
   **پاسخ تشریحی:** تعریف برای همهٔ n کافی بزرگ است.
3. **پرسش:** T=4n²+10n+3؟
   **پاسخ تشریحی:** Θ(n²).
4. **پرسش:** O(n) یعنی حتماً Θ(n)؟
   **پاسخ تشریحی:** نه؛ O فقط upper bound است.
5. **پرسش:** آیا ثابت‌ها دقیق‌اند؟
   **پاسخ تشریحی:** خیر؛ کران با هر ثابت مناسب برای n بزرگ برقرار می‌شود.
