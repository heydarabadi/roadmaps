## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

هستهٔ کوچک قابلیت‌های پایدار را فراهم می‌کند و pluginها ویژگی‌های قابل تعویض را اضافه می‌کنند؛ قرارداد extension نقطهٔ حیاتی است.

## مثال کاربردی

ابزار گزارش‌گیری هستهٔ احراز هویت و گردش‌کار دارد و pluginهای خروجی CSV/PDF اضافه می‌شوند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «الگوهای معماری» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** نسخه‌بندی plugin و سازگاری runtime هزینه می‌آورد.
- **بازبینی:** plugin architecture را برای چند قابلیت ثابت نساز؛ مدل امنیت و شکست extension را تعریف کن.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: هستهٔ کوچک قابلیت‌های پایدار را فراهم می‌کند و pluginها ویژگی‌های قابل تعویض را اضافه می‌کنند؛ قرارداد extension نقطهٔ حیاتی است.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: ابزار گزارش‌گیری هستهٔ احراز هویت و گردش‌کار دارد و pluginهای خروجی CSV/PDF اضافه می‌شوند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: نسخه‌بندی plugin و سازگاری runtime هزینه می‌آورد.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: plugin architecture را برای چند قابلیت ثابت نساز؛ مدل امنیت و شکست extension را تعریف کن.

## آموزش تکمیلی مستقل

### ۵. Microkernel

Microkernel یک هستهٔ کوچک و پایدار دارد و قابلیت‌های متغیر را به plugin یا extension منتقل می‌کند. این الگو برای platformهایی خوب است که third-party extensions یا محصول‌های edition-specific واقعی دارند.

مرز plugin باید نسخه‌بندی، permission، lifecycle، خطا و resource limit داشته باشد. Plugin تنها وقتی مفید است که رفتار را خارج از هسته توسعه یا نصب کنیم؛ اگر همهٔ pluginها همیشه با خود برنامه منتشر می‌شوند، ماژول داخلی شاید ساده‌تر باشد.

## نمودار معماری و خواندن مرحله‌ای

Microkernel یک core کوچک و پایدار را با pluginهای قابل‌افزودن ترکیب می‌کند. core باید قرارداد و lifecycle plugin را کنترل کند؛ سازگاری نسخه، مجوز، شکست plugin و هزینهٔ جداسازی را مشخص کن.
**دام رایج:** هر قابلیت را plugin نکن؛ core بزرگ یا pluginهای tightly coupled مزیت را از بین می‌برند.
**تمرین با پاسخ:** plugin ناسازگار با نسخه بارگذاری نشود؛ manifest و version constraint را پیش از activation اعتبارسنجی کن.

این یک view ساده است؛ طراحی production باید مالکیت، شکست، امنیت و محدودیت‌های عملیاتی را نیز روشن کند.

~~~text
       [Plugin A]       [Plugin B]
            \              /
             v            v
        [Extension contracts]
                 |
            [Microkernel]
                 |
           [Core services]
~~~

## نمودار معماری و خواندن مرحله‌ای

Microkernel یک core پایدار را با pluginها گسترش می‌دهد. core قرارداد، مجوز و lifecycle plugin را اداره می‌کند؛ سازگاری نسخه، شکست plugin و isolation را مشخص کن.
**دام رایج:** اگر core همهٔ قابلیت‌ها را در خود دارد یا pluginها tightly coupled هستند، microkernel فقط پیچیدگی افزوده است.
**تمرین با پاسخ:** plugin نسخهٔ ناسازگار دارد؛ manifest را پیش از activation بررسی و از بارگذاری رد کن.

این view ساده باید با تصمیم روشن دربارهٔ مالکیت، شکست، امنیت و عملیات کامل شود.

~~~text
       [Plugin A]       [Plugin B]
            \              /
             v            v
        [Extension contracts]
                 |
            [Microkernel]
                 |
           [Core services]
~~~
