## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

الگوهای POSA معمولاً در مقیاس معماری، هم‌زمانی و سیستم توزیع‌شده نیروها و ساختارهای تکرارشونده را ثبت می‌کنند؛ از الگوهای کوچک‌تر GoF فراتر می‌روند.

## مثال کاربردی

برای پردازش موازی، معماری Broker یا Layers را با محرک تغییر، جریان کنترل و نقاط شکست مستند کن.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «الگوهای طراحی» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** کاتالوگ‌های معماری از فناوری و نوع مسئله اثر می‌گیرند؛ عنوان یک الگو تضمین سازگاری نیست.
- **بازبینی:** الگوی POSA را به عنوان یک framework یا نسخهٔ سازمانی ثابت معرفی نکن.

## آموزش تکمیلی مستقل

### ۵. POSA و الگوهای معماری

POSA مخفف Pattern-Oriented Software Architecture است. در قیاس کلی، GoF بیشتر collaborationهای object و کلاس را پوشش می‌دهد، درحالی‌که POSA می‌تواند ساختار subsystem، concurrency، ارتباط شبکه‌ای و جریان runtime را توصیف کند. هنگام مطالعهٔ pattern معماری بپرس:

- چه نوع component و connector دارد؟
- کنترل و داده چگونه جریان می‌یابد؟
- کدام خاصیت مانند هم‌زمانی، fault isolation یا تغییرپذیری بهتر می‌شود؟
- چه فرضی دربارهٔ process، شبکه، failure و deployment دارد؟
- چه هزینهٔ عملیاتی ایجاد می‌کند و آیا گزینهٔ ساده‌تری هست؟

POSA نیز نسخهٔ ثابت نیست. pattern را با محدودیت سامانهٔ واقعی مقایسه کن. فهرست درس و منبع POSA در [فایل موضوعی](README.md) آمده است.

## نمودار نمونه: Broker

## نمودار نمونه: Broker

در معماری Broker، client به واسطه درخواست می‌دهد؛ broker سرویس را پیدا می‌کند و پیام را route می‌کند. client از محل server بی‌خبر می‌ماند، اما discovery، serialization، timeout و failureهای واسطه هزینهٔ واقعی‌اند. این نمودار یک صورت ساده‌شده است و همهٔ Brokerها یکسان نیستند.

**دام رایج:** broker مرکزی را بدون ظرفیت، دسترس‌پذیری و سیاست retry طراحی نکن.
**تمرین با پاسخ:** اگر server پاسخ نداد، broker باید timeout را به client گزارش کند یا retry محدود داشته باشد؛ retry نامحدود صف و تأخیر را پنهانی زیاد می‌کند.

این نمودار آموزشی است؛ سامانهٔ واقعی به قرارداد، مرز اعتماد و معنای شکستِ صریح نیاز دارد.

~~~text
[Client] -- request --> [Broker]
                           |
                  service discovery / route
                           v
                   [Server instance]
                           |
[Client] <-- response -- [Broker]
~~~
