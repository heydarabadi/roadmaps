# فصل ۰۴ — کارایی پایگاه داده

**زبان:** فارسی · [English version](README.en.md)


کندی صفحه سفارش ممکن است از انتظار اتصال، صدها رفت‌وبرگشت ORM، خواندن ردیف‌های زیاد، قفل یا دیسک باشد. این فصل کمک می‌کند این علت‌ها را جدا کنید و سپس تغییر متناسب را انتخاب کنید. هدف، کاهش کار لازم برای پاسخ درست است؛ افزایش تعداد اتصال، ایندکس یا Replica به‌تنهایی معیار موفقیت نیست.

این فصل دوازده مورد Databases در [نقشه راه Backend Performance](https://roadmap.sh/backend-performance-best-practices) را پوشش می‌دهد. **بررسی منابع: ۲۰۲۶-۱۱-۱۰**؛ پیوند `current` مستندات PostgreSQL هنگام بررسی نسخه ۱۸ را نشان می‌داد. برای اجرای واقعی، مستندات نسخه نصب‌شده را ببینید. همه SQLها و عددهای تمرین آموزشی‌اند و در این مجموعه اجرا نشده‌اند.

**همه درس‌ها به‌صورت خودبسنده در همان صفحه آموزش داده می‌شوند؛ پیوندهای منابع، مطالعه اختیاری برای تعمیق یا بررسی جزئیات موتورند و پیش‌نیاز انجام درس نیستند.**

## پیش‌نیاز و مسیر تشخیصی

Replication و Sharding پس از بررسی این مسیر مطرح می‌شوند.

## سناریوی پیوسته فصل

فروشگاهی آموزشی فهرست سفارش‌های یک مشتری را نشان می‌دهد. ابتدا زمان Pool و تعداد SQL هر درخواست را ثبت کنید. یک Pool محدود با بازگرداندن قطعی اتصال بسازید؛ برای فیلتر مشتری و ترتیب زمان، ایندکس متناسب بررسی کنید. نام مشتری را batch بگیرید، ستون بدنه رسید را از فهرست حذف کنید و پیمایش عمیق را با Keyset بسنجید. برای گزارش روزانه، Read model با زمان آخرین بازسازی تعریف کنید. پس از آن، آمار، VACUUM و قفل‌ها را بررسی کنید. فقط اگر بار خواندن باقی‌مانده و بودجه کهنگی توجیه داشت، Replica اضافه کنید؛ برای شارد کردن ابتدا الگوی دسترسی tenant و خطر tenant داغ را بنویسید.

این سناریو فرضی است. [گزارش مهندسی Discord در ۲۰۲۳](https://discord.com/blog/how-discord-stores-trillions-of-messages) نمونه واقعی اثر الگوی دسترسی و Hot partition است؛ نتیجه آن مجوز تعمیم انتخاب موتور به هر فروشگاه نیست.

## چک‌لیست پایان فصل

- [ ] زمان صف اتصال، اجرای SQL و پاسخ انتهابه‌انتها را جدا می‌سنجم.
- [ ] ظرفیت Pool تمام replicaهای برنامه و رزرو عملیاتی را جمع می‌کنم.
- [ ] ایندکس را با Query plan و هزینه write می‌سنجم.
- [ ] SQL تولیدشده ORM، تعداد query و اندازه نتیجه را دیده‌ام.
- [ ] Pagination ترتیب قطعی و Projection ستون‌های ضروری دارد.
- [ ] Read model مالک، بودجه کهنگی، replay و reconciliation دارد.
- [ ] Join معنا و cardinality درست دارد و VACUUM/ANALYZE پایش می‌شود.
- [ ] Slow log داده حساس را محافظت می‌کند؛ Profiling بازه و reset مشخص دارد.
- [ ] Replica جای Backup نیست و Failover، lag و read-after-write طراحی شده‌اند.
- [ ] پیش از Sharding، هزینه routing، hotspot، تراکنش و migration روشن است.
