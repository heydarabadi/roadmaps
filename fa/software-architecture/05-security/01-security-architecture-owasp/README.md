# تهدیدمدل‌سازی، OWASP و امنیت از طراحی

امنیت را از دارایی‌ها، مرز اعتماد و سوءاستفاده‌های محتمل شروع کن؛ چک‌لیست آسیب‌پذیری جای شناخت محصول را نمی‌گیرد. Threat modeling با STRIDE یا روش مشابه به تیم کمک می‌کند تهدید، کنترل، مالک و شواهد آزمون را ثبت کند. OWASP Top 10 آگاهی عمومی وب است؛ OWASP API Security ریسک‌های API را پوشش می‌دهد. هیچ‌کدام گواهی امن‌بودن محصول نیستند.

در فروشگاه، دارایی‌ها حساب مشتری، آدرس، پرداخت، اعتبار سبد و کلید API هستند. مرزهای مهم از مرورگر تا gateway، سرویس سفارش، provider پرداخت و دسترسی staff می‌گذرند. تهدیدها می‌توانند سرقت session، IDOR، injection، replay callback، نشت log و سوءاستفاده از دسترسی مدیر باشند.

کنترل‌های دفاعی شامل least privilege، اعتبارسنجی، TLS، مدیریت secret، segmentation شبکه، audit log، patching، backup آزموده‌شده و پاسخ رخدادند. هر کنترل را به تست یا telemetry وصل کن و استثنای پذیرفته‌شده را ثبت کن.

| هدف | کنترل نمونه | مدرک |
| --- | --- | --- |
| جلوگیری از دسترسی غیرمجاز | authorization برای هر resource/action | تست منفی |
| کاهش آسیب credential | secret manager و rotation | بازبینی تنظیمات |
| تشخیص حمله | log ساختاریافته و alert معنادار | تمرین رخداد |
| بازیابی | backup و تمرین restore | نتیجه و زمان بازیابی |

## درس گام‌به‌گام: threat modeling

۱. **سامانه و هدف را محدود کن.** جریان داده را بکش: client، API، سرویس، دیتابیس، provider پرداخت، صف و مدیر سیستم. مرزهایی را که داده از سطح اعتماد عبور می‌کند مشخص کن.
۲. **دارایی و آسیب را بنویس.** اطلاعات شخصی، credential، اعتبار/موجودی، دسترس‌پذیری سفارش و توان تغییر قیمت را جدا کن. پیامد سوءاستفاده را برای هرکدام توضیح بده.
۳. **کنشگر و سوءاستفاده را تصور کن.** کاربر عادی، کارمند، سرویس همکار، مهاجم ناشناس و account تصاحب‌شده را در نظر بگیر. بپرس مهاجم چه می‌خواهد بخواند، عوض کند، جعل کند یا از کار بیندازد.
۴. **STRIDE را یادآور قرار بده.** Spoofing جعل هویت؛ Tampering تغییر داده یا درخواست؛ Repudiation نبود شواهد قابل‌اتکا؛ Information disclosure افشای داده؛ Denial of service مصرف منابع؛ Elevation of privilege گرفتن اختیار بیشتر. همهٔ دسته‌ها برای هر جریان الزاماً مصداق ندارند.
۵. **اولویت را بر اساس ریسک تعیین کن.** احتمال، اثر، سطح مواجهه و کنترل موجود را ثبت کن. عدد ریسک فقط برای مقایسهٔ شفاف است، نه حقیقت قطعی.
۶. **کنترل و آزمون را به تهدید وصل کن.** برای IDOR تست دو tenant؛ برای replay ارسال callback تکراری؛ برای نشت log جست‌وجوی token؛ برای DoS محدودیت نرخ و آزمون بار کنترل‌شده.
۷. **مالک و موعد تعیین کن.** ریسک باقی‌مانده، مالک، اقدام و زمان بازبینی را بنویس. پذیرش ریسک باید آگاهانه و بازبینی‌پذیر باشد، نه بی‌صاحب.

## مثال حل‌شده: مشاهدهٔ سفارش

**قابلیت:** مشتری فقط سفارش‌های خودش را می‌بیند. **سوءاستفاده:** کاربر شناسهٔ سفارش را عوض می‌کند و سفارش دیگری را می‌خواند. **مرز خطا:** پنهان‌کردن شناسه یا دکمه در UI. **کنترل:** query سفارش را با شناسهٔ کاربر یا tenant معتبر محدود کن و مجوز را برای هر resource بررسی کن. **آزمون:** کاربر A سفارش B را درخواست کند؛ هیچ دادهٔ حساس در body، header یا log پاسخ نشود. **شواهد:** تست منفی خودکار، audit event بدون اطلاعات حساس و alert برای الگوی enumeration.

## امنیت در چرخهٔ توسعه

- در طراحی، جریان داده، مرز اعتماد و abuse case را مرور کن.
- در پیاده‌سازی، secure default، اعتبارسنجی، مجوز هر عمل، مدیریت secret و بررسی dependency را به‌کار ببر.
- در بازبینی، کد و تنظیم deployment، IAM، storage و شبکه را ببین.
- پیش از انتشار، آزمون متناسب با ریسک و patch dependency را انجام بده؛ اسکن موفق امنیت کلی را ثابت نمی‌کند.
- در عملیات، log محدود و ساختاریافته، alert، پاسخ رخداد، revoke credential و restore تمرین‌شده لازم است.

OWASP Top 10 دسته‌های رایج وب را برای آگاهی و گفت‌وگو خلاصه می‌کند. Threat model سوءاستفاده را از زمینهٔ واقعی محصول استخراج می‌کند و با تغییر مهم به‌روز می‌شود. هیچ فهرست عمومی همهٔ حملات، خطاهای پیکربندی و سوءاستفاده‌های تجاری را تضمین نمی‌کند.

## آزمون

۱. OWASP Top 10 چه چیزی نیست؟ **پاسخ:** threat model کامل یا اثبات امنیت برنامه.
۲. چرا authorization سمت server لازم است؟ **پاسخ:** کنترل client قابل دورزدن است؛ policy باید برای resource/action سنجیده شود.
۳. دفاع در عمق یعنی چه؟ **پاسخ:** چند کنترل مستقل برای کاهش احتمال و اثر شکست یک کنترل.
۴. threat model چه خروجی دارد؟ **پاسخ:** تهدید اولویت‌دار، کنترل، مالک، آزمون و ریسک پذیرفته‌شده.

## تمرین

برای endpoint مشاهدهٔ سفارش، سه abuse case بنویس و کنترل و آزمون هرکدام را تعیین کن.

## پاسخ نمونهٔ تمرین

سه abuse case: تغییر order ID برای IDOR؛ enumeration با IDهای افزایشی؛ افشای PII در response/log. برای هرکدام، authorization روی مالکیت/tenant در query سرور، rate limit/monitoring و response با حداقل داده را تعریف کن. آزمون منفی با دو user/tenant و بررسی log باید ثابت کند دادهٔ دیگری قابل‌دیدن نیست.
