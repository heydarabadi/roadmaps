## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

لایه‌ها مسئولیت UI، هماهنگی کاربرد، دامنه و زیرساخت را جدا می‌کنند؛ مدل دامنه نباید ناخواسته به دیتابیس و کنترلر وابسته شود.

## مثال کاربردی

use case سفارش، مدل دامنه را فراخوانی می‌کند و repository در لایهٔ زیرساخت آن را ذخیره می‌کند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «برنامه‌نویسی شیءگرا» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** لایه‌سازی رفت‌وبرگشت و mapping اضافه می‌کند؛ برای پروژهٔ کوچک کم‌لایه شروع کن.
- **بازبینی:** اگر هر لایه فقط همان داده را منتقل می‌کند بدون محافظت از مرز، هزینهٔ خالص دارد.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: لایه‌ها مسئولیت UI، هماهنگی کاربرد، دامنه و زیرساخت را جدا می‌کنند؛ مدل دامنه نباید ناخواسته به دیتابیس و کنترلر وابسته شود.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: use case سفارش، مدل دامنه را فراخوانی می‌کند و repository در لایهٔ زیرساخت آن را ذخیره می‌کند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: لایه‌سازی رفت‌وبرگشت و mapping اضافه می‌کند؛ برای پروژهٔ کوچک کم‌لایه شروع کن.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: اگر هر لایه فقط همان داده را منتقل می‌کند بدون محافظت از مرز، هزینهٔ خالص دارد.

## آموزش تکمیلی مستقل

### ۵. لایه‌بندی و جهت وابستگی

لایه‌های منطقی متداول:

1. **Presentation:** ورودی/خروجی HTTP، UI یا پیام را تبدیل می‌کند.
2. **Application:** use case را هماهنگ و transaction را مدیریت می‌کند.
3. **Domain:** مفهوم‌ها و invariantهای کسب‌وکار را نگه می‌دارد.
4. **Infrastructure:** دیتابیس، broker و providerهای خارجی را وصل می‌کند.

این لایه‌ها لزوماً process یا deploy جدا نیستند. قاعدهٔ اصلی، کنترل dependency است: domain به web framework یا ORM وابسته نشود؛ adapter بیرونی قرارداد لازم برای use case را پیاده کند. جریان فراخوانی زمان اجرا ممکن است به سمت بیرون باشد، ولی dependency source در لایهٔ domain نباید به جزئیات بیرونی جهت بگیرد.

~~~text
HTTP controller -> application use case -> domain model
infrastructure adapter implements a domain/application port
~~~

برای CRUD کوچک شاید تمام لایه‌ها نیاز نباشند. mapping و boilerplate را در برابر آزمون‌پذیری، استقلال قواعد و هزینهٔ تغییر بسنج. مرز خوب از یک تغییر واقعی محافظت می‌کند؛ پوشه‌بندی صرف به‌تنهایی معماری نمی‌سازد.

## نمونهٔ کد مرحله‌ای

در مدل لایه‌ای، controller درخواست را به use case می‌دهد؛ use case قواعد را هماهنگ می‌کند و از قرارداد repository استفاده می‌کند؛ adapter جزئیات SQL را پیاده می‌سازد. وابستگی منبع باید از policy به قرارداد اشاره کند، حتی اگر فراخوانی زمان اجرا به بیرون برسد.
**تمرین با پاسخ:** اگر تغییر ORM فایل‌های دامنه را دست می‌زند، مرز وابستگی برعکس یا نشت کرده است؛ interface را در سمت policy قرار بده.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا تصمیم طراحی روشن بماند.

~~~csharp
public interface IOrderStore
{
    Task Save(Order order, CancellationToken ct);
}

public sealed class PlaceOrder(IOrderStore store)
{
    public async Task Execute(Order order, CancellationToken ct)
    {
        order.ValidateForPlacement();
        await store.Save(order, ct);
    }
}
~~~
