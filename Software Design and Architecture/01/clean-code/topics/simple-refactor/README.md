# سادگی و بازآرایی پیوسته — Keep it simple and refactor often


> **زبان:** [نسخهٔ انگلیسی](../../../../en/01/clean-code/topics/simple-refactor/README.md)

[فصل کد تمیز](../../README.md) · [فهرست دوره](../../../../00-index.md)

## هدف درس

بتوانی مسئلهٔ این اصل را تشخیص بدهی، آن را در کد به‌کار ببری، trade-off را توضیح بدهی و در آزمون از نتیجه دفاع کنی.

## آموزش دقیق

سادگی یعنی فهم مسئله به کمترین مفهوم‌های لازم نیاز داشته باشد؛ نه اینکه validation، امنیت یا audit حذف شود. Refactoring ساختار داخلی را بهتر می‌کند بدون تغییر رفتار قابل مشاهده. برای همین باید تغییر ساختاری را از افزودن feature جدا نگه داری.

۱. رفتار را با آزمون مشخص کن؛ در legacy از characterization test آغاز کن.
۲. یک گام محدود انجام بده: rename، extract function، جابه‌جایی مسئولیت یا حذف تکرار.
۳. آزمون و diff را ببین، سپس گام بعدی را بردار.
۴. پس از تثبیت ساختار، نیازمندی جدید را جدا پیاده کن.
۵. cleanup را به محدودهٔ مرتبط نگه دار؛ بازنویسی بزرگ را پیش‌فرض نکن.

## مثال

دو endpoint فرمول تخفیف یکسان را پیاده کرده‌اند. ابتدا نرخ‌ها، rounding و مرز صفر را در آزمون ثبت کن؛ سپس سیاست را در نقطهٔ مشترک قرار بده؛ بعد قابلیت بعدی را اضافه کن. اگر قاعده هنوز از متخصص دامنه روشن نیست، کد را با حدس بازنویسی نکن.

## هزینه و خطاها

بازآرایی زمان می‌گیرد و ساختار قشنگ‌تر لزوماً ارزش محصولی ندارد. کد پرخطر و پرتغییر اولویت دارد. از شاخص «هر commit باید تمیزکاری داشته باشد» نسخهٔ مطلق نساز؛ هدف تغییر امن و خوانا است.

## تمرین

یک smell واقعی انتخاب کن، رفتار و آزمون محافظ را ثبت کن و سه گام کوچک بازآرایی طراحی کن. در هر گام، اگر آزمون شکست، علت را قبل از ادامه پیدا کن.

## نمونهٔ کد/قرارداد

~~~text
1. add or identify a behavior-preserving test
2. make one structural change
3. run the relevant test
4. inspect the diff
5. repeat; add new behavior in a separate change
~~~

## تمرین سنجش

نمونه‌ای از کد خودت یا یک پروژهٔ آموزشی انتخاب کن. مفهوم را در یک تغییر کوچک اعمال کن، آزمونی برای رفتار مرزی اضافه کن و با یک جمله ثبت کن که چه چیزی خواناتر یا امن‌تر شد.

## کوییز با پاسخ تشریحی

پیش از دیدن پاسخ، دلیل خودت را بنویس. پاسخ پیشنهادی باید با زمینه هماهنگ باشد؛ اگر گزینهٔ دیگری داری، trade-off آن را هم بیان کن.

1. **Refactoring چه چیزی را تغییر نمی‌دهد؟**
   - پاسخ تشریحی: رفتار قابل مشاهده و قرارداد بیرونی؛ ساختار داخلی را اصلاح می‌کند.
2. **چرا feature و refactor را جدا می‌کنی؟**
   - پاسخ تشریحی: علت شکست روشن‌تر و rollback و review دقیق‌تر می‌شوند.
3. **در کد legacy از کجا شروع می‌کنی؟**
   - پاسخ تشریحی: با درک رفتار فعلی و characterization tests برای بخش پرریسک.
