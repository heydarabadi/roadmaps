## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

سیاست سطح بالا قواعد کسب‌وکار است؛ جزئیات مانند وب‌فریم‌ورک، فایل و دیتابیس باید در لایهٔ بیرونی به سیاست وابسته باشند، نه برعکس.

## مثال کاربردی

قانون مجازبودن بازپرداخت از EF Core و HTTP جدا می‌ماند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «اصول معماری» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** مرز زیاد می‌تواند پروژهٔ ساده را بی‌جهت لایه‌لایه کند.
- **بازبینی:** اگر تغییر ORM منطق دامنه را مجبور به تغییر می‌کند، جهت وابستگی نشتی دارد.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: سیاست سطح بالا قواعد کسب‌وکار است؛ جزئیات مانند وب‌فریم‌ورک، فایل و دیتابیس باید در لایهٔ بیرونی به سیاست وابسته باشند، نه برعکس.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: قانون مجازبودن بازپرداخت از EF Core و HTTP جدا می‌ماند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: مرز زیاد می‌تواند پروژهٔ ساده را بی‌جهت لایه‌لایه کند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: اگر تغییر ORM منطق دامنه را مجبور به تغییر می‌کند، جهت وابستگی نشتی دارد.

## آموزش تکمیلی مستقل

### ۲. Policy در برابر Detail

Policy تصمیمی است که رفتار کسب‌وکار را تعیین می‌کند؛ detail راه فنی اجراست. قانون اینکه پس از چند روز بازپرداخت مجاز است policy است؛ استفاده از PostgreSQL، ASP.NET یا یک payment SDK detail است.

وابستگی source باید از detail به سمت policy برود: domain یا application قرارداد را تعریف کند؛ adapter دیتابیس و SDK آن را پیاده کنند. Runtime call ممکن است از policy به adapter برسد، اما کد policy نباید type و API بیرونی را مستقیماً بشناسد.

~~~text
Payment use case -> PaymentAuthorizer port <- Vendor adapter -> provider SDK
~~~

پنهان‌کردن همهٔ technologyها هدف نیست. اگر ORM قابلیت لازم دارد یا mapping هزینه می‌سازد، از آن استفاده کن؛ اما بدان کجا portability و testability را قربانی می‌کنی. مرز وقتی ارزشمند است که policy مستقل تغییر یا آزمون شود.

## نمودار معماری و خواندن مرحله‌ای

Policy بیان می‌کند سامانه چه تصمیمی می‌گیرد؛ detail توضیح می‌دهد آن را با چه کتابخانه، شبکه یا پایگاه‌داده‌ای اجرا می‌کنیم. detail می‌تواند به port وابسته باشد و policy باید در آزمون مستقل بماند.
**دام رایج:** runtime control flow را با dependency source یکی ندان.
**تمرین با پاسخ:** برای آزمون پرداخت، gateway جعلی را از راه contract تزریق کن؛ کد policy نباید به SDK واقعی یا شبکه وابسته باشد.

این نمودار ساده فقط یک view را نشان می‌دهد؛ سامانهٔ واقعی به تصمیم روشن دربارهٔ شکست، امنیت و مالکیت هم نیاز دارد.

~~~text
Source dependency points inward:
[Web / database / SDK] ---> [Ports] <--- [Business policy]

Runtime control may point outward:
[Business policy] ---> [Port] ---> [Web / database / SDK]
~~~
