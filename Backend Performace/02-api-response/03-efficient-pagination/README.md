# صفحه‌بندی کارآمد API — Efficient Pagination

**زبان:** فارسی · [English version](README.en.md)


Pagination قراردادِ دیدن یک مجموعه در چند پاسخ محدود است. API به کلاینت می‌گوید چه چیزی برگردانده، چگونه ادامه بدهد و چه زمانی پیمایش تمام شده است. این قرارداد هم حجم هر پاسخ را کنترل می‌کند و هم مانع الزام کلاینت به نگهداری کل مجموعه می‌شود.

**پس از این درس می‌توانید:** میان قرارداد API و اجرای Query تفاوت بگذارید؛ Page/Offset/Cursor را متناسب با کاربرد انتخاب کنید؛ سقف صفحه، ترتیب، پایان و خطای Token را تعریف کنید؛ و اثر تغییر داده میان صفحات را توضیح دهید. پیش‌نیاز: Endpoint فهرستی و [بودجهٔ Payload](../01-payload-size/README.md). تاریخ بررسی منابع: **۲۰۲۶-۱۱-۱۰**.

## اصطلاح‌های پایه

**Endpoint** نشانی و قراردادی است که کلاینت برای یک عمل API صدا می‌زند. **ترتیب قطعی** یعنی برای هر دو رکورد جایگاه مشخص داریم؛ اگر تاریخ برابر باشد، شناسهٔ پایدار می‌تواند tie-breaker باشد. **Token/Cursor** اطلاعات ادامهٔ پیمایش است که در این مثال opaque می‌ماند.

## مرز دقیق API و پایگاه داده

| لایه | مسئولیت | نمونهٔ سؤال |
| --- | --- | --- |
| API Pagination، موضوع این صفحه | قرارداد درخواست و پاسخ، Token، ترتیب، پایان و سازگاری | کلاینت بعد از این صفحه چه درخواستی بفرستد؟ |
| Database Pagination | اجرای محدود و مرتب Query، Keyset/Offset، Index و Plan | DB برای صفحهٔ بعد چند ردیف می‌خواند؟ |

داشتن `page_size=20` در URL تضمین نمی‌کند DB فقط ۲۰ ردیف پردازش کند؛ ممکن است برنامه همهٔ داده را واکشی و سپس Slice کند. برعکس، Query با `LIMIT` خوب به‌تنهایی به کلاینت قرارداد ادامه نمی‌دهد. SQL، Index مرکب و هزینهٔ Offset عمیق در [صفحه‌بندی پایگاه داده](../../04-databases/04-efficient-database-pagination/README.md) تدریس می‌شود؛ اینجا روی تعهد بیرونی تمرکز می‌کنیم.

## انتخاب شکل قرارداد

| روش | نمونهٔ درخواست | مناسب برای | هزینه/محدودیت |
| --- | --- | --- | --- |
| شمارهٔ صفحه | `?page=4&page_size=20` | رابطی با «برو به صفحهٔ ۴» | درج/حذف می‌تواند مرز صفحه را جابه‌جا کند؛ اجرای عمیق باید بررسی شود |
| Limit/Offset | `?limit=20&offset=60` | مصرف ساده و مجموعهٔ کوچک/کم‌تغییر | Offset بزرگ و تغییر هم‌زمان داده دردسرساز است |
| Cursor/Token | `?page_size=20&page_token=...` | Feed و پیمایش متوالی مجموعهٔ بزرگ | پرش دلخواه و تعداد کل ساده نیست؛ به ترتیب و Token معتبر نیاز دارد |

Cursor نام یک خانوادهٔ قرارداد است؛ هر Token لزوماً Keyset SQL نیست. Token می‌تواند اشاره به موقعیت، Snapshot یا وضعیت سمت سرور باشد. «Cursor همیشه O(1) است» یا «Cursor همیشه Snapshot کامل می‌دهد» ادعای درستی دربارهٔ همهٔ APIها نیست. مستندات Django REST نمونه‌های هر سه سبک و نیاز Cursor به ترتیب مناسب را نشان می‌دهد؛ رفتار دقیق آن Framework را به همهٔ پیاده‌سازی‌ها تعمیم ندهید. [Django REST pagination](https://www.django-rest-framework.org/api-guide/pagination/)

### اجزایی که باید پیش از عرضه روشن شوند

1. **اندازهٔ صفحه:** مقدار پیش‌فرض و حداکثر را مستند کنید. اگر درخواست بیش از سقف است، Clamp یا خطای پارامتر را یکدست اجرا کنید؛ تعداد برگشتی ممکن است به‌علت سقف بایت کمتر باشد.
2. **ترتیب قطعی:** مثلاً `created_at DESC, id DESC`. فقط تاریخ کافی نیست، چون چند رکورد می‌توانند زمان برابر داشته باشند. فیلد ترتیبِ قابل تغییر نیازمند توضیح رفتار جابه‌جایی است.
3. **ادامه و پایان:** `next_page_token` یا لینک `next` معیار ادامه باشد. در قرارداد Token، صفحهٔ کوتاه الزاماً پایان نیست؛ حتی صفحهٔ خالی می‌تواند Token ادامه داشته باشد.
4. **Token مبهم برای کلاینت:** مصرف‌کننده نباید ساختار آن را Parse کند یا بسازد. Token موقعیت است، نه مجوز؛ دسترسی هر صفحه باید دوباره بررسی شود.
5. **ثبات پارامترها:** Filter، ترتیب، Tenant و نمایش مرتبط را به پیمایش متصل کنید. تغییر Filter همراه Token قدیمی باید رفتار مشخص داشته باشد.
6. **انقضا و تغییر داده:** خطای Token نامعتبر/منقضی و راه شروع مجدد را تعریف کنید. برای گزارش حسابرسی، Snapshot یا Export با مرز دادهٔ ثابت لازم است؛ Feed زنده نیاز متفاوتی دارد.

این اصول با [Google AIP-158](https://google.aip.dev/158) هم‌راستا هستند: صفحه‌بندی را از ابتدا در قرارداد مجموعه ببینید؛ Token برای کلاینت opaque باشد؛ از Token به‌جای Authorization استفاده نشود. AIP برای APIهای پیرو آن قواعد مشخصی دارد؛ عدد سقف و شکل خطای مثال ما یک قرارداد آموزشی مستقل است.

## مثال حل‌شده: فهرست سفارش‌های پرداخت‌شده

**قرارداد فرضی:** پیش‌فرض ۲۰ و حداکثر ۵۰ آیتم؛ بیش از سقف به ۵۰ Clamp می‌شود؛ عدد منفی `400` دارد. ترتیب نزولی `(created_at,id)`؛ Token به Tenant و Filter متصل است. پایان با حذف `next_page_token` مشخص می‌شود و `total_count` پیش‌فرض وجود ندارد.

توکن‌های بالا فقط جای‌نگهدارند. در پیاده‌سازی، از Token قابل‌اعتبارسنجی یا نگاشت سمت سرور استفاده کنید؛ Base64 به‌تنهایی جلوی دست‌کاری یا افشای اطلاعات را نمی‌گیرد. اگر حاوی دادهٔ حساس است، امضا فقط صحت را حفظ می‌کند و محرمانگی ایجاد نمی‌کند. Token را کوتاه‌عمر و بدون اطلاعات حساس طراحی کنید یا از سازوکار مناسب حفاظت استفاده کنید.

در این مثال اگر سفارش جدیدی با زمان جدیدتر بین دو درخواست اضافه شود، ادامه از مرز قبلی می‌تواند از تکرار ابتدای Feed جلوگیری کند؛ ولی تضمین مشاهدهٔ دقیقاً یک‌بارهٔ همهٔ رکوردهای قابل تغییر نمی‌دهد. حذف، تغییر وضعیت یا تغییر فیلد مرتب‌سازی می‌تواند نتیجه را عوض کند. تضمین لازم برای Feed، پیمایش مدیریتی و خروجی مالی را جدا تعریف کنید.

**چرا Count پیش‌فرض نداریم؟** دانستن «آیا ادامه هست؟» با «کل نتایج دقیقاً چندتاست؟» یکی نیست. Count می‌تواند Query جدا و گران باشد و با دادهٔ متغیر نیز سریعاً کهنه شود. اگر محصول به تعداد نیاز دارد، هزینه، تازگی و دقیق/تخمینی بودن را مستند کنید.

## تمرین کوتاه و راه‌حل نمونه

روی کاغذ یا در یک فایل، فهرست نزولی `8,7,6,5,4,3` و اندازهٔ صفحهٔ ۳ را در نظر بگیرید. صفحهٔ نخست `8,7,6` است. قبل از صفحهٔ دوم `9` را به ابتدا اضافه کنید.

1. با Offset برابر ۳، صفحهٔ دوم را پیدا کنید.
2. با مرز «بعد از شناسهٔ ۶ در ترتیب نزولی»، صفحهٔ دوم را پیدا کنید.
3. حالا وضعیت رکورد ۵ را از Filter خارج کنید؛ آیا هنوز Snapshot ثابت دارید؟

**انتظار:** Offset صفحهٔ دوم `6,5,4` می‌دهد و ۶ تکرار می‌شود. مرز نمونه `5,4,3` می‌دهد. خروج رکورد ۵ از Filter نشان می‌دهد Keyset ساده Snapshot نیست. این یک شبیه‌سازی قرارداد است؛ کارایی Query و Index را در فصل DB جدا بررسی کنید.

## راه‌حل گام‌به‌گام تمرین

فهرست آغازین `8,7,6,5,4,3` با صفحهٔ ۳، صفحهٔ نخست `8,7,6` می‌دهد. درج ۹ در ابتدا، فهرست را `9,8,7,6,5,4,3` می‌کند؛ Offset برابر ۳ از جایگاه صفرمبنا، `6,5,4` را برمی‌گرداند و ۶ تکراری است. Cursor «بعد از ۶» در همان ترتیب، `5,4,3` را می‌دهد. اگر ۵ از Filter خارج شود، نتیجهٔ بعدی می‌تواند کوتاه‌تر شود؛ این مرز ادامه ترتیب را نشان می‌دهد، نه Snapshot ثابت. برای Snapshot واقعی، منبع باید امکان خواندن همان نسخه یا مرز زمانی را حفظ کند و قرارداد API آن را اعلام کند.

## شاهد واقعی و حدود آن

**GitHub REST API:** راهنمای رسمی استفاده از `Link` Header و رابطهٔ `next` را برای رفتن به صفحات بعد توضیح می‌دهد؛ پارامترها می‌توانند بین Endpointها متفاوت باشند. به‌جای حدس زدن URL بعدی، لینک دریافتی را دنبال کنید. این یک قرارداد واقعیِ مصرف API است؛ از آن نتیجهٔ عددی دربارهٔ latency نمی‌گیریم. [GitHub: Using pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)

**WordPress REST API:** `per_page` را بین ۱ و ۱۰۰ می‌پذیرد و سقف را برای جلوگیری از Queryهای بسیار بزرگ توضیح می‌دهد. این سقف اختصاصی WordPress است، نه سقف توصیه‌شده برای همهٔ APIها. [WordPress: Pagination](https://developer.wordpress.org/rest-api/using-the-rest-api/pagination/)

شواهد این درس مستندات عملیاتی سرویس‌ها و Framework هستند؛ مطالعهٔ قبل/بعد از یک Incident خاص با درصد بهبود یکسان یافت نشده و چنین نتیجه‌ای ادعا نمی‌شود.

## شکست‌ها و نشانه‌های عملیاتی

| شکست | علامت | اصلاح |
| --- | --- | --- |
| `page_size` بی‌سقف یا `include` بی‌حد | پاسخ بزرگ، حافظه و p99 نامتناسب | سقف تعداد/بایت/Expand را هم‌زمان اعمال کن |
| Slice پس از واکشی کل مجموعه | DB و RAM با کل داده رشد می‌کند | محدودیت را به برنامهٔ Query منتقل کن |
| ترتیب غیرقطعی یا قابل تغییر | تکرار/گم‌شدن رکورد بین صفحات | Tie-breaker و تضمین‌های پیمایش را روشن کن |
| Token جای مجوز | دسترسی به Tenant دیگر با Token | Tenant و مجوز هر صفحه را بررسی کن |
| کلاینت با طول صفحه پایان را حدس می‌زند | توقف زودهنگام و دادهٔ ناقص | Token/لینک ادامه را معیار کن |
| Count دقیق در همهٔ صفحات | زمان Count بخش عمدهٔ Trace است | Count اختیاری/جدا با معنای روشن بده |
| گرفتن همهٔ صفحات با Parallel نامحدود | Burst و خطای Rate Limit | بودجه و Concurrency محدود برای Export تعیین کن |

### چک‌لیست عملیاتی

- [ ] Default/Max اندازه، عدد نامعتبر و رفتار Clamp مستندند.
- [ ] ترتیب قطعی و معنای تغییر هم‌زمان داده مشخص است.
- [ ] Token به قرارداد و محدودهٔ دسترسی متصل است؛ مجوز مستقل بررسی می‌شود.
- [ ] پایان، صفحهٔ خالی با ادامه، Token خراب و انقضا تعریف دارند.
- [ ] Query واقعاً صفحه‌ای اجرا می‌شود و Count جدا اندازه‌گیری شده است.
- [ ] تکرار رکورد، خطای Token، تعداد صفحه‌های طی‌شده، بایت/صفحه و p95/p99 پایش می‌شوند.
- [ ] پیمایش حسابرسی/Export در صورت نیاز مرز Snapshot مشخص دارد.

## آزمون

1. آیا وجود `page_size` در API ثابت می‌کند Query کارآمد است؟
2. چرا مرتب‌سازی فقط بر اساس `created_at` ممکن است کافی نباشد؟
3. صفحه ۷ آیتم از سقف ۲۰ و Token ادامه دارد؛ اقدام کلاینت چیست؟
4. آیا Cursor ساده تضمین Snapshot ثابت می‌دهد؟
5. آیا Base64 کردن شناسهٔ آخر، Token را امن و مجوزدار می‌کند؟
6. برای رابطی با پرش مستقیم به صفحهٔ ۲۵، چرا Cursor ممکن است انتخاب پرهزینه‌ای باشد؟

### پاسخ تشریحی

1. خیر؛ ممکن است همهٔ داده واکشی و سپس Slice شود. اجرای Query، تعداد ردیف خوانده‌شده و Plan جدا بررسی می‌شوند.
2. چند رکورد می‌توانند زمان برابر داشته باشند؛ یک Tie-breaker پایدار مانند شناسه ترتیب قطعی می‌سازد.
3. درخواست بعدی با Token/لینک اعلام‌شده بفرستد؛ طول کمتر به‌تنهایی پایان را ثابت نمی‌کند.
4. خیر؛ Cursor موقعیت ادامه را نگه می‌دارد، اما داده/Filter می‌تواند تغییر کند. Snapshot نیازمند تضمین مستقل است.
5. خیر؛ Base64 کدگذاری است. Token نباید جای مجوز باشد و محتوا/صحت آن نیز باید متناسب با طراحی محافظت شود.
6. Cursor معمولاً پیمایش متوالی می‌خواهد و لزوماً شمارهٔ صفحه یا Count ندارد. نیاز محصول و هزینهٔ روش‌های جایگزین را بسنجید.

## جمع‌بندی

Pagination هم قرارداد ادامهٔ کلاینت است و هم اجرای صفحه‌ای در منبع؛ یکی جای دیگری را نمی‌گیرد. سقف، ترتیب پایدار، Token opaque و رفتار تغییر/پایان را تعریف کنید و هزینهٔ Query، Count و بایت هر صفحه را جدا بسنجید.
