## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

منطق مصرف‌کننده به قراردادی وابسته می‌شود که نیازش را بیان می‌کند، نه به جزئیات یک SDK یا دیتابیس.

## مثال کاربردی

سرویس سفارش از `InventoryReservation` استفاده می‌کند و adapter آن را به API انبار وصل می‌کند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «اصول طراحی» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** انتزاع ضعیف جزئیات را پنهان نمی‌کند و تغییرش همه را می‌شکند.
- **بازبینی:** abstraction را صرفاً برای mockکردن بساز؛ قرارداد باید زبان مسئله را بازتاب دهد.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: منطق مصرف‌کننده به قراردادی وابسته می‌شود که نیازش را بیان می‌کند، نه به جزئیات یک SDK یا دیتابیس.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: سرویس سفارش از `InventoryReservation` استفاده می‌کند و adapter آن را به API انبار وصل می‌کند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: انتزاع ضعیف جزئیات را پنهان نمی‌کند و تغییرش همه را می‌شکند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: abstraction را صرفاً برای mockکردن بساز؛ قرارداد باید زبان مسئله را بازتاب دهد.

## آموزش تکمیلی مستقل

### ۹. Program to Abstractions

مصرف‌کننده به قراردادی وابسته باشد که نیاز خودش را بیان می‌کند، نه کلاس concrete یا SDK خارجی. این فکر به DIP نزدیک است اما تأکیدش بر انتخاب نقطهٔ استفاده است: use case فقط قابلیت authorize را می‌خواهد، نه تمام عملیات vendor.

abstraction باید معنا را حفظ کند و failure mode را ترجمه کند. اگر API هنوز type و exception vendor را بیرون می‌دهد، consumer همچنان به جزئیات بسته است. برای هر class concrete یک interface نساز؛ آن را برای مرز تغییر، تست یا چند implementation واقعی نگه دار.

## نمونهٔ کد مرحله‌ای

کد مصرف‌کننده به قرارداد نیاز دارد، نه به concrete class خاص؛ composition root پیاده‌سازی را انتخاب می‌کند. انتزاع باید واژگان نیاز مصرف‌کننده را بیان کند، نه اینکه صرفاً نام یک SDK را پنهان کند.
**تمرین با پاسخ:** use case فقط ارسال پیام می‌خواهد؛ به IMessageSender وابسته شود تا ایمیل یا پیامک بدون تغییر use case انتخاب شود.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا انتخاب طراحی روشن بماند.

~~~csharp
public interface IMessageSender
{
    Task Send(Message message, CancellationToken ct);
}

public sealed class ReminderJob(IMessageSender sender)
{
    public Task Run(Message message, CancellationToken ct)
        => sender.Send(message, ct);
}
~~~
