# مستندسازی معماری و ارتباط تصمیم‌ها

## هدف یادگیری

- نمای معماری را برای مخاطب و پرسش مشخص بساز.
- بین نمودار ساختار، جریان رفتار و نقشهٔ استقرار فرق بگذار.
- تصمیم و دلیلش را بدون مستندات انباشته و کهنه ثبت کن.

## ایدهٔ مرکزی

مستند معماری ابزار فکرکردن و هماهنگی است. نمودار بی‌عنوان و بی‌مخاطب می‌تواند گمراه کند؛ سند مفصل اما بی‌مصرف هم هزینهٔ نگهداری دارد. هر نما باید به پرسشی پاسخ دهد، مرزش را مشخص کند و با ساختار واقعی سامانه همگام بماند.

## نماها و مدل‌ها

- **C4:** زمینهٔ سامانه، containerهای قابل استقرار یا اجرا، مؤلفه‌ها و در صورت نیاز کد. در این مدل container الزاماً Docker نیست؛ می‌تواند برنامهٔ وب، worker، پایگاه داده یا فرایندی مستقل باشد.
- **UML:** برای نمایش رفتار یا ساختار با نمادهای متعارف، مانند sequence، component و deployment.
- **نمودار جریان:** برای توضیح مسیر سفارش، کنترل خطا یا فرایند تحویل.
- **مدل استقرار:** محل اجرا، شبکه، replication، وابستگی بیرونی و failure domain.
- **ADR:** ثبت یک تصمیم با زمینه، مسئله، گزینه‌ها، تصمیم، پیامد و وضعیت.

برای هر نمودار بنویس: هدف چیست؟ چه کسی باید آن را بخواند؟ چه چیزهایی خارج از محدوده‌اند؟ فلش چه نوع رابطه‌ای را نشان می‌دهد؟ مالک به‌روزرسانی چه کسی است؟ اگر تغییر معماری تغییرات کد را دنبال می‌کند، نگهداری در مخزن کد و بازبینی همراه pull request معمولاً مفید است.

## هر نما چه پرسشی را پاسخ می‌دهد؟

یک معماری کامل را نمی‌توان در یک نمودار جا داد. بهتر است چند نمای کوچک بسازی و هرکدام را با پرسش و مخاطب مشخص کنی:

| نما | پرسش | مخاطب رایج |
| --- | --- | --- |
| C4 Context | این سامانه برای چه کسی است و به چه سامانه‌های بیرونی وصل می‌شود؟ | مدیر محصول، معمار، تیم‌های وابسته |
| C4 Container | چه برنامه‌ها/فرایندها/داده‌گاه‌هایی در مرز سامانه‌اند و چطور حرف می‌زنند؟ | توسعه، platform، عملیات |
| Component | مسئولیت اصلی یک container به چه مؤلفه‌هایی تقسیم شده؟ | تیم همان سامانه |
| Sequence | یک درخواست موفق و شکست‌خورده از چه مرحله‌هایی عبور می‌کند؟ | توسعه، QA، آن‌کال |
| Deployment | جزءها کجا اجرا می‌شوند، از چه شبکه‌ای می‌گذرند و failure domain کجاست؟ | cloud/platform/security |

در C4، واژهٔ «container» به واحد اجرایی مانند web app، worker، mobile app یا database اشاره می‌کند و الزاماً container image نیست. این سوءتفاهم رایج می‌تواند مخاطب را به فکر اشتباه دربارهٔ فناوری بیندازد.

### روش ساخت نمودار قابل‌خواندن

۱. عنوان را به‌صورت جملهٔ هدف بنویس؛ مثلاً «این نمودار مسیر سفارش تا callback پرداخت را نشان می‌دهد».  
۲. محدوده را مشخص کن؛ چه چیزی داخل سیستم است و چه چیزی بیرون.  
۳. elementها را با نام نقش و مسئولیت بنویس، نه فقط نام vendor.  
۴. هر connector را برچسب بزن: پروتکل، نوع داده یا جهت جریان.  
۵. خطاهای مهم را در نمودار رفتار نشان بده؛ مسیر موفق تنها مسیر واقعی نیست.  
۶. legend، مالک و تاریخ بازنگری را اضافه کن.  
۷. از یک هم‌تیمی بخواه نمودار را بخواند؛ اگر باید توضیح شفاهی برای فهم هر فلش بدهی، نمودار هنوز روشن نیست.

## معماری به‌صورت متن

گاهی یک متن کوتاه از نمودار روشن‌تر است:

~~~text
سامانه: فروشگاه
مخاطبان: خریدار، تیم پشتیبانی، مالی
مرز: ثبت سفارش، تلاش پرداخت و وضعیت سفارش؛ شبکهٔ بانکی بیرون از مرز است
مالک داده: Checkout مالک سفارش؛ PaymentAttempt مالک تلاش پرداخت است
ارتباط: HTTPS برای درخواست پرداخت؛ callback امضاشده برای نتیجه؛ outbox برای اعلان داخلی
شرط شکست: timeout به معنی رد پرداخت نیست؛ وضعیت تا استعلام در انتظار می‌ماند
~~~

این متن هنوز جای قرارداد API، security model یا runbook را نمی‌گیرد؛ اما نقطهٔ شروعی است که واژگان کلیدی را یکسان می‌کند.

## ADR چیست و چه نیست؟

ADR به یک تصمیم معماری محدود است. بخش «زمینه» دلیل مطرح‌شدن تصمیم را می‌دهد؛ «گزینه‌ها» راه‌های معقول و هزینه‌هایشان را؛ «تصمیم» گزینهٔ منتخب را؛ «پیامدها» سود، هزینه و ریسک باقیمانده را. وضعیت می‌تواند پیشنهادی، پذیرفته‌شده، ردشده یا superseded باشد. اگر تصمیم عوض شد، ADR قبلی را پاک نکن؛ وضعیت و لینک به تصمیم جایگزین را ثبت کن تا تاریخچه قابل‌فهم بماند.

ADR را به یک design document صدصفحه‌ای تبدیل نکن. اگر موضوع نیازمند چند تصمیم است، آن را به چند record بشکن و میانشان پیوند بده. اگر مسئله موقت است و تصمیم محلی/برگشت‌پذیر، یک comment یا توضیح در pull request می‌تواند کافی باشد.

## الگوی سادهٔ ADR

~~~markdown
# ADR-004: صف پایدار برای پردازش پس‌زمینه

وضعیت: پذیرفته‌شده

## زمینه
تولید فاکتور نباید زمان پاسخ ثبت سفارش را مسدود کند.

## گزینه‌ها
اجرای هم‌زمان؛ صف پایدار؛ زمان‌بندی batch.

## تصمیم
رویداد سفارش ثبت‌شده را در outbox ذخیره و به صف منتشر می‌کنیم.

## پیامدها
پذیرش سریع‌تر؛ پردازش eventual؛ نیاز به deduplication و پایش lag صف.
~~~

## مثال واقعی‌نما: راهنمای عملیات

تیم آن‌کال هنگام قطعی درگاه پرداخت باید بداند جریان درخواست از کجا می‌گذرد، کجا timeout می‌شود، چه کسی مالک سرویس است، چگونه حالت degraded فعال می‌شود و چطور سفارش‌های نامشخص پیدا می‌شوند. یک C4 سطح بالا، نمودار توالی پرداخت، ADR retry و runbook کنار هم برای این مخاطب از یک نمودار رنگی عمومی مفیدترند.

## دام‌های متداول

- نمودار یکسان برای مدیر، توسعه‌دهنده و عملیات.
- ثبت فناوری بدون ثبت دلیل انتخاب و پیامدهای آن.
- ایجاد سندی که بعد از انتشار نخست به‌روزرسانی نمی‌شود.
- نشان‌دادن همهٔ کلاس‌ها در نمودار سامانه و پنهان‌کردن مرزهای مهم.
- استفاده از واژهٔ «real-time» بدون تعریف latency و تازگی داده.

## آزمون خودسنجی

۱. چرا C4 context و container اغلب برای شروع کافی‌اند؟  
**پاسخ:** پرسش‌های «سیستم در کجای محیط است؟» و «اجزای اجرایی و ارتباطشان چیست؟» را پوشش می‌دهند؛ جزئیات بیشتر را فقط وقتی ارزش دارد اضافه می‌کنیم.

۲. چه چیزی ADR را از مستند فنی عمومی متمایز می‌کند؟  
**پاسخ:** ADR یک تصمیم مشخص و دلیل آن را ثبت می‌کند و پیامدها و وضعیتش را پیگیری‌پذیر نگه می‌دارد.

۳. برای فهمیدن timeout در پرداخت، چه نمایی بهتر است؟  
**پاسخ:** نمودار توالی یا flow با مرزهای سیستم بیرونی، timeout، retry و مسیر خطا؛ در کنار نمای ساختاری.

۴. چه راهی برای کاهش کهنگی سند وجود دارد؟  
**پاسخ:** نگهداری متن در مخزن نزدیک کد، مالک روشن، بازبینی در تغییرات مربوطه و استفاده از مدل/نمودار به‌صورت کد وقتی مناسب است.

## تمرین

برای برنامهٔ ثبت سفارش یک C4 context ساده، یک نمودار توالی پرداخت و یک ADR دربارهٔ API هم‌زمان یا صف بساز. هرکدام باید مخاطب و پرسش پاسخ‌داده‌شده داشته باشد.

## پاسخ نمونهٔ تمرین

Context diagram مشتری، فروشگاه، provider پرداخت و ارسال را نشان می‌دهد. Sequence سفارش پیام create، authorize، callback، duplicate callback و timeout را با state هر actor نشان می‌دهد. ADR می‌تواند queue را برای اعلان/گزارش انتخاب کند چون پاسخ checkout نباید منتظر این side effect بماند؛ پرداخت اصلی تا جایی sync یا orchestration می‌شود که نتیجهٔ business نامشخص شود. در هر شکل، owner و failure مسیر را مشخص کن.
