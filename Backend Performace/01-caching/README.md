# فصل ۰۱ — کش و استفاده دوباره از نتیجه

**زبان:** فارسی · [English version](README.en.md)


کش یعنی نگهداری نسخه‌ای قابل بازسازی از یک پاسخ، داده یا محاسبه برای استفاده دوباره. پرسش اصلی این فصل «کجا Redis نصب کنیم؟» نیست؛ باید بدانیم کدام کار تکراری را حذف می‌کنیم، تا چه مدت نتیجه قابل قبول است و وقتی نسخه‌ها با هم اختلاف دارند چه رفتاری مجاز است. نتیجه برای کاربر می‌تواند انتظار کمتر باشد؛ نتیجه برای سامانه می‌تواند کاهش کار پایگاه داده و شبکه باشد، به شرط آنکه هزینه نگهداری کش و miss را هم بسنجیم.

این فصل چهار زیرموضوع Caching در [نقشه راه Backend Performance](https://roadmap.sh/backend-performance-best-practices) را پوشش می‌دهد. **تاریخ بررسی منابع: ۲۰۲۶-۱۱-۱۰**. مثال‌ها آموزشی و مستقل از زبان هستند؛ عددهای آن‌ها اندازه‌گیری یک شرکت یا هدف عمومی ظرفیت نیستند.

## پیش‌نیاز و مسیر مطالعه

با درخواست/پاسخ HTTP، تفاوت خواندن و نوشتن در پایگاه داده، تأخیر، صدک، و مفهوم چند نمونه از یک سرویس آشنا باشید. شناخت ابتدایی key/value کافی است؛ اجرای Redis یا داشتن حساب ابری پیش‌نیاز نیست. هر درس اصطلاح‌های ضروری خودش را هم تعریف می‌کند و به تنهایی قابل مطالعه است؛ پیوندهای موضوعی و منابع بیرونی اختیاری‌اند و برای فهم درس لازم نیستند.

درس‌ها توضیح و مثال خودبسنده دارند؛ برای اجرای تمرین‌ها سرویس خاصی لازم نیست، مگر صفحه صریحاً آن را پیشنهاد کند.

در هر درس ابتدا مدل و مثال را بخوانید، تمرین را با کاغذ یا ابزار دلخواه انجام دهید، سپس بدون دیدن پاسخ‌نامه به آزمون جواب دهید. تمرین‌ها آزمایش پیشنهادی‌اند؛ اجرای آن‌ها در محیط شما ادعا نشده است.

## سناریوی پیوسته فصل

یک کاتالوگ آموزشی سه نوع داده دارد: تصویر نسخه‌دار کالا، توضیح عمومی کالا، و قیمت نهایی سفارش. تصویر با URL دارای هش محتوا در مرورگر و CDN قابل استفاده دوباره است. توضیح عمومی می‌تواند کش پاسخ و کش داده با بودجه کهنگی مشخص داشته باشد. قیمت نهایی به اعتبارسنجی منبع و قواعد تراکنش نیاز دارد؛ نسخه نمایشی کش‌شده به‌تنهایی مجوز ثبت سفارش نیست.

۱. در درس اول مسیر درخواست را رسم کنید و مالک هر کش را بنویسید.

۲. در درس دوم برای توضیح کالا Cache-aside انتخاب کنید و مسیر commit و ابطال را مشخص کنید.

۳. در درس سوم فقط اگر هزینه مراجعه به کش مشترک مسئله شد، L1 محلی اضافه کنید و شکست ارتباط ابطال را شبیه‌سازی کنید.

۴. در درس چهارم هم‌زمانی انقضای یک کالای محبوب و به‌روزرسانی قیمت را تحلیل کنید.

این انتخاب‌ها نسخه نهایی معماری نیستند؛ باید با ترافیک، تازگی و ظرفیت منبع خود ارزیابی شوند. تجربه عملیاتی [Amazon درباره چالش‌های کش](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/) برای دیدن خطر وابستگی ظرفیت سرویس به کش گرم مفید است.

## چک‌لیست مرور فصل

- [ ] می‌توانم تفاوت کش private مرورگر، shared HTTP و کش داده سرور را با مثال توضیح دهم.
- [ ] می‌دانم `no-cache`، `no-store` و `private` یک معنی ندارند.
- [ ] مسئول loader و مسیر write برای هر الگوی کش مشخص است.
- [ ] کلید کش تمام ابعاد مؤثر بر نتیجه و جداسازی tenant را در نظر می‌گیرد.
- [ ] برای هر سطح hit/miss جدا و برای منبع تعداد درخواست واقعی دارم.
- [ ] بودجه کهنگی، مسیر commit/ابطال، و رفتار هنگام قطع پیام مشخص است.
- [ ] انقضا، eviction، refresh و ابطال دستی را از هم تفکیک می‌کنم.
- [ ] برای hot key، cold start، خرابی کش و هجوم هم‌زمان برنامه محدود و قابل مشاهده دارم.
