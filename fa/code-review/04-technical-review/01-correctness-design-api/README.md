# درستی رفتار، طراحی و قرارداد API

**زبان:** فارسی · [English](../../../../en/code-review/04-technical-review/01-correctness-design-api/README.md)

> مسیر: [فصل ۴ — بررسی فنی](../README.md) · [فهرست دوره](../../README.md)

## آموزش

بپرس آیا تغییر مسئله را در مسیر عادی و حالت‌های مرزی حل می‌کند: مقدار خالی، retry، timeout، ترتیب رویداد، دادهٔ قدیمی و خطای dependency. سپس طراحی و جای منطق را بسنج: سادگی، coupling، خوانایی، نام‌گذاری و سازگاری معماری.

قرارداد API را جدی بگیر. تغییر معنای null، enum، pagination، مجوز یا خطا می‌تواند مصرف‌کنندگان را بشکند حتی اگر کد داخلی compile شود. رفتار قبلی، clientهای قدیمی و rollout چند نسخه‌ای را بررسی کن. برای چند راه‌حل معتبر، trade-off را مطرح کن؛ بهترین راه الزاماً ترجیح شخصی reviewer نیست.

Google هم review را فراتر از style می‌داند و بر design، functionality، complexity، tests، naming و documentation تاکید دارد. تغییر باید سلامت کلی سیستم را بهتر کند، نه فقط نیاز امروز را با پیچیدگی غیرضروری جواب دهد.

## روند پیشنهادی

1. رفتار مطلوب را از requirement بنویس.
2. موفقیت، خطا و edge case را دنبال کن.
3. contract و مصرف‌کننده‌های بیرونی را بررسی کن.
4. اثر تغییر بر معماری و سازگاری را بسنج.
5. طراحی را با پیامد توضیح بده، نه سلیقه.

## مثال کاربردی

افزودن فیلد API: آیا client قدیمی فیلد ناشناخته را تحمل می‌کند؟ آیا null با حذف فرق دارد؟ آیا schema و docs به‌روزند؟ آیا سرویس‌های قدیم و جدید هم‌زمان می‌توانند اجرا شوند؟

## خطاهای رایج

فقط happy path را ببین؛ ترجیح شخصی را bug بنام؛ API را بی‌توجه به client بشکن؛ برای آیندهٔ فرضی بیش‌مهندسی کن.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** کدام حالت مرزی برای API باید بررسی شود؟

   1. نام branch
   2. رفتار null/فیلد حذف‌شده و مصرف‌کنندهٔ قدیمی
   3. قالب ادیتور
   4. تعداد فایل

**پاسخ:** 2 — قرارداد API رفتار دادهٔ غایب را تعریف می‌کند.

### پرسش 2

**سؤال:** تغییر کوچک API چه ریسک دارد؟

   1. هیچ
   2. ممکن است معنای مورد انتظار clientها را بشکند
   3. فقط lint
   4. تست را حذف می‌کند

**پاسخ:** 2 — سطح مصرف‌کنندگان می‌تواند وسیع باشد.

### پرسش 3

**سؤال:** دو طراحی معتبر داریم؛ reviewer چه کند؟

   1. راه خود را تحمیل کند
   2. قیود و trade-off را روشن کند
   3. PR را رد کند
   4. راه پیچیده‌تر را بخواهد

**پاسخ:** 2 — تصمیم باید به نیاز و شواهد وصل باشد.

### پرسش 4

**سؤال:** برای بسنجیدن صحت رفتار چه لازم است؟

   1. نام خوب
   2. سناریو و انتظار قابل مشاهده
   3. کامنت بیشتر
   4. فقط compile

**پاسخ:** 2 — درستی را نسبت به نیازمندی می‌سنجیم.

## آموزش عمیق: از نیازمندی تا invariant

### بررسی درستی با چهار پرسش

1. **چه چیزی باید درست باشد؟** نیازمندی یا معیار پذیرش را به رفتار قابل‌مشاهده تبدیل کن.
2. **در کدام مسیرها؟** مسیر معمول، ورودی مرزی، حالت خالی، خطا، retry، درخواست هم‌زمان و دادهٔ قدیمی را بررسی کن.
3. **چه چیزی حفظ می‌شود؟** invariantها را نام ببر: مثلاً «هر پرداخت به حداکثر یک سفارش متصل است» یا «کاربر فقط رکورد tenant خود را می‌بیند».
4. **تغییر اطراف چه اثری دارد؟** callerها، clientهای قدیمی، queue، cache، database و feature flag را دنبال کن.

کد می‌تواند ظاهراً نیازمندی را اجرا کند ولی رفتار برای کاربر بد باشد. مثلاً پاسخ 404 در همهٔ خطاها ممکن است «عملیات موفق» نشان ندهد؛ اما اگر API برای جلوگیری از افشای وجود حساب عمداً پاسخ یکسان می‌دهد، نباید آن را به‌عنوان bug تغییر داد. سیاست محصول و امنیت زمینه را تعیین می‌کنند.

### طراحی و قرارداد

بررسی طراحی یعنی منطق در جای مناسب، وابستگی‌ها قابل‌فهم و تغییر با الگوی موجود سازگار باشد. سادگی به معنای کمترین خطوط نیست؛ منظور مدلی است که هم رفتار فعلی را توضیح دهد و هم تغییر بعدی را بی‌جهت سخت نکند. از نویسنده بخواه دلیل تصمیم‌های مهم را بنویسد؛ «این شکل را بیشتر دوست دارم» مبنای blocking نیست.

API را از دید مصرف‌کننده بررسی کن: نوع داده، null در برابر حذف فیلد، معنای خطا، pagination، ترتیب، default، دسترسی و نسخه. اضافه‌کردن فیلد معمولاً سازگارتر از تغییر معنای فیلد موجود است، اما بعضی clientها به schema بسته حساس‌اند؛ سازگاری باید با قراردادهای واقعی سنجیده شود.

### مثال حل‌شده: idempotency

endpoint سفارش اگر دوبار فراخوانی شود، دو سفارش می‌سازد. نیازمندی این است که retry همان عملیات را تکراری نکند. بازبین:

1. invariant را می‌نویسد: برای هر idempotency key فقط یک عملیات نهایی وجود دارد.
2. حالت رقابتی را دنبال می‌کند: دو درخواست هم‌زمان ممکن است هر دو پیش از insert جست‌وجو کنند.
3. می‌سنجد آیا قید یکتای دیتابیس یا transaction این رقابت را می‌بندد؛ check ساده در برنامه ممکن است کافی نباشد.
4. تست هم‌زمانی و retry پس از timeout را بررسی می‌کند.
5. قرارداد پاسخ تکراری و نگه‌داری key را روشن می‌خواهد.

### حالت‌های مرزی را سیستماتیک پیدا کن

- **داده:** null، خالی، تکراری، قدیمی، نامعتبر یا با اندازهٔ بیشینه.
- **زمان:** timeout، retry دیرهنگام، timezone، ساعت تغییر روز یا expiration.
- **هم‌زمانی:** دو writer، ترتیب متفاوت پیام‌ها، اجرای دوبارهٔ job.
- **وابستگی:** پاسخ ناقص، خطای موقت، قطع شبکه و خطای دائمی.
- **نسخه:** producer و consumer با نسخه‌های متفاوت در یک rollout.

همهٔ موارد همیشه مرتبط نیستند؛ از تغییر و سابقهٔ سیستم انتخاب کن. اگر هیچ تست یا توضیحی برای invariant اصلی وجود ندارد، آن را یافته یا پرسش کن.

### تمرین

در PRی که فیلد status تازه‌ای به API می‌افزاید، سه خطر compatibility و سه تست بنویس. پاسخ نمونه: client قدیمی enum ناشناخته را رد کند؛ default تازه معنی قبلی را عوض کند؛ ترتیب وضعیت از API برداشت متفاوتی شود. تست‌ها باید schema/contract قدیمی، مقدار null یا نبود فیلد و رفتار حالت انتقالی را پوشش دهند.
