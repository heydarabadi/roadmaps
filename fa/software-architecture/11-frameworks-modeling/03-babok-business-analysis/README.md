# BABOK و کشف نیاز کسب‌وکار

معمار باید نیاز واقعی ذی‌نفع را کشف کند، نه فقط خواستهٔ اولیه را به فناوری تبدیل کند. BABOK راهنمای IIBA برای تحلیل کسب‌وکار است و حوزه‌هایی مانند برنامه‌ریزی تحلیل، elicitation، مدیریت نیاز، تحلیل strategy، تحلیل requirement/design و ارزیابی solution را پوشش می‌دهد.

تکنیک‌ها شامل مصاحبه، مشاهده، workshop، process mapping، prototype، user story، decision analysis و acceptance criteria هستند. تحلیلگر کسب‌وکار، product owner و معمار می‌توانند وظایف را میان خود تقسیم کنند؛ عنوان نقش ثابت نیست. هدف مشترک، trace بین هدف، نیاز، طراحی و سنجهٔ نتیجه است.

## مثال

درخواست «گزارش سریع‌تر شود» را به پرسش تبدیل کن: کدام کاربر، کدام گزارش، چه زمانی از روز، چند ردیف، چه latency قابل‌قبولی، و تصمیم کسب‌وکاری بعد از دیدن گزارش چیست؟ ممکن است bottleneck query باشد یا خود فرایند تصمیم؛ راهکار UI بدون تحلیل مسئله چیزی را حل نمی‌کند.

## مصاحبهٔ نیاز به روش قابل‌تکرار

۱. **زمینه و actor:** چه کسی کار را انجام می‌دهد و چه اختیار/محدودیتی دارد؟
۲. **هدف، نه راهکار:** چرا این قابلیت خواسته شده و چه تصمیمی باید بهتر شود؟
۳. **جریان فعلی:** از شروع تا پایان، exception، handoff، انتظار و دادهٔ دوباره‌کاری را مشاهده کن.
۴. **معیار موفقیت:** زمان، نرخ خطا، throughput، رضایت یا هزینهٔ فعلی چیست و هدف قابل‌اندازه‌گیری کدام است؟
۵. **نیاز غیرعملکردی:** حجم هم‌زمان، دسترس‌پذیری، امنیت، audit و زمان پاسخ چه حدودی دارند؟
۶. **اعتبارسنجی:** prototype، مثال واقعی، دادهٔ نمونه یا workshop ابهام را حل می‌کند؟
۷. **ردیابی:** نیاز به acceptance criterion، تصمیم طراحی و آزمون وصل است؟

## مثال حل‌شده: «صندوق پرداخت سریع‌تر شود»

به‌جای انتخاب cache فوراً بپرس: کدام مرحله کند است؟ چند درصد درخواست‌ها؟ صدک ۹۵ فعلی چیست؟ چه چیزی برای کاربر کند محسوب می‌شود؟ آیا کندی از شبکهٔ provider، query، اعتبارسنجی یا کاربر است؟ اگر target مثلاً پایان checkout زیر X ثانیه باشد، measurement و سهم بودجهٔ هر مرحله را تعریف کن. راه‌حل ممکن است UX async، بهینه‌سازی query یا fallback provider باشد؛ تا علت را نبینی تصمیم درست نیست.

## نیازمندی و acceptance

User story قالب گفت‌وگوست، specification کامل نیست. acceptance criteria باید حالت موفق، ورودی نامعتبر، permission، concurrent update و failure dependency را پوشش دهد. نیاز غیرعملکردی را در سناریوی قابل‌آزمون بنویس: محرک، محیط، جزء، پاسخ و معیار اندازه‌گیری. اولویت با ارزش، ریسک و هزینه تعیین شود، نه صدای بلندتر ذی‌نفع.

## آزمون

۱. BABOK ابزار طراحی سرویس است؟ **پاسخ:** راهنمای تحلیل کسب‌وکار است؛ خروجی تحلیل به معماری ورودی می‌دهد.
۲. چرا elicitation فراتر از ثبت درخواست است؟ **پاسخ:** نیاز بیان‌شده ممکن است راهکار فرضی باشد؛ علت و ارزش باید بررسی شود.
۳. acceptance criteria چه می‌کند؟ **پاسخ:** رفتار قابل‌قبول را برای ذی‌نفع و تیم روشن می‌کند.
۴. traceability چه فایده‌ای دارد؟ **پاسخ:** اثر تغییر نیاز بر طراحی، تست و نتیجه را دنبال می‌کند.

## تمرین

برای «صندوق پرداخت باید سریع‌تر باشد» پنج پرسش کشف نیاز بنویس و دو نیاز قابل‌اندازه‌گیری بساز.

## پاسخ نمونهٔ تمرین

پرسش‌ها: کدام کاربر/مرحله کند است؟ latency p50/p95 فعلی چیست؟ حجم/ساعت اوج چقدر است؟ کندی در client، DB یا provider است؟ چه تصمیمی پس از مشاهدهٔ خروجی گرفته می‌شود؟ دو نیاز نمونه: 95% checkout داخلی زیر بودجهٔ latency agreed؛ گزارش فروش روزانه تا زمان مشخص با تازگی قابل‌سنجش. اعداد باید با baseline و ذی‌نفع تأیید شوند.
