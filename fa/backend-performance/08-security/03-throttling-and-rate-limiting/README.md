# Throttling و Rate Limiting — بودجه مصرف منصفانه

**زبان:** فارسی · [نسخهٔ انگلیسی](../../../../en/backend-performance/08-security/03-throttling-and-rate-limiting/README.md)  

**هدف یادگیری:** نرخ، burst و هم‌زمانی را جدا کنید، کلید و هزینه محدودسازی را متناسب با تهدید انتخاب کنید و رفتار خرابی/Retry را تحلیل کنید. **بررسی منابع: ۲۰۲۶-۱۱-۱۱**؛ الگوریتم و عددها آموزشی و اجرا‌نشده‌اند.

## تعریف و مدل ذهنی

Rate limit تعیین می‌کند در یک بازه چه مقدار مصرف پذیرفته شود؛ Throttling اصطلاح گسترده‌تری است و ممکن است رد، کاهش سرعت یا صف محدود باشد. یک درخواست می‌تواند کار ارزان جستجو یا export بسیار سنگین باشد؛ شمارش صرف request همیشه نماینده مصرف نیست. محدودسازی جای احراز هویت، مجوز یا حفاظت شبکه در برابر حمله حجمی را نمی‌گیرد.

| کنترل | چه چیزی را محدود می‌کند؟ | چه چیزی باقی می‌ماند؟ |
| --- | --- | --- |
| نرخ و burst | ورود کار در زمان | مدت هر کار و تعداد active |
| سقف هم‌زمانی | کارهای فعال | نرخ کارهای بسیار کوتاه |
| اندازه body/page/batch | اندازه یک درخواست | تعداد درخواست‌ها |
| deadline/timeout | زمان اشغال منابع | هزینه آغاز و retry |
| بودجه پولی/مصرف خارجی | SMS، API یا پردازش پولی | سایر منابع داخلی |

[OWASP API4:2023](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/) محدودیت اندازه، زمان، مصرف و هزینه را کنار هم مطرح می‌کند. ابتدا endpoint پرهزینه و منبع محدودش را مشخص کنید؛ سپس کلید، نرخ، burst و عمل هنگام رد را طراحی کنید. هویت تأییدنشده نباید بتواند با تغییر یک header دلخواه، سهمیه جدید بسازد.

## انتخاب الگوریتم و مصالحه

| الگوریتم | ویژگی | هزینه/خطای معمول |
| --- | --- | --- |
| Fixed window | شمارنده ساده هر بازه | burst دو سوی مرز |
| Sliding log/window | نگاه دقیق‌تر به بازه لغزان | حافظه/محاسبه یا تقریب بیشتر |
| Token bucket | refill با burst محدود | نیاز به update اتمیک و ساعت معتبر |
| Leaky bucket/صف محدود | هموارکردن خروج کار طبق طراحی | زمان انتظار، ظرفیت صف و deadline |

IP برای کنترل اولیه ناشناس مفید است، اما NAT کاربران را مشترک و مهاجم توزیع‌شده را پخش می‌کند؛ به header فورواردشده فقط از proxy مورد اعتماد تکیه کنید. پس از Authentication، tenant/account/credential و route می‌توانند کلیدهای مناسب‌تری باشند. محدودیت coarse در edge، سهم tenant و سقف سراسری worker مکمل‌اند. Pool و صف نامحدود کارهای ردنشده را نجات نمی‌دهند.

در چند نمونه برنامه، limiter محلی سقف سراسری دقیقی نمی‌دهد؛ سقف هر نمونه با تعداد نمونه‌ها جمع می‌شود. سرویس مشترک نیز latency و وابستگی عملیاتی می‌آورد؛ update باید atomic باشد و الگوریتم/همگام‌سازی واقعاً آن تضمین را بدهد. در خرابی، policy مشخص کنید: برای export گران، توقف موقت یا سهمیه محلی محافظه‌کارانه ممکن است مناسب باشد؛ bypass نامحدود خطر دارد. fail-open محدود با بودجه مستقل فقط تصمیم ریسک صریح برای مسیرهای مناسب است، نه رفتار تصادفی.

### تبدیل نیاز به یک محدودیت قابل اجرا

۱. **منبع حفاظت‌شده را مشخص کنید:** CPU، اتصال پایگاه داده، worker، هزینهٔ سرویس بیرونی یا سهم عادلانهٔ tenant. یک شمارنده به‌تنهایی همه این‌ها را کنترل نمی‌کند.

۲. **واحد هزینه را تعیین کنید:** اگر lookup ارزان و export گران است، یک درخواست برای هر دو نمایندهٔ مصرف نیست. هزینهٔ وزن‌دار یا سقف هم‌زمانی جدا می‌تواند مناسب باشد؛ وزن باید با اندازه‌گیری و سیاست محصول تعیین شود.

۳. **نرخ پایدار را از burst جدا کنید:** ظرفیت `C` اندازهٔ جهش پذیرفته‌شده و refill برابر `r` نرخ مجاز بلندمدت است. توکن‌های جدید با `tokens = min(C, old_tokens + r × elapsed_seconds)` محاسبه می‌شوند. درخواست زمانی می‌گذرد که توکن کافی برای هزینه‌اش وجود دارد؛ state نباید منفی شود.

۴. **مرز fairness را انتخاب کنید:** IP، حساب، credential، tenant و route سهم‌های متفاوتی می‌سازند. کنترل لبه برای ناشناس و کنترل هویت‌دار برای مصرف‌کنندهٔ شناخته‌شده مکمل‌اند؛ header جعل‌پذیر را کلید نهایی نکنید.

۵. **رد، خرابی و retry را طراحی کنید:** 429 و راهنمای انتظار، صف، deadline، سقف تلاش مجدد و قطع store بخشی از رفتار سیستم‌اند. `Retry-After` رزرو توکن آینده نیست؛ چند client ممکن است هم‌زمان دوباره درخواست دهند.

### محاسبهٔ دقیق Token bucket

فرض کنید ظرفیت `C=10`، refill برابر `r=2 token/s` و state پس از burst صفر است. در `t=0.5s` یک توکن ساخته می‌شود، پس یک درخواست یک‌واحدی پذیرفته می‌شود. اگر آن درخواست توکن را مصرف کند، state دوباره صفر است. در `t=1s` یک توکن دیگر ساخته می‌شود. اگر دو درخواست هم‌زمان برسند، فقط یکی باید توکن را بگیرد؛ برای این تضمین، خواندن و کم‌کردن state باید اتمیک باشد. اجرای «اول بخوان، بعد بنویس» ممکن است هر دو را مجاز کند.

مثال دوم: bucket پر است؛ ۸ درخواست یک‌واحدی پذیرفته شده و ۱٫۵ ثانیه می‌گذرد. state جدید `min(10, 2 + 1.5×2)=5` است. درخواست ۶واحدی رد می‌شود و state همان ۵ می‌ماند، اگر تعریف limiter این باشد که ردشدن token مصرف نکند. اگر semantics سیستم شما متفاوت است، آن را صریح کنید و با concurrency سازگار نگه دارید.

## مثال حل‌شده — Token bucket

فرض: ظرفیت bucket برابر ۱۰ واحد، refill برابر ۲ واحد در ثانیه، و هزینه هر جستجو یک واحد است. bucket ابتدا پر است. ده درخواست هم‌زمان مصرف می‌شوند؛ یازدهم بدون توکن رد می‌شود. پس از نیم ثانیه یک توکن جدید می‌رسد. درخواست export می‌تواند هزینه و محدودیت هم‌زمانی جدا داشته باشد؛ مدل هزینه را با مصرف واقعی تنظیم کنید.

<div dir="ltr" align="left">

```text
key = (verified_tenant, verified_subject, route_group)
atomic_on_authoritative_store:
    now = trusted_monotonic_or_store_time()
    tokens = min(capacity, old_tokens + rate * max(0, now - old_time))
    if tokens >= request_cost:
        tokens = tokens - request_cost
        persist(tokens, now, bounded_expiry)
        allow
    else:
        persist(tokens, now, bounded_expiry)
        deny_with_bounded_retry_hint()
```

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 1
Content-Type: application/json
Cache-Control: no-store

{"error":"rate_limit_exceeded"}
```

hint زمان، رزرو توکن آینده نیست؛ درخواست‌های دیگر می‌توانند توکن را مصرف کنند. واحد زمان، انقضای state، هزینه بیش از capacity و هماهنگی چند limiter باید تعریف شوند. انقضای زودهنگام state نباید پیش از زمان پرشدن طبیعی bucket سهمیه رایگان بسازد. در limiterهای چندلایه، مصرف token یک لایه و رد در لایه دیگر نیازمند semantics مشخص است؛ refund بدون کنترل می‌تواند بودجه را خراب کند.

## تمرین و مشاهده مورد انتظار

با همان bucket، ۱۲ درخواست در `t=0` و سه درخواست در `t=1s` روی کاغذ اجرا کنید؛ هیچ مصرف دیگری وجود ندارد. انتظار: ابتدا ۱۰ پذیرش و ۲ رد؛ در ثانیه یک، ۲ پذیرش و ۱ رد. سپس سه نمونه مستقل، هرکدام با bucket پر ۱۰تایی، را تحلیل کنید: تا ۳۰ پذیرش آنی ممکن است. در گام آخر همه 429ها را فوراً retry کنید؛ چرا کار ورودی بیشتر می‌شود بی‌آنکه ظرفیت refill بیشتر شود؟

**حل تمرین:** پس از burst اول bucket خالی است. تا ثانیهٔ بعد `2 token` ایجاد می‌شود؛ بنابراین از سه درخواست بعدی دو تا پذیرفته و یکی رد می‌شود. در سه replica مستقل، هرکدام ۱۰ token اولیه دارد و تا ۳۰ درخواست آنی از کنترل محلی می‌گذرد؛ این سقف سراسری نیست. retry فوری درخواست ردشده، کار شبکه و limiter را زیاد می‌کند و ممکن است درخواست معتبر را عقب بیندازد. backoff و jitter فشار را پخش می‌کنند، ولی جای rate limit را نمی‌گیرند.

## شاهد عمومی و حد شواهد

[مطالعه موردی Cloudflare درباره Have I Been Pwned](https://www.cloudflare.com/case-studies/troy-hunt/) گزارش می‌کند Troy Hunt برای کنترل جهش ترافیک، هزینه و سوءاستفاده API از محدودیت درخواست مبتنی بر IP استفاده کرد. این روایت عرضه‌کننده همراه نقل تجربه مشتری است؛ صفحه تاریخ انتشار روشنی در متن بررسی‌شده ندارد و شرح تاریخی آن را تنظیمات امروز HIBP نمی‌دانیم. از آن عدد تضمینی بهبود یا کافی‌بودن IP برای هر API نتیجه نمی‌گیریم؛ سناریوی bucket درس مستقل و فرضی است.

## شکست‌ها، سیگنال‌ها و چک‌لیست

read سپس write غیراتمیک، reset هم‌زمان پنجره‌ها، کلید با cardinality نامحدود، clock skew و queue بی‌سقف خطاهای رایج‌اند. نرخ 429 را کنار goodput درخواست مجاز، latency، saturation و هزینه خارجی ببینید. کم‌شدن latency فقط با رد کاربران معتبر، موفقیت کامل نیست. client باید Retry-After معتبر و backoff دارای jitter و سقف زمان/تعداد را رعایت کند؛ درخواست پولی یا تغییردهنده نیز idempotency لازم دارد.

- [ ] نرخ، burst، هزینه و هم‌زمانی برای routeهای پرهزینه جدا تعریف شده‌اند.
- [ ] کلید بر هویت تأییدشده و مرز proxy مورد اعتماد تکیه دارد.
- [ ] ضمانت local/global، اتمیک‌بودن، زمان و expiry روشن‌اند.
- [ ] صف، body/page/batch، timeout و بودجه پولی سقف مستقل دارند.
- [ ] خرابی store رفتار محدود، مستند و قابل مشاهده دارد.
- [ ] 429، Retry-After و retry budget در client/server هماهنگ‌اند.
- [ ] false rejection، fairness، goodput و منابع به‌طور هم‌زمان پایش می‌شوند.

## خودآزمایی

۱. تفاوت نرخ و هم‌زمانی چیست؟

۲. آیا limit صد درخواست برای همه routeها هزینه یکسانی کنترل می‌کند؟

۳. سه limiter محلی با ظرفیت ۱۰، سقف burst سراسری چند می‌دهند؟

۴. چرا IP تنها هویت کافی برای سهمیه نهایی نیست؟

۵. Retry-After آیا توکن آینده را برای client رزرو می‌کند؟

۶. چرا 429 کمتر به‌تنهایی نشانه عملکرد بهتر نیست؟

### پاسخ‌نامه با دلیل

۱. نرخ تعداد ورود در زمان است؛ هم‌زمانی تعداد کارهای فعال. کار طولانی حتی با نرخ کم active زیاد می‌سازد.

۲. خیر؛ یک export ممکن است از صدها lookup گران‌تر باشد و بودجه متفاوت بخواهد.

۳. در فرض bucketهای پر و مستقل تا ۳۰؛ limit محلی با limit مشترک برابر نیست.

۴. NAT، IP مشترک و توزیع مهاجم fairness/دقت را خراب می‌کنند؛ هویت معتبر و چند لایه لازم‌اند.

۵. خیر؛ فقط راهنمای انتظار است و رقابت سایر درخواست‌ها ادامه دارد.

۶. ممکن است کنترل خاموش یا store fail-open شده باشد؛ latency، goodput و منابع باید همراه آن دیده شوند.
