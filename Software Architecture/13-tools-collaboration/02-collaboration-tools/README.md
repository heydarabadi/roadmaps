# Slack، Trello و ابزارهای Atlassian

ابزارهای ارتباط و برنامه‌ریزی اطلاعات را میان افراد جابه‌جا می‌کنند؛ جایگزین مالک، تصمیم و مستند پایدار نیستند. Slack برای گفت‌وگوی زنده/ناهم‌زمان، Trello برای board سبک و گردش کارت، و Jira/Confluence/Bitbucket در مجموعهٔ Atlassian برای issue tracking، مستندات و repository کاربرد دارند.

تصمیم معماری را فقط در چت نگذار: گفتگو را به ADR یا صفحهٔ قابل‌جست‌وجو پیوند بده. ticket باید نتیجهٔ کار، acceptance criteria، وابستگی و مالک را نشان دهد؛ status board بدون دادهٔ واقعی پیشرفت، تنها ظاهر کنترل است. کانال تیمی و naming را ساده و دارای نگهدارنده نگه دار.

## طراحی جریان همکاری

برای یک تصمیم API، گفت‌وگو را در کانال موضوعی برگزار کن؛ هدف، گزینه‌ها و owner را در issue ثبت کن؛ تصمیم نهایی و پیامدش را در ADR بنویس؛ کارهای اجرایی و معیار پذیرش را به ticketهای قابل‌بستن تبدیل کن؛ release note را به تغییر پیوند بده. Chat برای تعامل سریع است، ADR برای دلیل پایدار و tracker برای وضعیت کار.

## منبع حقیقت و ابزار کم

برای هر نوع داده یک مرجع اصلی انتخاب کن: ticket در tracker، تصمیم در ADR، کد در Git، پیام روزمره در chat. لینک را میانشان بگذار، متن را در چند جای مستقل کپی نکن. naming و tag و notification را محدود کن؛ notification بیش‌ازحد و boardهای متعدد توجه تیم را خرد می‌کنند.

## جلسه و async

پیش‌خوانی و پرسش روشن پیش از جلسه بفرست. برای تصمیم async، deadline و مسیر پاسخ را بنویس. جمع‌بندی جلسه شامل تصمیم، گزینهٔ ردشده، owner و next action باشد. افراد غایب باید از روی نتیجه بتوانند ادامه دهند.

## سنجش سلامت جریان

به جای تعداد ticket بسته‌شده، زمان انتظار، lead time، دوباره‌کاری، unresolved decision age و کیفیت handoff را ببین. هیچ metric منفردی بهره‌وری فرد را ثابت نمی‌کند؛ هدف، یافتن گلوگاه سیستم تیم است.

## آزمون

۱. چه چیزی را در chat نگه نمی‌داری؟ **پاسخ:** تصمیم بلندمدت بدون ثبت قابل‌جست‌وجو.
۲. Ticket خوب چه چیزی را روشن می‌کند؟ **پاسخ:** هدف، مالک، معیار پذیرش و dependency.
۳. ابزار برنامه‌ریزی چه چیزی را تضمین نمی‌کند؟ **پاسخ:** کیفیت تصمیم یا تحویل ارزش را.
۴. تکرار محتوا در سه ابزار چه مشکلی دارد؟ **پاسخ:** نسخه‌های ناسازگار و منبع حقیقت نامعلوم می‌سازد.

## تمرین

برای تصمیم تغییر API، مسیر گفتگو، ثبت ADR، ticketهای اجرا و لینک release note را طوری طراحی کن که علت تصمیم گم نشود.

## پاسخ نمونهٔ تمرین

Chat برای گفتگو و گزینه‌ها؛ issue برای outcome، owner، acceptance و dependency؛ ADR برای زمینه/تصمیم/پیامد؛ PR به ADR و ticket لینک می‌دهد؛ release note نسخه و اثر بیرونی را به کاربر می‌گوید. هر artifact یک منبع حقیقت دارد و در chat فقط لینک/خلاصه می‌ماند. owner بازبینی تصمیم مشخص می‌شود.
