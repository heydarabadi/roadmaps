# Search Engines vs Relational DBs

[English version](../../../../../en/elasticsearch/01-foundations/topics/04-search-engines-vs-relational-dbs/README.md)


> فصل 01: مبانی و شناخت · درس 04

## هدف این درس
تفاوت مدل تراکنشی و retrieval را یاد بگیر و معماری همگام‌سازی پایگاه اصلی با index جست‌وجو را طراحی کن.
## تدریس کامل: چه وقت دیتابیس و چه وقت موتور جست‌وجو؟

پایگاه رابطه‌ای برای تراکنش، قید، رابطه‌ی بین جدول‌ها و عملیات قابل‌پیش‌بینی مناسب است. موتور جست‌وجو متن و فیلدهای نمایه‌شده را برای retrieval، رتبه‌بندی و aggregation آماده می‌کند. این ابزارها گاهی در قابلیت‌ها هم‌پوشانی دارند، اما مدل اجرا و trade-off یکسانی ندارند.

### مثال فروشگاه

ثبت سفارش، کسر موجودی و قید یکتایی باید در پایگاه اصلی انجام شود. جست‌وجوی «کیبورد بی‌سیم با قیمت زیر سقف» نیاز به full-text، فیلتر، رتبه‌بندی و دسته‌بندی دارد؛ این درخواست می‌تواند به Elasticsearch برود. در این الگو دیتابیس اصلی منبع حقیقت است و index جست‌وجو یک projection مشتق‌شده است.

~~~text

برنامه → پایگاه اصلی → رویداد/CDC/outbox → Elasticsearch

~~~

اگر index حذف شود یا mapping عوض شود، باید از منبع اصلی دوباره ساخته شود.

### همگام‌سازی و consistency

نوشتن به دو سامانه با دو درخواست مستقل خطر dual-write دارد: پایگاه اصلی ممکن است موفق شود و Elasticsearch شکست بخورد. Outbox یا CDC تغییر را پایدار ثبت می‌کند تا worker دوباره آن را بفرستد. برای جلوگیری از duplicate از ID پایدار و عملیات idempotent استفاده کن. حذف سند هم باید به projection برسد؛ در غیر این صورت نتیجه‌ی حذف‌شده در search باقی می‌ماند.

Search near real-time است؛ تغییر تازه ممکن است تا refresh بعدی دیده نشود. برای موجودی یا مجوز حساس، تصمیم نهایی را از منبع حقیقت بخوان، نه از نتیجه‌ی جست‌وجوی قدیمی.

### چه وقت Elasticsearch انتخاب مناسبی نیست؟

صرفاً JSON بودن داده دلیل انتقال نیست. اگر مسئله‌ی اصلی تراکنش چندرکوردی، constraint یا سازگاری قوی است، ابتدا پایگاه موجود را ارزیابی کن. Elasticsearch وقتی ارزش دارد که full-text، relevance، autocomplete، faceting یا query تحلیلی نیاز واقعی باشد و تیم بتواند sync، عملیات و rebuild را اداره کند.

### تمرین طراحی

برای کالا و سفارش مشخص کن: منبع حقیقت چیست؟ چه eventهایی به search index می‌روند؟ update و delete چگونه منتقل می‌شوند؟ index چطور rebuild می‌شود؟ کدام پاسخ باید بی‌درنگ authoritative باشد و کدام می‌تواند اندکی تأخیر داشته باشد؟

### آزمون تشریحی با پاسخ

1. **Projection چیست؟** نمای مشتق‌شده از منبع اصلی که برای query خاص، مانند جست‌وجو، مدل شده است.
2. **dual-write چه خطری دارد؟** یکی از نوشتن‌ها ممکن است موفق و دیگری ناموفق شود و داده‌ها از هم جدا شوند.
3. **چرا تصمیم نهایی موجودی را از سرچ index نگیریم؟** چون index ممکن است تا refresh یا sync بعدی از منبع اصلی عقب باشد.


## خودآزمایی
1. چرا Elasticsearch جایگزین بی‌قید پایگاه رابطه‌ای نیست؟ پاسخ: مدل تراکنش، consistency و constraintهای آن متفاوت است.
2. چگونه تغییرهای پایگاه اصلی به search index می‌رسند؟ پاسخ: CDC/outbox/job یا dual-write مدیریت‌شده؛ باید retry، idempotency و reconciliation داشته باشد.
