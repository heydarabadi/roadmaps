## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

MVC مسئولیت مدل، نمایش و کنترل ورودی را تفکیک می‌کند تا UI و منطق از هم جدا شوند؛ شکل دقیق MVC در frameworkها فرق می‌کند.

## مثال کاربردی

کنترلر فرم سفارش را اعتبارسنجی اولیه می‌کند، مدل use case را اجرا می‌کند و view نتیجه را نمایش می‌دهد.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «الگوهای معماری» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** کنترلرهای چاق و مدل‌های global در عمل coupling می‌سازند.
- **بازبینی:** نام MVC روی framework تضمین جداسازی قواعد دامنه نیست.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: MVC مسئولیت مدل، نمایش و کنترل ورودی را تفکیک می‌کند تا UI و منطق از هم جدا شوند؛ شکل دقیق MVC در frameworkها فرق می‌کند.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: کنترلر فرم سفارش را اعتبارسنجی اولیه می‌کند، مدل use case را اجرا می‌کند و view نتیجه را نمایش می‌دهد.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: کنترلرهای چاق و مدل‌های global در عمل coupling می‌سازند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: نام MVC روی framework تضمین جداسازی قواعد دامنه نیست.

## آموزش تکمیلی مستقل

### ۲. MVC

Model-View-Controller ورودی کاربر و نمایش را از مدل رفتار/داده جدا می‌کند. Controller request را می‌گیرد و به behavior مناسب می‌سپارد؛ View نتیجه را نمایش می‌دهد؛ Model بخش داده/رفتار است. چارچوب‌ها واژهٔ Model را متفاوت به کار می‌برند؛ اسم MVC تضمین نمی‌کند domain ruleها داخل Model یا خارج Controller باشند.

خطای رایج: controllerهای چاق که validation، قواعد دامنه، transaction و SQL را باهم اجرا می‌کنند. Controller را adapter مرزی نگه دار و منطق مهم را در application/domain model بگذار. برای UI، MVC می‌تواند ساختار سطح presentation باشد و هم‌زمان domain داخلی معماری دیگری داشته باشد.

## نمودار معماری و خواندن مرحله‌ای

MVC مسئولیت presentation را میان Model، View و Controller تقسیم می‌کند: controller درخواست را تفسیر می‌کند، model قواعد/داده را عرضه می‌کند و view نمایش می‌دهد. در برنامهٔ بزرگ، مرز use case و منطق دامنه را نیز جدا نگه دار.
**دام رایج:** business rule را در controller یا view انباشته نکن.
**تمرین با پاسخ:** اعتبارسنجی نهایی سفارش باید در domain/use case باشد؛ controller فقط ورودی HTTP را تبدیل و پاسخ مناسب را برمی‌گرداند.

این یک view ساده است؛ طراحی production باید مالکیت، شکست، امنیت و محدودیت‌های عملیاتی را نیز روشن کند.

~~~text
[Browser request] ---> [Controller] ---> [Model / use case]
                           |                    |
                           +---- View <---------+
                                  |
                              [Response]
~~~

## نمودار معماری و خواندن مرحله‌ای

MVC مسئولیت presentation را میان Model، View و Controller تقسیم می‌کند: controller درخواست را تفسیر می‌کند، model داده و قواعد را می‌دهد و view نمایش می‌دهد. در برنامهٔ بزرگ منطق use case را نیز از controller جدا نگه دار.
**دام رایج:** business rule را در view یا controller انباشته نکن.
**تمرین با پاسخ:** کنترل نهایی سفارش در domain/use case است؛ controller ورودی HTTP را نگاشت می‌کند و پاسخ برمی‌گرداند.

این view ساده باید با تصمیم روشن دربارهٔ مالکیت، شکست، امنیت و عملیات کامل شود.

~~~text
[Browser request] ---> [Controller] ---> [Model / use case]
                           |                    |
                           +---- View <---------+
                                  |
                              [Response]
~~~
