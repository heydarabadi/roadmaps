## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

انتزاع جزئیات را پشت مفهومی نگه می‌دارد که مصرف‌کننده برای کارش نیاز دارد؛ مرز خوب از زبان و قواعد مسئله می‌آید.

## مثال کاربردی

API ذخیره‌سازی سفارش عملیات `save` را ارائه می‌کند و جزئیات SQL را از use case دور نگه می‌دارد.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «برنامه‌نویسی شیءگرا» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** انتزاع بیش از حد مدل کاذب یا لایهٔ بی‌ارزش می‌سازد.
- **بازبینی:** رابطی که همهٔ جزئیات پیاده‌سازی را نشت می‌دهد انتزاع مؤثری نیست.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: انتزاع جزئیات را پشت مفهومی نگه می‌دارد که مصرف‌کننده برای کارش نیاز دارد؛ مرز خوب از زبان و قواعد مسئله می‌آید.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: API ذخیره‌سازی سفارش عملیات `save` را ارائه می‌کند و جزئیات SQL را از use case دور نگه می‌دارد.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: انتزاع بیش از حد مدل کاذب یا لایهٔ بی‌ارزش می‌سازد.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: رابطی که همهٔ جزئیات پیاده‌سازی را نشت می‌دهد انتزاع مؤثری نیست.

## آموزش تکمیلی مستقل

#### انتزاع (Abstraction)

انتزاع قرارداد لازم برای مصرف‌کننده را نگه می‌دارد و جزئیات نامربوط را پنهان می‌کند. use case سفارش باید بداند کالا را رزرو کند، نه اینکه هر اتصال دیتابیس و query SQL چگونه کار می‌کند.

انتزاع را از نیاز مصرف‌کننده استخراج کن: چه کاری لازم است؟ چه نتیجه و شکست‌هایی ممکن‌اند؟ چه جزئیاتی نباید به caller برسند؟ اگر API همچنان ORM entity یا خطای خام vendor را می‌دهد، انتزاع کامل نیست.

هر interface ارزشمند نیست. اگر تنها یک پیاده‌سازی، هیچ seam تست و هیچ دلیل تغییر وجود ندارد، قرارداد می‌تواند فقط یک لایهٔ اضافه باشد. انتزاع زودرس آینده را حدس می‌زند؛ انتزاع مناسب تغییر واقعی را محدود می‌کند.

## نمونهٔ کد مرحله‌ای

Use case فقط به عملیاتی نیاز دارد که برای انجام کارش لازم است؛ جزئیات پایگاه داده یا vendor پشت مرز می‌مانند. قرارداد را از نیاز مصرف‌کننده بساز و failureهای قابل مشاهده را هم مدل کن. اگر interface همان جزئیات پیاده‌سازی را بازتاب می‌دهد، هنوز انتزاع مفیدی نیست.
**تمرین با پاسخ:** اگر درگاه بانکی عوض شد، چه تغییری لازم است؟ Adapter تازه باید قرارداد را پیاده کند و use case ثابت بماند.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا تصمیم طراحی روشن بماند.

~~~csharp
public interface IPaymentGateway
{
    Task<PaymentResult> Capture(Money amount, CancellationToken ct);
}
~~~
