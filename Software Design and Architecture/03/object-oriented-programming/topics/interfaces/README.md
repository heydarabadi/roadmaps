## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

interface قرارداد رفتاری بین مصرف‌کننده و پیاده‌سازی است؛ رابط پایدار امکان تعویض adapter و تست boundary را می‌دهد.

## مثال کاربردی

use case به `Clock` وابسته است تا زمان را در تست ثابت کند و در تولید از ساعت واقعی بخواند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «برنامه‌نویسی شیءگرا» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** رابط اضافه هزینهٔ نگهداری دارد؛ هر جزئیات داخلی را پشت abstraction نبر.
- **بازبینی:** interface نباید با پیاده‌سازی خاص یا CRUD یک جدول گره بخورد.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: interface قرارداد رفتاری بین مصرف‌کننده و پیاده‌سازی است؛ رابط پایدار امکان تعویض adapter و تست boundary را می‌دهد.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: use case به `Clock` وابسته است تا زمان را در تست ثابت کند و در تولید از ساعت واقعی بخواند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: رابط اضافه هزینهٔ نگهداری دارد؛ هر جزئیات داخلی را پشت abstraction نبر.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: interface نباید با پیاده‌سازی خاص یا CRUD یک جدول گره بخورد.

## آموزش تکمیلی مستقل

#### Interface

Interface قرارداد capability است؛ مثلاً PaymentAuthorizer می‌گوید چه کاری در اختیار مصرف‌کننده است. interface را از نیاز consumer طراحی کن، نه از کل SDK فروشنده. اگر یک interface بزرگ همهٔ عملیات پرداخت، refund، گزارش و تنظیمات را ارائه می‌دهد، مصرف‌کننده‌ها به عملیات نامربوط وابسته می‌شوند؛ قرارداد کوچک‌تر بر اساس نقش‌ها می‌تواند مناسب باشد.

## نمونهٔ کد مرحله‌ای

Interface قرارداد را از پیاده‌سازی جدا می‌کند و برای چند implementation، مرز آزمون یا مالکیت مستقل مفید است. قرارداد را با نیاز مصرف‌کننده تعریف کن و رفتار خطا را هم مشخص کن؛ interface بزرگ یا بی‌مصرف وابستگی را فقط جابه‌جا می‌کند.
**تمرین با پاسخ:** اگر use case فقط Capture لازم دارد، قرارداد را محدود به Capture کن؛ جست‌وجو، refund و گزارش را به interfaceهای دیگری بسپار.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا تصمیم طراحی روشن بماند.

~~~csharp
public interface IPaymentCapture
{
    Task<PaymentResult> Capture(Money amount, CancellationToken ct);
}

public sealed class Checkout(IPaymentCapture payments)
{
    public Task<PaymentResult> Pay(Money amount, CancellationToken ct)
        => payments.Capture(amount, ct);
}
~~~
