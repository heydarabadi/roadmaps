# تست و بررسی امنیتی

**زبان:** فارسی · [English](../../en/04-technical-review/02-tests-security/README.md)

> مسیر: [فصل ۴ — بررسی فنی](../README.md) · [فهرست دوره](../../README.md)

## آموزش

تست باید رفتار قابل مشاهده و ریسک موردنظر را محافظت کند. assertion را بخوان؛ آیا در صورت regression شکست می‌خورد یا فقط mock صدا زده شده؟ تست مسیر عادی، failure، ورودی مرزی، تکرار و سازگاری داده را متناسب بررسی کن. سبز بودن CI برای همان revision لازم است، ولی تمام معنای درست را ثابت نمی‌کند.

در امنیت، جریان داده و مرز اعتماد را دنبال کن: ورودی، authentication، authorization، query، فایل، secret، dependency و log. کاربر authenticated لزوماً به منبع درخواستی مجاز نیست. تغییر dependency را از نظر نیاز، نسخه، lockfile، منبع، install script و license ببین.

SAST و scanner الگوهای آشنا را می‌یابند؛ business logic و منطق دسترسی ممکن است تحلیل انسانی بخواهد. هشدار را با کد بسنج و موارد حل‌نشده را مالک‌دار کن.

## روند پیشنهادی

1. تست‌ها را از نظر assertion و failure mode بخوان.
2. input را تا sink و data store دنبال کن.
3. identity را از permission جدا کن.
4. dependency و اسرار را بررسی کن.
5. ابزار خودکار را با تحلیل دستی تکمیل کن.

## مثال کاربردی

یک endpoint userId را از body می‌گیرد. تست دو کاربر باید ثابت کند کاربر A با جایگزین‌کردن شناسه به سفارش B نمی‌رسد. JWT معتبر به‌تنهایی مجوز همان سفارش را ثابت نمی‌کند.

## خطاهای رایج

coverage بالا را proof ندان؛ mock بیش‌ازحد را رفتار واقعی فرض نکن؛ SAST را تنها سد امنیتی ندان؛ dependency را صرفاً با محبوبیت تایید نکن.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** assertion خوب چه می‌کند؟

   1. فقط وجود تابع را می‌سنجد
   2. رفتاری را می‌سنجد که regression باید بشکند
   3. نام متغیر را چک می‌کند
   4. کد را اجرا نمی‌کند

**پاسخ:** 2 — تست باید انتظار را محافظت کند.

### پرسش 2

**سؤال:** authentication با authorization چه تفاوتی دارد؟

   1. هیچ
   2. اثبات هویت با اجازهٔ عمل روی منبع فرق دارد
   3. authorization فقط password است
   4. authentication بعد از merge است

**پاسخ:** 2 — کاربر شناخته‌شده ممکن است به منبع مجاز نباشد.

### پرسش 3

**سؤال:** SAST چه نقشی دارد؟

   1. تضمین امنیت
   2. یافتن برخی الگوها برای کمک به review
   3. جایگزین فهم business logic
   4. تایید خودکار merge

**پاسخ:** 2 — ابزار مکمل قضاوت انسانی است.

### پرسش 4

**سؤال:** dependency جدید را با چه معیارهایی ببینیم؟

   1. فقط نام
   2. نیاز، منبع، نسخه، lockfile، script و license
   3. فقط star
   4. رنگ لوگو

**پاسخ:** 2 — زنجیرهٔ تامین چند بخش دارد.

## آموزش عمیق: بررسی امنیتی به زبان جریان داده

### واژگان پایه

- **Authentication (احراز هویت):** سیستم می‌فهمد درخواست از چه هویتی آمده است.
- **Authorization (مجوزدهی):** سیستم تصمیم می‌گیرد آن هویت اجازهٔ انجام همین عمل روی همین منبع را دارد یا نه.
- **Trust boundary (مرز اعتماد):** جایی که داده یا تصمیم از حوزه‌ای وارد حوزهٔ دیگر می‌شود، مانند HTTP request، پیام queue، فایل upload یا سرویس بیرونی.
- **Source و sink:** منبع ورودی داده و مقصد حساس آن؛ مثلاً query دیتابیس، اجرای فرمان، log، فایل یا پاسخ HTML.
- **Secret:** credential مثل password، token، private key یا connection string که افشاشدنش دسترسی می‌دهد.

تغییر امنیتی را با دنبال‌کردن مسیر source → validation/authorization → transformation → sink تحلیل کن. اعتبارسنجی نوع ورودی مجوزدهی نیست: کاربر می‌تواند شناسهٔ عددی معتبر اما متعلق به tenant دیگر بفرستد.

### روش diff-based security review

1. فایل‌های متأثر را پیدا کن: auth، policy، query، config، dependency، log، serialization و API.
2. دارایی‌های حساس را فهرست کن: دادهٔ شخصی، پول، اسرار، عملیات مدیریتی و دسترس‌پذیری.
3. مرز اعتماد و ورودی‌های تازه را مشخص کن.
4. کنترل‌های فعلی را دنبال کن؛ آیا تغییر آن‌ها را دور می‌زند یا تضعیف می‌کند؟
5. منطق را هم در مسیر موفق و هم در حالت خطا/تکرار بررسی کن.
6. آزمون، SAST، dependency scanner و secret scanner را به‌عنوان لایه‌های مکمل ببین.

### مثال مجوزدهی

کد فرضی فقط session معتبر می‌خواهد و سپس سفارش را با شناسهٔ URL می‌خواند. خطر این است که کاربر A شناسهٔ سفارش B را حدس بزند. کنترل درست باید مجوز را به شیء وصل کند: query یا policy باید سفارش را هم با شناسه و هم با scope/مالکیت هویت جاری محدود کند. تست باید با دو کاربر مستقل ساخته شود؛ تستی که session و سفارش را همیشه از یک fixture می‌سازد ممکن است نقص را نبیند.

### Injection، output و secret

برای query یا فرمان، ببین دادهٔ untrusted با string concatenation به دستور اجرایی تبدیل می‌شود یا از API پارامتری استفاده شده است. در خروجی HTML، encoding و context مهم‌اند؛ یک escape عمومی برای همهٔ contextها کافی نیست. در log، token و اطلاعات حساس ممکن است کپی شوند و مدت زیادی باقی بمانند. error response هم نباید stack trace یا اطلاعات داخلی غیرضروری افشا کند.

این راهنما یک چک‌لیست کامل همهٔ آسیب‌پذیری‌ها نیست. نوع برنامه و threat model تعیین می‌کند کدام کنترل لازم است. cryptography، protocol پیچیده و policy قانونی را در صورت نیاز به متخصص مربوط بسپار.

### وابستگی و ابزار خودکار

در dependency تازه، علت نیاز، منبع، نسخه، lockfile، script نصب، مجوز نرم‌افزاری و سطح دسترسی را بررسی کن. scanner می‌تواند نسخهٔ آسیب‌پذیر یا secret شناخته‌شده را پیدا کند، ولی معمولاً نمی‌تواند بفهمد آیا منطق کسب‌وکار اجازهٔ دسترسی به resource اشتباه می‌دهد. هشدار را با evidence تعیین تکلیف کن؛ false positive بی‌دلیل نباید پاک شود و هشدار واقعی نباید صرفاً به‌خاطر فشار زمان کنار گذاشته شود.

### تمرین

برای endpoint دانلود سند، منبع، sink، کنترل احراز هویت، مجوز مالکیت، مسیر log و تست منفی را بنویس. یک تست مهم: کاربر A سند B را درخواست می‌کند و هیچ metadata یا محتوای سند به او نمی‌رسد. آیا پاسخ 403 یا 404 است؟ این تصمیم به سیاست افشای وجود سند وابسته است و باید در قرارداد ثبت شود.
