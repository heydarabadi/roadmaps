# ۱.۱ — معرفی Go و چرایی انتخاب آن

<div dir="rtl">

**زمان پیشنهادی:** ۴۵ دقیقه · **پیش‌نیاز:** ندارد · **نسخهٔ مبنا:** Go 1.27.4

## خروجی این درس

پس از این درس باید بتوانی توضیح بدهی Go چیست، یک برنامهٔ Go چگونه به فایل اجرایی تبدیل می‌شود، چرا نوع ایستا و garbage collector دارد، concurrency چه مشکلی را حل می‌کند و برای یک مسئلهٔ واقعی Go را با دلیل انتخاب یا رد کنی.

## ۱) Go نام چیست؟

نام زبان **Go** است. واژهٔ `golang` لقب غیررسمی و عبارت جست‌وجوی رایج است؛ در کد، فرمان و مستندات رسمی نام Go را می‌بینی. Go یک زبان عمومی، کامپایل‌شونده، دارای نوع ایستا و دارای مدیریت خودکار حافظه است. این جمله‌ها ویژگی‌های طراحی را توصیف می‌کنند؛ به‌تنهایی نمی‌گویند هر برنامهٔ Go سریع، امن یا مقیاس‌پذیر خواهد بود.

**نوع ایستا** یعنی نوع هر عبارت در زمان کامپایل قابل بررسی است. در نتیجه بسیاری از ناسازگاری‌ها پیش از اجرای برنامه پیدا می‌شوند. **کامپایل** یعنی مترجم Go سورس و packageهایش را بررسی و به برنامه‌ای مناسب سیستم‌عامل/معماری هدف تبدیل می‌کند. **garbage collector (GC)** حافظهٔ اشیایی را که دیگر از برنامه قابل دسترسی نیستند آزاد می‌کند؛ این ابزار نیاز به مدیریت دستی `free` را کم می‌کند، اما allocation زیاد یا نگه‌داشتن referenceهای بی‌مصرف همچنان هزینه دارد.

## ۲) Go برای چه مسئله‌هایی ساخته و استفاده می‌شود؟

Go در ساخت سرویس‌های شبکه‌ای، API، ابزارهای خط فرمان، سامانه‌های زیرساخت و پردازش‌های هم‌زمان کاربرد دارد. کتابخانهٔ استاندارد و toolchain واحد کمک می‌کنند برنامه را بدون زنجیرهٔ بزرگ از ابزارهای جدا build و test کنی. سبک زبان عمداً امکانات کمی دارد تا کد تیم‌ها شکل نسبتاً قابل پیش‌بینی داشته باشد.

باید سه مفهوم را جدا نگه داشت:

- **Concurrency / هم‌روندی:** چند کار در بازه‌های هم‌پوشان پیش بروند؛ scheduler می‌تواند نوبت اجرا را جابه‌جا کند.
- **Parallelism / موازی‌سازی:** چند کار واقعاً در همان لحظه روی چند هسته اجرا شوند.
- **Scalability / مقیاس‌پذیری:** سامانه زیر بار بیشتر چگونه رفتار می‌کند؛ این نتیجهٔ معماری، دیتابیس، شبکه، محدودیت resource و عملیات است، نه یک قابلیت جادویی زبان.

goroutine و channel ابزارهای Go برای ساخت برخی برنامه‌های هم‌روند هستند. استفادهٔ نادرست از آن‌ها هم می‌تواند deadlock، data race، goroutine leak یا فشار بیش‌ازحد بر دیتابیس بسازد.

## تاریخچهٔ کوتاه Go

هدف‌های طراحی Go در سال ۲۰۰۷ در Google شکل گرفت؛ ایده‌ها در واکنش به دشواری ساخت و نگه‌داری برنامه‌های بزرگ، اهمیت ماشین‌های چند‌هسته‌ای و نیاز به ابزارهای یکپارچه مطرح شدند. پروژه در ۱۰ نوامبر ۲۰۰۹ عمومی و متن‌باز شد؛ Go 1 در ۲۸ مارس ۲۰۱۲ به‌عنوان نقطهٔ سازگاری پایدار منتشر شد. این تاریخچه توضیح می‌دهد چرا concurrency، build، format و ابزار در کنار syntax زبان دیده می‌شوند؛ تاریخچه تضمین نمی‌کند هر تصمیم قدیمی برای workload امروزی مناسب است.
## ۳) چه وقت انتخاب Go منطقی است؟

برای انتخاب، این سؤال‌ها را جواب بده:

1. آیا مسئله سرویس شبکه‌ای، ابزار زیرساختی یا پردازش I/O هم‌زمان است؟
2. آیا build ساده و binary مستقل نسبت به اکوسیستم runtime ارزش دارد؟
3. آیا تیم تجربهٔ کافی دارد و کتابخانه‌های لازم در Go موجودند؟
4. گلوگاه واقعی latency، CPU، حافظه، توسعه، مجوز کتابخانه‌ها یا عملیات است؟
5. آیا با یک نمونهٔ کوچک و benchmark نماینده می‌توان فرضیه را سنجید؟

اگر محصول به کتابخانهٔ تخصصی بالغی نیاز دارد که در زبان دیگری موجود است، مهاجرت صرفاً برای «سرعت» ممکن است هزینه را زیاد کند. benchmark یک حلقهٔ مصنوعی نیز جای آزمایش مسیر واقعی با شبکه و دیتابیس را نمی‌گیرد.

## مثال کوتاه: تصمیم را به شرط‌های قابل مشاهده تبدیل کن

این تابع انتخاب معماری را انجام نمی‌دهد؛ فقط نشان می‌دهد یک فرضیه را می‌توان واضح و قابل آزمون نوشت:

</div>

```go
package main

import "fmt"

func shouldPrototypeGo(networkService, simpleDeployment bool) bool {
	return networkService && simpleDeployment
}

func main() {
	fmt.Println(shouldPrototypeGo(true, true))
}
```

<div dir="rtl">

`package main` برنامهٔ اجرایی می‌سازد. `import "fmt"` امکان چاپ را می‌دهد. تابع دو `bool` می‌گیرد و یک `bool` برمی‌گرداند. در `main` هر دو شرط درست‌اند، پس خروجی `true` است. در محصول واقعی، شرط‌ها را به latency هدف، روش deploy، staffing و نیاز اکوسیستم تبدیل کن؛ صرفاً براساس سلیقهٔ زبانی انتخاب نکن.

## تجربهٔ صنعتی: چه چیزی از case studyها یاد بگیریم؟

Dropbox نوشته است که بخشی از backendهای حساس به کارایی خود را از Python به Go منتقل کرده و برای نیازهای زیرساختی کتابخانه ساخته است. Twitch شرح داده که سرویس chat پرترافیکش با فشار GC روبه‌رو شد و اندازه‌گیری/گفت‌وگو با تیم Go به بهبود runtime کمک کرد. این مقاله‌ها مربوط به زمان و workload مشخص‌اند؛ از آن‌ها روش سنجش و trade-off را یاد بگیر، نه اینکه latency قدیمی را به Go فعلی نسبت بدهی.

## تمرین‌های مرحله‌ای

1. یک CLI که ورودی CSV می‌خواند، یک API فروشگاه و یک بازی دسکتاپ را مقایسه کن. برای هرکدام دو نیاز فنی و یک دلیل رد Go بنویس.
2. برای یک API ساده، پروتکل آزمایش انتخاب زبان را بنویس: workload، دادهٔ ورودی، p50/p95، مصرف حافظه و زمان توسعه.
3. به کسی که می‌گوید «Go چون سریع است» پاسخ بده و سه معیار قابل‌اندازه‌گیری پیشنهاد کن.

### پاسخ نمونهٔ تمرین ۱

CLI پردازش CSV می‌تواند به‌دلیل binary ساده و کتابخانهٔ استاندارد مناسب باشد. API فروشگاه ممکن است مناسب باشد، اما latency و توان تیم را باید سنجید. بازی دسکتاپ به موتور/گرافیک و ابزارهای آن وابسته است؛ نبود اکوسیستم مطلوب می‌تواند دلیل انتخاب زبان دیگری باشد.

### کلید پاسخ

1. نام رسمی Go است؛ Golang لقب رایج برای جست‌وجو و رفع ابهام است.
2. سازگاری نوع عبارت‌ها را پیش از اجرا، هنگام کامپایل بررسی می‌کند.
3. خیر؛ objectهای reachable زنده می‌مانند و allocation و GC هزینه دارند.
4. هم‌روندی هم‌پوشانی/سازمان‌دهی چند کار است؛ موازی‌سازی اجرای هم‌زمان فیزیکی روی چند هسته است.
5. خیر؛ concurrency با parallelism یکی نیست و تنظیم runtime/سخت‌افزار هم دخیل‌اند.
6. چون شبکه، serialization، دیتابیس و contention در benchmark تابع ممکن است غایب باشند.
7. workload، latency، حافظه، اکوسیستم، مهارت تیم، عملیات و هزینهٔ نگه‌داری نمونه‌هایی هستند.
8. اعداد latency و نتیجهٔ یک شرکت با workload/سخت‌افزار/نسخهٔ همان گزارش.
9. در نوامبر ۲۰۰۹ متن‌باز شد؛ Go 1 در مارس ۲۰۱۲ منتشر شد.
