# ۰۱.۴ — ابطال، تازگی، TTL و جلوگیری از Cache Stampede

**زبان:** فارسی · [English version](../../../../en/backend-performance/01-caching/04-invalidation-and-freshness/README.md)


**تاریخ بررسی منابع: ۲۰۲۶-۱۱-۱۰** · پیش‌نیاز: [Cache-aside](../02-cache-patterns/README.md)، [کش چندسطحی](../03-multi-level-caching/README.md)، deadline و هم‌زمانی.

## هدف یادگیری و تعریف

پس از این درس می‌توانید بودجه کهنگی را از زمان نگهداری فیزیکی جدا کنید، TTL و ابطال رخدادمحور را ترکیب کنید و هجوم readهای هم‌زمان پس از انقضا را محدود کنید. **Freshness** یعنی نتیجه در محدوده قرارداد تازگی محصول باشد؛ **invalidation** اعلام بی‌اعتباری نسخه؛ **TTL** مدت نگهداری/اعتبار تعیین‌شده در قرارداد کش است. معنی TTL در یک کش key/value با تازگی پاسخ HTTP کاملاً یکسان نیست و باید در طراحی روشن شود.

## اصطلاح‌های لازم در همین صفحه

**Deadline** آخرین زمانی است که عملیات یا نتیجه طبق قرارداد پذیرفتنی است. **هم‌زمانی** تعداد عملیات loader است که در یک لحظه فعال‌اند. **stale** نسخه‌ای است که از بازهٔ تازه‌بودن بیرون رفته اما شاید برای مصرف محدود هنوز مجاز باشد. در این درس اجازهٔ stale جدا از وجود فیزیکی داده تعریف می‌شود.

## مدل ذهنی: سه ساعت و چهار رویداد

برای یک ورودی، `sourceVersion` یا زمان تغییر منبع، `fetchedAt` و deadline استفاده از نسخه را از هم جدا کنید. اگر اکنون از یک read replica عقب‌مانده داده گرفته‌اید، `fetchedAt=now` ثابت نمی‌کند داده تازه‌ترین commit است. همچنین «هنوز در حافظه وجود دارد» معادل «اجازه مصرف دارد» نیست.

| رویداد | چه تغییری می‌کند؟ | معنای درست |
| --- | --- | --- |
| expiration | عمر تعیین‌شده تمام می‌شود | read بعدی ممکن است miss یا نیازمند refresh باشد |
| eviction | حافظه تحت سیاست ظرفیت آزاد می‌شود | می‌تواند پیش از TTL رخ دهد |
| invalidation | نسخه مشخص یا مجموعه وابسته نامعتبر می‌شود | معمولاً پس از تغییر منبع یا انتشار محتوا |
| refresh | داده دوباره از منبع تهیه/اعتبارسنجی می‌شود | موفقیت، خطا و هزینه آن باید دیده شود |

Redis TTL را از طریق فرمان‌هایی مانند [EXPIRE](https://redis.io/docs/latest/commands/expire/) فراهم می‌کند؛ سیاست حافظه و [eviction](https://redis.io/docs/latest/develop/reference/eviction/) موضوع جداست. TTL طولانی تضمین نمی‌کند ورودی تا آن زمان در حافظه بماند. در Redis می‌توان با `SET ... EX ...` مقدار و انقضا را در یک فرمان تعیین کرد؛ دو فرمان جدا، فاصله شکست دارند. بازنویسی عادی با `SET` هم می‌تواند TTL قبلی را از بین ببرد؛ گزینه‌ها را از [مستند SET](https://redis.io/docs/latest/commands/set/) بررسی کنید.

## انتخاب سیاست تازگی و ابطال

۱. **از محصول بپرسید:** آیا توضیح کالا می‌تواند چند ثانیه قدیمی باشد؟ آیا مجوز لغوشده یا قیمت قطعی چنین فرصتی دارد؟ برای هر دسته قرارداد جدا بنویسید.

۲. **کلیدهای وابسته را پیدا کنید:** تغییر کالا ممکن است کلید کالا، فهرست دسته و نتیجه جست‌وجو را تحت تأثیر قرار دهد. delete یک کلید همه آن‌ها را اصلاح نمی‌کند.

۳. **مسیر تغییر را تعریف کنید:** commit منبع، ثبت قابل اتکای رخداد تغییر در صورت نیاز، و سپس ابطال/refresh. رخداد پیش از commit می‌تواند موجب fill از نسخه قبلی شود.

۴. **برای شکست برنامه داشته باشید:** TTL پشتیبان، retry محدود، ثبت lag ابطال و جلوگیری از fill قدیمی. outbox می‌تواند رخداد را با commit هماهنگ کند، ولی مصرف‌کننده و retry آن نیز باید طراحی شوند.

| سیاست | مناسب‌تر برای | هزینه/محدودیت |
| --- | --- | --- |
| فقط TTL | داده با کهنگی قابل تحمل و writerهای ساده | تا انقضا امکان دیدن نسخه قدیمی هست |
| ابطال پس از write + TTL | داده پرتغییر با نیاز به واکنش سریع‌تر | پیام/حذف می‌تواند شکست بخورد؛ وابستگی کلیدها مهم است |
| کلید/URL نسخه‌دار | asset یا snapshot تغییرناپذیر | مصرف‌کننده باید نسخه جدید را پیدا کند؛ نسخه قدیمی باید جمع شود |
| soft expiry و refresh پس‌زمینه | نمایش داده‌ای که stale محدود را می‌پذیرد | stale باید سقف مشخص داشته باشد؛ برای هر داده‌ای مجاز نیست |
| خواندن معتبر در مسیر حساس | تصمیمی که کهنگی برایش پذیرفتنی نیست | هزینه منبع و تراکنش بیشتر؛ کش نمایشی جدا بررسی می‌شود |

این انتخاب‌ها trade-off هستند. TTL صفر یا بسیار کوتاه ممکن است تقریباً تمام بار را به منبع برگرداند؛ TTL بلند می‌تواند hit خوب و تجربه غلط تولید کند.

## Stampede چیست و چگونه محدود می‌شود؟

اگر ورودی یک کلید محبوب منقضی شود و چندین درخواست هم‌زمان همگی loader را اجرا کنند، کش به‌جای حذف کار تکراری آن را تکثیر کرده است. به این وضعیت Cache Stampede می‌گوییم. انقضای هم‌زمان کلیدهای فراوان یا restart همه replicaها نیز می‌تواند موج miss ایجاد کند.

- **Request coalescing / singleflight:** درخواست‌های هم‌زمان یک کلید، یک بارگذاری درحال اجرا را شریک می‌شوند. این کار با lock سراسری روی همه کلیدها فرق دارد و انتظار followers باید deadline داشته باشد.
- **TTL jitter:** زمان انقضای کلیدهای مختلف را پخش کنید. اگر بودجه تازگی حداکثر ۳۰ ثانیه است، نمونه `random(24,30)` آن را رد نمی‌کند؛ افزودن jitter مثبت تا ۴۰ ثانیه قرارداد را عوض می‌کند. jitter به‌تنهایی stampede یک hot key را متوقف نمی‌کند.
- **Soft expiry:** داده تا `freshUntil` تازه است؛ تا `staleUntil` فقط در صورت مجاز بودن stale، پاسخ قبلی ارائه و یک refresh آغاز می‌شود. بعد از سقف، منتظر refresh محدود می‌مانیم یا خطای کنترل‌شده می‌دهیم.
- **حد ظرفیت منبع:** concurrency limit و deadline برای بارگذاری، حتی اگر کش قطع باشد. refresh پس‌زمینه هم مصرف‌کننده همین ظرفیت است.

تجربه عملیاتی [Amazon درباره request coalescing و رفتار کش سرد](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/) پشتوانه خوبی برای این انتخاب‌هاست. coalescing محلی در ده replica می‌تواند تا ده بارگذاری هم‌زمان ایجاد کند؛ اگر این مقدار زیاد است، هماهنگی بین replicaها یا روش دیگری لازم است.

## مثال حل‌شده: soft و hard deadline برای یک توضیح عمومی

**سناریوی آموزشی، نه تنظیم توصیه‌شده برای همه سرویس‌ها:** شرح عمومی کالا از منبع معتبر در `t=0` گرفته می‌شود. محصول ۳۰ ثانیه reuse تازه و حداکثر ۱۵ ثانیه stale اضافه هنگام refresh را می‌پذیرد. این قرارداد را برای قیمت نهایی یا مجوز دسترسی استفاده نکرده‌ایم.

<div dir="ltr" align="left">

```text
entry = { value, sourceVersion, freshUntil: 30, staleUntil: 45 }

function getDescription(key, requestDeadline):
    entry = cache.getEnvelope(key)
    if entry.exists and now < entry.freshUntil:
        return entry.value
    if entry.exists and now < entry.staleUntil:
        startRefreshOncePerKey(key)  # bounded, shared inside this process
        return entry.value         # allowed stale, counted separately
    return awaitLoadOncePerKey(key, requestDeadline)
    # If load fails or deadline expires: return a defined error/degraded result.
```

</div>

در `t=32` بیست read هم‌زمان داخل **یک فرایند** می‌توانند نسخه قبلی را فوری بگیرند و یک refresh داشته باشند. اگر refresh در `t=34` موفق شود، envelope جدید از داده معتبر ساخته می‌شود. اگر refreshها شکست بخورند، در `t=46` دیگر اجازه ارائه همان نسخه به استناد این قرارداد نداریم؛ باید انتظار محدود یا خطای تعریف‌شده داشته باشیم. `staleUntil` با هر خطای refresh تمدید نمی‌شود. برای آنکه داده stale قابل ارائه باشد، مقدار باید تا hard deadline در storage باقی بماند؛ حذف فیزیکی در soft expiry این امکان را از بین می‌برد.

در HTTP، مفهوم نزدیک با `Cache-Control: max-age=30, stale-while-revalidate=15` بیان می‌شود؛ پشتیبانی و سایر دستورهای پاسخ باید بررسی شوند. هدر HTTP به‌خودی‌خود منطق `startRefreshOncePerKey` کش داخلی را نمی‌سازد. تعریف این extension و `stale-if-error` در [RFC 5861](https://www.rfc-editor.org/rfc/rfc5861.html) است؛ دو پنجره مستقل را با «اجازه stale برای همیشه» اشتباه نگیرید.

## race و lease: چرا یک قفل کافی نیست؟

خواننده A نسخه ۷ را می‌خواند، نویسنده B نسخه ۸ را commit و کش را باطل می‌کند، سپس A نسخه ۷ را fill می‌کند. TTL اثر را محدود می‌کند اما نقض را حذف نمی‌کند. یکی از راه‌های طراحی، نسل/نسخه قابل مقایسه همراه داده و کنترل اتمیک مجوز fill است. بررسی نسخه و سپس نوشتن در دو عمل مستقل دوباره race دارد؛ حذف کلید هم می‌تواند اطلاعات نسخه لازم برای رد fill قدیمی را حذف کند. این بخش نیازمند قرارداد مشخص writer و storage است، نه صرف افزودن فیلد `version` به JSON.

برای coalescing بین replicaها ممکن است lease محدود به زمان بگیرید. `SET lock:key token NX PX ...` یک primitive است، نه اثبات کامل هماهنگی: مالک باید token یکتا داشته باشد، آزادسازی باید به‌صورت اتمیک فقط با token همان مالک انجام شود، و loader قدیمی پس از پایان lease نباید بتواند روی داده جدید overwrite کند. توقف طولانی process و failover را هم در نظر بگیرید. [مستند Redis درباره distributed locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/) فرض‌ها و مرزها را شرح می‌دهد؛ برای کاهش بار کش از کتابخانه/طرح بررسی‌شده استفاده کنید و قفل را جای تضمین صحت تراکنش تجاری نگذارید.

## تمرین کوچک و راه‌حل نمونه

۱. روی خط زمان `0, 29, 32, 44, 46` بنویسید پاسخ تازه، stale مجاز یا نیازمند بارگذاری است. فرض کنید refresh همواره شکست می‌خورد.

۲. بیست read در `t=32` یک فرایند را یک بار با coalescing و یک بار بدون آن تحلیل کنید.

۳. همین بیست درخواست را میان پنج replica بدون هماهنگی مشترک پخش کنید.

۴. برای ۱۰۰ کلید که همگی در `t=0` پر شده‌اند، TTL ثابت ۳۰ را با TTL انتخاب‌شده از ۲۴ تا ۳۰ مقایسه کنید. درباره **یک** کلید بسیار محبوب جدا نتیجه بگیرید.

**انتظار:** در ۲۹ تازه، در ۳۲ و ۴۴ stale مجاز و در ۴۶ خارج از پنجره است. در یک فرایند با coalescing یک refresh کافی است؛ بدون آن تا ۲۰ loader ممکن است اجرا شود. در پنج replica، coalescing محلی تا پنج refresh را مجاز می‌گذارد. jitter موج انقضای کلیدهای مختلف را پخش می‌کند ولی بار هم‌زمان یک hot key را تجمیع نمی‌کند. این‌ها شمارش مسیر در مدل‌اند، نه اندازه‌گیری تولید.

## راه‌حل گام‌به‌گام تمرین

با refresh ناموفق: در ثانیهٔ ۰ و ۲۹ داده تازه است؛ در ۳۲ و ۴۴ داده stale ولی طبق قرارداد مجاز است؛ در ۴۶ از hard deadline گذشته و باید loader محدود یا پاسخ کنترل‌شده اجرا شود. در یک replica، singleflight بیست loader را به یکی کاهش می‌دهد؛ بدون آن تا بیست خواندن منبع ممکن است. با پنج replica و فقط coalescing محلی، سقف نمونه پنج loader است. TTLهای ۲۴ تا ۳۰ انقضای صد کلید را پخش می‌کنند و هیچ‌کدام از سقف ۳۰ ثانیه عبور نمی‌کنند؛ یک hot key همچنان می‌تواند هم‌زمان چند درخواست داشته باشد و به coalescing نیاز دارد.

## تجربه عمومی مستند: TTL متناسب با زمان داده در Netflix

> [Netflix TechBlog، ۶ آوریل ۲۰۲۶](https://netflixtechblog.com/stop-answering-the-same-question-twice-interval-aware-caching-for-druid-at-netflix-scale-22fadc9b840e) یک لایه **آزمایشی** interval-aware برای queryهای Druid داشبوردها را شرح می‌دهد. تیم برای تازه‌ترین داده، کهنگی محدود پنج‌ثانیه‌ای را آگاهانه پذیرفته و برای بازه‌های قدیمی‌تر TTL بلندتر در نظر گرفته است؛ late-arriving events در این انتخاب نقش دارند. شاهد مربوط به داشبوردهای همان محیط است، نه قاعده‌ای برای پرداخت یا مجوز دسترسی. نتیجه آموزشی: TTL باید با معنای زمان و تحمل مصرف‌کننده هماهنگ باشد؛ عددهای آن گزارش را بدون بررسی به سامانه دیگر منتقل نکنید.

## failure mode و سیگنال عملیاتی

| شکست | نشانه | اقدام بررسی |
| --- | --- | --- |
| موج انقضا | جهش miss، loader concurrency و p99 | پراکندگی expiry، coalescing و محدودیت منبع |
| stale بی‌پایان | سن داده رشد می‌کند ولی hit بالا می‌ماند | hard deadline، شمارنده stale و آخرین refresh موفق |
| ابطال عقب‌افتاده | lag رخداد و اختلاف version | مسیر commit/انتشار/مصرف و retry |
| cache error به‌عنوان not-found | نبود جعلی داده پس از timeout | تمایز خطا، miss و نبود قطعی |
| eviction قبل از TTL | افزایش miss در فشار حافظه | اندازه working set و سیاست eviction |
| lease منقضی و fill دیررس | برگشت نسخه قدیمی پس از refresh جدید | token، کنترل نسل و رد write قدیمی |

## چک‌لیست عملیاتی

- [ ] بودجه تازگی هر نوع داده و اجازه stale جدا و صریح است.
- [ ] سن داده، source version و زمان آخرین refresh موفق قابل مشاهده‌اند.
- [ ] TTL، soft deadline و نگهداری فیزیکی با هم سازگارند.
- [ ] کلیدهای مستقیم و مشتق‌شده در ابطال دیده شده‌اند.
- [ ] خطای delete/انتشار رخداد بعد از commit مسیر جبران دارد.
- [ ] بارگذاری هم‌زمان یک کلید و انقضای جمعی کلیدها جدا بررسی شده‌اند.
- [ ] jitter از حداکثر کهنگی مجاز فراتر نمی‌رود.
- [ ] coalescing، deadline، سقف concurrency و رفتار پس از hard expiry مشخص‌اند.
- [ ] خرابی کش، قطع پیام و loader دیررس با مدل شکست طراحی شده‌اند.

## آزمون

۱. تفاوت expiration و eviction چیست؟

۲. چرا `fetchedAt=now` ثابت نمی‌کند داده تازه‌ترین commit منبع است؟

۳. آیا TTL برابر ۳۰ با jitter مثبت ۱۵ همچنان سقف ۳۰ ثانیه را حفظ می‌کند؟

۴. در مثال، اگر refresh هر بار شکست بخورد آیا در `t=46` همان نسخه مجاز است؟

۵. singleflight محلی در پنج replica الزاماً چند loader مشترک بین همه ایجاد می‌کند؟

۶. چرا آزادسازی lock با `DEL` بدون بررسی token خطر دارد؟

۷. افزودن `version` به مقدار بدون کنترل اتمیک fill چه مشکلی را حل نمی‌کند؟

### پاسخ تشریحی

۱. expiration از عمر ورودی می‌آید و eviction از سیاست حافظه/ظرفیت؛ دومی می‌تواند زودتر رخ دهد. تضمین حضور تا پایان TTL نداریم.

۲. شاید منبع خواندن عقب‌مانده باشد؛ زمان fetch، سن یا نسخه واقعی منبع را به‌تنهایی اثبات نمی‌کند.

۳. خیر؛ زمان استفاده ممکن است تا ۴۵ برسد. برای سقف ۳۰، دامنه jitter باید درون همان سقف بماند یا قرارداد محصول صریحاً تغییر کند.

۴. خیر؛ hard deadline برابر ۴۵ است. تمدید خودکار در هر شکست، stale را نامحدود می‌کند و خلاف قرارداد مثال است.

۵. الزاماً یکی نیست؛ تا یک loader در هر replica، یعنی پنج تا، ممکن است داشته باشیم. هماهنگی بین replicaها قرارداد دیگری لازم دارد.

۶. ممکن است lease قبلی تمام شده و مالک جدید lock را گرفته باشد؛ مالک قدیمی با DEL قفل دیگری را حذف می‌کند. بررسی مالکیت و حذف باید اتمیک باشند.

۷. race میان بررسی نسخه و نوشتن باقی می‌ماند؛ fill قدیمی می‌تواند بعد از ابطال/نسخه جدید برگردد. باید مجوز انتشار نتیجه و رفتار writerها واقعاً هماهنگ شوند.

## جمع‌بندی

TTL، eviction و invalidation رویدادهای متفاوت‌اند؛ تازگی را از زمان دریافت تا deadline بسنجید و برای شکست ابطال یک مسیر جبران داشته باشید. برای stampede، coalescing و محدودیت بار منبع لازم است؛ jitter فقط موج چند کلید را پخش می‌کند و مجوز stale باید hard limit داشته باشد.

## منابع اختیاری و مرجع

مدل زمانی، محدودیت stale و پاسخ تمرین در همین درس تعریف شده‌اند؛ لینک‌ها مرجع فنی و مطالعهٔ اضافه‌اند.

- انگلیسی، مستند رسمی: [Redis EXPIRE](https://redis.io/docs/latest/commands/expire/)، [SET](https://redis.io/docs/latest/commands/set/) و [Key eviction](https://redis.io/docs/latest/develop/reference/eviction/)، برای معنای دقیق انقضا و ظرفیت.
- انگلیسی، قرارداد HTTP: [RFC 5861](https://www.rfc-editor.org/rfc/rfc5861.html)، برای stale-while-revalidate و stale-if-error؛ این RFC از نوع Informational است و پشتیبانی محصول باید جدا بررسی شود.
- انگلیسی، طراحی هماهنگی: [Redis distributed locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)، برای token، lease و فرض‌های ایمنی.
- انگلیسی، شواهد مهندسی: [Amazon caching challenges](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/) و [Netflix interval-aware caching](https://netflixtechblog.com/stop-answering-the-same-question-twice-interval-aware-caching-for-druid-at-netflix-scale-22fadc9b840e)، برای cold cache، coalescing و انتخاب تازگی وابسته به داده.
- فارسی، مرور آموزشی: [نت پارادیس: TTL، ابطال و Cache Stampede](https://netparadis.com/redis-data-types-caching-strategy/)، برای آشنایی واژگان و مثال؛ کد نمونه را جای طرح کامل هماهنگی توزیع‌شده نگذارید.
