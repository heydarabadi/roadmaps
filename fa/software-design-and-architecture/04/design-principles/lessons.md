# درس کامل: اصول طراحی نرم‌افزار


> **زبان:** [نسخهٔ انگلیسی](../../../../en/software-design-and-architecture/04/design-principles/lessons.md)

## هدف و روش استفاده

اصل طراحی پاسخ قطعی به هر مسئله نیست؛ راهنمایی است برای دیدن هزینهٔ احتمالی. هر اصل را با این چهار سؤال به کار ببر: چه تغییری محتمل است؟ چه چیزی در کد اکنون دردسر ایجاد می‌کند؟ این اصل چه مرزی پیشنهاد می‌دهد؟ چه پیچیدگی تازه‌ای تحمیل می‌کند؟

نمونه‌های این درس حول سامانهٔ سفارش‌اند. هدف این است که موقعیت استفاده و موقعیت کنارگذاشتن هر اصل را بفهمی، نه آنکه acronymها را حفظ کنی.

## ۱. SOLID به عنوان پنج راهنمای مرتبط

SOLID پنج اصل طراحی شیءگرا را جمع می‌کند. آن‌ها با هم انسجام، گسترش کنترل‌شده و وابستگی به قرارداد را بهتر می‌کنند، اما اجرای مکانیکی‌شان تعداد interface و class را زیاد می‌کند.

### S — Single Responsibility

یک ماژول باید حول یک مسئولیت منسجم یا یک گروهی که نیازمندی را تغییر می‌دهد جمع شود. منظور «هر کلاس فقط یک متد» یا «یک کار کوچک» نیست. اگر تغییر مالیات و تغییر قالب چاپ فاکتور معمولاً توسط دو actor مستقل درخواست می‌شود، احتمالاً دو مسئولیت داریم.

روش: تغییرهای اخیر را بررسی کن؛ نیازهای مستقلی که یک ماژول را دست می‌زنند پیدا کن؛ مرز را فقط وقتی جدا کن که coupling واقعی یا دشواری آزمون وجود دارد. ماژول‌های ریز با نام‌های عمومی می‌توانند cohesive بودن را بدتر کنند.

### O — Open-Closed

کد باید برای تغییر رفتار با افزودن گسترش مناسب باز باشد و درعین‌حال بخش‌های پایدار را بی‌دلیل دستکاری نکنیم. هدف جلوگیری از هر edit نیست؛ هدف کم‌کردن ریسک تغییر در منطق حساس و تست‌شده است.

اگر روش تخفیف مرتب اضافه می‌شود، Strategy یا rule registry ممکن است کمک کند. اگر فقط دو نوع ثابت وجود دارد و تغییر سالی یک‌بار است، switch خوانا و ساده شاید بهتر باشد. OCP بیشتر برای محور تغییری مناسب است که شواهد واقعی از رشد آن داریم.

### L — Liskov Substitution

زیرنوع باید جای نوع پایه بنشیند و قرارداد رفتاری را حفظ کند. اگر subtype استثنای تازه‌ای می‌طلبد، عملیات پایه را ممنوع می‌کند یا پس‌شرط را تضعیف می‌کند، احتمالاً رابطهٔ subtype غلط است.

contract test بنویس: برای همهٔ پیاده‌سازی‌ها، ورودی معتبر، خروجی، خطا و invariant مشترک را بررسی کن. صرف داشتن متدهایی با امضای برابر کافی نیست.

### I — Interface Segregation

مصرف‌کننده نباید به عملیاتی وابسته باشد که به آن نیاز ندارد. interface بزرگ با متدهای unrelated را بر اساس capability مصرف‌کننده تقسیم کن. اما ساختن interfaceهای یک‌متدی بی‌شمار هم شناخت معماری را دشوار می‌کند؛ ابتدا نقش واقعی callerها را ببین.

### D — Dependency Inversion

منطق سطح بالا به جزئیات پایین‌سطح وابسته نشود؛ هر دو به قرارداد پایدار تکیه کنند و جزئیات آن را پیاده کنند. کد source dependency از controller/SDK به قرارداد application یا domain جهت می‌گیرد. در runtime فراخوانی ممکن است از use case به adapter برسد؛ جهت اجرای فراخوانی با جهت dependency کد یکی نیست.

~~~text
Application policy -> PaymentAuthorizer contract <- Vendor adapter
~~~~

این اصل به معنای interface برای هر class نیست. آن را جایی به کار ببر که تغییر vendor، نیاز تست یا مرز ownership وجود دارد.

## ۲. DRY — Don't Repeat Yourself

DRY می‌گوید دانش و قاعدهٔ واحد را به چند منبع مستقل تبدیل نکن. هدف حذف هر شباهت متنی نیست. دو validation شبیه ممکن است قواعد متفاوتی از دو actor باشند؛ وصل‌کردنشان یک dependency ناموجه می‌سازد. برعکس، قانون مالیاتِ یکسان که در API و batch job جداگانه تکثیر شده، دیر یا زود ناسازگار می‌شود.

قبل از استخراج تابع مشترک، بپرس: آیا دو نسخه یک قاعده را بیان می‌کنند؟ آیا هم‌زمان تغییر می‌کنند؟ آیا خروجی/خطا باید یکسان باشد؟ اگر فقط ساختار syntax شبیه است، duplication را نگه دار تا دانش مشترک روشن شود.

## ۳. YAGNI — You Aren't Gonna Need It

قابلیتی را برای نیاز احتمالی اما اثبات‌نشده نساز. قابلیت آینده‌نگر هزینهٔ ساخت، تست، امنیت، مستند و پشتیبانی دارد و ممکن است هیچ‌وقت استفاده نشود. طراحی را قابل تکامل بساز، ولی plugin framework و abstraction چندلایه را برای فرض مبهم تحمیل نکن.

YAGNI بهانه‌ای برای رد امنیت، audit، privacy، سازگاری داده یا الزام قانونی نیست؛ این‌ها نیازهای فعلی واقعی‌اند. تصمیم‌های برگشت‌ناپذیر و مهاجرت داده هم ممکن است پیش‌بینی زودهنگام لازم داشته باشند.

## ۴. Law of Demeter — قانون دیمتر

یک واحد باید با همکارهای نزدیک خود ارتباط بگیرد، نه زنجیرهٔ عمیق ساختار داخلی را بداند. عبارت customer.address.city اگر در چند جای دامنه تکرار شود، ساختار objectها به caller نشت کرده است. API دامنه‌ای مانند shipping_destination() می‌تواند معنا را نگه دارد.

قانون دیمتر «هر نقطهٔ دسترسی ممنوع» نیست. متدهای واسط زیاد هم می‌توانند boilerplate بسازند. مسئله این است که caller به جزییاتی وابسته شده که حق مالکیتش را ندارد.

## ۵. Tell, Don't Ask — بگو، نپرس

وقتی object مالک state و invariant است، به آن operation بده به‌جای آنکه state را بخوانی، بیرون تصمیم بگیری و setter بزنی.

~~~python
# بهتر: owner خودش اعتبار انتقال را بررسی می‌کند
order.cancel(reason, now)

# شکننده: caller state را می‌خواند و تصمیم را خودش اجرا می‌کند
if order.state != "shipped":
    order.state = \"cancelled\"
~~~

این اصل همهٔ queryها را ممنوع نمی‌کند. گزارش و view می‌توانند داده بخوانند؛ مسئله زمانی است که چند caller قانون تغییر state را جداگانه پیاده کنند.

## ۶. Hollywood Principle — کنترل را به چارچوب بسپار

قاعدهٔ «ما با تو تماس می‌گیریم» می‌گوید چارچوب یا هماهنگ‌کننده جریان کنترل را در دست دارد و جزء از طریق hook یا contract فراخوانی می‌شود. نمونه: framework درخواست را به handler تزریق‌شده می‌سپارد؛ handler نباید چرخهٔ سرور را خودش کنترل کند.

این روش extension point و inversion of control را ممکن می‌کند، اما جریان اجرا را کمتر آشکار می‌کند. trace، log و naming روشن لازم است. Dependency Injection به تنهایی Hollywood Principle کامل نیست؛ تمرکز اصل بر کنترل فراخوانی است.

## ۷. Composition over Inheritance

ترکیب رفتار از اجزای کوچک به‌جای ساخت hierarchy عمیق، تغییر مستقل و همکاری چند قابلیت را آسان می‌کند. سفارش می‌تواند یک shipping policy و یک discount policy داشته باشد؛ برای ترکیب انواع مشتری، کمپین و مقصد classهای متعدد نساز.

Inheritance مناسب است وقتی subtype واقعاً قرارداد پایه را حفظ می‌کند. Composition هم رایگان نیست: wiring، collaborator و ترتیب همکاری را باید نگه داشت. اگر یک رفتار ساده و پایدار است، interface و strategy اضافی لازم نیست.

## ۸. Encapsulate What Varies

بخشی را جدا کن که احتمال تغییرش با بخش‌های دیگر متفاوت است. این احتمال را از تغییرهای اخیر، قواعد دامنه، نیاز چند مشتری یا vendor dependency پیدا کن. abstraction صرفاً بر مبنای «شاید یک روز» معمولاً حدس گران است.

نمونه: نرخ مالیات برای کشورها تغییر مستقل دارد؛ محاسبهٔ subtotal شاید ثابت است. سیاست نرخ را جدا می‌کنیم اما orchestration فاکتور را به ده interface تقسیم نمی‌کنیم.

## ۹. Program to Abstractions

مصرف‌کننده به قراردادی وابسته باشد که نیاز خودش را بیان می‌کند، نه کلاس concrete یا SDK خارجی. این فکر به DIP نزدیک است اما تأکیدش بر انتخاب نقطهٔ استفاده است: use case فقط قابلیت authorize را می‌خواهد، نه تمام عملیات vendor.

abstraction باید معنا را حفظ کند و failure mode را ترجمه کند. اگر API هنوز type و exception vendor را بیرون می‌دهد، consumer همچنان به جزئیات بسته است. برای هر class concrete یک interface نساز؛ آن را برای مرز تغییر، تست یا چند implementation واقعی نگه دار.

## ۱۰. چطور اصول را با هم بسنجیم؟

اصول گاهی تنش دارند:

- DRY در برابر coupling: ادغام دو مفهوم شبیه ممکن است هر تغییر را به هر دو تحمیل کند.
- OCP در برابر سادگی: extension point بیش از نیاز کد را پیچیده می‌کند.
- abstraction در برابر direct call: قرارداد تعویض‌پذیر هزینهٔ wiring دارد.
- composition در برابر inheritance: انعطاف بیشتر می‌تواند collaboratorهای زیادی بسازد.
- SRP در برابر fragmentation: مرز مستقل مفید است، کلاس بسیار کوچک ممکن است صرفاً انتقال کد باشد.

ترتیب تصمیم: فشار تغییر را مشخص کن؛ کوچک‌ترین طراحی را بساز؛ آزمون مرز را اضافه کن؛ هزینهٔ تغییر بعدی را پایش کن؛ وقتی شواهد کافی شد abstraction را شکل بده. ADR کوتاه برای تصمیم‌های پرهزینه ثبت کن.

## ۱۱. تمرین جامع

در یک checkout فرضی:

1. دو قانون تکراری را پیدا و تعیین کن آیا دانش واحدند (DRY).
2. یک boolean مبهم را به نام رفتار یا نوع معنی‌دار تبدیل کن.
3. state انتقال سفارش را کپسوله کن (Tell, Don't Ask).
4. تصمیم بگیر تخفیف‌ها نیاز به Strategy دارند یا switch کافی است (OCP/YAGNI).
5. قرارداد payment را از SDK جدا کن (DIP/abstraction).
6. ثبت کن چه زمانی این جداسازی را حذف یا گسترش می‌دهی.

## ۱۲. آزمون با پاسخ‌نامه

۱. آیا DRY یعنی تابع‌سازی هر دو کد شبیه؟
   - پاسخ: نه؛ باید یک دانش و مسیر تغییر مشترک داشته باشند. شباهت نحوی کافی نیست.
۲. در SOLID کدام اصل می‌گوید consumer نباید به متد نامرتبط وابسته شود؟
   - پاسخ: Interface Segregation.
۳. چرا OCP را برای هر switch اعمال نمی‌کنیم؟
   - پاسخ: محور تغییر ممکن است پایدار باشد و extension point هزینهٔ اضافی دارد.
۴. یک subtype متد پایه را با NotImplementedError جواب می‌دهد. چه اصلی را بررسی می‌کنی؟
   - پاسخ: Liskov substitution؛ رابطهٔ subtype و قرارداد پایه احتمالاً نادرست است.
۵. یوزکیس به SDK پرداخت وابسته است. چه تغییری با DIP پیشنهاد می‌شود؟
   - پاسخ: use case به contract محدود نیازش وابسته شود و adapter SDK را ترجمه کند.
۶. Tell, Don't Ask چه تفاوتی با حذف query دارد؟
   - پاسخ: query لازم است؛ اصل می‌گوید قانون تغییر state را در بیرون مالک تکرار نکن.
۷. یک interface با ۱۸ متد بهتر است یا ۱۸ interface تک‌متدی؟
   - پاسخ: هیچ عددی پاسخ نیست؛ بر اساس نقش واقعی caller و capabilityهای منسجم طراحی کن.
۸. YAGNI آیا اجازه می‌دهد audit پرداخت را حذف کنیم؟
   - پاسخ: خیر، اگر audit الزام فعلی محصول/قانون است؛ YAGNI برای قابلیت اثبات‌نشده است.
۹. Law of Demeter را در زنجیرهٔ objectها چطور می‌سنجی؟
   - پاسخ: آیا caller ساختار داخلی‌ای را می‌داند که owner می‌تواند رفتار دامنه‌ای واضح‌تری عرضه کند؟
۱۰. چه زمانی composition را انتخاب نمی‌کنی؟
   - پاسخ: وقتی variation واقعی نیست یا wiring و abstraction از سود تغییر مستقل بیشتر می‌شوند.
