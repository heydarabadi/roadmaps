   7: ## پیش‌نیاز و مسیر مطالعه
   8:

  20: ## سناریوی پیونددهنده
  21: 
  22: در فروشگاه **فرضی**، عکس‌ها و فونت عمومی‌اند ولی سفارش‌ها شخصی‌اند. انتقال API به نزدیک کاربر ممکن است با DB دور، سه رفت‌وبرگشت جدید بسازد. اول محل داده و مسیر checkout را تحلیل کنید؛ سپس Client طول‌عمر مناسب و Pool محدود بسازید. عکس نسخه‌دار را روی CDN قرار دهید و پاسخ سفارش را از کش مشترک خارج کنید. فقط فونت حیاتی همین صفحه را Preload و یک منبع عمومی محتمل برای صفحه بعد را با بودجه محدود Prefetch کنید. موفقیت یعنی پاسخ درست، تأخیر کمتر و هزینه قابل‌قبول؛ hit بیشتر یا اتصال کمتر به‌تنهایی کافی نیست.

   3: # ۱۰.۱ — انتخاب منطقه و تأخیر شبکه
   4: 
   5: **هدف یادگیری:** RTT را از ظرفیت لینک و زمان سرور جدا کنید، مسیر وابستگی را محاسبه کنید و محل برنامه/داده را با توزیع واقعی کاربران بسنجید. پیش‌نیاز: HTTP و Trace. بررسی منابع: **۲۰۲۶-۱۱-۱۰**؛ عددها آموزشی و اجرا‌نشده‌اند.
   6: 
   7: ## مدل ذهنی و روش کار
   8: 
   9: درخواست از کاربر به API و سپس به DB، Cache یا سرویس دیگر می‌رود. نزدیکی جغرافیایی می‌تواند زمان انتشار را کم کند، اما Routing، Peering، ازدحام و صف هم اثر دارند. یک Region نزدیک روی نقشه الزاماً بهترین مسیر شبکه را ندارد. RTT نیز زمان یک‌طرفه نیست؛ نصف آن بدون فرض تقارن، اندازه‌گیری دقیق یک‌طرفه نمی‌دهد.
  10: 
  11: | اندازه‌گیری | چه چیزی می‌گوید؟ | محدودیت |
  12: | --- | --- | --- |
  13: | RTT مسیر | رفت‌وبرگشت در شرایط نمونه | Ping/ICMP ممکن است رفتار HTTP را نمایندگی نکند |
  14: | DNS/Connect/TLS | هزینه کشف و آماده‌سازی اتصال | اتصال گرم این هزینه را برای هر درخواست تکرار نمی‌کند |
  15: | TTFB از دید کاربر | زمان تا اولین بایت پاسخ | شبکه، صف و پردازش می‌توانند ترکیب شوند |
  16: | زمان بدنه و Throughput | هزینه تحویل حجم پاسخ | loss، ظرفیت و کندی مصرف‌کننده مهم‌اند |
  17: | Trace وابستگی | hopهای سریال و انتظار پایین‌دست | مرز ابزارگذاری و زمان خارج Trace را بررسی کنید |
  18: 
  19: ۱. سهم کاربران، ISP/منطقه و Routeهای حساس را بنویسید. ۲. چند پنجره شامل اوج و اختلال را نمونه بگیرید. ۳. API، DB و تماس‌های بین‌منطقه‌ای را روی مسیر پاسخ رسم کنید. ۴. هم‌مکانی، کاهش call و کش مجاز را پیش از تکثیر سراسری مقایسه کنید. ۵. با ترافیک محدود، p95/p99، خطا و هزینه را بسنجید؛ درصدک‌های مناطق را میانگین نگیرید و آن را p95 کل ننامید.
  20: 
  21: ## مثال حل‌شده: API نزدیک، DB دور
  22: 
  23: مدل **فرضی** اتصال گرم، بدنه کوچک و سه call سریال DB دارد. پردازش کل ثابت ۲۰ ms است؛ هیچ صف، handshake یا هم‌پوشانی نداریم:
  24: 
  25: </div>
  26: 
  27: ```text
  28: Layout A: user -> API RTT 80 ms; API -> DB RTT 2 ms
  29: response = 80 + 3*2 + 20 = 106 ms
  30: 
  31: Layout B: user -> API RTT 20 ms; API -> DB RTT 70 ms
  32: response = 20 + 3*70 + 20 = 250 ms
  33: ```
  34: 
  35: <div dir="rtl" align="right">
  36: 
  37: در این مدل، نزدیک‌تر کردن فقط API زمان را ۱۴۴ ms بیشتر می‌کند؛ DB دور سه بار در مسیر است. این جمع ساده پیش‌بینی دقیق اینترنت نیست. اگر وابستگی‌ها مستقل باشند، هم‌پوشانی طبق [مسیر بحرانی](../../06-code-optimization/04-critical-paths/README.md) مدل دیگری دارد. پاسخ بزرگ نیز زمان انتقال اضافه می‌کند؛ ۱ MiB روی نرخ مؤثر ثابت ۲ MiB/s حدود ۰٫۵ ثانیه برای بدنه می‌خواهد، جدا از انتظار شروع.
  38: 
  39: ## کاربرد و مصالحه
  40: 
  41: برای کاربران متمرکز، هم‌مکانی برنامه و داده اغلب نامزد بررسی است. کاربران جهانی ممکن است به لبه، خواندن محلی یا چند منطقه نیاز داشته باشند، با هزینه replication، کهنگی، عملیات و failover. داده را فقط برای کم کردن RTT تکثیر نکنید؛ الزامات محل نگه‌داری، مجوز، سازگاری و بازیابی را تعریف کنید. تماس بین منطقه و خروج داده می‌تواند هزینه مالی نیز داشته باشد. خرابی یک منطقه نباید به routing به نود ناسالم یا هجوم ناگهانی به مقصد باقی‌مانده منجر شود.
  42: 
  43: ## تمرین و انتظار
  44: 
  45: در Layout B، DB را هم‌منطقه و RTT آن را ۲ ms کنید؛ سپس یک سرویس پرداخت سریال با RTT برابر ۹۰ ms اضافه کنید. **انتظار:** مدل اول `20+6+20=46 ms` و با پرداخت `136 ms` است. اکنون گلوگاه تازه را مشخص کنید. برای تصمیم واقعی، حداقل دو گروه کاربر و دو بازه بار را مقایسه کنید؛ نتیجه تمرین معیار تضمینی سرویس نیست.
  46: 
  47: ## شاهد عمومی و حدود آن
  48: 
  49: گزارش **۹ ژوئن ۲۰۲۶** [Discord Voice at the Edge](https://discord.com/blog/how-we-moved-discord-voice-to-the-edge) نشان می‌دهد پوشش جغرافیایی بیشتر به‌تنهایی کافی نبود: مسیریابی تماس و مشکلات زمان‌بندی برنامه/زیرساخت هم بر نتیجه اثر داشتند. این تجربه مربوط به رسانه بلادرنگ روی UDP و زیرساخت مشخص است؛ اعداد آن هدف HTTP API ما نیستند. سناریوی DB بالا فرضی و مستقل از این گزارش است.

  51: ## شکست‌ها، علائم و چک‌لیست
  52: 
  53: TTFB بد فقط در یک ISP، تماس‌های cross-region روی Trace، افزایش egress، و tail بد در اوج، مسیرهای بررسی‌اند. میانگین سالم ممکن است گروه کوچکی از کاربران دور را پنهان کند؛ یک آزمون از لپ‌تاپ نویسنده جای توزیع کاربران را نمی‌گیرد.
  54: 
  55: - [ ] کاربر، API، DB و وابستگی‌های سریال مکان و RTT مشخص دارند.
  56: - [ ] اتصال سرد/گرم و پاسخ کوچک/بزرگ جدا بررسی شده‌اند.
  57: - [ ] نمونه‌های اوج و تفکیک منطقه/ISP کنار هزینه ثبت می‌شوند.
  58: - [ ] سازگاری، محل داده، failover و ظرفیت مقصد جایگزین تعریف شده‌اند.
  59: - [ ] معیار کاربر با Trace داخلی و زمان خارج Trace تطبیق داده می‌شود.

   3: # ۱۰.۲ — بازاستفاده اتصال با توجه به نسخه HTTP
   4: 
   5: **هدف یادگیری:** هزینه ایجاد اتصال را از هر درخواست جدا کنید، Client/Pool محدود و طول‌عمر مناسب طراحی کنید و persistence در HTTP/1.1 را با multiplexing اشتباه نگیرید. پیش‌نیاز: TCP، TLS و HTTP. بررسی منابع: **۲۰۲۶-۱۱-۱۰**؛ شبه‌کد و محاسبه آموزشی‌اند.
   6: 
   7: ## مدل ذهنی و تفاوت نسخه‌ها
   8: 
   9: Reuse یعنی چند درخواست از اتصال قابل‌استفاده موجود عبور کنند. DNS، اتصال و TLS ممکن است در اتصال سرد هزینه داشته باشند؛ تعداد دقیق RTT به پروتکل، resumption و شبکه بستگی دارد. TCP keepalive، Header با نام Keep-Alive و HTTP persistent connection مفاهیم یکسانی نیستند.
  10: 
  11: | نسخه | بازاستفاده | محدودیت مهم |
  12: | --- | --- | --- |
  13: | HTTP/1.1 | persistence رفتار پیش‌فرض است، مگر پایان اتصال اعلام/ایجاد شود | بدون pipelining، روی هر اتصال یک exchange فعال داریم؛ Pool می‌تواند چند اتصال داشته باشد |
  14: | HTTP/2 | چند Stream هم‌زمان روی یک اتصال TCP | محدودیت Stream/flow control و اثر loss در TCP باقی است |
  15: | HTTP/3 | Streamهای چندگانه روی اتصال QUIC | ظرفیت، congestion، محدودیت Stream و پشتیبانی مسیر همچنان مهم‌اند |
  16: 
  17: [RFC 9112 بخش 9.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3) persistence را برای HTTP/1.1 تعریف می‌کند؛ برای فعال‌سازی معمول آن افزودن `Connection: keep-alive` لازم نیست. در **HTTP/2 و HTTP/3 نباید Headerهای connection-specific مانند `Connection` یا `Keep-Alive` تولید کنید**؛ تنظیم reuse در transport/Client انجام می‌شود. [RFC 9113 بخش 8.2.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.2.2) و [RFC 9114 بخش 4.2](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.2) قواعد را مشخص می‌کنند. نسخه سمت کاربر و سمت Origin پشت Proxy ممکن است متفاوت باشد؛ هر hop را جدا بررسی کنید.
  18: 
  19: ## روش و مثال حل‌شده
  20: 
  21: Client و transport را طبق مستند کتابخانه بازاستفاده کنید؛ wrapper تازه الزاماً transport تازه نیست، اما ساخت Pool مستقل برای هر درخواست می‌تواند reuse را از بین ببرد. پاسخ را کامل مصرف و منبع آن را آزاد کنید؛ در HTTP/1.1 بدنه ناتمام می‌تواند reuse را ناممکن کند. هنگام لغو، طبق API امن کتابخانه پاسخ/Stream را ببندید؛ بدنه نامحدود را صرفاً برای reuse تخلیه نکنید.
  22: 
  23: </div>
  24: 
  25: ```text
  26: # Created once per configured destination/policy, not per incoming request:
  27: client = shared_client(bounded_pool, bounded_pending_queue, idle_policy)
  28: 
  29: on_request(deadline):
  30:     response = client.send(request, deadline, cancellation)
  31:     try:
  32:         return read_bounded_response(response)
  33:     finally:
  34:         response.close_according_to_client_contract()
  35: ```
  36: 
  37: <div dir="rtl" align="right">
  38: 
  39: مدل **فرضی** ده درخواست سریال دارد: آماده‌سازی اتصال سرد ۶۰ ms و هر exchange روی اتصال آماده ۲۵ ms است. بدون reuse: `10*(60+25)=850 ms`؛ با یک اتصال پایدار: `60+10*25=310 ms`. صرفه‌جویی مدل ۵۴۰ ms است؛ این عدد تعداد RTT یا سود ثابت TLS/HTTP/2 نیست. Multiplexing درخواست‌های مستقل می‌تواند هم‌پوشانی اضافه ایجاد کند، ولی ظرفیت سرور و صف باید دوباره مدل شوند. Reuse تعداد query یا بایت پاسخ را خودکار کم نمی‌کند.
  40: 
  41: ## کاربرد، هزینه و تمرین
  42: 
  43: برای callهای مکرر به مقصد ثابت مفید است. اتصال idle نیز FD، حافظه و state مصرف می‌کند. سقف اتصال، صف acquire، deadline و برای HTTP/2/3 تعداد Stream را محدود کنید. idle timeout ناسازگار با Load balancer می‌تواند reset ایجاد کند. اتصال بسیار طولانی ممکن است تغییر DNS یا جابه‌جایی مقصد را دیر منعکس کند؛ سیاست refresh/lifetime به Client وابسته است. قطع اتصال لزوماً نشان نمی‌دهد write انجام نشده؛ Retry باید [ایمن و محدود](../../06-code-optimization/07-timeouts-and-retries/README.md) باشد.
  44: 
  45: **تمرین:** در مدل بالا آماده‌سازی را ۱۲۰ ms کنید؛ پاسخ قبل/بعد و تعداد اتصال تازه را حساب کنید. سپس بعد از درخواست پنجم، بسته‌شدن اتصال توسط Peer را فرض کنید. **انتظار:** بدون reuse برابر ۱۴۵۰ ms، با یک اتصال ۳۷۰ ms و با یک بازاتصال اضافی ۴۹۰ ms است؛ فرض کرده‌ایم شکست درخواست/Retry هزینه دیگری ندارد. در ابزار دلخواه، connection count، acquire wait، TLS و p99 را جدا ببینید؛ آزمایش واقعی در این درس انجام نشده است.
  46: 
  47: ## شاهد عملیاتی و حد آن
  48: 
  49: [راهنمای رسمی MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Connection_management_in_HTTP_1.x) مدل اتصال کوتاه/پایدار و تفاوت multiplexing را مستند می‌کند. این سند عملیاتی شاهد سازوکار است، نه گزارش benchmark یک شرکت. مطالعه تولیدی مستقلی با همین مدل ده‌درخواستی در منابع این درس ارائه نشده؛ اعداد فرضی‌اند. سازگاری Headerها را از RFCها و [مرجع Keep-Alive](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Keep-Alive) بخوانید.

  51: ## شکست‌ها و چک‌لیست
  52: 
  53: افزایش اتصال جدید و TLS در هر call، نشتی response، Pool اشباع، reset پس از idle و تعداد زیاد reconnect هنگام failover علائم قابل بررسی‌اند. بزرگ کردن Pool بدون دیدن ظرفیت مقصد می‌تواند overload را تشدید کند.
  54: 
  55: - [ ] نسخه HTTP و reuse در هر hop مشاهده شده است.
  56: - [ ] Client/transport چرخه عمر روشن و Pool/صف محدود دارد.
  57: - [ ] پاسخ در موفقیت، خطا و لغو طبق قرارداد آزاد می‌شود.
  58: - [ ] idle/lifetime، DNS و shutdown هماهنگ‌اند؛ reconnect هجوم نمی‌سازد.
  59: - [ ] connection count، reuse، acquire wait، خطا و Streamهای فعال پایش می‌شوند.
  60: - [ ] هیچ Header connection-specific به HTTP/2/3 افزوده نمی‌شود.

  66: ۲. تفاوت reuse با multiplexing چیست؟
  67:

  69:

  71: 
  72: ۵. آیا reuse مشکل N+1 را خودکار حل می‌کند؟
  73: 
  74: ۶. اگر اتصال بعد از write قطع شد، آیا Retry بی‌قید امن است؟

  76: ### پاسخ با دلیل
  77: 
  78: ۱. خیر؛ persistence پیش‌فرض است. سیاست Peer و بسته‌شدن اتصال همچنان تعیین‌کننده‌اند.
  79: 
  80: ۲. reuse چند درخواست را از اتصال موجود عبور می‌دهد؛ multiplexing exchangeهای چند Stream را هم‌زمان روی آن حمل می‌کند.
  81: 
  82: ۳. فیلد connection-specific در آن پروتکل ممنوع است؛ اتصال با سازوکار پروتکل مدیریت می‌شود.
  83: 
  84: ۴. منابع/اتصال ممکن است اشغال بمانند؛ در HTTP/1.1 مرز و مصرف بدنه برای reuse اهمیت دارد و کتابخانه قرارداد آزادسازی دارد.
  85: 
  86: ۵. خیر؛ هزینه ساخت اتصال کمتر می‌شود ولی N درخواست هنوز وجود دارد؛ برنامه واکشی/Batch باید اصلاح شود.
  87: 
  88: ۶. خیر؛ نتیجه ممکن است اعمال شده باشد. idempotency یا استعلام نتیجه و بودجه Retry لازم‌اند.
