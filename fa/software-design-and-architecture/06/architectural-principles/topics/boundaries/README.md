## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

مرز معماری سطحی است که قرارداد، مالکیت داده و جهت وابستگی را روشن می‌کند؛ مرز می‌تواند درون فرایند، شبکه، تیم یا محصول باشد.

## مثال کاربردی

پرداخت و کاتالوگ ابتدا componentهای داخلی‌اند؛ زمانی که مالکیت یا مقیاس جدا لازم شد مرز سرویس ارزیابی می‌شود.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «اصول معماری» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** مرز شبکه‌ای refactor و تراکنش را گران‌تر می‌کند؛ مرز درون‌فرایندی انعطاف‌پذیرتر است.
- **بازبینی:** مرز را از روی جدول دیتابیس یا پوشه انتخاب نکن؛ مسئولیت و تغییرات هم‌زمان را بررسی کن.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: مرز معماری سطحی است که قرارداد، مالکیت داده و جهت وابستگی را روشن می‌کند؛ مرز می‌تواند درون فرایند، شبکه، تیم یا محصول باشد.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: پرداخت و کاتالوگ ابتدا componentهای داخلی‌اند؛ زمانی که مالکیت یا مقیاس جدا لازم شد مرز سرویس ارزیابی می‌شود.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: مرز شبکه‌ای refactor و تراکنش را گران‌تر می‌کند؛ مرز درون‌فرایندی انعطاف‌پذیرتر است.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: مرز را از روی جدول دیتابیس یا پوشه انتخاب نکن؛ مسئولیت و تغییرات هم‌زمان را بررسی کن.

## آموزش تکمیلی مستقل

### ۴. Boundaries

مرز مشخص می‌کند چه کسی مالک state است، چه قراردادهایی قابل‌استفاده‌اند و dependency از کجا عبور می‌کند. مرز می‌تواند:

- منطقی داخل package یا process؛
- سطح API بین سرویس‌ها؛
- شبکه یا trust boundary امنیتی؛
- ownership تیمی؛
- یا مرز محصول و bounded context باشد.

برای تصمیم مرز:

1. actor و قواعدی که باهم تغییر می‌کنند را پیدا کن.
2. دادهٔ منبع حقیقت و مسئولیت invariant را مشخص کن.
3. collaboration بین طرفین را بشمار و latency/failure را لحاظ کن.
4. قرارداد و روش مشاهدهٔ نتیجه را طراحی کن.
5. تا وقتی مرز درون‌فرایندی کافی است، network boundary را تحمیل نکن.

مرز زیاد هم خطر دارد: split کردن یک transaction به چند سرویس eventual consistency، retry، reconciliation و عملیات می‌خواهد. مرز کم هم مالکیت مبهم و تغییرهای هم‌زمان ایجاد می‌کند.

## نمودار معماری و خواندن مرحله‌ای

مرز را بر اساس مالکیت تصمیم، state و تغییرات هم‌زمان پیدا کن؛ نام پوشه یا جدول پایگاه‌داده به‌تنهایی مرز مناسبی نیست. API، ماژول، سرویس و bounded context می‌توانند مرزهای متفاوتی باشند و هرکدام هزینهٔ هماهنگی خود را دارند.
**دام رایج:** هر مرز منطقی را فوراً به سرویس قابل‌استقرار جدا تبدیل نکن.
**تمرین با پاسخ:** قانون قیمت‌گذاری و موجودی مالک‌های متفاوت دارند؛ قراردادشان را جدا کن، ولی محل استقرار را با شواهد عملیاتی تعیین کن.

این نمودار ساده فقط یک view را نشان می‌دهد؛ سامانهٔ واقعی به تصمیم روشن دربارهٔ شکست، امنیت و مالکیت هم نیاز دارد.

~~~text
+---------------------+      contract      +----------------------+
| Pricing policy     | <----------------> | Inventory capability |
| owns price rules   |                     | owns stock state     |
+---------------------+                     +----------------------+
             \                                  /
              \------ composition / API -------/
~~~
