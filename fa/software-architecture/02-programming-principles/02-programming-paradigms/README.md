# شیءگرایی، تابعی، واکنشی و Actor

## هدف یادگیری

مدل‌های اصلی برنامه‌نویسی را به‌عنوان راه‌های سازمان‌دهی state، رفتار و هم‌زمانی بشناس و برای مسئلهٔ مناسب انتخاب کن.

## مفاهیم

- **OOP:** گردآوری داده و رفتار کنار هم، با استفاده از encapsulation و قراردادها. وراثت یکی از ابزارهاست، نه هدف طراحی.
- **Functional programming:** توابع خالص، دادهٔ تغییرناپذیر, composition و اثرهای جانبی کنترل‌شده. این کار reasoning و آزمون را ساده می‌کند، هرچند I/O و state همچنان در مرزها وجود دارند.
- **Reactive programming:** واکنش به جریان داده یا رخدادها با درنظرگرفتن زمان، فشار تولید، لغو و خطا. «Reactive UI» الزاماً به معنای reactive architecture سراسرسامانه نیست.
- **Actor model:** هر actor مالک state خودش است و از طریق پیام با دیگر actorها ارتباط می‌گیرد؛ این جداسازی از قفل مشترک می‌کاهد اما پیام گم‌شده، ترتیب، تکثیر و بازیابی باید مدیریت شود.

پارادایم‌ها انحصاری نیستند. یک سامانهٔ وب شیءگرا می‌تواند در لایهٔ domain از توابع خالص استفاده کند، UI آن reactive باشد و workerهای توزیع‌شده الگوی actor یا پیام را پیاده کنند. معماری باید روشن کند state کجا نگهداری می‌شود و کدام بخش اثر جانبی دارد.

## عمیق‌تر: state، اثر جانبی و هم‌زمانی

**State** هر داده‌ای است که میان دو لحظهٔ اجرای رفتار تغییر می‌کند. وقتی چند بخش برنامه به یک mutable state مشترک دسترسی دارند، باید ترتیب تغییر و رقابت هم‌زمانی را اداره کرد. شیءگرایی این state را داخل object با invariant مشخص محصور می‌کند؛ برنامه‌نویسی تابعی ترجیح می‌دهد مقدار را immutable نگه دارد و نتیجهٔ جدید بسازد؛ Actor مالک state را به یک عامل پیام‌محور می‌دهد. این‌ها شکل‌های متفاوت کنترل همان مسئله‌اند.

**Effect** کاری است که نتیجه‌اش به جهان بیرون وابسته است: query پایگاه داده، خواندن ساعت، فراخوانی HTTP، نوشتن فایل یا ارسال پیام. اگر قاعدهٔ قیمت‌گذاری همزمان ساعت سیستم، شبکه و database را مستقیم بخواند، تست آن هم به همهٔ این وابستگی‌ها نیاز دارد. اگر قاعده را تابعی با ورودی روشن بسازیم، می‌توان آن را مستقل آزمود و سپس اتصال بیرونی را در adapter تست کرد.

Reactive programming معمولاً با جریان‌هایی سروکار دارد که با زمان تغییر می‌کنند؛ مانند جست‌وجوی کاربر هنگام تایپ. رفتار درست باید پاسخ‌های دیررس را مدیریت کند: اگر کاربر «کفش» و سپس «کفش مردانه» را جست، پاسخ درخواست اول ممکن است دیرتر برسد و نتیجهٔ جدید را overwrite کند. cancel، sequence number، backpressure و error channel جزئی از طراحی‌اند.

در Actor model نیز پیام بخشی از قرارداد است: آیا پیام durable است؟ آیا ترتیب برای یک کلید حفظ می‌شود؟ اگر Actor وسط کار crash کند، پیام دوباره می‌آید؟ چطور message deduplication می‌شود؟ تا وقتی این پرسش‌ها پاسخ ندارند، انتخاب Actor فقط تغییر شکل برنامه است و نه راه‌حل کامل distributed systems.

## نمونهٔ انتخاب

- قانون تخفیف بر اساس ورودی و قواعد ثابت: تابع pure برای آزمون‌پذیری.
- وضعیت سفارش و invariantهایش: object یا aggregate با رفتارهای محدود.
- به‌روزرسانی لحظه‌ای صفحهٔ قیمت: جریان reactive با لغو درخواست قدیمی.
- شمارش مستقل رویدادهای telemetry: consumerهای پیام‌محور یا Actor با idempotency.

معماری ترکیبی می‌تواند از این مدل‌ها کنار هم استفاده کند، به شرطی که boundary اثرهای جانبی، مالکیت state و error handling روشن بماند.

## مثال: قیمت‌گذاری سفارش

قانون تخفیف را می‌توان به تابعی خالص تبدیل کرد: ورودی سفارش و قواعد، خروجی مبلغ تخفیف است. دریافت قیمت از سرویس بیرونی اثر جانبی است و در adapter قرار می‌گیرد. رویداد «قیمت نهایی شد» می‌تواند پیام به مصرف‌کنندهٔ فاکتور باشد. این جداسازی آزمون قاعده را از شبکه و پایگاه داده مستقل می‌کند.

~~~text
pure:
  discount = calculate_discount(order, campaign_rules)

effectful boundary:
  inventory = await inventory_client.get(order.items)
  await message_bus.publish(OrderPriced(order.id, discount))
~~~

## چه زمانی کدام مدل؟

| رویکرد | سود اصلی | هزینه / خطر |
| --- | --- | --- |
| OOP | مدل‌سازی رفتارهای با invariant و مرز روشن | سلسله‌مراتب ارث‌بری شکننده |
| تابعی | آزمون ساده‌تر و اثر جانبی آشکار | یادگیری مفاهیم و کتابخانه‌های متفاوت |
| Reactive | مدیریت جریان‌های ناهمگام یا push | دشواری دیباگ، backpressure و جریان خطا |
| Actor | مالکیت state و جداسازی پیام‌محور | پیچیدگی توزیع و پروتکل پیام |

## دام‌ها

- برابر دانستن OOP با وراثت زیاد.
- ادعای بی‌state بودن سیستمی که state را فقط پنهان کرده است.
- ساخت stream/reactive chain برای عملیات سادهٔ request/response.
- فرض «یک پیام = دقیقاً یک‌بار» بدون طراحی تضمین و idempotency.

## آزمون

۱. تابع خالص چه مزیتی برای آزمون دارد؟  
**پاسخ:** خروجی تنها به ورودی وابسته است و تست به شبکه، ساعت یا state بیرونی نیاز ندارد.

۲. آیا functional programming به معنی نداشتن side effect است؟  
**پاسخ:** نه؛ اثرها را در مرزهای قابل‌کنترل نگه می‌دارد و بخش زیادی از منطق را مستقل می‌سازد.

۳. Actorها چگونه از race condition می‌کاهند؟  
**پاسخ:** state هر actor را انحصاری می‌کنند و تعامل را به پیام بدل می‌سازند؛ اما خطاهای پیام و توزیع باقی است.

۴. reactive programming چه مسئله‌ای را حل می‌کند و چه مسئله‌ای نمی‌کند؟  
**پاسخ:** جریان ناهمگام و واکنش به داده را سازمان می‌دهد؛ نیازمندی محصول، سازگاری یا مالکیت داده را خودبه‌خود حل نمی‌کند.

## تمرین

منطق محاسبهٔ هزینهٔ ارسال را از سرویس REST جدا کن. کدام بخش pure است؟ کدام adapter؟ اگر نرخ ارسال تغییر کرد، چه آزمون‌هایی لازم‌اند؟

## پاسخ نمونهٔ تمرین

تابع محاسبهٔ هزینه، ورودی‌های وزن، مقصد و tariff را می‌گیرد و مبلغ را بدون شبکه یا mutation برمی‌گرداند؛ این بخش pure و با جدول مرزی آزمون‌پذیر است. REST adapter نرخ را دریافت و timeout/خطا را به نوع داخلی تبدیل می‌کند. آزمون‌ها شامل وزن صفر/منفی، مرز bracket قیمت، tariff منقضی، timeout سرویس و پاسخ نامعتبرند. قانون مبلغ را با unit test و adapter را با contract/integration test بررسی کن.
