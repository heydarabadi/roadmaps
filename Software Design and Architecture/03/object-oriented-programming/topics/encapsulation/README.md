## مثال کاربردی

فقط `cancel()` سفارش را لغو می‌کند و زمان مجاز لغو را بررسی می‌کند؛ setter عمومی وضعیت وجود ندارد.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «برنامه‌نویسی شیءگرا» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** قفل‌کردن state می‌تواند تست یا همکاری را سخت کند؛ API لازم را روشن و کمینه نگه دار.
- **بازبینی:** فیلد خصوصی بدون invariant یا قرارداد، به‌تنهایی کپسوله‌سازی معنادار نیست.

## آموزش تکمیلی مستقل

#### کپسوله‌سازی (Encapsulation)

کپسوله‌سازی دسترسی مستقیم به state را کنترل می‌کند تا invariant حفظ شود. invariant شرطی است که باید پیش و پس از همهٔ operationهای معتبر برقرار بماند؛ برای مثال موجودی حساب پس از برداشت نباید از حد اعتباری مجاز عبور کند.

گام‌ها: invariant را بنویس؛ setter آزاد را محدود کن؛ operation دامنه‌ای بساز؛ تغییر state را فقط از همان مسیر انجام بده؛ تلاش کن حالت نامعتبر حتی قابل ساخت نباشد.

~~~python
class Account:
    def __init__(self, balance_cents, credit_limit_cents=0):
        self._balance = balance_cents
        self._credit_limit = credit_limit_cents

    def withdraw(self, amount_cents):
        if amount_cents <= 0:
            raise ValueError("Amount must be positive")
        if self._balance - amount_cents < -self._credit_limit:
            raise InsufficientFunds()
        self._balance -= amount_cents
~~~

فیلد private بدون کنترل mutation کافی نیست؛ اگر متد دیگری مقدار را بدون invariant تغییر دهد، کپسوله‌سازی شکسته است. برای مجموعه‌های mutable باید مراقب باش reference داخلی از property بیرون نشت نکند.

## نمونهٔ کد مرحله‌ای

کپسوله‌سازی یعنی اختیار تغییر state و حفظ invariant را به مالک آن بسپاری. private کردن فیلد کافی نیست اگر setter عمومی یا عملیات جایگزین بتواند حالت نامعتبر بسازد. هر عملیات باید پیش‌شرط، نتیجه و شکستش را روشن کند.
**تمرین با پاسخ:** برداشت بیش از موجودی را کجا رد می‌کنی؟ در Account، چون همان مالک balance است؛ آزمون باید موجودی صفر، مقدار دقیق و برداشت بیش از موجودی را پوشش دهد.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا تصمیم طراحی روشن بماند.

~~~csharp
public sealed class Account(Money openingBalance)
{
    public Money Balance { get; private set; } = openingBalance;

    public void Withdraw(Money amount)
    {
        if (amount <= Money.Zero || amount > Balance)
            throw new InvalidOperationException("Invalid withdrawal.");
        Balance -= amount;
    }
}
~~~
