# اندازه و محدودیت Payload

**زبان:** فارسی · [English version](README.en.md)


Payload بدنهٔ پیام است؛ در این درس تمرکز بر دادهٔ پاسخ API است. «پاسخ کم‌حجم» یعنی حجم داده با نیاز مصرف‌کننده تناسب داشته باشد. «محدودیت» یعنی قرارداد جلوی رشد بی‌مهار تعداد آیتم، اندازهٔ فیلد یا Expand تو‌در‌تو را بگیرد. سقف زیرساخت با بودجهٔ مناسب تجربهٔ کاربر برابر نیست.

**پس از این درس می‌توانید:** اندازهٔ بازشده و منتقل‌شده را جدا تفسیر کنید؛ نمایش خلاصه بسازید؛ سقف آیتم و بایت را کنار هم تعریف کنید؛ و برای پاسخ بزرگ راه خروج قابل‌فهم طراحی کنید. پیش‌نیاز: JSON و HTTP. تاریخ بررسی منابع: **۲۰۲۶-۱۱-۱۰**.

## اصطلاح‌های پایه

HTTP درخواست و پاسخ را با Header و بدنه مبادله می‌کند؛ **JSON** یکی از قالب‌های متنی بدنه است. در این درس Payload یعنی محتوای بدنه، و اندازهٔ «بازشده» بایت JSON پس از بازکردن Compression است. این اندازه می‌تواند با بایت منتقل‌شده و حافظهٔ زمان Parse فرق کند.

## مدل ذهنی: هزینه از قبل از شبکه شروع می‌شود

| مرحله | هزینه‌ای که با دادهٔ اضافی رشد می‌کند | پرسش بازبینی |
| --- | --- | --- |
| واکشی | خواندن ستون/رابطه، انتقال از DB | آیا مصرف‌کننده این فیلد را لازم دارد؟ |
| ساخت پاسخ | Allocation، محاسبه، Serialization | آیا نمایش فهرست مستقل از نمایش جزئیات است؟ |
| انتقال | بایت روی شبکه و زمان دریافت | آیا اندازهٔ واقعی انتقال ثبت شده است؟ |
| مصرف | Decompression، Parse، حافظه و Render | آیا گوشی ضعیف می‌تواند پاسخ را مصرف کند؟ |

Compression مرحلهٔ انتقال را کوچک می‌کند، اما تعداد رکوردها و ساختار JSON پس از بازشدن همان است. انتخاب فیلد باید تا حد امکان پیش از واکشی/محاسبه اعمال شود؛ حذف فیلد در آخر Serializer فقط بخشی از هزینه را کم می‌کند. نمونهٔ رسمی Google Drive پارامتر `fields` را برای درخواست زیرمجموعهٔ داده مستند کرده است؛ این قابلیت قراردادی است و در هر API خودبه‌خود وجود ندارد. [منبع: Drive fields](https://developers.google.com/workspace/drive/api/guides/fields-parameter)

مسیر تصمیم‌گیری پیشنهادی:

1. برای هر مصرف‌کننده فیلدهای واقعاً مورد نیاز را بنویسید؛ مثلاً «کارت سفارش» به تاریخچهٔ همهٔ اقلام نیاز ندارد.
2. پاسخ خلاصه را پیش‌فرض کنید و جزئیات/رابطهٔ بزرگ را با درخواست صریح در دسترس بگذارید. فیلدهایی که برای ادامهٔ صفحه لازم‌اند، مانند Token، را فراموش نکنید.
3. تعداد آیتم، طول فیلدهای آزاد، تعداد و عمق Expand و بایت بدنهٔ بازشده را محدود کنید. سقف عددی را با دادهٔ واقعی و نیاز محصول انتخاب کنید.
4. اندازهٔ بازشده، اندازهٔ منتقل‌شده و حافظهٔ اوج را جدا بسنجید؛ `Content-Length` ممکن است در پاسخ فشرده اندازهٔ فشرده را نشان دهد یا اصلاً موجود نباشد.
5. عبور از حد را در قرارداد تعریف کنید: صفحهٔ کوچک‌تر با لینک ادامه، درخواست اصلاح پارامتر، یا Export جدا. بدنهٔ JSON را وسط یک شیء قطع نکنید.

### بودجهٔ آموزشی و سقف سخت

| نوع حد | نمونهٔ فرضی | رفتار طراحی‌شده |
| --- | --- | --- |
| بودجهٔ پایش | p95 بدنهٔ بازشدهٔ فهرست زیر ۱۰۰ KiB | هشدار و بررسی تغییر Schema؛ الزاماً خطا نیست |
| سقف تعداد | `page_size <= 50` | Clamp یا خطای پارامتر، طبق قرارداد مستند |
| سقف بایت | حداکثر ۲۵۶ KiB برای هر صفحهٔ این API | کمتر از سقف آیتم برگردان؛ Token ادامه بده |
| فیلد منفرد بسیار بزرگ | توضیح ۲ MiB در یک آیتم | خلاصهٔ مستند و مسیر جزئیات/فایل جدا |

این عددها **پیشنهاد عمومی یا نتیجهٔ آزمایش تولید نیستند**. اگر محدودیت بایتی یک آیتم را هم جا ندهد، کم کردن تعداد صفحه کافی نیست؛ باید نمایش آن آیتم یا مسیر تحویل تغییر کند. کلاینت نیز نباید «کمتر از `page_size`» را پایان قطعی بداند؛ قرارداد Token تعیین‌کننده است.

## مثال حل‌شده: کارت سفارش

**سناریوی فرضی:** Endpoint قبلی ۱۰۰ سفارش، همراه با تاریخچه و فایل درون JSON برمی‌گرداند. رابط فقط خلاصه را نمایش می‌دهد. قرارداد جدید چنین است:

<div dir="ltr" align="left">

```http
GET /v1/orders?page_size=2&fields=id,status,total HTTP/1.1
Host: api.example.test
Accept: application/json
```

```json
{
  "items": [
    {"id": "o-102", "status": "paid", "total": 480000},
    {"id": "o-101", "status": "pending", "total": 120000}
  ],
  "next_page_token": "opaque-token-1"
}
```

</div>

در قرارداد این مثال، `fields` فقط فیلدهای داخل `items` را کنترل می‌کند؛ Metadata ادامه همیشه باقی می‌ماند. مجوز مشاهدهٔ فیلدها مستقل از این پارامتر بررسی می‌شود. درخواست فیلد ناشناخته خطای مستند پارامتر دارد. یک URL جزئیاتِ تحت مجوز، جای انتقال خودکار فایل را می‌گیرد؛ این URL نباید دسترسی دائمی عمومی به فایل خصوصی ایجاد کند.

فرض کنید در خط مبنای آموزشی ۱۰۰ آیتم × ۲۰ KiB برابر حدود ۲۰۰۰ KiB دادهٔ آیتم است. نمایش خلاصهٔ ۵۰ آیتم × ۰٫۵ KiB حدود ۲۵ KiB می‌شود؛ Envelope و Header جدا هستند. این حساب نشان می‌دهد کاهش تعداد و کاهش اندازهٔ هر آیتم دو اهرم مستقل‌اند؛ نسبت واقعی را با JSON سریال‌شده بسنجید، نه با اندازهٔ شیء در حافظه.

## تمرین کوتاه و راه‌حل نمونه

یک نمونهٔ محلی JSON از ۲۰ سفارش بسازید که هرکدام یک توضیح بلند و تاریخچه دارند. بدون نیاز به سرور، دو فایل تولید کنید: «همهٔ فیلدها» و «فقط `id,status,total`». در PowerShell اندازهٔ UTF-8 ذخیره‌شده را بخوانید:

<div dir="ltr" align="left">

```powershell
Get-Item -LiteralPath .\orders-full.json, .\orders-summary.json |
    Select-Object Name, Length
```

</div>

سپس یک آیتم با توضیح بسیار بزرگ اضافه کنید و دوباره اندازه‌ها را مقایسه کنید. **انتظار:** تعداد آیتم ثابت است ولی اندازهٔ کامل زیاد می‌شود؛ نمایش خلاصه نباید با رشد تاریخچه افزایش مشابه داشته باشد. تفاوت بایت با تعداد کاراکتر را، به‌ویژه برای متن فارسی UTF-8، یادداشت کنید. این تمرین اندازه را نشان می‌دهد؛ ادعای کاهش latency یا CPU نیازمند اندازه‌گیری سرور است.

## راه‌حل نمونهٔ تمرین

اگر هر یک از ۲۰ سفارش در فایل کامل حدود ۲ KiB تاریخچه/توضیح داشته باشد، سهم آن بخش نزدیک `20×2=40 KiB` است؛ نمایش خلاصه‌ای با حدود 0.1 KiB برای هر سفارش نزدیک 2 KiB می‌شود، پیش از Envelope و فاصله‌گذاری JSON. اگر به یک سفارش 64 KiB توضیح اضافه شود، فایل کامل حدود 64 KiB دیگر رشد می‌کند، ولی خلاصه‌ای که آن فیلد را ندارد تقریباً ثابت می‌ماند. اندازهٔ واقعی را همان `Length` فایل می‌دهد؛ برای متن فارسی تعداد کاراکتر را با تعداد بایت UTF-8 یکی نگیرید.

## شاهد واقعی و حدود آن

**شاهد عملیاتی رسمی:** مستندات Google Drive برای `files.list` یک مجموعهٔ فیلد پیش‌فرض محدود معرفی می‌کند و امکان درخواست فیلدهای مشخص را توضیح می‌دهد. این نمونهٔ قابل‌استنادِ API واقعی است؛ این صفحه درصد بهبود سرویس ما را ثابت نمی‌کند. [Drive fields parameter](https://developers.google.com/workspace/drive/api/guides/fields-parameter)

**حد زیرساخت واقعی:** جدول HTTP API در Amazon API Gateway در تاریخ بررسی، Payload را ۱۰ MB و غیرقابل‌افزایش نشان می‌دهد. این عدد مربوط به همین نوع API است؛ آن را به همهٔ Gatewayها، APIهای Streaming یا وضعیت‌های پاسخ تعمیم ندهید. [جدول رسمی HTTP API quotas](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html)

`413 Content Too Large` به بزرگ بودن **محتوای درخواست** اشاره می‌کند؛ آن را کد عمومی «پاسخ سرور بزرگ شد» فرض نکنید. برای خروجی بزرگ، پیش از ارسال Header قرارداد صفحه/Export را اجرا کنید. [MDN: 413](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/413)

## هزینه‌ها، تناسب و شکست‌های رایج

نمایش ثابت خلاصه ساده‌تر و Cache آن قابل‌پیش‌بینی‌تر است. انتخاب آزاد فیلد به کلاینت‌های متفاوت انعطاف می‌دهد، اما ترکیب‌های Cache، مستندسازی و بررسی مجوز را بیشتر می‌کند. برای API کوچک با پاسخ چندصدبایتی، زبان پیچیدهٔ Projection ممکن است بیش از صرفه‌جویی هزینه داشته باشد. برای Export کامل، مسیر فایل/Streaming را بررسی کنید؛ محدودیت پاسخ تعاملی را بی‌حد نکنید.

| شکست | علامت عملیاتی | اقدام |
| --- | --- | --- |
| محدود کردن تعداد بدون محدود کردن فیلد بزرگ | p99 اندازه با تعداد یکسان جهش دارد | بیشترین اندازهٔ آیتم و Expand را جدا کنترل کن |
| حذف فیلد فقط پس از Queryهای گران | بایت کم شده ولی DB/CPU ثابت است | Projection و برنامهٔ واکشی را زودتر اعمال کن |
| ارسال بی‌صدای خروجی ناقص | کاربر بخشی از سفارش‌ها را گم می‌کند | Metadata ادامه و معنای خلاصه را مستند کن |
| حذف ناگهانی فیلد موجود | خطای کلاینت قدیمی | نسخه/تغییر سازگار و دورهٔ مهاجرت طراحی کن |
| ثبت بدنهٔ بزرگ در Log | هزینه و تأخیر Log یا افشای داده | اندازه و نوع نمایش را ثبت کن؛ بدنه لازم نیست |

### چک‌لیست عملیاتی

- [ ] برای Endpoint و مصرف‌کنندهٔ اصلی، فیلدهای ضروری ثبت شده‌اند.
- [ ] سقف آیتم، بایت، طول فیلد و Expand باهم مشخص‌اند.
- [ ] رفتار عبور از حد و تک‌آیتم بسیار بزرگ روشن است.
- [ ] اندازهٔ بازشده/منتقل‌شده و p95/p99 به تفکیک Route ثبت می‌شود.
- [ ] فیلد حساس با انتخاب کاربر یا Serializer خودکار افشا نمی‌شود.
- [ ] سناریوی مجموعهٔ خالی، متن فارسی بلند و کلاینت قدیمی مرور شده است.

## آزمون — ابتدا بدون پاسخ‌ها حل کنید

1. چرا سقف ۵۰ آیتم به‌تنهایی سقف بایت تضمین نمی‌کند؟
2. پاسخ ۲ MiB پس از gzip به ۱۰۰ KiB رسیده است؛ آیا حافظهٔ Parse کلاینت هم حتماً ۹۵٪ کم شده؟
3. اگر `fields=id` فقط در انتهای Serializer اعمال شود، کدام هزینه ممکن است باقی بماند؟
4. آیا `413` پاسخ استانداردی برای «JSON خروجی من بزرگ است» است؟
5. صفحه به علت سقف بایت ۱۸ آیتم از سقف ۵۰ دارد و Token ادامه هم موجود است؛ کلاینت باید متوقف شود؟
6. اضافه کردن Projection آزاد چه هزینه‌ای در مقایسه با نمایش ثابت خلاصه دارد؟

### پاسخ تشریحی

1. اندازهٔ آیتم‌ها یکسان نیست؛ یک فیلد بلند یا فایل درون‌خطی می‌تواند بودجه را بشکند. تعداد و بایت هر دو لازم‌اند.
2. خیر؛ داده پس از بازشدن تقریباً همان JSON قبلی است. حافظهٔ Parse به نمایش بازشده و Runtime نیز وابسته است.
3. واکشی رابطه‌ها، انتقال DB و محاسبهٔ فیلدها؛ برنامهٔ اجرای مبتنی بر فیلد باید زودتر تصمیم بگیرد.
4. خیر؛ معنای آن محتوای درخواست بزرگ‌تر از حد پذیرفته‌شده است. راهکار خروجی باید در قرارداد API تعریف شود.
5. خیر؛ Token ادامه می‌گوید نتیجهٔ بیشتری قابل درخواست است. تعداد کمتر از سقف، به‌خودی‌خود علامت پایان نیست.
6. ترکیب‌های بیشتری برای مجوز، Cache و نگه‌داری قرارداد ایجاد می‌کند؛ فقط با نیاز واقعی این پیچیدگی را بپذیرید.

## جمع‌بندی

ابتدا فیلد، تعداد آیتم و عمق رابطه را در قرارداد محدود کنید؛ سپس اندازهٔ بازشده، بایت انتقالی و حافظهٔ مصرف‌کننده را جدا بسنجید. سقف بایت باید راه ادامه یا خروجی جایگزین داشته باشد و به قطع بی‌صدای JSON منجر نشود.

## منابع اختیاری و مرجع

تعریف Payload، مثال و راه‌حل در همین صفحه برای یادگیری کافی‌اند؛ این منابع برای مطالعهٔ بیشتر و بررسی قراردادهای مشخص‌اند.

- [فارسی: بخش انتخاب فیلد در طراحی REST — نت پارادیس](https://netparadis.com/rest-design-pagination-filtering-versioning/): مقدمهٔ مرتبط با `fields` و `include`؛ منبع مکمل است، نه مرجع رفتار همهٔ APIها.
- [English: Google Drive fields](https://developers.google.com/workspace/drive/api/guides/fields-parameter): نمونهٔ دقیق قرارداد انتخاب فیلد و خطای انتخاب نامعتبر.
- [English: Google Drive API performance](https://developers.google.com/workspace/drive/api/guides/performance): توضیح partial response و کاهش فیلدهای بازگشتی؛ syntax پارامترها مخصوص Google Drive است.
- [English: WordPress REST global parameters](https://developer.wordpress.org/rest-api/using-the-rest-api/global-parameters/): نمونهٔ واقعی projection با `_fields`؛ قرارداد API وردپرس را به APIهای دیگر تعمیم ندهید.
- [English: Google API Design Guide](https://cloud.google.com/apis/design): اصول طراحی resource و فیلد پاسخ هماهنگ؛ راهنمای طراحی است، نه الزام همهٔ APIها.
- [English: MDN Content-Length](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Length): برای تفسیر طول بدنه؛ Header جای اندازه‌گیری همهٔ مراحل را نمی‌گیرد.
- [English: AWS HTTP API quotas](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html): نمونهٔ سقف سخت زیرساخت، قابل‌بررسی هنگام انتخاب مسیر تحویل.
