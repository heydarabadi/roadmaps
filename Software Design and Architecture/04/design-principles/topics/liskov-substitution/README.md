# اصل جانشینی لیسکوف (LSP) — Liskov Substitution Principle

## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

زیرنوع باید پیش‌شرط‌ها، پس‌شرط‌ها و انتظار رفتاری نوع پایه را حفظ کند تا مصرف‌کننده با نوع واقعی غافلگیر نشود.

## مثال کاربردی

اگر `ReadOnlyAccount` از حسابی ارث ببرد که `withdraw` دارد ولی خطا دهد، قرارداد پایه درست طراحی نشده است.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «اصول طراحی» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** گاهی رابطهٔ ارثی باید با دو abstraction مستقل جایگزین شود.
- **بازبینی:** فقط هم‌شکل‌بودن متدها به معنای سازگاری رفتاری نیست.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: زیرنوع باید پیش‌شرط‌ها، پس‌شرط‌ها و انتظار رفتاری نوع پایه را حفظ کند تا مصرف‌کننده با نوع واقعی غافلگیر نشود.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: اگر `ReadOnlyAccount` از حسابی ارث ببرد که `withdraw` دارد ولی خطا دهد، قرارداد پایه درست طراحی نشده است.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: گاهی رابطهٔ ارثی باید با دو abstraction مستقل جایگزین شود.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: فقط هم‌شکل‌بودن متدها به معنای سازگاری رفتاری نیست.

## آموزش تکمیلی مستقل

#### L — Liskov Substitution

زیرنوع باید جای نوع پایه بنشیند و قرارداد رفتاری را حفظ کند. اگر subtype استثنای تازه‌ای می‌طلبد، عملیات پایه را ممنوع می‌کند یا پس‌شرط را تضعیف می‌کند، احتمالاً رابطهٔ subtype غلط است.

contract test بنویس: برای همهٔ پیاده‌سازی‌ها، ورودی معتبر، خروجی، خطا و invariant مشترک را بررسی کن. صرف داشتن متدهایی با امضای برابر کافی نیست.

## نمونهٔ کد مرحله‌ای

زیرنوع باید قرارداد رفتاری پایه را حفظ کند: پیش‌شرط را سخت‌تر نکند، پس‌شرط و invariant را تضعیف نکند و خطای تازهٔ ناسازگار نسازد. شباهت امضای متد کافی نیست؛ همهٔ پیاده‌سازی‌ها را با قرارداد مشترک آزمون کن.
**تمرین با پاسخ:** اگر یکی از implementationها برای ورودی معتبر خطای اضافه می‌دهد، قرارداد یا subtype غلط است؛ خطا را در قرارداد عمومی مدل کن یا subtype را جدا کن.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا انتخاب طراحی روشن بماند.

~~~csharp
public interface ITransferAccount
{
    TransferResult TransferTo(ITransferAccount target, Money amount);
}

// Contract tests run the same valid, insufficient-funds,
// and self-transfer cases against every implementation.
~~~

## خلاصه

اصل جانشینی لیسکوف (LSP) را برای حل مسئلهٔ مشخص به کار ببر، trade-off آن را ثبت کن و با یک آزمون/معیار قابل مشاهده بررسی کن که آیا مرز طراحی واقعاً بهتر شده است.
