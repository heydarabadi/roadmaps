# اولویت، style و حل اختلاف

**زبان:** فارسی · [English](../../en/05-feedback/02-priority-conflict/README.md)

> مسیر: [فصل ۵ — بازخورد، شدت و اختلاف](../README.md) · [فهرست دوره](../../README.md)

## آموزش

blocker باید merge را متوقف کند چون باگ، امنیت، داده، قرارداد یا الزام تیم را تهدید می‌کند. suggestion بهبود اختیاری است؛ question برای فهم؛ nit نکتهٔ جزئی است. از برچسب‌هایی که تیم توافق کرده استفاده کن و روشن بنویس پیشنهاد غیرمسدودکننده است.

اول اثر و بعد polish را مطرح کن. formatter و linter برای style مناسب‌اند و style guide مرجع اختلاف است. تعداد کامنت معیار مهارت نیست؛ یک blocker دربارهٔ مجوز از ده‌ها nit مهم‌تر است.

اختلاف را به معیار تبدیل کن: requirement، داده، style guide، آزمون، design doc یا expert حوزه. اگر بحث می‌چرخد، گزینه‌ها و trade-off را خلاصه کن و owner مناسب را وارد کن. تصمیم و دلیل را ثبت کن تا در PR بعدی از نو بحث نشود. reviewer باید با شواهد نظرش را عوض کند و نویسنده نیز پاسخ مستدل بدهد.

## روند پیشنهادی

1. شدت را از پیامد مشخص کن.
2. blocker، suggestion، question و nit را جدا کن.
3. style را به ابزار و قاعدهٔ تیم ارجاع بده.
4. اختلاف را با معیار/شواهد و owner مناسب حل کن.
5. تصمیم و trade-off را ثبت کن.

## مثال کاربردی

نظر دربارهٔ نام متغیر اختیاری است و PR را متوقف نمی‌کند؛ اما تستی که دسترسی به tenant دیگر را نشان می‌دهد blocker است و باید پیش از merge حل شود.

## خطاهای رایج

همهٔ نظرها را blocker نکن؛ ایراد امنیتی را nit ننام؛ استاندارد شخصی را قانون تیم جا نزن؛ اختلاف را با عنوان شغلی حل نکن؛ comment را بی‌پاسخ رها نکن.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** کدام مورد blocker است؟

   1. ترجیح نام
   2. دسترسی به دادهٔ tenant دیگر
   3. پیشنهاد اختیاری refactor
   4. سؤال دربارهٔ علت

**پاسخ:** 2 — نقض مجوز باید پیش از merge حل شود.

### پرسش 2

**سؤال:** nit برای چیست؟

   1. ریسک بحرانی
   2. نکتهٔ جزئی و غیرمسدودکننده
   3. secret افشاشده
   4. هر مورد نامفهوم

**پاسخ:** 2 — برچسب باید شدت واقعی را نشان دهد.

### پرسش 3

**سؤال:** تعارض style را چه حل می‌کند؟

   1. رتبه
   2. style guide و formatter
   3. تعداد کامنت
   4. سلیقهٔ آخر

**پاسخ:** 2 — قاعدهٔ توافق‌شده به همه تعلق دارد.

### پرسش 4

**سؤال:** بحث دورانی چطور شکسته شود؟

   1. پیام بیشتر
   2. معیار، گزینه، trade-off و owner تصمیم
   3. تغییر موضوع
   4. approve فوری

**پاسخ:** 2 — بحث باید به تصمیم قابل‌ثبت برسد.

## آموزش عمیق: شدت، سلیقه و حل اختلاف

### طبقه‌بندی برای کم‌کردن سوءتفاهم

- **Blocker:** باگ، security، داده، قرارداد یا الزام روشن را تهدید می‌کند؛ تا حل یا تصمیم مسئول مناسب، merge متوقف است.
- **Suggestion:** بهترشدن را پیشنهاد می‌کند، اما راه فعلی هم قابل‌قبول است؛ اگر تیم توافق کند، مانع merge نیست.
- **Question:** برای فهم تصمیم یا invariant پرسیده می‌شود؛ پاسخ می‌تواند نیاز به تغییر ایجاد کند یا نکند.
- **Nit:** نکتهٔ کوچک و غیرمسدودکننده است؛ باید واقعاً اختیاری باشد.

این برچسب‌ها در همهٔ تیم‌ها یکسان نیستند. تیم باید در agreement خود مشخص کند چه کسی blocker را تعیین می‌کند، اختلاف چگونه حل می‌شود و آیا suggestionها پیش از merge لازم‌الاجرا هستند. برچسب جای دلیل را نمی‌گیرد.

### آیا این مورد blocker است؟

از خود بپرس:

1. آیا رفتار با نیازمندی، قرارداد یا policy توافق‌شده تعارض دارد؟
2. آیا پیامد قابل‌توضیح و شواهد کافی دارم؟
3. آیا رفع آن لازم است پیش از ادغام، یا می‌توان با issue و تصمیم آگاهانه پیگیری کرد؟
4. آیا این واقعاً سلیقه/پیشنهاد است که باید غیرمسدودکننده بماند؟

اگر پاسخ‌ها مبهم‌اند، سؤال یا درخواست شواهد مطرح کن، نه blocker مطلق. در مقابل، secret افشاشده یا دسترسی غیرمجاز را به‌خاطر لحن مؤدبانهٔ نویسنده کوچک نکن.

### سبک کد را شخصی نکن

از قاعدهٔ تیم، formatter و linter شروع کن. اگر راهنما دربارهٔ موردی ساکت است، از owner بپرس آیا این الزام معماری است یا ترجیح. بحثی که در PRهای بسیار تکرار می‌شود، نشانهٔ نیاز به تصمیم مستند یا اتوماسیون است. «من همیشه این‌طور می‌نویسم» قاعدهٔ عمومی نیست.

### حل اختلاف در پنج گام

1. اختلاف را در یک جمله تعریف کن.
2. معیار مورد استناد هر طرف را نام ببر: نیازمندی، امنیت، داده، style یا سلیقه.
3. گزینه‌ها و هزینهٔ هرکدام را بنویس.
4. owner/maintainer یا متخصص بی‌طرف را برای تصمیم حوزه‌ای وارد کن.
5. تصمیم و دلیل را در PR ثبت کن؛ اگر موضوع بزرگ‌تر شد، issue/design record باز کن.

اگر reviewer نظرش را با شواهد اصلاح می‌کند، این ضعف نیست؛ هدف بهترشدن تصمیم است. اگر بحث به حملهٔ شخصی تبدیل شد، مکالمه را متوقف، موضوع را از شخصیت جدا و طبق فرایند تیم تصعید کن.

### مثال

بازبین درخواست یک library برای format تاریخ می‌کند؛ نویسنده نشان می‌دهد نیاز فقط دو قالب است و dependency جدید مجوز/حجم بسته را تغییر می‌دهد. معیار تیم می‌گوید dependency تازه باید ارزش نگه‌داری داشته باشد. راه حل با بررسی کارکرد، footprint و policy تعیین می‌شود، نه با «فلان شرکت هم از آن استفاده می‌کند».

### تمرین

سه کامنت را طبقه‌بندی کن: (الف) «ترتیب import در style guide غلط است و CI fail می‌شود»؛ (ب) «نام متغیر را من کوتاه‌تر می‌کنم»؛ (ج) «این API می‌تواند دادهٔ tenant دیگر را برگرداند.» پاسخ: الف الزام قابل‌سنجش است و CI باید نشان دهد blocker است یا فقط قاعدهٔ خودکار؛ ب پیشنهاد/سلیقه و غیرمسدودکننده؛ ج اگر مسیر و اثر تأیید شود blocker امنیتی است.
