## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

مدل نوشتن که قواعد تغییر state را اجرا می‌کند از مدل خواندن جداست؛ در شکل ساده هر دو می‌توانند در یک سرویس و یک دیتابیس باشند.

## مثال کاربردی

ثبت سفارش با aggregate و query فهرست سفارش با projection متناسب با صفحه انجام می‌شود.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «الگوهای معماری» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** projection و سازگاری نهایی مدل خواندن را پیچیده می‌کند.
- **بازبینی:** CQRS لزوماً دو دیتابیس یا دو microservice نیست؛ فقط وقتی مدل خواندن/نوشتن واقعاً فرق دارد سود دارد.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: مدل نوشتن که قواعد تغییر state را اجرا می‌کند از مدل خواندن جداست؛ در شکل ساده هر دو می‌توانند در یک سرویس و یک دیتابیس باشند.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: ثبت سفارش با aggregate و query فهرست سفارش با projection متناسب با صفحه انجام می‌شود.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: projection و سازگاری نهایی مدل خواندن را پیچیده می‌کند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: CQRS لزوماً دو دیتابیس یا دو microservice نیست؛ فقط وقتی مدل خواندن/نوشتن واقعاً فرق دارد سود دارد.

## آموزش تکمیلی مستقل

### ۱۰. CQRS

CQRS مدل نوشتن و خواندن را جدا می‌کند. نسخهٔ ساده می‌تواند دو handler و دو model logical در یک process و دیتابیس باشد. مدل write invariant و transaction را اجرا می‌کند؛ read projection برای صفحه یا گزارش شکل می‌گیرد.

~~~python
def place_order(command, order_repository):
    order = Order.from_command(command)
    order_repository.save(order)
    return order.id

def get_order_summary(query, read_store):
    return read_store.find_summary(query.order_id)
~~~

CQRS لزوماً دو database یا دو service نیست. جداسازی physical زمانی ارزش دارد که query load، schema یا scalability به‌طور واقعی متفاوت باشد؛ در آن صورت projection delay و سازگاری نهایی نیز بخشی از قراردادند. Fowler هشدار می‌دهد که CQRS برای بسیاری از سیستم‌ها پیچیدگی ناموجه می‌سازد.

## نمودار معماری و خواندن مرحله‌ای

CQRS وقتی مفید است که نیازهای خواندن و نوشتن واقعاً متفاوت‌اند. commandها مدل نوشتن را تغییر می‌دهند؛ queryها projection خواندنی را می‌خوانند. جداسازی هزینهٔ همگام‌سازی و eventual consistency دارد و به‌تنهایی معماری microservices نیست.
**دام رایج:** برای CRUD کوچک دو مدل و دو دیتابیس نساز.
**تمرین با پاسخ:** dashboard کمی تأخیر می‌پذیرد؛ projection ناهمگام مناسب است، اما نتیجهٔ command را از مدل نوشتن و وضعیت commit بگیر.

این یک view ساده است؛ طراحی production باید مالکیت، شکست، امنیت و محدودیت‌های عملیاتی را نیز روشن کند.

~~~text
[Command] ---> [Write model] ---> [Write store]
                       |
                    events
                       v
[Query] <--- [Read projection] <--- [Projector]
~~~

## نمودار معماری و خواندن مرحله‌ای

CQRS وقتی مناسب است که نیاز خواندن و نوشتن واقعاً متفاوت باشد. command مدل نوشتن را تغییر می‌دهد و query projection خواندنی را می‌خواند؛ جداسازی، هزینهٔ همگام‌سازی و eventual consistency می‌آورد و به‌تنهایی microservices نیست.
**دام رایج:** برای CRUD کوچک مدل و دیتابیس دوتایی نساز.
**تمرین با پاسخ:** dashboard تأخیر را می‌پذیرد؛ projection ناهمگام بساز، اما نتیجهٔ commit را از مدل نوشتن برگردان.

این view ساده باید با تصمیم روشن دربارهٔ مالکیت، شکست، امنیت و عملیات کامل شود.

~~~text

                       |
                    events
                       v
[Query] <--- [Read projection] <--- [Projector]
~~~
