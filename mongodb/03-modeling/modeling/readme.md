# مدل‌سازی داده: Embed یا Reference

> **English edition:** [Read this lesson in English](../../en/03-modeling/modeling/readme.md).

> **هدف یادگیری:** مدل سند را بر اساس query و حد رشد طراحی کنید.

## جایگاه در مسیر
این درس بخشی از فصل مربوط است. مثال‌ها برای محیط آزمایشی‌اند؛ نسخه و قابلیت deployment خود را در مستندات رسمی بررسی کنید.

## تدریس کامل: schema را از query طراحی کنید

### اصل اول: طراحی برای workload

برای هر feature، فهرست queryهای اصلی را پیش از ساخت collection بنویسید. مثال order history:
- فهرست سفارش‌های یک مشتری، جدیدترین اول.
- نمایش یک سفارش به همراه اقلام و آدرس زمان خرید.
- یافتن سفارش بر اساس شناسه.
- گزارش فروش بر حسب روز و SKU.

هر query مشخص می‌کند چه فیلدهایی باید باهم در دسترس باشند، چه indexی لازم است و آیا داده‌ای باید کپی شود.

### Embed چه وقت خوب است؟

داده را داخل سند والد بگذارید اگر:
- معمولاً همراه والد خوانده می‌شود.
- رابطهٔ مالکیت روشن است.
- تعدادش محدود یا سقف‌دار است.
- جداگانه و مستقل تغییر نمی‌کند.
- اتمیک‌بودن یک سند به کار می‌آید.

نشانی زمان ثبت سفارش را embed کنید، چون آدرس مشتری ممکن است بعداً عوض شود ولی فاکتور باید وضعیت زمان خرید را نگه دارد. همچنین اقلام سفارش را به همراه عنوان و قیمت زمان خرید به شکل snapshot ذخیره کنید.

### Reference چه وقت مناسب است؟

داده را جدا نگه دارید اگر:
- رشد بالقوه نامحدود است.
- چند والد به یک موجودیت مشترک اشاره دارند.
- داده lifecycle و مجوز مستقلی دارد.
- سند از حد اندازه یا اندازهٔ عملی مناسب عبور می‌کند.
- دسترسی مستقل به عضوها پرتکرار است.

orderها را به صورت آرایهٔ بی‌انتها در سند customer نگذارید. orders collection جدا با customerId، createdAt و _id امکان query و pagination بهتر می‌دهد.

### Denormalization و consistency

کپی فیلد می‌تواند read را ساده کند اما هزینهٔ تغییر دارد. اگر عنوان محصول در سفارش snapshot است، آن را هنگام خرید کپی کنید؛ اگر قیمت جاری محصول است، منبع حقیقت products بماند. برای هر کپی این تصمیم‌ها را ثبت کنید:
- authoritative field کجاست؟
- چه وقت copy به‌روز می‌شود؟
- stale بودن تا چه مدت قابل‌قبول است؟
- backfill یا repair چگونه انجام می‌شود؟

### روند سه‌مرحله‌ای

1. Shape: queryها و documentهای پیشنهادی را با کاغذ رسم کنید.
2. Prototype: دادهٔ نماینده درج و queryها را با driver واقعی اجرا کنید.
3. Refine: index، cardinality، اندازهٔ سند و concurrency را اندازه‌گیری و schema را اصلاح کنید.

### الگوها و ضدالگوها

Subset pattern فقط بخش پرمصرف را در سند نگه می‌دارد و بقیه را جدا. Computed pattern مقدار تکراری پرهزینه را پیش‌محاسبه می‌کند. Outlier pattern داده‌های پرتعداد را از سندهای عادی جدا می‌کند. هیچ patternی بدون access pattern انتخاب نمی‌شود.

ضدالگوهای رایج: آرایهٔ بی‌انتها، سند حجیم با داده‌های بی‌ربط، تعداد بسیار زیاد collection برای هر نوع ریزداده، و normalization افراطی که هر صفحه را به چندین round trip تبدیل می‌کند.

## آموزش
از queryهای واقعی شروع کنید. داده‌ای که معمولاً با هم خوانده می‌شود، مالکیت روشنی دارد و رشدش محدود است ممکن است embed شود. دادهٔ مستقل، مشترک، چندبه‌چند یا نامحدود اغلب با reference و collection جدا قابل‌کنترل‌تر است. Denormalization کپی حساب‌شده برای read سریع است، اما به همگام‌سازی نیاز دارد.

الگوهایی مانند subset، computed و outlier مناسب شرایط مشخص‌اند. محدودیت 16 MiB و رشد آرایه را در نظر بگیرید. برای هر تصمیم، query غالب، update، حد رشد، نیاز consistency و راه migration را ثبت کنید. $lookup وجود دارد، ولی joinهای پرتکرار را نیز باید ارزیابی کرد.

## مثال
~~~javascript
{
  _id: "order-100",
  customerId: "C-4",
  shippingAddressAtPurchase: { city: "تهران" },
  lines: [{ sku: "A-1", titleAtPurchase: "ماوس", qty: 2 }]
}
~~~

## تجربهٔ واقعی یا سناریوی کاربردی
Victoria’s Secret در مطالعهٔ موردی خود از مهاجرت صدها database و replication آگاه از schema گفت. درس عملی، دسته‌بندی داده و اجرای مهاجرت مرحله‌ای است؛ ارقام مطالعه benchmark عمومی نیستند.

## خطاهای رایج
- سند بزرگ برای تمام اطلاعات کاربر.
- کپی داده بدون روش sync.
- normalize کردن همه‌چیز از روی عادت.
- embed آرایهٔ بی‌انتها.

## تمرین
1. customer/orders را برای صفحهٔ تاریخچه مدل کنید.
2. توضیح دهید چرا آدرس snapshot خرید شاید reference زنده نباشد.

## آزمون و پاسخ
1. **پرسش:** از چه چیزی شروع می‌کنیم؟
   **پاسخ:** الگوی دسترسی.
2. **پرسش:** مزیت embed چیست؟
   **پاسخ:** دادهٔ مرتبط با یک عملیات خوانده و تغییر تک‌سندی اتمیک می‌شود.
3. **پرسش:** چه زمانی reference بهتر است؟
   **پاسخ:** دادهٔ مستقل یا نامحدود.
4. **پرسش:** چرا باید از «سند بزرگ برای تمام اطلاعات کاربر.» پرهیز کرد؟
   **پاسخ:** این الگو می‌تواند سند را نامحدود بزرگ کند یا دادهٔ تکراری را ناسازگار سازد؛ رشد و sync را قبل از embedding بنویسید.
5. **مسئلهٔ کاربردی:** customer/orders را برای صفحهٔ تاریخچه مدل کنید.
   **پاسخ نمونه:** سفارش‌ها را collection جدا نگه دارید؛ اقلام و آدرس هنگام خرید را به‌صورت snapshot محدود داخل order ذخیره کنید و برای دادهٔ مستقل reference به کار ببرید.

## آزمون تکمیلی — مفاهیم و تصمیم‌گیری

6. **پرسش:** چه داده‌ای candidate مناسبی برای embedding است؟
   **پاسخ:** دادهٔ کوچک، محدود و معمولاً همراه با والد خوانده‌شده.
7. **پرسش:** چه وقت reference را ترجیح می‌دهیم؟
   **پاسخ:** دادهٔ مستقل، مشترک یا با رشد نامحدود.
8. **پرسش:** چرا order باید قیمت زمان خرید را snapshot کند؟
   **پاسخ:** قیمت جاری محصول نباید تاریخچهٔ invoice را تغییر دهد.
9. **پرسش:** denormalization چه هزینه‌ای دارد؟
   **پاسخ:** تکرار داده و نیاز به همگام‌سازی.
10. **پرسش:** چرا query را پیش از schema می‌نویسیم؟
   **پاسخ:** شکل سند و index باید نیاز دسترسی واقعی را پشتیبانی کنند.
