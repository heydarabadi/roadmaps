# ایندکس — کم‌کردن مسیر جستجو

**زبان:** فارسی · [English version](../../../../en/backend-performance/04-databases/02-indexes/README.md)


**هدف یادگیری:** از روی فیلتر و ترتیب یک query ایندکس پیشنهادی بسازید، استفاده واقعی آن را بررسی کنید و هزینه write را در تصمیم وارد کنید. **بررسی منابع: ۲۰۲۶-۱۱-۱۰**؛ SQL نمونه برای PostgreSQL است و اجرا نشده است.

## مدل ذهنی

ایندکس ساختار کمکی برای پیدا کردن ردیف‌هاست؛ همه پرس‌وجوها از آن سود نمی‌برند. اگر بیشتر جدول لازم باشد یا جدول بسیار کوچک باشد، Sequential scan ممکن است انتخاب درست باشد. در ایندکس مرکب ترتیب ستون‌ها به فیلتر، sort و قابلیت موتور بستگی دارد؛ نسخه‌ها و نوع index را یکسان فرض نکنید.

| الگوی دسترسی | گزینه بررسی | هزینه همراه |
| --- | --- | --- |
| برابری مشتری و ترتیب زمان | B-tree مرکب | write و فضای بیشتر |
| شرط روی زیرمجموعه ثابت | Partial index در موتور پشتیبان | predicate باید قابل استفاده باشد |
| داده فضایی | GiST/PostGIS مناسب عملگر | دانش نوع و operator class |
| بازگشت ستون‌های محدود | Covering index | index پهن‌تر و هزینه نگهداری |

ابتدا SQL واقعی و پارامتر نماینده را پیدا کنید؛ آمار را به‌روز کنید؛ پلن و bufferها را ببینید؛ یک تغییر انجام دهید؛ با بار مشابه read/write مقایسه کنید. [راهنمای PostgreSQL درباره بررسی استفاده ایندکس](https://www.postgresql.org/docs/current/indexes-examine.html) بر آمار و داده نماینده تأکید می‌کند.

## کاربرد و مصالحه

ایندکس برای جستجوی انتخابی یا ترتیب سازگار مفید است. برای ستون کم‌تمایز نیز ممکن است در ترکیب مناسب سودمند باشد، ولی نام ستون به‌تنهایی تصمیم را تعیین نمی‌کند. هر INSERT/UPDATE/DELETE ممکن است کار ایندکس و WAL بیشتری ایجاد کند. تابع یا cast روی ستون می‌تواند مسیر استفاده از ایندکس معمولی را تغییر دهد. حذف ایندکس «کم‌مصرف» بدون دیدن بازه کامل workload و نقش constraint خطرناک است.

## مثال حل‌شده

جدول فرضی `orders(id bigint primary key, customer_id bigint, created_at timestamp, total numeric)` را در نظر بگیرید. برای فهرست آخرین سفارش‌های یک مشتری:

<div dir="ltr" align="left">

```sql
CREATE INDEX orders_customer_time_idx
    ON orders(customer_id, created_at DESC, id DESC);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, total
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

</div>

برابری روی مشتری و ترتیب همسان، نامزد مسیر index scan با توقف زودهنگام است؛ پلن قطعی یا زمان مشخص تضمین نمی‌شود. `id` ترتیب زمان‌های مساوی را قطعی می‌کند. `EXPLAIN ANALYZE` واقعاً query را اجرا می‌کند؛ در آزمایش SELECT هم بار ایجاد می‌شود.

## تمرین کوچک و مشاهده مورد انتظار

در دیتابیس آزمایشی برای ۱۰۰ مشتری، ۱۰۰ هزار سفارش با توزیع نامتوازن بسازید. پیش و پس از index و `ANALYZE orders`، query بالا را برای مشتری کوچک و بزرگ بررسی کنید. rows، sort، buffer hit/read و زمان را یادداشت کنید؛ سپس هزینه درج یک batch یکسان را بسنجید. انتظار: index ممکن است خواندن/مرتب‌سازی را کم کند، اما write رایگان نیست و مشتری‌های متفاوت می‌توانند پلن متفاوت داشته باشند. با ۱۰ ردیف نتیجه معنادار ظرفیت نگیرید.

## شاهد عمومی و حد شواهد

[مستند رسمی PostgreSQL](https://www.postgresql.org/docs/current/indexes-examine.html) توضیح می‌دهد چرا داده کوچک و توزیع غیرواقعی نتیجه آزمایش را منحرف می‌کند؛ شاهد اصلی این درس عملیاتی است. [نوشته فارسی آرتا سنجش نگار درباره PostGIS](https://asnegar.ir/blog/postgis-optimization/) نیز نمونه عمومی تغییر پلن فضایی گزارش می‌کند؛ عددهای آن مستقل بازتولید نشده و رفتار GiST را نباید به B-tree تعمیم داد. ادعای «بدون قفل» برای ساخت concurrent را مطلق نخوانید؛ محدودیت و مراحل آن را از مستند موتور بررسی کنید.

## شکست‌ها، سیگنال‌ها و چک‌لیست

write latency، WAL و اندازه index را کنار read latency ببینید. اختلاف estimated/actual rows می‌تواند از آمار یا توزیع داده باشد. ایندکس نامناسب ممکن است هیچ query مهمی را بهتر نکند و همچنان write را گران کند.

- [ ] فیلتر، sort، selectivity و پارامترهای نماینده مشخص‌اند.
- [ ] آمار تازه و Query plan پیش/پس نگهداری شده است.
- [ ] ترتیب ستون‌ها با مسیر دسترسی سنجیده شده است.
- [ ] هزینه write، فضا، WAL و زمان ساخت اندازه‌گیری می‌شود.
- [ ] ساخت و حذف، constraint و قفل‌های migration را در نظر می‌گیرد.
- [ ] index usage در بازه کاری کامل بررسی می‌شود.

## پیش‌نیازها، روند انتخاب و خواندن نتیجه

انتخاب‌پذیری سهم ردیف‌هایی است که یک شرط نگه می‌دارد؛ پلن مسیر اجرایی انتخاب‌شده توسط موتور است؛ ایندکس ساختار کمکی است که شاید یافتن محدوده ردیف یا ترتیب را ارزان کند. ابتدا query، فیلتر، ترتیب و تعداد خروجی را بنویسید. سپس نامزد index را بررسی کنید، آمار را تازه کنید، پلن و هزینه write را در بار نماینده بسنجید. ترتیب ستون‌ها وابسته به workload است و این قاعده مستند موتور را جایگزین نمی‌کند.

### حل گام‌به‌گام سفارش‌ها و تمرین

برابری customer_id محدوده یک مشتری را مشخص می‌کند؛ created_at و id با ترتیب DESC می‌توانند نتیجه مرتب را بخوانند و پس از ۲۰ ردیف متوقف شوند. id زمان‌های برابر را مرتب می‌کند. اگر آن مشتری سهم بزرگی از جدول داشته باشد یا جدول کوچک باشد، scan دیگری همچنان ارزان‌تر است. پس گزاره درست «این index نامزد است»، نه «حتماً index scan می‌شود». پاسخ تمرین باید rows، sort، buffers و زمان هر دو query را ثبت کند و درج یک batch یکسان را نیز بسنجد. مشتری کوچک ممکن است سود ببرد؛ مشتری پرحجم شاید پلن دیگری بگیرد. زمان قطعی را از داده فرضی نتیجه نمی‌گیریم.

### مسیر عیب‌یابی

query کند و پارامتر نماینده را بگیرید؛ پلن و آمار را بررسی کنید؛ اختلاف estimate/actual را به آمار، skew یا وابستگی ستون‌ها پیگیری کنید؛ buffers و sort را برای I/O ببینید؛ یک تغییر index بدهید و همان بار read/write را تکرار کنید. اگر read بهتر ولی write latency یا WAL بیشتر شد، تصمیم با هدف workload سنجیده می‌شود. index کم‌مصرف را پیش از حذف از نظر constraint، queryهای کم‌تکرار اما مهم و بازه کاری کامل بررسی کنید.

## جمع‌بندی

ایندکس شاید مسیر خواندن را کوتاه کند اما فضای پایدار و کار نوشتن می‌افزاید. query و داده واقعی نشان می‌دهند که نامزد index از scan ارزان‌تر است یا نه.

## خودآزمایی

۱. آیا Seq Scan همیشه نشانه مشکل است؟

۲. چرا `id` به ترتیب زمان افزوده شد؟

۳. ایندکس روی همه ستون‌ها چه هزینه‌ای دارد؟

۴. اگر estimated rows با actual فرق زیادی داشت، چه چیزی را بررسی می‌کنید؟

۵. آیا سریع‌شدن SELECT برای تأیید index کافی است؟

### پاسخ‌نامه با دلیل

۱. خیر؛ برای جدول کوچک یا سهم بزرگ ردیف‌ها می‌تواند ارزان‌ترین مسیر باشد.

۲. برای شکستن تساوی timestamp و ساخت ترتیب قطعی؛ صفحه‌بندی به این ویژگی نیاز دارد.

۳. فضا، حافظه، WAL و تغییر ایندکس در write؛ اضافه‌کردن بی‌هدف هزینه دائمی دارد.

۴. تازگی آمار، هم‌بستگی ستون‌ها، skew و پارامتر واقعی؛ تخمین غلط روی انتخاب پلن اثر می‌گذارد.

۵. خیر؛ latency نوشتن، throughput، فضای مصرفی و قفل ساخت نیز جزو نتیجه‌اند.
