## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

مصرف‌کننده نباید به متدهایی وابسته باشد که استفاده نمی‌کند؛ رابط‌های متمرکز روی نقش client تغییر را محدود می‌کنند.

## مثال کاربردی

به‌جای یک درگاه بزرگ شامل refund، capture و payout برای همه، قابلیت‌های پرداخت واقعاً لازم را جدا کن.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «اصول طراحی» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** تعداد interfaceهای خرد می‌تواند خوانایی را پایین بیاورد.
- **بازبینی:** فقط به دلیل اندازهٔ فایل رابط را خرد نکن؛ وابستگی و نیاز مصرف‌کننده را ببین.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: مصرف‌کننده نباید به متدهایی وابسته باشد که استفاده نمی‌کند؛ رابط‌های متمرکز روی نقش client تغییر را محدود می‌کنند.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: به‌جای یک درگاه بزرگ شامل refund، capture و payout برای همه، قابلیت‌های پرداخت واقعاً لازم را جدا کن.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: تعداد interfaceهای خرد می‌تواند خوانایی را پایین بیاورد.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: فقط به دلیل اندازهٔ فایل رابط را خرد نکن؛ وابستگی و نیاز مصرف‌کننده را ببین.

## آموزش تکمیلی مستقل

#### I — Interface Segregation

مصرف‌کننده نباید به عملیاتی وابسته باشد که به آن نیاز ندارد. interface بزرگ با متدهای unrelated را بر اساس capability مصرف‌کننده تقسیم کن. اما ساختن interfaceهای یک‌متدی بی‌شمار هم شناخت معماری را دشوار می‌کند؛ ابتدا نقش واقعی callerها را ببین.

## نمونهٔ کد مرحله‌ای

مصرف‌کننده نباید به عملیات نامرتبط وابسته شود. interface را بر اساس نقش caller تقسیم کن، اما از ساختن interface تک‌متدی بی‌دلیل پرهیز کن. معیار، وابستگی واقعی مصرف‌کننده و تغییر مستقل قابلیت‌هاست.
**تمرین با پاسخ:** دستگاه ساده فقط چاپ می‌کند؛ آن را مجبور به پیاده‌سازی Scan نکن. قرارداد چاپگر و اسکنر جدا باشد.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا انتخاب طراحی روشن بماند.

~~~csharp
public interface IPrinter
{
    Task Print(Document document, CancellationToken ct);
}

public interface IScanner
{
    Task<Scan> Scan(CancellationToken ct);
}

public sealed class BasicPrinter : IPrinter { /* print only */ }
~~~
