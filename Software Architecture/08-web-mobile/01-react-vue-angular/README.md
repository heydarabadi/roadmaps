# React، Vue و Angular در معماری محصول

React، Vue و Angular ابزار ساخت رابط کاربری‌اند؛ خودشان مرز backend، قرارداد API یا معماری کل محصول را تعیین نمی‌کنند. انتخاب را با مهارت تیم، اندازه و چرخهٔ عمر UI، دسترس‌پذیری، ecosystem، شیوهٔ rendering، نیاز آزمون و هزینهٔ upgrade انجام بده.

React کتابخانه‌ای انعطاف‌پذیر است و برای معماری برنامه به frameworkها یا تصمیم‌های تیم نیاز دارد. Vue رویکرد تدریجی و راهنمای رسمی برای SPA و SSR دارد. Angular چارچوب کامل‌تر با ابزارهای routing، dependency injection و گزینه‌های rendering عرضه می‌کند. این تفاوت‌ها به‌تنهایی رتبه‌بندی کیفیت نیستند.

## تصمیم نمونه

برای داشبورد داخلی با تیم React باتجربه، استفاده از ابزار موجود شاید بیشترین بازده را بدهد. برای محصول عمومی با SEO و زمان نمایش اولیه مهم، SSR/SSG را با caching و نیاز داده بررسی کن. برای سامانهٔ سازمانی بزرگ، قراردادهای component، تست، routing و upgrade plan وزن بیشتری پیدا می‌کنند.

## دام‌ها

- انتخاب framework بر مبنای محبوبیت لحظه‌ای.
- قراردادن منطق امنیتی در client.
- استفاده از state سراسری برای هر داده.
- نادیده‌گرفتن accessibility و bundle size.
- ساخت design system داخلی بدون مالک و معیار استفاده.

## چارچوب تصمیم‌گیری مرحله‌ای

۱. **مخاطب و سطح تعامل:** سایت محتوامحور عمومی، پنل داخلی و ابزار تعاملی نیاز یکسان ندارند.
۲. **توان تیم:** تجربهٔ موجود، قابلیت استخدام، سرعت یادگیری و توان ارتقا را بسنج.
۳. **نوع rendering:** نیاز SEO و زمان نمایش اولیه را به SSR/SSG و caching پیوند بده.
۴. **ساختار محصول:** routing، فرم، state، دسترس‌پذیری، internationalization و test runner را بررسی کن.
۵. **اکوسیستم و عمر:** cadence نسخه، مهاجرت breaking change، پشتیبانی browser و وابستگی‌های بحرانی را مرور کن.
۶. **معیار خروج:** پیش از انتخاب، prototype کوتاه برای مسیر پرریسک بساز و bundle، accessibility، maintainability و زمان توسعه را بسنج.

## مدل‌کردن state رابط کاربری

state محلیِ یک component را تا جای ممکن محلی نگه دار؛ state مشترک را در نزدیک‌ترین مالک مشترک قرار بده؛ state سرور را مثل cache دادهٔ بیرونی با loading، stale، error و invalidation مدیریت کن. کپی‌کردن هر پاسخ API در global state اغلب منبع حقیقت‌های تکراری می‌سازد. برای فرم سفارش، دادهٔ ویرایش‌نشده، نتیجهٔ validation و وضعیت submit سه مفهوم جدا هستند.

## مرز امنیتی و تجربه

Framework دسترسی داده را enforce نمی‌کند. قیمت، موجودی و مجوز سمت server تعیین می‌شوند. UI باید صفحه‌کلید، focus، label، contrast، پیام خطای قابل‌فهم و semantics صحیح را از ابتدا رعایت کند. برای route حساس، loading و error state، دسترسی مستقیم با URL، refresh و session expiry را هم طراحی کن.

## ارتقا و نگهداری

نسخهٔ پشتیبانی‌شده، cadence ارتقا، راهبرد dependency lock، آزمون پس از upgrade و owner را ثبت کن. Design system وقتی ارزش دارد که چند تیم آن را مصرف و نگهداری کنند؛ بدون owner به انبار componentهای ناسازگار تبدیل می‌شود.

## آزمون

۱. انتخاب UI framework معماری backend را تعیین می‌کند؟ **پاسخ:** نه؛ اما قرارداد API، cache و rendering را تحت تأثیر می‌گذارد.
۲. چرا تجربهٔ تیم معیار معماری است؟ **پاسخ:** کیفیت، سرعت رفع اشکال و هزینهٔ پشتیبانی را تغییر می‌دهد.
۳. چه چیزی را در upgrade policy ثبت می‌کنی؟ **پاسخ:** cadence، نسخه‌های پشتیبانی‌شده، آزمون سازگاری و مسئول نگهداری.
۴. چرا دسترسی‌پذیری را دیر اضافه نمی‌کنیم؟ **پاسخ:** اجزای پایه و تعامل‌ها از ابتدا بر تجربه و انطباق اثر دارند.

## تمرین

برای یک فروشگاه و یک پنل داخلی، stackهای متفاوت یا مشترک پیشنهاد بده و trade-off تیمی، SSR و نگهداری را مستند کن.

## پاسخ نمونهٔ تمرین

فروشگاه عمومی را می‌توان با frameworkی که تیم توان نگهداری‌اش را دارد SSR/SSG کرد؛ پنل داخلی ممکن است همان stack و SPA باشد. مشترک‌بودن زبان/کامپوننت هزینهٔ آموزش را کم می‌کند؛ جداسازی framework در صورت UX یا team boundary واقعی. هر انتخاب با bundle, accessibility, routing, SSR, security و cadence ارتقا سنجیده می‌شود.
