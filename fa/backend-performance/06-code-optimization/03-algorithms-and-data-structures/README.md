# ۶.۳ — الگوریتم‌ها و ساختمان داده‌ها

**زبان:** فارسی · [English version](../../../../en/backend-performance/06-code-optimization/03-algorithms-and-data-structures/README.md)


الگوریتم تعیین می‌کند چه کاری و چند بار انجام شود؛ ساختمان داده هزینهٔ دسترسی، تغییر و نگه‌داری را شکل می‌دهد. بهینه‌سازی این لایه غالباً حذف کار تکراری است، اما باید ابتدا [Profile](../02-application-profiling/README.md) نشان دهد این کار در بار هدف سهم معنادار دارد.

**هدف یادگیری:** تشخیص رشد هزینه با اندازهٔ ورودی، انتخاب میان اسکن/Hash/ترتیب، محاسبهٔ هزینهٔ ساخت و حافظه و تشخیص مرز ادعای Big-O. پیش‌نیاز: حلقه و مجموعه. بررسی منابع: **۲۰۲۶-۱۱-۱۰**.

## پیش‌نیازهای همین درس

مجموعه (Collection) چند عضو را نگه می‌دارد. در این صفحه n تعداد سفارش‌ها و m تعداد مشتری‌هاست؛ lookup یعنی پیدا کردن عضو با کلید. Big-O نرخ رشد تعداد عملیات را با بزرگ‌شدن ورودی توصیف می‌کند و میلی‌ثانیه یا هزینهٔ دقیق CPU نیست. بدترین حالت، بیشترین کار در ورودی مجاز را می‌سنجد؛ در Map نیز Hash محاسبهٔ کد کلید برای یافتن خانهٔ محتمل است و برخورد دو کلید می‌تواند کار اضافه بسازد. Heap ساختار اولویت‌دار برای دسترسی سریع به عضو کمینه/بیشینه است؛ Deque صفی است که افزودن و برداشتن از هر دو سر را می‌پذیرد. این تعریف‌ها کمک می‌کنند پیچیدگی انتخاب داده‌ساختار را با الگوی عملیات تطبیق دهید.

## مدل ذهنی: رشد، ثابت و حافظه

`O(n)` نرخ رشد را در مدل مشخص بیان می‌کند، نه زمان برحسب میلی‌ثانیه. Cache locality، اندازهٔ کلید، تخصیص حافظه، قفل و پیاده‌سازی ضریب واقعی را تغییر می‌دهند. مقایسهٔ الگوریتم‌ها باید semantics یکسان داشته باشد: حفظ ترتیب، رفتار با کلید تکراری و برابری متن فارسی/Unicode را روشن کنید.

| نیاز | گزینهٔ ساده | گزینهٔ جایگزین | هزینهٔ جایگزین |
| --- | --- | --- | --- |
| یک lookup در فهرست کوچک | اسکن خطی | Hash map | ساخت و حافظه شاید سود را ببلعد |
| lookupهای مکرر با کلید | اسکن برای هر درخواست | Map/Set | رشد حافظه، برخورد و نگه‌داری تغییرات |
| کمترین k مقدار از n | مرتب‌سازی کل | Heap محدود k | پیاده‌سازی و حفظ ترتیب نهایی |
| پیمایش مرتب یا بازه | فهرست مرتب/درخت | Hash map | Hash ترتیب یا range را مستقیم نمی‌دهد |
| حذف اولین عنصر صف | جابه‌جایی آرایه در هر حذف | Deque/Ring buffer | ظرفیت و سیاست پر شدن |

برای Hash، دسترسی میانگین یا مورد انتظار ممکن است نزدیک ثابت باشد؛ بدترین حالت، برخورد، تغییر اندازه و هزینهٔ Hash کلید همچنان اهمیت دارند. برای Top-k با Heap محدود، نگه‌داری معمولاً `O(n log k)` و حافظهٔ کمکی `O(k)` است؛ اگر ترتیب نهایی لازم باشد، مرتب‌سازی k عضو نیز اضافه می‌شود.

## مثال حل‌شده: اتصال داده در حافظه

**فرض آموزشی:** ۱۰٬۰۰۰ سفارش و ۵٬۰۰۰ مشتری در حافظه داریم. برای هر سفارش باید نام مشتری را پیدا کنیم؛ کلید یکتا و رفتار مشتری گمشده مشخص است.

<div dir="ltr" align="left">

```text
# Before: repeated scan
for order in orders:
    order.customer_name = find_by_id(customers, order.customer_id)

# After: build once, then lookup
by_id = map(customers, key = customer.id)
for order in orders:
    customer = by_id.get(order.customer_id)
    order.customer_name = customer.name if found else "unknown"
```

</div>

اسکن تکراری در بدترین حالت حدود ۵۰ میلیون مقایسه دارد: `n*m`. ساخت Map و lookupها در مدل Hash مناسب، تعداد عملیاتی متناسب با `n+m = 15000` دارند؛ این نسبت **نسبت زمان واقعی نیست**. حافظهٔ Map، هزینهٔ Hash و ساخت اولیه هم وجود دارد. اگر فقط یک سفارش و پنج مشتری داریم، روش ساده ممکن است کافی یا سریع‌تر باشد.

Map را برای هر سفارش دوباره نسازید؛ آن‌گاه هزینهٔ ساخت تکرار می‌شود. اگر مشتری‌ها در DB هستند، ابتدا واکشی دسته‌ای/Join و [راهبرد ORM](../../04-databases/03-orm-fetch-strategies/README.md) را بررسی کنید؛ ساخت Map پس از هزاران درخواست شبکه مشکل رفت‌وبرگشت قبلی را از بین نمی‌برد. Map سراسری نیز باید قرارداد تازگی و هم‌زمانی داشته باشد.

## تمرین و نتیجهٔ مورد انتظار

برای <span dir="ltr">n = 100, 1000, 10000</span> و <span dir="ltr">m = n/2</span>، تعداد مقایسهٔ بدترین حالت روش اسکن را حساب کنید. برای Map، هزینهٔ ساخت را جدا از lookup بنویسید. سپس یک بار با lookup واحد و یک بار با همهٔ سفارش‌ها مقایسه کنید. **راه‌حل:** برای یک lookup، سقف اسکن به‌ترتیب <span dir="ltr">50, 500, 5000</span> مقایسه است؛ برای همهٔ سفارش‌ها، <span dir="ltr">n × m</span> به‌ترتیب <span dir="ltr">5,000, 500,000, 50,000,000</span> می‌شود. در مدل Hash مورد انتظار، ساخت حدود <span dir="ltr">m</span> و lookupها حدود <span dir="ltr">n</span> عملیات‌اند؛ برای همه، مجموع‌های تقریبی <span dir="ltr">150, 1,500, 15,000</span> است، اما این‌ها میلی‌ثانیه و ضمانت بدترین حالت نیستند. پس با ده برابر شدن هر دو مجموعه، اسکن صد برابر و مدل ساخت+lookup حدود ده برابر می‌شود. اگر فقط یک جست‌وجو دارید، ساخت Map ممکن است سود را ببلعد. اگر پیاده‌سازی می‌کنید، خروجی دو روش، حافظه، ورودی‌های تکراری و زمان ساخت را هم بررسی کنید؛ شمارش عملیات جای اندازه‌گیری Runtime را نمی‌گیرد.

## شاهد واقعی و شکاف شواهد

**سند ابزار عملیاتی:** [Redis Sorted Sets](https://redis.io/docs/latest/develop/data-types/sorted-sets/) کاربرد مجموعهٔ دارای امتیاز برای leaderboard و پیچیدگی عملیات را مستند می‌کند. این شاهدی است که نیاز به رتبه/بازه با انتخاب داده‌ساختار مرتبط است، نه تضمین زمان ثابت همهٔ دستورات. برای نمونهٔ مشخص «اسکن مشتری به Map» این درس، مطالعهٔ تولیدی عمومی قابل‌مقایسه پیدا نشد؛ کاهش عملیات بالا استدلال آموزشی است و ادعای نتیجهٔ یک شرکت نیست.

## تناسب، شکست‌ها و علائم

پیش از پیچیده کردن الگوریتم، اندازهٔ واقعی و توزیع ورودی را ثبت کنید. بهبود Big-O وقتی ورودی رشد می‌کند ارزشمند است، اما ساختار پیچیده برای مجموعهٔ همیشه کوچک هزینهٔ خوانایی دارد. Hash ورودی کنترل‌شده و ورودی مهاجم یک فرض امنیتی یکسان ندارند؛ از پیاده‌سازی استاندارد و محدودیت ورودی استفاده کنید.

| شکست | نشانه | بازبینی |
| --- | --- | --- |
| ساخت ایندکس در حلقهٔ بیرونی | Allocation زیاد و CPU ثابت | چرخهٔ عمر ساختار را اصلاح کن |
| از دست دادن ترتیب یا duplicate | خروجی سریع ولی غلط | قرارداد برابر بودن و ترتیب را حفظ کن |
| Map نامحدود سراسری | حافظه با کلیدهای جدید رشد می‌کند | عمر، ظرفیت و حذف را تعریف کن |
| فقط اندازه‌گیری ورودی کوچک | شکست در دادهٔ بزرگ | طیف اندازه و skew را اضافه کن |
| بهبود کد خارج از hot path | latency تقریباً ثابت | سهم مسیر در Profile/Trace را بررسی کن |

### چک‌لیست عملیاتی

- [ ] اندازهٔ p50 و بدترین ورودی مجاز، تعداد lookup و skew معلوم‌اند.
- [ ] هزینهٔ ساخت، تغییر، lookup و آزادسازی جدا حساب شده است.
- [ ] ترتیب، duplicate، missing key و Unicode semantics حفظ می‌شوند.
- [ ] حافظه، تخصیص، Resize و هم‌زمانی بررسی شده‌اند.
- [ ] ورودی بزرگ/خصمانه و سقف منابع در نظر گرفته شده است.
- [ ] کاهش هزینه با خروجی درست و بار نماینده تأیید می‌شود.

## آزمون

1. چرا `O(1)` برای Hash به معنای یک نانوثانیه نیست؟
2. در مثال، با ده برابر شدن n و m، اسکن در بدترین حالت چند برابر می‌شود؟
3. چرا Map برای یک lookup روی پنج عضو الزاماً بهتر نیست؟
4. Top-k چه زمانی می‌تواند از مرتب‌سازی همهٔ داده کم‌هزینه‌تر باشد؟
5. اگر ترتیب قبلی حذف شود، آیا کاهش زمان موفقیت است؟
6. چرا Map بعد از N درخواست جدا به DB، مشکل N رفت‌وبرگشت را حل نمی‌کند؟

### پاسخ تشریحی

1. Big-O رشد را بیان می‌کند؛ Hash کلید، برخورد، حافظه و ثابت‌های پیاده‌سازی هزینه دارند و بدترین حالت جداست.
2. صد برابر؛ ضرب دو اندازه هرکدام ده برابر می‌شود.
3. ساخت Map و تخصیص ممکن است از یک اسکن کوتاه گران‌تر باشد؛ تعداد استفاده اهمیت دارد.
4. وقتی k بسیار کوچک‌تر از n است و فقط همان اعضا لازم‌اند؛ هزینهٔ Heap و ترتیب نهایی را نیز باید حساب کرد.
5. خیر، اگر ترتیب جزو قرارداد است خروجی نادرست شده است؛ صحت شرط مقایسه است.
6. آن درخواست‌ها پیش‌تر انجام شده‌اند؛ باید برنامهٔ واکشی را عوض کرد، سپس اتصال در حافظه را بهینه کرد.

## جمع‌بندی

ساختمان داده را از روی عملیات غالب و اندازهٔ واقعی انتخاب کنید؛ هزینهٔ ساخت و عمر حافظه را هم در حساب بیاورید. حفظ ترتیب، duplicateها، کلید مفقود و قرارداد Unicode شرط صحت است. اگر داده در DB است، ابتدا تعداد رفت‌وبرگشت و طرح واکشی را اصلاح کنید؛ Map محلی آن‌ها را حذف نمی‌کند.
