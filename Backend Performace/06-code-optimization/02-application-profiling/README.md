# ۶.۲ — پروفایلینگ برنامه (Application Profiling)

**زبان:** فارسی · [English version](README.en.md)


Profile تصویری از مصرف منابع داخل برنامه در یک بازه و بار مشخص است. با آن فرضیهٔ «احتمالاً این تابع کند است» را به شواهد تبدیل می‌کنیم. **ابتدا اندازه‌گیری، سپس انتخاب تغییر**؛ بازنویسی کد بدون شناخت محدودیت ممکن است فقط بخش ارزان را سریع‌تر کند.

**هدف یادگیری:** انتخاب Profile مناسب، تفکیک CPU از انتظار، تفسیر Self/Total و Flame graph، و مقایسهٔ قبل/بعد با شرایط همسان. پیش‌نیاز: تابع، فراخوانی، CPU و I/O. بررسی منابع: **۲۰۲۶-۱۱-۱۰**.

## پیش‌نیازهای همین درس

تابع مجموعه‌ای از دستورهاست و Stack زنجیرهٔ تابعی است که برای رسیدن به یک کار فراخوانی شده‌اند. CPU-time مقدار زمانی است که پردازنده واقعاً برای فرایند مصرف کرده؛ زمان دیواری از شروع تا پایان، انتظار شبکه و صف را هم دربر می‌گیرد. Profile نمونه‌ها یا رویدادهای مصرف منابع را در یک بازه جمع می‌کند؛ نمونه‌برداری تخمین آماری است، نه ثبت دقیق هر دستور.

## مدل ذهنی: چهار پرسش متفاوت

| ابزار | پرسش | چیزی که به‌تنهایی ثابت نمی‌کند |
| --- | --- | --- |
| CPU profile | نمونه‌های زمان پردازنده در کدام Stack هستند؟ | زمان کامل انتظار شبکه و صف |
| Allocation/Heap profile | کجا حافظه ساخته یا نگه داشته می‌شود؟ | هر Allocation نشتی است |
| Lock/Block/Wait profile | کار کجا منتظر منبع یا هماهنگی است؟ | علت نهایی مشکل بدون زمینه |
| Trace درخواست | کدام وابستگی و ترتیب، پاسخ را عقب انداخته؟ | جزئیات همهٔ توابع داخلی |

راهنمای رسمی [Go Diagnostics](https://go.dev/doc/diagnostics) انتخاب میان Profile، Trace و آمار Runtime را توضیح می‌دهد. نام ابزار و معنای Profile در Runtimeها متفاوت است؛ حتی Heap ممکن است «زنده در لحظه» یا «تخصیص تجمعی» را نشان دهد. برچسب نمودار را بخوانید.

در پروفایل نمونه‌بردار، تعداد زیاد نمونه نشانهٔ سهم بیشتر آن Stack در کمیت اندازه‌گیری‌شده است؛ تخمین آماری است. `Self` سهم خود تابع و `Total/Cumulative` سهم تابع همراه فرزندان است. جمع Total همهٔ ردیف‌ها دوباره‌شماری می‌کند. در Flame graph معمول، عرض سهم نمونه‌هاست؛ محور افقی معمولاً خط زمان نیست. تنظیم دقیق ابزار را بررسی کنید.

## روش کار

1. مسئله را محدود کنید: Route، ورودی، نسخه، شدت بار و معیار مشکل. زمان دیواری پاسخ را با CPU فرایند یکی نگیرید.
2. یک پنجرهٔ نماینده شامل شرایط کند ثبت کنید؛ build مناسب، Symbol و نسخهٔ Runtime را نگه دارید. warmup/JIT و cache سرد یا گرم را مستند کنید.
3. با هزینهٔ کم شروع کنید، سپس CPU، حافظه یا انتظار را طبق علامت انتخاب کنید. سربار ابزار را نسبت به خط مبنا بسنجید.
4. داده را با Trace و Metric تطبیق دهید. CPU پایین و صف بلند می‌تواند انتظار I/O یا Pool را نشان دهد.
5. یک علت قابل‌آزمایش انتخاب کنید؛ بعد از تغییر همان بار و همان تعریف خروجی موفق را مقایسه کنید.

## مثال حل‌شده

دادهٔ زیر **فرضی** است؛ سه مرحلهٔ سریال برای یک درخواست بدون هم‌پوشانی داریم:

| مرحله | زمان دیواری | CPU مصرف‌شده |
| --- | ---: | ---: |
| انتظار Pool و DB | ۱۶۰ ms | ۲ ms |
| ساخت و Encode پاسخ | ۳۰ ms | ۳۰ ms |
| ارسال و انتظار مصرف‌کننده | ۱۰ ms | ۱ ms |

CPU profile احتمالاً Encode را برجسته می‌کند، چون از مجموع ۳۳ ms CPU، ۳۰ ms آنجاست؛ اما پاسخ ۲۰۰ ms طول می‌کشد. نصف کردن Encode در این مدل ۱۵ ms صرفه‌جویی و پاسخ ۱۸۵ ms ایجاد می‌کند. برای هدف ۱۰۰ ms، باید بخش ۱۶۰ ms را با Trace، صف Pool و ابزار DB بررسی کرد. کاهش CPU همچنان ممکن است هزینه و ظرفیت را بهتر کند، ولی پاسخ هدف را به‌تنهایی برآورده نمی‌کند.

در Heap فرضی، اگر در هر درخواست ۲ MiB تخصیص و پس از جمع‌آوری فقط ۳۰ KiB باقی بماند، تخصیص بالا داریم؛ برای ادعای نشتی باید نگه‌داری و رشد حافظهٔ زنده در بازهٔ طولانی بررسی شود.

## تمرین و مشاهدهٔ مورد انتظار

یک Handler کوچک در زبان دلخواه را به دو بخش تقسیم کنید: محاسبهٔ تکراری و انتظار ساختگی I/O. بدون تغییر خروجی، یک بار انتظار را زیاد و بار دیگر محاسبه را زیاد کنید. اگر ابزار ندارید، جدول زمان‌ها و سهم CPU را مانند مثال بسازید. **راه‌حل و انتظار:** اگر ۱۰ ms محاسبه را ثابت نگه دارید و انتظار را از ۲۰ به ۱۰۰ ms برسانید، زمان دیواری ۸۰ ms زیاد می‌شود اما CPU-time تقریباً همان ۱۰ ms می‌ماند؛ CPU profile نباید این انتظار شبکه را به تابع محاسبه نسبت دهد. اگر محاسبه را از ۱۰ به ۲۰ ms برسانید و انتظار ۲۰ ms بماند، زمان دیواری و CPU-time هر دو حدود ۱۰ ms افزایش می‌یابند. چند ثبت کوتاه را مقایسه کنید؛ درصدهای نزدیک ممکن است به‌علت نمونه‌برداری نوسان کنند. این تمرین باید محلی باشد؛ Endpoint پروفایل تولید را عمومی نکنید.

## شاهد واقعی

در گزارش **۹ ژوئن ۲۰۲۶** [Discord Voice at the Edge](https://discord.com/blog/how-we-moved-discord-voice-to-the-edge)، تیم ابتدا با Probe محدودهٔ تأخیر را به داخل VM محدود کرد و سپس با نمونه‌برداری CPU هر Thread و Flame graph به starvation در حلقهٔ دریافت رسید. اصلاح اول تمام spikeها را حل نکرد؛ بررسی بعدی contention زیرساخت را آشکار کرد. این تجربه نشان می‌دهد Profile باید با شواهد دیگر ترکیب شود؛ انتخاب Rust مانع starvation نشده بود.

## هزینه‌ها، خطاها و عملیات

Profiler می‌تواند زمان‌بندی، مصرف CPU یا توقف‌ها را تغییر دهد؛ Heap snapshot در بعضی Runtimeها سنگین است. ثبت محدود و کنترل دسترسی لازم است، چون نام تابع، مسیر و گاهی دادهٔ حافظه حساس‌اند. پروفایل روی ورودی کوچک و بدون رقابت، رفتار قفل زیر بار را نشان نمی‌دهد. درصد CPU به‌تنهایی با تغییر تعداد هسته یا سهم container قابل‌مقایسه نیست؛ CPU-time به ازای کار موفق را هم ثبت کنید.

| اشتباه | علامت | اصلاح |
| --- | --- | --- |
| نتیجه‌گیری از Profile بدون درخواست کند | گلوگاه پیدا نمی‌شود | پنجرهٔ نماینده و هم‌بستگی با latency |
| جمع کردن Cumulative توابع | سهم‌ها بیش از کل می‌شوند | Self و رابطهٔ والد/فرزند را تفکیک کن |
| نامیدن Allocation به‌عنوان Leak | Heap زنده ثابت ولی حجم تخصیص بالاست | روند retention و GC را جدا بخوان |
| مقایسهٔ build یا بار متفاوت | بهبود با خطا/افت خروجی همراه است | شرایط و معیار موفقیت را ثابت کن |

### چک‌لیست عملیاتی

- [ ] نسخهٔ کد/Runtime، سخت‌افزار، محدودیت CPU و الگوی بار ثبت شده‌اند.
- [ ] Metric، Trace و Profile هر کدام پرسش مشخصی را پاسخ می‌دهند.
- [ ] سربار، مدت و نرخ نمونه‌برداری معلوم است.
- [ ] Symbolها و معنای Self/Total و نوع Heap بررسی شده‌اند.
- [ ] خطا، throughput موفق و p99 در کنار مصرف منابع مقایسه می‌شوند.
- [ ] Profile و Endpoint تشخیصی دسترسی محدود و عمر نگه‌داری مشخص دارند.

## آزمون

1. چرا داغ‌ترین تابع CPU الزاماً بزرگ‌ترین عامل latency نیست؟
2. Total یک تابع شامل چه چیزی است و چرا جمع Totalها گمراه‌کننده است؟
3. آیا Heap ثابت همراه تخصیص زیاد اثبات نشتی است؟
4. عرض یک Frame در Flame graph معمول چه معنایی دارد؟
5. برای درخواست کند با CPU پایین، چه داده‌ای را اضافه می‌کنید؟
6. اگر نسخهٔ جدید CPU کمتری دارد ولی نصف درخواست‌ها را رد می‌کند، نتیجه چیست؟

### پاسخ تشریحی

1. CPU زمان انتظار DB، شبکه یا صف را کامل نمی‌بیند؛ latency به مسیر کامل وابسته است.
2. خود تابع و فرزندان؛ فرزندان در چند والد دوباره ظاهر می‌شوند و جمع کل دوباره‌شماری می‌شود.
3. خیر؛ اشیای موقت ممکن است آزاد شوند. رشد حافظهٔ زنده و نگه‌دارنده‌ها باید بررسی شود.
4. سهم نمونه‌ها در معیار انتخاب‌شده؛ ترتیب افقی معمولاً زمان وقوع نیست.
5. Trace، مدت انتظار Pool، I/O، قفل و صف؛ علت خارج از CPU محتمل است ولی باید سنجیده شود.
6. بهبود ثابت نشده؛ کار موفق کمتر شده است. هزینهٔ هر موفقیت و نرخ خطا باید برابر یا قابل‌قبول باشند.

## جمع‌بندی

CPU profile محل مصرف پردازنده را نشان می‌دهد، نه تمام زمان انتظار درخواست. Heap/Allocation و Wait Profile پرسش‌های جدا دارند؛ آن‌ها را با Trace و Metrics به Route و بازهٔ مشکل‌دار وصل کنید، سپس فقط یک علت را تغییر دهید و همان بار، خروجی موفق و شرایط اجرا را دوباره بسنجید.

## منابع تکمیلی اختیاری

برای فهم این درس یا حل تمرین، بازکردن پیوندهای زیر لازم نیست؛ آن‌ها برای مطالعهٔ بیشتر و بررسی رفتار مستند ابزارها هستند.

- [فارسی: مستندات Python برای sampling profiler](https://docs.python.org/fa/3/library/profiling.sampling.html): توضیح فارسی نمونه‌برداری آماری؛ API این صفحه از Python 3.15 است، برای نسخهٔ قدیمی آن را فرض نکنید.
- [English: Go Diagnostics](https://go.dev/doc/diagnostics): انتخاب `pprof` و ابزارهای CPU، Heap و Trace در Go.
- [English: .NET profiling tools](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/profilers): پروفایل CPU، حافظه و Stack با ابزارهای .NET؛ جزئیات ابزار به نسخه و سیستم‌عامل بستگی دارد.
- [English: Java Flight Recorder performance troubleshooting](https://docs.oracle.com/en/java/javase/26/troubleshoot/troubleshoot-performance-issues-using-jfr.html): تفکیک CPU از I/O، انتظار قفل و GC از روی رویدادها؛ رخداد و سربار به تنظیم ضبط و نسخهٔ JVM وابسته است.
- [English: Profiling Node.js Applications](https://nodejs.org/en/learn/getting-started/profiling): مثال رسمی تشخیص مصرف CPU در Node؛ API و ابزار به نسخه وابسته‌اند.
- [English: Discord Voice](https://discord.com/blog/how-we-moved-discord-voice-to-the-edge): نمونهٔ گزارش‌شدهٔ ترکیب Probe، Flame graph و بررسی زیرساخت.
