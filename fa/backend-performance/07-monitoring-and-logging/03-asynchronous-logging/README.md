# ۷.۳ — لاگ‌گیری غیرهمگام | Asynchronous Logging

**زبان:** فارسی · [English version](../../../../en/backend-performance/07-monitoring-and-logging/03-asynchronous-logging/README.md)


لاگ‌گیری غیرهمگام، تحویل رخداد به مقصد کند را از مسیر مستقیم درخواست جدا می‌کند: درخواست رخداد را به بافر می‌دهد و مصرف‌کننده آن را بعداً می‌نویسد. **بازگشت تابع Log معمولاً به معنی پذیرش در بافر است، نه رسیدن به مخزن و نه دوام پس از Crash.** این جدایی می‌تواند انتظار درخواست را کم کند، اما کار Serialize، حافظه و I/O را حذف نمی‌کند.

**تاریخ بررسی منابع: <span dir="ltr">2026-11-10</span>.** اعداد و شبه‌کد فرض آموزشی‌اند؛ رفتار محصول در بخش شاهد رسمی با نام Apache Log4j مشخص شده است. مثال به زبان برنامه‌نویسی خاص وابسته نیست.

## پیش‌نیازهای همین درس

در لاگ‌گیری همگام، مسیر درخواست تا پایان نوشتن یا انتظار مقصد درگیر است؛ در حالت غیرهمگام، درخواست پیام را به صف می‌سپارد و Writer جداگانه می‌فرستد. صف محدود ظرفیت مشخص دارد. ACK یا تأیید مقصد یعنی مرز پذیرش اعلام‌شده رسیده، اما تا زمانی که دوام و بازیابی مقصد تعریف نشده، به‌تنهایی به معنی ماندگاری پس از Crash نیست. این درس تفاوت این مرزها را مرحله‌به‌مرحله توضیح می‌دهد.

## خروجی‌های یادگیری

- فرق زمان پذیرش Log، زمان قابل جست‌وجو شدن و مرز دوام را توضیح می‌دهید.
- ظرفیت و زمان پُرشدن صف را از نرخ تولید/مصرف تخمین می‌زنید.
- برای Queue Full، Crash، Shutdown و مقصد قطع‌شده سیاست انتخاب می‌کنید.
- سربار ابزارگذاری، Context و خطای Writer را قابل مشاهده نگه می‌دارید.

## مدل ذهنی: چه چیزی از مسیر درخواست خارج می‌شود؟

| مرحله | ممکن است هنوز در درخواست باشد؟ | هزینه/قرارداد |
| --- | --- | --- |
| بررسی Level و انتخاب فیلد | بله | بهتر است پیش از ساخت پیام گران انجام شود |
| Snapshot Context و داده مجاز | بله | کپی، اندازه و حذف داده حساس |
| ساخت/Encode پیام | بسته به پیاده‌سازی | Async لزوماً این CPU را جابه‌جا نمی‌کند |
| Enqueue | بله | Lock/رقابت، سقف زمان و رفتار صف پُر |
| نوشتن و ارسال دسته‌ای | معمولاً Writer جدا | دیسک/شبکه، Retry و خطای مقصد |
| ایندکس و جست‌وجو | در مقصد | تأخیر دریافت تا قابل مشاهده شدن |

حتی نوشتن در `stdout` می‌تواند با پُرشدن بافر مسیر خروجی مسدود شود؛ چاپ‌کردن را معادل تحویل سریع و پایدار نگیرید. فرایند Writer روی همان ماشین نیز CPU، دیسک و حافظه را با برنامه شریک است. در محیط تک‌هسته‌ای، جابه‌جایی کار بین Threadها الزاماً سود ندارد.

## قرارداد را پیش از صف بنویسید

۱. **رخداد تشخیصی را از سابقه ضروری جدا کنید.** Log عادی ممکن است با سیاست مشخص حذف شود. رویدادی که صحت سفارش یا Audit ضروری به ثبتش وابسته است، نیاز به مرز پذیرش پایدار و رسیدگی به خطا دارد؛ آن را به صف حافظه‌ایِ قابل حذف نسپارید. نوشتن همگام هم بدون قرارداد Flush، ذخیره و ACK، دوام مطلق نمی‌سازد. برای هماهنگی سابقه ضروری با تغییر کسب‌وکار، ثبت تراکنشی و انتقال بعدی می‌تواند لازم باشد؛ [درس Job و Outbox](../../03-asynchronism/01-background-jobs/README.md) مرز دو Write را توضیح می‌دهد.

۲. **صف محدود انتخاب کنید.** سقف تعداد رخداد و بایت هر دو مهم‌اند؛ هزار پیام یک‌کیلوبایتی با هزار Stack Trace بزرگ برابر نیست. حافظه واقعی شامل Object، Context، ساختار صف و بافر Batch هم هست. برای اندازه هر رخداد، فیلد و طول Stack Trace سقف بگذارید.

۳. **Queue Full را صریح کنید.** انتخاب باید با اهمیت رخداد و بودجه تأخیر سازگار باشد؛ هیچ گزینه‌ای ظرفیت بی‌نهایت تولید نمی‌کند.

| سیاست | فایده | هزینه و مرز |
| --- | --- | --- |
| حذف کنترل‌شده یا Sampling | حفظ بودجه درخواست و حافظه | از دست رفتن جزئیات؛ شمارش حذف لازم است |
| انتظار محدود، سپس تصمیم معلوم | جذب موج کوتاه | افزایش تأخیر؛ پس از مهلت همچنان شکست/حذف ممکن است |
| Block تا جا باز شود | بازگرداندن فشار به تولیدکننده | مقصد کند می‌تواند درخواست را نامحدود معطل کند |
| مسیر پایدار با ظرفیت محدود | بازیابی بهتر پس از Crash | I/O، فضای دیسک، ACK و عملیات بیشتر |

برای سطح‌های مهم می‌توان سهمیه یا مسیر جدا داشت؛ اما ERROR بودن پیام، ظرفیت یا دوام تضمین‌شده نمی‌سازد. Fallback به ارسال همگام هنگام قطع مقصد نیز ممکن است همان حادثه را وارد مسیر درخواست کند. قرارداد آن باید سقف زمان و رفتار شکست داشته باشد.

۴. **داده را پیش از عبور از مرز Async ثابت کنید.** Context درخواست ممکن است پس از بازگشت پاک یا برای درخواست دیگر استفاده شود. فیلدهای مجاز، زمان رخداد، Trace ID و در صورت نیاز شماره ترتیب محلی را Snapshot کنید؛ به Object تغییرپذیر یا Thread-local وابسته نمانید. حذف Token و داده شخصی را قبل از Enqueue انجام دهید، نه فقط هنگام نمایش.

۵. **Batch و Retry را محدود کنید.** Batch بزرگ تعداد Write را کم می‌کند اما تأخیر، حافظه و داده در معرض از دست رفتن را زیاد می‌کند. Flush با سقف تعداد/بایت و زمان انجام شود. Retry باید Backoff، سقف زمان و سقف بافر داشته باشد. ACK گم‌شده می‌تواند باعث ارسال دوباره شود؛ ترتیب سرتاسری و Exactly Once را بدون قرارداد مقصد ادعا نکنید.

## شبه‌کد: Log عملیاتی با حذف قابل مشاهده

این مثال فقط Log تشخیصی را با سیاست **حذف در نبود ظرفیت** مدل می‌کند؛ مسیر Audit و رویداد ضروری کسب‌وکار نیست. جزئیات Primitiveهای صف و Writer پیاده‌سازی نشده‌اند. هر بافر، شامل Batch جداشده، بودجه مستقل محدود دارد.

تابع `write_one_batch(deadline)` فقط یک Batch را رسیدگی می‌کند. Worker پس‌زمینه آن را پیوسته تکرار می‌کند؛ هنگام Shutdown، پس از توقف پذیرش، تکرار فقط تا تخلیه صف و پایان Batch جاری یا رسیدن به مهلت Shutdown ادامه دارد. Worker برای هر فراخوانی یک Deadline تازه با ساعت Monotonic می‌سازد و هنگام Drain آن را به مهلت باقی‌مانده Shutdown محدود می‌کند؛ انتظار صف و ارسال هر دو از همین بودجه مصرف می‌کنند. باقی‌مانده در پایان مهلت، تحویل‌شده محسوب نمی‌شود.

</div>

```text
log_operational(level, context, fields):
    if not level_enabled(level):
        return FILTERED
    event = snapshot_allowlisted_bounded_fields(level, context, fields)
    if not queue.try_enqueue_atomically(event, count_limit, byte_limit):
        dropped_total.increment(reason="queue_capacity")
        return DROPPED
    return ACCEPTED_IN_MEMORY

write_one_batch(deadline):
    batch = queue.take_bounded_batch(max_events, max_bytes, min(max_wait, remaining(deadline)))
    if batch.is_empty:
        return
    result = send_with_bounded_retry(batch, deadline)
    if result.acknowledged:
        delivered_total.add(batch.count)
    else:
        undelivered_total.add(batch.count)
        record_export_failure_via_independent_bounded_signal()
```

<div dir="rtl" align="right">

شمارنده‌ها Labelهای محدود دارند و از همان صف Log عبور نمی‌کنند؛ ثبت خطای Writer با همان Logger می‌تواند حلقه خطا بسازد. `undelivered_total` یعنی تأیید تحویل در بودجه به دست نیامده؛ ممکن است مقصد بخشی را پذیرفته باشد. حتی ACK هم دوام را فقط تا مرز تعریف‌شده همان مقصد نشان می‌دهد. در این مثال، Batch ناموفق پس از پایان بودجه نگه داشته نمی‌شود و از دست رفتن داده ممکن است؛ برای نیاز دیگر باید سیاست پایدار دیگری انتخاب کرد.

## مثال حل‌شده: صف چقدر زمان می‌خرد؟

فرض کنید تولید ۵۰۰۰ رخداد در ثانیه، مصرف پایدار ۴۰۰۰، ظرفیت صف ۲۰هزار رخداد و Payload ثابت ۱ کیلوبایت ده‌دهی است. صف ابتدا خالی است، اندازه رخدادها یکسان است، Writer بدون وقفه کار می‌کند و Retry/Batch را در این تقریب کنار می‌گذاریم.

</div>

```text
growth = 5000 - 4000 = 1000 events/s
time_to_full = 20000 / 1000 = 20 s
queued_payload_at_full = 20000 * 1000 = 20,000,000 bytes
after input falls to 2000/s: net drain = 4000 - 2000 = 2000/s
drain_time_from_full = 20000 / 2000 = 10 s
```

<div dir="rtl" align="right">

حجم ۲۰ مگابایت فقط Payload است؛ حافظه واقعی بیشتر است. پس از پُرشدن در بار ثابت، سیاست Drop در بلندمدت حدود ۱۰۰۰ رخداد در ثانیه را حذف می‌کند؛ سیاست Block تولیدکننده را کند می‌کند و بار مشاهده‌شده تولید ممکن است کاهش یابد. صف بزرگ‌تر، نرخ مصرف را افزایش نمی‌دهد؛ فقط زمان رسیدن به تصمیم را عقب می‌اندازد.

در FIFO و مصرف ثابت ۴۰۰۰، رخداد پذیرفته‌شده نزدیک انتهای صف پُر، حدود پنج ثانیه منتظر شروع خدمت می‌ماند؛ پذیرش سریع Log با آماده‌شدن سریع آن برای بررسی یکسان نیست. وقفه مقصد این برآورد را تغییر می‌دهد. نمودار تأخیر API خوب همراه با سن Log بالا، می‌تواند تشخیص حادثه را عقب بیندازد.

برای مقایسه هزینه درخواست، فرض جداگانه بگذارید: در مسیر همگام دو ارسال سری هرکدام ۳ میلی‌ثانیه انتظار دارند؛ در مدل Async دو پذیرش هرکدام ۰٫۰۵ میلی‌ثانیه و صف دارای ظرفیت است. انتظار مستقیم از حدود ۶ به ۰٫۱ میلی‌ثانیه می‌رسد؛ اختلاف ۵٫۹ میلی‌ثانیه، کاهش فرضی انتظار است، نه صرفه‌جویی CPU اندازه‌گیری‌شده و نه حذف ارسال. Serialize یا صف پُر می‌توانند سود را کم یا معکوس کنند.

## Crash، Shutdown و ترتیب

در Shutdown کنترل‌شده، ابتدا ورود کار جدید و تولید معمول رخداد متوقف شود، سپس Writer با مهلت مشخص Flush کند و نتیجه/باقی‌مانده اعلام شود. مهلت باید با فرصت واقعی خاتمه Process هماهنگ باشد. Flush با Timeout ممکن است کامل نشود؛ Crash، قطع برق یا Kill ناگهانی فرصت Flush نمی‌دهند. بافر دیسکی می‌تواند ریسک را کم کند، ولی باید دانست کدام مرحله واقعاً پایدار شده و در Restart چگونه بازیابی می‌شود.

چند Writer، Batch و Retry می‌توانند ترتیب مشاهده را تغییر دهند. زمان تولید و زمان دریافت را جدا ذخیره کنید؛ برای تحلیل یک درخواست از Trace ID و رابطه رخدادها استفاده کنید. ترتیب دریافت مقصد را ترتیب قطعی همه رخدادهای چند ماشین ننامید.

## شاهد عملیاتی رسمی و حد شواهد

> [راهنمای Apache Log4j درباره Async Loggers](https://logging.apache.org/log4j/2.x/manual/async.html) توضیح می‌دهد بار پایدار بیشتر از توان Appender، صف را پُر می‌کند و گزارش خطای نوشتن به درخواست دشوارتر می‌شود. در این محصول، سیاست پیش‌فرض Queue Full مسدودکردن فراخواننده است و سیاست Discard برای حذف سطح‌های تعیین‌شده وجود دارد. این رفتار را به همه Loggerها تعمیم ندهید.
>
> همین راهنما درباره Snapshot پیام تغییرپذیر و انتخاب مسیر همگام برای Audit هشدار می‌دهد. شاهد این بخش مستند عملیاتی رسمی است؛ برای بار فرضی این درس گزارش مستقل تولید یا عدد بهبود قابل تعمیم ارائه نمی‌کنیم. شبه‌کد بالا قرارداد آموزشی متفاوتِ Drop دارد و تنظیم پیش‌فرض Log4j نیست.

## چه وقت مناسب است و چه وقت انتخاب ضعیفی است؟

وقتی انتظار مقصد Log در مسیر حساس هزینه دارد و تأخیر کوتاه یا حذف محدود رخداد تشخیصی پذیرفتنی است، Async می‌تواند مناسب باشد. اگر Logger فعلی هزینه ناچیز دارد، Thread، صف و Shutdown اضافی شاید پیچیدگی بی‌فایده بسازند. در تولید دائماً بیشتر از مصرف، درمان اصلی کاهش داده، انتخاب مقصد مناسب یا افزایش ظرفیت واقعی است. برای ثبت ضروریِ بدون تحمل ازدست‌رفتن، ابتدا پروتکل دوام و شکست را حل کنید؛ واژه Async آن را تعیین نمی‌کند.

## تمرین کوچک و مشاهده مورد انتظار

این تمرین محاسباتی/مرور خرابی است. تولید ۳۰۰۰ رخداد در ثانیه، مصرف ۲۰۰۰ و صف خالی با ظرفیت ۱۰هزار را فرض کنید. زمان پُرشدن را حساب کنید. سپس قطع کامل مقصد را با مصرف صفر، از صف خالی مدل کنید. برای هر حالت، نتیجه Drop، Block و صف پایدار محدود را بنویسید. در پایان فرض کنید ۴۰۰ رخداد در حافظه مانده و Process ناگهان می‌میرد.

**راه‌حل:** در بار عادی، رشد خالص صف <span dir="ltr">3000 − 2000 = 1000</span> رخداد/s است؛ <span dir="ltr">10,000 ÷ 1,000 = 10</span> ثانیه تا پرشدن. هنگام قطع کامل مقصد، رشد خالص <span dir="ltr">3,000</span> رخداد/s است؛ <span dir="ltr">10,000 ÷ 3,000 ≈ 3.33</span> ثانیه. Drop حافظه را محدود و رخداد را حذف می‌کند؛ Block انتظار را به تولیدکننده منتقل می‌کند؛ صف پایدار فقط تا ظرفیت و مرز ACK خود دوام می‌آورد. ۴۰۰ رخداد حافظه‌ای هنگام Crash ممکن است از دست بروند؛ Flush هنگام Shutdown کنترل‌شده، اثبات دوام در Crash نیست. هیچ قطع واقعی مقصد یا اندازه‌گیری کارایی در این تمرین انجام نشده است.

| خطا | نشانه عملیاتی | اقدام بررسی |
| --- | --- | --- |
| صف نامحدود | رشد RAM، GC و OOM | حد تعداد/بایت و سقف اندازه رخداد |
| حذف خاموش | شکایت بدون Log کافی | شمارنده Drop مستقل و سن داده |
| Retry نامحدود مقصد قطع | صف پیر و دیسک پُر | بودجه Retry و سیاست پایان |
| Logger داخل خطای Logger | تکرار خطا و مصرف CPU | مسیر مستقل و محدود گزارش خطا |
| Object تغییرپذیر پس از Enqueue | Context اشتباه یا داده متعلق به درخواست دیگر | Snapshot امن پیش از مرز Async |
| Fallback همگام بی‌مهلت | جهش p99 هنگام حادثه | سقف انتظار و قرارداد Queue Full |
| اتکا به Shutdown برای دوام | آخرین رخدادها پس از Crash نیستند | مرز پایدار و بازیابی؛ تفکیک Audit |

## چک‌لیست عملیاتی

- [ ] پذیرش حافظه‌ای، ACK مقصد و دوام پایدار از هم تفکیک شده‌اند.
- [ ] Log تشخیصی و سابقه ضروری قراردادهای مناسب خود دارند.
- [ ] صف و Batch حد تعداد/بایت دارند؛ پیام و Context نیز محدودند.
- [ ] Queue Full، Retry و شکست نهایی سیاست قابل مشاهده دارند.
- [ ] Drop، صف، سن رخداد، خطای Writer و زمان API کنار هم دیده می‌شوند.
- [ ] داده حساس و Object تغییرپذیر پیش از Enqueue کنترل می‌شوند.
- [ ] Shutdown، Crash، قطع مقصد و تغییر ترتیب مرور شده‌اند.
- [ ] سود Async با بار نماینده و هزینه CPU/حافظه سنجیده می‌شود؛ عدد عمومی فرض نشده است.

## آزمون مرور

۱. آیا `ACCEPTED_IN_MEMORY` یعنی Log پس از Crash قابل بازیابی است؟

۲. در مثال ۵۰۰۰ ورودی و ۴۰۰۰ خروجی با ظرفیت ۲۰هزار، صف چه زمانی پُر می‌شود؟

۳. آیا دوبرابرکردن صف مشکل نرخ تولید دائماً بیشتر از مصرف را رفع می‌کند؟

۴. چرا ERROR بودن پیام، تضمین تحویل نمی‌سازد؟

۵. چرا باید Context پیش از عبور از مرز Async ثبت شود؟

۶. آیا «Flush را در Shutdown صدا می‌زنیم» برای دوام Audit کافی است؟

۷. آیا Timeout ارسال یعنی مقصد قطعاً هیچ رخدادی نگرفته است؟

۸. چرا Drop و خطای Writer نباید فقط از همان Logger گزارش شوند؟

### پاسخ‌نامه توضیحی

۱. **خیر.** تنها پذیرش در حافظه اعلام شده است؛ Crash می‌تواند رخداد را پیش از ارسال از بین ببرد.

۲. **حدود ۲۰ ثانیه.** رشد خالص ۱۰۰۰ رخداد در ثانیه است؛ این حساب با فرض صف خالی و نرخ ثابت است.

۳. **خیر.** زمان پُرشدن بیشتر می‌شود، اما اختلاف نرخ باقی است؛ مصرف، تولید یا سیاست پذیرش باید تغییر کند.

۴. **سطح اهمیت، منبع ذخیره و ظرفیت نیست.** حتی مسیر جدا نیز سقف دارد؛ قرارداد Queue Full و ACK/دوام باید تعریف شود.

۵. **عمر و مقدار Context می‌تواند تغییر کند.** نگهداری Snapshot محدود و تغییرناپذیر از جابه‌جایی شناسه‌ها و خطای هم‌زمانی جلوگیری می‌کند.

۶. **خیر.** Crash فرصت Shutdown نمی‌دهد و Flush هم ممکن است Timeout شود؛ Audit ضروری مرز پایدار و رسیدگی به شکست می‌خواهد.

۷. **خیر.** دریافت یا ACK ممکن است نامعلوم باشد؛ Retry می‌تواند Duplicate بسازد. `undelivered` یعنی بی‌تأیید در بودجه، نه اثبات عدم دریافت.

۸. **مسیر خراب نمی‌تواند تنها شاهد خرابی خودش باشد.** صف پُر ممکن است گزارش Drop را هم حذف کند یا حلقه خطا بسازد؛ شمارنده/مسیر مستقل محدود لازم است.

## جمع‌بندی

Async Logging انتظار مقصد را از درخواست جدا می‌کند، ولی هزینهٔ ساخت پیام، حافظه و ارسال باقی است. برای صف محدود، نرخ و سن داده و سیاست Queue Full را پایش کنید. رخداد تشخیصی را با Audit یکی نگیرید؛ اگر تحویل/دوام ضروری است، پذیرش پایدار، ACK، Retry و بازیابی را به‌عنوان قرارداد مستقل طراحی کنید.

## منابع تکمیلی اختیاری

برای فهم این درس یا حل تمرین، بازکردن پیوندهای زیر لازم نیست؛ آن‌ها برای مطالعهٔ بیشتر و بررسی رفتار مستند پیاده‌سازی‌ها هستند.

- **فارسی:** در بررسی منابع این درس، مقاله فارسیِ قابل بررسی و مستقیم درباره صف محدودِ لاگ برنامه، Queue Full و دوام Async پیدا نشد؛ توضیح فارسی همین صفحه این مرزها را پوشش می‌دهد. نوشته‌های مربوط به Transaction Log و Delayed Durability پایگاه داده، جایگزین این موضوع نیستند.
- **انگلیسی، رسمی و مستقیم:** [Apache Log4j Async Loggers](https://logging.apache.org/log4j/2.x/manual/async.html)؛ مصالحه‌های صف، سیاست پُرشدن، پیام تغییرپذیر و Audit؛ مثال پیاده‌سازی، نه الزام استفاده از Java یا Log4j.
- **انگلیسی، مستندات Python:** [QueueHandler and QueueListener](https://docs.python.org/3/library/logging.handlers.html#queuehandler)؛ انتقال کار Handler به Thread جدا؛ نوع صف و رفتار Queue Full باید جدا تعریف شود.
- **انگلیسی، مستندات Serilog:** [Async sink wrapper](https://github.com/serilog/serilog-sinks-async)؛ صف محدود، حذف رخدادها و Flush هنگام خاتمه؛ پیاده‌سازی نمونه است، نه تضمین دوام عمومی.
- **انگلیسی، مستندات Pino:** [Asynchronous logging](https://github.com/pinojs/pino/blob/main/docs/asynchronous.md)؛ Buffer و خطر از دست‌رفتن رخدادهای تازه در Crash؛ تصمیم‌های Lambda و Flush به همان Runtime/transport مربوط‌اند.
- **انگلیسی، مکمل عملیاتی:** [OpenTelemetry Collector Resiliency](https://opentelemetry.io/docs/collector/resiliency/)؛ رفتار صف ارسال پایین‌دست و مرز ازدست‌رفتن داده. Collector جای Logger داخل برنامه نیست؛ هر دو مرز باید جدا بررسی شوند.
