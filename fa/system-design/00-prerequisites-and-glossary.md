# پیش‌نیازها، واژه‌نامه و روش مطالعه

این صفحه کمک می‌کند مطالب ۱۰ فصل را بدون کتاب یا دورهٔ بیرونی دنبال کنی. برای فهم مثال‌ها لازم نیست قبلاً معماری توزیع‌شده طراحی کرده باشی؛ آشنایی مقدماتی با برنامه‌نویسی، HTTP و SQL مفید است. هر اصطلاح انگلیسی را در نخستین استفاده با معنای فارسی توضیح داده‌ایم و در صورت نیاز به عمق بیشتر، منابع اختیاری هر درس را ببین.

## پیش‌نیازهای حداقلی

### برنامه و فرایند

برنامه کد و config است؛ process نمونهٔ در حال اجرای برنامه روی سیستم‌عامل است. چند process می‌توانند هم‌زمان سرویس یکسانی اجرا کنند. اگر داده فقط در حافظهٔ process باشد، با restart از دست می‌رود و process دیگر آن را نمی‌بیند.

### درخواست و پاسخ

Client درخواست می‌فرستد و server پاسخ می‌دهد. درخواست وب معمولاً method، path، header و body دارد؛ پاسخ status، header و body. `2xx` موفقیت پروتکلی، `4xx` مشکل درخواست/مجوز و `5xx` خطای server یا dependency را نشان می‌دهد؛ semantics دقیق endpoint باید روشن باشد. Timeout فقط یعنی پاسخ در مهلت نرسیده، نه اینکه عملیات حتماً اجرا نشده است.

### پایگاه داده و تراکنش

جدول ردیف/ستون، primary key هویت ردیف و index مسیر جست‌وجوست. Transaction مجموعه‌ای از تغییرها را در محدودهٔ یک DB به‌صورت همه/هیچ commit می‌کند. Unique constraint جلوی مقادیر تکراری را حتی زیر رقابت هم‌زمان می‌گیرد. backup نسخهٔ قابل‌بازیابی است؛ replica نسخهٔ زنده برای دوام یا خواندن بیشتر است.

### شبکه قابل اعتماد نیست

اتصال می‌تواند دیر شود، packet گم شود، پاسخ از مسیر برگشت نرسد یا بخشی از سرویس‌ها جدا بمانند. هر call شبکه باید timeout/deadline و رفتار failure داشته باشد. retry فقط در صورت امن‌بودن اثر و با سقف/backoff انجام می‌شود.

## واژه‌نامهٔ اصلی

| اصطلاح | توضیح کوتاه |
| --- | --- |
| Availability | احتمال یا نسبت زمانی/درخواستی که سرویس طبق قرارداد پاسخ قابل‌استفاده می‌دهد |
| Backpressure | کندکردن/محدودکردن تولید کار وقتی مصرف‌کننده ظرفیت ندارد |
| Cache | نسخهٔ موقت و سریع‌تر داده برای کم‌کردن latency/بار منبع |
| Consistency | قرارداد اینکه تغییر داده چگونه و چه زمانی برای خواننده‌ها دیده می‌شود |
| Consumer / Producer | دریافت‌کننده / تولیدکنندهٔ پیام |
| Dependency | سرویس، DB یا زیرساختی که مسیر درخواست به آن نیاز دارد |
| Idempotency | اجرای دوبارهٔ یک intent اثر تجاری را تکرار نمی‌کند |
| Latency | مدت تکمیل یک درخواست یا کار |
| Load shedding | رد/حذف کنترل‌شدهٔ کار کم‌اهمیت برای حفاظت از هستهٔ سرویس |
| Partition | جداشدن nodeها از نظر ارتباط یا تقسیم داده میان بخش‌ها، بسته به زمینه |
| p95 / p99 | percentile؛ 95%/99% مشاهدات حداکثر تا این زمان‌اند |
| Queue | محل نگهداری موقت کار تا زمان پردازش |
| Replication lag | فاصلهٔ زمانی/داده‌ای replica از منبع نوشتن |
| RPO | حداکثر بازهٔ داده‌ای که پس از خرابی قابل‌از‌دست‌رفتن است |
| RTO | حداکثر زمان هدف تا بازگشت سرویس |
| Scalability | توان حفظ کیفیت با رشد بار/داده/کاربر |
| SLI / SLO / SLA | شاخص اندازه‌گیری / هدف داخلی / تعهد بیرونی |
| Throughput | تعداد کار تکمیل‌شده در واحد زمان |
| Timeout / Deadline | سقف انتظار یک عملیات / بودجهٔ زمانی کل مسیر |
| Source of truth | مخزن مرجعی که حقیقت تجاری داده را تعیین می‌کند |
| Hot key | کلید پرترافیک که بار را روی یک partition یا node متمرکز می‌کند |
| Blast radius | دامنهٔ بخش‌هایی که یک خرابی متأثر می‌کند |
| Graceful degradation | ارائهٔ قابلیت محدود اما صادقانه به‌جای سقوط کامل |

## فرمول‌هایی که در درس‌ها استفاده می‌شوند

### نرخ و ظرفیت

میانگین نرخ درخواست `تعداد درخواست / ثانیه‌های بازه` است. برای تخمین اوج، ضریب اوج را به‌صورت فرض وارد کن و آن را با داده بسنج. ظرفیت مسیر از ضعیف‌ترین component می‌آید؛ ظرفیت مستقل API را نباید ظرفیت کل سیستم فرض کرد.

### قانون Little

در وضعیت پایدار: `L = λ × W`. `L` تعداد متوسط کارهای داخل سیستم، `λ` نرخ ورود و `W` متوسط زمان ماندن است. 200 درخواست در ثانیه × 0.3 ثانیه ≈ 60 درخواست هم‌زمان. اگر ورودی از توان تکمیل بیشتر بماند، صف با زمان رشد می‌کند و فرض پایداری برقرار نیست.

### دسترس‌پذیری سری و موازی

برای دو جزء سری مستقل که هر دو لازم‌اند: `A = A1 × A2`. برای دو مسیر موازی مستقل که کافی است یکی سالم باشد: `A = 1 - (1-A1)(1-A2)`. این محاسبه با خرابی مشترک، مسیر routing مشترک یا دادهٔ ناسالم معتبر نیست.

### Downtime و error budget

`downtime مجاز = (1 - هدف availability) × مدت بازه`. در 30 روز، 99.9% تقریباً 43.2 دقیقه و 99.99% حدود 4.32 دقیقه است. اگر شاخص بر اساس درخواست باشد، درصد uptime را مستقیم به درخواست‌های ناموفق تعمیم نده.

## روش استفاده از درس‌ها

1. ایدهٔ مرکزی را با زبان خودت بازگو کن.
2. فرض‌های مثال را استخراج کن و عددها را دوباره حساب کن.
3. آزمون را پیش از پاسخ‌نامه حل کن؛ اگر پاسخ ناقص است، بگو کدام فرض را جا انداخته‌ای.
4. تمرین را با پروژه‌ای که می‌شناسی اجرا کن: فروشگاه، سامانهٔ رزرو یا سرویس محتوا.
5. برای هر تصمیم بپرس: چه نیازی؟ چه trade-offی؟ چطور می‌فهمم درست کار می‌کند؟ هنگام failure چه می‌شود؟
