# جایگزین‌های Kubernetes و معیار انتخاب

**فصل:** [مقدمه و مدل ذهنی](../../README.md)

## هدف یادگیری

گزینه‌ها را بر اساس نوع بار، مسئولیت عملیات و هزینه مقایسه کنید؛ به‌جای اینکه ابزار محبوب‌تر را پیش‌فرض بگیرید.

## خانواده‌های جایگزین

| گزینه | وقتی بررسی شود | هزینه یا محدودیت قابل‌بررسی |
| --- | --- | --- |
| یک VM یا پلتفرم سنتی | یک سرویس کوچک و انتشار ساده دارید | ظرفیت و failover را خودتان طراحی می‌کنید |
| Docker Compose | محیط تک‌میزبان، توسعه یا سرویس ساده دارید | کنترل چندمیزبانی و policyهای cluster-level محدودتر است |
| Container App / سرویس managed | ترجیح می‌دهید زیرساخت orchestration را provider پنهان کند | وابستگی به قرارداد و قابلیت‌های provider |
| Nomad | orchestration سبک‌تر یا چندنوع workload مهم است | باید ecosystem و یکپارچگی با ابزارهای تیم را ارزیابی کنید |
| Docker Swarm | عملیات ساده و سازگاری با ابزار موجود ارزشمند است | قابلیت‌ها و اکوسیستم موردنیاز را برای نیاز خود بسنجید |
| OpenShift | Kubernetes همراه با قابلیت‌ها و پشتیبانی سازمانی می‌خواهید | محصول و مدل عملیاتی مشخص‌تری را می‌پذیرید |
| Kubernetes مدیریت‌شده | API و اکوسیستم Kubernetes لازم است ولی control plane را می‌خواهید واگذار کنید | هزینهٔ provider و مسئولیت‌های باقی‌مانده را محاسبه کنید |

این جدول حکم رتبه‌بندی ثابت نیست؛ پروژه‌ها و قابلیت‌های سرویس‌ها تغییر می‌کنند. قبل از تصمیم نهایی، مستندات و قرارداد فعلی provider را بررسی کنید.

## ماتریس تصمیم

برای هر گزینه از 1 تا 5 امتیاز دهید و وزن را با اولویت محصول تعیین کنید:

- زمان رسیدن به production
- دسترس‌پذیری و recovery
- مهارت on-call و استخدام
- portability و وابستگی به provider
- هزینهٔ control plane، node، storage، network و افزونه‌ها
- امنیت، audit و انطباق
- نیاز به autoscaling و rollout
- بار عملیاتی کل

برای نمونه، تیمی با چند microservice و استقرار پرتکرار احتمالاً از API یکپارچه بهره می‌برد. تیمی با یک پردازش زمان‌بندی‌شده و ترافیک اندک ممکن است container job managed را ساده‌تر نگه دارد.

## مهاجرت مرحله‌ای

اگر برنامهٔ فعلی کار می‌کند، آن را صرفاً برای «cloud-native شدن» بازنویسی نکنید. ابتدا یک سرویس کم‌ریسک را انتخاب، معیار موفقیت بنویسید، image و manifest را بسازید، بار و rollback را آزمایش کنید و هزینهٔ عملیات را اندازه بگیرید. بعد از اثبات ارزش، مهاجرت را گسترش دهید.

## دام‌های رایج

- مقایسه فقط براساس قابلیت فنی و نادیده‌گرفتن مسئولیت 24/7.
- محاسبهٔ هزینهٔ ماشین‌ها بدون وقت مهندسی، شبکه و ذخیره‌سازی.
- فرض انتقال آسان میان cloudها فقط چون همه Kubernetes API دارند.
- انتقال دیتابیس stateful قبل از طراحی backup و restore.
- استفاده از Kubernetes به‌عنوان راه‌حل معماری برنامهٔ نامناسب.

## کوییز تشریحی

1. چه موقع Compose گزینهٔ معقولی است؟ — وقتی نیاز تک‌میزبان یا توسعه‌ای است و قابلیت‌های cluster چندمیزبانی ارزش هزینهٔ اضافی ندارد.
2. managed Kubernetes کدام مسئولیت را معمولاً ساده می‌کند؟ — نگهداری بخشی از control plane؛ اما workload، داده، دسترسی و هزینه همچنان نیاز به مدیریت دارند.
3. یک معیار غیرقیمتی برای تصمیم چیست؟ — ظرفیت on-call، مهارت تیم، audit، portability یا زمان رسیدن به محصول.
4. چگونه ارزش مهاجرت را اثبات می‌کنید؟ — پایلوت کم‌ریسک با معیارهای موفقیت، rollback و اندازه‌گیری هزینهٔ کل.
