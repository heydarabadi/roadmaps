# دامنه و اندازهٔ PR

**زبان:** فارسی · [English](../../../../en/code-review/02-author/01-pr-scope/README.md)

> مسیر: [فصل ۲ — آماده‌سازی نویسنده](../README.md) · [فهرست دوره](../../README.md)

## آموزش

PR کوچک و متمرکز معمولاً فهم، بررسی و بازگردانی آسان‌تری دارد. کوچک به معنی تعداد خط ثابت نیست؛ معیار بهتر یک دلیل روشن برای تغییر، چند مفهوم مستقل، پیچیدگی و زمانی است که reviewer برای دنبال‌کردن اثر نیاز دارد. تغییر کم‌خط در احراز هویت می‌تواند از rename چندفایلی پرریسک‌تر باشد.

کار بزرگ را به مراحل معنادار تقسیم کن: migration سازگار، پیاده‌سازی، فعال‌سازی با feature flag، و پاک‌سازی مسیر قدیمی. PRهای وابسته باید ترتیب و base روشن داشته باشند. اگر شکستن تغییر آن را غیرقابل‌اجرا یا گمراه‌کننده می‌کند، بخش‌های پرریسک را در شرح برجسته کن و از review زودهنگام کمک بگیر.

یک PR نباید هم‌زمان چند مسئلهٔ نامرتبط، refactor بزرگ و تغییر رفتاری را پنهان کند. نویسنده باید نویز generated files یا formatting را از منطق جدا کند تا reviewer بداند واقعاً چه تصمیمی را می‌سنجد.

## روند پیشنهادی

1. هدف PR را در یک جمله بنویس.
2. تغییرات نامرتبط را جدا کن.
3. مراحل وابسته را با ترتیب merge مشخص کن.
4. risk را پنهان نکن و بخش‌های مهم را برجسته کن.
5. اگر طراحی پرریسک است پیش از پیاده‌سازی بازخورد بگیر.

## مثال کاربردی

ویژگی checkout مرحله‌ای است. نویسنده ابتدا schema سازگار را می‌سازد، سپس رفتار را پشت flag اضافه می‌کند، و در مرحلهٔ آخر مسیر قدیمی را حذف می‌کند. هر PR توضیح می‌دهد با کدام نسخهٔ سرویس باید سازگار باشد.

## خطاهای رایج

عدد ثابت «حد PR» نساز؛ تغییر بزرگ را به گام‌های بی‌معنا خرد نکن؛ تغییر حساس را به‌خاطر کم‌خط‌بودن کم‌ریسک ندان؛ نویز formatter را با منطق قاطی نکن.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** PR کوچک‌تر چه ویژگی مهمی دارد؟

   1. زیر تعداد خط مشخص است
   2. هدف روشن و دامنهٔ قابل‌فهم دارد
   3. فقط یک فایل دارد
   4. بدون تست است

**پاسخ:** 2 — اندازه با فهم‌پذیری و هدف سنجیده می‌شود.

### پرسش 2

**سؤال:** چرا چند خط تغییر مجوز هنوز پرریسک است؟

   1. خطوط کم سریع نوشته می‌شوند
   2. اثر دسترسی و داده ممکن است وسیع باشد
   3. چون PR باید بزرگ باشد
   4. چون تست لازم نیست

**پاسخ:** 2 — اثر تغییر مهم‌تر از تعداد خط است.

### پرسش 3

**سؤال:** feature flag چه زمانی کمک می‌کند؟

   1. برای مخفی‌کردن review
   2. برای rollout مرحله‌ای یک feature ناقص/پرریسک
   3. برای حذف تست
   4. برای هر typo

**پاسخ:** 2 — flag می‌تواند فعال‌سازی و بازگشت را کنترل کند.

### پرسش 4

**سؤال:** اگر تغییر قابل‌شکستن نیست چه باید کرد؟

   1. بی‌توضیح ارسال کرد
   2. ریسک، زمینه و اعتبارسنجی را برجسته کرد
   3. از review صرف‌نظر کرد
   4. تست‌ها را حذف کرد

**پاسخ:** 2 — توضیح دقیق بررسی تغییر ناگزیر را ممکن می‌کند.

## آموزش عمیق: اندازه را با قابلیت فهم بسنج

### چرا PR متمرکز بهتر بازبینی می‌شود؟

بازبین باید در حافظهٔ کاری نگه دارد نیازمندی چه بود، هر فایل چه نقشی دارد، داده از کجا می‌آید و کدام رفتار عوض می‌شود. وقتی diff چند مسئلهٔ مستقل را مخلوط می‌کند، این زنجیره بار شناختی زیادی پیدا می‌کند. کامنت‌ها هم بین تغییرهای مهم و کم‌اهمیت پخش می‌شوند و نقص مهمی ممکن است جا بماند. PR متمرکز کمک می‌کند بازبین اثر را دنبال کند و نویسنده اگر جهت کلی رد شد کار کمتری را دور بریزد.

«کوچک» را با عدد خط تعریف نکن. سه خط در کنترل دسترسی می‌تواند پرریسک باشد؛ تغییر مکانیکی چندفایلی ممکن است رفتار کمی عوض کند، اما reviewer باید مطمئن شود واقعاً مکانیکی است. معیارها: یک دلیل تغییر، تعداد رفتارهای مستقل، پیچیدگی، وضوح وابستگی‌ها، زمان فهم، سختی rollback و دامنهٔ اثر.

### روش شکستن کار

1. **هدف را قطعه‌بندی کن:** ابتدا refactor بی‌رفتار، سپس API، بعد مصرف‌کنندهٔ API.
2. **هر مرحله را معنادار نگه دار:** PR نباید سیستم را در حالت شکسته بگذارد، مگر feature عمداً خاموش یا پشت flag باشد.
3. **وابستگی را ثبت کن:** بگو PR بعدی به کدام تغییر متکی است و ترتیب merge چیست.
4. **تغییر ماشینی را جدا کن:** rename، formatter و generated file را از منطق تفکیک کن یا روش تولیدشان را نشان بده.
5. **با reviewer هماهنگ شو:** اگر تغییر ناگزیر بزرگ است، بخش‌ها، مسیر خواندن و نقاط حساس را در شرح مشخص کن.

راهنمای Google «یک تغییر خودبسنده» را مهم‌تر از سقف همیشگی خطوط می‌داند؛ Microsoft نیز روی PR متمرکز با یک علت روشن برای تغییر پروژه تأکید می‌کند. این‌ها راهنمای همان سازمان‌ها هستند، نه حد عددی جهانی.

### مثال حل‌شده: قابلیت پرداخت

PR اولیه migration، API، UI، گزارش مالی، rename پوشه‌ها و formatting کل مخزن را مخلوط کرده است. راه بهتر:

1. تغییر مکانیکی را جدا کن تا نویز نپوشاند کدام کد رفتار را تغییر می‌دهد.
2. migration سازگار و قابل‌برگشت را آماده کن.
3. API و تست قرارداد را اضافه کن.
4. UI را به API وصل کن.
5. feature را مرحله‌ای فعال کن و مسیر قدیمی را پس از اطمینان پاک کن.

اگر migration به‌تنهایی سرویس را خراب می‌کند، آن را صرفاً به چند PR خرد نکن؛ ابتدا migration سازگار با نسخه‌های قدیمی و جدید بساز. هدف «کمترین خطوط در هر PR» نیست؛ هدف امکان فهم و استقرار امن است.

### ضدالگوها

- **PR کوچک اما بی‌معنا:** افزودن API بدون هیچ نمونهٔ استفاده‌ای فهم مقصد را سخت می‌کند.
- **Stacking بدون نقشه:** چند PR وابسته که base یا ترتیب mergeشان معلوم نیست صف را شکننده می‌کند.
- **پنهان‌کردن فایل‌ها:** collapse کردن diff جای توضیح و review را نمی‌گیرد.
- **حد خط مکانیکی:** ۱۰۰ خط همیشه خوب و ۱۰۱ خط همیشه بد نیست.

### تمرین و پاسخ پیشنهادی

PR پنج بخش دارد: migration، dependency جدید، API، UI و بازنویسی formatter. کدام‌ها را جدا می‌کنی؟

**پاسخ پیشنهادی:** formatter را مستقل می‌کنم چون نویز دارد؛ dependency را با دلیل، license و اثر bundle توضیح می‌دهم؛ migration را با نسخه‌های هم‌زمان سازگار می‌سازم؛ API و UI را بر اساس ترتیب قابل‌استقرار می‌شکنم. اگر جداسازی PR بی‌مصرف بسازد، آن را تحمیل نمی‌کنم.

### معیار تصمیم

اگر هر بخش هدف و تست روشن دارد و می‌تواند امن merge/deploy شود، جداسازی مفید است. اگر جداسازی state ناسازگار، API استفاده‌نشده یا history گمراه‌کننده می‌سازد، یک PR منسجم با راهنمای خواندن بهتر است. هیچ‌وقت از عدد خطوط به‌تنهایی نتیجه نگیر.
