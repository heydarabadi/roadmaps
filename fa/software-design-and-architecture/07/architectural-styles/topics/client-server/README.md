## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

کارخواه درخواست می‌فرستد و کارساز سرویس یا منبعی را پاسخ می‌دهد؛ اتصال، auth، protocol و versioning باید روشن باشند.

## مثال کاربردی

اپلیکیشن موبایل از REST API سفارش ثبت می‌کند؛ سرور اعتبار و موجودی را کنترل می‌کند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «سبک‌های معماری» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** مرکزیت server آن را نقطهٔ نیازمند دسترس‌پذیری و ظرفیت می‌کند.
- **بازبینی:** به کارخواه اعتماد نکن؛ اعتبارسنجی و مجوزدهی سمت سرور ضروری است.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: کارخواه درخواست می‌فرستد و کارساز سرویس یا منبعی را پاسخ می‌دهد؛ اتصال، auth، protocol و versioning باید روشن باشند.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: اپلیکیشن موبایل از REST API سفارش ثبت می‌کند؛ سرور اعتبار و موجودی را کنترل می‌کند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: مرکزیت server آن را نقطهٔ نیازمند دسترس‌پذیری و ظرفیت می‌کند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: به کارخواه اعتماد نکن؛ اعتبارسنجی و مجوزدهی سمت سرور ضروری است.

## آموزش تکمیلی مستقل

### ۵. Client-Server

Client درخواست می‌دهد و server مالک resource یا capability است. HTTP API معمولاً stateless request/response دارد، اما server همچنان state پایدار و session/domain data نگه می‌دارد. سمت client را منبع معتبر امنیتی فرض نکن: authentication, authorization و validation سمت server لازم‌اند.

هزینه‌ها: network latency، timeout، retry، نسخه‌بندی قرارداد، server capacity و failure جزئی. درخواست ممکن است server را اجرا کرده باشد ولی پاسخ در شبکه گم شود؛ command باید idempotency key یا reconciliation داشته باشد.

## نمودار معماری و خواندن مرحله‌ای

Client درخواست را می‌فرستد و server مسئولیت پاسخ و معمولاً state مشترک را دارد. مرز شبکه latency، timeout، authentication و failure می‌آورد؛ retry بدون idempotency ممکن است عمل را تکرار کند.
**دام رایج:** server را بی‌نهایت در دسترس فرض نکن.
**تمرین با پاسخ:** درخواست پرداخت timeout شد؛ پیش از retry با کلید idempotency یا استعلام وضعیت، روشن کن پرداخت اول انجام شده یا نه.

این نمودار ساده فقط یک view را نشان می‌دهد؛ سامانهٔ واقعی به تصمیم روشن دربارهٔ شکست، امنیت و مالکیت هم نیاز دارد.

~~~text
[Client] -- request / response --> [Server] ---> [Database]
    ^                                  |
    +--------------- response --------+
~~~
