# تست، مستندات و ریسک‌های تغییر

**زبان:** فارسی · [English](../../../../en/code-review/02-author/03-tests-docs-risk/README.md)

> مسیر: [فصل ۲ — آماده‌سازی نویسنده](../README.md) · [فهرست دوره](../../README.md)

## آموزش

نویسنده شواهد لازم را آماده می‌کند. برای bug، تست بازتولیدکننده باید پیش از fix شکست بخورد و پس از fix قبول شود. درصد coverage به‌تنهایی کیفیت assertion یا پوشش سناریو را نشان نمی‌دهد. مسیر موفق، خطا، ورودی مرزی، retry و دادهٔ قدیمی را متناسب با ریسک در نظر بگیر.

تغییر schema، API، config و feature می‌تواند مستندات یا runbook را منسوخ کند. هر comment یا صفحه‌ای که اکنون رفتار را نادرست می‌گوید، باید اصلاح شود. docs صرفاً نوشتار جانبی نیستند؛ بخشی از قرارداد تیم و مصرف‌کننده‌اند.

پیامد performance، security و scalability را آشکار کن. اثر روی cache، queue، migration، dependency و سرویس‌های وابسته را بسنج. برای migration یا تغییر با deploy حساس، سازگاری نسخه‌ها، rollout، rollback و دادهٔ از قبل ذخیره‌شده را توضیح بده.

## روند پیشنهادی

1. رفتار مورد انتظار و سناریوی شکست را تعریف کن.
2. تستی بنویس که regression را نشان دهد.
3. حالت مرزی و failure dependency را بسنج.
4. docs، config و runbook را به‌روز کن.
5. محدودیت آزمون و ریسک rollout را اعلام کن.

## مثال کاربردی

باگ retry پرداخت: تست یک درخواست را دوبار می‌فرستد و دو سفارش می‌بیند؛ پس از افزودن idempotency key ثابت می‌کند هر دو پاسخ یک سفارش را برمی‌گردانند.

## خطاهای رایج

coverage را جای کیفیت تست نگذار؛ تست بدون assertion اضافه نکن؛ migration را کم‌ریسک فرض نکن؛ ریسک شناخته‌شده را تا review مخفی نکن.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** تست بازتولیدکنندهٔ bug چه می‌کند؟

   1. قبل از fix رفتار غلط را نشان می‌دهد
   2. فقط coverage را بالا می‌برد
   3. فقط mock را صدا می‌زند
   4. هیچ خروجی‌ای ندارد

**پاسخ:** 1 — تست به regression واقعی وصل است.

### پرسش 2

**سؤال:** coverage بالا چه چیزی را تضمین نمی‌کند؟

   1. اجرای برخی خط‌ها
   2. درستی assertionها و پوشش رفتار مهم
   3. وجود گزارش
   4. اجرای pipeline

**پاسخ:** 2 — درصد اجرا کیفیت انتظار را ثابت نمی‌کند.

### پرسش 3

**سؤال:** در migration چه چیزی باید ارزیابی شود؟

   1. فقط lint
   2. دادهٔ قبلی، سازگاری هم‌زمان، کارایی و rollback
   3. رنگ صفحه
   4. نام branch

**پاسخ:** 2 — سرویس‌ها و داده‌ها ممکن است چند نسخه را هم‌زمان داشته باشند.

### پرسش 4

**سؤال:** اگر benchmark انجام نشده چه باید گفت؟

   1. عدد تخمینی ارائه کنیم
   2. عدم انجام را روشن و ریسک را مدیریت کنیم
   3. performance بی‌اهمیت است
   4. شرح را پاک کنیم

**پاسخ:** 2 — ادعای دقیق بهتر از عدد بی‌شاهد است.

## آموزش عمیق: تست باید رفتار را محافظت کند

### «تست دارد» با «تست خوب دارد» فرق می‌کند

تست مفید می‌گوید چه رفتاری انتظار می‌رود و در صورت regression واقعاً شکست می‌خورد. اگر تست فقط می‌گوید تابع X صدا زده شد، ولی خروجی نادرست هم همان فراخوانی را تولید می‌کند، پس رفتار کاربر را محافظت نکرده است. برای bug، ابتدا سناریویی بساز که خطا را بازتولید کند؛ باید پیش از اصلاح fail و پس از اصلاح pass شود. این ترتیب پیوند تست به علت bug را نشان می‌دهد.

چهار نوع تست را بشناس:

- **Unit:** بخش کوچک با dependencyهای محدود؛ سریع، ولی ممکن است integration را نبیند.
- **Integration:** تعامل واقعی‌تر میان اجزا یا دیتابیس را می‌آزماید.
- **Contract:** توافق بین producer و consumer API را بررسی می‌کند.
- **End-to-end:** مسیر کاربر را از ابتدا تا انتها می‌سنجد؛ ارزشمند اما کندتر و شکننده‌تر.

برای یک bug ساده لازم نیست همهٔ انواع را اضافه کنی. نوعی را انتخاب کن که فرضیهٔ اصلی را با کمترین شکنندگی می‌آزماید.

### ساخت ماتریس سناریو

برای endpoint پرداخت یک جدول ذهنی بساز:

| حالت | مثال ورودی/شرط | انتظار |
|---|---|---|
| موفق | پرداخت مجاز و موجودی کافی | یک تراکنش ثبت شود |
| مرزی | مبلغ صفر یا حد بیشینه | رفتار قراردادی روشن باشد |
| خطای dependency | درگاه timeout می‌دهد | سفارش دوباره charge نشود |
| تکرار | client درخواست را retry می‌کند | idempotency حفظ شود |
| دسترسی | کاربر مالک سفارش نیست | داده یا عملیات افشا نشود |

تست همهٔ ترکیب‌های نظری را لازم ندارد. از requirement، سابقهٔ bug و هزینهٔ شکست برای انتخاب استفاده کن. Coverage درصد اجرای کد است؛ به‌تنهایی کیفیت assertion، معنای تست یا پوشش مسیرهای واقعی را ثابت نمی‌کند.

### mock و flakiness

Mock برای کنترل dependency بیرونی یا حالت سخت‌تکرار مفید است. اگر تمام رفتارهای داخلی را mock کنی، تست ممکن است فقط قرارداد ساختگی خودش را ثابت کند. از سوی دیگر، تست integration واقعی هم می‌تواند کند باشد؛ یک مجموعهٔ متعادل لازم است.

تست flaky گاهی سبز و گاهی قرمز می‌شود، بدون تغییر کد. علت ممکن است زمان‌بندی، ترتیب تست، clock، شبکه یا دادهٔ مشترک باشد. flaky test را بی‌تفاوت نادیده نگیر: تکرار هشدار اعتماد تیم به CI را کم می‌کند. در review بپرس pipeline برای آخرین revision اجرا شده؟ آیا این تست به ساعت/ترتیب وابسته است؟ آیا assertion علت شکست را دقیق نشان می‌دهد؟

### مستندات بخشی از قراردادند

مستندات لازم را با اثر تغییر تعیین کن:

- API یا رفتار عمومی عوض شد؟ توضیح، مثال و schema را اصلاح کن.
- تنظیمات جدید اضافه شد؟ مقدار پیش‌فرض، دامنه، امنیت و زمان فعال‌سازی را بنویس.
- migration یا عملیات production عوض شد؟ runbook، rollback و پایش را به‌روز کن.
- comment کد اکنون دروغ می‌گوید؟ آن را اصلاح یا حذف کن؛ comment ناسازگار از نبود comment بدتر است.

### مثال خطای پرداخت

فرضیه: درخواست retry پس از timeout، پرداخت را دو بار ثبت می‌کند. تست بازتولیدکننده یک idempotency key می‌فرستد، پاسخ timeout را شبیه‌سازی می‌کند و همان درخواست را دوباره اجرا می‌کند. انتظار: یک transaction و پاسخ سازگار. پس از fix تست باید سبز شود. اگر فقط می‌سنجی که متد gateway یک بار در mock فراخوانی شده، ممکن است ثبت دوباره در DB را نبینی؛ تست integration یا قید یکتا می‌تواند invariant را بهتر نشان دهد.

### تمرین

برای تغییر migration یک ستون اجباری، سه خطر و آزمون/شاهد مرتبط بنویس. پاسخ نمونه: دادهٔ قدیمی null دارد—migration مرحله‌ای و backfill؛ نسخهٔ جدید و قدیم هم‌زمان فعال‌اند—سازگاری دو نسخه؛ جدول بزرگ است—plan اجرا و زمان/قفل. راه بازگشت نیز باید با مرحله‌ای که migration داده را حذف می‌کند سازگار باشد.

### تسلط یعنی بتوانی…

- assertion را از روی رفتاری که محافظت می‌کند توضیح دهی؛
- نوع تست را بر اساس ریسک انتخاب کنی؛
- محدودیت coverage و mock را بشناسی؛
- تست، docs، migration و rollback را به یک تغییر واحد وصل کنی.
