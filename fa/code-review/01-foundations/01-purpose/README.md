# هدف و مرزهای Code Review

**زبان:** فارسی · [English](../../../../en/code-review/01-foundations/01-purpose/README.md)

> مسیر: [فصل ۱ — هدف، جریان و مدل ذهنی](../README.md) · [فهرست دوره](../../README.md)

## آموزش

بازبینی کد یعنی فردی غیر از نویسنده تغییر را قبل از ادغام بررسی کند. هدف تنها یافتن باگ نیست: سلامت طراحی، فهم‌پذیری، امنیت، انتقال دانش، مالکیت جمعی و ثبت چرایی تصمیم نیز مهم‌اند. review باید به مسئله و معیار پذیرش وصل باشد؛ یک خط جدا از نیاز و معماری ممکن است گمراه‌کننده باشد.

بازبینی تضمین نمی‌کند نرم‌افزار بی‌خطاست. بازبین می‌تواند نکته‌ای را نبیند؛ تست، تحلیل ایستا، مرور انسانی و پایش تولید نقص‌های متفاوتی را می‌یابند. برای همین review بخشی از دفاع چندلایه است، نه جایگزین تست یا rollout امن.

سلیقهٔ فردی قانون پروژه نیست. راهنمای تیم، قرارداد API و ابزارهای خودکار باید style را یکدست کنند. reviewer زمان خود را روی رفتار، طراحی، حالت شکست، داده و ریسک واقعی بگذارد. اگر اطمینان یا زمینه کافی نیست، باید سؤال بپرسد یا متخصص مناسب را دعوت کند.

## روند پیشنهادی

1. مسئله، کاربر و معیار پذیرش را بفهم.
2. تغییر را در زمینهٔ مخزن بخوان، نه به‌صورت قطعهٔ جدا.
3. ادعا را به شواهد و محدودیت review را آشکارا بیان کن.
4. style مکانیکی را خودکار و توجه انسانی را صرف معنای تغییر کن.
5. با تست، تحلیل ابزار و پایش، review را تکمیل کن.

## مثال کاربردی

تغییر API پرداخت شاید چند خط باشد اما سازگاری مصرف‌کننده‌ها را بشکند. در مقابل، اختلاف دربارهٔ فاصله‌گذاری که formatter حل می‌کند نباید مانع ادغام شود.

## خطاهای رایج

review را تضمین بی‌خطایی ندان؛ تعداد کامنت را معیار کیفیت نکن؛ پیشنهاد سلیقه‌ای را blocker معرفی نکن؛ از روی عنوان یا سابقهٔ نویسنده دربارهٔ صحت نتیجه نگیر.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** هدف کامل‌تر بازبینی چیست؟

   1. فقط یافتن همهٔ باگ‌ها
   2. بهبود سلامت تغییر و انتقال دانش در کنار ابزارهای مکمل
   3. جایگزینی تست
   4. اثبات بی‌خطایی

**پاسخ:** 2 — review مفید است اما پوشش کامل یا اثبات رسمی نمی‌دهد.

### پرسش 2

**سؤال:** چه چیزی بهتر است برای style انجام شود؟

   1. بحث سلیقه‌ای در هر PR
   2. style guide و formatter/linter
   3. توقف merge دائمی
   4. حذف تست‌ها

**پاسخ:** 2 — قاعدهٔ مشترک اختلاف تکراری را کم می‌کند.

### پرسش 3

**سؤال:** CI سبز به‌تنهایی چه چیزی را ثابت نمی‌کند؟

   1. کنترل‌های CI اجرا شده‌اند
   2. رفتار همهٔ سناریوهای production درست است
   3. pipeline به پایان رسیده
   4. گزارشی ساخته شده

**پاسخ:** 2 — CI فقط کنترل‌های تعریف‌شده را پوشش می‌دهد.

### پرسش 4

**سؤال:** در صورت نداشتن زمینه چه کنیم؟

   1. فرض کنیم نویسنده اشتباه کرده
   2. سؤال دقیق یا درخواست کمک از متخصص
   3. approve سریع
   4. نویسنده را سرزنش کنیم

**پاسخ:** 2 — زمینه باید پیش از قضاوت روشن شود.

## آموزش عمیق: چرا review می‌کنیم؟

### ۱. خروجی مورد انتظار

پیش از بازکردن diff، یک جمله بنویس: «این تغییر باید باعث شود …» این جمله معیار خواندن کد است. اگر PR می‌گوید «بهبود cache»، باید بتوانی بگویی کدام پاسخ سریع‌تر، برای کدام کاربر و با چه محدودیت تازه‌ای. اگر نتیجه روشن نیست، review از همان‌جا با یک سؤال دربارهٔ هدف شروع می‌شود.

review ارزشمند می‌تواند چند نوع مشکل را پیدا کند:

- **درستی:** رفتار با نیازمندی نمی‌خواند یا حالت خطا ناقص است.
- **امنیت و حریم خصوصی:** کاربر به داده‌ای می‌رسد که مالک آن نیست یا راز در log می‌رود.
- **طراحی و نگه‌داری:** تغییر مسئولیت را در جای نامناسب قرار می‌دهد یا فهم تغییر آینده را سخت می‌کند.
- **سازگاری:** API، schema یا قرارداد رفتاری مصرف‌کنندهٔ قبلی را می‌شکند.
- **شواهد ناکافی:** تست یا rollout نشان نمی‌دهد تغییر در شرایط مهم کار می‌کند.
- **انتقال دانش:** بازبین می‌آموزد یا تصمیم معماری در PR ثبت می‌شود تا نفر بعدی چرایی آن را بفهمد.

این هدف‌ها به معنی نیاز همهٔ PRها به شش دور بازبینی نیست. اولویت به هزینهٔ شکست بستگی دارد: ایراد در نام دکمه کم‌اثر است؛ افشای سند بین دو مشتری می‌تواند بحرانی باشد.

### ۲. review با چه چیزهایی فرق دارد؟

| کار | پرسش اصلی | چه چیزی را خوب پیدا می‌کند | چه چیزی را تضمین نمی‌کند |
|---|---|---|---|
| Code review همتا | آیا تغییر در زمینهٔ سیستم قابل‌قبول است؟ | معنا، طراحی، منطق کسب‌وکار و معماری | نبود همهٔ باگ‌ها |
| تست خودکار | آیا سناریوهای تعریف‌شده انتظار را دارند؟ | regressionهای همان سناریوها | سناریوهای نوشته‌نشده |
| lint و تحلیل ایستا | آیا قواعد ماشینی نقض شده‌اند؟ | الگوهای تکراری و قواعد سبک | منطق تجاری یا سیاست محصول |
| pair programming | آیا دو نفر هنگام ساخت کد بازخورد می‌گیرند؟ | یادگیری حین کار و کشف زودهنگام | آمادگی همهٔ رفتارها برای انتشار |
| تست پذیرش/QA | آیا جریان مشخص کاربر در محیط آزمون درست است؟ | خطاهای end-to-end همان جریان | همهٔ ترکیب‌های محیط و بار واقعی |

این روش‌ها مکمل‌اند. تست می‌تواند ثابت کند کاربر A به سفارش B دسترسی ندارد؛ بازبین هم می‌سنجد که آیا آزمون واقعاً مرز tenant را بررسی می‌کند و آیا endpoint مشابه دیگری جا افتاده است.

### ۳. معیار کیفیت چیست؟

«کامل و بی‌نقص» معیار عملی نیست. معیار قابل‌استفاده این است: آیا تغییر سلامت سیستم را بهتر می‌کند و آیا ریسک شناخته‌شده‌ای دارد که باید پیش از merge مهار شود؟ ممکن است پیاده‌سازی جای polish داشته باشد اما به‌اندازهٔ کافی واضح و امن باشد. reviewer باید blocker را از فرصت بهبود جدا کند؛ وگرنه review به انتظار کمال تبدیل می‌شود و تیم یاد می‌گیرد آن را دور بزند.

### مثال حل‌شده

فرض کن endpoint دریافت سفارش، شناسه را از URL می‌گیرد و فقط احراز هویت را بررسی می‌کند. هدف PR «اضافه‌کردن صفحهٔ جزئیات سفارش» است.

1. شرط کاربر را روشن کن: کاربر فقط باید سفارش‌های حساب خودش را ببیند.
2. مسیر داده را دنبال کن: آیا query هم orderId و هم tenantId کاربر فعلی را محدود می‌کند؟
3. تست منفی بخواه: کاربر A با شناسهٔ سفارش B نباید اطلاعات مجاز بگیرد.
4. اگر ایراد تأیید شد، آن را blocker و با پیامد افشای داده بیان کن.
5. نام متغیر و import را تا بعد از مسئلهٔ دسترسی کنار بگذار.

### تمرین خودآموز

PR فرضی‌ای دارد که تغییر متن دکمه و migration دیتابیس را با هم انجام می‌دهد. چه چیزهایی را review می‌کنی و چه چیزی را به ابزار می‌سپاری؟

**پاسخ پیشنهادی:** دو هدف مستقل را جدا کن؛ متن را با تست UI یا بازبینی محصول بسنج؛ migration را از نظر دادهٔ قبلی، سازگاری نسخه‌ها، زمان اجرا و rollback بررسی کن؛ formatter را خودکار اجرا کن. معیار، اثر هر تغییر است نه تعداد خط.

### تسلط یعنی بتوانی…

- بگویی چرا review لازم است و چه خطری را هدف گرفته؛
- توضیح بدهی تست و ابزار چه چیزی را پوشش داده‌اند و چه چیزی را نه؛
- برای هر کامنت اثر قابل‌توضیحی پیدا کنی؛
- دربارهٔ ریسک باقیمانده تصمیم آگاهانه بگیری، نه این‌که انتظار کمال داشته باشی.
