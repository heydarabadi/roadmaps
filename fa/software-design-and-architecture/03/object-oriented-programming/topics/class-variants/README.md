## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

گونه‌های کلاس روش‌هایی برای مدل‌کردن حالت‌ها و تفاوت رفتارند: subclass، composition، sum type یا strategy؛ انتخاب باید حالت نامعتبر را کم کند.

## مثال کاربردی

روش ارسال با `StandardDelivery` و `Pickup` مدل می‌شود و فقط گزینه‌های مجاز در هر سفارش ساخته می‌شوند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «برنامه‌نویسی شیءگرا» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** یک کلاس برای هر ترکیب ممکن، انفجار تعداد نوع می‌سازد؛ enum ساده گاهی کافی است.
- **بازبینی:** booleanهای قابل‌ترکیب را به مدل حالتی تبدیل کن تا ترکیب نامعتبر ممکن نباشد.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: گونه‌های کلاس روش‌هایی برای مدل‌کردن حالت‌ها و تفاوت رفتارند: subclass، composition، sum type یا strategy؛ انتخاب باید حالت نامعتبر را کم کند.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: روش ارسال با `StandardDelivery` و `Pickup` مدل می‌شود و فقط گزینه‌های مجاز در هر سفارش ساخته می‌شوند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: یک کلاس برای هر ترکیب ممکن، انفجار تعداد نوع می‌سازد؛ enum ساده گاهی کافی است.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: booleanهای قابل‌ترکیب را به مدل حالتی تبدیل کن تا ترکیب نامعتبر ممکن نباشد.

## آموزش تکمیلی مستقل

#### Entity، value و class variant

Entity با identity پایدار و lifecycle خود شناخته می‌شود؛ ایمیل مشتری عوض شود، CustomerId همان است. Value object بر اساس مقدار معنا دارد؛ Money(100, USD) با Money(100, USD) برابر است، اما 100 USD با 100 EUR برابر نیست. value object معمولاً تغییرناپذیر است و invariant را هنگام ساخت می‌گیرد.

حالت‌ها و variantها را طوری مدل کن که ترکیب نامعتبر کم شود. دو Boolean می‌توانند چهار ترکیب بسازند که شاید فقط یکی مجاز باشد. enum، tagged union، subclass یا composition را بر اساس تعداد حالت‌ها، رفتار مستقل و جهت تغییر انتخاب کن؛ کلاس بیشتر همیشه مدل بهتر نیست.

## نمونهٔ کد مرحله‌ای

از subtype وقتی استفاده کن که نوع‌های گوناگون واقعاً قرارداد رفتاری مشترک و قابل جانشینی دارند. برای چند flag که حالت‌های نامعتبر می‌سازند، نوع‌های محدود یا discriminated union روشن‌ترند. اضافه‌کردن variant باید رفتار مصرف‌کننده را قابل پیش‌بینی نگه دارد.
**تمرین با پاسخ:** به‌جای سه boolean برای پرداخت، بساز Pending، Authorized و Captured را به‌صورت نوع‌های متمایز؛ هر انتقال نامعتبر را در مدل رد کن.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا تصمیم طراحی روشن بماند.

~~~csharp
public abstract record PaymentState;
public sealed record Pending : PaymentState;
public sealed record Authorized(string Reference) : PaymentState;
public sealed record Captured(string Reference, Money Amount) : PaymentState;

public sealed record Payment(PaymentState State);
~~~
