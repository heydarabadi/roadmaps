# فصل 09: الگوهای نرم‌افزار سازمانی — Enterprise Patterns


> **زبان:** [نسخهٔ انگلیسی](../../en/09/enterprise-patterns/README.md)

> [ورود به درس کامل الگوهای سازمانی](lessons.md) — DTO، Repository، ORM، Entity، Value Object و سایر موضوع‌ها با مثال سفارش و پاسخ‌نامه.

## هدف یادگیری

- الگوهای سازمانی پل میان منطق دامنه، تعامل کاربرد و ذخیره‌سازی‌اند. این الگوها قراردادهای ساده‌ای برای query، persistence و مرز API می‌دهند اما در صورت ترکیب مکانیکی، لایه‌سازی اضافی می‌سازند.
- بتوانی میان مسئله، الگو و هزینهٔ عملیاتی تمایز بگذاری.
- برای یک تصمیم، مثال، مبادله و معیار بازبینی بنویسی.

## ایدهٔ مرکزی فصل

الگوهای سازمانی پل میان منطق دامنه، تعامل کاربرد و ذخیره‌سازی‌اند. این الگوها قراردادهای ساده‌ای برای query، persistence و مرز API می‌دهند اما در صورت ترکیب مکانیکی، لایه‌سازی اضافی می‌سازند. این فصل را همراه با فصل‌های مجاور بخوان: طراحی شیء و اصول، کیفیت کد را درون جزء بهتر می‌کنند؛ سبک و الگوی معماری رابطهٔ چند جزء و مرزهای استقرار را شکل می‌دهند؛ الگوهای سازمانی اغلب درون این مرزها اجرا می‌شوند.

## نقشهٔ مفهومی و درس‌های مستقل

- [شیء انتقال داده (DTO) — Data Transfer Object (DTO)](topics/dto/README.md) — DTO داده را از یک مرز عبور می‌دهد و شکل آن برای API، view یا پیام بهینه می‌شود؛ باید از مدل دامنه و entity persistence جدا دیده شود.
- [نقشهٔ هویت — Identity Map](topics/identity-map/README.md) — در یک واحد کاری، identity map تضمین می‌کند یک ردیف/شناسه به یک نمونهٔ شیء در حافظه نگاشت شود و بارگذاری تکراری به نمونهٔ دیگری نینجامد.
- [موارد کاربرد — Use Cases](topics/use-cases/README.md) — use case یک هدف قابل مشاهدهٔ کاربر یا سامانه را هماهنگ می‌کند؛ orchestration و مرز تراکنش را نگه می‌دارد اما قواعد دامنه را تصاحب نمی‌کند.
- [مخزن‌ها (Repository) — Repositories](topics/repositories/README.md) — repository مجموعه‌ای از aggregateهای دامنه را مانند collection قابل پرس‌وجو/ذخیره‌سازی عرضه می‌کند و جزئیات persistence را پنهان می‌کند.
- [نگاشت‌گرها (Mappers) — Mappers](topics/mappers/README.md) — mapper تبدیل میان دو مدل مستقل را انجام می‌دهد؛ مدل‌ها می‌توانند DTO، دامنه، persistence یا پیام باشند.
- [اسکریپت تراکنش — Transaction Script](topics/transaction-script/README.md) — Transaction Script منطق یک عملیات کسب‌وکار را در رویه‌ای سازمان می‌دهد؛ برای عملیات ساده و تراکنش‌محور کم‌هزینه است.
- [فرمان‌ها و پرس‌وجوها — Commands and Queries](topics/commands-queries/README.md) — command درخواست تغییر است و query پاسخ می‌خواند بدون تغییر state؛ قراردادشان side effect، validation و پاسخ را شفاف می‌کند.
- [اشیای ارزشی — Value Objects](topics/value-objects/README.md) — value object با مقدار و معنا شناخته می‌شود نه شناسهٔ مستقل؛ معمولاً immutable است و invariant را در ساختن حفظ می‌کند.
- [مدل دامنه — Domain Models](topics/domain-model-enterprise/README.md) — در الگوهای سازمانی، domain model رفتار و قواعد پیچیده را کنار مفاهیم دامنه نگه می‌دارد؛ گزینه‌ای در برابر transaction script است.
- [موجودیت‌ها (Entities) — Entities](topics/entities/README.md) — entity هویت پایدار دارد و ویژگی‌هایش در طول زمان تغییر می‌کنند؛ هویت، lifecycle و invariantهای مجاز مهم‌اند.
- [نگاشت‌گر شیء-رابطه‌ای (ORM) — Object-Relational Mappers (ORMs)](topics/orms/README.md) — ORM تفاوت مدل شیء و رابطه را پنهان/مدیریت می‌کند و query، identity، transaction و mapping را آسان می‌سازد.

## توضیح یکپارچهٔ فصل

برای هر تصمیم سه سؤال را جواب بده: **چه چیزی تغییر می‌کند؟ چه کسی مالک قاعده/داده است؟ و کدام ویژگی کیفی اهمیت دارد؟** سپس سطح راه‌حل را انتخاب کن: تابع و نوع، مرز ماژول، سرویس، صف یا مدل داده. این ترتیب کمک می‌کند نام الگو جای شناخت مسئله را نگیرد.

توضیح‌ها و مثال‌های هر مفهوم در فایل مستقل بالا آمده‌اند. برای مقایسه، نمونهٔ زیر عمداً یک مسئلهٔ مشترک را با چند سطح طراحی نشان می‌دهد: در فروشگاه، قانون لغو سفارش یک قاعدهٔ دامنه‌ای است؛ جداکردن آن از کنترلر مرز درون‌برنامه‌ای می‌سازد؛ اگر تیم و چرخهٔ انتشار مستقل شوند شاید component کافی باشد؛ اگر داده و بار و مالکیت مستقل باشند جداسازی سرویس بررسی می‌شود. هر مرحله نیازمند شاهد تازه است و مرحلهٔ بعدی را خودکار توجیه نمی‌کند.

## مطالعهٔ موردی و تجربهٔ صنعتی مستند

کاتالوگ Fowler الگوهای Repository، Identity Map و Data Mapper را برای مسائل نگاشت شیء و دیتابیس مستند می‌کند. راهنمای Microsoft برای سرویس سفارش eShopOnContainers نمونهٔ آموزشی از DTO، command/query، repository و مدل دامنه است. این منابع کاربرد را نشان می‌دهند، اما نباید آن‌ها را حکم استفاده در همهٔ پروژه‌ها دانست.

- [Martin Fowler؛ Enterprise Application Architecture catalog](https://martinfowler.com/eaaCatalog/index.html) — گزارش/منبع اصلی یا مرجع مرتبط با تجربهٔ مستند.
- [Microsoft Learn؛ مدل دامنه و لایهٔ زیرساخت](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice) — گزارش/منبع اصلی یا مرجع مرتبط با تجربهٔ مستند.

**روش خواندن مطالعهٔ موردی:** مسئلهٔ اولیه، محدودیت workload، گزینه‌های ردشده، هزینهٔ ارتباط و پیامد بعدی را استخراج کن. عدد یا تصمیم گزارش‌شده را به کل شرکت و همهٔ سامانه‌ها تعمیم نده.

## نمونهٔ کد یا قرارداد

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Money:
    amount: int
    currency: str

@dataclass(frozen=True)
class OrderSummaryDto:
    order_id: str
    total: Money
```

value object و DTO دو مسئولیت دارند: حفظ معنای مقدار دامنه و انتقال نمای محدود داده.

## دام‌ها و سوءبرداشت‌ها

- الگو را از روی ترند انتخاب‌کردن، پیش از شناخت فشار طراحی.
- یک ساختار را همه‌جا تحمیل‌کردن؛ حتی وقتی پیچیدگی دامنه و چرخهٔ تغییر متفاوت است.
- نمونهٔ واقعی یک سازمان را بدون workload، تیم، هزینه و تاریخچه کپی‌کردن.
- بهینه‌سازی برای شاخص ساده‌ای مثل تعداد کلاس، سرویس یا خط کد به‌جای هدف محصول.

## کوییز جامع فصل با پاسخ‌نامه

1. مفهوم اصلی این فصل را چگونه برای یک سامانهٔ سفارش توضیح می‌دهی؟ از یکی از موضوع‌ها نام ببر و مسئله‌اش را بیان کن.
   - پاسخ/معیار ارزیابی: الگوهای سازمانی پل میان منطق دامنه، تعامل کاربرد و ذخیره‌سازی‌اند. این الگوها قراردادهای ساده‌ای برای query، persistence و مرز API می‌دهند اما در صورت ترکیب مکانیکی، لایه‌سازی اضافی می‌سازند.
2. در سناریویی که API سفارش `OrderSummaryDto` را با فیلدهای لازم موبایل برمی‌گرداند، نه کل graph موجودیت را. چه trade-offی را پیش از انتخاب می‌سنجی؟
   - پاسخ/معیار ارزیابی: DTO داده را از یک مرز عبور می‌دهد و شکل آن برای API، view یا پیام بهینه می‌شود؛ باید از مدل دامنه و entity persistence جدا دیده شود. mapping و نسخه‌بندی فیلدها هزینه دارد.
3. یک مورد از این فصل را انتخاب کن که ممکن است over-engineering شود؛ چه نشانه‌ای باعث می‌شود آن را حذف یا ساده کنی؟
   - پاسخ/معیار ارزیابی: وقتی abstraction یا عملیات/نگهداری از نیاز مشاهده‌شده بیشتر می‌شود، ساده‌سازی را انتخاب کن؛ YAGNI و دادهٔ واقعی را راهنما بگیر.
4. برای یکی از تصمیم‌های فصل، چه آزمون یا سنجه‌ای نشان می‌دهد طراحی بهبود یافته است?
   - پاسخ/معیار ارزیابی: آزمون‌های رفتار/قرارداد، زمان تغییر، نرخ خطا، latency یا هزینه را با توجه به هدف انتخاب کن و قبل/بعد را مقایسه کن.
5. کدام بخش سناریوی مستند فصل را می‌توان به مسئلهٔ خودت تعمیم داد و کدام بخش وابسته به زمینهٔ همان شرکت است?
   - پاسخ/معیار ارزیابی: اصل مسئله و trade-off را تعمیم بده؛ فناوری، بار و ساختار سازمانی شرکت را بدون شواهد کپی نکن.
6. رابط یا مرزی را طراحی کن که تغییر یک مسئولیت را از بقیه جدا کند؛ توضیح بده این مرز کدام نوع coupling را کم می‌کند.
   - پاسخ/معیار ارزیابی: ORM تفاوت مدل شیء و رابطه را پنهان/مدیریت می‌کند و query، identity، transaction و mapping را آسان می‌سازد.

## تمرین عملی

یک سیستم کوچک فروش، رزرو یا صدور فاکتور انتخاب کن. برای سه نیازمندی پرتغییر، نقشهٔ مسئولیت‌ها را بکش؛ یک قرارداد و آزمون بنویس؛ سپس توضیح بده چرا فعلاً از مرز انتخاب‌شده استفاده می‌کنی و چه نشانه‌ای باعث می‌شود آن را تغییر بدهی. تمرین را با [قالب ADR](https://adr.github.io/) ثبت کن.
