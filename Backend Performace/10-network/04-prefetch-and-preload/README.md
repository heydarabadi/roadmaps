# ۱۰.۴ — Prefetch و Preload؛ شروع زودتر با بودجه مشخص

**زبان:** فارسی · [نسخهٔ انگلیسی](README.en.md)  

**هدف یادگیری:** دریافت زودهنگام منبع لازم همین صفحه را از حدس نیاز آینده جدا کنید، سود احتمالی و بایت تلف‌شده را بسنجید و کار حدسی Backend را محدود نگه دارید. پیش‌نیاز: HTTP Cache، مسیر بحرانی و Deadline. بررسی منابع: **۲۰۲۶-۱۱-۱۱**؛ مثال‌ها آموزشی و اجرا‌نشده‌اند.

## مدل ذهنی

شروع زودتر، زمان کشف/انتظار را جابه‌جا می‌کند؛ حجم یا کار لازم را الزاماً کم نمی‌کند. یک منبع بی‌استفاده همچنان bandwidth، حافظه، باتری یا ظرفیت Origin مصرف می‌کند. [راهنمای web.dev](https://web.dev/learn/performance/resource-hints) این hintها را برای هدف‌های متفاوت توضیح می‌دهد:

| سازوکار | قصد | نمونه | هزینه/محدودیت |
| --- | --- | --- | --- |
| preload | منبع معلوم و حیاتی برای همین صفحه، با کشف دیرهنگام | تصویر LCP در CSS | رقابت با منابع حیاتی دیگر؛ استفاده واقعی باید مطابق درخواست باشد |
| prefetch | منبع محتمل برای navigation آینده | سند عمومی مرحله بعد راهنما | حدس ممکن است غلط باشد؛ Browser می‌تواند آن را انجام ندهد |
| preconnect | آماده کردن اتصال به Origin مهم | میزبان فونت | داده را نمی‌گیرد؛ اتصال اضافی هزینه دارد |
| پیش‌دریافت داده در Backend | آماده کردن read محتمل برای مرحله بعد | گزینه‌های ارسالِ قابل بازسازی | هزینه Query، تازگی، مجوز و اتلاف |

Preload به‌تنهایی CSS را اعمال یا Script را اجرا نمی‌کند؛ مصرف‌کننده اصلی هنوز باید منبع را بخواهد. URL، نوع درخواست `as` و حالت CORS/credentials باید با مصرف بعدی سازگار باشند، وگرنه دریافت دوباره ممکن است رخ دهد. برای فونت حتی هم‌مبدأ، الگوی CORS و `crossorigin` مناسب لازم است. ماژول JavaScript سازوکار `modulepreload` دارد؛ همه نوع منبع را با یک hint فرض نکنید. جزئیات در [MDN preload](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/preload) است.

### تصمیم را با سه آزمون بگیرید

۱. **آیا منبع حیاتی همین صفحه است یا فقط شاید بعداً لازم شود؟** نیاز قطعی اما دیرکشف‌شده می‌تواند نامزد `preload` باشد؛ مسیر محتمل بعدی نامزد `prefetch` است. اتصال به origin مهم، بدون گرفتن محتوا، نامزد `preconnect` است.

۲. **چه مقدار زمان واقعاً پنهان می‌شود؟** شروع زودتر می‌تواند بخشی از مدت دریافت را با پردازش/رندر یا زمان حرکت کاربر هم‌پوشان کند. اگر منبع بعداً کشف می‌شد یا به‌هرحال موازی بارگیری می‌شد، سود واقعی کمتر است. زمان کل کار لزوماً کم نمی‌شود؛ ممکن است فقط زمان کاربر تا محتوای قابل‌مشاهده بهتر شود.

۳. **هزینهٔ حدس از بودجه می‌گذرد؟** برای preload، رقابت با منابع مهم‌تر صفحه را اندازه بگیرید؛ برای prefetch، احتمال استفاده قبل از منقضی‌شدن، بایت تلف‌شده، cache pollution، محدودیت مصرف داده و فشار Origin را بسنجید. با overload ابتدا کار حدسی را قطع کنید.

یک معیار سادهٔ تصمیم، اندازه‌گیری جداگانهٔ دو سمت است: (الف) درصد مواجهه‌هایی که منبع حدسی واقعاً مصرف شد و زمان انتظار پنهان‌شده، (ب) بایت بی‌مصرف و تغییر عملکرد منابع حیاتی. میلی‌ثانیه و بایت را بدون مدل محصول از هم کم نکنید؛ آن‌ها را با هدف تجربه و بودجهٔ شبکه/دستگاه مقایسه کنید.

## مثال مرورگر و ترتیب انتخاب

فرض: تصویر ثابت پس‌زمینه، محتوای اصلی همین صفحه است و CSS آن را دیر آشکار می‌کند؛ راهنمای مرحله بعد نیز عمومی و بدون side effect است:

</div>

```html
<link rel="preload" href="/assets/hero.a1b2c3.avif"
      as="image" type="image/avif" fetchpriority="high">
<link rel="prefetch" href="/guide/step-2.html">
<style>
  .hero { background-image: url('/assets/hero.a1b2c3.avif'); }
</style>
```

<div dir="rtl" align="right">

این مثال تضمین زمان‌بندی Browser نیست؛ در حالت واقعی CSS می‌تواند فایل جدا باشد. ابتدا با Waterfall منبع حیاتی دیرکشف‌شونده را شناسایی کنید؛ اگر تصویر از ابتدا در HTML آشکار است، preload ممکن است فایده افزوده‌ای نداشته باشد. برای تصویر responsive، منبع متناسب viewport و درخواست واقعی را هماهنگ کنید. سپس فقط نیاز آینده با احتمال مصرف بالا را در بودجه جدا بررسی کنید. رفتار browser، cache partitioning، TTL و تنظیم کاهش مصرف داده می‌تواند reuse را محدود کند؛ دریافت prefetch تضمین استفاده در navigation بعد نیست.

## مثال عددی و Backend

مدل **فرضی**: به ۱۰۰ کاربر، منبع عمومی ۲۰۰ KiB را پیش‌دریافت می‌کنیم؛ ۷۰ نفر پیش از انقضا آن را مصرف می‌کنند. دانلود حدسی کل ۲۰٬۰۰۰ KiB و بخش بی‌مصرف ۶٬۰۰۰ KiB، حدود ۵٫۸۶ MiB است. اگر هر مصرف واقعاً ۱۲۰ ms انتظار را پنهان کند، سود مجموع مدل `70*120=8400 ms` و میانگین بر ۱۰۰ مواجهه ۸۴ ms است؛ نه سود ۱۲۰ ms برای همه. هزینه رقابت با صفحه فعلی در این محاسبه نیست و می‌تواند سود را معکوس کند.

در Backend، بعد از نمایش سبد شاید «گزینه‌های ارسال» زودتر خوانده شود؛ این داده جای قیمت نهایی/رزرو موجودی قطعی را نمی‌گیرد. این سازوکار با HTML prefetch یک API واحد ندارد. سیاست پیشنهادیِ مفهومی:

</div>

```text
if likely_next_step and spare_capacity and speculative_budget_available:
    data = read_authorized_shipping_options(user_context, short_deadline)
    store_bounded(user_scoped_key(cart_version, address_version), data, short_ttl)

on_actual_checkout:
    recheck_authorization_and_versions()
    use_if_fresh_or_fetch_normally()
    validate_final_price_and_stock_at_commit()
```

<div dir="rtl" align="right">

حد تعداد/بایت، concurrency و Deadline را برای کار حدسی جدا کنید و هنگام overload آن را متوقف کنید. Context و کلید باید کاربر/tenant و نسخه ورودی را حفظ کنند. با انصراف، در صورت نبود مصرف‌کننده دیگر کار را لغو کنید. دریافت زودهنگام نباید سفارش، پرداخت یا تغییر وضعیت بسازد؛ endpoint دارای side effect را برای حدس navigation صدا نزنید. مجوز و قواعد عملیات واقعی دوباره بررسی می‌شوند.

## کاربرد، تمرین و انتظار

برای منبع حیاتی دیرکشف‌شونده یا مسیر آینده قابل‌پیش‌بینی مناسب است. برای ویدئوی بزرگ کم‌احتمال، API شخصی بدون قرارداد کش، کاربر با محدودیت داده یا پایین‌دست اشباع انتخاب ضعیفی است. Cache pollution یعنی داده حدسی کم‌ارزش، داده مفید را بیرون می‌راند؛ hit بالاتر بدون اندازه‌گیری بایت مصرف‌شده کافی نیست.

**تمرین:** احتمال مصرف را در مدل از ۷۰٪ به ۲۰٪ کم کنید. **انتظار:** ۸۰ منبع بی‌مصرف، برابر ۱۶٬۰۰۰ KiB یا ۱۵٫۶۲۵ MiB داریم؛ سود میانگین مدل فقط ۲۴ ms بر مواجهه است. سپس TTL را کوتاه‌تر از زمان رفتن کاربر به مرحله بعد بگذارید؛ دریافت مجدد ممکن است سود را حذف کند. در یک Waterfall فرضی، یک preload مفید و یک prefetch مزاحم منبع LCP را مشخص کنید. این اعداد آزمایش واقعی نیستند.

**حل تمرین:** از ۱۰۰ کاربر، ۲۰ نفر منبع را مصرف می‌کنند؛ پس ۸۰ دانلود تلف می‌شود: `80×200=16,000 KiB` که با `1024 KiB/MiB` برابر تقریباً `15.625 MiB` است. سود انتظاریِ زمان در مدل `0.20×120=24 ms` به ازای هر مواجهه است، نه ۱۲۰ ms برای همه. اگر TTL قبل از navigation تمام شود یا دانلود رقیب تصویر LCP شود، این سود می‌تواند کمتر شود؛ پس قبل/بعد را با Waterfall، نرخ مصرف prefetch، زمان LCP و بایت شبکه مقایسه کنید.

## شاهد عملیاتی و حدود شواهد

[راهنمای web.dev درباره prefetch](https://web.dev/articles/link-prefetch) کاربرد برای navigation آینده و هزینه بایت اضافی را مستند می‌کند؛ [MDN preload](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/preload) دریافت پیش از کشف عادی را توضیح می‌دهد. این‌ها سند عملیاتی Browser هستند. مطالعه تولیدی مستقیمی که سود همین سناریوی ۱۰۰کاربری یا Backend ارسال را ثابت کند در منابع این درس ارائه نشده؛ مثال‌ها فرضی‌اند و بهبود تضمین نمی‌شود.

## عیب‌یابی نتیجهٔ واقعی

- اگر در Network دو دانلود برای یک URL می‌بینید، URL، `as`، credentials/CORS، redirect و variant responsive را میان preload و مصرف‌کننده تطبیق دهید.
- اگر هشدار preload بلااستفاده است، منبع واقعاً دیرکشف‌شده و حیاتی نیست یا markup/route مصرف‌کننده در همه حالت‌ها اجرا نمی‌شود؛ hint را به‌جای نگه‌داشتنِ بی‌دلیل حذف کنید.
- اگر prefetch مصرف نمی‌شود، نرخ navigation واقعی، TTL، cache policy، انتخاب کاربر و محدودیت browser را جدا کنید؛ شروع دانلود را معادل استفاده نشمارید.
- اگر LCP یا p99 backend افت کرده است، priority و پهنای باند رقابت‌کننده، مصرف Origin، concurrency کار حدسی و بار real user را در همان بازه مقایسه کنید؛ hint را کم یا متوقف کنید و baseline را دوباره بگیرید.

## شکست‌ها و چک‌لیست

دریافت تکراری یک URL، هشدار preload بی‌استفاده، رشد egress، افت hit داده مفید، p99 بدترِ درخواست واقعی و خواندن داده کهنه سیگنال بررسی‌اند. حذف hint باید تجربه پایه صحیح را باقی بگذارد؛ کاربر نباید برای دریافت پاسخ درست به اجرای حدس قبلی وابسته باشد.

- [ ] preload برای نیاز معلومِ همین صفحه و prefetch برای نیاز محتمل آینده است.
- [ ] URL، as، CORS و مصرف واقعی سازگارند؛ Browserهای هدف بررسی می‌شوند.
- [ ] احتمال استفاده پیش از انقضا و بایت مفید/تلف‌شده ثبت می‌شوند.
- [ ] سقف بایت/زمان/هم‌زمانی و سیاست کاهش مصرف داده وجود دارد.
- [ ] کار حدسی زیر overload قربانی می‌شود و ظرفیت کار واقعی را نمی‌گیرد.
- [ ] مجوز، tenant، نسخه داده و نبود side effect حفظ می‌شوند.
- [ ] LCP/تأخیر مرحله بعد، خطا، هزینه Origin و cache pollution با هم سنجیده می‌شوند.

## خودآزمایی

۱. برای تصویر حیاتی همین صفحه که در CSS دیر کشف می‌شود کدام hint نامزد است؟

۲. آیا prefetch وعده می‌دهد کاربر حتماً صفحه بعد را می‌بیند؟

۳. چرا as یا CORS ناهماهنگ می‌تواند هزینه بسازد؟

۴. در احتمال ۲۰٪، چند KiB از مدل ۱۰۰کاربری بی‌مصرف است؟

۵. چرا گزینه ارسال پیش‌دریافت‌شده مجوز پرداخت قطعی نیست؟

۶. اگر p99 کار واقعی زیر بار بدتر شد، با کار حدسی چه می‌کنید؟

### پاسخ با دلیل

۱. preload؛ نیاز معلوم همین صفحه است، به شرط اندازه‌گیری تأخیر کشف و هماهنگی منبع مصرف‌شده.

۲. خیر؛ حدس است و حتی Browser ممکن است دریافت را اجرا نکند یا کش بعداً قابل reuse نباشد.

۳. درخواست مصرف‌کننده ممکن است با دریافت اولیه تطابق نداشته باشد و دوباره دانلود کند.

۴. `80*200=16000 KiB`؛ فقط ۲۰ نفر مصرف می‌کنند و منابع ۸۰ نفر بی‌استفاده می‌مانند.

۵. داده می‌تواند کهنه یا ورودی سبد/آدرس عوض شده باشد؛ قواعد مجوز، قیمت و موجودی عملیات واقعی باید برقرار باشند.

۶. آن را محدود/متوقف می‌کنیم و بودجه را بازبینی می‌کنیم؛ سود حدسی نباید ظرفیت کار لازم را بخورد.
