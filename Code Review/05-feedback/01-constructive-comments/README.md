# کامنت مشخص و سازنده

**زبان:** فارسی · [English](../../en/05-feedback/01-constructive-comments/README.md)

> مسیر: [فصل ۵ — بازخورد، شدت و اختلاف](../README.md) · [فهرست دوره](../../README.md)

## آموزش

کامنت خوب رفتار مشخص، پیامد و درخواست/سؤال را می‌گوید. به کد نقد کن، نه به نویسنده. اگر راه‌حل روشن است نمونه بده؛ اگر context نداری پرسش باز بپرس. شدت را بیان کن تا نویسنده بداند چه چیزی مانع merge است.

لحن و شواهد مهم‌اند. «این race condition قطعاً هست» فقط وقتی بنویس که مسیرش را نشان داده‌ای. جملهٔ بهتر: «اگر دو درخواست هم‌زمان برسند، هر دو ممکن است شرط را ببینند؛ آیا constraint دیتابیس invariant را تضمین می‌کند؟» فرض کن نویسنده محدودیتی می‌داند که تو هنوز ندیده‌ای. سؤال محترمانه می‌تواند بهتر از دستور باشد.

در پایان، خلاصهٔ review بده: blockers، سؤال‌ها و موارد غیرمسدودکننده. قدردانی از راه‌حل خوب هم می‌تواند الگوی ارزشمند را بین اعضا پخش کند.

review برای بهترشدن سلامت کد است، نه رسیدن به کمال خیالی؛ میان بهبود فوری و هزینهٔ بلندمدت تعادل بگذار. Pair programming می‌تواند مکمل review باشد، مخصوصاً برای یادگیری یا طراحی مبهم. اگر در جریان گفت‌وگو شواهد تازه دیدی، بازخورد خودت را اصلاح کن.

## روند پیشنهادی

1. خط و رفتار دقیق را نشان بده.
2. اثر یا خطری که می‌بینی توضیح بده.
3. درخواست یا سؤال کوچک و قابل‌پاسخ بنویس.
4. قطعیت و شدت را با شواهد تنظیم کن.
5. review را با جمع‌بندی وضعیت تمام کن.

## مثال کاربردی

ضعیف: «این افتضاح است.» بهتر: «check و update جدا اجرا می‌شوند؛ دو درخواست هم‌زمان ممکن است سفارش را دوبار ثبت کنند. آیا transaction یا unique constraint این invariant را حفظ می‌کند؟»

## خطاهای رایج

«بهترش کن» ننویس؛ sarcasm نکن؛ نیت نویسنده را حدس نزن؛ دربارهٔ موضوع نامطمئن ادعای قطعی نکن.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** قالب کامنت قابل اقدام چیست؟

   1. قضاوت شخصی
   2. رفتار + اثر + درخواست/سؤال
   3. فقط غلط است
   4. پاراگراف دربارهٔ کل پروژه

**پاسخ:** 2 — جزئیات کمک می‌کند نویسنده مسئله را اصلاح کند.

### پرسش 2

**سؤال:** در صورت ابهام چه کنیم؟

   1. قطعیت ساختگی
   2. سؤال دربارهٔ invariant و شاهد
   3. سکوت
   4. سرزنش

**پاسخ:** 2 — ابهام باید به پرسش روشن تبدیل شود.

### پرسش 3

**سؤال:** چرا جمع‌بندی review لازم است؟

   1. طولانی‌شدن
   2. تفکیک blocker و پیشنهاد و وضعیت کلی
   3. تکرار diff
   4. حذف خط‌کامنت

**پاسخ:** 2 — نویسنده خروجی قابل‌اقدام می‌گیرد.

### پرسش 4

**سؤال:** کدام جمله محترمانه‌تر است؟

   1. چرا همیشه این‌طور خراب می‌کنی؟
   2. آیا محدودیتی هست که باعث این انتخاب شده؟
   3. این را بلد نیستی
   4. بدون بحث عوض کن

**پاسخ:** 2 — در مورد کد و زمینه می‌پرسد، نه شخصیت.

## آموزش عمیق: comment را طوری بنویس که پاسخ‌پذیر باشد

### چهار جزء یک بازخورد روشن

1. **مشاهده:** به رفتار یا خطی مشخص اشاره کن؛ نه به شخصیت نویسنده.
2. **پیامد:** توضیح بده چه می‌تواند برای کاربر، داده یا نگه‌داری رخ دهد.
3. **درخواست:** تغییر مشخص، سؤال یا شواهدی که می‌خواهی روشن شود.
4. **شدت/قطعیت:** بگو blocking است یا اختیاری و چقدر از فرض خود مطمئنی.

مثال: «اگر دو job هم‌زمان این رکورد را بخوانند، هر دو ممکن است آن را آزاد ببینند و دوبار پردازش کنند. آیا قید یکتا یا transaction این invariant را تضمین می‌کند؟ اگر نه، لطفاً تست هم‌زمانی اضافه کن.» جمله رفتار، اثر و درخواست را دارد و پاسخ‌پذیر است.

### از حکم به مشاهده برس

| واکنش مبهم/تند | نسخهٔ مفیدتر |
|---|---|
| «این خیلی بد است.» | «این query برای هر ردیف جدا اجرا می‌شود؛ روی صفحهٔ ۵۰۰ ردیفی ممکن است ۵۰۰ درخواست DB بسازد. آیا batch کردن مناسب است؟» |
| «چرا این را این‌طور نوشتی؟» | «کدام محدودیت باعث انتخاب این concurrency model شد؟ من نگرانی race دارم.» |
| «بهترش کن.» | «وقتی token منقضی است، این مسیر چه پاسخی می‌دهد؟ لطفاً انتظار را با یک تست مشخص کن.» |
| «حتماً باگ دارد.» | «من هنوز proof ندارم، اما این دو عملیات بدون transaction جدا هستند؛ آیا درخواست هم‌زمان می‌تواند invariant را بشکند؟» |

قطعیت را به شاهد وصل کن. اگر مسئله را بازتولید کرده‌ای، بگو با چه ورودی. اگر فقط خطری می‌بینی، آن را فرضیه معرفی کن. سؤال صادقانه ضعف نیست؛ از blocker بی‌شاهد دقیق‌تر است.

### سطح مناسب راهنمایی

reviewer مسئول گزارش مسئله است، نه لزوماً نوشتن کل طراحی جایگزین. برای باگ آشکار پیشنهاد مستقیم می‌تواند مفید باشد؛ برای ابهام طراحی، سؤال و trade-off به نویسنده فضای تصمیم می‌دهد. کامنت نباید پچ ۳۰خطی بنویسد مگر آن‌که تیم/ابزار این همکاری را بخواهد. نویسنده مالک راه‌حل است، reviewer مالک وضوح نگرانی.

### feedback مثبت و خلاصهٔ کلی

اگر تست edge case خوبی اضافه شده یا رفتار قبلی ساده شده، بگو چرا این کار ارزش دارد. تحسین واقعی دانش را تثبیت می‌کند؛ تعریف اجباری برای «ساندویچ‌کردن» نقد لازم نیست. بعد از commentهای خطی، خلاصهٔ کلی بگو: «یک blocker در مجوز باقی است؛ دو پیشنهاد اختیاری را می‌توان merge کرد؛ بعد از تست اصلاح لطفاً re-review بده.»

### تمرین: جمله را بازنویسی کن

کامنت خام: «این اصلاً مقیاس نمی‌گیرد.»

**نمونهٔ پاسخ:** «هر درخواست، همهٔ eventهای کاربر را در حافظه بارگذاری می‌کند و سپس فیلتر می‌کند. اگر تاریخچه بزرگ شود، مصرف حافظه و latency رشد می‌کند. آیا می‌توانیم فیلتر را در query صفحه‌بندی‌شده انجام دهیم؟ اگر حجم فعلی عمداً محدود است، لطفاً حد و منبع آن را در قرارداد ثبت کنیم.» این پاسخ observation، اثر، گزینه و احتمالاً فرض محدودیت را جدا می‌کند.

### تسلط یعنی بتوانی…

- یک comment را در یک رفتار مشخص جا بدهی؛
- اثر را بگویی بدون حمله به نویسنده؛
- سؤال را از دستور و blocker را از پیشنهاد جدا کنی؛
- اگر شاهد تازه رسید، نظر قبلی را اصلاح کنی.
