## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

اصول مؤلفه‌ای مانند انسجام انتشار و وابستگی پایدار کمک می‌کنند کد را در ماژول‌هایی گروه‌بندی کنیم که باهم تغییر، انتشار یا استفادهٔ مجدد شوند.

## مثال کاربردی

قواعد سفارش در یک component مالکیت‌دار می‌مانند و دیگر اجزا از API عمومی آن استفاده می‌کنند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «اصول معماری» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** تقسیم component هزینهٔ هماهنگی، نسخه‌بندی و dependency graph دارد.
- **بازبینی:** پوشه‌بندی را با مؤلفهٔ مستقل اشتباه نگیر؛ مرز باید از دسترسی و تغییر محافظت کند.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: اصول مؤلفه‌ای مانند انسجام انتشار و وابستگی پایدار کمک می‌کنند کد را در ماژول‌هایی گروه‌بندی کنیم که باهم تغییر، انتشار یا استفادهٔ مجدد شوند.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: قواعد سفارش در یک component مالکیت‌دار می‌مانند و دیگر اجزا از API عمومی آن استفاده می‌کنند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: تقسیم component هزینهٔ هماهنگی، نسخه‌بندی و dependency graph دارد.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: پوشه‌بندی را با مؤلفهٔ مستقل اشتباه نگیر؛ مرز باید از دسترسی و تغییر محافظت کند.

## آموزش تکمیلی مستقل

### ۱. Component principles

Component مؤلفه‌ای است که مسئولیت و contract مشخص دارد. Package، assembly یا folder به‌تنهایی component معماری نیست؛ مرز باید جلوی دسترسی بی‌رویه را بگیرد و مالکیت/تغییر را منسجم کند.

برای یک component مناسب:

1. یک capability یا بخش دامنه‌ای منسجم را مالک کن.
2. داده و invariantهایش را مشخص کن.
3. API عمومی را کوچک و پایدار نگه دار.
4. dependencyهای مجاز را تعریف و cycleها را ممنوع کن.
5. تست، نسخه‌بندی و ownership را به مرز وصل کن.

اصول کلاسیک component می‌پرسند چه چیزهایی باهم release یا reuse می‌شوند و dependency به کدام جهت پایداری می‌کند. یک قاعدهٔ کاربردی: چیزهایی که باهم تغییر می‌کنند نزدیک باشند؛ چیزهایی که جدا تغییر می‌کنند با contract کنترل‌شده همکاری کنند. مرز را از کد و تاریخچهٔ تغییر کشف کن، نه از سلیقهٔ پوشه‌بندی.

#### تجربهٔ مستند Shopify

Shopify توضیح داده که کدبیس Rails بزرگش را به componentهای دامنه‌ای‌تر نزدیک کرد، از جمله با package boundary tooling. هدف، فهم بخش‌های مرتبط، تست محدودتر و مالکیت روشن بود؛ آن‌ها هم‌زمان از استخراج همه‌چیز به سرویس‌های شبکه‌ای پرهیز کردند چون distributed system هزینه دارد. این تجربه نشان می‌دهد component می‌تواند درون یک monolith باشد.

مطالعه: [Deconstructing the Monolith](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity) و [Enforcing Modularity with Packwerk](https://shopify.engineering/enforcing-modularity-rails-apps-packwerk).

## نمودار معماری و خواندن مرحله‌ای

چرخهٔ وابستگی میان componentها تغییر و release را دشوار می‌کند. Acyclic Dependencies Principle می‌خواهد گراف جهت‌دار componentها بدون چرخه باشد؛ برای بسته‌ای که با هم تغییر و منتشر می‌شود، مرز release و reuse را با هم بسنج.
**دام رایج:** شکستن چرخه با یک interface صوری، بدون روشن‌کردن مالک قرارداد، coupling را پنهان می‌کند.
**تمرین با پاسخ:** اگر C به A وابسته است و A به C، قرارداد پایدار را به component سوم منتقل یا مالکیت را بازطراحی کن تا چرخه حذف شود.

این نمودار ساده فقط یک view را نشان می‌دهد؛ سامانهٔ واقعی به تصمیم روشن دربارهٔ شکست، امنیت و مالکیت هم نیاز دارد.

~~~text
Before:                         After:
[A] ---> [B]                   [A] ---> [B]
 ^        |                               |
 |        v                               v
 +------ [C]                         [Contracts]
                                      ^       ^
                                      |       |
                                      [C] ----+
~~~
