## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

کلاس‌های abstract/concrete، محدودهٔ دسترسی و interface ابزارهای تعریف قرارداد، reuse و کنترل سطح افشا هستند.

## مثال کاربردی

ماژول پرداخت `IPaymentGateway` را برای use case می‌بیند و پیاده‌سازی واقعی را زیرساخت فراهم می‌کند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «برنامه‌نویسی شیءگرا» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** جزئیات زبان‌ها متفاوت است؛ معنا را از نحو جدا کن.
- **بازبینی:** هر کلاس را interfaceدار نکن؛ interface زمانی مفید است که مرز یا چند پیاده‌سازی واقعی وجود دارد.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: کلاس‌های abstract/concrete، محدودهٔ دسترسی و interface ابزارهای تعریف قرارداد، reuse و کنترل سطح افشا هستند.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: ماژول پرداخت `IPaymentGateway` را برای use case می‌بیند و پیاده‌سازی واقعی را زیرساخت فراهم می‌کند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: جزئیات زبان‌ها متفاوت است؛ معنا را از نحو جدا کن.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: هر کلاس را interfaceدار نکن؛ interface زمانی مفید است که مرز یا چند پیاده‌سازی واقعی وجود دارد.

## آموزش تکمیلی مستقل

### ۳. ویژگی‌های زبان: interface، abstract class، concrete class، scope

#### Interface

Interface قرارداد capability است؛ مثلاً PaymentAuthorizer می‌گوید چه کاری در اختیار مصرف‌کننده است. interface را از نیاز consumer طراحی کن، نه از کل SDK فروشنده. اگر یک interface بزرگ همهٔ عملیات پرداخت، refund، گزارش و تنظیمات را ارائه می‌دهد، مصرف‌کننده‌ها به عملیات نامربوط وابسته می‌شوند؛ قرارداد کوچک‌تر بر اساس نقش‌ها می‌تواند مناسب باشد.

#### Abstract class

کلاس انتزاعی مستقیماً نمونه‌سازی نمی‌شود و ممکن است پیاده‌سازی مشترک یا الگوریتم قالب داشته باشد. Template Method وقتی مناسب است که ترتیب مراحل ثابت و یک گام قابل تغییر باشد. اگر زیرکلاس‌ها ترتیب را تغییر می‌دهند یا چند محور مستقل variation هست، composition معمولاً coupling کمتری دارد.

#### Concrete class

کلاس عینی قرارداد را کامل پیاده می‌کند و قابل ساخت است. StripeGateway نمونهٔ adapter concrete است. composition root یا factory باید وابستگی‌های حساس را پیکربندی کند؛ callerهای متعدد نباید خودشان درگاه واقعی را new کنند. interface را فقط به خاطر «شاید روزی» نساز.

#### Scope و visibility

Scope محدودهٔ اعتبار نام در زبان است: block، function، module یا global. Visibility سطح دسترسی بیرونی است: private، protected، internal/package یا public. این دو مرتبط‌اند اما یکی نیستند.

از کمترین visibility لازم شروع کن. public member قرارداد پشتیبانی‌شدهٔ بیرونی می‌سازد و تغییر آن سازگاری می‌خواهد. protected هم نوعی API برای وارثان است. global mutable state ردیابی تغییر را سخت می‌کند؛ constant تغییرناپذیر خطر کمتری دارد.

## نمونهٔ کد مرحله‌ای

OOP state و عملیات مرتبط را کنار هم می‌گذارد، پیاده‌سازی را پشت قرارداد پنهان می‌کند و با dispatch چندریختی رفتار متناسب با نوع را انتخاب می‌کند. این‌ها ابزارند؛ برای تبدیل یک تابع ساده یا دادهٔ بی‌رفتار به hierarchy کلاس از آن‌ها استفاده نکن.
**تمرین با پاسخ:** اضافه‌کردن روش ارسال جدید نباید شرط‌های use case را زیاد کند؛ قرارداد مشترک و implementation جدا می‌تواند تغییر را محدود کند.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا تصمیم طراحی روشن بماند.

~~~csharp
public interface IDeliveryMethod
{
    DeliveryQuote Quote(Parcel parcel);
}

public sealed class CourierDelivery : IDeliveryMethod
{
    public DeliveryQuote Quote(Parcel parcel) => CalculateCourierQuote(parcel);
}
~~~
