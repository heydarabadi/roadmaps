# فصل ۱ — شناخت Redis و انتخاب کاربرد

> English edition: [Chapter 1 — Redis foundations](../../../en/redis/01-foundations/README.md)

> هدف فصل این است که پیش از حفظ فرمان‌ها، بدانی Redis چه مسئله‌ای را حل می‌کند، چه تضمینی می‌دهد و چه زمانی انتخاب بدی است. زمان پیشنهادی: ۲ تا ۳ ساعت، به‌علاوهٔ یادداشت‌برداری.

## پیش‌نیاز و مسیر مطالعه

پیش‌نیاز برنامه‌نویسی خاصی نیست. فقط مفهوم برنامه، داده و شبکه را در حد client/server بدان. درس‌ها را به این ترتیب بخوان:

1. [Redis چیست؟](redis-overview/README.md): مدل in-memory key/value، ساختار داده، دستورها، اجرای فرمان، حافظه و جایگاه Redis کنار منبع داده.
2. [کاربردها و الگوها](use-cases/README.md): cache، session، counter، leaderboard، queue/event، rate limit و خطرهای هر الگو.
3. [مقایسه و انتخاب datastore](choose-datastore/README.md): تفاوت نیازهای cache/key-value، SQL، document، search و broker.

## مدل ذهنی فصل

تصور کن هر درخواست از برنامه به Redis دستور می‌فرستد و پاسخ می‌گیرد. کلید نام یک شیء است؛ مقدار می‌تواند String، Hash، List، Set، Sorted Set یا نوع تخصصی باشد. Redis فقط یک «جدول key/value» نیست: نوع داده، عملیات مجاز و پیچیدگی عملیات بخش مهمی از طراحی‌اند.

سریع بودن به معنی «همه‌چیز را در Redis قرار بده» نیست. Redis معمولاً یک لایهٔ تخصصی کنار دیتابیس ماندگار است. پیش از نگهداری داده بپرس: منبع authoritative کجاست؟ اگر Redis خالی شد چه می‌شود؟ داده قابل بازسازی است؟ چه مدت باید بماند؟

## گام طراحی برای هر کاربرد

برای مثال cache محصول:

1. منبع اصلی محصول را مشخص کن؛ Redis cache است.
2. query را ثبت کن: «محصول با شناسهٔ ۴۲ را بخوان.»
3. مقدار و serialization را تعیین کن: مثلاً JSON string یا Hash.
4. انقضا بگذار، چون نامحدود ماندن cache حافظه می‌گیرد و اطلاعات را کهنه می‌کند.
5. cache miss را تعریف کن: خواندن از دیتابیس، پاسخ، سپس cache کردن.
6. failure را تمرین کن: اگر Redis در دسترس نبود، برنامه چطور به منبع اصلی می‌رسد و چگونه جلوی هجوم همزمان را می‌گیرد؟

همین سؤال‌ها برای session، rate limit یا queue جواب یکسان ندارند. «Redis سریع است» هنوز دلیل کافی نیست؛ نیاز، دادهٔ از دست‌رفته و راه بازیابی را مشخص کن.

## خروجی لازم از فصل

برای سه workload زیر، در یک جدول بنویس: منبع اصلی، key/data model، TTL، رفتار هنگام miss/outage، خطر دادهٔ کهنه و معیار پایش.

| workload | سؤال اصلی |
| --- | --- |
| صفحهٔ محصول پربازدید | چند ثانیه/دقیقه دادهٔ کهنه پذیرفتنی است؟ |
| session کوتاه‌عمر | در دسترس نبودن Redis کاربر را خارج می‌کند یا ورود مجدد ممکن است؟ |
| شمارش request در پنجرهٔ زمانی | مرز پنجره و دقت شمارش چیست؟ |

## آزمون عبور

1. چرا Redis سرعتی و درعین‌حال نامناسب برای منبع اصلی بعضی داده‌هاست؟
2. cache miss و cache outage چه تفاوتی دارند؟
3. برای هر الگو بگو چه چیزی Redis نگه می‌دارد و کدام سیستم حقیقت نهایی است.
4. یک failure mode برای cache stampede و یک راه کنترل پیشنهاد کن.

<details><summary>پاسخ راهنما</summary>

سرعت به latency/مدل اجرا و in-memory بودن مربوط است؛ دوام/رابطه‌ها/گزارش‌گیری و consistency ممکن است به پایگاه اصلی نیاز داشته باشند. Miss یعنی کلید موجود نیست؛ outage یعنی خود سرویس قابل‌دسترسی نیست. برای cache، دیتابیس معمولاً authoritative است؛ session ممکن است state مهم عملیاتی باشد و سیاست تحمل outage لازم دارد. stampede یعنی تعداد زیادی miss همزمان به منبع اصلی؛ single-flight/lock محدود، jitter در TTL، stale-while-revalidate یا rate limit راه‌های ممکن‌اند، هرکدام trade-off خود را دارند.
