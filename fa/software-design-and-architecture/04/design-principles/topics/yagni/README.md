## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

پیچیدگی را برای نیازی که هنوز معتبر نشده پیاده نکن؛ طراحی را آن‌قدر منعطف نگه دار که نیاز ثابت‌شده را بتوان بعداً پاسخ داد.

## مثال کاربردی

درگاه فعلی فقط یک روش پرداخت دارد؛ ابتدا interface ساده و آزمون بگذار، plugin framework را تا نیاز واقعی عقب بینداز.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «اصول طراحی» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** بعضی تصمیم‌های پرهزینه یا ایمنی‌محور باید پیشاپیش طراحی شوند.
- **بازبینی:** YAGNI بهانهٔ نادیده‌گرفتن امنیت، دادهٔ مهاجرت یا الزام قانونی نیست.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: پیچیدگی را برای نیازی که هنوز معتبر نشده پیاده نکن؛ طراحی را آن‌قدر منعطف نگه دار که نیاز ثابت‌شده را بتوان بعداً پاسخ داد.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: درگاه فعلی فقط یک روش پرداخت دارد؛ ابتدا interface ساده و آزمون بگذار، plugin framework را تا نیاز واقعی عقب بینداز.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: بعضی تصمیم‌های پرهزینه یا ایمنی‌محور باید پیشاپیش طراحی شوند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: YAGNI بهانهٔ نادیده‌گرفتن امنیت، دادهٔ مهاجرت یا الزام قانونی نیست.

## آموزش تکمیلی مستقل

### ۳. YAGNI — You Aren't Gonna Need It

قابلیتی را برای نیاز احتمالی اما اثبات‌نشده نساز. قابلیت آینده‌نگر هزینهٔ ساخت، تست، امنیت، مستند و پشتیبانی دارد و ممکن است هیچ‌وقت استفاده نشود. طراحی را قابل تکامل بساز، ولی plugin framework و abstraction چندلایه را برای فرض مبهم تحمیل نکن.

YAGNI بهانه‌ای برای رد امنیت، audit، privacy، سازگاری داده یا الزام قانونی نیست؛ این‌ها نیازهای فعلی واقعی‌اند. تصمیم‌های برگشت‌ناپذیر و مهاجرت داده هم ممکن است پیش‌بینی زودهنگام لازم داشته باشند.

## نمونهٔ کد مرحله‌ای

YAGNI می‌گوید قابلیتی را برای آیندهٔ فرضی نساز؛ هزینهٔ abstraction، نگهداری و تصمیم نادرست را هم حساب کن. این اصل مانع طراحی ضروری یا مرز امنیتی نیست: وقتی نیاز واقعی شد، تغییر سنجیده را ساده کن.
**تمرین با پاسخ:** دو روش مالیات قطعی و ثابت‌اند؛ یک تابع ساده بنویس. وقتی variation واقعی شد، آن را با آزمون و شواهد استخراج کن.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا انتخاب طراحی روشن بماند.

~~~csharp
static Money CalculateTax(Money subtotal, TaxRate rate)
{
    return (subtotal * rate).RoundToCurrencyUnit();
}
~~~

اصل «فعلاً لازم نیست» (YAGNI) را برای حل مسئلهٔ مشخص به کار ببر، trade-off آن را ثبت کن و با یک آزمون/معیار قابل مشاهده بررسی کن که آیا مرز طراحی واقعاً بهتر شده است.
