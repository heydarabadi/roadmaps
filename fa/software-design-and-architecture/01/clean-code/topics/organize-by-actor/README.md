# سازمان‌دهی بر اساس عامل تغییر — Organize code by the actor it belongs to


> **زبان:** [نسخهٔ انگلیسی](../../../../../../en/software-design-and-architecture/01/clean-code/topics/organize-by-actor/README.md)

[فصل کد تمیز](../../README.md) · [فهرست دوره](../../../../00-index.md)

## هدف درس

بتوانی مسئلهٔ این اصل را تشخیص بدهی، آن را در کد به‌کار ببری، trade-off را توضیح بدهی و در آزمون از نتیجه دفاع کنی.

## آموزش دقیق

Actor در این اصل یعنی ذی‌نفع یا گروهی که درخواست تغییر را ایجاد می‌کند؛ در برنامهٔ تجاری ممکن است مالی، انبار، پشتیبانی یا یک business capability باشد. وقتی همه‌چیز بر پایهٔ فناوری در پوشه‌های Controllers/Services/Helpers پخش است، یک feature کوچک تغییرهای پراکنده و بازبینی سخت می‌سازد.

۱. درخواست‌های اخیر را مرور کن و بخش‌هایی را که معمولاً باهم تغییر می‌کنند پیدا کن.
۲. ماژول را بر اساس واژگان دامنه یا capability سازمان بده.
۳. تغییر مالکیت قواعد و داده را در همان مرز منعکس کن.
۴. اجزا از API مشخص هم استفاده کنند؛ پوشه به‌تنهایی مرز ایجاد نمی‌کند.

## مثال

Orders می‌تواند مدل و use case لغو/ثبت را کنار آزمون‌های خودش نگه دارد؛ Shipping مالک محاسبهٔ مسیر و ارسال باشد. اگر تغییر بازپرداخت هم‌زمان در پنج پوشهٔ فنی لازم می‌شود، احتمالاً مسئولیت‌ها پراکنده‌اند. اگر قابلیت کوچک و پایدار است، پوشه‌بندی سادهٔ فعلی کافی است.

## محدوده

هر نقش کاربری نیازمند ماژول نیست. دو actor ممکن است یک قاعده را به اشتراک بگذارند یا مالکیت تیم‌ها تغییر کند؛ از تاریخچهٔ تغییر، language و invariantها شواهد بگیر. این روش جای معماری لایه‌ای و جهت dependency را حذف نمی‌کند.

## تمرین

ده commit اخیر را به actor/capability نسبت بده. ببین چه فایل‌هایی با هم تغییر کرده‌اند و فقط یک مرز پیشنهادی را با شواهد توضیح بده.

## نمونهٔ کد/قرارداد

~~~text
orders/
  domain/       # order rules and invariants
  application/  # place, pay, cancel use cases
  api/          # public transport contract
  tests/        # order behavior
~~~

## تمرین سنجش

نمونه‌ای از کد خودت یا یک پروژهٔ آموزشی انتخاب کن. مفهوم را در یک تغییر کوچک اعمال کن، آزمونی برای رفتار مرزی اضافه کن و با یک جمله ثبت کن که چه چیزی خواناتر یا امن‌تر شد.

## کوییز با پاسخ تشریحی

پیش از دیدن پاسخ، دلیل خودت را بنویس. پاسخ پیشنهادی باید با زمینه هماهنگ باشد؛ اگر گزینهٔ دیگری داری، trade-off آن را هم بیان کن.

1. **actor به چه کسی/چیزی اشاره می‌کند؟**
   - پاسخ تشریحی: ذی‌نفع یا قابلیتی که نیازمندی را تغییر می‌دهد، نه الزاماً یک class یا user role.
2. **چه شواهدی برای مرز می‌خواهی؟**
   - پاسخ تشریحی: قواعد و دادهٔ مالک‌دار، هم‌زمانی تغییرها، نیاز انتشار و وابستگی واقعی.
3. **چرا پوشه‌بندی فنی می‌تواند دردسر شود؟**
   - پاسخ تشریحی: یک feature برای تغییر نیاز به دست‌زدن به چند محل پراکنده دارد.
