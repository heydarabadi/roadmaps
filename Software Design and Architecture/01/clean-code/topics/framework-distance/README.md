# فاصله از فریم‌ورک — Keep framework code distant


> **زبان:** [نسخهٔ انگلیسی](../../../../en/01/clean-code/topics/framework-distance/README.md)

[فصل کد تمیز](../../README.md) · [فهرست دوره](../../../../00-index.md)

## هدف درس

بتوانی مسئلهٔ این اصل را تشخیص بدهی، آن را در کد به‌کار ببری، trade-off را توضیح بدهی و در آزمون از نتیجه دفاع کنی.

## آموزش دقیق

فریم‌ورک وب، ORM و SDK درگاه جزئیات فنی‌اند و معمولاً نرخ تغییرشان با قواعد دامنه فرق دارد. اگر منطق سفارش ناچار است از کلاس پایهٔ ORM ارث ببرد، annotationهای HTTP بگیرد یا SDK یک فروشنده را صدا کند، ابزار بیرونی در مرکز تصمیم قرار گرفته است.

مرزی ساده می‌تواند چنین باشد: controller درخواست را اعتبارسنجی اولیه و به use case تبدیل کند؛ use case کار را هماهنگ کند؛ مدل دامنه invariant را نگه دارد؛ adapter قرارداد پرداخت یا ذخیره‌سازی را به ابزار واقعی وصل کند. این جداسازی می‌تواند در یک پروژه باشد؛ تعداد پوشه‌ها یا assemblyها معیار نیست.

## مثال و انتخاب مرز

برای زمان، Clock را تزریق کن اگر تست باید زمان ثابت داشته باشد یا چند policy زمان واقعی نیاز است. برای هر کلاس ساده interface نساز. اگر تغییر framework منطق دامنه را تغییر می‌دهد، آزمون دامنه بدون بالا آوردن زیرساخت ممکن نیست، یا vendor dependency باید قابل تعویض باشد، جداسازی ارزش بیشتری دارد.

## هزینه و خطاها

Adapter، mapping و abstraction هزینهٔ نگهداری دارند. پنهان‌کردن کامل امکانات مفید فریم‌ورک هم اتلاف است. مرز را بر اساس تغییر، آزمون‌پذیری و ریسک مهاجرت انتخاب کن. منطق کسب‌وکار را صرفاً با نام clean به ده لایه تبدیل نکن.

## تمرین

dependency graph یک use case را رسم کن. مشخص کن کدام وابستگی policy است و کدام ابزار. سپس یک آزمون قاعده را بدون وب‌سرور و database بنویس.

## نمونهٔ کد/قرارداد

~~~text
domain rules -> application use case <- infrastructure adapter

# Source dependencies point toward stable contracts.
# Runtime calls may travel outward to adapters.
~~~

## تمرین سنجش

نمونه‌ای از کد خودت یا یک پروژهٔ آموزشی انتخاب کن. مفهوم را در یک تغییر کوچک اعمال کن، آزمونی برای رفتار مرزی اضافه کن و با یک جمله ثبت کن که چه چیزی خواناتر یا امن‌تر شد.

## کوییز با پاسخ تشریحی

پیش از دیدن پاسخ، دلیل خودت را بنویس. پاسخ پیشنهادی باید با زمینه هماهنگ باشد؛ اگر گزینهٔ دیگری داری، trade-off آن را هم بیان کن.

1. **چه چیزی را از framework دور نگه می‌داری؟**
   - پاسخ تشریحی: قواعد و واژگان مرکزی دامنه، تا حدی که تغییر ابزار آن‌ها را مجبور به تغییر نکند.
2. **آیا همه framework را باید پنهان کرد؟**
   - پاسخ تشریحی: خیر؛ abstraction هزینه دارد و فقط مرز تغییر، آزمون یا policy را جدا می‌کنیم.
3. **یک نشانهٔ وابستگی زیاد چیست؟**
   - پاسخ تشریحی: قاعدهٔ دامنه بدون راه‌اندازی ORM یا وب‌سرور قابل آزمون نیست.
