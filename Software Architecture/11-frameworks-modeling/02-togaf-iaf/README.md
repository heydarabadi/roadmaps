# TOGAF، IAF و معماری سازمانی

معماری سازمانی ارتباط راهبرد، قابلیت کسب‌وکار، داده، سامانه و فناوری را در کل سازمان بررسی می‌کند. TOGAF چارچوبی از مفاهیم، Architecture Development Method، محتوا، governance و راهنماهای زمینه‌ای است. ADM چرخه‌ای برای تعریف vision، وضع موجود/هدف، گزینه‌های گذار و مدیریت تغییر فراهم می‌کند؛ باید آن را برای محیط سازمان tailor کرد.

IAF در roadmap به Integrated Architecture Framework اشاره دارد، اما این سرواژه ممکن است در زمینه‌های دیگر معناهای متفاوت داشته باشد. IAF شناخته‌شدهٔ Capgemini دیدهای کسب‌وکار، اطلاعات، سیستم اطلاعاتی و زیرساخت فناوری را به مصنوعات معماری پیوند می‌دهد. نام framework بدون نسخه، سازمان و دامنهٔ کاربرد کافی نیست.

Framework خروجی را به هدف وصل می‌کند: تصمیم سرمایه‌گذاری؟ نقشهٔ تحول؟ هم‌ترازی business و IT؟ انطباق؟ اگر تنها deliverable برای پرکردن template تولید شود، هزینهٔ governance از ارزش بیشتر می‌شود.

## ADM را به زبان پروژه بفهمیم

ADM چرخهٔ روش توسعهٔ معماری در TOGAF است: از vision و محدوده شروع می‌کنی، معماری business/data/application/technology را برای وضع موجود و هدف بررسی می‌کنی، گزینه‌های گذار و migration را طراحی می‌کنی، سپس پیاده‌سازی و تغییر را با governance دنبال می‌کنی. مراحل را یکبار خطی اجرا نمی‌کنی؛ یافتهٔ جدید به مرحلهٔ قبلی بازمی‌گردد.

برای نوسازی صورتحساب:

۱. **محرک و ذی‌نفع:** مشکل چیست، کدام هدف کسب‌وکار، چه محدودیت قانونی/بودجه‌ای؟
۲. **وضع موجود:** منبع داده، ارتباط‌ها، وابستگی افراد و failure را فهرست کن.
۳. **هدف قابل‌اندازه‌گیری:** مثلاً کاهش زمان صدور یا حذف دوباره‌کاری، همراه baseline و سنجه.
۴. **گزینه‌ها:** حفظ/بهبود، محصول آماده، سرویس جدید یا مهاجرت مرحله‌ای را با هزینه و ریسک بسنج.
۵. **transition architecture:** گام‌های قابل‌تحویل، data migration، coexistence و rollback را ثبت کن.
۶. **governance:** تصمیم‌های مهم، استثنا، معیار انطباق و owner اجرا را مشخص کن.

## Artifact را بر اساس تصمیم بساز

Capability map وقتی سرمایه‌گذاری را به توان کسب‌وکار وصل می‌کند مفید است؛ application portfolio وقتی تکرار و ریسک سامانه‌ها را نشان می‌دهد؛ roadmap وقتی ترتیب انتقال و dependency را روشن می‌کند. اگر خروجی تصمیم، سرمایه‌گذاری یا migration را تغییر نمی‌دهد، احتمالاً سند اضافی است.

## Tailoring و محدودیت

Framework زبان و روش می‌دهد، solution معماری برای زمینهٔ واقعی می‌سازد. عمق governance را با ریسک، مقررات، اندازه و سرعت تغییر متناسب کن. IAF را با مالک، نسخه و معنی مخفف مشخص کن؛ نام مشابه ممکن است به چارچوب‌های دیگر اشاره کند.

## آزمون

۱. TOGAF ADM چه کمکی می‌کند؟ **پاسخ:** فرایند تکرارشوندهٔ توسعه و ادارهٔ معماری سازمانی را سازمان می‌دهد.
۲. framework با architecture solution چه تفاوتی دارد؟ **پاسخ:** framework روش/ساختار را فراهم می‌کند؛ solution باید برای یک زمینه طراحی شود.
۳. چرا منظور از IAF را باید مشخص کرد؟ **پاسخ:** مخفف چندمعناست و نسخه/مالک چارچوب بر دامنه و روش اثر دارد.
۴. چه زمانی framework را tailor می‌کنی؟ **پاسخ:** تقریباً همیشه؛ عمق و مصنوعات باید متناسب با مقیاس، مقررات و ارزش باشند.

## تمرین

برای نوسازی سیستم فاکتوردهی، وضع موجود، معماری هدف، سه transition، ذی‌نفع و تصمیم governance را روی یک صفحه نشان بده.

## پاسخ نمونهٔ تمرین

As-is: سیستم فاکتور دستی، فایل‌های پراکنده، مالکیت داده نامعلوم و SLA ثبت‌نشده. Target: فرایند دیجیتال با منبع حقیقت، API، audit و گزارش lineageدار. Transitionها: inventory و baseline؛ pilot با coexistence؛ انتقال data و خاموش‌سازی پس از reconcile. ذی‌نفع‌ها مالی، عملیات، امنیت و مشتری‌اند؛ architecture board فقط exception و ریسک cross-cutting را تصویب می‌کند.
