## آموزش

سامانه به‌صورت یک واحد deploy می‌شود؛ درون آن می‌تواند ماژولار و خوش‌ساخت یا به‌شدت درهم‌تنیده باشد.

## مثال کاربردی

فروشگاه یک سرویس وب، یک انتشار و مرزهای ماژولی داخلی دارد.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «سبک‌های معماری» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** استقرار و تراکنش ساده‌تر است، اما انتشار و مقیاس‌دادن بخش‌ها به هم گره می‌خورند.
- **بازبینی:** Monolith را با modular monolith یا monolith بی‌مرز یکی ندان.

## آموزش تکمیلی مستقل

### ۲. Monolithic و Modular Monolith

Monolith یک واحد deploy است؛ این تعریف نمی‌گوید کد داخلش تمیز است یا آشفته. Modular monolith یک deployment با مرزهای درون‌فرایندی کنترل‌شده دارد: اجزا API محدود دارند، داده را از پشت contract می‌خوانند و مالکیت تغییر روشن است.

مزیت monolith: deployment و debug ساده‌تر، local call سریع، transaction سراسری آسان‌تر، هزینهٔ عملیاتی کم. ریسک: deploy همهٔ بخش‌ها به هم گره می‌خورد، مقیاس واحد است و boundaryها ممکن است فرسوده شوند.

Shopify گزارش کرده که بخش اصلی Rails خود را با componentها modular کرده و فقط کارکردهایی چون storefront rendering یا پرداخت حساس را با دلیل مستقل‌تری جدا کرده است. [گزارش Shopify](https://shopify.engineering/shopify-monolith).

## نمودار معماری و خواندن مرحله‌ای

Monolith یک واحد قابل‌استقرار است؛ می‌تواند داخل خود ماژول‌های منظم داشته باشد. استقرار و فراخوانی محلی ساده‌اند، اما coupling و هماهنگی تیمی می‌تواند رشد کند. مرز ماژول را روشن کن و پیش از جداسازی سرویس، کیفیت مرز را درون process ثابت کن.
**دام رایج:** monolith را مترادف کد آشفته نگیر و برای رفع آن فوراً microservices نساز.
**تمرین با پاسخ:** سفارش و پرداخت shared table دارند؛ ابتدا ownership و قرارداد را جدا کن و coupling را اندازه بگیر، سپس دربارهٔ deployment تصمیم بگیر.

این نمودار ساده فقط یک view را نشان می‌دهد؛ سامانهٔ واقعی به تصمیم روشن دربارهٔ شکست، امنیت و مالکیت هم نیاز دارد.

~~~text
One deployment:
+---------------------------------------+
| [Orders] <contract> [Payments]        |
| [Catalog] <contract> [Inventory]      |
| Shared process; modules own decisions |
+---------------------------------------+
~~~
