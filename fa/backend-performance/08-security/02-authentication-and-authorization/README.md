# احراز هویت و مجوز دسترسی — Authentication و Authorization

**زبان:** فارسی · [نسخهٔ انگلیسی](../../../../en/backend-performance/08-security/02-authentication-and-authorization/README.md)  

**هدف یادگیری:** تشخیص دهید «چه کسی هستی؟» با «اجازه چه کاری روی کدام منبع داری؟» چه تفاوتی دارد و هزینه این کنترل‌ها را با حفظ صحت و امکان ابطال مدیریت کنید. **بررسی منابع: ۲۰۲۶-۱۱-۱۱**؛ نمونه‌ها مفهومی و اجرا‌نشده‌اند.

## تعریف و مسیر تصمیم

Authentication هویت ادعاشده را اعتبارسنجی می‌کند؛ Authorization تصمیم می‌گیرد این هویت در این context اجازه عملیات روی این منبع را دارد یا نه. Quota نیز جداست: کاربر می‌تواند مجاز باشد ولی سهم مصرفش تمام شده باشد. ورود موفق یا داشتن JWT معتبر، مجوز خواندن سفارش هر مشتری نیست.

| پرسش | ورودی معتبر مورد نیاز | نمونه رد |
| --- | --- | --- |
| هویت چیست؟ | session معتبر یا token اعتبارسنجی‌شده | session منقضی/امضای نامعتبر |
| عملیات مجاز است؟ | subject، tenant، action، object و policy | کاربر A روی سفارش B |
| مقدار مصرف مجاز است؟ | هویت تأییدشده و شمارنده سهمیه | export بیش از بودجه |

در هر درخواست، context هویت را از سازوکار معتبر بسازید، شیء/عملیات و tenant را مشخص کنید، policy را با پیش‌فرض منع بررسی کنید و سپس داده مجاز را بخوانید. مسیر فایل، endpoint جایگزین و worker نیز باید همین قواعد را داشته باشند. [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) بررسی مجوز در هر درخواست و least privilege را توصیه می‌کند؛ قرارداشتن ID در URL به‌تنهایی نقص نیست، نبود بررسی دسترسی نقص است.

برای دنبال‌کردن جریان، اصطلاح‌های پایه را این‌طور بخوانید: **principal** موجودیتی است که درخواست را انجام می‌دهد؛ **credential** مدرکی است که برای اثبات هویت ارائه می‌شود؛ **claim** گزاره‌ای درباره هویت یا زمینه در credential است؛ **resource/object** چیزی است که می‌خواهیم بخوانیم یا تغییر دهیم؛ **policy** قاعده‌ای است که principal، عملیات، شیء و زمینه را ارزیابی می‌کند. Role و scope روش‌هایی برای بیان بخشی از policy هستند؛ هیچ‌کدام به‌تنهایی مالکیت یک شیء خاص را ثابت نمی‌کنند.

### مسیر تصمیم برای یک درخواست

۱. **Credential را اعتبارسنجی کنید.** اگر session منقضی است یا token از نظر امضا، issuer، audience و زمان معتبر نیست، principal تاییدشده نداریم و اجرای کاربر متوقف می‌شود.

۲. **Context قابل اعتماد بسازید.** tenant یا عضویت را از منبعی بگیرید که سرور تایید کرده است. header ارسالی کاربر فقط درخواست انتخاب context است، نه مدرک عضویت.

۳. **عملیات و شیء را مشخص کنید.** `order:read` روی سفارش 81 با همان عملیات روی سفارش 82 یک تصمیم واحد نیست؛ بررسی route به‌تنهایی ممکن است کافی نباشد.

۴. **Policy را با پیش‌فرض منع ارزیابی کنید.** اگر دادهٔ لازم نامعلوم است یا سرویس policy در دسترس نیست، تصمیم نامعلوم را به allow تبدیل نکنید؛ عملیات را با شکست کنترل‌شده متوقف کنید.

۵. **داده را با قیدهای مجوز بخوانید.** شرط tenant/مالکیت در query یا لایهٔ دامنه یک دفاع تکمیلی در برابر خطاست، اما جای policy روشن و بررسی همه مسیرها را نمی‌گیرد.

۶. **نتیجه را کم‌افشا ثبت کنید.** مدت auth و policy، نتیجه و نسخهٔ policy مفیدند؛ token، رمز و کل سفارش را در log قرار ندهید.

| حالت | هویت | مجوز | رفتار مفهومی |
| --- | --- | --- | --- |
| credential نامعتبر یا منقضی | نامعتبر | ارزیابی نمی‌شود | درخواست متوقف شود |
| credential معتبر، مالک و tenant درست | معتبر | مجاز | فقط فیلدهای لازم بازگردند |
| credential معتبر، سفارش متعلق به دیگری | معتبر | رد | داده خوانده یا افشا نشود |
| نقش لغوشده ولی token هنوز معتبر | ممکن است معتبر باشد | طبق policy تازه رد | قرارداد ابطال/نسخهٔ نقش مهم است |
| identity یا policy نامطمئن | نامعلوم | نامعلوم | شکست کنترل‌شده؛ allow پیش‌فرض نشود |

انتخاب پاسخ عدم دسترسی باید با قرارداد API و نیاز جلوگیری از افشای وجود منبع سازگار باشد. می‌توان پاسخ منبع ناموجود و غیرقابل‌دسترسی را برای caller یکنواخت کرد؛ این تصمیم پیام بیرونی را عوض می‌کند، نه لزوم ثبت علت داخلی امن.

## کاربرد و مصالحه امنیت/latency

احراز هویت رمزعبور باید از کتابخانه و password hashing مناسب با هزینه تنظیم‌شده استفاده کند. کاهش هزینه یا حذف MFA صرفاً برای سریع‌ترشدن، قرارداد امنیتی را عوض می‌کند. برای login، ظرفیت کنترل‌شده، محافظت از brute force و پاسخ بدون افشای وجود حساب لازم است. [راهنمای OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) مدیریت session، پاسخ خطا و احراز مجدد عملیات حساس را پوشش می‌دهد.

اعتبارسنجی محلی token امضاشده می‌تواند رفت‌وبرگشت شبکه را کم کند، اما امضا، issuer، audience، زمان اعتبار، نوع token و claimهای لازم طبق پروفایل مصرف، و سیاست الگوریتم باید در کتابخانه معتبر بررسی شوند. عمر token و revocation قرارداد دارند؛ local validation خودبه‌خود ابطال فوری نمی‌دهد. شناسه issuer یا URL کلید از ورودی تأییدنشده نباید مقصد دلخواه شبکه را تعیین کند. کلیدهای اعتماد از تنظیم معتبر می‌آیند و refresh آن‌ها باید محدود و قابل پایش باشد.

cache تصمیم مجوز تنها با کلید کامل، تازگی و ابطال قابل بررسی است؛ subject، tenant، action، object و نسخه policy از ابعاد ممکن‌اند. حذف یک بعد ممکن است نتیجه مجاز کاربر/منبع دیگری را reuse کند. هر درخواست همچنان باید کنترل مجوز را طی کند؛ cache فقط روش دستیابی به تصمیم معتبر را تغییر می‌دهد. تغییر مالکیت و حذف نقش باید در بودجه ابطال اثر کند. اختلال identity/policy نباید به اعطای مجوز پیش‌فرض برسد؛ پاسخ کنترل‌شده ناموفق با مجوز دادن تفاوت دارد.

## مثال حل‌شده مستقل از زبان

فرض: مشتری می‌تواند سفارش خودش را در tenant فعال ببیند. tenant از context معتبر عضویت می‌آید، نه صرفاً یک header انتخابی کاربر. نمونه SQL پایین یک بخش از اجرای policy ساده مالکیت است، نه جایگزین policyهای پیچیده واقعی.

<div dir="ltr" align="left">

```text
principal = trusted_authenticator.validate(request.credentials)
context = resolve_verified_membership(principal, requested_tenant)
authorize_route(principal, context, action = "order:read")
order = database.query_one(
  "SELECT id, total FROM orders " +
  "WHERE id = ? AND tenant_id = ? AND customer_id = ?",
  [request.order_id, context.tenant_id, principal.customer_id]
)
if order is absent:
    return uniform_resource_unavailable_response()
return order
```

</div>

برای کارمند پشتیبانی که طبق policy مجاز به چند مشتری است، قاعده باید صریح مدل شود؛ حذف بی‌قید شرط شرط مالکیت برای همه، راه حل نیست. توکن یا secret را در log ننویسید؛ تصمیم، policy version و شناسه هم‌بستگیِ مناسب را با حداقل داده لازم ثبت کنید. پاسخ عدم دسترسی نباید اطلاعات خصوصی شیء را برای ساخت پیام خطا بخواند و افشا کند.

## تمرین و مشاهده مورد انتظار

جدول تصمیمی برای دو مشتری A و B، دو سفارش و دو tenant رسم کنید. شش حالت را مرور کنید: token منقضی، مالک درست، مالک اشتباه، tenant اشتباه، نقش لغوشده و endpoint دریافت فایل رسید. انتظار: فقط ترکیب مجاز عبور کند و هر دو مسیر JSON و فایل بررسی داشته باشند. سپس cache با کلید فقط `role` را تحلیل کنید؛ چرا نتیجه مجوز یک سفارش برای سفارش دیگر قابل اعتماد نیست؟ این تمرین، تست اجراشده روی سامانه نیست.

**حل تمرین:** ماتریسی با ستون‌های «هویت معتبر؟»، «tenant معتبر؟»، «مالک/نقش مجاز؟»، «مسیر JSON یا فایل؟» و «تصمیم» بسازید. token منقضی در ستون اول رد می‌شود؛ کاربر A روی سفارش B در ستون مالکیت رد می‌شود؛ عضویت لغوشده حتی با token معتبر، طبق policy تازه رد می‌شود. مسیر فایل نیز همان بررسی شیء را باید طی کند؛ تغییر قالب خروجی، سفارش را عمومی نمی‌کند. cache فقط بر اساس role نمی‌داند کدام tenant و کدام سفارش بررسی شده است، پس برای reuse تصمیم کافی نیست.

## شاهد عمومی و حد شواهد

[OWASP API1:2023 — Broken Object Level Authorization](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/) سناریوهای دسترسی شیء و ضرورت کنترل منبع را مستند می‌کند. این شاهد طبقه‌بندی و راهنمای عملیاتی است، نه گزارش incident مشخص یک شرکت یا benchmark latency. در این درس مطالعه عمومی مستقیمی که زمان بهینه‌سازی auth همین مثال را اندازه گرفته باشد ارائه نشده؛ اعداد و جریان فروشگاه فرضی‌اند. UUID یا مبهم‌کردن شناسه نیز مجوز را جایگزین نمی‌کند.

## شکست‌ها، سیگنال‌ها و چک‌لیست

اعتماد به نقش داخل payload تأییدنشده، عدم بررسی tenant، cache بدون ابطال، مسیر دانلود عمومیِ داده خصوصی و policy دارای پیش‌فرض allow خطرناک‌اند. زمان احراز/مجوز، خطای وابستگی هویت، نرخ رد به تفکیک route و رخداد تغییر نقش را ببینید؛ نرخ deny بالا لزوماً حمله نیست و می‌تواند خطای پیکربندی باشد. label با token یا شناسه خام نامحدود نسازید.

- [ ] هویت با کتابخانه معتبر و تنظیم trust صریح اعتبارسنجی می‌شود.
- [ ] مجوز object/action/tenant در همه مسیرها با deny-by-default اعمال می‌شود.
- [ ] session، token expiry، revocation و key rotation مالک و قرارداد دارند.
- [ ] cache تصمیم، کلید کامل و بودجه ابطال دارد؛ هر درخواست کنترل می‌شود.
- [ ] login و عملیات حساس کنترل سوءاستفاده و احراز مجدد متناسب دارند.
- [ ] قطعی policy یا identity باعث دسترسی بدون مجوز نمی‌شود.
- [ ] log و خطا، secret یا اطلاعات خصوصی منبع را افشا نمی‌کنند.

## خودآزمایی

۱. چرا token معتبر برای خواندن هر سفارش کافی نیست؟

۲. آیا UUID کنترل مجوز شیء را حذف می‌کند؟

۳. cache مجوز با کلید تنها `role` چه نقصی دارد؟

۴. local token validation چه مسئله‌ای را خودکار حل نمی‌کند؟

۵. اگر سرویس policy قطع شد، allow پیش‌فرض چه اثری دارد؟

۶. چرا latency auth را باید جدا ثبت کرد؟

### پاسخ‌نامه با دلیل

۱. Authentication هویت را می‌گوید؛ Authorization باید رابطه همان هویت با شیء/عملیات را بررسی کند.

۲. خیر؛ سختی حدس‌زدن شناسه تضمین دسترسی نیست و شناسه ممکن است از مسیر دیگری معلوم شود.

۳. tenant، شیء، عمل و context را مخلوط می‌کند و ممکن است نتیجه مجازِ مورد دیگر را reuse کند.

۴. ابطال فوری و تغییر نقش/مالکیت؛ عمر token و سازوکار freshness باید طراحی شوند.

۵. اختلال را به bypass کنترل تبدیل می‌کند؛ باید خطای کنترل‌شده و منع دسترسی نامطمئن داشت.

۶. برای دیدن هزینه امضا، شبکه یا policy و اصلاح همان عامل؛ میانگین زمان endpoint علت را نشان نمی‌دهد.
