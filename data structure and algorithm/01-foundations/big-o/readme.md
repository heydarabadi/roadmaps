# Big-O: کران بالا

> مسیر: [فصل ۱ — پایه‌ها و تحلیل الگوریتم](../readme.md) · پیش‌نیاز پیشنهادی: فصل ۱ و مبانی برنامه‌نویسی · [English](readme.en.md)

## پیش‌نیازها و نقشهٔ ذهنی

تابع هزینه، n و نمادهای مجانبی. ابتدا مفهوم را به‌عنوان یک قرارداد ببین، سپس نمایش حافظه و عملیات را دنبال کن. هدف حفظ‌کردن نام نیست؛ باید بتوانی برای یک ورودی کوچک، state را بعد از هر گام بنویسی.

## ایده از پایه

Big-O کران بالای رشد است، نه مقدار دقیق زمان. می‌گوید با بزرگ‌شدن ورودی هزینه حداکثر تا یک ضریب ثابت از تابع g رشد می‌کند. در مکالمهٔ مهندسی معمولاً برای worst-case استفاده می‌شود، اما خود نماد worst-case را تعیین نمی‌کند؛ آن را بنویس.

## مدل، قرارداد و ناوردا

f(n)∈O(g(n)) اگر c>0 و n₀ وجود داشته باشد که برای تمام n≥n₀، 0≤f(n)≤c·g(n). O(n) مجموعه‌ای از تابع‌هاست، نه برابر دقیق با n. اگر f=Θ(n)، آن‌گاه f∈O(n²) نیز هست اما کران شل است.

ناوردا (invariant) جمله‌ای است که در تمام مراحل الگوریتم باید درست بماند. نوشتن آن پیش از کدنویسی، هم به اثبات درستی کمک می‌کند و هم خطاهای مرزی را آشکار می‌سازد.

## الگوریتم یا عملیات گام‌به‌گام

شمار عملیات را بنویس و جملهٔ غالب را پیدا کن. loop nتایی با body ثابت O(n)؛ nested n×n، O(n²)؛ merge sort Θ(n log n). «ترکیب» هزینهٔ پشت‌سرهم جمع می‌شود؛ در رشد، max غالب می‌شود: O(n²+n)=O(n²).

در پیاده‌سازی واقعی، قرارداد ورودی/خروجی را دقیق تعریف کن: رفتار ورودی تهی، مقدار تکراری، عنصر پیدا‌نشده و ظرفیت تمام‌شده باید روشن باشد.

## اجرای حل‌شده با ردگیری

جست‌وجوی خطی در آرایهٔ nتایی در worst-case n مقایسه می‌کند، پس O(n). جست‌وجوی دودویی O(log n) است و چون log n≤n، آن هم O(n) هست؛ اما Θ(log n) کران tight و اطلاعات‌دارتر است.

برای تمرین، جدولی با ستون‌های «گام»، «اندیس/اشاره‌گر»، «بخش فعال»، «تغییر state» و «دلیل» بساز. این روش به‌خصوص برای الگوریتم‌های درجا و تقسیم‌و‌غلبه جلوی پرش ذهنی را می‌گیرد.

## چرا درست است؟

کران باید به تابع عملیاتِ حالت مشخص مربوط باشد. اگر case و پارامترها حذف شوند، ادعا مبهم است. برای dynamic array append بگو amortized O(1)، برای hash lookup بگو expected/average O(1) تحت فرض مناسب.

اثبات معمولاً سه بخش دارد: (۱) آغاز—ناوردا پیش از نخستین گام درست است؛ (۲) نگهداری—هر گام آن را حفظ می‌کند؛ (۳) پایان—شرط توقف همراه invariant جواب موردنیاز را نتیجه می‌دهد. اگر یکی از این سه بخش نامشخص است، هنوز درک الگوریتم کامل نشده است.

## تحلیل زمان و حافظه

O(1) constant، O(log n) logarithmic، O(n) linear، O(n log n)، O(n²) و O(2^n) رشدهای رایج‌اند. زمان و فضای کمکی جدا گزارش شوند. Big-O به ثانیه، latency قطعی یا performance benchmark تبدیل نمی‌شود.

در Big-O ورودی را تعریف کن (مثلاً n تعداد عناصر)، نوع حالت را نام ببر (بهترین/میانگین/بدترین)، و فضای کمکی را از حافظهٔ خود ورودی جدا کن. مرتبهٔ رشد زمان واقعی بر حسب ثانیه نیست؛ cache، تخصیص حافظه و ثابت‌های پیاده‌سازی هم اثر دارند.

## کاربرد واقعی و انتخاب مناسب

ظرفیت‌سنجی worst-case، مقایسهٔ ساختار و توضیح scale. در service، الگوریتم با بدترین ورودی نامطمئن شاید latency tail بسازد؛ case و distribution را کنار تحلیل بنویس.

پیش از انتخاب بپرس: چه عملیاتی پرتکرارند؟ آیا ترتیب مهم است؟ دادهٔ ورودی چه اندازه است؟ آیا محدودیت حافظه، latency بدترین‌حالت یا thread-safety داریم؟ ساختار خوب برای workload نامناسب می‌تواند انتخاب بدی باشد.

## خطاهای رایج و edge caseها

Big-O را «دقیقاً همین تعداد» نخوان. worst-case به‌عنوان تعریف نچسبان. n و m مستقل را در O(n+m) حفظ کن. constantهای بزرگ می‌توانند در n کوچک مهم باشند.

حالت‌های مرزی را جداگانه بررسی کن: ورودی خالی، یک عضو، همهٔ اعضا برابر، هدف غایب، حداقل/حداکثر مقدار و اندازهٔ بزرگ. سرریز عدد صحیح در محاسبهٔ اندیس/ظرفیت نیز بسته به زبان مهم است.

## تمرین‌های مرحله‌ای

۱) 3n²+7n+4 را Big-O و Θ کن. ۲) چرا Θ(n) عضو O(n²) است؟ ۳) hash table lookup را با average/worst دو ادعا بنویس.

برای هر تمرین، اول پاسخ ساده و درست بنویس، بعد پیچیدگی را حساب کن، سپس edge case اضافه کن. تمرین را با دست‌کم یک ورودی کوچک ردگیری کن و خروجی را با انتظار مستقل مقایسه کن.

## آزمون جامع با پاسخ تشریحی

ابتدا پاسخ‌ها را نخوان؛ جواب را با استدلال بنویس، سپس توضیح را مقایسه کن.

1. **پرسش:** تعریف Big-O؟
   **پاسخ تشریحی:** کران بالا تا یک ضریب ثابت برای n کافی بزرگ.
2. **پرسش:** آیا O(g) tight است؟
   **پاسخ تشریحی:** الزاماً نه؛ می‌تواند شل باشد.
3. **پرسش:** O(log n) در O(n) هم هست؟
   **پاسخ تشریحی:** بله، برای n کافی بزرگ؛ اما اطلاعاتش ضعیف‌تر است.
4. **پرسش:** بدترین‌حالت از خود O می‌آید؟
   **پاسخ تشریحی:** خیر، case باید جدا تعریف شود.
5. **پرسش:** append پویا؟
   **پاسخ تشریحی:** O(1) amortized؛ گاهی resize منفرد O(n).

## راهنمای بازگویی از حافظه
