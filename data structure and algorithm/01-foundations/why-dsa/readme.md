# چرا ساختمان داده مهم است؟

> مسیر: [فصل ۱ — پایه‌ها و تحلیل الگوریتم](../readme.md) · پیش‌نیاز پیشنهادی: فصل ۱ و مبانی برنامه‌نویسی · [English](readme.en.md)

## پیش‌نیازها و نقشهٔ ذهنی

درک input/output و برنامهٔ ساده. ابتدا مفهوم را به‌عنوان یک قرارداد ببین، سپس نمایش حافظه و عملیات را دنبال کن. هدف حفظ‌کردن نام نیست؛ باید بتوانی برای یک ورودی کوچک، state را بعد از هر گام بنویسی.

## ایده از پایه

DSA کمک می‌کند قبل از آنکه داده یا تعداد درخواست‌ها بزرگ شود، رفتار برنامه را پیش‌بینی کنی و راه‌حل درست را برای workload انتخاب کنی. ارزش آن فقط مصاحبه نیست: latency، هزینهٔ حافظه، throughput، پایداری و امکان توضیح trade-offها به آن وابسته‌اند.

## مدل، قرارداد و ناوردا

هر مسئله را با query/update mix، اندازه، ترتیب، خطا، رشد آینده و محدودیت سخت‌افزار توصیف کن. الگوریتم سریع برای query ممکن است update را گران کند؛ cache سریع باشد اما memory bound شود.

ناوردا (invariant) جمله‌ای است که در تمام مراحل الگوریتم باید درست بماند. نوشتن آن پیش از کدنویسی، هم به اثبات درستی کمک می‌کند و هم خطاهای مرزی را آشکار می‌سازد.

## الگوریتم یا عملیات گام‌به‌گام

مقایسهٔ membership در n عضو: list scan O(n)، sorted array binary search O(log n) اما update درج O(n)، hash set average O(1) اما order ندارد و worst collision O(n). انتخاب از نیاز واقعی می‌آید.

در پیاده‌سازی واقعی، قرارداد ورودی/خروجی را دقیق تعریف کن: رفتار ورودی تهی، مقدار تکراری، عنصر پیدا‌نشده و ظرفیت تمام‌شده باید روشن باشد.

## اجرای حل‌شده با ردگیری

اگر 100 رکورد و یک lookup باشد، hash index ساختن/نگهداری شاید سود نکند. اگر 10 میلیون رکورد و میلیون‌ها query باشد، index هزینهٔ حافظه/ساخت را جبران می‌کند. اندازهٔ کوچک/بزرگ و دفعات عملیات تصمیم را عوض می‌کند.

برای تمرین، جدولی با ستون‌های «گام»، «اندیس/اشاره‌گر»، «بخش فعال»، «تغییر state» و «دلیل» بساز. این روش به‌خصوص برای الگوریتم‌های درجا و تقسیم‌و‌غلبه جلوی پرش ذهنی را می‌گیرد.

## چرا درست است؟

ادعای بهبود باید با مقایسهٔ منصفانهٔ workload، ورودی نماینده و محدودیت صحت سنجیده شود. قبل از بهینه‌سازی، baseline و bottleneck واقعی را پیدا کن؛ حدس دربارهٔ زمان کافی نیست.

اثبات معمولاً سه بخش دارد: (۱) آغاز—ناوردا پیش از نخستین گام درست است؛ (۲) نگهداری—هر گام آن را حفظ می‌کند؛ (۳) پایان—شرط توقف همراه invariant جواب موردنیاز را نتیجه می‌دهد. اگر یکی از این سه بخش نامشخص است، هنوز درک الگوریتم کامل نشده است.

## تحلیل زمان و حافظه

Big-O مقیاس رشد را می‌گوید، profiling رفتار واقعی را. correctness و security نیز مهم‌اند: hash flooding، recursion exhaustion، integer overflow و memory allocation می‌توانند از complexity ظاهری مهم‌تر باشند.

در Big-O ورودی را تعریف کن (مثلاً n تعداد عناصر)، نوع حالت را نام ببر (بهترین/میانگین/بدترین)، و فضای کمکی را از حافظهٔ خود ورودی جدا کن. مرتبهٔ رشد زمان واقعی بر حسب ثانیه نیست؛ cache، تخصیص حافظه و ثابت‌های پیاده‌سازی هم اثر دارند.

## کاربرد واقعی و انتخاب مناسب

database indexing، routing، autocomplete، scheduling و queueing. دانش DSA کمک می‌کند واژهٔ «سریع» را با latency/space/throughput و فرض‌های مشخص جایگزین کنی.

پیش از انتخاب بپرس: چه عملیاتی پرتکرارند؟ آیا ترتیب مهم است؟ دادهٔ ورودی چه اندازه است؟ آیا محدودیت حافظه، latency بدترین‌حالت یا thread-safety داریم؟ ساختار خوب برای workload نامناسب می‌تواند انتخاب بدی باشد.

## خطاهای رایج و edge caseها

همیشه ساختار پیچیده‌تر سریع‌تر نیست؛ constant، locality، حجم کم و frequency operationها مهم‌اند. DSA جای مهندسی سیستم، تست، observability و معماری را نمی‌گیرد، بلکه ابزار استدلال است.

حالت‌های مرزی را جداگانه بررسی کن: ورودی خالی، یک عضو، همهٔ اعضا برابر، هدف غایب، حداقل/حداکثر مقدار و اندازهٔ بزرگ. سرریز عدد صحیح در محاسبهٔ اندیس/ظرفیت نیز بسته به زبان مهم است.

## تمرین‌های مرحله‌ای

۱) برای workload 90% read و 10% insert میان list/sorted array/hash trade-off بنویس. ۲) چه زمانی profile می‌کنی؟ ۳) یک مثال از پیامد انتخاب غلط: کندی، حافظه یا correctness بیاور.

برای هر تمرین، اول پاسخ ساده و درست بنویس، بعد پیچیدگی را حساب کن، سپس edge case اضافه کن. تمرین را با دست‌کم یک ورودی کوچک ردگیری کن و خروجی را با انتظار مستقل مقایسه کن.

## آزمون جامع با پاسخ تشریحی

ابتدا پاسخ‌ها را نخوان؛ جواب را با استدلال بنویس، سپس توضیح را مقایسه کن.

1. **پرسش:** فایدهٔ DSA در عمل؟
   **پاسخ تشریحی:** پیش‌بینی scale و انتخاب trade-off مناسب.
2. **پرسش:** آیا Big-O زمان دقیق است؟
   **پاسخ تشریحی:** خیر، نرخ رشد تحت مدل است؛ benchmark لازم است.
3. **پرسش:** یک index چه هزینه‌ای دارد؟
   **پاسخ تشریحی:** فضا و هزینهٔ نگهداری در write.
4. **پرسش:** کدام روش bottleneck را می‌یابد؟
   **پاسخ تشریحی:** اندازه‌گیری/profiling نماینده.
5. **پرسش:** DSA جایگزین چیست؟
   **پاسخ تشریحی:** ابزار تکمیلی مهندسی، نه جایگزین reliability و معماری.

## راهنمای بازگویی از حافظه

بدون نگاه به متن، ایده، پیش‌شرط، invariant، یک ردگیری واقعی، پیچیدگی، edge case و یک کاربرد را در چند دقیقه روی کاغذ توضیح بده. اگر فقط pseudocode را حفظی می‌نویسی اما دلیل درستی یا محدودیت‌ها را نمی‌دانی، یک بار دیگر بخش‌های invariant و خطاها را مرور کن.
