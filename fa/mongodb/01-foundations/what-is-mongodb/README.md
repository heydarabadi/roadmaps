# MongoDB چیست و چه وقت انتخاب مناسبی است؟

> **English edition:** [Read this lesson in English](../../../../en/mongodb/01-foundations/what-is-mongodb/README.md).

> **هدف یادگیری:** مدل سندی را توضیح دهید و انتخاب MongoDB را با نیاز واقعی بسنجید.

## جایگاه در مسیر
این درس بخشی از فصل مربوط است. مثال‌ها برای محیط آزمایشی‌اند؛ نسخه و قابلیت deployment خود را در مستندات رسمی بررسی کنید.

## آموزش
MongoDB پایگاه‌دادهٔ سندگراست: داده در سندهای BSON ذخیره و در collectionها سازمان‌دهی می‌شود. برنامه با driver وصل می‌شود؛ Atlas سرویس مدیریت‌شدهٔ ابری MongoDB است. انعطاف ساختار به معنی بی‌نیازی از طراحی، قرارداد و اعتبارسنجی نیست.

از queryها شروع کنید: چه داده‌ای با هم خوانده می‌شود؟ روابط و قیدها چقدر مهم‌اند؟ آیا transaction چندسندی لازم است؟ چه کسی backup، امنیت و پایش را انجام می‌دهد؟ مدل سندی برای داده‌های خودبسنده و ویژگی‌های متغیر می‌تواند مناسب باشد. اگر گزارش‌ها و قیدهای joinمحور غالب‌اند، پایگاه‌دادهٔ رابطه‌ای را هم ارزیابی کنید. هیچ گزینه‌ای همیشه سریع‌تر نیست؛ benchmark باید بار کاری واقعی را بازنمایی کند.

## تدریس کامل از صفر

### ۱) پایگاه داده در برنامه چه نقشی دارد؟

برنامه برای پاسخ‌دادن به درخواست کاربر باید داده را نگه دارد، پیدا کند و تغییر دهد. دیتابیس جایی است که این داده‌ها با قواعد مشخص ثبت می‌شوند. MongoDB یک server دارد که درخواست‌ها را از کلاینت می‌گیرد. کلاینت می‌تواند mongosh، Compass یا برنامه‌ای باشد که با یک driver رسمی نوشته شده است.

در پایگاه‌دادهٔ رابطه‌ای، معمولاً داده‌ها در table و row سازمان می‌گیرند. در MongoDB داده‌ها در document ذخیره می‌شوند. سند می‌تواند field، آرایه و سند توکار داشته باشد؛ بنابراین اطلاعاتی که برنامه همیشه باهم می‌خواند گاهی در یک سند طبیعی‌تر جا می‌گیرد. این تفاوت به معنی «رابطه نداشتن» یا «تراکنش نداشتن» نیست. MongoDB قابلیت reference، $lookup و transaction هم دارد.

### ۲) واژه‌های پایه را با یک مثال یاد بگیرید

فرض کنید اپ فروشگاه داریم:
- database: فضای منطقی داده‌های فروشگاه، مثلاً shop.
- collection: مجموعه‌ای از سندهای هم‌خانواده، مثل products و orders.
- document: یک محصول یا سفارش مشخص.
- field: ویژگی سند، مثل price یا createdAt.
- value: مقدار field، مثل عدد دقیق قیمت یا تاریخ ثبت سفارش.
- index: ساختاری کمکی برای پیدا کردن سندها بدون بررسی تک‌تک همهٔ collection.

مسیر معمول درخواست این است: API یک query را با driver می‌فرستد؛ server filter را ارزیابی می‌کند؛ index مناسب را انتخاب می‌کند؛ سندهای مطابق را می‌خواند یا می‌نویسد؛ نتیجه به driver و سپس به API برمی‌گردد.

### ۳) تصمیم انتخاب را با access pattern بگیرید

برای هر عملیات برنامه این سؤال‌ها را پاسخ دهید:
1. کاربر دقیقاً چه چیزی را می‌خواند؟
2. چه filter و sortی دارد؟
3. چه چیزی را با هم تغییر می‌دهد؟
4. آیا دادهٔ مرتبط باهم به‌روزرسانی می‌شود؟
5. اگر یکی از چند تغییر موفق و دیگری ناموفق باشد، چه رفتاری باید رخ دهد؟
6. داده چقدر رشد می‌کند و چه کسی آن را نگهداری می‌کند؟

مثلاً نمایش صفحهٔ محصول که عنوان، قیمت و چند ویژگی محدود را باهم می‌خواند می‌تواند با یک سند محصول خوب کار کند. گزارش‌های مالی پیچیده با قیدهای سخت بین چند موجودیت ممکن است با مدل رابطه‌ای ساده‌تر باشد. تصمیم باید با نمونهٔ واقعی workload سنجیده شود؛ هیچ قاعده‌ای نمی‌گوید یک دیتابیس برای همهٔ کارها بهتر است.

### ۴) مدل سندی به معنی schema-free نیست

MongoDB جلوی تنوع شکل سند را می‌گیرد، اما اگر برنامه انتظار داشته باشد stock همیشه عدد باشد، دادهٔ string می‌تواند query و محاسبه را خراب کند. قرارداد فیلدها را در برنامه و در صورت نیاز با schema validation enforce کنید. تغییر ساختار را هم مثل تغییر API مرحله‌بندی کنید: reader سازگار، writer جدید، مهاجرت اسناد قدیمی، و حذف شکل قدیمی.

### ۵) آزمایش انتخاب

برای یک سامانهٔ رزرو، سه طراحی را بنویسید:
- رزرو چگونه جست‌وجو می‌شود؟
- موجودی صندلی کجا ثبت می‌شود؟
- چه چیزی باید اتمیک باشد؟
- کدام اطلاعات کوچک و ثابت کنار رزرو embed می‌شوند؟
- آیا می‌توان گزارش درآمد را با queryهای عملیاتی اجرا کرد؟

جواب خوب فقط نام دیتابیس نیست؛ queryها، invariantها، هزینهٔ رشد، دسترس‌پذیری و برنامهٔ backup را هم روشن می‌کند.

### جمع‌بندی قابل حفظ

MongoDB یک پایگاه‌دادهٔ سندگرا با BSON، query، index، transaction و ابزارهای مقیاس‌دهی است. انتخابش را بر اساس شکل دسترسی و قواعد داده انجام دهید. schema را طراحی کنید، امنیت و پشتیبان‌گیری را از ابتدا در نظر بگیرید و ادعای سرعت را با benchmark خودتان بیازمایید.

## مثال
~~~javascript
{
  sku: "KB-42",
  title: "صفحه‌کلید",
  price: NumberDecimal("49.90"),
  attributes: { layout: "fa", wireless: true },
  categories: ["لوازم جانبی", "کامپیوتر"]
}
~~~

## تجربهٔ واقعی یا سناریوی کاربردی
مطالعهٔ موردی Forbes دربارهٔ مهاجرت CMS به Atlas، نیاز به توسعهٔ سریع و کاهش بار نگهداری زیرساخت را گزارش کرده است. این گزارش فروشنده/مشتری‌محور است و برتری MongoDB برای همهٔ CMSها را ثابت نمی‌کند؛ از آن پرسش‌های طراحی استخراج کنید.

## خطاهای رایج
- تصمیم با شعار «NoSQL همیشه مقیاس‌پذیرتر است».
- انتخاب فقط به دلیل انعطاف ظاهری schema.
- مقایسهٔ سرعت بدون workload یکسان.
- نادیده‌گرفتن گزارش‌گیری و هزینهٔ عملیات.

## تمرین
1. سه query پرتکرار فروشگاه را بنویسید و مشخص کنید چه داده‌ای با هم خوانده می‌شود.
2. برای سامانهٔ مالی، معیارهای انتخاب پایگاه‌دادهٔ رابطه‌ای و MongoDB را مقایسه کنید.

## آزمون و پاسخ
1. **پرسش:** واحد اصلی داده چیست؟
   **پاسخ:** سند BSON؛ سندها داخل collection قرار می‌گیرند.
2. **پرسش:** انعطاف schema یعنی نیازی به قرارداد نداریم؟
   **پاسخ:** خیر؛ validation و مهاجرت همچنان لازم‌اند.
3. **پرسش:** از چه چیزی انتخاب را شروع کنیم؟
   **پاسخ:** الگوی دسترسی و نیاز consistency؛ سپس رشد، هزینه و مهارت تیم.
4. **پرسش:** چرا باید از «تصمیم با شعار «NoSQL همیشه مقیاس‌پذیرتر است».» پرهیز کرد؟
   **پاسخ:** چون تصمیم‌گیری با شعار workload، قیدهای consistency و هزینهٔ عملیات را نادیده می‌گیرد؛ ابتدا queryها و invariantها را بنویسید و با دادهٔ نماینده اندازه بگیرید.
5. **مسئلهٔ کاربردی:** سه query پرتکرار فروشگاه را بنویسید و مشخص کنید چه داده‌ای با هم خوانده می‌شود.
   **پاسخ نمونه:** برای هر query سندهای درگیر، filter و sort را بنویسید؛ اگر سندهای مرتبط معمولاً یک‌جا خوانده می‌شوند و رشدشان محدود است embedding را بسنجید؛ روابط پررنگ و joinهای پیچیده می‌توانند گزینهٔ رابطه‌ای را مناسب‌تر کنند.

## آزمون تکمیلی — مفاهیم و تصمیم‌گیری

6. **پرسش:** آیا MongoDB بدون schema است؟
   **پاسخ:** خیر؛ انعطاف ساختار وجود دارد اما قرارداد، validation و مهاجرت لازم است.
7. **پرسش:** کدام queryها تصمیم مدل داده را هدایت می‌کنند؟
   **پاسخ:** خواندن، نوشتن، filter، sort، رابطه و رشد واقعی برنامه.
8. **پرسش:** چه وقت پایگاه‌دادهٔ رابطه‌ای را هم بررسی می‌کنیم؟
   **پاسخ:** وقتی قیدهای رابطه‌ای و گزارش‌های joinمحور غالب هستند.
9. **پرسش:** آیا $lookup وجود رابطه را نفی می‌کند؟
   **پاسخ:** خیر؛ MongoDB می‌تواند collectionها را به هم پیوند دهد.
10. **پرسش:** عملکرد MongoDB چگونه مقایسه می‌شود؟
   **پاسخ:** با benchmark برابر روی داده و workload نماینده، نه با ادعای عمومی.
