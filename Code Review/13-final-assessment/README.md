# آزمون جامع پایانی Code Review

**زبان:** فارسی · [English](../en/13-final-assessment/README.md)

این آزمون توان تشخیص و استدلال را می‌سنجد، نه حفظ اصطلاح‌ها را. پیش از خواندن پاسخ، انتخاب و دلیل را یادداشت کن. برای هر سؤال فقط یک گزینه بهترین پاسخ است؛ در بعضی موقعیت‌ها پاسخ نهایی به policy تیم وابسته است، اما سؤال فرض‌های لازم را می‌گوید.

## بخش اول — هدف و جریان

### ۱. PR پنج خط تغییر مجوز دارد. چه نتیجه‌ای می‌گیری؟

1. کم‌ریسک است چون کوچک است.
2. فقط یک approve لازم است.
3. اندازهٔ diff به‌تنهایی ریسک را تعیین نمی‌کند؛ دامنهٔ دسترسی و داده را دنبال می‌کنم.
4. تست دیگر لازم نیست.

**پاسخ: ۳.** تغییر کوچک می‌تواند سطح دسترسی را برای کاربران زیادی عوض کند. گزینه‌های ۱ و ۲ اندازه یا تعداد reviewer را بی‌دلیل به ریسک وصل می‌کنند؛ گزینهٔ ۴ هم آزمون مجوز را حذف می‌کند.

### ۲. Formatter موفق است و CI سبز؛ reviewer هنوز چه چیزی را بررسی می‌کند؟

1. هیچ چیز؛ سبز یعنی درست.
2. نیازمندی، رفتار، edge case و کنترل‌هایی که CI ندارد.
3. فقط تعداد commit.
4. فقط نام نویسنده.

**پاسخ: ۲.** CI فقط checkهای تعریف‌شده را اجرا می‌کند؛ formatter نیز semantics را نمی‌فهمد. سایر گزینه‌ها شواهد رفتاری نیستند.

### ۳. کدام PR نیازمند context بیشتر است؟

1. اصلاح فاصله با formatter.
2. تغییر API که رفتار null و دادهٔ قبلی را عوض می‌کند.
3. حذف comment تکراری بی‌اثر.
4. اصلاح typo در README.

**پاسخ: ۲.** قرارداد و دادهٔ قدیمی مصرف‌کننده دارند؛ سه مورد دیگر معمولاً دامنهٔ رفتاری کم‌تری دارند، هرچند مخزن مقصد را هم باید شناخت.

### ۴. هدف review چیست؟

1. اطمینان از حذف همهٔ باگ‌ها.
2. نگه‌داشتن سلامت تغییر و کاهش ریسک با شواهد و کنترل‌های مکمل.
3. برنده‌شدن reviewer در بحث.
4. برابرکردن style همهٔ پروژه‌ها.

**پاسخ: ۲.** Review کمک می‌کند اما تضمین ریاضی بی‌خطایی نیست. سه گزینهٔ دیگر یا مطلق‌اند یا سلیقه را قانون می‌کنند.

## بخش دوم — نویسنده

### ۵. شرح PR فقط می‌گوید «fix bug». چه چیزی کم است؟

1. رنگ ادیتور.
2. مسئله، راه‌حل، تست، اثر و محدودیت‌های مهم.
3. تعداد ساعت کار.
4. نام تک‌تک variableها.

**پاسخ: ۲.** شرح باید برای بازبین و آینده‌خوان دلیل تغییر و evidence را نگه دارد؛ بقیه به فهم تصمیم کمک نمی‌کنند.

### ۶. چرا self-review را روی diff نهایی انجام می‌دهیم؟

1. حافظهٔ نویسنده همیشه دقیق است.
2. فایل یا تغییر ناخواسته ممکن است بعد از کدنویسی وارد diff شده باشد.
3. برای جایگزین‌کردن تست.
4. چون reviewer نباید diff را بخواند.

**پاسخ: ۲.** هدف، خواندن تغییر واقعی از نگاه نفر تازه است؛ self-review تست را حذف نمی‌کند.

### ۷. PR بزرگ را چه وقت می‌شکنی؟

1. همیشه به فایل‌های یک‌خطی.
2. وقتی بخش‌ها هدف و مرز معنادار و استقرار امن دارند.
3. وقتی هر مرحله سیستم را عمداً خراب می‌کند.
4. فقط وقتی reviewer درخواست کند.

**پاسخ: ۲.** شکست باید قابلیت فهم را زیاد کند نه این‌که history یا سیستم را بی‌معنا سازد. عدد خط ثابت وجود ندارد.

### ۸. برای bug، تست بازتولیدکننده چه نتیجه‌ای دارد؟

1. پیش از اصلاح fail و پس از اصلاح pass می‌شود.
2. فقط تابع موردنظر را صدا می‌زند.
3. coverage را بدون assertion بالا می‌برد.
4. به دادهٔ مورد انتظار احتیاج ندارد.

**پاسخ: ۱.** این چرخه نشان می‌دهد تست واقعاً به رفتار معیوب وصل است؛ گزینه‌های دیگر می‌توانند تست ظاهری بسازند.

## بخش سوم — آماده‌سازی بازبین

### ۹. اولین گذر روی یک PR پیچیده چیست؟

1. نوشتن comment روی اولین خط عجیب.
2. خواندن هدف و نیازمندی، سپس نقشهٔ فایل‌ها و اثر تغییر.
3. شمارش خطوط.
4. اجرای formatter روی branch نویسنده.

**پاسخ: ۲.** context پیش از قضاوت لازم است؛ باقی گزینه‌ها هدف و رفتار را روشن نمی‌کنند.

### ۱۰. CODEOWNERS چه چیزی را ثابت نمی‌کند؟

1. مالکیت فایل را نشان می‌دهد.
2. می‌تواند reviewer را به مسیر تغییر وصل کند.
3. به‌تنهایی کیفیت یا درستی منطق را تضمین می‌کند.
4. می‌تواند با branch rule ترکیب شود.

**پاسخ: ۳.** مکانیزم route/approval است؛ مالکیت قدیمی یا review سطحی هنوز ممکن است.

### ۱۱. بازبین تخصص لازم ندارد و تغییر auth حساس است. بهترین پاسخ چیست؟

1. حدس بزند و approve کند.
2. تخصصش را روشن کند و domain/security reviewer بخواهد.
3. از نویسنده بخواهد خودش approve کند.
4. فقط به لحن مطمئن نویسنده اعتماد کند.

**پاسخ: ۲.** عدم قطعیت را مدیریت می‌کند؛ بقیه risk را پنهان یا کنترل را بی‌اثر می‌کنند.

### ۱۲. reviewer برای یک PR کوچک چه باید کند؟

1. همیشه review کامل امنیتی/عملیاتی همهٔ مخزن.
2. سطح بررسی را با رفتار و ریسک همین تغییر متناسب کند.
3. بدون خواندن شرح approve کند.
4. تغییر کوچک را ذاتاً بی‌اهمیت بداند.

**پاسخ: ۲.** سطح بررسی متناسب است؛ کم‌حجمی به‌تنهایی کافی نیست.

## بخش چهارم — بررسی فنی

### ۱۳. تست فقط می‌گوید تابع gateway فراخوانی شد. چه چیز ممکن است جا بماند؟

1. هیچ چیز.
2. مبلغ/وضعیت نهایی و رفتار واقعی retry یا ذخیره‌سازی.
3. فقط indentation.
4. نام branch.

**پاسخ: ۲.** فراخوانی mock لزوماً نتیجهٔ کسب‌وکار را ثابت نمی‌کند؛ باقی گزینه‌ها به رفتار کاربر وصل نیستند.

### ۱۴. کاربر login کرده اما سفارش tenant دیگر را درخواست می‌کند. کدام کنترل لازم است؟

1. Authentication دوباره.
2. Authorization شیء/tenant بر اساس هویت فعلی.
3. Formatter.
4. فقط rate limit.

**پاسخ: ۲.** احراز هویت هویت را می‌شناسد؛ مجوز باید دسترسی به همان resource را محدود کند.

### ۱۵. SAST سبز است؛ چه چیزی همچنان نیاز review انسانی دارد؟

1. هیچ چیز.
2. منطق کسب‌وکار، کنترل دسترسی context-specific و مسیرهای دادهٔ پیچیده.
3. فقط تعداد خطوط.
4. نام branch.

**پاسخ: ۲.** ابزار الگوهایی را می‌یابد که تعریف شده‌اند، نه همهٔ معنای business logic.

### ۱۶. بعد از افزودن retry به پرداخت، پرسش مهم چیست؟

1. آیا نام متغیر کوتاه است؟
2. آیا درخواست تکراری idempotent است و تعداد retry محدود می‌شود؟
3. آیا همهٔ warningها خاموش‌اند؟
4. آیا branch نام انگلیسی دارد؟

**پاسخ: ۲.** retry بدون idempotency می‌تواند charge تکراری و بار تشدیدشونده بسازد.

### ۱۷. Migration روی جدول بزرگ چه شواهدی می‌خواهد؟

1. فقط compile موفق.
2. plan اجرا، سازگاری نسخه‌ها، مدت/قفل، دادهٔ قدیمی و recovery.
3. یک screenshot UI.
4. تعداد approval ثابت برای همهٔ شرکت‌ها.

**پاسخ: ۲.** تغییر schema با داده و سرویس‌های زنده تعامل دارد؛ عدد approval به‌تنهایی معیار فنی نیست.

### ۱۸. کدام benchmark قابل‌تفسیرتر است؟

1. «سریع‌تر شد» بدون عدد.
2. روش، محیط، داده، تکرار و مقایسهٔ قبل/بعد مشخص.
3. یک اجرا روی لپ‌تاپ بدون ثبت.
4. مقایسه با خاطرهٔ توسعه‌دهنده.

**پاسخ: ۲.** نتیجه را قابل بازبینی می‌کند؛ بقیه روش یا baseline ندارند.

## بخش پنجم — بازخورد و اختلاف

### ۱۹. کدام comment سازنده‌تر است؟

1. «این افتضاح است.»
2. «دو request هم‌زمان ممکن است هر دو موجودی را ببینند؛ آیا transaction این invariant را حفظ می‌کند؟»
3. «تو concurrency بلد نیستی.»
4. «بهترش کن.»

**پاسخ: ۲.** رفتار و خطر را مشخص و سؤال قابل‌پاسخ مطرح می‌کند؛ دیگر گزینه‌ها توهین‌آمیز یا مبهم‌اند.

### ۲۰. اختلاف فقط دربارهٔ نام‌گذاری است و style guide/formatter دارد. چه می‌کنی؟

1. PR را blocker می‌کنی.
2. قاعدهٔ تیم یا formatter را مرجع می‌گیری و سلیقه را تحمیل نمی‌کنی.
3. reviewer با رتبهٔ بالاتر برنده است.
4. بحث را خارج از PR ادامه می‌دهی بدون تصمیم ثبت‌شده.

**پاسخ: ۲.** قانون توافق‌شده راه تکرار اختلاف را می‌بندد؛ نظر شخصی علت blocking نیست.

### ۲۱. comment واقعاً اختیاری است. چه برچسبی مناسب‌تر است؟

1. blocker.
2. nit یا suggestion طبق قرارداد تیم، و توضیح این‌که merge را متوقف نمی‌کند.
3. security.
4. request changes بدون توضیح.

**پاسخ: ۲.** شدت باید واقعی باشد؛ اصطلاح دقیق را تیم تعریف می‌کند.

### ۲۲. بحث review دور می‌زند. چه کار می‌کنی؟

1. کامنت‌ها را زیاد می‌کنی.
2. مسئله، معیار، گزینه‌ها و owner تصمیم را مشخص و نتیجه را ثبت می‌کنی.
3. نویسنده را تهدید می‌کنی.
4. بدون تصمیم merge می‌کنی.

**پاسخ: ۲.** گفت‌وگو را به تصمیم قابل‌ردیابی تبدیل می‌کند.

## بخش ششم — پاسخ و merge

### ۲۳. نویسنده با suggestion مخالف است. چه پاسخ مناسبی است؟

1. سکوت.
2. دلیل و شواهد/قیود را ثبت کند و در صورت لزوم clarification بخواهد.
3. thread را بی‌توضیح resolve کند.
4. بحث را شخصی کند.

**پاسخ: ۲.** مخالفت مستدل بخشی از همکاری است؛ سکوت وضعیت را مبهم می‌کند.

### ۲۴. thread resolved شده؛ آیا این کافی است؟

1. بله، ابزار correctness را ثابت می‌کند.
2. خیر؛ نتیجهٔ کد و آزمون باید بررسی شود.
3. فقط اگر نویسنده senior باشد.
4. بله، اگر CI قدیمی سبز است.

**پاسخ: ۲.** وضعیت گفت‌وگو و صحت revision دو مفهوم‌اند.

### ۲۵. approval پیش از push جدید صادر شده؛ چه چیزی را بررسی می‌کنی؟

1. فقط تعداد approvals.
2. diff تازه، CI برای HEAD و policy stale approval.
3. آخرین comment مثبت.
4. فقط عنوان PR.

**پاسخ: ۲.** تایید به چیزی مربوط است که reviewer دیده است.

### ۲۶. پس از merge چه چیزی برای تغییر پراثر لازم است؟

1. فرض کنیم CI سلامت production را ثابت کرده.
2. rollout، metric مرتبط، alert مالک‌دار و recovery plan.
3. حذف همهٔ logها.
4. بیشترکردن commentهای review.

**پاسخ: ۲.** کنترل تغییر پس از ادغام ادامه دارد؛ بقیه evidence عملیاتی نیستند.

## بخش هفتم — تیم و تجربهٔ صنعتی

### ۲۷. کدام مورد KPI فردی ضعیفی است؟

1. نمونه‌برداری کیفیت review و روند rework.
2. تعداد commentهای گذاشته‌شده.
3. اندازهٔ صف و زمان اولین پاسخ برای تحلیل جریان.
4. توزیع دانش و بار review.

**پاسخ: ۲.** comment count به‌راحتی nit یا نظر بی‌ارزش را تشویق می‌کند.

### ۲۸. CI flaky است و تیم هشدارها را نادیده می‌گیرد. اقدام چیست؟

1. هشدارها را کامل خاموش کنیم.
2. flaky test را ownerدار و قابل‌رفع کنیم و policy رسیدگی روشن کنیم.
3. approveها را بیشتر کنیم.
4. نویسنده‌ها را مقصر بدانیم.

**پاسخ: ۲.** کنترل باید قابل‌اعتماد باشد؛ خاموش‌کردن همهٔ هشدارها پوشش را حذف می‌کند.

### ۲۹. از Cloudflare 2019 چه نتیجهٔ دقیق‌تری می‌توان گرفت؟

1. علت قطعاً reviewer بی‌توجه بود.
2. worst-case performance، تست، rollout و کنترل blast radius باید بررسی شوند؛ جزئیات علت را از گزارش رسمی جدا نقل کن.
3. regex نباید هیچ‌وقت استفاده شود.
4. بیشتر reviewerها همیشه حادثه را پیشگیری می‌کنند.

**پاسخ: ۲.** این نتیجه درس مهندسی است بدون تقلیل postmortem به یک فرد یا یک عامل.

### ۳۰. incident postmortem را چطور به فرایند تبدیل می‌کنی؟

1. فرد مقصر را ثبت و پرونده را می‌بندی.
2. finding را به تست، guardrail، rollout یا runbook دارای owner تبدیل می‌کنی.
3. تعداد approvalها را بدون تحلیل زیاد می‌کنی.
4. علت را در چت موقت می‌گذاری.

**پاسخ: ۲.** هدف یادگیری قابل‌اقدام و کاهش احتمال تکرار است.

## نمره و تفسیر

- **۲۷ تا ۳۰:** توان تحلیل مستقل خوب است؛ روی سیستم واقعی، policy و تخصص حوزه را بیاموز.
- **۲۲ تا ۲۶:** پایه قوی است؛ سؤال‌های اشتباه را به فصل مربوط برگردان و دوباره با PR تمرین کن.
- **۱۵ تا ۲۱:** مفاهیم کلی آشناست؛ برای هر اشتباه یک سناریوی واقعی و شاهد بنویس.
- **کمتر از ۱۵:** آزمون را دوباره از ابتدا حفظ نکن؛ مسیر چهار‌هفته‌ای را انجام بده و هر بار دلیل گزینه‌ها را بنویس.

نمره به‌تنهایی صلاحیت امنیتی یا اجازهٔ approve نمی‌دهد. تصمیم واقعی به حوزه، policy، زمینه و evidence مربوط است.
