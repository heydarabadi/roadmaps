## آموزش

تغییر در بار واقعی‌نما ممکن است مشکلی نشان دهد که تست واحد نشان نمی‌دهد: N+1 query، پیچیدگی رشدکننده، regex پرهزینه، cache stampede، retry بدون سقف یا مصرف حافظه. در مسیر پرترافیک benchmark، query plan یا آزمون بدترین حالت بخواه؛ عدد بدون محیط و داده قابل تفسیر نیست.

عملیات هم بخشی از تغییر است. timeout و retry، logging/metrics، health check، rollout تدریجی، rollback، schema compatibility و راه تشخیص را بسنج. برای تغییر پراثر، مالک alert و حد توقف را معلوم کن. docs و runbook باید رفتار واقعی را توضیح دهند.

Cloudflare دربارهٔ رخداد ۲۰۱۹ خود نوشت یک regex در WAF باعث مصرف شدید CPU و قطعی شد. درس قابل دفاع، بررسی worst-case و دفاع چندلایه است؛ منبع حادثه را صرفاً به اشتباه reviewer نسبت نمی‌دهد.

## روند پیشنهادی

1. مسیرهای hot و اندازهٔ ورودی را پیدا کن.
2. پیچیدگی، query plan و tail latency را بررسی کن.
3. dependency failure، timeout و retry را دنبال کن.
4. rollout، metric، alert، rollback و runbook را ببین.
5. نتیجهٔ benchmark را با روش/محیط مستند کن.

## مثال کاربردی

تغییر query روی درصد کمی از ترافیک فعال می‌شود؛ p95 latency و database load اندازه‌گیری می‌شود؛ اگر حد مشخصی رد شد flag خاموش می‌شود. merge به‌تنهایی نشانهٔ سلامت production نیست.

## خطاهای رایج

micro-optimization بی‌داده نخواه؛ average را به‌جای tail latency نسنج؛ retry بی‌سقف را تاب‌آوری ننام؛ deploy green را سلامت تولید فرض نکن.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آموزش عمیق: از complexity تا rollout

### کارایی را از روی مسیر واقعی بسنج

برای هر کار سنگین بپرس: تعداد ورودی‌ها چقدر می‌شود؟ هزینه با رشد داده چگونه بالا می‌رود؟ آیا query در حلقه اجرا می‌شود؟ cache چطور invalidate می‌شود؟ concurrency و queue چه فشاری ایجاد می‌کنند؟ به Big-O توجه کن، اما آن را جای اندازه‌گیری نگذار: ضریب ثابت، دیتابیس، شبکه و شکل داده ممکن است نتیجه را عوض کنند.

- **N+1 query:** برای هر رکورد یک درخواست جدا به DB؛ تعداد رفت‌وبرگشت با تعداد نتیجه رشد می‌کند.
- **Tail latency:** میانگین پاسخ ممکن است مناسب باشد ولی درصد کمی از درخواست‌ها بسیار کند شوند.
- **Retry amplification:** سرویس کند می‌شود، clientها retry می‌کنند و بار بیشتر، کندی را تشدید می‌کند.
- **Resource exhaustion:** زمان CPU، حافظه، thread، اتصال یا فضای دیسک محدود است.
- **Cache stampede:** انقضای هم‌زمان کلیدها درخواست فراوانی را به منبع اصلی می‌فرستد.

برای benchmark، محیط، حجم/توزیع داده، نسخه، تعداد اجرا و مقایسهٔ قبل/بعد را ثبت کن. یک عدد روی لپ‌تاپ evidence کافی برای ادعای production نیست.

### Resilience و شکست وابستگی

timeout را مشخص کن؛ retry باید محدود، با backoff و مناسب idempotency باشد؛ circuit breaker یا queue فقط وقتی ارزش دارد که رفتار شکست و recovery تعریف شده باشد. retry عملیات غیر-idempotent ممکن است سفارش یا پرداخت تکراری بسازد. برای خطای دائمی، retry بی‌پایان سیستم را پر می‌کند.

### آمادگی انتشار

تغییر عملیاتی را همراه کد ببین: metric هدف، alert با owner، rollout مرحله‌ای، feature flag، سازگاری schema در rolling deploy و راه بازگشت. rollback همیشه ممکن نیست؛ اگر migration داده حذف کرده، باید روش forward-fix یا backup روشن باشد. پایش نیز باید به هدف feature وصل باشد، نه فقط dashboard عمومی.

### مثال: query تازه

PR صفحه‌ای می‌سازد که سفارش‌ها را می‌آورد و برای هر سفارش وضعیت ارسال را جدا می‌خواند. با ۱۰ سفارش شاید خوب به‌نظر برسد؛ با ۲۰هزار ردیف، N+1 بار ایجاد می‌کند. reviewer می‌پرسد آیا join یا batch query مناسب است، صفحه‌بندی محدود است، index لازم داریم و p95 تحت بار نماینده چیست. سپس rollout کم‌دامنه و metric تعداد query را هم بررسی می‌کند.

### درس پروندهٔ Cloudflare

Cloudflare دربارهٔ رخداد ۲۰۱۹ گزارش داد regex در WAF مصرف CPU را شدیداً بالا برد. از این پرونده می‌توان پرسید: آیا بدترین ورودی آزموده شده؟ آیا engine محدودیت زمانی دارد؟ آیا فعال‌سازی تدریجی و راه خاموش‌کردن rule وجود دارد؟ این پرسش‌ها lesson مهندسی‌اند؛ نسبت‌دادن کل حادثه به یک reviewer یا یک کامنت از گزارش رسمی نتیجه نمی‌شود.

### تمرین

تغییری را تصور کن که timeout سرویس بیرونی را از ۲ به ۳۰ ثانیه زیاد می‌کند. چه metricها و خطرهایی بررسی می‌کنی؟ پاسخ نمونه: تعداد connection/thread در حال انتظار، tail latency، timeout caller، retry و ظرفیت pool؛ آیا timeout بلند باعث انباشت کار می‌شود؟ هدف باید نرخ موفقیت و زمنیهٔ کاری مرتبط باشد، نه «عدد timeout بزرگ‌تر پس بهتر».
