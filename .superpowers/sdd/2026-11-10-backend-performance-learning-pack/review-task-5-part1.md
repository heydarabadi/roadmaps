   3: # استخر اتصال — Connection Pooling
   4: 
   5: **هدف یادگیری:** بتوانید بازاستفاده از اتصال را از کش داده جدا کنید، اندازه Pool را با ظرفیت دیتابیس تنظیم کنید و علت انتظار گرفتن اتصال را تشخیص دهید. **بررسی منابع: ۲۰۲۶-۱۱-۱۰**؛ مثال‌ها آموزشی و اجرا‌نشده‌اند.
   6: 
   7: ## مدل ذهنی و سازوکار
   8: 
   9: ساخت اتصال شامل شبکه، احراز هویت و ایجاد نشست است. Pool اتصال‌های باز را نگه می‌دارد؛ درخواست اتصال را قرض می‌گیرد، کار کوتاه خود را انجام می‌دهد و در مسیر موفقیت یا خطا پس می‌دهد. Pool محدود، هم‌زمانی ورود به دیتابیس را کنترل می‌کند؛ ظرفیت اجرای SQL نامحدود نمی‌شود.
  10: 
  11: | مرحله | زمان قابل اندازه‌گیری | علت احتمالی کندی |
  12: | --- | --- | --- |
  13: | گرفتن اتصال | acquire wait | Pool اشباع، نشت، تراکنش طولانی |
  14: | اجرای SQL | execution/lock wait | پلن، قفل، I/O یا CPU |
  15: | آزادسازی | hold duration | نگه‌داشتن اتصال حین تماس با سرویس دیگر |
  16: 
  17: Pool در driver و Pooler بیرونی دو لایه متفاوت‌اند. در [PgBouncer](https://www.pgbouncer.org/config)، حالت session اتصال سرور را تا قطع کلاینت، transaction تا پایان تراکنش، و statement تا پایان statement نگه می‌دارد؛ حالت آخر تراکنش چنددستوری را نمی‌پذیرد. این تفاوت روی state نشست اثر دارد.
  18: 
  19: ## کاربرد و مصالحه
  20: 
  21: برای درخواست‌های کوتاه پرتکرار مفید است. تراکنش طولانی یا session state مانند temp table و SET پایدار نیازمند بررسی سازگاری حالت Pooler است. پشتیبانی prepared statement به نسخه، driver، پروتکل و تنظیم وابسته است؛ PgBouncer با `max_prepared_statements` غیرصفر برخی prepared statementهای نام‌دار در سطح پروتکل را مدیریت می‌کند، اما SQL-level PREPARE همان رفتار را ندارد. عدد تنظیم را از مستند نسخه خود بردارید.
  22: 
  23: Pool بزرگ‌تر صف را موقتاً کم می‌کند، ولی می‌تواند رقابت CPU، حافظه و قفل را بیشتر کند. timeout گرفتن اتصال، deadline درخواست و سیاست رد بار را هماهنگ کنید؛ retry بی‌وقفه صف جدید می‌سازد.
  24: 
  25: ## مثال حل‌شده
  26: 
  27: فرض آموزشی: ۴ نمونه برنامه، هرکدام Pool حداکثر ۲۰ اتصال؛ مجموع بالقوه ۸۰ اتصال است. اگر بودجه توافق‌شده این سرویس در دیتابیس ۶۰ باشد، تنظیم قابل قبول نیست؛ حتی اگر هر نمونه جداگانه سالم به نظر برسد. رزرو admin، worker و سرویس‌های دیگر نیز باید جدا حساب شود.
  28: 
  29: <div dir="ltr" align="left">
  30: 
  31: ```text
  32: connection = pool.acquire(timeout = remaining_request_budget)
  33: try:
  34:     begin(connection)
  35:     rows = query(connection, parameterized_sql)
  36:     commit(connection)
  37:     return rows
  38: catch error:
  39:     rollback_if_needed(connection)
  40:     raise error
  41: finally:
  42:     pool.release_or_discard_broken(connection)
  43: ```
  44: 
  45: </div>
  46: 
  47: تماس HTTP یا پردازش تصویر را پیش از گرفتن اتصال یا پس از آزادسازی انجام دهید، مگر نیاز تراکنشی مشخصی وجود داشته باشد. rollback خطادار یا اتصال خراب نباید بدون پاک‌سازی به مصرف‌کننده بعد برسد.
  48: 
  49: ## تمرین کوچک و مشاهده مورد انتظار
  50: 
  51: در یک محیط آزمایشی ۱۰ درخواست هم‌زمان را با Pool دواتصالی اجرا کنید؛ هر query را عمداً ۱۰۰ میلی‌ثانیه شبیه‌سازی کنید و acquire wait/hold time را جدا بنویسید. سپس یک درخواست را در مسیر خطا قرار دهید و آزادسازی را بررسی کنید. انتظار: درخواست‌ها در چند موج سرویس می‌گیرند؛ زمان SQL ثابت می‌ماند ولی انتظار Pool رشد می‌کند. پس از خطا، ظرفیت باید به دو برگردد. این آزمایش throughput واقعی موتور را ثابت نمی‌کند.
  52: 
  53: ## شاهد عمومی و حد شواهد
  54: 
  55: [مستند عملیاتی PgBouncer](https://www.pgbouncer.org/config) چرخه آزادسازی و محدودیت‌های حالت‌ها را مستند می‌کند. این شاهد رفتار ابزار است؛ مطالعه موردی عمومی با درصد بهبود قابل تعمیم برای مثال این درس ارائه نشده است. اندازه ۲۰ در مثال، گزارش شرکت یا توصیه پیش‌فرض نیست.

  57: ## شکست‌ها، سیگنال‌ها و چک‌لیست عملیاتی
  58: 
  59: نشت اتصال با busy ثابت و رشد acquire timeout دیده می‌شود. `idle in transaction` می‌تواند قفل/نسخه قدیمی نگه دارد. Scale-out برنامه، failover یا بازسازی هم‌زمان Poolها نیز می‌تواند هجوم اتصال بسازد. شمارش waiters را کنار CPU و active transaction ببینید.
  60: 
  61: - [ ] سقف تجمعی تمام نمونه‌ها، workerها و کاربران Pooler معلوم است.
  62: - [ ] acquire timeout و deadline سراسری محدودند؛ صف نامحدود نیست.
  63: - [ ] finally/cleanup و rollback در مسیر خطا وجود دارد.
  64: - [ ] سازگاری session state و prepared statement برای نسخه واقعی بررسی شده است.
  65: - [ ] acquire wait، hold time، busy/idle، timeouts و DB saturation ثبت می‌شوند.
  66: - [ ] رفتار failover، اتصال شکسته و بازاتصال تدریجی مشخص است.

   3: # ایندکس — کم‌کردن مسیر جستجو
   4: 
   5: **هدف یادگیری:** از روی فیلتر و ترتیب یک query ایندکس پیشنهادی بسازید، استفاده واقعی آن را بررسی کنید و هزینه write را در تصمیم وارد کنید. **بررسی منابع: ۲۰۲۶-۱۱-۱۰**؛ SQL نمونه برای PostgreSQL است و اجرا نشده است.
   6: 
   7: ## مدل ذهنی
   8: 
   9: ایندکس ساختار کمکی برای پیدا کردن ردیف‌هاست؛ همه پرس‌وجوها از آن سود نمی‌برند. اگر بیشتر جدول لازم باشد یا جدول بسیار کوچک باشد، Sequential scan ممکن است انتخاب درست باشد. در ایندکس مرکب ترتیب ستون‌ها به فیلتر، sort و قابلیت موتور بستگی دارد؛ نسخه‌ها و نوع index را یکسان فرض نکنید.
  10: 
  11: | الگوی دسترسی | گزینه بررسی | هزینه همراه |
  12: | --- | --- | --- |
  13: | برابری مشتری و ترتیب زمان | B-tree مرکب | write و فضای بیشتر |
  14: | شرط روی زیرمجموعه ثابت | Partial index در موتور پشتیبان | predicate باید قابل استفاده باشد |
  15: | داده فضایی | GiST/PostGIS مناسب عملگر | دانش نوع و operator class |
  16: | بازگشت ستون‌های محدود | Covering index | index پهن‌تر و هزینه نگهداری |
  17: 
  18: ابتدا SQL واقعی و پارامتر نماینده را پیدا کنید؛ آمار را به‌روز کنید؛ پلن و bufferها را ببینید؛ یک تغییر انجام دهید؛ با بار مشابه read/write مقایسه کنید. [راهنمای PostgreSQL درباره بررسی استفاده ایندکس](https://www.postgresql.org/docs/current/indexes-examine.html) بر آمار و داده نماینده تأکید می‌کند.
  19: 
  20: ## کاربرد و مصالحه
  21: 
  22: ایندکس برای جستجوی انتخابی یا ترتیب سازگار مفید است. برای ستون کم‌تمایز نیز ممکن است در ترکیب مناسب سودمند باشد، ولی نام ستون به‌تنهایی تصمیم را تعیین نمی‌کند. هر INSERT/UPDATE/DELETE ممکن است کار ایندکس و WAL بیشتری ایجاد کند. تابع یا cast روی ستون می‌تواند مسیر استفاده از ایندکس معمولی را تغییر دهد. حذف ایندکس «کم‌مصرف» بدون دیدن بازه کامل workload و نقش constraint خطرناک است.
  23: 
  24: ## مثال حل‌شده
  25: 
  26: جدول فرضی `orders(id bigint primary key, customer_id bigint, created_at timestamp, total numeric)` را در نظر بگیرید. برای فهرست آخرین سفارش‌های یک مشتری:
  27: 
  28: <div dir="ltr" align="left">
  29: 
  30: ```sql
  31: CREATE INDEX orders_customer_time_idx
  32:     ON orders(customer_id, created_at DESC, id DESC);
  33: 
  34: EXPLAIN (ANALYZE, BUFFERS)
  35: SELECT id, created_at, total
  36: FROM orders
  37: WHERE customer_id = 42
  38: ORDER BY created_at DESC, id DESC
  39: LIMIT 20;
  40: ```
  41: 
  42: </div>
  43: 
  44: برابری روی مشتری و ترتیب همسان، نامزد مسیر index scan با توقف زودهنگام است؛ پلن قطعی یا زمان مشخص تضمین نمی‌شود. `id` ترتیب زمان‌های مساوی را قطعی می‌کند. `EXPLAIN ANALYZE` واقعاً query را اجرا می‌کند؛ در آزمایش SELECT هم بار ایجاد می‌شود.
  45: 
  46: ## تمرین کوچک و مشاهده مورد انتظار
  47: 
  48: در دیتابیس آزمایشی برای ۱۰۰ مشتری، ۱۰۰ هزار سفارش با توزیع نامتوازن بسازید. پیش و پس از index و `ANALYZE orders`، query بالا را برای مشتری کوچک و بزرگ بررسی کنید. rows، sort، buffer hit/read و زمان را یادداشت کنید؛ سپس هزینه درج یک batch یکسان را بسنجید. انتظار: index ممکن است خواندن/مرتب‌سازی را کم کند، اما write رایگان نیست و مشتری‌های متفاوت می‌توانند پلن متفاوت داشته باشند. با ۱۰ ردیف نتیجه معنادار ظرفیت نگیرید.
  49: 
  50: ## شاهد عمومی و حد شواهد
  51: 
  52: [مستند رسمی PostgreSQL](https://www.postgresql.org/docs/current/indexes-examine.html) توضیح می‌دهد چرا داده کوچک و توزیع غیرواقعی نتیجه آزمایش را منحرف می‌کند؛ شاهد اصلی این درس عملیاتی است. [نوشته فارسی آرتا سنجش نگار درباره PostGIS](https://asnegar.ir/blog/postgis-optimization/) نیز نمونه عمومی تغییر پلن فضایی گزارش می‌کند؛ عددهای آن مستقل بازتولید نشده و رفتار GiST را نباید به B-tree تعمیم داد. ادعای «بدون قفل» برای ساخت concurrent را مطلق نخوانید؛ محدودیت و مراحل آن را از مستند موتور بررسی کنید.
  53:

   3: # راهبرد دریافت در ORM — Lazy، Eager و Batch
   4: 
   5: **هدف یادگیری:** N+1 را از روی SQL شناسایی کنید، بین join و batch انتخاب کنید و تعداد query را کنار اندازه داده بسنجید. **بررسی منابع: ۲۰۲۶-۱۱-۱۰**؛ مثال مستقل از ORM و اجرا‌نشده است.
   6: 
   7: ## مدل ذهنی
   8: 
   9: Lazy loading رابطه را هنگام دسترسی می‌خواند. Eager loading آن را پیشاپیش دریافت می‌کند؛ ممکن است با join یا query جدا باشد. Batch/select-in شناسه‌ها را جمع می‌کند و چند رابطه را یک‌جا می‌خواند. اصطلاح Eager الزاماً به معنی «دقیقاً یک SQL» نیست.
  10: 
  11: | راهبرد | شکل کار | خطر |
  12: | --- | --- | --- |
  13: | Lazy | query پایه و سپس دریافت موردی | N+1 و I/O پنهان در serializer |
  14: | Joined eager | یک join با داده تکراری والد | افزایش شدید ردیف‌ها در چند collection |
  15: | Batch/select-in | والدها، سپس فرزندان با مجموعه ID | حد پارامتر، حافظه و چند snapshot |
  16: 
  17: اگر ۲۰ سفارش و برای هرکدام query مشتری اجرا شود، الگوی ۱+۲۰ داریم؛ identity map یا cache برخی ORMها ممکن است شمارش را کاهش دهد، پس SQL واقعی را بشمارید. [مستند SQLAlchemy 2.0](https://docs.sqlalchemy.org/en/20/orm/queryguide/relationships.html) تفاوت lazy، joined و select-in و راه جلوگیری از lazy ناخواسته را شرح می‌دهد؛ API هر ORM را جدا بررسی کنید.
  18: 
  19: ## کاربرد و مصالحه
  20: 
  21: برای یک رابطه تک‌مقداری کوچک، join می‌تواند مناسب باشد. دو collection با ۱۰ و ۵ فرزند ممکن است ۵۰ ردیف ترکیبی برای یک والد بسازند؛ batch گاهی بایت و حافظه کمتری می‌گیرد، هرچند round-trip بیشتری دارد. Lazy برای روابطی که اغلب استفاده نمی‌شوند می‌تواند قابل قبول باشد. فهرست نامحدود را eager نکنید. خواندن دو query در isolation معمول ممکن است تغییر هم‌زمان را ببیند؛ اگر snapshot ثابت لازم است، تراکنش/isolation متناسب را طراحی کنید.
  22: 
  23: ## مثال حل‌شده
  24: 
  25: طرح فرضی: `orders(id, customer_id)` و `customers(id, name)`. فهرست فقط شناسه سفارش و نام مشتری می‌خواهد. دریافت ۲۰ والد و نام مشتری‌های یکتا به صورت batch:
  26: 
  27: <div dir="ltr" align="left">
  28: 
  29: ```sql
  30: SELECT id, customer_id FROM orders ORDER BY id DESC LIMIT 20;
  31: -- Application collects DISTINCT customer_id values, e.g. 7, 9, 12.
  32: SELECT id, name FROM customers WHERE id IN (7, 9, 12);
  33: -- Map customer_id -> name, then build response.
  34: ```
  35: 
  36: </div>
  37: 
  38: در اجرا، مقادیر را bind کنید؛ فهرست را با الحاق متن SQL نسازید. شمار query معمولاً دو است، اما اگر حد پارامتر مجبور به chunk کند بیشتر می‌شود. برای نیاز فوق یک join نیز نامزد مقایسه است؛ «دو» هدف عمومی نیست.
  39: 
  40: ## تمرین و مشاهده مورد انتظار
  41: 
  42: ۲۰ سفارش با مشتری‌های مشترک بسازید. نسخه lazy، join و batch را روی یک خروجی یکسان مقایسه کنید: query count، rows returned، bytes و زمان. سپس دو collection به هر سفارش اضافه کنید و دوباره بسنجید. انتظار: lazy می‌تواند رشد خطی round-trip نشان دهد؛ join چند collection می‌تواند ردیف‌های تکراری بسازد؛ batch رشد حاصل‌ضرب collectionها را کم می‌کند. اعداد به ORM و داده وابسته‌اند.
  43: 
  44: ## شاهد عمومی و حد شواهد
  45: 
  46: [راهنمای رسمی SQLAlchemy](https://docs.sqlalchemy.org/en/20/orm/queryguide/relationships.html) شاهد فنی روش‌های loading است؛ این درس نتیجه تولیدی یک شرکت یا درصد بهبود مستند ندارد. مثال فروشگاه فرضی است. انتخاب باید از SQL تولیدشده و اندازه پاسخ اثبات شود، نه نام راهبرد.

  54: - [ ] join، batch و lazy با خروجی و semantics یکسان مقایسه شده‌اند.
  55: - [ ] محدودیت IN، chunk و parameter binding رعایت می‌شود.
  56: - [ ] قرارداد snapshot و رفتار هنگام بسته‌شدن session روشن است.
