## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

مسئولیت‌ها در لایه‌هایی مانند presentation، application، domain و infrastructure تقسیم می‌شوند؛ قوانین وابستگی باید مشخص باشند.

## مثال کاربردی

کنترلر HTTP فرمان را به use case می‌دهد، use case دامنه را اجرا می‌کند و adapter داده را ذخیره می‌کند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «سبک‌های معماری» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** نگاشت مدل و عبور از لایه‌ها سربار دارد؛ گاهی ساده‌سازی CRUD سودمندتر است.
- **بازبینی:** لایهٔ داخلی نباید به لایهٔ بیرونی وابسته شود، مگر آنکه این جهت عمداً بخشی از طرح باشد.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: مسئولیت‌ها در لایه‌هایی مانند presentation، application، domain و infrastructure تقسیم می‌شوند؛ قوانین وابستگی باید مشخص باشند.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: کنترلر HTTP فرمان را به use case می‌دهد، use case دامنه را اجرا می‌کند و adapter داده را ذخیره می‌کند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: نگاشت مدل و عبور از لایه‌ها سربار دارد؛ گاهی ساده‌سازی CRUD سودمندتر است.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: لایهٔ داخلی نباید به لایهٔ بیرونی وابسته شود، مگر آنکه این جهت عمداً بخشی از طرح باشد.

## آموزش تکمیلی مستقل

### ۳. Layered / N-tier

Layered architecture مسئولیت منطقی را به presentation, application, domain و infrastructure تقسیم می‌کند. N-tier معمولاً آن لایه‌ها را به deployment/network tier هم تبدیل می‌کند. این دو واژه را با هم یکی ندان.

لایه‌بندی برای separation of concerns مفید است، اما call از UI تا دیتابیس می‌تواند از چند mapping و class عبور کند. dependency direction را تعریف کن؛ domain نباید از جزئیات web/database خبر داشته باشد اگر استقلال قواعد مهم است. برای CRUD کوچک، چندلایه‌سازی سنگین هزینهٔ اضافی می‌سازد.

## نمودار معماری و خواندن مرحله‌ای

Layered style مسئولیت را در ردیف‌هایی مثل presentation، application، domain و infrastructure جدا می‌کند. callها ممکن است در runtime به لایهٔ بیرونی برسند، اما جهت وابستگی source باید آگاهانه باشد. لایهٔ عبوری بدون policy یا transformation فقط latency و mapping اضافه می‌کند.
**دام رایج:** هر CRUD ساده را مجبور به عبور از چند DTO و mapper نکن.
**تمرین با پاسخ:** تغییر ORM نباید rule دامنه را تغییر دهد؛ قرارداد ذخیره‌سازی را در سمت use case تعریف و در adapter پیاده کن.

این نمودار ساده فقط یک view را نشان می‌دهد؛ سامانهٔ واقعی به تصمیم روشن دربارهٔ شکست، امنیت و مالکیت هم نیاز دارد.

~~~text
Runtime calls:
[Presentation] -> [Application] -> [Domain] -> [Persistence adapter]

Source dependencies:
[Presentation] -> [Application] -> [Domain contract] <- [Persistence adapter]
~~~
