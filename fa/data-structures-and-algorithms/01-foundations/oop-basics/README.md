# مبانی شیءگرایی

> مسیر: [فصل ۱ — پایه‌ها و تحلیل الگوریتم](../README.md) · پیش‌نیاز پیشنهادی: فصل ۱ و مبانی برنامه‌نویسی · [English](../../../../en/data-structures-and-algorithms/01-foundations/oop-basics/README.md)

## پیش‌نیازها و نقشهٔ ذهنی

توابع، نوع داده و collection. ابتدا مفهوم را به‌عنوان یک قرارداد ببین، سپس نمایش حافظه و عملیات را دنبال کن. هدف حفظ‌کردن نام نیست؛ باید بتوانی برای یک ورودی کوچک، state را بعد از هر گام بنویسی.

## ایده از پایه

OOP داده و عملیات وابسته را در object/class سازمان می‌دهد. در DSA، class می‌تواند Node، Stack یا Graph را پیاده کند؛ interface/API قرارداد عملیات است و representation جزئیات داخلی. Encapsulation اجازه می‌دهد representation عوض شود بدون شکستن caller.

## مدل، قرارداد و ناوردا

class blueprint؛ object نمونه؛ field state؛ method behavior. constructor invariant اولیه را برقرار می‌کند. composition یعنی objectی دیگری را دربرگیرد؛ inheritance رابطهٔ subtype می‌سازد. برای ساختار داده معمولاً composition و encapsulation از inheritance عمیق روشن‌ترند.

ناوردا (invariant) جمله‌ای است که در تمام مراحل الگوریتم باید درست بماند. نوشتن آن پیش از کدنویسی، هم به اثبات درستی کمک می‌کند و هم خطاهای مرزی را آشکار می‌سازد.

## الگوریتم یا عملیات گام‌به‌گام

Stack API: `push`, `pop`, `peek`, `isEmpty`; نمایش داخلی array/list پنهان. پس از هر method باید invariant مانند top در بازهٔ معتبر برقرار باشد. caller نباید مستقیماً فیلد داخلی را طوری تغییر دهد که invariant بشکند.

در پیاده‌سازی واقعی، قرارداد ورودی/خروجی را دقیق تعریف کن: رفتار ورودی تهی، مقدار تکراری، عنصر پیدا‌نشده و ظرفیت تمام‌شده باید روشن باشد.

## اجرای حل‌شده با ردگیری

دو پیاده‌سازی Stack: dynamic array و linked list. یک client با push/pop در هر دو کار می‌کند. هزینه‌ها فرق دارند، اما قرارداد LIFO یکسان است. این جداسازی ADT از implementation را به کلاس وصل می‌کند.

برای تمرین، جدولی با ستون‌های «گام»، «اندیس/اشاره‌گر»، «بخش فعال»، «تغییر state» و «دلیل» بساز. این روش به‌خصوص برای الگوریتم‌های درجا و تقسیم‌و‌غلبه جلوی پرش ذهنی را می‌گیرد.

## چرا درست است؟

constructor باید state معتبر بسازد و هر public method پیش/پس‌شرط را رعایت کند. اگر method exception می‌دهد، object باید در state معتبر باقی بماند یا رفتار آن مستند باشد.

اثبات معمولاً سه بخش دارد: (۱) آغاز—ناوردا پیش از نخستین گام درست است؛ (۲) نگهداری—هر گام آن را حفظ می‌کند؛ (۳) پایان—شرط توقف همراه invariant جواب موردنیاز را نتیجه می‌دهد. اگر یکی از این سه بخش نامشخص است، هنوز درک الگوریتم کامل نشده است.

## تحلیل زمان و حافظه

OOP به‌خودی‌خود complexity را تغییر نمی‌دهد؛ virtual dispatch معمولاً constant overhead، allocation object و pointer indirection ممکن است در workload پرحجم اثر کنند. abstraction هزینه دارد اما نگهداری و correctness را بهتر می‌کند.

در Big-O ورودی را تعریف کن (مثلاً n تعداد عناصر)، نوع حالت را نام ببر (بهترین/میانگین/بدترین)، و فضای کمکی را از حافظهٔ خود ورودی جدا کن. مرتبهٔ رشد زمان واقعی بر حسب ثانیه نیست؛ cache، تخصیص حافظه و ثابت‌های پیاده‌سازی هم اثر دارند.

## کاربرد واقعی و انتخاب مناسب

کتابخانهٔ collection، graph nodes، domain model و پلاگین‌پذیری implementation. در الگوریتم competitive، structهای ساده ممکن است کافی باشند؛ در محصول API پایدار و testability اهمیت دارد.

پیش از انتخاب بپرس: چه عملیاتی پرتکرارند؟ آیا ترتیب مهم است؟ دادهٔ ورودی چه اندازه است؟ آیا محدودیت حافظه، latency بدترین‌حالت یا thread-safety داریم؟ ساختار خوب برای workload نامناسب می‌تواند انتخاب بدی باشد.

## خطاهای رایج و edge caseها

inheritance صرفاً برای reuse خطر coupling دارد. expose کردن mutable field invariant را می‌شکند. objectهای زیاد allocation/cache locality را تحت تأثیر می‌گذارند. abstraction بیش‌ازحد مسیر داده را مبهم می‌کند.

حالت‌های مرزی را جداگانه بررسی کن: ورودی خالی، یک عضو، همهٔ اعضا برابر، هدف غایب، حداقل/حداکثر مقدار و اندازهٔ بزرگ. سرریز عدد صحیح در محاسبهٔ اندیس/ظرفیت نیز بسته به زبان مهم است.

## تمرین‌های مرحله‌ای

۱) Stack را به‌صورت class با دو representation طراحی کن. ۲) invariant و رفتار pop-empty را تعریف کن. ۳) inheritance و composition را برای Graph و Vertex مقایسه کن.

برای هر تمرین، اول پاسخ ساده و درست بنویس، بعد پیچیدگی را حساب کن، سپس edge case اضافه کن. تمرین را با دست‌کم یک ورودی کوچک ردگیری کن و خروجی را با انتظار مستقل مقایسه کن.

## آزمون جامع با پاسخ تشریحی

ابتدا پاسخ‌ها را نخوان؛ جواب را با استدلال بنویس، سپس توضیح را مقایسه کن.

1. **پرسش:** class و object؟
   **پاسخ تشریحی:** class تعریف نوع/رفتار؛ object نمونهٔ ساخته‌شده.
2. **پرسش:** encapsulation چه هدفی دارد؟
   **پاسخ تشریحی:** پنهان‌کردن representation و محافظت از invariant.
3. **پرسش:** interface چه می‌دهد؟
   **پاسخ تشریحی:** قرارداد عملیات، مستقل از implementation.
4. **پرسش:** OOP complexity را خودکار عوض می‌کند؟
   **پاسخ تشریحی:** خیر؛ semantics و representation همچنان هزینه دارند.
5. **پرسش:** composition چیست؟
   **پاسخ تشریحی:** ساختن رفتار با نگه‌داشتن objectهای دیگر درون یک object.

## راهنمای بازگویی از حافظه

بدون نگاه به متن، ایده، پیش‌شرط، invariant، یک ردگیری واقعی، پیچیدگی، edge case و یک کاربرد را در چند دقیقه روی کاغذ توضیح بده. اگر فقط pseudocode را حفظی می‌نویسی اما دلیل درستی یا محدودیت‌ها را نمی‌دانی، یک بار دیگر بخش‌های invariant و خطاها را مرور کن.
