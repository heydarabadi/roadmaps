## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

سیاست سطح بالا نباید به جزئیات زیرساخت وابسته باشد؛ هر دو به قرارداد پایدار وابسته شوند و جزئیات قرارداد را پیاده کنند.

## مثال کاربردی

use case پردازش پرداخت به قرارداد درگاه وابسته است و adapter آن قرارداد را به SDK فروشنده وصل می‌کند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «اصول طراحی» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** قرارداد اضافی باید مرز واقعی تغییر یا آزمون را جدا کند.
- **بازبینی:** این اصل را با افزودن interface برای هر کلاس یکی نگیر.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: سیاست سطح بالا نباید به جزئیات زیرساخت وابسته باشد؛ هر دو به قرارداد پایدار وابسته شوند و جزئیات قرارداد را پیاده کنند.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: use case پردازش پرداخت به قرارداد درگاه وابسته است و adapter آن قرارداد را به SDK فروشنده وصل می‌کند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: قرارداد اضافی باید مرز واقعی تغییر یا آزمون را جدا کند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: این اصل را با افزودن interface برای هر کلاس یکی نگیر.

## آموزش تکمیلی مستقل

#### D — Dependency Inversion

منطق سطح بالا به جزئیات پایین‌سطح وابسته نشود؛ هر دو به قرارداد پایدار تکیه کنند و جزئیات آن را پیاده کنند. کد source dependency از controller/SDK به قرارداد application یا domain جهت می‌گیرد. در runtime فراخوانی ممکن است از use case به adapter برسد؛ جهت اجرای فراخوانی با جهت dependency کد یکی نیست.

~~~text
Application policy -> PaymentAuthorizer contract <- Vendor adapter
~~~~

این اصل به معنای interface برای هر class نیست. آن را جایی به کار ببر که تغییر vendor، نیاز تست یا مرز ownership وجود دارد.

## نمونهٔ کد مرحله‌ای

منطق سطح‌بالا به قرارداد پایدار وابسته می‌شود و adapter سطح‌پایین آن را پیاده می‌کند. این جهت وابستگی کد است؛ جهت فراخوانی runtime ممکن است از use case به دیتابیس برود. برای هر کلاس interface نساز؛ مرز باید تغییر یا آزمون را محدود کند.
**تمرین با پاسخ:** جایگزینی ORM نباید قواعد دامنه را تغییر دهد؛ repository contract در سمت policy می‌ماند و adapter دیتابیس آن را پیاده می‌کند.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا انتخاب طراحی روشن بماند.

~~~csharp
public interface IOrderStore
{
    Task Save(Order order, CancellationToken ct);
}

public sealed class PlaceOrder(IOrderStore store)
{
    public Task Execute(Order order, CancellationToken ct)
    {
        order.ValidateForPlacement();
        return store.Save(order, ct);
    }
}
~~~

## خلاصه

اصل وارونگی وابستگی (DIP) را برای حل مسئلهٔ مشخص به کار ببر، trade-off آن را ثبت کن و با یک آزمون/معیار قابل مشاهده بررسی کن که آیا مرز طراحی واقعاً بهتر شده است.
