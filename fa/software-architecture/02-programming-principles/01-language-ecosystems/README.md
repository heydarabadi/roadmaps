# انتخاب زبان و اکوسیستم‌ها

## هدف یادگیری

بتوانی Java/Kotlin/Scala، Python، Ruby، Go، JavaScript/TypeScript و خانوادهٔ .NET را در چارچوب قابلیت تیم و نیاز سیستم مقایسه کنی، بدون اینکه بر اساس محبوبیت یا یک benchmark منفرد تصمیم بگیری.

## ایدهٔ مرکزی

زبان، ابزار ساخت و ادارهٔ نرم‌افزار است. برای معمار، سؤال اصلی «بهترین زبان چیست؟» نیست؛ «با این زبان و این تیم، این قابلیت را با کیفیت موردنیاز و هزینهٔ قابل‌قبول چگونه می‌سازیم؟» است. سرعت توسعه، کارایی، کتابخانه‌ها، مدل همروندی، امنیت حافظه، ابزار آزمون، مشاهده‌پذیری، جذب نیرو، چرخهٔ انتشار و سازگاری با سیستم‌های موجود را بسنج.

## مقایسهٔ کاربردی

| خانواده | قوت‌های رایج | هزینه‌ای که باید بررسی شود |
| --- | --- | --- |
| Java و Kotlin | اکوسیستم بالغ، ابزار سازمانی و runtime پایدار | مصرف حافظه، پیچیدگی پیکربندی و سازگاری نسخه |
| Scala | مدل‌های تابعی و داده‌پردازی JVM | منحنی یادگیری و دسترسی به نیروی متخصص |
| Python و Ruby | بازخورد سریع، ابزار وب و داده | مدیریت کارایی و dependency در بار سنگین |
| Go | ابزار توزیع، سرویس‌های شبکه‌ای و build ساده | مدل type و abstraction محدودتر از بعضی زبان‌ها |
| JavaScript و TypeScript | UI و سرویس‌های وب در یک اکوسیستم گسترده | وابستگی‌های زیاد و تغییرات سریع ابزارها |
| .NET | ابزار مهندسی و پلتفرم سازمانی بالغ | نیاز به شناخت deployment و ecosystem انتخابی |

این‌ها گرایش‌اند، نه قانون. نسخه، framework، runtime، معماری برنامه و تجربهٔ تیم نتیجه را تغییر می‌دهند. آزمایش واقعی با سناریوی بار و deployment مشابه تولید از مقایسهٔ میکروبنچمارک جداگانه معتبرتر است.

## درس تصمیم‌گیری زبان

انتخاب را از لایهٔ محصول آغاز کن، نه از فهرست زبان‌ها. یک API درخواست‌محور، job تحلیلی batch، رابط browser و کتابخانهٔ embedded نیازهای متفاوتی دارند. برای هر workload این اطلاعات را جمع کن:

۱. **الگوی بار:** CPU-bound، I/O-bound، batch، stream، latency حساس یا throughput بالا؟  
۲. **محیط اجرا:** container، serverless، browser، mobile، on-prem یا runtime موجود؟  
۳. **قراردادهای بیرونی:** SDK بانکی، کتابخانهٔ علمی، legacy .NET/Java یا interoperability چندزبان؟  
۴. **ویژگی‌های زبانی:** type system، concurrency، memory model، error handling، reflection و serialization.  
۵. **چرخهٔ عمر:** ابزار build، dependency scanning، debug، profiling، upgrade، پشتیبانی و جذب نیرو.

معیارها را رتبه‌بندی کن و یک نمونهٔ کوچک روی bottleneck واقعی بساز. اگر مسئله latency پایگاه داده است، عوض‌کردن زبان معمولاً آن را حل نمی‌کند. اگر زمان start-up، مصرف memory یا serialization عامل اصلی است، آن‌ها را مستقیم اندازه بگیر. در بارهای متفاوت باید percentileهای tail و هزینهٔ هر درخواست را دید، نه فقط میانگین.

## انتخاب تک‌زبان یا Polyglot

یک stack غالب آموزش، build، observability و on-call را ساده می‌کند. Polyglot زمانی ارزش دارد که یک مرز workload یا قابلیت روشن سود خاصی بگیرد. برای هر زبان اضافه باید owner، base image، SDKهای مشترک، patching cadence و سطح مهارت on-call مشخص باشد. انتخاب چند زبان برای استقلال ظاهری تیم‌ها اگر قرارداد و پشتیبانی نداشته باشد، وابستگی را پنهان می‌کند.

## تصمیم نمونه

**مسئله:** تیم ۵ نفره باید جست‌وجوی کاتالوگ را در شش هفته عرضه کند؛ بیشتر درخواست‌ها I/O هستند و تیم TypeScript را می‌شناسد.  
**گزینهٔ A:** Node.js/TypeScript — مهارت آماده و هم‌زبانی با UI؛ باید connection pooling و CPU-heavy work را پایش کرد.  
**گزینهٔ B:** Go — ابزار server و concurrency مناسب؛ آموزش و عملیات زبان تازه هزینه دارد.  
**گزینهٔ C:** Python — توسعهٔ سریع و کتابخانهٔ داده؛ اگر پردازش CPU سنگین شد باید اجرای آن جدا ارزیابی شود.  
**تصمیم آغازین:** TypeScript، چون ریسک اصلی زمان عرضه و integration است؛ سنجهٔ latency و CPU guardrail تعریف می‌شود. اگر bottleneck اندازه‌گیری‌شده به CPU یا مصرف memory محدود شد، سرویس خاص را دوباره ارزیابی می‌کنیم.

## مثال تصمیم

تیم چهارماهه برای ساخت API انبار، Go را به‌خاطر مهارت تیم و سادگی استقرار می‌سنجد، اما گزارش‌گیری با Spark/JVM در تیم داده از قبل جا افتاده است. انتخاب polyglot وقتی خوب است که مرز، مالکیت، پشتیبانی و pipeline هر زبان روشن باشد. زبان تازه برای یک سرویس کوچک، اگر شیفت آن‌کال نتواند آن را پشتیبانی کند، هزینهٔ پنهان خواهد داشت.

## چک‌لیست تصمیم

- چه نوع محاسبه و latency داریم؟
- کدام کتابخانه، پروتکل و SDK الزام محصول را پوشش می‌دهد؟
- تیم امروز چه مهارتی دارد و آموزش چقدر زمان می‌برد؟
- چگونه dependency، آسیب‌پذیری و نسخه را مدیریت می‌کنیم؟
- build، تست، rollout و observability چه کیفیتی دارند؟
- آیا زبان خاص به قرارداد رسمی نیاز دارد یا انتخاب تیمی کافی است؟

## کد مفهومی: ثبت تصمیم

~~~text
Context: سرویس پردازش batch روزانه، نه مسیر پاسخ بلادرنگ
Options: Python / JVM / Go
Decision: Python، چون کتابخانه و مهارت تحلیلی تیم آماده است
Risk: اجرای کندتر هنگام رشد حجم
Guardrail: اندازه‌گیری زمان و هزینه در دادهٔ نماینده؛ بازنگری در عبور از SLO
~~~

## دام‌ها

- polyglot شدن به‌خاطر علاقهٔ فردی، بدون مرزهای روشن.
- رد زبان بر اساس نمودار benchmark که workload واقعی را نمایندگی نمی‌کند.
- تمرکز فقط بر سرعت کدنویسی و نادیده‌گرفتن ارتقا و نگهداری.
- انتخاب یک زبان برای همهٔ مسئله‌ها به‌خاطر «استاندارد سازمانی».

## آزمون

۱. چرا مهارت تیم بخشی از کیفیت معماری است؟  
**پاسخ:** روی زمان تحویل، خطا، پاسخ‌گویی آن‌کال، کیفیت review و هزینهٔ نگهداری اثر مستقیم دارد.

۲. آیا یک زبان برای همهٔ سرویس‌ها بهتر است؟  
**پاسخ:** گاهی کاهش پیچیدگی سازمانی مفید است؛ اما اگر workload یا اکوسیستم خاصی تفاوت مهمی داشته باشد، استثنای مستدل ارزش دارد.

۳. چگونه latency دو زبان را منصفانه مقایسه می‌کنی؟  
**پاسخ:** همان workload، داده، سخت‌افزار، پیکربندی و سنجه‌های tail latency و throughput را اجرا می‌کنم.

۴. مهم‌ترین خطر polyglot چیست؟  
**پاسخ:** هزینهٔ چند toolchain و مهارت عملیاتی، کتابخانه‌های ناهمسان و دشواری جابه‌جایی بین سرویس‌ها.

## تمرین و پاسخ راهنما

برای یک سرویس ثبت سفارش با تیمی که TypeScript را می‌شناسد و یک job پردازش گزارش که Python/Spark در سازمان جاافتاده است، تصمیم زبان و مرز deployment را بنویس. workload، latency، امنیت، مهارت on-call، dependency و سنجهٔ بازبینی را وارد کن.

**پاسخ راهنما:** مجبور نیستیم یک زبان برای همهٔ workloadها انتخاب کنیم. اگر API سفارش از اکوسیستم TypeScript سود می‌برد و تحلیل از Spark/Python، دو زبان با دو مرز روشن قابل‌قبول‌اند. مالک build و پایش هر دو، قرارداد event، serialization، امنیت dependency و on-call باید مشخص باشد. اگر job کوچک و یک‌بارمصرف است، اضافه‌کردن stack دوم شاید هزینهٔ بیشتری از سودش داشته باشد. معیار نهایی از benchmark روی workload نماینده و توان تیم می‌آید.
