# کارایی و مقیاس‌پذیری

## هدف یادگیری

- مسئله‌ای را که این مفهوم حل می‌کند تعریف کنی.
- برای یک سامانهٔ نمونه انتخاب را با trade-off توضیح بدهی.
- رفتار سیستم را هنگام اختلال پیش‌بینی کنی.

## ایدهٔ مرکزی

کارایی کیفیت پاسخ زیر بار فعلی است؛ مقیاس‌پذیری حفظ کیفیت با رشد بار است. سیستم سریع ممکن است با رشد داده به‌سرعت از نفس بیفتد.

## نقشهٔ مفهومی

نیاز کسب‌وکار ← قرارداد بار/کیفیت ← انتخاب الگو ← نقطهٔ شکست ← مشاهده و بازیابی

## توضیح کامل

گلوگاه را در CPU، حافظه، شبکه، I/O، قفل یا DB اندازه بگیر. مقیاس عمودی ساده ولی محدود و گران‌تر است؛ مقیاس افقی نمونه‌های بیشتری می‌افزاید و به توزیع بار، مدیریت state و هماهنگی نیاز دارد. ظرفیت کل تابع کندترین جزء است. خواندن را می‌توان با replica/cache و نوشتن را با partitioning یا صف جدا کرد، اما بعد از اندازه‌گیری.

## درس گام‌به‌گام

### اول مشخص کن چه چیزی باید بهتر شود

«کارایی» چند معیار دارد: latency یک درخواست، throughput تکمیل کارها، مصرف CPU/حافظه، هزینهٔ هر عملیات و نرخ خطا. ممکن است throughput را با batch بالا ببری ولی تأخیر هر کار را زیاد کنی. پیش از تغییر، SLI و محدودهٔ اندازه‌گیری را تعیین کن: endpoint، اندازهٔ payload، cache hit/miss، نوع درخواست و percentileها. benchmark با دادهٔ کوچک و warm cache ممکن است رفتار تولید را بازنمایی نکند.

### گلوگاه ظرفیت را پیدا کن

یک درخواست از چند منبع استفاده می‌کند. اگر API در هر درخواست 4 query بزند و DB حداکثر 2,000 query در ثانیه تحمل کند، سقف نظری این مسیر حدود 500 درخواست در ثانیه است؛ قبل از اینکه CPU API پر شود، ممکن است connection pool یا lock دیتابیس اشباع شود. ظرفیت نظری را به ظرفیت امن تبدیل کن: فرض کن برای burst و failover حدود 30% headroom می‌خواهی، پس سقف کاری کمتر از حدود 350 درخواست در ثانیه خواهد بود. این درصد نسخهٔ ثابت نیست و باید با آزمون بار تعیین شود.

از «قانون Amdahl» هم نتیجهٔ ساده‌ای می‌گیریم: اگر 80% زمان در DB و فقط 20% در کد برنامه باشد، دو برابرکردن سرعت CPU برنامه حداکثر کمی به زمان کل کمک می‌کند. ابتدا جزء غالب را اصلاح کن؛ پس از هر اصلاح ممکن است گلوگاه به جای دیگری منتقل شود.

### مقیاس عمودی و افقی چه بهایی دارند؟

Vertical scaling یک ماشین را CPU، RAM یا IOPS بیشتری می‌دهد. عملیات ساده‌تر و تغییر کد کمتر است، اما سقف سخت، هزینهٔ غیرخطی و failure domain بزرگ دارد. Horizontal scaling چند نمونه اضافه می‌کند و ظرفیت/تحمل خرابی می‌سازد، اما state محلی، session، lock و فایل محلی را مسئله می‌کند. نمونهٔ API معمولاً باید stateless باشد؛ state پایدار در datastore مشترک یا توزیع‌شده قرار گیرد.

### رشد خواندن و نوشتن را جدا تحلیل کن

اگر 1,000 درخواست در ثانیه داریم و 85% خواندن است، 850 درخواست خواندن داریم. اگر cache به‌طور واقعی 80% این خواندن‌ها را پاسخ دهد، حدود 170 خواندن به DB می‌رسد؛ به‌علاوه 150 نوشتن، یعنی تقریباً 320 عملیات ساده در ثانیه به‌جای 1,000. اما این حساب وزن queryها، cache miss هم‌زمان، invalidation و هزینهٔ نوشتن را لحاظ نمی‌کند. برای write-heavy workload ممکن است cache سود کمی بدهد و partitioning، batch یا تغییر مدل داده لازم شود.

### چرا scale-out گاهی بدتر می‌کند؟

افزودن نمونه‌ها تعداد اتصال‌های هم‌زمان به DB را زیاد می‌کند؛ اگر pool هر نمونه 100 اتصال داشته باشد، 20 replica می‌توانند 2,000 اتصال باز کنند. DB ممکن است پیش از CPU در مدیریت اتصال‌ها کم بیاورد. در سیستم توزیع‌شده، شبکه و coordination هم هزینه دارند؛ برای مثال یک قفل سراسری می‌تواند همهٔ nodeها را پشت یک صف پنهان نگه دارد. scale-out ظرفیت component مستقل را بالا می‌برد، نه الزاماً ظرفیت انتهابه‌انتها را.

### روند عملی عیب‌یابی

1. بار واقعی یا نزدیک به واقعی را تعریف کن و baseline ثبت کن.
2. نمودار latency، throughput، error، saturation و dependencyها را کنار هم ببین.
3. trace یک درخواست کند را بررسی و مدت هر پرش را جدا کن.
4. فرضیه‌ای بساز، یک تغییر محدود انجام بده و همان بار را دوباره اجرا کن.
5. کیفیت، هزینه و failure mode پس از تغییر را مقایسه کن؛ بهبود یک شاخص ممکن است شاخص دیگر را خراب کند.

## مثال عملی

صفحهٔ کالا read-heavy است و cache می‌تواند بار DB را کم کند؛ موجودی checkout باید با منبع حقیقت تأیید شود.

## نمونهٔ قرارداد / شبه‌کد

~~~text
ظرفیت مؤثر سیستم از کوچک‌ترین ظرفیت میان API، DB و worker بیشتر نمی‌شود.
~~~

## دام‌ها و سوءبرداشت‌ها

- افزودن replica بدون رفع contention؛ autoscaling بی‌سقف؛ cache کردن همه‌چیز؛ ظرفیت‌سنجی از روی میانگین.
- عددهای مثال آموزشی‌اند؛ SLO و ظرفیت نهایی را از دادهٔ واقعی تعیین کن.

## آزمون کوتاه

1. تفاوت performance و scalability چیست؟
2. چرا scale-out نوشتن DB ساده نیست؟
3. قبل از cache چه چیزی را اندازه می‌گیری؟

### پاسخ‌نامهٔ فشرده

1. performance کیفیت در بار فعلی است؛ scalability توان حفظ آن هنگام رشد بار است.
2. چون contention، قفل، ترتیب تراکنش یا hotspot باقی می‌ماند و افزودن node هماهنگی می‌خواهد.
3. نرخ درخواست و p95/p99، CPU/IO، query/lock، hit ratio و ظرفیت هر لایه را بگیر.

## تمرین

برای یک فروشگاه اینترنتی، مسیر درخواست این مفهوم را رسم کن. منبع حقیقت، مرز شبکه، رفتار شکست، دادهٔ حساس، معیار پایش و راه بازگشت را مشخص کن. سپس یک آزمون خرابی بنویس که بتواند فرض اصلی را رد کند.

## خلاصه

کارایی کیفیت پاسخ زیر بار فعلی است؛ مقیاس‌پذیری حفظ کیفیت با رشد بار است. سیستم سریع ممکن است با رشد داده به‌سرعت از نفس بیفتد. پیش از پیاده‌سازی رفتار عادی، حالت اختلال و معیار موفقیت را ثبت کن.
