## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

چندریختی امکان فراخوانی یک قرارداد مشترک با پیاده‌سازی‌های متفاوت را می‌دهد و شرط‌های نوع‌محور را کاهش می‌دهد.

## مثال کاربردی

سرویس خروجی `Exporter` برای CSV و PDF یک عملیات `export` فراخوانی می‌کند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «برنامه‌نویسی شیءگرا» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** افزودن abstraction برای یک حالت ثابت می‌تواند پیچیدگی بیافریند.
- **بازبینی:** چندریختی را جایگزین هر `if` نکن؛ تنوع واقعی و پایدار لازم است.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: چندریختی امکان فراخوانی یک قرارداد مشترک با پیاده‌سازی‌های متفاوت را می‌دهد و شرط‌های نوع‌محور را کاهش می‌دهد.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: سرویس خروجی `Exporter` برای CSV و PDF یک عملیات `export` فراخوانی می‌کند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: افزودن abstraction برای یک حالت ثابت می‌تواند پیچیدگی بیافریند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: چندریختی را جایگزین هر `if` نکن؛ تنوع واقعی و پایدار لازم است.

## آموزش تکمیلی مستقل

#### چندریختی (Polymorphism)

چندریختی یعنی consumer با قرارداد مشترک کار کند و رفتار بر اساس implementation واقعی انتخاب شود. subtype polymorphism از interface/base type استفاده می‌کند؛ parametric polymorphism از generic؛ برخی زبان‌ها dispatch بر حسب overload یا pattern matching دارند.

~~~python
class DiscountPolicy(Protocol):
    def apply(self, subtotal_cents: int) -> int: ...

def checkout(subtotal_cents, policy: DiscountPolicy):
    return policy.apply(subtotal_cents)
~~~

این کار branchهای پراکنده را کم می‌کند، اگر الگوریتم‌های تخفیف واقعاً متفاوت و قابل تعویض باشند. اگر فقط یک policy داریم و change driver مشخصی نیست، تابع مستقیم ساده‌تر است. برای قرارداد مشترک، test contract داشته باش تا implementationها یک رفتار حداقلی را رعایت کنند.

## نمونهٔ کد مرحله‌ای

چندریختی اجازه می‌دهد مصرف‌کننده با قرارداد ثابت کار کند و هر نوع رفتار خودش را ارائه دهد. برای جلوگیری از switch بر اساس نوع مفید است، اما انتخاب پیاده‌سازی و قرارداد مشترک باید روشن باشد؛ وراثت رفتاریِ نادرست جانشینی را می‌شکند.
**تمرین با پاسخ:** روش ارسال تازه اضافه کن با پیاده‌سازی IDeliveryMethod؛ اگر باید use case را هم پر از شرط کنی، abstraction درست انتخاب نشده.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا تصمیم طراحی روشن بماند.

~~~csharp
public interface IDeliveryMethod
{
    DeliveryQuote Quote(Parcel parcel);
}

var quote = deliveryMethod.Quote(parcel);
~~~
