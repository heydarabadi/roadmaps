# چرا Kubernetes؟

**فصل:** [مقدمه و مدل ذهنی](../../README.md)

## هدف یادگیری

ارزش‌های واقعی Kubernetes را از شعارهایی مانند «مقیاس‌پذیری خودکار» جدا کنید و بتوانید در یک مسئلهٔ مشخص مزایا و هزینه‌ها را بسنجید.

## مسئلهٔ پیش از orchestration

وقتی چند نسخهٔ برنامه روی چند میزبان اجرا می‌شوند، تیم باید جای اجرای فرایند، سلامت آن، انتشار نسخه، تغییر ترافیک و جایگزینی پس از خرابی را هماهنگ کند. اگر این کار با دستورهای دستی و اسکریپت‌های پراکنده انجام شود، نتیجه به افراد و ترتیب اجرای دستورها وابسته می‌شود.

Kubernetes این کار را با قراردادهای API و controllerها استاندارد می‌کند:

- desired state را ثبت می‌کنید و تغییر آن در Git یا pipeline قابل بازبینی می‌شود.
- Deployment کنترل نسخه‌ها و replicaهای برنامهٔ stateless را پیگیری می‌کند.
- Service آدرس منطقی برای Podهای متغیر می‌دهد.
- scheduler workloadها را با توجه به منابع و قیدها روی nodeها می‌گذارد.
- probeها آمادگی و سلامت process را به سیستم اعلام می‌کنند.
- API و اکوسیستم افزونه‌ها یک سطح مشترک برای automation می‌سازند.

این مزایا رایگان نیستند: باید node، شبکه، storage، هویت، امنیت، upgrade، ظرفیت و مشاهده‌پذیری را مدیریت کنید. خود Kubernetes هم می‌تواند خرابی را تکثیر کند؛ اگر manifest خراب باشد، کنترلر آن را مداوم اعمال خواهد کرد.

## مثال: فروشگاه آنلاین

فرض کنید فروشگاه سه مؤلفه دارد: storefront، API و worker صف.

- storefront معمولاً stateless است؛ Deployment چند replica می‌سازد.
- API با Service کشف می‌شود؛ replicaهای جدید خودکار endpoint می‌شوند.
- worker را می‌توان جداگانه مقیاس داد؛ HPA فقط وقتی درست عمل می‌کند که metric و محدودیت ظرفیت node آماده باشند.
- پایگاه داده stateful است؛ اجرای دیتابیس در کلاستر نیازمند طراحی backup، storage، replication و restore است.

برای تیم کوچک، ممکن است دیتابیس managed و فقط APIها در Kubernetes باشد. «همه‌چیز را داخل کلاستر بگذار» قانون معماری نیست.

## تصمیم بر اساس هزینهٔ کل مالکیت

هزینهٔ مستقیم شامل control plane یا ماشین‌هاست؛ هزینهٔ غیرمستقیم شامل ساعت نیروی فنی، یادگیری، on-call، افزونه‌ها، شبکهٔ خروجی، ذخیره‌سازی، مانیتورینگ و incident است. این‌ها را برای workload و حجم آینده تخمین بزنید. اگر ارزش deploymentهای تکرارپذیر و استانداردسازی از این هزینه بیشتر نیست، گزینهٔ ساده‌تر انتخاب خوبی است.

## تجربهٔ واقعی

گزارش CNCF دربارهٔ Michelin از پلتفرمی برای صدها برنامه و چندین کلاستر خبر می‌دهد. چنین مقیاسی می‌تواند سرمایه‌گذاری در قابلیت self-service تیم‌ها و عملیات مشترک را توجیه کند. از عدد کلاسترها نتیجه نگیرید که هر محصولی به همان معماری نیاز دارد؛ ابتدا تعداد تیم، deploymentها و ظرفیت on-call خود را بسنجید.

## زمان انتخاب نکردن Kubernetes

- یک برنامهٔ کوچک با یک فرایند انتشار کم‌تکرار دارید.
- یک سرویس container managed تمام نیاز را پوشش می‌دهد.
- تیم توان پاسخ‌گویی به failureهای cluster، network و storage را ندارد.
- محدودیت حقوقی، هزینه یا سادگی محصول با پیچیدگی platform سازگار نیست.

## کوییز تشریحی

1. «خودترمیمی» دقیقاً چه چیزی را ترمیم می‌کند؟ — کنترلر می‌تواند تعداد Podها را بازگرداند یا container را restart کند؛ باگ برنامه و خرابی وابستگی بیرونی خودبه‌خود رفع نمی‌شوند.
2. چرا Service مفید است؟ — Pod IPها تغییرپذیرند؛ Service دسترسی پایدار به گروه Pod می‌دهد.
3. HPA بدون cluster autoscaler چه محدودیتی دارد؟ — می‌تواند Pod بیشتری درخواست کند، اما اگر nodeها ظرفیت ندارند Podها Pending می‌مانند.
4. یک نشانهٔ مناسب‌بودن Kubernetes و یک نشانهٔ نامناسب‌بودن آن بگویید. — deployment چندسرویسی تکراری می‌تواند مناسب باشد؛ workload ساده با نیاز عملیاتی پایین ممکن است با گزینهٔ ساده‌تر بهتر اجرا شود.
