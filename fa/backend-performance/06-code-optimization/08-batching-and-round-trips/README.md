# ۶.۸ — Batching و کاهش رفت‌وبرگشت

**زبان:** فارسی · [English version](../../../../en/backend-performance/06-code-optimization/08-batching-and-round-trips/README.md)


Batching چند عملیات مستقل و سازگار را در یک فراخوانی جمع می‌کند تا هزینهٔ ثابت اتصال، Header، dispatch یا رفت‌وبرگشت میان آن‌ها سرشکن شود. مقدار محاسبهٔ واقعی الزاماً کم نمی‌شود. دستهٔ بزرگ‌تر می‌تواند throughput را بهتر و latency انتظار، حافظه یا دامنهٔ شکست را بدتر کند.

**هدف یادگیری:** محاسبهٔ هزینهٔ round-trip، تفکیک Batch از coalescing و concurrency، طراحی سقف تعداد/بایت/زمان و بازیابی خطای جزئی. پیش‌نیاز: HTTP، فراخوانی DB و [Timeout/Retry](../07-timeouts-and-retries/README.md). بررسی منابع: **۲۰۲۶-۱۱-۱۰**.

## پیش‌نیازهای همین درس

رفت‌وبرگشت (Round-trip) زمانی است که یک درخواست از فرستنده به مقصد برود و پاسخ/تأیید برگردد؛ تاخیر شبکه و هزینهٔ dispatch به زمان کار اضافه می‌شود. Batch چند عملیات را در یک درخواست نگه می‌دارد. Coalescing کارهای هم‌زمان برای همان کلید را به یک محاسبهٔ مشترک بدل می‌کند؛ concurrency فقط کارهای جدا را هم‌زمان اجرا می‌کند. خطای جزئی یعنی پاسخ برخی اعضا موفق و برخی ناموفق باشد.

## مدل ذهنی و انتخاب

| روش | چه چیزی تغییر می‌کند؟ | هزینه یا محدودیت |
| --- | --- | --- |
| چند فراخوانی سریال | هر عملیات رفت‌وبرگشت جدا دارد | latency تجمعی |
| فراخوانی موازی محدود | رفت‌وبرگشت‌ها هم‌پوشانی می‌گیرند | تعداد کار و فشار پایین‌دست باقی است |
| Batch | چند عملیات در یک envelope | انتظار تشکیل دسته، payload و خطای جزئی |
| Request coalescing | درخواست‌های هم‌زمان برای همان داده یک کار مشترک دارند | تطابق کلید/مجوز و مدیریت subscriber |
| Connection reuse | اتصال دوباره ساخته نمی‌شود | تعداد درخواست‌ها لزوماً کم نمی‌شود |

راهنمای [Azure Chatty I/O](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/chatty-io/) الگوی درخواست‌های کوچک فراوان و سربار تجمعی آن را توضیح می‌دهد. HTTP/2 یا اتصال پایدار هزینهٔ برقراری/هم‌پوشانی را تغییر می‌دهند، اما Query و dispatch هر درخواست همچنان می‌تواند هزینه داشته باشد. برای DB، Batch یا Join را با حجم نتیجه و طرح Query بسنجید؛ `IN` عظیم یا Join چند رابطهٔ بزرگ ممکن است بار را افزایش دهد.

### فرایند طراحی

1. تعداد calls/request، بایت و زمان ثابت هر call را اندازه بگیرید؛ اگر بیشتر زمان محاسبه است، صرفه‌جویی round-trip محدود خواهد بود.
2. عملیات را فقط در محدودهٔ درست مجوز و semantics جمع کنید. Batch نباید دادهٔ tenant دیگر را آشکار کند.
3. Flush را با **هرکدام زودتر رخ دهد** اجرا کنید: سقف تعداد، سقف بایت، مهلت انتظار یا نزدیک شدن Deadline.
4. برای هر آیتم شناسه و نتیجهٔ مستقل برگردانید؛ ترتیب بازگشت را تضمین یا با شناسه بازیابی کنید. معنی atomic بودن باید صریح باشد.
5. Retry را فقط برای آیتم‌های شکست‌خوردهٔ قابل‌تکرار انجام دهید؛ دوباره فرستادن writeهای موفق نیازمند idempotency است.
6. اندازه و زمان انتظار را با p99، throughput موفق و فشار پایین‌دست تنظیم کنید، نه فقط کم شدن تعداد درخواست.

## مثال حل‌شده

**مدل فرضی:** ۲۰ lookup مستقل داریم. هر round-trip سریال ۱۵ ms هزینهٔ ثابت دارد و پردازش هر آیتم ۱ ms است؛ transfer/صف را برای ساده‌سازی کنار گذاشته‌ایم.

<div dir="ltr" align="left">

```text
20 serial calls:       20 * (15 + 1) = 320 ms
1 batch of 20 items:   15 + 20 * 1   = 35 ms
2 serial batches/10:   2 * (15 + 10) = 50 ms
```

</div>

۳۵ ms تضمین واقعی نیست؛ پیاده‌سازی Batch ممکن است داخلی همچنان فراخوانی‌های سریال داشته باشد و حجم بیشتر صف بسازد. اگر برای جمع شدن دسته تا ۱۰ ms صبر کنیم، نخستین آیتم تا حدود ۱۰ ms اضافه انتظار می‌کشد. در بار کم، انتظار نامحدود برای رسیدن به ۲۰ آیتم می‌تواند هرگز تمام نشود؛ تایمر لازم است.

نمونهٔ قرارداد آموزشی:

<div dir="ltr" align="left">

```json
{
  "results": [
    {"request_id": "r1", "status": "ok", "value": 42},
    {"request_id": "r2", "status": "retryable_error", "code": "TEMPORARY"},
    {"request_id": "r3", "status": "not_found"}
  ]
}
```

</div>

در این قرارداد، نتیجهٔ Envelope به‌تنهایی موفقیت همهٔ اعضا نیست. فقط `r2` نامزد تکرار است و آن هم با بودجه و ایمنی تکرار. `not_found` طبق این مثال نتیجهٔ نهایی است. اگر کل Envelope بی‌پاسخ بماند، وضعیت همهٔ اعضا نامعلوم است؛ عملیات نوشتن باید idempotency یا روش استعلام وضعیت داشته باشد.

## تمرین و انتظار

دسته‌ای با حد ۱۰ آیتم، ۶۴ KiB و ۵ ms انتظار در نظر بگیرید. سه آیتم ۱ KiB در زمان‌های ۰، ۱ و ۲ ms وارد شوند؛ دسته در ۵ ms از ورود نخست Flush می‌شود. سپس یک آیتم ۷۰ KiB وارد کنید. **راه‌حل:** در زمان ۵ ms فقط <span dir="ltr">3 KiB</span> از حد بایت و <span dir="ltr">3/10</span> از حد تعداد مصرف شده است؛ با این حال max-wait دسته را Flush می‌کند، پس درخواست در بار کم معطل نمی‌ماند. آیتم <span dir="ltr">70 KiB</span> از سقف <span dir="ltr">64 KiB</span> بیشتر است و باید طبق قرارداد رد، تقسیم مجاز یا به مسیر جدا فرستاده شود؛ شکستن بی‌معنای JSON راهکار نیست. اگر دو عضو از ده شکست retryable باشند و هشت عضو موفق، فقط دو شناسهٔ شکست‌خورده دوباره ارسال می‌شوند؛ وضعیت نامعلومِ کل Envelope بی‌پاسخ نیازمند idempotency یا استعلام است.

## شاهد واقعی

در گزارش **۱۷ اوت ۲۰۲۰** [Meta Async](https://engineering.fb.com/2020/08/17/production-engineering/async/)، چند Job در یک mega job جمع شدند تا فشار صف و رفت‌وبرگشت dispatcher-worker کمتر شود؛ worker همچنان کار اعضا را انجام می‌داد. مقاله به delay tolerance هم توجه دارد. این تجربه مربوط به سامانهٔ Job است؛ مناسب بودن همان انتظار برای API تعاملی را ثابت نمی‌کند.

همچنین [Discord در ۲۰۲۳](https://discord.com/blog/how-discord-stores-trillions-of-messages) چند درخواست هم‌زمان برای همان row را به یک Query مشترک متصل کرد. این **coalescing** است؛ با Batch کردن شناسه‌های متفاوت فرق دارد و Cache دائمی نتیجه هم محسوب نمی‌شود.

## شکست‌ها و علائم

| شکست | نشانه | اقدام |
| --- | --- | --- |
| انتظار فقط برای پر شدن دسته | latency زیاد در بار کم | max-wait و Flush نزدیک Deadline |
| سقف فقط بر تعداد | یک آیتم بزرگ RSS را می‌شکند | حد بایت و رفتار تک‌آیتم بزرگ |
| یک عضو کند کل دسته را نگه می‌دارد | tail زیاد و deadline جمعی | اندازه محدود و قرارداد partial result |
| Retry کل دسته | side effect یا هزینهٔ تکراری | نتیجهٔ هر عضو و idempotency |
| دستهٔ چند tenant با مجوز مشترک | افشای داده | context و بررسی مجوز هر عضو |
| فراخوانی کم ولی DB سنگین‌تر | CPU/lock/rows read بیشتر | طرح Query و حجم نتیجه را بررسی کن |

### چک‌لیست عملیاتی

- [ ] هزینهٔ ثابت و کار واقعی هر آیتم جدا اندازه‌گیری شده‌اند.
- [ ] حداکثر تعداد، بایت، زمان انتظار و هم‌زمانی معلوم است.
- [ ] Deadline و لغوِ عضو/دسته قرارداد مشخص دارند.
- [ ] مجوز، ترتیب، atomicity و خطای جزئی تعریف شده‌اند.
- [ ] Retry عضو موفق را بی‌دلیل تکرار نمی‌کند.
- [ ] batch size، fill ratio، queue wait، bytes، p99 و خطاهای هر عضو پایش می‌شوند.

## آزمون

1. Batching کدام بخش هزینه را هدف می‌گیرد؟
2. چرا فقط حد ۱۰۰ آیتم کافی نیست؟
3. در مثال ۲۰ آیتم، زمان ایده‌آل یک Batch بدون انتظار چقدر است؟
4. فرق coalescing و Batch چند کلید چیست؟
5. اگر دو عضو شکست خوردند، چرا Retry کل دسته ممکن است غلط باشد؟
6. آیا Connection reuse تعداد Queryهای برنامه را خودبه‌خود کم می‌کند؟

### پاسخ تشریحی

1. هزینهٔ ثابت هر فراخوانی و رفت‌وبرگشت را سرشکن می‌کند؛ کار واقعی اعضا لزوماً حذف نمی‌شود.
2. در بار کم ممکن است هرگز پر نشود و یک آیتم بزرگ هم سقف بایت را بشکند؛ زمان و بایت هم لازم‌اند.
3. ۳۵ ms در مدل فرضی؛ ۱۵ ms ثابت و ۲۰ ms پردازش، بدون صف/انتقال/سربار دیگر.
4. coalescing کار تکراری همان کلید را مشترک می‌کند؛ Batch عملیات متفاوت را در یک envelope حمل می‌کند.
5. اعضای موفق ممکن است دوباره side effect ایجاد کنند و هزینه افزایش یابد؛ خطای هر عضو و تکرار امن لازم است.
6. خیر؛ اتصال دوباره استفاده می‌شود ولی برنامه ممکن است همان تعداد درخواست یا Query را ارسال کند.

## جمع‌بندی

Batch هزینهٔ ثابت رفت‌وبرگشت را میان عملیات تقسیم می‌کند، اما کار واقعی و فشار مقصد را حذف نمی‌کند. Flush باید سقف تعداد، بایت و انتظار داشته باشد؛ نتیجهٔ هر عضو، مجوز، ترتیب و atomicity روشن باشند. برای Retry جزئی، فقط اعضای امن و شکست‌خورده را با بودجهٔ مشترک دوباره بفرستید.

## منابع تکمیلی اختیاری

برای فهم این درس یا حل تمرین، بازکردن پیوندهای زیر لازم نیست؛ آن‌ها برای مطالعهٔ بیشتر و بررسی رفتار عملیاتی سامانه‌ها هستند.

- [فارسی: درخواست‌های دسته‌ای](https://pro-nee.net/terms/batch-requests/): واژه‌نامهٔ مکمل دربارهٔ Batch و خطای جزئی؛ صفحه در نتایج جست‌وجو با محتوای مرتبط دیده شد، اما واکشی کامل در این بررسی timeout شد، پس منبع رفتار هنجاری نیست.
- [English: Azure Chatty I/O](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/chatty-io/): تشخیص هزینهٔ فراخوانی‌های زیاد و بده‌بستان تجمیع.
- [English: Redis pipelining](https://redis.io/docs/latest/develop/using-commands/pipelining/): اثر RTT و اندازهٔ Pipeline بر درخواست/پاسخ و حافظه؛ مثال‌ها مربوط به Redis و محدودیت بافر سمت سرور را نیز ببینید.
- [English: GraphQL DataLoader](https://github.com/graphql/dataloader): نمونهٔ مرجع Batch و Cache در محدودهٔ درخواست؛ DataLoader برای مجوزها و عمر Cache باید مطابق Context هر کاربر ساخته شود.
- [English: Meta Async](https://engineering.fb.com/2020/08/17/production-engineering/async/): تجربهٔ Batching در Jobهای پس‌زمینه و ارتباط آن با تحمل تأخیر.
- [English: Discord message storage](https://discord.com/blog/how-discord-stores-trillions-of-messages): coalescing و routing هم‌کلید، به‌عنوان سازوکاری متمایز از Batch.
