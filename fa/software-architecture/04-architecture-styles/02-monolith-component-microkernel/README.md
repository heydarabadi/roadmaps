# معماری یکپارچه، مؤلفه‌ای و Microkernel

Monolith یک واحد build/deploy است و می‌تواند ماژولار باشد. Modular Monolith در یک deployment می‌ماند، اما ماژول‌های دارای قرارداد، مالکیت و قواعد وابستگی دارد. Component-based طراحی را حول مؤلفه‌های مستقل می‌چیند. Microkernel هسته‌ای پایدار با قابلیت‌های افزوده‌شونده از طریق plugin دارد؛ برای محصولات قابل‌گسترش مناسب است.

Monolith بدطراحی نیست. راهبرد monolith-first می‌تواند برای شناخت دامنه و یافتن مرزهای واقعی مفید باشد. شکستن زودهنگام به سرویس، مرزهای فرضی را به تعهد شبکه‌ای پرهزینه تبدیل می‌کند.

## مثال

محصول حسابداری هستهٔ ثبت سند و مالیات دارد؛ افزونه‌ها اتصال به بانک و قالب گزارش را اضافه می‌کنند. اگر plugin مستقیم جداول core را تغییر دهد، استقلالش ظاهری است. قرارداد افزونه باید versioning، مجوز، sandbox و failure handling را تعریف کند.

| ساختار | مزیت | هزینه |
| --- | --- | --- |
| Monolith | build و debug آسان | تغییر می‌تواند کل محصول را درگیر کند |
| Modular monolith | عملیات ساده با مرز داخلی | نیاز به enforcement و انضباط |
| Microkernel | extension و تنوع مشتری | سازگاری نسخه و امنیت افزونه |
| سرویس جدا | انتشار یا scale مستقل | شبکه، telemetry و consistency |

اول boundary را درون process enforce کن؛ فقط در صورت نیاز واقعی به scale، انتشار، مالکیت یا failure isolation مستقل، مرز شبکه‌ای بساز.

## درس گام‌به‌گام: ساخت Modular Monolith

فروشگاه را با ماژول‌های catalog، orders، inventory و payments تصور کن:

۱. **مالک قانون چیست؟** قانون رزرو کالا متعلق به inventory است؛ orders می‌تواند درخواست رزرو دهد، ولی مقدار موجودی را مستقیماً تغییر نمی‌دهد.
۲. **داده را چه کسی می‌نویسد؟** هر ماژول مالک جدول‌ها و migration خودش است. خواندن از projection داخلی با نوشتن مستقیم در جدول همسایه فرق دارد.
۳. **قرارداد چیست؟** ReserveStock با شناسهٔ سفارش و اقلام؛ پاسخ می‌تواند Reserved، InsufficientStock یا Unavailable باشد. قرارداد خطای کسب‌وکار را از خطای زیرساخت جدا می‌کند.
۴. **وابستگی کدام‌طرفه است؟** orders به قرارداد inventory وابسته است؛ inventory نباید نوع داخلی orders را import کند. چرخهٔ وابستگی را با قرارداد کوچک یا بازطراحی جهت تماس رفع کن.
۵. **مرز چگونه enforce می‌شود؟** package visibility، API داخلی، آزمون namespace، lint معماری یا review لازم است؛ قرارداد شفاهی با گذر زمان می‌شکند.

این طراحی هنوز یک build و deploy دارد؛ پس تغییر schema یا خرابی حافظه می‌تواند کل برنامه را درگیر کند. در عوض، trace، debug و تراکنش درون‌فرایندی ساده‌ترند. مرز ماژول باید همین حالا مستقل و آزمون‌پذیر باشد، حتی اگر هرگز سرویس نشود.

## چه وقت استخراج سرویس توجیه دارد؟

شواهد جمع کن: آیا انتشار مستقل لازم است؟ آیا الگوی بار با کل برنامه فرق دارد؟ آیا تیم مالک و مسئول on-call مستقل دارد؟ آیا failure isolation یا الزام امنیتی خاص می‌خواهد؟ آیا داده را می‌توان با قرارداد روشن جدا کرد؟ آیا ارزش استقلال از هزینهٔ شبکه، tracing، deployment، پایش، incident و سازگاری داده بیشتر است؟

اگر پاسخ روشن نیست، اول مرز داخلی را اندازه‌گیری کن. استخراج را تدریجی انجام بده: مصرف‌کنندگان قرارداد را شناسایی کن، API داخلی پایدار بساز، مالکیت داده را منتقل کن، مسیر قدیمی و جدید را با برنامهٔ هم‌زیستی مدیریت کن، telemetry مقایسه‌ای اضافه کن و بعد مسیر قدیمی را خاموش کن. dual write بی‌قیدوشرط نساز؛ دو منبع حقیقت ناسازگار می‌شوند.

## درس Microkernel: هسته و افزونه

هسته قابلیت‌های ضروری و قرارداد افزونه را تعریف می‌کند. افزونهٔ گزارش می‌تواند ReportProvider را پیاده‌سازی کند. نقطهٔ توسعه باید نسخهٔ قرارداد، timeout، quota، مجوز هر capability، ثبت و حذف افزونه، خطا و سیاست ناسازگاری را تعریف کند. افزونه‌ای که در همان process اجرا می‌شود ممکن است به حافظه و credential برنامه دسترسی داشته باشد؛ برای افزونهٔ غیرقابل‌اعتماد process جدا یا sandbox واقعی لازم است. «plugin» خودش مرز امنیتی نیست.

## تصمیم نمونه

برای فروشگاهی با یک تیم و دامنهٔ در حال تغییر، modular monolith با چهار ماژول و یک دیتابیس عملی است. اگر تیم inventory بعداً به انتشار و scale مستقل نیاز داشت و مالکیت داده را پذیرفت، همان مرز کاندید استخراج می‌شود. تصمیم را با latency، نرخ خطا، چرخهٔ release، بار تیم و هزینهٔ on-call دوباره ارزیابی کن.

## دام‌ها

- نام‌گذاری پوشه به‌جای ساختن boundary واقعی.
- دادن دسترسی کامل به دیتابیس core به plugin.
- تجزیه بر پایهٔ جدول یا لایهٔ فنی.
- مهاجرت big-bang و تغییر هم‌زمان همه‌چیز.

## آزمون

۱. Modular monolith چه تفاوتی با کد بی‌مرز دارد؟ **پاسخ:** ماژول‌ها قرارداد و قواعد وابستگی دارند و تخطی قابل‌سنجش است.

۲. Microkernel برای چه مسئله‌ای مناسب است؟ **پاسخ:** هستهٔ پایدار با قابلیت‌های اختیاری و افزونه‌ای.

۳. چه چیزی جداسازی به سرویس را توجیه می‌کند؟ **پاسخ:** نیاز واقعی به release، scale، ownership یا isolation مستقل همراه با توان عملیات.

۴. چرا «شاید بعداً سرویس شود» کافی نیست؟ **پاسخ:** هزینهٔ شبکه و عملیات را امروز قطعی می‌کند و منفعت را فرضی می‌گذارد.

## تمرین

فروشگاه را به ماژول‌های catalog، order، inventory و billing تقسیم کن. owner، قرارداد و dependency rule هرکدام را بنویس.

## پاسخ نمونهٔ تمرین

catalog مالک محصول و قیمت فهرست، order مالک lifecycle سفارش، inventory مالک رزرو/تعداد، billing مالک payment attempt و refund است. هر ماژول API داخلی دارد؛ orders مجاز است قرارداد inventory را صدا بزند اما جدولش را ننویسد. dependency rule را با import check یا test enforce کن. این جداسازی اول در یک deployment می‌ماند.
