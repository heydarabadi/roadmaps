# اصول طراحی و کد تمیز

## ایدهٔ مرکزی

اصل طراحی، راهی برای دیدن هزینهٔ وابستگی و تغییر است، نه فرمولی که بدون زمینه رعایت شود. این اصول وقتی ارزش دارند که پیش‌بینی‌پذیری تغییر را بالا ببرند و رفتار را واضح‌تر کنند؛ abstraction بی‌نیاز می‌تواند برعکس، فهم را دشوار سازد.

## اصول مهم

- **SOLID:** مسئولیت متمرکز، توسعه با گسترش کنترل‌شده، جایگزینی قراردادها، interface کوچک و وابستگی به abstraction. این اصول عمدتاً به طراحی شیءگرا مربوط‌اند و مرزهای معماری کل سیستم را جایگزین نمی‌کنند.
- **DRY:** از تکرار دانش یکسان بپرهیز؛ دو قطعه کد شبیه ممکن است دو قاعدهٔ متفاوت باشند و نباید زودهنگام یکی شوند.
- **YAGNI:** قابلیت فرضی آینده را پیشاپیش نساز؛ اما الزامات قطعی و هزینهٔ تغییر معماری را هم نادیده نگیر.
- **Law of Demeter:** ماژول به زنجیرهٔ داخلی آبجکت‌های دیگر وابسته نشود.
- **Tell, don’t ask:** رفتار را به مالک داده بسپار، نه اینکه state را بگیری و بیرون تصمیم بگیری.
- **Composition over inheritance:** با کنار هم گذاشتن اجزای کوچک، رفتار قابل‌تعویض بساز.
- **Program to an interface:** مصرف‌کننده به قرارداد متکی باشد، نه جزئیات زیرساختی.
- **High cohesion / low coupling:** هر بخش مسئولیت مرتبط داشته و تغییرش وابستگی بی‌دلیل به بخش‌های دیگر ایجاد نکند.
- **Keep policy apart from detail:** قاعدهٔ کسب‌وکار وابسته به framework، پایگاه داده یا UI نباشد.

## SOLID با مثال

فرض کنیم کلاس Checkout هم مبلغ را محاسبه می‌کند، کوپن را اعتبارسنجی می‌کند، مستقیم به provider پرداخت وصل می‌شود، سفارش را ذخیره می‌کند و ایمیل می‌فرستد. هر تغییر تجاری یا فنی ممکن است همین کلاس را مجبور به تغییر کند. SOLID این بوها را با پنج زاویه بررسی می‌کند:

- **Single Responsibility:** یک ماژول باید دلیل اصلی و منسجم برای تغییر داشته باشد. تقسیم بر پایهٔ «هر متد یک کلاس» افراطی است؛ هدف هم‌راستایی رفتارهای مرتبط است.
- **Open/Closed:** افزودن روش پرداخت جدید نباید شرط‌های provider را در همهٔ جریان checkout پخش کند. قرارداد مشترک و adapter می‌تواند تغییر را محدود کند؛ abstraction عمومی برای provider خیالی آینده ارزش ندارد.
- **Liskov Substitution:** پیاده‌سازی جایگزین باید قرارداد مصرف‌کننده را رعایت کند. اگر ProviderB همیشه timeout می‌کند، validation یا semantics متفاوت دارد، نمی‌توان فرض کرد با تعویض object رفتار درست می‌ماند.
- **Interface Segregation:** کلاینت نباید به متدهای بی‌استفاده وابسته شود. interface پرداخت و refund ممکن است برای نقش‌های متفاوت مناسب‌تر از یک interface بزرگ باشد.
- **Dependency Inversion:** policy checkout به جزئیات provider و دیتابیس وابسته نشود؛ جزئیات adapter قرارداد داخلی را پیاده کنند. Dependency inversion جهت وابستگی کد است، نه الزاماً استفاده از container تزریق وابستگی.

## cohesion و coupling را چطور تشخیص دهیم؟

کوهیژن بالا یعنی اجزای یک ماژول برای یک هدف نزدیک کنار هم‌اند. اگر تغییر قانون refund باعث تغییر renderer و report هم می‌شود، احتمالاً responsibility یا مدل تغییر خوب جدا نشده است. coupling پایین یعنی مصرف‌کننده برای استفاده از یک قابلیت لازم نیست جزئیات خصوصی و ناپایدار provider را بشناسد.

کاهش coupling به معنی صفرکردن وابستگی نیست. API برای ارتباط، data contract برای انتقال و domain language برای فهم مشترک لازم‌اند. پرسش درست این است: وابستگی به چه چیزی است، کدام بخش مالک آن است و تغییر قرارداد چطور مدیریت می‌شود؟

## اصل‌ها را در اندازهٔ مناسب اعمال کن

### تصمیم نمونه: ساخت abstraction

**وضعیت فعلی:** یک provider پرداخت داریم؛ پیاده‌سازی مستقیم در use case است.  
**نیاز قطعی:** تست بدون تماس شبکه و ثبت تراکنش نامشخص.  
**تغییر کافی:** قرارداد کوچک PaymentGateway برای authorize/status، یک adapter واقعی و یک fake تست.  
**چیزی که هنوز لازم نیست:** plugin discovery عمومی، runtime provider loading و registry چندمستاجره.  
**بازنگری:** وقتی provider دوم با قرارداد و چرخهٔ خطای واقعاً متفاوت وارد شد.

به این ترتیب اصل program to abstraction عملی می‌شود، بدون ساخت framework زودهنگام.

## مثال: ارسال اعلان

به‌جای اینکه سرویس سفارش مستقیماً ایمیل و SMS بسازد، به یک قرارداد NotificationPort وابسته شود. adapterهای ایمیل و پیامک جزئیات ارائه‌دهنده‌اند. اگر یک قاعدهٔ واحد برای همهٔ کانال‌هاست، اشتراک آن منطقی است؛ اگر تفاوت‌های محصولی دارد، یک تابع مشترک برای حذف چند خط کد ممکن است طراحی بدتری بسازد.

~~~csharp
public interface INotifier
{
    Task SendAsync(Notification message, CancellationToken ct);
}
~~~

## اصل، نشانه و عمل

| نشانه | پرسش راهنما |
| --- | --- |
| تغییر یک قاعده چند ماژول را می‌شکند | آیا یک منبع دانش پراکنده است؟ |
| mockها از implementation تقلید می‌کنند | آیا مرز قرارداد درست انتخاب شده؟ |
| abstraction فقط یک پیاده‌سازی و یک مصرف‌کننده دارد | آیا این abstraction اکنون سودی دارد؟ |
| کلاس مسئول همه‌چیز است | آیا مسئولیت‌ها و دلیل تغییر متفاوت‌اند؟ |

## دام‌ها

- تبدیل SOLID به الزامات «یک interface برای هر class».
- DRY افراطی که تفاوت دامنه‌ها را پنهان کند.
- نوشتن framework داخلی پیش از وجود use case واقعی.
- استفاده از abstraction صرفاً برای mocking در آزمون.

## آزمون

۱. چه زمانی دو قطعهٔ تکراری را نباید یکی کرد؟  
**پاسخ:** وقتی فقط شکل کد شبیه است اما دانش کسب‌وکار یا سرعت تغییرشان متفاوت است.

۲. تفاوت decoupling با حذف همهٔ وابستگی‌ها چیست؟  
**پاسخ:** سامانه به قراردادها و داده نیاز دارد؛ هدف وابستگی روشن و قابل‌کنترل است، نه نبودن ارتباط.

۳. چرا composition می‌تواند از inheritance امن‌تر باشد؟  
**پاسخ:** رفتار را با اجزای مستقل ترکیب می‌کند و از وابستگی عمیق به سلسله‌مراتب پایه می‌کاهد.

۴. YAGNI چگونه با طراحی آینده‌پذیر سازگار می‌شود؟  
**پاسخ:** برای نیاز محتمل و هزینهٔ تغییر برنامه‌ریزی می‌کنیم، اما قابلیت‌های فرضی را بدون شواهد پیاده نمی‌سازیم.

## تمرین

یک کلاس فرضی OrderService را که پرداخت، ارسال ایمیل، ذخیره‌سازی و محاسبهٔ تخفیف دارد، به مسئولیت‌ها و قراردادهای روشن تقسیم کن. سه اصل کاربردی و هزینهٔ abstraction خود را توضیح بده.

## پاسخ نمونهٔ تمرین

OrderService را به هماهنگ‌کنندهٔ use case، Order domain، DiscountPolicy، PaymentGateway port، OrderRepository و Email adapter جدا کن. قانون تخفیف در دامنه/policy، SQL در repository adapter و ارسال پیام پس از commit در outbox قرار گیرد. SRP و dependency inversion تغییر را محدود می‌کنند؛ interface بی‌نیاز، mapperهای متعدد و indirection هزینه‌اند. برای هر abstraction دلیل تغییر مستقل و آزمون ساده‌تر را نشان بده.
