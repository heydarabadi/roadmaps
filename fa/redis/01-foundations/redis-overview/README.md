# Redis چیست؟

> English edition: [What is Redis?](../../../../en/redis/01-foundations/redis-overview/README.md)

> سطح پیشنهادی: مقدماتی تا میانی · زمان: ۳۰ تا ۶۰ دقیقه

## هدف یادگیری

مدل کلید-مقدار ساختاریافته و تفاوت حافظه با دوام را توضیح بدهی.

## درس

Redis یک سرور دادهٔ درون‌حافظه‌ای با مدل کلید-مقدار است؛ مقدار می‌تواند String، List، Hash، Set، Sorted Set یا نوع‌های تخصصی‌تر باشد. دستورها عملیات معنایی و اغلب اتمی روی ساختار انجام می‌دهند. Redis را فقط cache دانستن اشتباه است: می‌تواند cache، session store، شمارنده، صف ساده یا کانال رویداد باشد؛ انتخاب نقش به دوام، ترتیب، تحویل پیام و تحمل خرابی وابسته است.

داده معمولاً در RAM نگهداری می‌شود؛ RDB/AOF ماندگاری روی دیسک را اختیاری می‌کنند. RAM هزینه و ظرفیت دارد و persistence جای backup مستقل را نمی‌گیرد. Redis جایگزین خودکار SQL نیست: join، constraint و query رابطه‌ای را به‌طور عمومی ارائه نمی‌دهد.

## مدل ذهنی: برنامه، شبکه، سرور، کلید، مقدار

تصور کن برنامهٔ تو در یک طرف و Redis Server در طرف دیگر شبکه است. برنامه معمولاً از یک library به نام client استفاده می‌کند؛ در تمرین ما redis-cli همان نقش را دارد. client فرمان را با پروتکل Redis روی اتصال TCP می‌فرستد، server آن را روی database انتخاب‌شده اجرا می‌کند و پاسخ را برمی‌گرداند. بنابراین Redis یک dictionary درون همان process برنامه نیست؛ یک سرویس مستقل است و هزینهٔ network round trip و اتصال را هم باید در نظر گرفت.

هر key نام یکتای یک مقدار در همان database منطقی است. value شکل داده را مشخص می‌کند. اگر مقدار یک رشته باشد، GET مناسب است؛ اگر key از نوع Hash باشد، HGET/HSET مناسب‌اند. در هر لحظه key یک نوع دارد. دستور ناسازگار معمولاً خطای WRONGTYPE می‌دهد؛ این خطا نشانهٔ آن است که مدل کلید یا دستور را اشتباه انتخاب کرده‌ای، نه اینکه Redis نوع را خودکار تبدیل می‌کند.

## انواع داده چه مسئله‌ای را حل می‌کنند؟

| نوع | تصویر ذهنی | یک عملیات مهم | مثال |
|---|---|---|---|
| String | یک مقدار یا رشتهٔ بایت | GET/SET و INCR | token، counter، payload کوچک |
| List | دنبالهٔ مرتب با دو سر | LPUSH/RPOP | صف ساده |
| Set | کیسهٔ عضوهای یکتا و بی‌ترتیب | SADD/SISMEMBER | tag و membership |
| Hash | رکورد با field/value | HSET/HGET | profile کوچک |
| Sorted Set | عضوهای یکتا با score مرتب | ZADD/ZRANGE | رتبه‌بندی |

انواع دیگری مانند Bitmap، HyperLogLog، Stream، Geo، JSON، Time Series و Vector Sets برای نیازهای تخصصی‌اند؛ آن‌ها را در فصل‌های مربوطه می‌خوانی. انتخاب نوع باید بر اساس عملیات پرتکرار انجام شود. اگر برنامه هر بار مجبور است کل JSON را بگیرد، تغییر دهد و دوباره ذخیره کند تا فقط یک counter عوض شود، احتمالاً مدل بهتری وجود دارد.

## اتمیک بودن یعنی چه؟

یک فرمان Redis هنگام اجرا به‌صورت کامل اعمال می‌شود؛ کلاینت دیگری بین دو نیمهٔ همان فرمان وارد نمی‌شود. برای همین INCR شمارنده از این الگو امن‌تر است: برنامه GET می‌کند، خودش یک واحد اضافه می‌کند و SET می‌کند. دو برنامه ممکن است هم‌زمان مقدار یکسان بخوانند و یکی از افزایش‌ها گم شود.

این ویژگی به معنی اتمیک بودن کل منطق برنامه نیست. اگر workflow شامل خواندن موجودی، بررسی شرط، ثبت سفارش و پرداخت است، چند GET و SET جدا ممکن است بین‌شان با درخواست دیگری تداخل کنند. برای بخشی از این نیازها WATCH/MULTI یا script/function استفاده می‌شود؛ حتی آن‌ها هم جای طراحی transaction دامنه‌ای در دیتابیس اصلی را نمی‌گیرند.

## In-memory با durable یکی نیست

Redis داده را برای دسترسی سریع در حافظه نگه می‌دارد. «در RAM» نمی‌گوید پس از خاموشی چه می‌شود. اگر persistence غیرفعال باشد، با خروج process داده از بین می‌رود. RDB در زمان‌های مشخص snapshot می‌سازد؛ AOF تغییرها را ثبت می‌کند و در startup بازپخش می‌کند. هرکدام پنجرهٔ از‌دست‌رفتن، هزینهٔ write، حجم فایل و زمان restore خود را دارند.

سه مفهوم را جدا نگه دار:

1. **Replication:** کپی‌کردن تغییرها به replica برای availability/خواندن؛ معمولاً ناهمگام است.
2. **Persistence:** نوشتن وضعیت روی دیسک برای بارگذاری دوباره.
3. **Backup:** نسخهٔ قابل‌بازیابی در مقصدی جدا، همراه با آزمون restore.

داشتن replica یا فایل persistence به‌تنهایی ثابت نمی‌کند که از حذف اشتباهی، خرابی دیسک یا تغییر مخرب می‌توانی برگردی. برای state مهم، منبع حقیقت، RPO، RTO و مسیر بازیابی را قبل از deploy بنویس.

## Walkthrough دستورهای پایه

در لَب فصل صفر این فرمان‌ها را یکی‌یکی اجرا کن:

~~~text
SET user:42:name "Sara"
GET user:42:name
TYPE user:42:name
HSET user:42 profile "premium" city "Tehran"
HGETALL user:42
TYPE user:42
~~~

ردّ خروجی:

1. SET key رشته‌ای را ایجاد/جایگزین می‌کند و معمولاً OK برمی‌گرداند.
2. GET مقدار همان رشته را برمی‌گرداند.
3. TYPE برای key اول string می‌گوید.
4. HSET دو field با مقدارهایشان می‌نویسد؛ در key تازه، پاسخ عددی تعداد fieldهای جدید است.
5. HGETALL تمام field/valueهای رکورد را برمی‌گرداند.
6. TYPE برای key دوم hash می‌گوید.

دو key در مثال نام‌گذاری متفاوت دارند تا fieldهای یک Hash را با رشتهٔ مستقل اشتباه نگیری. اگر به‌جای HGET روی key رشته‌ای دستور بزنی، خطای نوع می‌گیری. اگر key را با SET دوباره بنویسی، مقدار قبلی آن key جایگزین می‌شود؛ keyهای هم‌نام فضاهای منطقی جدا نیستند.

## Redis را کجا نگذاریم؟

- وقتی داده باید با constraintهای رابطه‌ای، joinهای پیچیده و گزارش تحلیلی مدیریت شود، SQL معمولاً مرجع اصلی مناسب‌تری است.
- وقتی پیام آفلاین نباید گم شود، Pub/Sub ساده کافی نیست؛ Streams یا broker مناسب را بررسی کن.
- وقتی cache را نمی‌توان از جای دیگری بازسازی کرد، دیگر با cache قابل‌دورریختن طرف نیستی؛ durability و backup را جدی بگیر.
- وقتی data set از RAM فراتر می‌رود، هزینه، eviction و tiering را پیش از انتخاب بسنج.

## چک‌لیست پیش از استفاده

پیش از اضافه‌کردن Redis به سرویس، این سؤال‌ها را جواب بده: کدام داده ذخیره می‌شود؟ منبع اصلی چیست؟ حجم پیک و نرخ خواندن/نوشتن چقدر است؟ چه مقدار stale data پذیرفته می‌شود؟ اگر Redis unreachable شود چه می‌کنیم؟ keyها چطور منقضی/پاک می‌شوند؟ چه کسی ACL و backup را اداره می‌کند؟ موفقیت را با کدام metric می‌سنجیم؟

## خطاهای رایج

فرض دوام به‌خاطر in-memory بودن، انتخاب Redis به‌عنوان منبع حقیقت بدون RPO/RTO روشن، یا تصور یکسان بودن رفتار همهٔ نوع‌ها.

## تمرین

1. مثال را در Redis محلی اجرا و خروجی را با زبان خودت توضیح بده.
2. دو حالت شکست یا edge case برای این الگو بنویس.
3. برای workload خودت حجم داده، نرخ خواندن/نوشتن، TTL یا retention و رفتار زمان outage را مشخص کن.
4. یک معیار بگذار: p95 latency، hit rate، RAM، lag، pending count یا زمان restore.
