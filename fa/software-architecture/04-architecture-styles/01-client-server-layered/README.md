# معماری کلاینت–سرور و لایه‌ای

## ایدهٔ مرکزی

این الگوها مسئولیت و وابستگی را سازمان می‌دهند: client از server درخواست می‌کند؛ در معماری لایه‌ای، presentation، application/domain و infrastructure/data جدا می‌شوند. تقسیم‌بندی وقتی ارزش دارد که مرزهای رفتاری و قواعد وابستگی را روشن کند.

## مفاهیم و مثال

کلاینت درخواست را به قرارداد می‌فرستد و پاسخ یا خطا می‌گیرد. مرورگر و API، موبایل و backend، یا سرویس billing و هویت نمونه‌اند. server می‌تواند sessionدار یا stateless باشد؛ مرز شبکه latency و خرابی می‌آورد، پس timeout، retry محدود، idempotency، احراز هویت و versioning لازم‌اند.

لایهٔ UI ورودی را می‌گیرد؛ application service use case را هماهنگ می‌کند؛ domain قواعد را نگه می‌دارد؛ infrastructure ذخیره‌سازی و اتصال بیرونی را انجام می‌دهد. «لایه» تقسیم منطقی است؛ «tier» مرز اجرایی deployment. در سامانهٔ نوبت‌دهی، controller ورودی را به command تبدیل می‌کند، application service رزرو را اجرا می‌کند، domain تداخل زمان را رد می‌کند و repository ذخیره می‌کند.

~~~text
Browser -> HTTPS -> Web/API -> Use cases -> Domain rules
                                           ^ interface
                                      SQL adapter
~~~

| سبک | مناسب | خطر |
| --- | --- | --- |
| لایه‌ای | دامنهٔ سنتی و تغییرات نه‌چندان مکرر | CRUD pass-through و coupling به دیتابیس |
| client-server | چند نوع client یا جداسازی مالکیت | round-trip و وابستگی شبکه |
| tierهای جدا | مرز امنیت یا scale مستقل | هزینهٔ شبکه و consistency |

## درس گام‌به‌گام: درخواست از مرورگر تا داده

فرض کنیم مشتری دکمهٔ «ثبت سفارش» را می‌زند. هر گام مسئولیت جدا دارد:

۱. **مرورگر** ورودی را برای تجربهٔ کاربری بررسی می‌کند؛ این بررسی مرز امنیتی نیست، چون کاربر می‌تواند درخواست HTTP را خودش بسازد.
۲. **API** هویت را از session یا token معتبر استخراج می‌کند، شکل پیام را اعتبارسنجی می‌کند و خطای ورودی را به پاسخ قراردادی تبدیل می‌کند.
۳. **Application service** use case را هماهنگ می‌کند: اعتبار سبد را می‌خواند، قانون دامنه را صدا می‌زند و تراکنش را مدیریت می‌کند.
۴. **Domain** قواعدی مانند «سفارش باید حداقل یک قلم داشته باشد» یا «مبلغ از قیمت معتبر سمت سرور محاسبه می‌شود» را اعمال می‌کند. این قانون را در controller یا صفحهٔ وب پنهان نکن.
۵. **Repository/adapter** قرارداد داخلی را به SQL یا سرویس بیرونی وصل می‌کند. domain نباید به نوع دیتابیس یا SDK ارائه‌دهنده گره بخورد.
۶. پاسخ موفق یا خطا به قرارداد بیرونی تبدیل می‌شود. stack trace و query را به مشتری نشان نده.

این جریان به‌تنهایی کار را اتمی نمی‌کند. اگر رزرو موجودی و پرداخت در دو سامانهٔ مستقل انجام شوند، یک تراکنش SQL هر دو را commit نمی‌کند؛ برای آن مسئله به فرایند چندمرحله‌ای، idempotency و جبران نیاز داریم.

## لایه در برابر tier

لایه مرز **کد و مسئولیت** است؛ tier مرز **فرایند، ماشین یا شبکه** است. می‌توان چند لایه را در یک برنامه و یک فرایند اجرا کرد؛ همچنین می‌توان API و پایگاه داده را در tierهای جدا مستقر کرد. جداسازی اجرایی latency، credential، اتصال‌های قابل‌قطع و نیاز عملیاتی می‌آورد؛ آن را وقتی بپذیر که امنیت، scale، مالکیت یا دسترس‌پذیری از آن سود بگیرد.

## قواعد وابستگی که واقعاً لایه می‌سازند

- use case، domain را برای اجرای قانون صدا می‌زند؛ domain به abstraction وابسته است، نه adapter مشخص.
- adapterها در لبه‌اند: HTTP، پایگاه داده، صف و provider پرداخت را به قرارداد داخلی وصل می‌کنند.
- اگر همهٔ لایه‌ها بتوانند یکدیگر را دور بزنند، ساختار فقط نام‌گذاری پوشه است. dependency rule را با آزمون معماری، lint یا review قابل‌اجرا کن.
- لایهٔ بیشتر خودبه‌خود کیفیت بیشتر نمی‌دهد؛ لایه‌ای را نگه دار که تغییر را محدود کند یا مسئولیت قابل‌فهمی داشته باشد.

## ادارهٔ شکست در client-server

شبکه نتیجهٔ مبهم می‌دهد: timeout یعنی «پاسخ در مهلت نرسید»، نه اینکه «سرور قطعاً کاری نکرد». برای query معمولاً retry محدود پس از backoff قابل‌قبول است؛ برای command ابتدا اثر تکرار را مشخص کن. client برای command یک idempotency key می‌فرستد؛ server همان نتیجهٔ قبلی را برای همان هویت و payload بازمی‌گرداند. دامنهٔ یکتایی، ماندگاری نتیجه و مدت نگهداری کلید را تعریف کن. اگر payload متفاوتی با همان کلید رسید، آن را رد کن.

retry لایه‌های مختلف می‌توانند روی هم ضرب شوند و بار خرابی را زیاد کنند. deadline کلی درخواست، تعداد retry، backoff همراه jitter و سقف هم‌زمانی را با latency بودجه‌بندی کن. برای دادهٔ cacheشده نیز مشخص کن چه مقدار کهنگی پذیرفتنی است.

### نمونهٔ انتخاب برای فروشگاه

برای تصویر محصول، مرورگر می‌تواند فایل را با URL موقت مستقیم به ذخیره‌سازی بفرستد تا ترافیک از سرور برنامه عبور نکند. اما برای ثبت سفارش، قیمت و مجوز باید از دادهٔ معتبر server محاسبه شود. اگر API و پایگاه داده در یک فرایند deploy شوند، اجرا ساده‌تر است؛ اگر جداسازی شبکه برای حفاظت داده یا scale مستقل ارزش قابل‌اندازه‌گیری دارد، tier جدا توجیه می‌شود.

## دام‌ها

- فرض اینکه deployment جدا coupling را خودکار کم می‌کند.
- گذاشتن business rule در controller.
- نادیده‌گرفتن failure mode و timeout.
- ساختن لایه‌هایی که فقط داده را پاس می‌دهند.

## آزمون خودسنجی

۱. Layer و tier چه تفاوتی دارند؟ **پاسخ:** layer تقسیم منطقی مسئولیت است؛ tier مرز فیزیکی یا اجرایی استقرار.

۲. چرا retry بی‌قیدوشرط خطرناک است؟ **پاسخ:** ممکن است عملیات دوباره اعمال یا retry storm ایجاد شود؛ idempotency و سقف لازم است.

۳. لایه‌ای چه زمانی سودمند است؟ **پاسخ:** وقتی جداسازی وظایف وابستگی را کنترل و ساختار را قابل‌فهم می‌کند.

۴. چه زمانی لایه‌ها به ceremony تبدیل می‌شوند؟ **پاسخ:** وقتی هیچ boundary یا policy را محافظت نمی‌کنند و فقط پاس‌دهنده‌اند.

## تمرین

use case لغو نوبت را از HTTP تا پایگاه داده ترسیم کن و جای قانون بازپرداخت را مشخص کن.

## پاسخ نمونهٔ تمرین

لغو نوبت از HTTP adapter وارد application use case می‌شود؛ domain بررسی می‌کند آیا بازهٔ زمانی و policy لغو/جریمه مجاز است؛ repository وضعیت را اتمی ذخیره می‌کند. پرداخت بازگشتی در adapter پرداخت و workflow جدا انجام می‌شود، نه در controller. API پس از commit پاسخ قراردادی می‌دهد و side effect پیام/بازپرداخت با state و idempotency دنبال می‌شود.
