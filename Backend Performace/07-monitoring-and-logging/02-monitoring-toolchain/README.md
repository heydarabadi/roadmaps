# ۷.۲ — زنجیره ابزارهای پایش | Monitoring Toolchain

**زبان:** فارسی · [English version](README.en.md)


زنجیره پایش، داده برنامه را به مشاهده و اقدام تبدیل می‌کند: تولید، جمع‌آوری، پردازش، ذخیره، پرس‌وجو، نمایش و هشدار. خرید یا نصب داشبورد فقط یکی از این مرحله‌هاست. **هدف این درس طراحی مسئولیت‌ها و مرز خرابی است؛ Prometheus، Grafana و ELK مثال‌اند، نه پشته اجباری.**

**تاریخ بررسی منابع: <span dir="ltr">2026-11-10</span>.** سناریوها و اعداد فرض آموزشی‌اند؛ مستندات عملیاتی رسمی با حد شواهد مشخص آمده‌اند.

## پیش‌نیازهای همین درس

Metric اندازه‌گیری عددی و قابل‌تجمیع است؛ Log رخداد زمان‌دار و Trace مجموعهٔ مرحله‌های مرتبط یک کار است. Collector داده را از برنامه/میزبان می‌گیرد و به مقصد می‌رساند؛ ذخیره‌ساز آن را نگه می‌دارد و امکان Query می‌دهد؛ داشبورد نتیجه را نمایش می‌دهد. این مرزبندی در همین صفحه توضیح داده می‌شود، پس برای فهم آن نیازی به نصب محصول یا خواندن درس دیگری نیست.

## خروجی‌های یادگیری

- نقش ابزارگذاری، Collector، ذخیره‌ساز، Query و داشبورد را جدا می‌کنید.
- برای نیاز کوچک یا چندسرویسی، زنجیره متناسب انتخاب می‌کنید.
- تأخیر داده، ظرفیت نگهداری و خرابی مسیر Telemetry را محاسبه می‌کنید.
- هشدار قابل اقدام و پایش مستقلِ خود ابزارها طراحی می‌کنید.

## مدل ذهنی و اجزای نمونه

| مسئولیت | مثال ابزار یا سازوکار | چیزی که به‌تنهایی حل نمی‌کند |
| --- | --- | --- |
| تولید داده | Metric/Log/Span در برنامه و Exporter میزبان | نگهداری و جست‌وجوی مرکزی |
| جمع‌آوری | Scrape، Agent یا OpenTelemetry Collector | معنی درست سیگنال و دسترسی ایمن |
| ذخیره و Query | پایگاه داده زمانی، موتور جست‌وجوی Log، مخزن Trace | تشخیص خودکار همه علت‌ها |
| نمایش | Grafana یا رابط محصول انتخابی | وجود داده تازه و کامل |
| ارزیابی و اعلان | Rule Evaluator و سامانه مسیریابی هشدار | واکنش انسانی بدون مالک و دستور اقدام |

Prometheus می‌تواند متریک هدف‌ها را Scrape، ذخیره و Query کند و Rule ارزیابی کند؛ Alertmanager نمونه‌ای برای گروه‌بندی و مسیریابی هشدار است. Grafana از Data Sourceهایی مانند Prometheus یا پایگاه داده دیگر Query می‌گیرد؛ [مستند رسمی Data Sources](https://grafana.com/docs/grafana/latest/datasources/) این جدایی را توضیح می‌دهد. Grafana همچنین قابلیت‌های هشدار دارد، اما یک نمودار به‌خودی‌خود ذخیره‌ساز همه سیگنال‌ها نیست.

نام تاریخی **ELK** از Elasticsearch، Logstash و Kibana می‌آید: به‌ترتیب جست‌وجو/ذخیره، پردازش/انتقال و مشاهده. [مستند فعلی Elastic برای Logs](https://www.elastic.co/docs/solutions/observability/logs) مسیرهای مختلف جمع‌آوری را معرفی می‌کند؛ وجود Logstash در همه استقرارها شرط نیست. سرویس مدیریت‌شده، Agent دیگر یا ابزار ساده‌تر نیز ممکن است کافی باشد. OpenTelemetry هم می‌تواند داده استانداردشده را به مقصد سازگار بفرستد؛ همان محصول ذخیره‌ساز نیست.

## مسیر تصمیم مرحله‌به‌مرحله

۱. **از پرسش و هدف شروع کنید.** مثلاً «آیا رزرو موفق در مهلت افت کرده؟» و «کدام وابستگی زمان را گرفته؟» برای هر پرسش، سیگنال، مالک و زمان نگهداری تعیین کنید. فهرست طولانی ابزار جای این تصمیم نیست.

۲. **داده حداقلی را از مبدأ تعریف کنید.** نام سرویس، محیط، Route الگو، واحد مدت، نسخه استقرار و Context لازم را یکدست کنید. شناسه مشتری را وارد Label نکنید. CPU میزبان با زمان کاربر یکسان نیست؛ هر دو ممکن است برای تحلیل لازم باشند.

۳. **جمع‌آوری را با نوع کار هماهنگ کنید.** Scrape دوره‌ای برای سرویس زنده مناسب است؛ Job کوتاه ممکن است پیش از Scrape تمام شود و به راه جمع‌آوری دیگری نیاز داشته باشد. Export دوره‌ای، ارسال رخداد و صف واسط نیز تأخیر و شکست خاص خود دارند. چند Agent موازی یا دو مسیر دریافت یک Log می‌توانند Duplicate بسازند.

۴. **بودجه منابع را حساب کنید.** تعداد سری، نرخ Log، اندازه Span، نگهداری، تکرار داده، ایندکس و Query هم‌زمان هزینه دارند. Query گران روی داشبورد با Refresh سریع هم می‌تواند مقصد پایش را اشباع کند. جداسازی منابع پایش از مسیر حساس برنامه، سهمیه و حد Query را متناسب با اندازه سامانه انتخاب کنید.

۵. **تحویل و دسترسی را روشن کنید.** اتصال رمزگذاری‌شده، هویت Agent، دسترسی محدود Data Source و محافظت Endpoint متریک لازم‌اند. Token، Cookie و داده حساس باید پیش از خروج از مبدأ حذف یا پوشانده شوند؛ حذف در صفحه داشبورد، نسخه ذخیره‌شده را پاک نمی‌کند. Retention بر اساس نیاز و داده انتخاب می‌شود، نه همیشه نگهداری حداکثری.

۶. **از داده به اقدام برسید.** هشدار باید اثر، محدوده، زمان شروع، مالک، لینک داشبورد و اقدام بررسی داشته باشد. خطای کاربر و تأخیر نتیجه مناسب‌تر از Page برای هر نوسان CPU هستند. آستانه‌ها، پنجره زمانی، حداقل نمونه و دوره پایداری را متناسب با سرویس تعیین کنید؛ عدد نمونه این درس استاندارد عمومی نیست.

## مثال حل‌شده: اندازه داده و تأخیر کشف

فرض کنید ۱۰۰۰ Log در ثانیه با میانگین ۵۰۰ بایت Payload تولید می‌شود. حجم خام روزانه برابر ۴۳٫۲ گیگابایت و برای هفت روز ۳۰۲٫۴ گیگابایت است؛ واحدها ده‌دهی‌اند. این محاسبه شامل ایندکس، Replica، Metadata، فشرده‌سازی، فضای موقت و سربار انتقال نیست. برای برنامه‌ریزی واقعی باید نرخ اوج و ضرایب اندازه‌گیری‌شده همان زنجیره را اضافه کرد. ذخیره Trace و Metric نیز بودجه جدا می‌خواهد.

اکنون Scrape هر ۱۵ ثانیه، ارزیابی Rule هر ۳۰ ثانیه و تحویل اعلان تا ۱۰ ثانیه فرض کنید. اگر شرط هشدار از اولین نمونه قابل مشاهده باشد، Rule تأخیر پایداری نداشته باشد و تأخیرهای دیگر را صفر فرض کنیم، انتظار فازی تا Scrape بعدی و ارزیابی بعدی و سپس ارسال می‌تواند تقریباً تا ۵۵ ثانیه شود. پنجره محاسبه نرخ، شرط `for`، Jitter، Timeout و وقفه شبکه می‌توانند آن را بیشتر کنند. نتیجه، تضمین واقعی محصول نیست؛ «داشبورد هر ثانیه Refresh شود» الزاماً این مسیر کشف را سریع‌تر نمی‌کند.

در نسبت خطا، صورت و مخرج باید به یک جمعیت و بازه اشاره کنند. صفر درخواست را خودکار «۱۰۰٪ موفق» ننامید؛ ممکن است ترافیک واقعاً کم یا جمع‌آوری خراب باشد. برای **No Data**، مقدار صفر، نمونه قدیمی و خطای Query حالت‌های جدا تعریف کنید. در پنل تأخیر نیز Range زمانی و تجمیع نمونه‌ها باید واضح باشند؛ میانگین p95 نمونه‌ها معتبر نیست.

## پایش خود زنجیره و مرز تضمین

Collector نیز سرویس است: CPU و حافظه، طول/ظرفیت صف، سن داده، نرخ ورودی/خروجی، Drop و شکست Export آن را بسنجید. سلامت Process با رسیدن داده تازه به مقصد فرق دارد. یک رخداد آزمایشی کم‌حجم با زمان تولید می‌تواند تأخیر «تولید تا قابل جست‌وجو شدن» را نشان دهد. مسیر آزمایشی اعلان هم باید تحویل را بسنجد، نه فقط فعال‌شدن Rule.

همه خرابی‌ها را از همان دامنه خرابی مشاهده نکنید. وقتی کل زنجیره داخلی قطع است، یک Probe خارجی یا مسیر اعلان مستقل می‌تواند نبود داده یا عدم دریافت Heartbeat را نشان دهد. [راهنمای Alerting در Prometheus](https://prometheus.io/docs/practices/alerting/) بر هشدار مربوط به اثر کاربر و بررسی سرتاسریِ خود سامانه پایش تأکید دارد.

> **شاهد عملیاتی رسمی و حد آن:** [OpenTelemetry Collector Resiliency](https://opentelemetry.io/docs/collector/resiliency/) توضیح می‌دهد صف ارسال حافظه‌ای قطع کوتاه مقصد را جذب می‌کند، ولی پُرشدن صف، پایان بودجه Retry و Crash می‌توانند داده را از بین ببرند. صف پایدار مبتنی بر ذخیره‌ساز، بازیابی را بهتر می‌کند اما خرابی دیسک، ظرفیت محدود و خطای غیرقابل Retry را حذف نمی‌کند.
>
> این شاهد رفتار عملیاتی مستند یک ابزار است، نه گزارش حادثه یک شرکت یا تضمین «بدون ازدست‌رفتن داده». برای مقایسه عددی چند پشته در بار همین مثال، مطالعه تولیدِ قابل قیاس ارائه نمی‌کنیم؛ اعداد حجم و تأخیر این صفحه فرض‌اند.

## چه وقت انتخاب مناسب یا ضعیف است؟

برای یک سرویس کوچک، چند شاخص کاربر، Log ساختاریافته محدود و یک مسیر هشدار می‌تواند نقطه شروع کافی باشد. چند سرویس با Context مشترک و نیاز به بررسی رخدادها، ذخیره مرکزی و Trace را ارزشمندتر می‌کند. پشته خودمیزبان کنترل و انعطاف می‌دهد ولی نگهداری، نسخه‌گذاری، ظرفیت و بازیابی می‌خواهد. سرویس مدیریت‌شده بخشی از عملیات را برمی‌دارد، اما هزینه حجم، دسترسی و وابستگی به ارائه‌دهنده باقی است. نصب همه اجزا قبل از پرسش مشخص، انتخاب ضعیفی است؛ خاموش‌کردن کل پایش برای کم‌کردن هزینه هم راه شناخت مشکل را می‌بندد.

## تمرین کوچک و مشاهده مورد انتظار

این تمرین کاغذی است. زنجیره‌ای با برنامه، Agent/Collector، ذخیره‌ساز، Query، داشبورد و اعلان رسم کنید. محل‌های بافر و مرزهای پایدار را علامت بزنید. قطع دو دقیقه‌ای ذخیره‌ساز و سپس Crash Collector را جدا بررسی کنید. برای ۲۰۰ Log/s و ۱۰۰۰ بایت Payload، حجم خام یک روز را حساب کنید؛ یک هشدار No Data و یک هشدار اثر کاربر بنویسید.

**راه‌حل:** <span dir="ltr">200 × 1000 × 86,400 = 17,280,000,000</span> بایت ده‌دهی، یعنی <span dir="ltr">17.28 GB</span> دادهٔ خام در روز است؛ ایندکس، Replica و سربار هنوز اضافه نشده‌اند. بافر حافظه‌ای قطع کوتاه را فقط تا ظرفیت جذب می‌کند و Crash می‌تواند آن را از بین ببرد؛ بافر دیسکی هم ظرفیت و قرارداد ACK می‌خواهد. هشدار No Data درباره نبود مشاهده است و هشدار اثر درباره نسبت شکست/دیرکرد؛ یکی جای دیگری را نمی‌گیرد. برای هر دو مالک و راه بررسی لازم است. هیچ قطعی واقعی یا ارسال اعلان در این تمرین اجرا نشده است.

| خطا | چه چیزی دیده می‌شود؟ | کنترل/بررسی |
| --- | --- | --- |
| داشبورد سبز با نمونه قدیمی | زمان آخرین داده عقب مانده | Freshness و No Data |
| رشد بی‌حد Label و ایندکس | RAM/دیسک زیاد و Query کند | بودجه سری، فیلد و Retention |
| فقط پایش CPU | کاربر کند، CPU کم | زمان سرتاسری، صف و وابستگی |
| همه هشدارها روی یک مسیر قطع‌شده | حادثه بدون اعلان | Probe و مسیر مستقل متناسب |
| ارسال دوباره از دو Agent | شمارش/حجم بیش از ورودی | مالکیت دریافت و Duplicate |
| Retry نامحدود Collector | صف پیر، حافظه یا دیسک پُر | سقف صف، Retry و Drop قابل مشاهده |

## چک‌لیست عملیاتی

- [ ] هر ابزار نقش مشخص دارد و انتخابش با اندازه/نیاز سامانه متناسب است.
- [ ] داده تازه، No Data و خطای Query قابل تفکیک‌اند.
- [ ] هزینه خام، ایندکس، Replica و Query سنجیده و Retention تعریف شده است.
- [ ] داده حساس در مبدأ کنترل و Endpointهای مدیریتی محدود شده‌اند.
- [ ] صف، Drop و تأخیر تحویل خود زنجیره دیده می‌شوند.
- [ ] هشدار مالک، اقدام و لینک بررسی دارد؛ مسیر تحویل قابل بررسی است.
- [ ] خرابی Collector/مقصد و بازگشت پس از آن قرارداد روشن دارد.

## آزمون مرور

۱. آیا Grafana به‌تنهایی به معنی ذخیره‌شدن همه داده‌هاست؟

۲. فرق Metric Exporter با مخزن Trace چیست؟

۳. در مثال ۱۰۰۰ Log/s با ۵۰۰ بایت، چرا ۴۳٫۲ گیگابایت بودجه کامل دیسک نیست؟

۴. چرا Refresh یک‌ثانیه‌ای داشبورد، کشف یک‌ثانیه‌ای حادثه را تضمین نمی‌کند؟

۵. آیا نبود نمونه خطا، همان خطای صفر است؟

۶. چرا لازم است خود مسیر اعلان را بررسی کنیم؟

۷. آیا صف دیسکی Collector تضمین می‌کند هیچ داده‌ای از دست نرود؟

### پاسخ‌نامه توضیحی

۱. **خیر.** Grafana داده را از Data Source می‌خواند؛ باید مسیر جمع‌آوری و ذخیره مستقل روشن باشد. قابلیت دیگر محصول، جای طراحی این مسیر را نمی‌گیرد.

۲. **اولی داده اندازه‌گیری را برای جمع‌آوری عرضه/ارسال می‌کند؛ دومی Spanها را نگه می‌دارد و Query می‌کند.** تولید، انتقال و ذخیره مسئولیت‌های متفاوت‌اند.

۳. **این فقط Payload خام است.** ایندکس، Replica، فضای موقت و نرخ اوج باید با اندازه‌گیری اضافه شوند؛ فشرده‌سازی هم ممکن است حجم را کم کند.

۴. **جمع‌آوری، پنجره Rule، ارزیابی و تحویل هرکدام زمان دارند.** نمایش سریع داده قدیمی مسیر تولید داده را سریع نمی‌کند.

۵. **خیر.** نبود ترافیک، نمونه قدیمی، خطای Query یا قطع جمع‌آوری باید از صفر واقعی تفکیک شوند.

۶. **Rule فعال بدون تحویل، کسی را مطلع نمی‌کند.** بررسی سرتاسری و در صورت نیاز مسیر مستقل، خرابی اعلان را قابل مشاهده می‌کند.

۷. **خیر.** ظرفیت، خطای دیسک، Retry و قرارداد پذیرش/ACK هنوز محدودیت دارند؛ باید سناریوهای خرابی و Drop مشخص باشند.

## جمع‌بندی

طراحی را از پرسش، سیگنال و مالک آغاز کنید؛ سپس زنجیرهٔ تولید تا اعلان را با ظرفیت، تازگی داده، امنیت و مرز خرابی بسازید. سلامت خود Collector و تحویل هشدار را جدا پایش کنید. پشتهٔ کوچک کافی، از زنجیرهٔ کامل ولی ناپایدار مفیدتر است.

## منابع تکمیلی اختیاری

برای فهم این درس یا حل تمرین، بازکردن پیوندهای زیر لازم نیست؛ آن‌ها برای مطالعهٔ بیشتر و بررسی مستندات عملیاتی ابزارها هستند.

- **فارسی، مکمل و فهرست دوره:** [مانیتورینگ با گرافانا و پرومتئوس — محمد فزونی](https://www.m-fozouni.ir/courses/monitoring-grafana-prometheus/)؛ معرفی اجزای Metric، داشبورد و Alertmanager. صفحه عمومی قابل خواندن است؛ هنگام بررسی، دوره بسته بود و دسترسی به درس‌های کامل تأیید نشده است. عبارت تبلیغی Production-Ready را تأیید مستقل این بسته ندانید.
