# بهداشت وابستگی‌ها — Dependency Hygiene

**زبان:** فارسی · [نسخهٔ انگلیسی](../../../../en/backend-performance/08-security/01-dependency-hygiene/README.md)  

**هدف یادگیری:** dependency مستقیم و غیرمستقیم را inventory کنید، نتیجه اسکن را در context تفسیر کنید و به‌روزرسانی را با حفظ امنیت و کارایی منتشر کنید. **بررسی منابع: ۲۰۲۶-۱۱-۱۱**؛ مثال و تمرین فرضی و اجرا‌نشده‌اند.

## تعریف و مدل ذهنی

هر کتابخانه، runtime، image پایه یا ابزار build بخشی از زنجیره اعتماد نرم‌افزار است. نقص در parser، HTTP client یا کتابخانه فشرده‌سازی می‌تواند به مصرف نامحدود CPU/حافظه، اختلال یا دسترسی نامجاز برسد. بهداشت وابستگی یعنی بدانیم چه اجزایی در artifact وجود دارند، از کجا آمده‌اند، چه کسی نگهداری‌شان می‌کند و چگونه اصلاح می‌شوند.

| مدرک | چه چیزی می‌گوید؟ | چه چیزی را ثابت نمی‌کند؟ |
| --- | --- | --- |
| Manifest | نیازمندی‌های اعلام‌شده پروژه | نسخه دقیق همه اجزای artifact |
| Lockfile | نسخه‌های resolveشده طبق ابزار | امن‌بودن آن نسخه‌ها |
| SBOM | فهرست اجزای یک build/release | نبود آسیب‌پذیری یا اصالت خودکار |
| SCA/advisory scan | تطبیق اجزا با اطلاعات شناخته‌شده | کشف همه نقص‌های ناشناخته |
| Provenance/امضای معتبر | ارتباط artifact با منشأ و فرایند تعریف‌شده | بی‌نقص‌بودن منطق کد |

ابتدا release و اجزای مستقیم/غیرمستقیم را ثبت کنید؛ سپس advisory معتبر و وضعیت پشتیبانی را بررسی کنید؛ اثر و مواجهه را بسنجید؛ اصلاح یا کنترل موقتِ محدود تعریف کنید؛ در نهایت artifact جدید و شواهد استقرار را تطبیق دهید. [OWASP مدیریت وابستگی آسیب‌پذیر](https://cheatsheetseries.owasp.org/cheatsheets/Vulnerable_Dependency_Management_Cheat_Sheet.html) بر تصمیم متناسب با وضعیت تأکید دارد؛ یافتن CVE، پایان بررسی نیست.

## کاربرد و مصالحه امنیت/کارایی

همه سرویس‌های دارای کد بیرونی به این چرخه نیاز دارند. حذف dependency بلااستفاده می‌تواند سطح حمله و حجم build را کم کند؛ بازنویسی شتاب‌زده قابلیت حساس امنیتی جایگزین مناسبی نیست. نسخه pinشده تکرارپذیری را بهتر می‌کند، ولی pin ابدی می‌تواند آسیب‌پذیری را ماندگار کند. ارتقای خودکار بدون بررسی تغییر رفتار نیز ممکن است سازگاری یا مصرف منابع را خراب کند.

به‌روزرسانی parser می‌تواند حد ورودی یا هزینه پردازش را تغییر دهد؛ صحت، امنیت، latency و حافظه را با ورودی نماینده مقایسه کنید. اگر نسخه اصلاح‌شده کندتر است، گلوگاه را با تنظیم پشتیبانی‌شده، کاهش کار غیرضروری یا ظرفیت بررسی کنید؛ بازگشت بی‌برنامه به نسخه آسیب‌پذیر یا غیرفعال‌کردن اعتبارسنجی راه بهینه‌سازی نیست. کنترل موقت باید مالک، دامنه، موعد و مسیر patch داشته باشد.

## مثال حل‌شده مستقل از زبان

فرض آموزشی: سرویس رسید از `receipt-renderer` استفاده می‌کند و آن به `image-parser` وابسته است. advisory فرضی می‌گوید ورودی تصویری خاص در نسخه آسیب‌پذیر باعث مصرف حافظه زیاد می‌شود. نام‌ها و نسخه‌های زیر واقعی نیستند و توصیه نصب محسوب نمی‌شوند.

<div dir="ltr" align="left">

```text
release: receipts-2026-11-10
artifact: sha256:<digest-of-built-artifact>
dependency path:
  receipt-renderer 3.1.0 -> image-parser 4.2.1
proposed fix:
  supported renderer release resolving parser 4.2.2
verification:
  inspect resolved graph and final artifact
  compare output correctness, bounded inputs, memory and latency
deployment:
  staged rollout with error/resource signals and recovery plan
```

</div>

تغییر فقط فایل اصلی پروژه تضمین نمی‌کند نسخه transitive عوض شود؛ lockfile، خروجی build و artifact مستقر باید بررسی شوند. registry خصوصی/عمومی و نام بسته نیز مهم‌اند: دریافت بسته هم‌نام از منشأ اشتباه با ارتقای نسخه حل نمی‌شود. [OWASP زنجیره تأمین](https://cheatsheetseries.owasp.org/cheatsheets/Software_Supply_Chain_Security_Cheat_Sheet.html) منشأ، dependency و build را بخش‌های مرتبط اما متفاوت می‌بیند.

## آموزش گام‌به‌گام: از هشدار تا نسخهٔ اصلاح‌شده

برای خواندن نتیجهٔ اسکن، این اصطلاح‌ها را از هم جدا کنید:

| اصطلاح | معنی در این درس | پرسش عملی |
| --- | --- | --- |
| dependency مستقیم | برنامه آن را مستقیماً درخواست می‌کند | کدام قابلیت ما به آن وابسته است؟ |
| dependency غیرمستقیم یا transitive | dependency دیگری آن را وارد می‌کند | کدام مسیر در درخت وابستگی آن را آورده؟ |
| advisory/CVE | شناسه یا گزارش یک نقص شناخته‌شده | کدام نسخه و کدام شرایط استفاده متاثر است؟ |
| lockfile | تصمیم resolver درباره نسخه‌های مشخص | آیا build از همین فایل استفاده کرده است؟ |
| SBOM | فهرست اجزای یک artifact مشخص | آیا فهرست به digest همان خروجی وصل است؟ |
| artifact | خروجی قابل نصب/اجرا، مثل image یا بسته | آیا همین خروجی اصلاح‌شده deploy شد؟ |

چرخه را به‌ترتیب اجرا کنید: **۱)** نام و نسخهٔ دقیق را از هشدار بردارید؛ نام کتابخانه به‌تنهایی کافی نیست، چون چند نسخه یا چند مسیر ممکن است وجود داشته باشد. **۲)** dependency graph خروجی را بخوانید و وجود آن را در artifact تولیدی تایید کنید. **۳)** شرط اثر را با برنامه تطبیق دهید؛ مثلاً آیا parser آسیب‌پذیر با ورودی قابل دسترس از شبکه صدا زده می‌شود؟ نبود مسیر مستقیم خطر را خودکار صفر نمی‌کند؛ پیامد و امکان دسترسی را با هم بسنجید. **۴)** نسخهٔ اصلاح‌شده و پشتیبانی‌شده را انتخاب کنید. کنترل موقت باید مسیر در معرض را محدود، مالک و موعد داشته باشد. **۵)** ورودی‌های مرزی را با نسخهٔ قبل و بعد مقایسه کنید؛ صحت خروجی، خطای پردازش، حافظه و زمان را جدا بسنجید. **۶)** graph/SBOM، شناسهٔ build و digest استقرار را تطبیق دهید تا معلوم شود artifact اصلاح‌شده واقعاً فعال است.

در مثال بالا، اگر `receipt-renderer` به `image-parser 4.2.2` ارتقا یابد اما شاخهٔ `B` هنوز نسخهٔ `4.2.1` را وارد کند، یک مسیر قدیمی ممکن است باقی بماند. پاسخ را از روی حدس resolver تعیین نکنید: graph نهایی را بخوانید. اگر دو نسخه کنار هم هستند، مشخص کنید کدام قابلیت کدام نسخه را صدا می‌زند؛ اگر resolver یک نسخه برای هر دو شاخه انتخاب کرده، سازگاری API را هم بررسی کنید.

## تمرین و مشاهده مورد انتظار

روی کاغذ نمودار `App → A → Parser` و `App → B → Parser` بسازید. فقط A را ارتقا دهید، در حالی که B هنوز Parser قدیمی را نگه می‌دارد. انتظار: بسته به resolver، نسخه قدیمی ممکن است همچنان در artifact باقی بماند؛ «نسخه مستقیم تازه شد» مدرک بسته‌شدن finding نیست. برای release بعد، فهرست اجزا، مالک patch، زمان بازبینی و معیار مصرف منابع را بنویسید. اسکن واقعی یا نصب بسته لازم نیست.

**حل تمرین:** مسیرهای هر دو شاخه را از `App` تا `Parser` فهرست کنید و برای هر مسیر نسخهٔ حل‌شده و قابلیت استفاده‌کننده را ثبت کنید. اگر هر مسیر نسخهٔ آسیب‌پذیر را نشان دهد، finding باز است. اگر graph تمیز است، هنوز باید artifact را با digest استقرار و ورودی مرزی مرتبط تطبیق دهید. عبارت «فایل اصلی پروژه تغییر کرد» مدرک کافی برای بستن نیست.

## شاهد عمومی و حد شواهد

[اعلامیه رسمی Cisco درباره Log4j در دسامبر ۲۰۲۱](https://www.cisco.com/c/en/us/support/docs/csa/cisco-sa-apache-log4j-qRuKNEbd.html) بررسی محصولات و چند آسیب‌پذیری مرتبط، از جمله DoS، را مستند می‌کند. این شاهد اول‌شخص و تاریخی است؛ نسخه‌های patch آن زمان توصیه نسخه امروز نیستند. از این سند عدد کاهش latency یا ادعای رخداد در پروژه شما نتیجه نمی‌گیریم.

## شکست‌ها، سیگنال‌ها و چک‌لیست

image پایه فراموش‌شده، بسته transitively واردشده، artifact قدیمی پس از restart، پایان پشتیبانی و suppression بدون موعد از خطاهای رایج‌اند. شمار finding به‌تنهایی کیفیت نیست: سن finding مهم، زمان تا اصلاح، پوشش inventory و تعداد releaseهای با منشأ نامعلوم را هم ببینید. scanner و نصب وابستگی نیز با حداقل مجوز و حفاظت از secretها اجرا می‌شوند.

- [ ] inventory/SBOM به digest همان artifact قابل استقرار متصل است.
- [ ] dependency مستقیم، transitive، runtime و image پایه دیده شده‌اند.
- [ ] advisory از منبع معتبر با نسخه و شرایط مواجهه تطبیق دارد.
- [ ] pin/lockfile همراه برنامه update و پایش advisory است.
- [ ] patch مالک، موعد، بررسی صحت و بودجه کارایی دارد.
- [ ] کنترل موقت یا استثنا دلیل، دامنه و تاریخ انقضا دارد.
- [ ] استقرار artifact اصلاح‌شده و حذف نسخه قدیمی تأیید می‌شود.

## خودآزمایی

۱. آیا lockfile نشانه امن‌بودن dependency است؟

۲. چرا ارتقای A در نمودار تمرین ممکن است finding را نبندد؟

۳. آیا SBOM جای اسکن و بازبینی را می‌گیرد؟

۴. اگر patch مصرف CPU را بیشتر کرد، واکنش مناسب چیست؟

۵. چرا امضای artifact با امنیت کامل کد برابر نیست؟

۶. suppression بدون موعد چه مشکلی ایجاد می‌کند؟

### پاسخ‌نامه با دلیل

۱. خیر؛ نسخه resolveشده را تثبیت می‌کند، حتی اگر همان نسخه آسیب‌پذیر باشد.

۲. B ممکن است مسیر مستقل نسخه قدیمی را نگه دارد؛ خروجی resolver و artifact باید دیده شود.

۳. خیر؛ inventory برای تطبیق و بررسی لازم است، اما نبود نقص را اثبات نمی‌کند.

۴. علت را با حفظ اصلاح امنیتی اندازه‌گیری و تنظیم/ظرفیت را بررسی می‌کنیم؛ کنترل موقت هم برنامه و موعد دارد.

۵. امضا به اعتماد به منشأ/یکپارچگی کمک می‌کند؛ کد منشأ معتبر نیز می‌تواند نقص داشته باشد.

۶. پذیرش موقت خطر به فراموشی دائمی تبدیل می‌شود و امکان پیگیری مالک و اصلاح از بین می‌رود.
