# فهم زمینه و تحلیل ریسک

**زبان:** فارسی · [English](../../../../en/code-review/03-reviewer/01-context-risk/README.md)

> مسیر: [فصل ۳ — آماده‌سازی بازبین](../README.md) · [فهرست دوره](../../README.md)

## آموزش

قبل از خواندن جزءبه‌جزء diff، issue، نیازمندی، معیار پذیرش، design doc و شرح PR را ببین. سپس تغییرات غیرمستقیم را دنبال کن: callerها، مصرف‌کنندگان API، migration، cache، queue، log و config. سؤال اصلی این است که رفتار سیستم کجا و برای چه کسی عوض می‌شود.

ریسک را با احتمال، شدت، دامنهٔ اثر و برگشت‌پذیری بسنج. تغییر مجوز یا payment نیازمند دقت بیشتری از typo است. بااین‌حال تعداد خطوط به‌تنهایی سطح ریسک را نمی‌گوید. اگر فهم سیستم یا تخصص کافی نداری، سؤال مطرح کن و domain expert بیاور.

برای review هدفمند، از نیازمندی checklist کوتاه بساز. در صورت نیاز کد را محلی اجرا کن، اما شواهد آزمون را با revision و محیط مربوط بسنج. ناآگاهی را به‌صورت سؤال دقیق بیان‌کردن حرفه‌ای‌تر از حدس قطعی است.

## روند پیشنهادی

1. هدف و معیار پذیرش را از issue/شرح بخوان.
2. ورودی، خروجی و مصرف‌کننده را دنبال کن.
3. وابستگی، config و اثر داده را پیدا کن.
4. احتمال، شدت، blast radius و rollback را بسنج.
5. سطح review و تخصص لازم را تعیین کن.

## مثال کاربردی

یک شرط پنج‌خطی در endpoint را دنبال می‌کنی و می‌بینی bulk job از همان مسیر استفاده می‌کند، اما tenant آن از job context می‌آید نه HTTP request. زمینهٔ واقعی، تست‌هایی را که باید دیده شوند تغییر می‌دهد.

## خطاهای رایج

فقط از روی نام تابع نتیجه نگیر؛ کل سیستم را بی‌هدف بررسی نکن؛ بر مبنای ارشدیت تصمیم نگیر؛ ریسک خارج از تخصص را با حدس نپوشان.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** برای فهم هدف تغییر از کجا شروع می‌کنی؟

   1. نام branch
   2. شرح PR، issue و معیار پذیرش
   3. تعداد فایل
   4. کامنت آخر

**پاسخ:** 2 — نیازمندی چارچوب سنجش را تعیین می‌کند.

### پرسش 2

**سؤال:** blast radius به چه اشاره دارد؟

   1. اندازهٔ diff
   2. دامنهٔ سیستم/کاربران متأثر از شکست
   3. تعداد reviewer
   4. سرعت CI

**پاسخ:** 2 — اثر شکست مهم است.

### پرسش 3

**سؤال:** با تغییر مجوز در حوزهٔ ناآشنا چه باید کرد؟

   1. تست سبز را کافی دانست
   2. متخصص مناسب را وارد و ابهام را ثبت کرد
   3. بی‌چون‌وچرا approve کرد
   4. از نویسنده خواست approve کند

**پاسخ:** 2 — ریسک حساس به expertise مرتبط نیاز دارد.

### پرسش 4

**سؤال:** چه چیزی عمق review را تعیین می‌کند؟

   1. فقط خطوط
   2. حساسیت، شدت پیامد و برگشت‌پذیری
   3. سن نویسنده
   4. زمان روز

**پاسخ:** 2 — سطح بررسی باید متناسب با ریسک باشد.

## آموزش عمیق: از مسئله تا نقشهٔ اثر

### چرا diff به‌تنهایی کافی نیست؟

diff فقط آنچه عوض شده را نشان می‌دهد؛ نیازمندی، callerها، دادهٔ قدیمی، deploy هم‌زمان و رفتار سرویس‌های دیگر ممکن است بیرون قاب باشند. بازبین باید دو تصویر بسازد: **تصویر نیت** از issue، طرح و معیار پذیرش؛ و **تصویر اثر** از مسیر داده و مصرف‌کننده‌های کد. اگر این دو تصویر با هم جور نیستند، ابتدا سؤال بپرس، بعد دربارهٔ patch قضاوت کن.

### روش خواندن در دو گذر

**گذر اول، نقشه:** عنوان و شرح PR، issue، فایل‌های تغییرکرده، ساختار پوشه و تفاوت کلی را بخوان. دسته‌بندی کن: رفتار، config، dependency، schema، test، docs یا generated file. هدف آن است بفهمی تغییر یک موضوع است یا چند موضوع مخلوط.

**گذر دوم، مسیرها:** ورودی را دنبال کن تا تصمیم، ذخیره، خروجی و اثر بیرونی. برای endpoint: هویت از کجا می‌آید؟ داده از کدام tenant خوانده می‌شود؟ خطا چه پاسخی می‌دهد؟ برای migration: نسخهٔ قدیمی و جدید هم‌زمان چه می‌کنند؟ برای queue: retry، ترتیب، duplicate و dead-letter چه رفتاری دارند؟

یک خط تغییر ممکن است اثر بسیار دوری داشته باشد. تغییر در serialization می‌تواند cache قدیمی یا consumerهای دیگر را بشکند؛ نام جدید function این اثر را نشان نمی‌دهد.

### مدل سادهٔ اولویت ریسک

برای هر سناریو این پرسش‌ها را بپرس:

1. **احتمال:** چه شرایطی باید رخ دهد تا مشکل فعال شود؟
2. **شدت:** اگر رخ دهد، آیا داده، پول، امنیت یا دسترس‌پذیری آسیب می‌بیند؟
3. **دامنه:** یک کاربر، یک tenant یا کل سرویس متأثر است؟
4. **کشف:** آیا metric یا log پیش از کاربر نشان می‌دهد؟
5. **بازگشت:** flag، rollback یا اصلاح داده چقدر آسان است؟

این جدول امتیاز رسمی یا فرمول دقیق نیست؛ ابزاری برای گفت‌وگوی منظم است. دو ریسک با حاصل‌ضرب عددی یکسان ممکن است نیاز متفاوتی داشته باشند، چون امنیت داده و دسترس‌پذیری به یک روش مدیریت نمی‌شوند.

### مثال تشریحی

PR مقدار userId را از request body به query انتقال می‌دهد. ابتدا هدف را از issue پیدا کن: جلوگیری از دسترسی cross-tenant. سپس مسیر را دنبال کن: middleware هویت را از session می‌سازد یا شناسهٔ body را معتبر می‌داند؟ query تنها orderId را محدود می‌کند یا tenant فعلی را هم؟ تست منفی دو حساب و دو سفارش را می‌سازد. اگر فقط ظاهر query را ببینی، شاید تست موجود را بپذیری که هر دو شناسه را از یک fixture می‌گیرد و مرز جداسازی را هرگز نمی‌آزماید.

### تمرین

برای تغییر endpoint دانلود فایل، نقشه‌ای چهارمرحله‌ای بنویس: منبع شناسه، کنترل مجوز، محل فایل، پاسخ خطا. سپس دو مورد بیرون diff را نام ببر؛ مثلاً URL عمومی/امضاشده یا cache browser. پاسخ به مخزن وابسته است؛ اگر نمی‌توانی آن را از کد/مستند بخوانی، سؤال review بساز.

### تسلط یعنی بتوانی…

- نیازمندی را به مسیرهای کد و داده وصل کنی؛
- سناریوی failure و مصرف‌کنندهٔ غیرمستقیم را پیدا کنی؛
- احتمال را از شدت و دامنه جدا کنی؛
- معلوم/نامعلوم و فرض/شاهد را در کامنت جدا بنویسی.
