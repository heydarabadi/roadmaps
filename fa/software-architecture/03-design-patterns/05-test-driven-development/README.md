# توسعهٔ آزمون‌محور (TDD)

## ایدهٔ مرکزی

در TDD یک چرخهٔ کوتاه تکرار می‌شود: آزمون شکست‌خورده برای رفتار لازم، کمترین کد برای سبزشدن، سپس بازآرایی با حفظ رفتار. TDD طراحی را از راه بازخورد سریع شکل می‌دهد، اما جای آزمون یکپارچه‌سازی، قرارداد، امنیت، کارایی یا آزمون کاربر واقعی را نمی‌گیرد.

## چرخهٔ Red–Green–Refactor

۱. یک رفتار کوچک و قابل‌مشاهده انتخاب کن.  
۲. آزمونی بنویس که ابتدا شکست بخورد و دلیل شکست روشن باشد.  
۳. کمترین پیاده‌سازی را اضافه کن.  
۴. پس از سبزشدن، duplication و نام‌گذاری را اصلاح کن.  
۵. مجموعهٔ آزمون سریع و مستقل بماند.

آزمون باید از بیرون قابلیت قابل‌مشاهده را بررسی کند، نه اینکه به ساختار خصوصی کلاس بچسبد. آزمون‌هایی که بیش از حد implementation را mock می‌کنند، ممکن است پس از refactor بشکنند بی‌آنکه رفتار خراب شده باشد.

## از واحد تا تولید: لایه‌های آزمون

- **Unit:** یک قاعده یا component کوچک را سریع و مستقل می‌سنجد؛ معمولاً dependency بیرونی ندارد.
- **Integration:** اتصال واقعی بین دو جزء، مانند repository و پایگاه داده یا adapter و provider sandbox را می‌سنجد.
- **Contract:** توافق schema و رفتار میان producer و consumer را کنترل می‌کند، بدون اجرای کل سامانه.
- **End-to-end:** مسیر اصلی کاربر را از مرز بیرونی تا نتیجه بررسی می‌کند؛ تعدادش کم و سناریویش باارزش باشد تا نگهداری دشوار نشود.
- **Performance/resilience/security:** ویژگی‌هایی را می‌سنجد که unit test نمی‌تواند ثابت کند.

TDD به این معنی نیست که فقط unit test بنویسیم. مثلاً محاسبهٔ تخفیف با unit test خوب پوشش داده می‌شود؛ idempotency callback به integration با database و آزمون تکرار پیام نیاز دارد؛ latency checkout به load test نیاز دارد.

## یک دور کامل Red–Green–Refactor

**رفتار:** مشتری با کد تخفیف معتبر تا سقف ۲۰٪ تخفیف می‌گیرد، اما مبلغ از حداقل قیمت مجاز پایین‌تر نمی‌آید.  
**Red:** آزمونی برای تخفیف ۳۰٪ می‌نویسیم و ابتدا شکست آن را می‌بینیم.  
**Green:** حداقل منطق لازم برای cap تخفیف را پیاده می‌کنیم.  
**Refactor:** نام‌گذاری و مرز policy را روشن می‌کنیم و آزمون‌ها را دوباره اجرا می‌کنیم.  
**گسترش رفتار:** کوپن منقضی، currency نامعتبر، و دو کوپن ناسازگار را جداگانه تعریف می‌کنیم.

تست را به مثال قابل‌فهم business بدل کن: ورودی، شرط و نتیجه باید در نام تست یا arrange/act/assert خوانا باشد. اگر تست برای خوانده‌شدن به implementation خصوصی تکیه دارد، boundary را بررسی کن.

## مثال: محاسبهٔ هزینهٔ ارسال

ابتدا قاعده را با سه حالت مشخص کن: سفارش رایگان‌ارسال، سفارش زیر آستانه، و مقصد خارج از محدوده. بعد پیاده‌سازی خالص را بنویس؛ اتصال به سرویس نرخ‌دهی را در آزمون قراردادی یا integration جدا بسنج.

~~~text
test: مبلغ >= آستانه -> هزینه ارسال صفر
test: مبلغ کمتر از آستانه -> هزینه بر اساس منطقه
test: منطقه ناشناخته -> خطای دامنهٔ قابل‌فهم
~~~

## TDD و معماری

آزمون سریع روی منطق دامنه می‌تواند تغییر داخلی را ارزان کند. آزمون قرارداد میان سرویس‌ها کشف می‌کند که تغییر API مصرف‌کننده را نشکند. آزمون معماری می‌تواند وابستگی‌های نامجاز را کنترل کند. بااین‌حال، اگر boundary نامناسب باشد، تست هم آن را جادویی درست نمی‌کند؛ معماری نیاز به مشاهده و بازطراحی دارد.

## دام‌ها

- نوشتن تست برای هر getter و setter بدون ارزش رفتاری.
- ساختن abstraction صرفاً برای اینکه mocking ساده شود.
- پذیرش تستی که فقط با implementation خاص پاس می‌شود.
- داشتن فقط unit test و اعتماد بی‌پایه به اتصال واقعی.
- اجرای کند و flaky که تیم را به نادیده‌گرفتن تست سوق دهد.

## آزمون

۱. هدف مرحلهٔ Red چیست؟  
**پاسخ:** اثبات اینکه آزمون جدید رفتار موردنظر را می‌سنجد و در وضعیت فعلی شکست می‌خورد.

۲. چرا ابتدا کمترین پیاده‌سازی؟  
**پاسخ:** از ساخت قابلیت اضافی جلوگیری می‌کند و مسیر رفت‌وبرگشت کوتاه نگه می‌دارد.

۳. آزمون واحد و قرارداد چه تفاوتی دارند؟  
**پاسخ:** واحد منطق محدود را می‌سنجد؛ قرارداد سازگاری توافق میان provider و consumer را بررسی می‌کند.

۴. آیا TDD برای هر بخش مناسب است؟  
**پاسخ:** برای منطق قاعده‌مند معمولاً سودمند است؛ برای کشف UI یا فناوری ناآشنا، prototype و آزمایش هم لازم است.

## تمرین

برای تابع اعتبارسنجی کد تخفیف پنج آزمون رفتاری بنویس؛ یکی را به آزمون property-based یا جدول‌محور تبدیل کن و توضیح بده چرا boundary برای فهم منطق مهم است.

## پاسخ نمونهٔ تمرین

پنج آزمون کد تخفیف: قبل از شروع/پس از انقضا رد شود؛ تاریخ شروع مجاز پذیرفته شود؛ حداقل مبلغ دقیق پذیرفته و یک واحد زیر رد شود؛ استفادهٔ tenant دیگر مجاز نباشد؛ سقف مصرف هم‌زمان از حد نگذرد. Property نمونه: مبلغ نهایی هرگز از مبلغ پیش از تخفیف بیشتر و منفی نمی‌شود. جدول مرزی کمک می‌کند inclusive/exclusive بودن زمان و مبلغ به رفتار صریح تبدیل شود.
