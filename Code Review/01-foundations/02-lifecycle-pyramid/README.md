# چرخهٔ review و هرم تمرکز

**زبان:** فارسی · [English](../../en/01-foundations/02-lifecycle-pyramid/README.md)

> مسیر: [فصل ۱ — هدف، جریان و مدل ذهنی](../README.md) · [فهرست دوره](../../README.md)

## آموزش

چرخه از روشن‌شدن مسئله شروع می‌شود: نویسنده تغییر را آماده و خودبازبینی می‌کند؛ reviewer زمینه می‌گیرد؛ بحث، اصلاح و بازبینی مجدد انجام می‌شود؛ سپس merge، انتشار و پایش می‌آید. پرسیدن زودهنگام دربارهٔ طراحی می‌تواند از PR پرهزینه جلوگیری کند.

هرم Code Review پیشنهاد می‌کند کارهای مکانیکی مانند قالب‌بندی و lint خودکار شوند تا انسان روی تست، طراحی، رفتار پیاده‌سازی و معنای API تمرکز کند. API semantics و تغییر رفتاری به زمینه وابسته‌اند و هزینهٔ اصلاحشان پس از انتشار بالاست. ترتیب بررسی باید از هدف و اثر به جزئیات سبک برسد.

این هرم قانون یا سنجهٔ قطعی نیست. تعداد خطوط به‌تنهایی ریسک را نشان نمی‌دهد؛ تغییر کوچک در مجوز یا API ممکن است اثر وسیع داشته باشد. عمق review را از حساسیت داده، blast radius، برگشت‌پذیری و مخاطبان تغییر تعیین کن.

## روند پیشنهادی

1. شرح و نیازمندی را بخوان.
2. فایل‌های تغییرکرده و کد اطراف را مرور کن.
3. رفتار و قراردادها را پیش از جزئیات سبک بررسی کن.
4. تست، امنیت، کارایی و خطاها را بسنج.
5. پس از گفت‌وگو، اصلاح، تایید و پایش را پیگیری کن.

## مثال کاربردی

تغییر regex از lint می‌گذرد، اما همچنان ممکن است با ورودی بدترین حالت CPU را اشباع کند. همین‌جا review انسانی باید performance و rollout را بسنجد.

## خطاهای رایج

از اولین خط و بدون هدف شروع نکن؛ CI را تضمین صحت ندان؛ همهٔ PRها را با عمق ثابت بررسی نکن؛ ابزار را برای تحلیل business logic به‌کار نگیر.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** کدام بررسی مکانیکی مناسب CI است؟

   1. سازگاری قرارداد API
   2. قالب‌بندی استاندارد
   3. درک نیاز کاربر
   4. انتخاب trade-off

**پاسخ:** 2 — قواعد مکانیکی تکرارپذیرند.

### پرسش 2

**سؤال:** چرا API semantics به توجه انسانی نیاز دارد؟

   1. قواعد syntax است
   2. اثر به مصرف‌کنندگان و قراردادهای سیستم وابسته است
   3. همیشه lint می‌سنجد
   4. بی‌اهمیت است

**پاسخ:** 2 — معنای تغییر در context سیستم مشخص می‌شود.

### پرسش 3

**سؤال:** از چه چیز عمق بررسی را تعیین کنیم؟

   1. فقط تعداد خطوط
   2. حساسیت، blast radius و برگشت‌پذیری
   3. رتبهٔ نویسنده
   4. تعداد کامنت

**پاسخ:** 2 — ریسک عملی معیار مفیدتری است.

### پرسش 4

**سؤال:** پس از merge برای تغییر پراثر چه لازم است؟

   1. هیچ
   2. پایش و کنترل rollout
   3. فقط تعداد approvals
   4. حذف تست‌ها

**پاسخ:** 2 — رفتار تولید باید با انتظار مقایسه شود.

## آموزش عمیق: از هدف تا پایش

### چرخهٔ کامل یک تغییر

1. **زمینه‌سازی:** مسئله، کاربر و معیار پذیرش روشن می‌شود. طرح یا API مبهم را می‌توان پیش از نوشتن کد با همکار مرور کرد.
2. **آماده‌سازی نویسنده:** تغییر متمرکز می‌ماند، تست و مستندات لازم اضافه می‌شود و نویسنده diff نهایی را می‌خواند.
3. **درخواست review:** عنوان، شرح، لینک مسئله، نتیجهٔ تست، ریسک و سؤال کنار diff می‌آیند.
4. **فهم بازبین:** ابتدا نیازمندی و نمای کلی فایل‌ها، سپس مسیرهای رفتاری و موارد پرریسک بررسی می‌شوند.
5. **گفت‌وگو و اصلاح:** بازبین یافته را با اثر توضیح می‌دهد؛ نویسنده تغییر می‌دهد یا با شواهد پاسخ می‌دهد.
6. **بازبینی دوباره و تصمیم:** آخرین revision و نتیجهٔ pipeline بررسی می‌شود؛ blocker، سؤال و پیشنهاد اختیاری از هم جدا می‌شوند.
7. **ادغام، انتشار و یادگیری:** تغییر طبق policy ادغام می‌شود؛ برای تغییر پراثر rollout و metric پایش می‌شود و رخدادها به اقدام پیشگیرانه برمی‌گردند.

چرخه کاملاً خطی نیست: نویسنده ممکن است در مرحلهٔ اول سؤال بپرسد، CI ممکن است هنگام بررسی مشکل نشان دهد، یا پایش پس از انتشار فرضی را رد کند. هر مرحله پرسش خودش را دارد و پاسخ یک مرحله جای بقیه را نمی‌گیرد.

### هرم تمرکز را درست بخوان

در پایین هرم، lint، قالب‌بندی و قواعد یکنواخت‌اند: سریع و تکرارپذیر، پس مناسب اتوماسیون. بالاتر، تست‌های رفتاری قرار می‌گیرند؛ طراحی و semantics به زمینه نیاز دارند؛ قرارداد API و اثر معماری ممکن است مصرف‌کنندگان ناشناخته داشته باشند و اصلاح بعد از انتشار هزینه‌بر باشد. بنابراین وقت انسان را صرف چیزی کن که ابزار به‌تنهایی نمی‌تواند بفهمد.

هرم قانون یا امتیاز عددی برای merge نیست. ریسک از زمینه می‌آید. اگر lint مخزن درست پیکربندی نشده، باید همان نقص فرایند گزارش شود. تغییر style در صدها فایل شاید رفتار کمی عوض کند، اما نویز زیاد می‌تواند review را دشوار کند. از طرف دیگر، تغییر کوتاه مجوز دسترسی ممکن است شدیداً پرریسک باشد.

### مثال مرحله‌به‌مرحله

تیمی endpoint حذف حساب می‌سازد. ابتدا از محصول می‌پرسد حذف فوری است یا دورهٔ بازیابی دارد؛ سپس شرح PR، تست authorization و سیاست نگه‌داری داده را می‌آورد؛ بازبین مسیر مجوز، خطای سرویس و retry را می‌سنجد؛ CI آزمون و secret scan را اجرا می‌کند؛ پس از اصلاح، reviewer آخرین diff را می‌خواند؛ در rollout نرخ حذف و خطا پایش می‌شود. اگر فقط «approve و merge» را review بنامیم، سیاست محصول و پایش را از دست می‌دهیم.

### تمرین

یک تغییر کوچک در مخزن خودت انتخاب کن و هفت مرحلهٔ چرخه را برایش پر کن. کنار هر مرحله شاهدش را بنویس: issue، فایل تغییر، تست، comment، pipeline، approval یا dashboard. اگر شاهدی نداری، آن را از حافظه نساز؛ بنویس «نامعلوم» و تصمیم بگیر آیا ریسک تغییر به آن نیاز دارد.

### تسلط یعنی بتوانی…

- چرخهٔ review را از انتشار جدا کنی؛
- بگویی چه چیزی خودکار می‌شود و چه چیزی قضاوت انسانی می‌خواهد؛
- سطح بررسی را بر اساس پیامد و برگشت‌پذیری تغییر تنظیم کنی؛
- نبود یک مرحله را با شواهد توضیح دهی.
