# Redis در برابر SQL و NoSQL

> English edition: [Redis vs. SQL and NoSQL](../../../../en/redis/01-foundations/choose-datastore/README.md)

> سطح پیشنهادی: مقدماتی تا میانی · زمان: ۳۰ تا ۶۰ دقیقه

## هدف یادگیری

موارد مناسب و نامناسب Redis را با معیارهای سامانه توضیح بدهی.

## درس

SQL معمولاً برای دادهٔ ماندگار، constraint، join، query تحلیلی و تراکنش دامنه‌ای مناسب است. Redis برای دسترسی سریع به کلید/ساختار، شمارنده، cache و session کاربرد دارد. این برچسب‌ها مطلق نیستند: Redis می‌تواند persist کند، اما مدل query و هزینهٔ RAM با دیتابیس رابطه‌ای فرق دارد.

پیش از انتخاب بپرس: منبع حقیقت کجاست؟ latency هدف؟ حجم و نرخ دسترسی؟ اگر Redis قطع شود چه می‌شود؟ چه consistency و RPO می‌خواهی؟ آیا query با کلید/ساختار حل می‌شود؟ هزینهٔ replication و RAM چقدر است؟

## مقایسهٔ مسئله‌محور

| سؤال | Redis معمولاً مناسب است وقتی… | دیتابیس رابطه‌ای معمولاً مناسب‌تر است وقتی… |
|---|---|---|
| مدل پرس‌وجو چیست؟ | key lookup، counter، membership یا rank پرتکرار است. | join، گزارش چندجدولی، constraint و queryهای متنوع لازم است. |
| داده چقدر زنده است؟ | حذف/انقضا، latency پایین یا state کوتاه‌عمر ارزش دارد. | داده باید مرجع پایدار و حسابرسی‌پذیر باشد. |
| چه trade-offی می‌پذیری؟ | RAM، replica و احتمال stale cache کنترل شده‌اند. | می‌خواهی constraint/transaction مرکزی پایگاه داده مسئول صحت باشد. |
| اگر سرویس قطع شود؟ | fallback یا recovery برای کاربرد تعریف شده است. | از دسترس‌پذیری و durability دیتابیس مرجع استفاده می‌کنی. |

این جدول حکم انتخاب قطعی نیست. نوع workload، نسخه، سرویس مدیریت‌شده و مهارت تیم می‌تواند نتیجه را عوض کند. Redis هم persistence دارد؛ SQL هم می‌تواند cache داشته باشد. تفاوت اصلی، مدل دسترسی و تضمین‌هایی است که باید خودت طراحی کنی.

## سه تمرین انتخاب

### A. کد یک‌بارمصرف تأیید تلفن

کد کوتاه‌عمر، کلید lookup روشن و TTL کوتاه دارد؛ Redis می‌تواند گزینهٔ مناسبی باشد. با این حال، شمار دفعات تلاش، مصرف یک‌باره، حدس‌زدن کد، پاک‌شدن پس از موفقیت و rate limit را هم طراحی کن. فقط نگهداری کد در Redis جلوی حمله را نمی‌گیرد.

### B. پرداخت و دفتر حساب

ثبت تراکنش مالی، قید یکتایی و تاریخچهٔ قابل‌حسابرسی را معمولاً در پایگاه دادهٔ اصلی نگه دار. Redis می‌تواند دادهٔ نمایشی یا cache کم‌خطر را ارائه کند، اما پاسخ سریع cache به‌تنهایی اثبات پرداخت نیست. تصمیم قطعی باید از منبع authoritative خوانده شود.

### C. تعداد بازدید صفحه

اگر شمارش تقریبی کافی است و تعداد unique لازم داری، HyperLogLog گزینه است. اگر تعداد دقیق لازم است، هزینهٔ نوشتن و model exact را بسنج. این دو نوع خروجی را در گزارش با برچسب «تخمینی» یا «دقیق» مشخص کن.

## الگوی کنارهم‌زیستی

یک معماری رایج این است: PostgreSQL دادهٔ اصلی را نگه می‌دارد؛ برنامه ابتدا Redis را برای پاسخ پرتکرار می‌پرسد؛ در miss به PostgreSQL می‌رود و نتیجه را cache می‌کند؛ تغییر داده در PostgreSQL بعداً cache key را invalidate می‌کند. این معماری دو نسخه از داده دارد، بنابراین خطر stale data و خرابی invalidation را اضافه می‌کند. TTL یک حد زمانی برای stale بودن می‌دهد، ولی consistency فوری تضمین نمی‌کند.

## چک‌لیست تصمیم

1. query اصلی را دقیق بنویس، مثل «شناسهٔ محصول را بده و خلاصه را بخوان».
2. freshness مجاز را تعیین کن: چند ثانیه یا دقیقه stale data قابل‌قبول است؟
3. منبع حقیقت را مشخص کن و بگو Redis حذف‌شدنی است یا نه.
4. peak key count، اندازهٔ average key/value و رشد ماهانه را برآورد کن.
5. هزینهٔ miss و اثر outage را محاسبه کن؛ مسیر fallback هم باید محدودشده باشد.
6. consistency، TTL، invalidation و عملیات چندکلیدی را مدل کن.
7. با payload و الگوی کلید واقعی benchmark بگیر و p95/p99 را ثبت کن؛ نتیجهٔ یک SET کوچک پیش‌بینی کل سیستم نیست.

**پاسخ تمرین:** کد کوتاه‌عمر، cache محصول و ranking نیازهای متفاوت‌اند؛ انتخاب Redis برای اولی و دومی به امنیت/freshness و برای سومی به exactness بستگی دارد. پرداخت مرجع را صرفاً برای سریع‌شدن به cache منتقل نمی‌کنیم.

## مثال و آزمایش

قیمت محصول را در PostgreSQL منبع اصلی فرض کن و صفحهٔ پربازدید را در Redis cache کن. بنویس تغییر قیمت چطور cache را invalid می‌کند و هنگام outage چه fallbackی داری.

## تجربهٔ واقعی منتشرشده

## خطاهای رایج

مقایسه با یک benchmark دستور یا برچسب NoSQL؛ نادیده گرفتن consistency، query، دوام و هزینهٔ نگهداری.

## تمرین

1. مثال را در Redis محلی اجرا و خروجی را با زبان خودت توضیح بده.
2. دو حالت شکست یا edge case برای این الگو بنویس.
3. برای workload خودت حجم داده، نرخ خواندن/نوشتن، TTL یا retention و رفتار زمان outage را مشخص کن.
4. یک معیار بگذار: p95 latency، hit rate، RAM، lag، pending count یا زمان restore.
