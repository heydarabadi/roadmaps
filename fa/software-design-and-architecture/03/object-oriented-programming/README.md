- شیءگرایی روشی برای حفاظت از وضعیت و قواعد و تعریف همکاری از راه قراردادهاست. از مفاهیم OOP برای بیان رفتار واقعی دامنه استفاده کن، نه برای تبدیل هر داده به یک کلاس.

- برای یک تصمیم، مثال، مبادله و معیار بازبینی بنویسی.

## ایدهٔ مرکزی فصل

شیءگرایی روشی برای حفاظت از وضعیت و قواعد و تعریف همکاری از راه قراردادهاست. از مفاهیم OOP برای بیان رفتار واقعی دامنه استفاده کن، نه برای تبدیل هر داده به یک کلاس. این فصل را همراه با فصل‌های مجاور بخوان: طراحی شیء و اصول، کیفیت کد را درون جزء بهتر می‌کنند؛ سبک و الگوی معماری رابطهٔ چند جزء و مرزهای استقرار را شکل می‌دهند؛ الگوهای سازمانی اغلب درون این مرزها اجرا می‌شوند.

## نقشهٔ مفهومی و درس‌های مستقل

- [برنامه‌نویسی شیءگرا — Object Oriented Programming](topics/object-oriented-programming/README.md) — در OOP داده و رفتار مرتبط در شیءها کنار هم قرار می‌گیرند و پیام/رابط قرارداد همکاری است؛ شیء خوب صرفاً ظرف داده نیست و invariantهای خود را حفظ می‌کند.
- [اصول پایهٔ شیءگرایی — Primary OOP Principles](topics/primary-principles/README.md) — چهار مفهوم encapsulation، abstraction، inheritance و polymorphism ابزارهایی برای محافظت از وضعیت و تنوع رفتارند؛ استفاده‌شان باید نیاز مدل را حل کند.
- [وراثت — Inheritance](topics/inheritance/README.md) — وراثت رفتار و نوع را از نوع پایه می‌گستراند و رابطهٔ «نوعی از» را بیان می‌کند؛ زیرنوع باید در جای پایه رفتار درست داشته باشد.
- [چندریختی — Polymorphism](topics/polymorphism/README.md) — چندریختی امکان فراخوانی یک قرارداد مشترک با پیاده‌سازی‌های متفاوت را می‌دهد و شرط‌های نوع‌محور را کاهش می‌دهد.
- [انتزاع — Abstraction](topics/abstraction/README.md) — انتزاع جزئیات را پشت مفهومی نگه می‌دارد که مصرف‌کننده برای کارش نیاز دارد؛ مرز خوب از زبان و قواعد مسئله می‌آید.
- [کپسوله‌سازی — Encapsulation](topics/encapsulation/README.md) — کپسوله‌سازی داده و قواعد را پشت عملیات کنترل‌شده نگه می‌دارد تا وضعیت نامعتبر از بیرون ساخته نشود.
- [ویژگی‌های پارادایم شیءگرا — OOP Paradigm Features](topics/paradigm-features/README.md) — کلاس‌های abstract/concrete، محدودهٔ دسترسی و interface ابزارهای تعریف قرارداد، reuse و کنترل سطح افشا هستند.
- [کلاس انتزاعی — Abstract Classes](topics/abstract-classes/README.md) — کلاس انتزاعی بخشی از قرارداد یا پیاده‌سازی مشترک را فراهم می‌کند ولی مستقیم نمونه‌سازی نمی‌شود؛ در زبان‌های مختلف محدودیت‌های متفاوت دارد.
- [کلاس عینی — Concrete Classes](topics/concrete-classes/README.md) — کلاس عینی قرارداد لازم را پیاده می‌کند و می‌تواند نمونه‌سازی شود؛ آن باید رفتار کامل و معتبر برای کاربرد هدف داشته باشد.
- [محدوده و سطح دسترسی — Scope and Visibility](topics/scope-visibility/README.md) — scope محل اعتبار نام در کد را تعیین می‌کند و visibility مشخص می‌کند کدام کد بیرونی به عضو دسترسی دارد؛ سطح دسترسی بخشی از API و مرز تغییر است.
- [رابط‌ها — Interfaces](topics/interfaces/README.md) — interface قرارداد رفتاری بین مصرف‌کننده و پیاده‌سازی است؛ رابط پایدار امکان تعویض adapter و تست boundary را می‌دهد.
- [طراحی مدل‌محور — Model-Driven Design](topics/model-driven-design/README.md) — طراحی مدل‌محور واژگان و قواعد کلیدی حوزه را در مدل اجرایی منعکس می‌کند و گفت‌وگوی متخصص دامنه و توسعه‌دهنده را به کد وصل می‌سازد.
- [مدل دامنه — Domain Models](topics/domain-models/README.md) — مدل دامنه مفاهیم، رفتار، روابط و محدودیت‌های مسئله را در زبان نرم‌افزار بازنمایی می‌کند؛ باید با قواعد واقعی کسب‌وکار هماهنگ بماند.
- [مدل بی‌رفتار (Anemic) — Anemic Models](topics/anemic-models/README.md) — مدل بی‌رفتار داده را نگه می‌دارد و منطق در سرویس‌های بیرونی می‌ماند؛ گاهی برای CRUD ساده مناسب و برای قواعد پیچیده پراکنده‌ساز است.
- [زبان دامنه — Domain Language](topics/domain-language/README.md) — زبان دامنه واژه‌های مشترک و دقیق میان متخصص کسب‌وکار و تیم فنی است؛ ابهام را در نام‌ها، APIها و آزمون‌ها کم می‌کند.
- [گونه‌های کلاس — Class Variants](topics/class-variants/README.md) — گونه‌های کلاس روش‌هایی برای مدل‌کردن حالت‌ها و تفاوت رفتارند: subclass، composition، sum type یا strategy؛ انتخاب باید حالت نامعتبر را کم کند.
- [معماری لایه‌ای در مدل‌سازی — Layered Architectures in Model Design](topics/layered-architectures-oop/README.md) — لایه‌ها مسئولیت UI، هماهنگی کاربرد، دامنه و زیرساخت را جدا می‌کنند؛ مدل دامنه نباید ناخواسته به دیتابیس و کنترلر وابسته شود.

## توضیح یکپارچهٔ فصل

برای هر تصمیم سه سؤال را جواب بده: **چه چیزی تغییر می‌کند؟ چه کسی مالک قاعده/داده است؟ و کدام ویژگی کیفی اهمیت دارد؟** سپس سطح راه‌حل را انتخاب کن: تابع و نوع، مرز ماژول، سرویس، صف یا مدل داده. این ترتیب کمک می‌کند نام الگو جای شناخت مسئله را نگیرد.

توضیح‌ها و مثال‌های هر مفهوم در فایل مستقل بالا آمده‌اند. برای مقایسه، نمونهٔ زیر عمداً یک مسئلهٔ مشترک را با چند سطح طراحی نشان می‌دهد: در فروشگاه، قانون لغو سفارش یک قاعدهٔ دامنه‌ای است؛ جداکردن آن از کنترلر مرز درون‌برنامه‌ای می‌سازد؛ اگر تیم و چرخهٔ انتشار مستقل شوند شاید component کافی باشد؛ اگر داده و بار و مالکیت مستقل باشند جداسازی سرویس بررسی می‌شود. هر مرحله نیازمند شاهد تازه است و مرحلهٔ بعدی را خودکار توجیه نمی‌کند.

## مطالعهٔ موردی و تجربهٔ صنعتی مستند

در یک سامانهٔ فروش، قواعد سفارش، بازپرداخت و ارسال با مدل دامنه و قراردادهای مشخص پیاده می‌شوند. Shopify در نوشته‌های فنی خود دربارهٔ سامان‌دهی کد براساس مفاهیم کسب‌وکار مثل سفارش، ارسال و پرداخت توضیح می‌دهد؛ این نمونه نشان می‌دهد مدل شیء باید با دامنه و مرزهای واقعی هماهنگ باشد.

- [Shopify؛ سازمان‌دهی اجزای کد براساس حوزه‌های واقعی](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity) — گزارش/منبع اصلی یا مرجع مرتبط با تجربهٔ مستند.

**روش خواندن مطالعهٔ موردی:** مسئلهٔ اولیه، محدودیت workload، گزینه‌های ردشده، هزینهٔ ارتباط و پیامد بعدی را استخراج کن. عدد یا تصمیم گزارش‌شده را به کل شرکت و همهٔ سامانه‌ها تعمیم نده.

## نمونهٔ کد یا قرارداد

```python
class Order:
    def __init__(self, lines):
        self._lines = list(lines)

    def total(self):
        return sum(line.amount for line in self._lines)
```

دادهٔ خطوط و رفتاری که از آن مشتق می‌شود در یک abstraction قرار گرفته است؛ قواعد کامل وضعیت سفارش باید به متدهای دامنه‌ای افزوده شوند.

## نمونهٔ تصمیم معماری

| پرسش | نمونهٔ پاسخ |
| --- | --- |
| نیاز یا فشار چیست؟ | تغییر مکرر قواعد سفارش و نیاز به بررسی مستقل آن‌ها. |
| ساده‌ترین گزینه چیست؟ | یک ماژول منسجم در برنامهٔ موجود با قرارداد داخلی و آزمون. |
| چه چیزی نتیجه را عوض می‌کند؟ | نیاز واقعی به استقرار مستقل، مقیاس متفاوت، امنیت یا مالکیت تیمی مستقل. |
| چگونه می‌سنجیم؟ | زمان تغییر، اثر انتشار، خطاهای مرزی، سربار ارتباط/عملیات و نیازهای محصول. |

## دام‌ها و سوءبرداشت‌ها

- الگو را از روی ترند انتخاب‌کردن، پیش از شناخت فشار طراحی.
- یک ساختار را همه‌جا تحمیل‌کردن؛ حتی وقتی پیچیدگی دامنه و چرخهٔ تغییر متفاوت است.
- نمونهٔ واقعی یک سازمان را بدون workload، تیم، هزینه و تاریخچه کپی‌کردن.
- بهینه‌سازی برای شاخص ساده‌ای مثل تعداد کلاس، سرویس یا خط کد به‌جای هدف محصول.

## کوییز جامع فصل با پاسخ‌نامه

1. مفهوم اصلی این فصل را چگونه برای یک سامانهٔ سفارش توضیح می‌دهی؟ از یکی از موضوع‌ها نام ببر و مسئله‌اش را بیان کن.
   - پاسخ/معیار ارزیابی: شیءگرایی روشی برای حفاظت از وضعیت و قواعد و تعریف همکاری از راه قراردادهاست. از مفاهیم OOP برای بیان رفتار واقعی دامنه استفاده کن، نه برای تبدیل هر داده به یک کلاس.
2. در سناریویی که شیء `Order` می‌تواند فقط از وضعیت مجاز به وضعیت بعدی برود و محاسبهٔ جمع را بر اساس خطوط سفارش انجام دهد. چه trade-offی را پیش از انتخاب می‌سنجی؟
   - پاسخ/معیار ارزیابی: در OOP داده و رفتار مرتبط در شیءها کنار هم قرار می‌گیرند و پیام/رابط قرارداد همکاری است؛ شیء خوب صرفاً ظرف داده نیست و invariantهای خود را حفظ می‌کند. OOP می‌تواند وابستگی، وراثت عمیق و پراکندگی منطق بسازد؛ استفادهٔ درست به مرز و همکاری ساده نیاز دارد.
3. یک مورد از این فصل را انتخاب کن که ممکن است over-engineering شود؛ چه نشانه‌ای باعث می‌شود آن را حذف یا ساده کنی؟
   - پاسخ/معیار ارزیابی: وقتی abstraction یا عملیات/نگهداری از نیاز مشاهده‌شده بیشتر می‌شود، ساده‌سازی را انتخاب کن؛ YAGNI و دادهٔ واقعی را راهنما بگیر.
4. برای یکی از تصمیم‌های فصل، چه آزمون یا سنجه‌ای نشان می‌دهد طراحی بهبود یافته است?
   - پاسخ/معیار ارزیابی: آزمون‌های رفتار/قرارداد، زمان تغییر، نرخ خطا، latency یا هزینه را با توجه به هدف انتخاب کن و قبل/بعد را مقایسه کن.
5. کدام بخش سناریوی مستند فصل را می‌توان به مسئلهٔ خودت تعمیم داد و کدام بخش وابسته به زمینهٔ همان شرکت است?
   - پاسخ/معیار ارزیابی: اصل مسئله و trade-off را تعمیم بده؛ فناوری، بار و ساختار سازمانی شرکت را بدون شواهد کپی نکن.
6. رابط یا مرزی را طراحی کن که تغییر یک مسئولیت را از بقیه جدا کند؛ توضیح بده این مرز کدام نوع coupling را کم می‌کند.
   - پاسخ/معیار ارزیابی: لایه‌ها مسئولیت UI، هماهنگی کاربرد، دامنه و زیرساخت را جدا می‌کنند؛ مدل دامنه نباید ناخواسته به دیتابیس و کنترلر وابسته شود.

## تمرین عملی

یک سیستم کوچک فروش، رزرو یا صدور فاکتور انتخاب کن. برای سه نیازمندی پرتغییر، نقشهٔ مسئولیت‌ها را بکش؛ یک قرارداد و آزمون بنویس؛ سپس توضیح بده چرا فعلاً از مرز انتخاب‌شده استفاده می‌کنی و چه نشانه‌ای باعث می‌شود آن را تغییر بدهی. تمرین را با [قالب ADR](https://adr.github.io/) ثبت کن.
