# بازگشت

> نسخهٔ انگلیسی: [English version](readme.en.md)

> مسیر: [فصل ۸ — الگوهای حل مسئله](../readme.md) · پیش‌نیاز پیشنهادی: فصل ۱ و مبانی برنامه‌نویسی

## پیش‌نیازها و نقشهٔ ذهنی

تابع، پارامتر و stack. ابتدا مفهوم را به‌عنوان یک قرارداد ببین، سپس نمایش حافظه و عملیات را دنبال کن. هدف حفظ‌کردن نام نیست؛ باید بتوانی برای یک ورودی کوچک، state را بعد از هر گام بنویسی.

## ایده از پایه

تابع بازگشتی مسئله را با نسخه‌ای کوچک‌تر از خودش حل می‌کند. هر تعریف درست باید base case و گامی داشته باشد که به base نزدیک شود؛ وگرنه بازگشت بی‌نهایت رخ می‌دهد.

## مدل، قرارداد و ناوردا

هر call فریم جدا با آرگومان‌ها و متغیرهای خودش روی call stack دارد. بازگشت خطی عمق n، فضای stack برابر O(n) می‌گیرد. درخت بازگشت، تعداد callها و عمق را از هم جدا نشان می‌دهد.

ناوردا (invariant) جمله‌ای است که در تمام مراحل الگوریتم باید درست بماند. نوشتن آن پیش از کدنویسی، هم به اثبات درستی کمک می‌کند و هم خطاهای مرزی را آشکار می‌سازد.

## الگوریتم یا عملیات گام‌به‌گام

طراحی را در چهار پرسش بنویس: تابع چه چیزی برمی‌گرداند؟ base case چیست؟ فرض می‌کنیم تابع برای زیرمسئله درست کار می‌کند؛ چطور از پاسخ آن جواب فعلی را می‌سازیم؟ اندازهٔ زیرمسئله چطور کم می‌شود؟ مثال factorial: n≤1→1، وگرنه n×fact(n−1).

در پیاده‌سازی واقعی، قرارداد ورودی/خروجی را دقیق تعریف کن: رفتار ورودی تهی، مقدار تکراری، عنصر پیدا‌نشده و ظرفیت تمام‌شده باید روشن باشد.

## اجرای حل‌شده با ردگیری

sum([4,2,7]): sum(index)=A[index]+sum(index+1)؛ پایه index==n جواب 0. باز شدن: 4+sum(1)→4+2+sum(2)→4+2+7+sum(3)→13. برگشت stack نتیجه را جمع می‌کند.

برای تمرین، جدولی با ستون‌های «گام»، «اندیس/اشاره‌گر»، «بخش فعال»، «تغییر state» و «دلیل» بساز. این روش به‌خصوص برای الگوریتم‌های درجا و تقسیم‌و‌غلبه جلوی پرش ذهنی را می‌گیرد.

## چرا درست است؟

فرض استقرایی: فراخوانی با ورودی کوچک‌تر پاسخ تعریف‌شدهٔ همان زیرمسئله را برمی‌گرداند. base case درست است؛ ترکیب پاسخ‌های فرعی مطابق recurrence خروجی صحیح را می‌دهد. termination نیز نیازمند اندازهٔ صحیح و کاهنده است.

اثبات معمولاً سه بخش دارد: (۱) آغاز—ناوردا پیش از نخستین گام درست است؛ (۲) نگهداری—هر گام آن را حفظ می‌کند؛ (۳) پایان—شرط توقف همراه invariant جواب موردنیاز را نتیجه می‌دهد. اگر یکی از این سه بخش نامشخص است، هنوز درک الگوریتم کامل نشده است.

## تحلیل زمان و حافظه

زمان/فضا از recurrence می‌آید. factorial یک call در هر n، زمان/stack O(n)؛ binary search زمان O(log n)، stack O(log n). tail-call optimization به زبان/compiler وابسته است و نباید بی‌مدرک فرض شود.

در Big-O ورودی را تعریف کن (مثلاً n تعداد عناصر)، نوع حالت را نام ببر (بهترین/میانگین/بدترین)، و فضای کمکی را از حافظهٔ خود ورودی جدا کن. مرتبهٔ رشد زمان واقعی بر حسب ثانیه نیست؛ cache، تخصیص حافظه و ثابت‌های پیاده‌سازی هم اثر دارند.

## کاربرد واقعی و انتخاب مناسب

درخت‌ها، divide-and-conquer، parserها، پیمایش ساختارهای تو‌در‌تو و backtracking. برای دادهٔ عمیق نامطمئن نسخهٔ iterative می‌تواند از محدودیت stack جلوگیری کند.

پیش از انتخاب بپرس: چه عملیاتی پرتکرارند؟ آیا ترتیب مهم است؟ دادهٔ ورودی چه اندازه است؟ آیا محدودیت حافظه، latency بدترین‌حالت یا thread-safety داریم؟ ساختار خوب برای workload نامناسب می‌تواند انتخاب بدی باشد.

## خطاهای رایج و edge caseها

base case فراموش، آرگومان بدون پیشرفت، محاسبهٔ تکراری (مثل Fibonacci ساده)، stack overflow، و کپی ناخواستهٔ آرایه در هر فراخوانی. عمق و تعداد call را جدا تحلیل کن.

حالت‌های مرزی را جداگانه بررسی کن: ورودی خالی، یک عضو، همهٔ اعضا برابر، هدف غایب، حداقل/حداکثر مقدار و اندازهٔ بزرگ. سرریز عدد صحیح در محاسبهٔ اندیس/ظرفیت نیز بسته به زبان مهم است.

## تمرین‌های مرحله‌ای

۱) factorial و جمع آرایه را با recurrence و base بنویس. ۲) Fibonacci بازگشتی ساده چندبار fib(2) حساب می‌کند؟ ۳) traversal درخت را با stack صریح بازنویسی کن.

برای هر تمرین، اول پاسخ ساده و درست بنویس، بعد پیچیدگی را حساب کن، سپس edge case اضافه کن. تمرین را با دست‌کم یک ورودی کوچک ردگیری کن و خروجی را با انتظار مستقل مقایسه کن.

## آزمون جامع با پاسخ تشریحی

ابتدا پاسخ‌ها را نخوان؛ جواب را با استدلال بنویس، سپس توضیح را مقایسه کن.

1. **پرسش:** چه دو جزء لازم‌اند؟
   **پاسخ تشریحی:** base case و recursive stepی که به base نزدیک شود.
2. **پرسش:** عمق call stack چه می‌سنجد؟
   **پاسخ تشریحی:** تعداد فراخوانی‌های هم‌زمان، نه کل تعداد فراخوانی‌ها.
3. **پرسش:** Fibonacci ساده کند است چرا؟
   **پاسخ تشریحی:** زیرمسئله‌ها را بارها دوباره حل می‌کند.
4. **پرسش:** tail recursion حتماً بهینه می‌شود؟
   **پاسخ تشریحی:** نه؛ وابسته به زبان/runtime/compiler است.
5. **پرسش:** برای ورودی عمیق چه گزینه‌ای هست؟
   **پاسخ تشریحی:** نسخهٔ iterative با stack صریح.

## راهنمای بازگویی از حافظه

بدون نگاه به متن، ایده، پیش‌شرط، invariant، یک ردگیری واقعی، پیچیدگی، edge case و یک کاربرد را در چند دقیقه روی کاغذ توضیح بده. اگر فقط pseudocode را حفظی می‌نویسی اما دلیل درستی یا محدودیت‌ها را نمی‌دانی، یک بار دیگر بخش‌های invariant و خطاها را مرور کن.
