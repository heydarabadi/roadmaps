## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

یک ماژول باید حول یک actor یا یک دلیل منسجم برای تغییر سازمان یابد؛ منظور «فقط یک کار» به معنای محدود نیست.

## مثال کاربردی

قواعد گزارش‌گیری مدیر فروش را از قالب‌بندی PDF جدا کن اگر این دو توسط نیازهای متفاوت تغییر می‌کنند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «اصول طراحی» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** تقسیم بسیار ریز وابستگی و هماهنگی را زیاد می‌کند.
- **بازبینی:** تعداد متدهای کلاس یا فعل نام آن را جای تحلیل actor و تغییر نگذار.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: یک ماژول باید حول یک actor یا یک دلیل منسجم برای تغییر سازمان یابد؛ منظور «فقط یک کار» به معنای محدود نیست.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: قواعد گزارش‌گیری مدیر فروش را از قالب‌بندی PDF جدا کن اگر این دو توسط نیازهای متفاوت تغییر می‌کنند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: تقسیم بسیار ریز وابستگی و هماهنگی را زیاد می‌کند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: تعداد متدهای کلاس یا فعل نام آن را جای تحلیل actor و تغییر نگذار.

## آموزش تکمیلی مستقل

#### S — Single Responsibility

یک ماژول باید حول یک مسئولیت منسجم یا یک گروهی که نیازمندی را تغییر می‌دهد جمع شود. منظور «هر کلاس فقط یک متد» یا «یک کار کوچک» نیست. اگر تغییر مالیات و تغییر قالب چاپ فاکتور معمولاً توسط دو actor مستقل درخواست می‌شود، احتمالاً دو مسئولیت داریم.

روش: تغییرهای اخیر را بررسی کن؛ نیازهای مستقلی که یک ماژول را دست می‌زنند پیدا کن؛ مرز را فقط وقتی جدا کن که coupling واقعی یا دشواری آزمون وجود دارد. ماژول‌های ریز با نام‌های عمومی می‌توانند cohesive بودن را بدتر کنند.

## نمونهٔ کد مرحله‌ای

مسئولیت واحد یعنی یک ماژول حول یک actor یا دلیل منسجم برای تغییر باشد، نه اینکه فقط یک کار انجام دهد. تغییرهای واقعی را ببین و مرز را با cohesion و مالکیت تصمیم بسنج؛ خردکردن بیش‌ازحد هم هزینه دارد.
**تمرین با پاسخ:** محاسبهٔ مبلغ و چاپ PDF را جدا کن اگر گروه‌های متفاوت قواعدشان را تغییر می‌دهند؛ اگر همیشه با هم تغییر می‌کنند، جداسازی شاید سودی نداشته باشد.

در این طرح C#، نوع‌های پشتیبان کوتاه شده‌اند تا انتخاب طراحی روشن بماند.

~~~csharp
public sealed class InvoiceCalculator
{
    public Money Calculate(Invoice invoice) => /* business rule */ invoice.Subtotal;
}

public sealed class InvoicePdfRenderer
{
    public byte[] Render(Invoice invoice) => /* presentation */ RenderPdf(invoice);
}
~~~

## خلاصه

اصل مسئولیت واحد (SRP) را برای حل مسئلهٔ مشخص به کار ببر، trade-off آن را ثبت کن و با یک آزمون/معیار قابل مشاهده بررسی کن که آیا مرز طراحی واقعاً بهتر شده است.
