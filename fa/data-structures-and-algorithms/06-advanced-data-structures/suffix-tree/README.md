# درخت پسوندی

> نسخهٔ انگلیسی: [English version](../../../../en/data-structures-and-algorithms/06-advanced-data-structures/suffix-tree/README.md)

> مسیر: [فصل ۶ — ساختمان‌های دادهٔ پیشرفته](../README.md) · پیش‌نیاز پیشنهادی: فصل ۱ و مبانی برنامه‌نویسی

## پیش‌نیازها و نقشهٔ ذهنی

رشته، trie، suffix array و edgeهای فشرده. ابتدا مفهوم را به‌عنوان یک قرارداد ببین، سپس نمایش حافظه و عملیات را دنبال کن. هدف حفظ‌کردن نام نیست؛ باید بتوانی برای یک ورودی کوچک، state را بعد از هر گام بنویسی.

## ایده از پایه

Suffix tree trie فشردهٔ تمام پسوندهای متن است: مسیرهایی که تنها یک فرزند دارند روی یک edge ادغام می‌شوند و edge با بازه‌ای از متن برچسب می‌گیرد تا حافظهٔ رشته تکراری مصرف نشود.

## مدل، قرارداد و ناوردا

با افزودن sentinel یکتا، هر پسوند در برگ جدا پایان می‌یابد. جست‌وجوی الگوی P مسیر edgeها را با نمادهای P تطبیق می‌دهد؛ وجود کامل P وسط یک edge نیز موفق است، لازم نیست node دقیقاً پایان آن باشد.

ناوردا (invariant) جمله‌ای است که در تمام مراحل الگوریتم باید درست بماند. نوشتن آن پیش از کدنویسی، هم به اثبات درستی کمک می‌کند و هم خطاهای مرزی را آشکار می‌سازد.

## الگوریتم یا عملیات گام‌به‌گام

ساخت naive با درج همهٔ پسوندها می‌تواند O(n²) یا بدتر شود. الگوریتم Ukkonen با suffix link و ساخت آنلاین در زمان خطی تحت مدل alphabet/ساختار مناسب کار می‌کند، اما پیاده‌سازی ظریف است. برای یادگیری، اول ساخت دستی رشتهٔ کوتاه و فشرده‌کردن trie را انجام بده.

در پیاده‌سازی واقعی، قرارداد ورودی/خروجی را دقیق تعریف کن: رفتار ورودی تهی، مقدار تکراری، عنصر پیدا‌نشده و ظرفیت تمام‌شده باید روشن باشد.

## اجرای حل‌شده با ردگیری

متن `banana$` پسوندها `$`, `a$`, `ana$`, `anana$`, `banana$`, `na$`, `nana$` را دارد. دو مسیر مشترک `ana` با edgeهای حاوی indexهای متن به شاخه‌های متفاوت و برگ‌های متناظر می‌رسند. pattern=`nan` با طی prefix مناسب وجودش مشخص می‌شود.

برای تمرین، جدولی با ستون‌های «گام»، «اندیس/اشاره‌گر»، «بخش فعال»، «تغییر state» و «دلیل» بساز. این روش به‌خصوص برای الگوریتم‌های درجا و تقسیم‌و‌غلبه جلوی پرش ذهنی را می‌گیرد.

## چرا درست است؟

هر suffix دقیقاً یک برگ دارد و concatenation برچسب‌های مسیر ریشه تا آن برگ همان suffix است. edge labelها بازهٔ متن اصلی‌اند، پس نیازی به کپی رشته نداریم.

اثبات معمولاً سه بخش دارد: (۱) آغاز—ناوردا پیش از نخستین گام درست است؛ (۲) نگهداری—هر گام آن را حفظ می‌کند؛ (۳) پایان—شرط توقف همراه invariant جواب موردنیاز را نتیجه می‌دهد. اگر یکی از این سه بخش نامشخص است، هنوز درک الگوریتم کامل نشده است.

## تحلیل زمان و حافظه

ساخت Ukkonen O(n) زمان و فضای O(n) تحت فرض‌های مدل؛ search یک الگوی طول m معمولاً O(m) به‌علاوهٔ خروجی رخدادها. پیاده‌سازی و ثابت حافظه پیچیده‌تر از suffix array و trie است.

در Big-O ورودی را تعریف کن (مثلاً n تعداد عناصر)، نوع حالت را نام ببر (بهترین/میانگین/بدترین)، و فضای کمکی را از حافظهٔ خود ورودی جدا کن. مرتبهٔ رشد زمان واقعی بر حسب ثانیه نیست؛ cache، تخصیص حافظه و ثابت‌های پیاده‌سازی هم اثر دارند.

## کاربرد واقعی و انتخاب مناسب

index ثابت متن برای substring search، ژنوم، زیست‌اطلاعات و تحلیل تکرار. در عمل suffix array/FM-index به‌دلیل حافظهٔ کمتر گاهی ترجیح داده می‌شود.

پیش از انتخاب بپرس: چه عملیاتی پرتکرارند؟ آیا ترتیب مهم است؟ دادهٔ ورودی چه اندازه است؟ آیا محدودیت حافظه، latency بدترین‌حالت یا thread-safety داریم؟ ساختار خوب برای workload نامناسب می‌تواند انتخاب بدی باشد.

## خطاهای رایج و edge caseها

بدون sentinel، برخی suffixها prefix suffix دیگرند و برگ‌های مجزا/پایان آشکار نمی‌شود. edge label را کپی نکن. بحث O(n) به فرض alphabet و ساختار childها وابسته است.

حالت‌های مرزی را جداگانه بررسی کن: ورودی خالی، یک عضو، همهٔ اعضا برابر، هدف غایب، حداقل/حداکثر مقدار و اندازهٔ بزرگ. سرریز عدد صحیح در محاسبهٔ اندیس/ظرفیت نیز بسته به زبان مهم است.

## تمرین‌های مرحله‌ای

۱) suffix trie رشتهٔ `aba$` بساز و unary paths را فشرده کن. ۲) محل پایان pattern وسط edge را بررسی کن. ۳) trade-off suffix tree و suffix array را در memory/search بنویس.

برای هر تمرین، اول پاسخ ساده و درست بنویس، بعد پیچیدگی را حساب کن، سپس edge case اضافه کن. تمرین را با دست‌کم یک ورودی کوچک ردگیری کن و خروجی را با انتظار مستقل مقایسه کن.

## آزمون جامع با پاسخ تشریحی

ابتدا پاسخ‌ها را نخوان؛ جواب را با استدلال بنویس، سپس توضیح را مقایسه کن.

1. **پرسش:** چه چیزی فشرده می‌شود؟
   **پاسخ تشریحی:** مسیرهای تک‌فرزند trie suffixها.
2. **پرسش:** edge label چگونه ذخیره می‌شود؟
   **پاسخ تشریحی:** به‌صورت بازه‌ای از متن اصلی.
3. **پرسش:** چرا sentinel؟
   **پاسخ تشریحی:** هر suffix پایان آشکار و برگ مستقل داشته باشد.
4. **پرسش:** ساخت Ukkonen؟
   **پاسخ تشریحی:** O(n) با فرض‌های مناسب، اما پیاده‌سازی پیچیده.
5. **پرسش:** جایگزین کم‌حافظه‌تر؟
   **پاسخ تشریحی:** Suffix array همراه LCP یا FM-index.
