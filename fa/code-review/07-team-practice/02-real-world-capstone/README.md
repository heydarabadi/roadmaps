# تجربه‌های واقعی و کارگاه پایانی

**زبان:** فارسی · [English](../../../../en/code-review/07-team-practice/02-real-world-capstone/README.md)

> مسیر: [فصل ۷ — تیم، تجربه و تمرین](../README.md) · [فهرست دوره](../../README.md)

## آموزش

منابع صنعتی را در زمینه بخوان. Google، GitLab و Microsoft راهنمای فرایند خودشان را منتشر کرده‌اند؛ تجربهٔ مفیدند نه قانون جهان‌شمول. پژوهش code review هم به نمونه‌های خاص تعلق دارد؛ همبستگی را علت قطعی ندان.

Cloudflare در رخداد ۲ ژوئیهٔ ۲۰۱۹ نوشت regex در WAF مصرف CPU را شدیداً بالا برد و قطعی ایجاد شد. درس قابل انتقال: worst-case performance، تست، rollout و دفاع چندلایه را بررسی کن؛ حادثه را صرفاً به «review ضعیف» نسبت نده. GitHub در رخداد اکتبر ۲۰۱۸ زنجیرهٔ رویدادهای عملیاتی و فرایند بازیابی را مستند کرد؛ کنترل تغییر، observability و recovery نیز مهم‌اند.

پس از rollout موفق، نتیجه و یادگیری را با تیم به اشتراک بگذار و از مشارکت‌های مفید قدردانی کن؛ این کار دانش تیمی و کیفیت review را تقویت می‌کند.

کارگاه: این تابع فرضی گذرواژه را log می‌کند. ریسک secret، race، validation و پاسخ email تکراری را پیدا کن. snippet کامل نیست؛ دربارهٔ hashing و قرارداد محصول سؤال بپرس. بنویس یک blocker، یک سؤال و یک پیشنهاد اختیاری، سپس تست موردنیاز را مشخص کن.

## روند پیشنهادی

1. منبع اول‌دست و علت اعلام‌شده را جدا کن.
2. از تجربه یک کنترل عملی استخراج کن.
3. در snippet مسیر داده و دسترسی را trace کن.
4. finding قطعی را از سؤال نیازمند زمینه جدا کن.
5. comment را با شدت، اثر و تست همراه کن.

## مثال کاربردی

<pre dir="ltr"><code>async function register(email, password) {
  logger.info("register", { email, password });
  const user = await users.findByEmail(email);
  if (!user) await users.insert({ email, password });
  return { ok: true };
}</code></pre>

نمونهٔ blocker: «این log گذرواژهٔ خام را ذخیره می‌کند؛ secret را حذف کنیم و logهای موجود را طبق policy incident بررسی کنیم.» پرسش: «آیا پاسخ email تکراری باید یکسان باشد؟» تست: ثبت هم‌زمان دو درخواست یک email و invariant یکتایی.

## خطاهای رایج

snippet ناقص را کد production کامل ندان؛ hashing در لایهٔ نامشهود را قطعی فرض نکن؛ علت incident را فراتر از منبع تعمیم نده؛ شخص را به‌جای سیستم مقصر نکن.

## چک‌لیست

- [ ] هدف و انتظار کاربر را می‌فهمم.
- [ ] یافته را با اثر یا شاهد مشخص می‌کنم.
- [ ] ریسک مرتبط را بررسی می‌کنم.
- [ ] الزام، پیشنهاد، سؤال و ترجیح را جدا می‌کنم.
- [ ] محدودیت شواهد را پنهان نمی‌کنم.

## آزمون

### پرسش 1

**سؤال:** ریسک روشن snippet چیست؟

   1. نام تابع
   2. ارسال password به logger
   3. ترتیب فایل
   4. نام branch

**پاسخ:** 2 — کد آشکارا password را وارد log می‌کند.

### پرسش 2

**سؤال:** کدام ادعا از snippet به‌تنهایی ثابت نیست؟

   1. password به logger می‌رود
   2. رفتار duplicate روشن نیست
   3. دو درخواست هم‌زمان ممکن است race کنند
   4. رمز در DB حتماً خام ذخیره می‌شود

**پاسخ:** 4 — ممکن است لایهٔ دیگری hashing انجام دهد؛ زمینه لازم است.

### پرسش 3

**سؤال:** از Cloudflare 2019 چه درس قابل دفاعی می‌گیریم؟

   1. هر regex را حذف کنیم
   2. worst-case، تست و rollout را چندلایه بررسی کنیم
   3. حادثه فقط از review بود
   4. reviewerهای بیشتر همه‌چیز را حل می‌کنند

**پاسخ:** 2 — این نتیجه با گزارش رسمی سازگار است و علت را ساده‌سازی نمی‌کند.

### پرسش 4

**سؤال:** کامنت مؤثر کدام است؟

   1. این افتضاح است
   2. اشاره به secret، پیامد و درخواست مشخص برای حذف/پیشگیری
   3. بهترش کن
   4. سکوت

**پاسخ:** 2 — شفاف، محترمانه و قابل‌اقدام است.

## آموزش عمیق: پروندهٔ واقعی را دقیق و بی‌اغراق بخوان

### پروندهٔ ۱: Cloudflare، ۲ ژوئیهٔ ۲۰۱۹

گزارش رسمی Cloudflare می‌گوید یک regex در WAF باعث جهش مصرف CPU و اختلال گسترده شد؛ شرکت حدود ۲۷ دقیقه اختلال جهانی را گزارش کرد و بعداً جزئیات فنی و تغییرهای پیشگیرانه را منتشر کرد. نکتهٔ آموزشی این نیست که «بازبین باید regex را حذف می‌کرد». گزارش رخداد زنجیره‌ای از طراحی rule، ویژگی اجرای regex، تست/انتشار و روش مهار را بررسی می‌کند.

از این واقعه چهار سؤال برای review استخراج کن:

1. ورودی بدترین حالت برای regex یا parser بررسی شده؟
2. تست performance دارد یا فقط درستی تطبیق را می‌سنجد؟
3. rule در چه دامنه‌ای فعال می‌شود و آیا rollout تدریجی/خاموش‌کردن دارد؟
4. اگر dashboard یا ابزار مدیریت هم وابسته به همان سرویس باشد، مسیر پاسخ حادثه چیست؟

این پرسش‌ها اقدام‌های مهندسی هستند؛ علت اصلی و فرایند دقیق را فقط مطابق گزارش Cloudflare نقل کن.

### پروندهٔ ۲: GitHub، اکتبر ۲۰۱۸

تحلیل رسمی GitHub یک جدایی/اختلال شبکه در زمان کار برنامه‌ریزی‌شده را به زنجیره‌ای از رویدادهای دیتابیس و recovery پیوند می‌دهد. گزارش دربارهٔ حفظ صحت داده، بازیابی و کنترل تغییر توضیح می‌دهد. این پرونده هم نمونهٔ «یک PR بد» نیست؛ نشان می‌دهد ایمنی سیستم به هم‌زمانی عملیات، تشخیص، تصمیم‌های بازیابی و معماری داده وابسته است.

سؤال‌های قابل‌انتقال:

- آیا تغییر عملیاتی و deploy هم‌زمان روی دیتابیس با حالت failover بررسی شده؟
- آیا عملیات تکرارشونده و failover رفتارهای جداگانه دارد؟
- آیا تیم برای توقف تغییر، جلوگیری از write بیشتر و بازیابی داده ابزار و اختیار روشن دارد؟
- آیا پس از incident، یادگیری به runbook و کنترل سیستم برگشته است؟

### پرونده را با این قالب تحلیل کن

| بخش | چیزی که می‌نویسی |
|---|---|
| مشاهدهٔ مستند | رویداد/اثر که منبع رسمی می‌گوید |
| علت اعلام‌شده | فقط علت‌هایی که گزارش مستقیماً بیان کرده |
| حد نامعلوم | آنچه منبع نمی‌گوید یا نمی‌توان از آن نتیجه گرفت |
| درس مهندسی | پرسش یا کنترل پیشنهادی برای سیستم خودمان |
| اقدام | تست، guardrail، rollout یا تمرین پاسخ حادثه با owner |

از رابطهٔ «پس از رخداد» به‌تنهایی علت نساز؛ postmortem عمومی لزوماً تمام اطلاعات داخلی شرکت را منتشر نمی‌کند.

### کارگاه کامل: بازبینی ثبت‌نام

کد فرضی زیر را بخوان. این نمونه عمداً ناقص است؛ فقط چیزهایی را قطعی بدان که در همین snippet دیده می‌شود:

<pre dir="ltr"><code>async function register(email, password) {
  logger.info("register", { email, password });
  const user = await users.findByEmail(email);
  if (!user) await users.insert({ email, password });
  return { ok: true };
}</code></pre>

#### گام ۱: هدف و قرارداد را بپرس

آیا endpoint برای کاربر جدید حساب می‌سازد؟ پاسخ duplicate باید چه باشد؟ آیا وجود یک email باید برای درخواست‌کننده قابل‌تشخیص باشد؟ سیاست محصول و امنیت می‌توانند پاسخ را عوض کنند؛ از خود کد حدس نزن.

#### گام ۲: یافته‌های قطعی را جدا کن

- **قطعی در snippet:** شیء شامل password به logger داده شده است؛ اگر logger مقدارها را ثبت کند، credential افشا می‌شود. باید حذف و مسیر log موجود طبق سیاست incident بررسی شود.
- **نیازمند زمینه:** کد password را به users.insert می‌دهد، اما ممکن است repository آن را hash کند. قبل از ادعای ذخیرهٔ خام، implementation یا contract آن را بخوان.
- **ریسک محتمل:** دو درخواست هم‌زمان می‌توانند هر دو email را خالی ببینند. قید unique، transaction یا منطق repository را بررسی کن.
- **سؤال محصول:** پاسخ email تکراری یکسان باشد تا وجود حساب افشا نشود، یا خطای صریح لازم است؟
- **موارد دیگری برای بررسی:** اعتبارسنجی email، rate limit، خطاهای database، reset flow، حذف داده در log و تست‌های مربوط.

#### گام ۳: commentها را بنویس

**Blocker نمونه:** «این log، password را به logger می‌دهد. لطفاً credential را از log حذف کن و بررسی کن logهای ثبت‌شده چه دسترسی و retentionی دارند؛ همچنین test/guardrail بگذار تا secretهای مشابه ثبت نشوند.»  
**سؤال:** «برای email تکراری پاسخ عمومی یکسان می‌خواهیم یا وجود حساب باید اعلام شود؟ این تصمیم روی enumeration و UX اثر دارد.»  
**پیشنهاد:** «اگر الگوی این سرویس اجازه می‌دهد، اعتبارسنجی ورودی را در یک مسیر مشترک متمرکز کنیم تا endpointهای دیگر نیز همان قرارداد را داشته باشند.»

#### گام ۴: آزمون‌های پیشنهادی

1. log ثبت‌شده شامل password یا token نباشد.
2. دو ثبت هم‌زمان برای یک email فقط یک حساب بسازد.
3. خطای DB پاسخ کنترل‌شده و log بی‌راز تولید کند.
4. پاسخ duplicate دقیقاً با policy تعیین‌شده سازگار باشد.
5. رمز عبور در مسیر ذخیره‌سازی با سیاست سیستم hash شود؛ جزئیات الگوریتم را از استاندارد تیم بگیر، cryptography اختصاصی نساز.

#### گام ۵: نمره‌دهی به review

یک review خوب password logging را blocker می‌داند؛ دربارهٔ hashing تا دیدن repository ادعای قطعی نمی‌کند؛ duplicate race را با شواهد یا تست دنبال می‌کند؛ پاسخ duplicate را به policy محصول می‌سپارد؛ و preference دربارهٔ شکل validation را suggestion می‌نویسد. کیفیت review تعداد ایرادهای فرضی نیست، بلکه دقتِ تفکیکِ شاهد، فرض، ریسک و سؤال است.

### تمرین مستقل

یک PR عمومی کوچک در مخزنی که زبانش را می‌فهمی انتخاب کن. شرح، diff و تست را بخوان. سه مورد ثبت کن: یک مسئلهٔ رفتاریِ قابل‌بازتولید، یک سؤال واقعی دربارهٔ زمینه، و یک پیشنهاد غیرمسدودکننده. سپس reviewهای قبلی مخزن را ببین و مقایسه کن آیا policy نانوشته‌ای وجود دارد. برای نخستین مشارکت، ابتدا قوانین مشارکت همان پروژه را بخوان.
