# ۴.۲ — تابع‌ها، چند خروجی، variadic و closure

## ۱) تابع چیست و چه چیزی را پنهان می‌کند؟

تابع یک نام برای یک عملیات مشخص است: ورودی می‌گیرد، کاری انجام می‌دهد و ممکن است نتیجه برگرداند. هدف فقط کوتاه‌کردن کد تکراری نیست؛ تابع باید یک قرارداد قابل‌فهم بسازد. اگر نام تابع <code>ParsePort</code> باشد، خواننده انتظار دارد متن را اعتبارسنجی و به عدد تبدیل کند، نه اینکه شبکه باز کند یا متغیر global را تغییر دهد.

تابع سطح package با <code>func</code> تعریف می‌شود. نوع هر پارامتر بخشی از قرارداد است. در گروهی از پارامترهای هم‌نوع، نام‌ها را می‌توان کنار هم نوشت.

</div>

~~~go
func add(a, b int) int {
	return a + b
}

func main() {
	total := add(7, 5)
	fmt.Println(total)
}
~~~

<div dir="rtl">

این نمونهٔ کامل باید در فایل <code>main.go</code> با import از <code>fmt</code> قرار بگیرد. تابع <code>add</code> دو <code>int</code> می‌گیرد و یک <code>int</code> پس می‌دهد. نوع خروجی پس از فهرست پارامترها می‌آید. در تابعی که خروجی غیرخالی دارد، هر مسیر عادی اجرا باید به <code>return</code> برسد؛ خطای «missing return» نشانهٔ آن است که کامپایلر نمی‌تواند خروجی را در یک مسیر ثابت کند.

## ۲) آرگومان با value کپی می‌شود

Go آرگومان را با مقدارش به تابع می‌دهد؛ خود متغیر caller به تابع منتقل نمی‌شود. این را call by value می‌گویند. اگر مقدار یک عدد باشد، تابع نسخهٔ عدد را می‌گیرد؛ تغییر نسخه، متغیر caller را عوض نمی‌کند.

</div>

~~~go
func incrementCopy(n int) {
	n++
}

func main() {
	value := 10
	incrementCopy(value)
	fmt.Println(value) // 10
}
~~~

<div dir="rtl">

اما value ممکن است چیزی باشد که به حافظهٔ دیگری اشاره می‌کند: pointer، slice، map، channel یا function. کپی‌کردن چنین مقداری فقط descriptor یا آدرس را کپی می‌کند؛ هر دو طرف هنوز می‌توانند به دادهٔ مشترک برسند. به همین دلیل «همه‌چیز در Go کپی می‌شود» به معنی «تابع هرگز دادهٔ caller را تغییر نمی‌دهد» نیست.

</div>

~~~go
func changeFirst(values []int) {
	if len(values) > 0 {
		values[0] = 99
	}
}

func main() {
	numbers := []int{1, 2, 3}
	changeFirst(numbers)
	fmt.Println(numbers) // [99 2 3]
}
~~~

<div dir="rtl">

تابع یک کپی از header مربوط به slice را می‌گیرد، اما header کپی‌شده به همان backing array اشاره می‌کند؛ نوشتن روی خانهٔ موجود دیده می‌شود. اگر داخل تابع append کنی، ممکن است backing array جدید ساخته شود؛ آن وقت تغییر header تابع لزوماً طول slice caller را تغییر نمی‌دهد. اگر تابع باید طول جدید را به caller برگرداند، slice جدید را return کن یا pointer به خود slice را فقط با دلیل روشن به کار ببر.

این قراردادها را در API صریح کن: آیا تابع ورودی را mutate می‌کند؟ آیا داده را نگه می‌دارد یا فقط در زمان فراخوانی استفاده می‌کند؟ آیا نتیجه مستقل است یا به حافظهٔ ورودی alias دارد؟

## ۳) چند خروجی و الگوی value, error

یک تابع می‌تواند چند مقدار برگرداند. الگوی معمول عملیات شکست‌پذیر این است که نتیجه و خطا را با هم برگرداند: <code>(value, error)</code>. caller باید خطا را بررسی کند؛ نباید فرض کند مقدار در خطا معتبر است.

</div>

~~~go
package main

import (
	"errors"
	"fmt"
	"strconv"
)

func parsePort(text string) (int, error) {
	port, err := strconv.Atoi(text)
	if err != nil {
		return 0, fmt.Errorf("تبدیل پورت %q: %w", text, err)
	}
	if port < 1 || port > 65535 {
		return 0, fmt.Errorf("پورت باید بین 1 و 65535 باشد: %d", port)
	}
	return port, nil
}

func main() {
	port, err := parsePort("8080")
	if err != nil {
		fmt.Println("خطا:", err)
		return
	}
	fmt.Println("port =", port)
}
~~~

<div dir="rtl">

در نمونه:

1. <code>strconv.Atoi</code> تبدیل متن به عدد را انجام می‌دهد.
2. خطای تبدیل با <code>%w</code> wrap می‌شود تا زنجیرهٔ خطا حفظ شود.
3. محدودهٔ پورت جداگانه اعتبارسنجی می‌شود؛ تبدیل موفق به‌تنهایی یعنی ورودی از نظر برنامه معتبر است.
4. در موفقیت، خطا <code>nil</code> است.
5. caller قبل از استفاده از پورت خطا را می‌سنجد.

برای ساختن خطا از <code>errors.New</code> یا <code>fmt.Errorf</code> استفاده کن. اگر caller باید نوع یا هویت خطا را تشخیص دهد، error wrapping را با <code>%w</code> نگه‌دار و در سمت مصرف از <code>errors.Is</code> یا <code>errors.As</code> کمک بگیر. متن خطا را برای اپراتور و لاگ مفید بنویس، ولی secret، token یا دادهٔ حساس را داخلش نگذار.

## ۴) خروجی‌های چندتایی دیگر: ok و نتیجهٔ محاسبه

چند خروجی فقط برای خطا نیستند. گاهی مقدار همراه با وضعیت وجود یا موفقیت برمی‌گردد. map با <code>value, ok</code> چنین الگویی دارد؛ تابع هم می‌تواند همین قرارداد را بیان کند.

</div>

~~~go
func lookupScore(scores map[string]int, name string) (int, bool) {
	score, ok := scores[name]
	return score, ok
}
~~~

<div dir="rtl">

بهتر است از خروجی‌های زیاد و مبهم دوری کنی. تابعی با شش مقدار خروجی caller را وادار می‌کند ترتیب را حفظ کند و هر خروجی را به خاطر بسپارد. اگر نتیجه چند مفهوم دارد، یک struct نام‌دار برگردان.

## ۵) پارامتر variadic

پارامتر variadic با سه نقطه پیش از نوع نوشته می‌شود و درون تابع مانند slice همان نوع استفاده می‌شود. این پارامتر باید آخرین پارامتر باشد. تابع می‌تواند با صفر، یک یا چند آرگومان مستقیم فراخوانی شود.

</div>

~~~go
func sum(values ...int) int {
	total := 0
	for _, value := range values {
		total += value
	}
	return total
}

func main() {
	fmt.Println(sum())          // 0
	fmt.Println(sum(2, 3, 5))   // 10

	numbers := []int{4, 6, 8}
	fmt.Println(sum(numbers...)) // slice را باز می‌کند
}
~~~

<div dir="rtl">

هنگام پاس‌دادن یک slice موجود، <code>values...</code> لازم است. خود variadic ورودی در تابع slice است. اگر تابع آن را نگه‌داری نکند، خواندنش ساده است؛ اگر ذخیره یا mutate کند، aliasing و مالکیت backing array را در قرارداد توضیح بده. پارامتر variadic برای APIهایی مثل <code>fmt.Println</code> مناسب است، اما نباید ورودی‌های زیادی را در یک فهرست نامحدود و نامستند پنهان کند.

## ۶) تابع، مقدار است

نوع تابع را می‌توان به‌عنوان نوع متغیر نوشت. بنابراین می‌توان تابع را به تابع دیگری داد، از تابع برگرداند و در متغیر نگه داشت. این قابلیت برای callback، مرتب‌سازی سفارشی، middleware و سیاست‌های قابل‌تعویض کاربرد دارد.

</div>

~~~go
func apply(value int, operation func(int) int) int {
	return operation(value)
}

func main() {
	double := func(n int) int {
		return n * 2
	}
	fmt.Println(apply(7, double)) // 14
}
~~~

<div dir="rtl">

تابع anonymous نام مستقل ندارد و می‌تواند همان‌جا تعریف شود. وقتی رفتار کوتاه و محلی است، خوانایی بالا می‌رود؛ اگر بدنه طولانی شد یا نام مفهومی دارد، تابع نام‌دار جدا بساز. نوع تابع بخشی از قرارداد است: در مثال، callback باید یک <code>int</code> بگیرد و یک <code>int</code> بدهد.

## ۷) closure یعنی تابع به محیط lexical دسترسی دارد

Closure تابعی است که علاوه بر بدنه، به متغیرهای scope بیرونی خود دسترسی دارد. این دسترسی به متغیر است، نه عکس ثابت آن در لحظهٔ تعریف. هر بار فراخوانی closure می‌تواند همان متغیر captureشده را بخواند یا تغییر دهد.

</div>

~~~go
func makeCounter() func() int {
	count := 0

	return func() int {
		count++
		return count
	}
}

func main() {
	next := makeCounter()
	fmt.Println(next()) // 1
	fmt.Println(next()) // 2

	another := makeCounter()
	fmt.Println(another()) // 1
}
~~~

<div dir="rtl">

متغیر <code>count</code> بعد از بازگشت <code>makeCounter</code> هم زنده می‌ماند، چون تابع برگشتی هنوز به آن نیاز دارد. این رفتار را escape analysis و مدیریت حافظهٔ Go پشتیبانی می‌کند؛ لازم نیست خودت دستی حافظه آزاد کنی. هر بار <code>makeCounter</code> یک محیط مستقل می‌سازد.

### closure و loop

وقتی closure را در حلقه راه‌اندازی می‌کنی، از خودت بپرس: آیا callback باید مقدار همین دور را ببیند یا متغیر مشترک را در زمان اجرا؟ از Go 1.22 به بعد، متغیری که در سرآیند loop با <code>:=</code> تعریف شده، برای هر iteration مجزا است؛ این رفتار به go directive ماژول وابسته است. کدهای قدیمی یا متغیری که پیش از حلقه تعریف شده و با <code>=</code> مقدار می‌گیرد، ممکن است capture مشترک داشته باشند. در کار هم‌زمان، انتقال مقدار به پارامتر closure همچنان راهی صریح و قابل‌فهم است.

یک closure که وضعیت را تغییر می‌دهد و هم‌زمان بین چند goroutine استفاده می‌شود، به synchronization نیاز دارد؛ closure به خودی خود thread-safe نیست.

## ۸) named return values

می‌توان خروجی تابع را نام‌گذاری کرد. نام‌ها در بدنه مانند متغیر محلی در دسترس‌اند و <code>return</code> خالی همان مقادیر فعلی را بازمی‌گرداند.

</div>

~~~go
func bounds(values []int) (minimum int, maximum int, ok bool) {
	if len(values) == 0 {
		return
	}

	minimum, maximum = values[0], values[0]
	for _, value := range values[1:] {
		if value < minimum {
			minimum = value
		}
		if value > maximum {
			maximum = value
		}
	}
	ok = true
	return
}
~~~

<div dir="rtl">

نام خروجی گاهی مستندات مفیدی فراهم می‌کند و در تابع کوتاه، مسیرهای متعدد را جمع‌وجور می‌سازد. اما <code>naked return</code> در تابع طولانی پنهان می‌کند هر متغیر کجا مقدار گرفته است؛ در API با چند خروجی، struct هم اغلب روشن‌تر است. از نام یکسان برای پارامتر و خروجی پرهیز کن، چون shadowing یا خواندن کد را دشوار می‌کند.

## ۹) طراحی تابع‌های قابل‌آزمون و قابل‌فهم

پیش از نوشتن تابع این موارد را مشخص کن:

- ورودی‌ها چه invariantهایی دارند؟ تابع آن‌ها را بررسی می‌کند یا از caller انتظار دارد؟
- نتیجه چیست و کدام حالت‌ها خطا هستند؟
- تابع دادهٔ ورودی را تغییر می‌دهد یا نه؟
- وابستگی خارجی مثل clock، فایل، شبکه یا database را چطور می‌توان جایگزین کرد؟
- چه زمانی باید return کند و چه کسی مسئول retry یا logging است؟
- آیا نام تابع اثر جانبی مهم را صادقانه نشان می‌دهد؟

تابع خالصی مثل <code>parsePort</code> که فقط ورودی را می‌گیرد و خروجی می‌دهد، ساده‌تر از تابعی است که پنهانی global می‌خواند. هرچه اثر جانبی روشن‌تر و محدودتر باشد، تست و بازبینی آسان‌تر است. خطا را نزدیک لایه‌ای مدیریت کن که تصمیم معنادار دارد؛ لایه‌های میانی معمولاً خطا را با context wrap می‌کنند و به بالاتر می‌فرستند.

## خطاهای رایج

- فرض‌کردن اینکه Go pass by reference دارد.
- فراموش‌کردن اینکه slice/map/pointerهای کپی‌شده می‌توانند دادهٔ مشترک داشته باشند.
- استفاده از مقدار برگشتی در حالی که <code>err != nil</code> است.
- قورت‌دادن خطا یا برگرداندن error بدون context لازم.
- استفاده از variadic برای API نامحدود و مبهم.
- فرض‌کردن closure مقدار متغیر را snapshot می‌کند.
- استفادهٔ هم‌زمان از closure mutable بدون mutex یا کانال.
- زیاده‌روی در خروجی‌های named و return خالی.
- نوشتن تابعی که چند مسئولیت و چند اثر جانبی نامرتبط دارد.

## تمرین‌های مرحله‌ای با راه‌حل

### تمرین ۱: جمع با کنترل سرریز مسئلهٔ کاربردی

تابعی بنویس که دو <code>int</code> بگیرد و مجموع را برگرداند. در این تمرین سرریز عدد صحیح را نادیده نگیر: مشخص کن چرا تشخیص سرریز در همهٔ حالت‌ها به type و سیاست برنامه وابسته است. برای یک راه‌حل سادهٔ آموزشی، ورودی را در بازهٔ امن محدود کن؛ در سامانهٔ واقعی، محدودیت دامنه را در قرارداد نوع یا validation روشن کن.

**راهنمای پاسخ:** برای دادهٔ پولی از <code>float64</code> استفاده نکن؛ مقدار را با واحد کوچک‌تر صحیح (مثلاً ریال/سنت) و قواعد domain ذخیره کن. برای این درس، مهم‌تر از پیاده‌سازی عمومی تشخیص overflow، بیان invariant و آزمایش مرزهای ورودی است.

### تمرین ۲: <code>ParsePort</code>

ورودی رشته‌ای را به پورت ۱ تا ۶۵۵۳۵ تبدیل کن. خطای تبدیل و خطای خارج از بازه باید قابل‌تشخیص باشند.

**راه‌حل:** تابع کامل <code>parsePort</code> در بخش ۳ از <code>strconv.Atoi</code> و <code>fmt.Errorf</code> استفاده کرد. آن را به package دیگری منتقل و برای سه ورودی «8080»، «abc» و «70000» تست table-driven بنویس.

### تمرین ۳: میانگین با خروجی چندتایی

تابعی بنویس که slice عددها را بگیرد و <code>(float64, error)</code> بدهد؛ برای slice خالی خطا برگرداند.

~~~go
func average(values []int) (float64, error) {
	if len(values) == 0 {
		return 0, errors.New("میانگین slice خالی تعریف نشده است")
	}
	total := 0
	for _, value := range values {
		total += value
	}
	return float64(total) / float64(len(values)), nil
}
~~~

**تحلیل:** تبدیل به float قبل از تقسیم صحیح لازم است. این نسخه هنوز دربارهٔ سرریز <code>total</code> محدودیت دارد؛ برای ورودی بسیار بزرگ باید سیاست و نوع دامنه را تعیین کنی.

### تمرین ۴: closure مستقل

دو شمارنده از <code>makeCounter</code> بساز و ثابت کن افزایش یکی روی دیگری اثر ندارد. پاسخ: هر فراخوانی سازنده یک متغیر <code>count</code> تازه ایجاد می‌کند؛ closure مربوط به همان فراخوانی آن را نگه می‌دارد.

### تمرین ۵: variadic

تابع <code>joinWith(separator string, values ...string) string</code> بساز. پاسخ پیشنهادی: از <code>strings.Join(values, separator)</code> استفاده کن؛ ورودی خالی را به رشتهٔ خالی تبدیل کن، نه اینکه جداکنندهٔ اضافی بسازی.

11. آیا closure mutable خودبه‌خود در برابر هم‌زمانی ایمن است؟
12. named return چه فایده و چه هزینه‌ای دارد؟
13. چرا struct برای تعداد زیادی خروجی می‌تواند بهتر باشد؟
14. تفاوت تبدیل موفق با اعتبارسنجی domain چیست؟
15. کجا باید خطا log شود، و چرا log کردن در هر لایه بد است؟
16. برای مبلغ پول چرا نباید بی‌دلیل از float استفاده کرد؟

### کلید پاسخ

1. <code>func add(a, b int) int</code>.
2. مقدار آرگومان کپی می‌شود؛ خود متغیر caller منتقل نمی‌شود.
3. header slice کپی است ولی backing array می‌تواند مشترک باشد.
4. خروجی نتیجه همراه با خطا است؛ خطای non-nil یعنی caller باید شکست را مدیریت کند.
5. بعد از بررسی <code>err == nil</code> یا طبق قراردادی که نوع خروجی/خطا مستند کرده است.
6. <code>values...</code>؛ این syntax عناصر slice را به آرگومان‌های variadic باز می‌کند.
7. تا تمام آرگومان‌های پیشین به پارامترهای معمول تعلق بگیرند و باقی به فهرست variadic.
8. نگه‌داشتن تابع در متغیر، ارسال به تابع دیگر، بازگرداندن به‌عنوان callback.
9. دسترسی به متغیرهای lexical scope؛ capture لزوماً کپی ثابت مقدار نیست.
10. خیر؛ معمولاً همان متغیر را می‌بیند.
11. خیر؛ اگر محیط mutable بین goroutineها مشترک باشد، synchronization لازم است.
12. نام‌ها قرارداد را روشن می‌کنند؛ در مقابل return خالی در بدنهٔ طولانی دنبال‌کردن مقدار را سخت می‌کند.
13. چون خروجی‌های نام‌دار و نوع‌دار هستند و caller لازم نیست ترتیب چند مقدار را حفظ کند.
14. parser فقط می‌گوید رشته به عدد تبدیل شد؛ domain ممکن است همچنان آن عدد را نامعتبر بداند.
15. در لایه‌ای که بتواند تصمیم بگیرد؛ log تکراری یک خطا در چند لایه نویز و هشدار تکراری می‌سازد.
16. چون نمایش اعشاری دودویی بسیاری از کسرهای ده‌دهی را دقیق نگه نمی‌دارد؛ نوع صحیح با واحد تعریف‌شده و قواعد گردکردن روشن‌تر است.
