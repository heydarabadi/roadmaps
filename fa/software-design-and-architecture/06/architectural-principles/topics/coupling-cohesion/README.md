## هدف یادگیری

پس از این درس بتوانی مفهوم را با زبان خودت تعریف کنی، در مثال دامنه‌ای تشخیصش بدهی و هزینهٔ انتخاب یا کنارگذاشتنش را توضیح بدهی.

## آموزش

انسجام نشان می‌دهد اعضا برای یک هدف تغییر می‌کنند؛ coupling نشان می‌دهد تغییر یک بخش چه بخش‌های دیگری را مجبور به تغییر می‌کند. هدف حذف همهٔ وابستگی‌ها نیست، بلکه محدودکردن وابستگی ناموجه است.

## مثال کاربردی

مدول انبار API کوچک دارد و تغییر روش ذخیره‌سازی‌اش به کد تخفیف سرایت نمی‌کند.

این مثال آموزشی است و ادعای پیاده‌سازی دقیق یک شرکت مشخص را ندارد. نمونهٔ صنعتی مستند و زمینهٔ آن در فصل «اصول معماری» پیوند داده شده است.

## تصمیم معماری و محدودیت‌ها

- **چه زمانی به‌کار ببر:** وقتی مسئلهٔ اصلی‌ای که مفهوم حل می‌کند در سامانه واقعاً دیده می‌شود و قراردادش می‌تواند در کد یا آزمون بررسی شود.
- **چه زمانی ساده‌تر بماند:** جداسازی بیش‌ازحد تماس‌های شبکه‌ای و mapping را اضافه می‌کند.
- **بازبینی:** کاهش عددی وابستگی بدون بررسی مسیر تغییر، هدف اشتباه است.

## کوییز با پاسخ تشریحی

پاسخ را بپوشان و ابتدا با کلمات خودت توضیح بده؛ پاسخ پیشنهادی معیار سنجش است، نه تنها عبارت درست.

1. **این مفهوم دقیقاً چه مسئله‌ای را حل می‌کند؟**
   - پاسخ پیشنهادی: انسجام نشان می‌دهد اعضا برای یک هدف تغییر می‌کنند؛ coupling نشان می‌دهد تغییر یک بخش چه بخش‌های دیگری را مجبور به تغییر می‌کند. هدف حذف همهٔ وابستگی‌ها نیست، بلکه محدودکردن وابستگی ناموجه است.
2. **در مثال زیر چه تصمیمی می‌گیری و چرا؟**
   - پاسخ پیشنهادی: مدول انبار API کوچک دارد و تغییر روش ذخیره‌سازی‌اش به کد تخفیف سرایت نمی‌کند.
3. **چه زمانی انتخاب آن نامناسب یا پرهزینه است؟**
   - پاسخ پیشنهادی: جداسازی بیش‌ازحد تماس‌های شبکه‌ای و mapping را اضافه می‌کند.
4. **کدام خطای رایج را قبل از ادغام کد بررسی می‌کنی؟**
   - پاسخ پیشنهادی: کاهش عددی وابستگی بدون بررسی مسیر تغییر، هدف اشتباه است.

## آموزش تکمیلی مستقل

### ۳. Coupling و Cohesion

**Cohesion** میزان ارتباط بخش‌های داخل component با یک مسئولیت مشترک است. **Coupling** میزان دانشی است که یک component دربارهٔ دیگری دارد و تغییر یک جزء چه مقدار را به تغییر وابسته می‌کند. هدف صفرکردن dependency نیست؛ سامانه بدون collaboration چیزی انجام نمی‌دهد. هدف محدودکردن dependency ناموجه و پرهزینه است.

نشانه‌های coupling:

- تغییر schema یک ماژول، callerهای متعدد را می‌شکند؛
- component از private field یا table داخلی دیگری می‌خواند؛
- دو سرویس برای تکمیل یک request پیوسته به هم call می‌کنند؛
- ترتیب چند event به شکل پنهان برای درست‌کارکردن لازم است.

نشانه‌های انسجام:

- operationها حول یک capability و زبان مشترک‌اند؛
- تغییرهای هم‌زمان در همان مرز رخ می‌دهند؛
- component می‌تواند با contract روشن تست شود.

#### سنجش عملی

به جای عبارت «coupling زیاد است» یک تغییر واقعی را دنبال کن: «اگر روش محاسبهٔ ارسال عوض شود، کدام فایل، تیم، آزمون، سرویس و deploy تغییر می‌کند؟» ثبت کن چند مرز نقض می‌شود، کدام تغییر ناخواسته به دیگران سرایت می‌کند، و چه هزینه‌ای برای refactor لازم است.

جداسازی بیش‌ازحد coupling را از call محلی به mapping، API و network منتقل می‌کند؛ ممکن است دشوارتر شود. Component boundary درون‌فرایندی اغلب ارزان‌تر از مرز سرویس است و فرصت تغییر آینده را حفظ می‌کند.

## نمودار معماری و خواندن مرحله‌ای

Coupling می‌سنجد تغییر یک بخش تا چه حد به دانستن جزئیات بخش دیگر وابسته است؛ cohesion می‌سنجد مسئولیت‌های داخل یک بخش چقدر به هم مربوط‌اند. coupling کمتر بدون cohesion کافی به پراکندگی بی‌فایده می‌انجامد؛ هدف، مرزهایی با مسئولیت منسجم و قرارداد کوچک است.
**دام رایج:** تعداد import کمتر را به‌تنهایی نشانهٔ معماری بهتر ندان.
**تمرین با پاسخ:** اگر Invoice هم ایمیل، ذخیره و محاسبهٔ مالیات را مالک است، مسئولیت‌هایی را که actorهای جدا تغییر می‌دهند جدا کن.

این نمودار ساده فقط یک view را نشان می‌دهد؛ سامانهٔ واقعی به تصمیم روشن دربارهٔ شکست، امنیت و مالکیت هم نیاز دارد.

~~~text
Low cohesion / broad coupling:
[Invoice: tax + email + database + PDF] ---> [Many unrelated modules]

Higher cohesion / explicit contracts:
[Tax policy]   [Invoice storage]   [PDF renderer]
      \              |                 /
       +---------- [Invoice use case] -+
~~~
