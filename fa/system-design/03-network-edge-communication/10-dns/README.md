# DNS و Service Naming

## هدف یادگیری

- مسئله‌ای را که این مفهوم حل می‌کند تعریف کنی.
- برای یک سامانهٔ نمونه انتخاب را با trade-off توضیح بدهی.
- رفتار سیستم را هنگام اختلال پیش‌بینی کنی.

## ایدهٔ مرکزی

DNS نام را به رکورد شبکه تبدیل می‌کند و با cache و TTL در مسیریابی نقش دارد؛ تغییر رکورد فوراً همهٔ cacheها را عوض نمی‌کند.

## نقشهٔ مفهومی

نیاز کسب‌وکار ← قرارداد بار/کیفیت ← انتخاب الگو ← نقطهٔ شکست ← مشاهده و بازیابی

## توضیح کامل

Resolverها ممکن است پاسخ را cache کنند. A/AAAA برای آدرس IPv4/IPv6، CNAME برای alias و TXT برای اثبات/سیاست است. DNS load balancing هدایت سطح بالا می‌دهد اما انتخاب endpoint در cache کلاینت‌ها محدود است. داخل محیط پویا، service discovery باید چرخهٔ عمر نمونه‌ها را بشناسد.

## درس گام‌به‌گام

### یک lookup چه مسیرهایی دارد؟

کاربر `api.example.com` را می‌خواهد. مرورگر و سیستم‌عامل ابتدا cache محلی را می‌سنجند؛ اگر پاسخ نباشد، recursive resolver از cache خودش استفاده می‌کند یا مرحله‌های DNS را طی می‌کند: root server محل TLD را می‌دهد، name server دامنهٔ `.com` محل authoritative server را، و authoritative server رکورد دامنه را برمی‌گرداند. این مراحل معمولاً cache می‌شوند، پس هر درخواست به root نمی‌رود.

DNS نام را به رکورد می‌نگارد، نه اینکه یک اتصال HTTP را proxy کند. بعد از دریافت IP، client خودش اتصال TCP/QUIC و TLS را برقرار می‌کند. رکورد DNS به تنهایی تضمین نمی‌کند مقصد سالم، مجاز یا نزدیک‌ترین مقصد باشد.

### رکوردهای پرکاربرد

- `A`: نگاشت hostname به IPv4؛ `AAAA`: نگاشت به IPv6.
- `CNAME`: alias یک نام به نام canonical دیگر؛ در بسیاری از کاربردها apex دامنه محدودیت خاص دارد.
- `MX`: مقصد دریافت ایمیل؛ `TXT`: متن سیاست/اثبات مالکیت؛ `NS`: سرورهای مرجع دامنه.
- `SRV`: نام سرویس، پورت و اولویت را در برخی پروتکل‌ها منتشر می‌کند.

تغییر zone ممکن است در authoritative server سریع باشد، اما resolverهای میانی تا پایان TTL مقدار قبلی را نگه دارند. Negative caching نیز پاسخ «این نام وجود ندارد» را موقتاً cache می‌کند؛ بنابراین ساخت رکوردی که همین تازگی پرس‌وجو شده ممکن است فوری دیده نشود.

### TTL و تغییر مسیر

TTL مدت پیشنهادی cache است، نه دکمهٔ invalidate برای همهٔ clientها. بعضی clientها، برنامه‌ها و resolverها cache متفاوت دارند. برای مهاجرت آدرس، TTL را پیشاپیش کاهش بده، مقصد جدید را آماده و صحت TLS/health را بسنج، سپس رکورد را تغییر بده. پس از پایان پنجرهٔ انتقال و مشاهدهٔ ترافیک، TTL را به مقدار عملیاتی برگردان.

### GeoDNS و load balancing

GeoDNS می‌تواند براساس مکان resolver یا سیاست سرویس، IP منطقه‌ای بدهد. مکان resolver الزاماً مکان کاربر نیست؛ VPN، resolver عمومی و cache روی نتیجه اثر دارند. DNS round-robin هم درخواست‌ها را به شکل دقیق و متوازن تقسیم نمی‌کند، چون clientها پاسخ را cache می‌کنند و اتصال‌های موجود ادامه می‌یابند. برای health-aware routing و کنترل درخواست، LB لایهٔ شبکه/HTTP مناسب‌تر است.

### امنیت و عیب‌یابی

DNSSEC صحت منشأ پاسخ را با امضا بررسی می‌کند؛ جای رمزنگاری محتوا یا کنترل دسترسی نیست. برای troubleshooting، پاسخ authoritative و recursive را جدا بررسی کن، رکورد و TTL را ببین، و با resolverهای چند شبکه مقایسه کن. در سامانهٔ داخلی از نام‌های private/split-horizon با سیاست روشن استفاده کن و IP داخلی را ناخواسته در DNS عمومی افشا نکن.

## مثال عملی

برای cutover API، TTL را از قبل کاهش بده و resolverهای مهم را بررسی کن؛ TTL پایین cache موجود را فوراً پاک نمی‌کند.

## دام‌ها و سوءبرداشت‌ها

- فراموشی negative caching؛ انتظار failover آنی؛ سوءاستفاده از رکوردها؛ DNSSEC بی‌توجه.
- عددهای مثال آموزشی‌اند؛ SLO و ظرفیت نهایی را از دادهٔ واقعی تعیین کن.

## آزمون کوتاه

1. CNAME چه می‌کند؟
2. چرا انتشار تغییر DNS آنی نیست؟
3. AAAA برای کدام نسخهٔ IP است؟

### پاسخ‌نامهٔ فشرده

1. CNAME یک نام را به نام canonical دیگری alias می‌کند.
2. resolverها و clientها پاسخ را تا TTL یا حتی سیاست cache داخلی نگه می‌دارند.
3. IPv6؛ رکورد A آدرس IPv4 است.

## تمرین

برای یک فروشگاه اینترنتی، مسیر درخواست این مفهوم را رسم کن. منبع حقیقت، مرز شبکه، رفتار شکست، دادهٔ حساس، معیار پایش و راه بازگشت را مشخص کن. سپس یک آزمون خرابی بنویس که بتواند فرض اصلی را رد کند.

## خلاصه

DNS نام را به رکورد شبکه تبدیل می‌کند و با cache و TTL در مسیریابی نقش دارد؛ تغییر رکورد فوراً همهٔ cacheها را عوض نمی‌کند. پیش از پیاده‌سازی رفتار عادی، حالت اختلال و معیار موفقیت را ثبت کن.
