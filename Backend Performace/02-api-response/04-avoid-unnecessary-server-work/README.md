# حذف پردازش غیرضروری سرور

**زبان:** فارسی · [English version](README.en.md)


کار غیرضروری کاری است که برای نتیجهٔ موردنیاز این درخواست لازم نیست: واکشی رابطه‌ای که نمایش داده نمی‌شود، محاسبهٔ فیلد انتخاب‌نشده، ساخت دوبارهٔ نمایش تغییرنکرده یا فراخوانی یک سرویس جانبی که خروجی‌اش مصرف نمی‌شود. ابتدا علت انجام کار را بررسی کنید؛ سریع‌تر کردن یا موازی کردنِ کاری که حذف‌شدنی است قدم اول مناسبی نیست.

**پس از این درس می‌توانید:** مسیر بحرانی یک پاسخ را به کارهای لازم و اختیاری تفکیک کنید؛ تصمیم انتخاب فیلد را به قبل از محاسبه ببرید؛ Revalidation را بدون وعدهٔ نادرست دربارهٔ CPU پیاده‌سازی کنید؛ و حذف کار را با Trace و شمارنده ثابت کنید. پیش‌نیاز: HTTP، مفهوم مجوز و [قرارداد Payload](../01-payload-size/README.md). تاریخ بررسی منابع: **۲۰۲۶-۱۱-۱۰**.

## اصطلاح‌های لازم

**Authorization** بررسی می‌کند این هویت اجازهٔ خواندن/تغییر کدام داده را دارد. **Validator** مانند ETag نسخهٔ نمایش را برای درخواست شرطی مشخص می‌کند. **Trace** مسیر و زمان بخش‌های یک درخواست را ثبت می‌کند. این کارهای صحت/امنیت را از محاسبهٔ اختیاری جدا می‌کنیم.

## مدل ذهنی: قبل از انجام کار تصمیم بگیرید

| نیاز درخواست | تصمیم زودهنگام | کار قابل حذف |
| --- | --- | --- |
| فقط خلاصهٔ سفارش | نمایش خلاصه و Field Set معتبر | جزئیات اقلام، محاسبهٔ آمار مشتری، Serialization آن‌ها |
| فیلتر سفارش‌های پرداخت‌شده | انتقال Filter معتبر به منبع داده | واکشی همه و فیلتر در حافظه |
| نمایش قبلی هنوز معتبر است | مقایسهٔ Validator ارزان پس از بررسی دسترسی | ساخت دوباره و ارسال بدنه |
| نتیجهٔ یک Lookup در همان درخواست چند بار لازم است | استفادهٔ دوباره در محدودهٔ همان درخواست | فراخوانی تکراری برای کلید یکسان |
| فقط وجود نتیجه لازم است | عملیات وجودسنجی متناسب | شمارش یا بارگیری همهٔ رکوردها |

این پیشنهادها قانون «هر محاسبه‌ای را Cache کن» نیستند. ابتدا با Trace و Profile ببینید کدام کار چه سهمی دارد. راهنمای Microsoft استفاده از اجزای برنامه فقط در زمان نیاز و کاهش مصرف غیرضروری را توصیه می‌کند؛ افزودن منابع برای پوشاندن کار اضافی علت را برطرف نمی‌کند. [Microsoft Well-Architected](https://learn.microsoft.com/en-us/azure/well-architected/performance-efficiency/optimize-code-infrastructure)

### روش بررسی یک Endpoint

1. **خروجی لازم را بنویسید:** کدام فیلد و تضمین صحت برای این مصرف‌کننده ضروری است؟ Authorization، اعتبارسنجی و تعهدات ثبت رویداد «اضافی» محسوب نمی‌شوند.
2. **هزینه‌ها را تفکیک کنید:** زمان و تعداد Query، فراخوانی شبکه، محاسبه، Serialization و بایت پاسخ را در Trace جدا ببینید؛ فقط مدت کل کافی نیست.
3. **نیاز را زود اعلام کنید:** برنامهٔ واکشی بر اساس نمایش/فیلدهای مجاز ساخته شود. فیلتر، سقف صفحه و Projection را تا لایهٔ مناسب جلو ببرید.
4. **تکرار محلی را حذف کنید:** Lookup یکسان در محدودهٔ Request را یک بار انجام دهید، مشروط به اینکه معنای تازگی و مجوز ثابت بماند. Cache بین درخواست‌ها قواعد ابطال و جداسازی کاربر دارد و در [فصل Cache](../../01-caching/README.md) بررسی می‌شود.
5. **خروج زودهنگام امن طراحی کنید:** ورودی نامعتبر زود رد شود؛ نمایش تغییرنکرده با Validator بررسی شود. لغو درخواست می‌تواند کار اختیاریِ باقی‌مانده را متوقف کند، اما نباید تراکنش یا اثر کسب‌وکارِ لازم را نیمه‌تمام رها کند.
6. **دوباره اندازه بگیرید:** اگر بایت کمتر شده ولی Query Count ثابت است، فقط خروجی کوچک شده؛ اگر p95 بهتر شده ولی خطا یا CPU بیشتر شده، نتیجه کامل نیست.

## مثال حل‌شده: خلاصه‌ای که آمار سنگین نمی‌خواهد

**سناریوی فرضی:** صفحهٔ سفارش فقط `id,status,total` می‌خواهد. پیاده‌سازی قبلی هر بار اقلام را بارگیری و امتیاز مشتری را از سرویس دیگری می‌گیرد، سپس Serializer این دو را حذف می‌کند. نمایش خلاصه را به ابتدای مسیر منتقل می‌کنیم:

<div dir="ltr" align="left">

```text
handleSummary(request):
    principal = authenticate(request)
    authorizeRead(principal, request.orderId)
    fields = validateAllowedFields(request.fields)
    plan = buildPlanFor(fields, view="summary")

    revision = readSummaryRevision(request.orderId, principal.tenant)
    validator = makeWeakValidator(revision, fields, view="summary")
    if matchesIfNoneMatch(request, validator):
        return 304 with validator and private-cache-policy, no body

    summary = readAuthorizedSummaryProjection(plan)
    if plan.needsItems:
        summary.items = readItemsWithinBudget()
    if plan.needsCustomerScore:
        summary.customerScore = fetchCustomerScore()
    return 200 with JSON(summary) and validatorFor(summary)
```

</div>

این Pseudocode الگوریتم کامل HTTP یا زبان مشخصی نیست. مقایسهٔ `If-None-Match` را به کتابخانهٔ سازگار HTTP بسپارید؛ مقایسهٔ خام یک رشته تمام حالات Header را پوشش نمی‌دهد. [MDN: If-None-Match](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-None-Match) معنای مقایسه و Headerهای لازم در پاسخ شرطی را توضیح می‌دهد. `revision` باید تمام وابستگی‌های نمایش، Tenant، فیلد و نسخهٔ قرارداد را پوشش دهد. اگر داده بین خواندن نسخه و خواندن بدنه عوض شد، Validator خروجی باید از همان نمایش خوانده‌شده ساخته شود یا خواندن سازگار/تلاش مجدد وجود داشته باشد؛ Revision قدیمی را به بدنهٔ جدید نچسبانید.

نمونهٔ تبادل برای نمایش خصوصی که باید پیش از استفاده دوباره اعتبارسنجی شود:

<div dir="ltr" align="left">

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, no-cache
ETag: W/"o42-summary-fields-a-v7"

{"id":"o42","status":"paid","total":480000}
```

```http
GET /v1/orders/o42?view=summary HTTP/1.1
Host: api.example.test
If-None-Match: W/"o42-summary-fields-a-v7"
```

```http
HTTP/1.1 304 Not Modified
Cache-Control: private, no-cache
ETag: W/"o42-summary-fields-a-v7"
```

</div>

کلاینت باید بدنهٔ قبلی را داشته باشد؛ `304` بدنهٔ تازه ندارد. `no-cache` اجازهٔ ذخیره را با الزام اعتبارسنجی می‌دهد؛ با `no-store` یکسان نیست. Validator این نمونه Weak است و برای اعتبارسنجی GET به کار می‌رود؛ نمایش‌های مجاز و معنای تغییر باید روشن باشند. این مثال احراز هویت و Headerهای کامل محیط را نمایش نمی‌دهد. [MDN: HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

**نکتهٔ کلیدی:** اگر ETag را پس از اجرای همهٔ Queryها و ساخت JSON با Hash بدنه بسازید، `304` هنوز بایت انتقال را کم می‌کند ولی بیشتر پردازش سرور از قبل انجام شده است. کاهش CPU زمانی رخ می‌دهد که اعتبار نمایش را زودتر و با هزینهٔ کمتر از ساخت آن بفهمید. اگر Revision قابل‌اعتماد ندارید، ادعای حذف محاسبه نکنید؛ اعتبارسنجیِ صحیح اما دیرهنگام هم می‌تواند مفید باشد.

## تمرین کوتاه و راه‌حل نمونه

برای یک Handler آزمایشی یا حتی شبیه‌سازی دستی، چهار شمارنده بگذارید: `summary_reads`، `items_reads`، `score_calls` و `serializations`.

1. درخواست خلاصه را با اجرای قدیمی شبیه‌سازی کنید: همهٔ شمارنده‌ها افزایش می‌یابند.
2. تصمیم فیلدها را پیش از اجرا ببرید: خلاصه را بسازید ولی اقلام و امتیاز را نخوانید.
3. یک درخواست شرطی با Validator معتبر و یک درخواست پس از تغییر وضعیت شبیه‌سازی کنید.

**انتظار:** در مرحلهٔ دوم `items_reads` و `score_calls` صفر بمانند. در مسیر `304` با Revision ارزان، Serialization بدنه و جزئیات اجرا نشوند، اما بررسی مجوز و خواندن اعتبار می‌تواند باقی بماند. پس از تغییر وضعیت باید `200` و دادهٔ تازه برگردد. اگر فقط ظاهر JSON عوض شد و شمارنده‌ها ثابت ماندند، حذف کار را در لایهٔ درست انجام نداده‌اید. این تمرین اثبات عملکرد تولید یا Benchmark نیست.

## راه‌حل گام‌به‌گام تمرین

برای Handler قدیمی، هر درخواست خلاصه یک بار `summary_reads`, `items_reads`, `score_calls` و `serializations` را افزایش می‌دهد. پس از ساخت plan خلاصه، مقدارهای `items_reads=0` و `score_calls=0` می‌شوند؛ `summary_reads` و یک Serialization پاسخ 200 هنوز لازم‌اند. با Validator معتبر، مسیر 304 پس از authenticate/authorize و خواندن Revision به بدنه‌سازی نمی‌رسد: `serializations=0` و هیچ Query اقلام/امتیاز نداریم. تغییر status باید Revision را عوض کند و مسیر 200 تازه را برگرداند. در نتیجه برای ادعای حذف CPU، شمارنده‌ها و Spanهای هزینه را هم مقایسه می‌کنیم، نه فقط بایت پاسخ.

## شاهد واقعی و حدود آن

**WordPress REST API:** مستندات `_fields` صراحتاً می‌گوید WordPress هنگام تولید شیء پاسخ فیلدهای غیرلازم را کنار می‌گذارد تا محاسبهٔ داخلی و Queryهای احتمالی آن‌ها انجام نشوند. این شاهد، تفاوت «نساختن فیلد» و «پاک‌کردن فیلد پس از ساخت» را در یک پیاده‌سازی واقعی روشن می‌کند. [WordPress Global Parameters](https://developer.wordpress.org/rest-api/using-the-rest-api/global-parameters/)

**GitHub REST API:** راهنمای رسمی درخواست شرطی با `ETag`/`If-None-Match` و پاسخ `304` را توضیح می‌دهد؛ همچنین پیشنهاد می‌کند درخواست‌ها مشخص و پایدار باشند تا نمایش کمتر بی‌جهت تغییر کند. معافیت `304` از Primary Rate Limit در آن سرویس به درخواست درستِ احرازهویت‌شده وابسته است؛ این یک قاعدهٔ GitHub است، نه HTTP عمومی. این سند نمی‌گوید چه مقدار CPU داخلی GitHub حذف می‌شود. [GitHub Best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

برای این درس از شواهد عملیاتی عمومی استفاده شده است؛ عدد کاهش latency/CPU برای شرکت یا Endpoint فرضی ما از این منابع استخراج نشده و ادعا نمی‌شود.

## Trade-off و شکست‌های رایج

| تصمیم/شکست | پیامد | راه بررسی |
| --- | --- | --- |
| حذف رابطه فقط در خروجی | Queryهای N+1 و محاسبه باقی می‌مانند | Span و Query Count برای هر نمایش را مقایسه کن |
| Validator با وابستگی ناقص | `304` اشتباه و دادهٔ کهنه | تغییر هر وابستگیِ قابل‌نمایش را مرور کن |
| Revalidation پس از Hash کامل | شبکه کمتر، CPU تقریباً قبلی | زمان ساخت Validator را جدا ثبت کن |
| Cache نتیجه بدون Tenant/مجوز | افشای داده | هویت و محدودهٔ دسترسی را در طراحی بررسی کن |
| موازی کردن همهٔ کارهای اختیاری | فشار به Pool/وابستگی و Tail Latency | اول کار بی‌مصرف را حذف کن؛ Concurrency را محدود کن |
| حذف کار لازم تحت عنوان بهینه‌سازی | صحت ناقص، مجوز دورزده‌شده یا رویداد گمشده | تعهد کسب‌وکار را شرط پذیرش نگه دار |

برنامهٔ اجرای مبتنی بر فیلد برای Endpoint دارای چند نمایش و محاسبهٔ گران مفید است. برای پاسخ ساده، شاخه‌های زیاد و Revision پیچیده ممکن است نگه‌داری را سخت‌تر از سود واقعی کند؛ ابتدا دو نمایش صریح «خلاصه/جزئیات» را بسنجید. انتقال کار به Background آن را حذف نمی‌کند؛ زمان و تضمین تحویل را عوض می‌کند و موضوع [کار پس‌زمینه](../../03-asynchronism/01-background-jobs/README.md) است.

### چک‌لیست عملیاتی

- [ ] فیلدهای لازم و کارهای ضروری کسب‌وکار از قبل مشخص‌اند.
- [ ] احراز هویت و مجوزدهی پیش از خروج زودهنگام اعمال می‌شوند.
- [ ] Query/فراخوانی وابسته برای فیلد انتخاب‌نشده اجرا نمی‌شود.
- [ ] هر Validator تمام وابستگی‌ها و نمایش مربوط را پوشش می‌دهد.
- [ ] نسخه و بدنهٔ خروجی از نظر هم‌زمانی سازگارند.
- [ ] درصد `304` در کنار CPU/Query Count سنجیده می‌شود؛ به‌تنهایی معیار موفقیت نیست.
- [ ] پس از تغییر داده، Cache سرد، لغو درخواست و خطای وابستگی رفتار مشخص است.
- [ ] p95/p99، Allocation، تعداد فراخوانی و خطای کاربر با خط مبنا مقایسه شده‌اند.

## آزمون

1. کوچک شدن JSON چه زمانی ثابت نمی‌کند کار سرور کم شده است؟
2. چرا Hash کردن بدنهٔ کامل برای ETag ممکن است CPU را چندان کم نکند؟
3. آیا `304` مجوز حذف بررسی دسترسی را می‌دهد؟
4. فیلد محاسبه‌شده‌ای به دو منبع وابسته است؛ Revision فقط یکی را پوشش می‌دهد. خطر چیست؟
5. تفاوت حذف یک کار و انتقال آن به Background چیست؟
6. چه شواهدی نشان می‌دهد حذف امتیاز مشتری واقعاً اجرا نشده و فقط پنهان نشده است؟

### پاسخ تشریحی

1. وقتی داده/رابطه و محاسبه قبلاً انجام و فیلد فقط هنگام خروج حذف شده باشد. Trace و شمارندهٔ کارها باید تغییر را تأیید کنند.
2. چون ساخت بدنه، Query و محاسبه پیش از Hash انجام شده‌اند؛ صرفه‌جویی اصلی می‌تواند فقط انتقال باشد.
3. خیر؛ کاربر ممکن است دیگر دسترسی نداشته باشد. درخواست شرطی هم درخواست دسترسی به همان منبع است.
4. تغییر منبع دوم ممکن است ETag را تغییر ندهد و `304` نادرست تولید شود؛ Validator باید نمایش واقعی را پوشش دهد.
5. حذف یعنی مصرف منابع آن کار لازم نیست؛ Background همان کار را بعداً با تعهد اجرا/خطا انجام می‌دهد.
6. `score_calls=0` در مسیر خلاصه، نبود Span مربوط و کاهش هزینهٔ وابستگی، در کنار خروجی صحیح؛ فقط غیبت فیلد در JSON کافی نیست.

## جمع‌بندی

کار غیرضروری را پیش از اجرا حذف کنید، اما مجوز، اعتبارسنجی و اثر لازم کسب‌وکار را حفظ کنید. ETag/304 بایت را کم می‌کند؛ فقط Validator ارزان و کامل می‌تواند ساخت بدنه یا Queryهای گران را نیز حذف کند، که باید با Trace ثابت شود.
