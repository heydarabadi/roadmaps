# واژه‌نامهٔ معماری نرم‌افزار

این واژه‌نامه برای خواندن درس‌هاست، نه ترجمهٔ جایگزین مستندات رسمی. یک واژه ممکن است در سازمان‌های مختلف تعریف دقیق متفاوتی داشته باشد؛ در تصمیم واقعی، تعریف مورد استفادهٔ تیم را ثبت کن.

## معماری، مدل‌سازی و کیفیت

| اصطلاح | توضیح |
| --- | --- |
| **Architecture / معماری** | ساختار و تصمیم‌های مهمی که شکل سامانه، تغییر، اجرا و ویژگی‌های کیفی آن را تعیین می‌کنند. |
| **Architectural decision / تصمیم معماری** | انتخابی با پیامد قابل‌توجه بر ساختار، کیفیت یا هزینهٔ سامانه؛ شامل زمینه، گزینه‌ها، دلیل و پیامد است. |
| **ADR** | Architecture Decision Record؛ سند کوتاه یک تصمیم، زمینه، گزینه‌ها، نتیجه و پیامدهای آن. |
| **Stakeholder / ذی‌نفع** | شخص یا گروهی که از سامانه اثر می‌گیرد، بر آن اثر می‌گذارد یا دربارهٔ آن تصمیم می‌گیرد. |
| **Quality attribute / ویژگی کیفی** | ویژگی سنجش‌پذیر مانند latency، امنیت، دسترس‌پذیری، تغییرپذیری یا قابلیت بازیابی. |
| **Scenario / سناریوی کیفیت** | محرک، محیط، جزء تحت‌تأثیر، پاسخ مورد انتظار و معیار قابل‌اندازه‌گیری برای یک ویژگی کیفی. |
| **Trade-off / مصالحه** | انتخابی که یک کیفیت را بهتر می‌کند و ممکن است کیفیت، هزینه یا پیچیدگی دیگری را بدتر کند. |
| **C4** | روش نمایش معماری از زمینه، container، component و code؛ هر نمودار به مخاطب و سطح جزئیات مشخصی پاسخ می‌دهد. |
| **UML** | زبان مدل‌سازی استاندارد با نمودارهای ساختاری و رفتاری؛ ابزار ارتباط و تحلیل است، نه تضمین صحت کد. |
| **Layer / لایه** | جداسازی منطقی مسئولیت و وابستگی در کد. |
| **Tier / ردهٔ استقرار** | جداسازی اجرایی مانند process، ماشین یا شبکه؛ معمولاً هزینه و مرز failure جدید می‌آورد. |
| **Boundary / مرز** | نقطه‌ای که مالکیت، قرارداد، داده، اعتماد یا تغییر یک بخش از بخش دیگر جدا می‌شود. |
| **Coupling / وابستگی متقابل** | میزان تأثیری که تغییر یا شکست یک جزء بر اجزای دیگر می‌گذارد. |
| **Cohesion / انسجام** | میزان تمرکز یک جزء روی مسئولیت‌ها و مفاهیم مرتبط. |
| **Modularity / پیمانه‌ای بودن** | جداسازی سامانه به بخش‌هایی با مسئولیت، قرارداد و وابستگی کنترل‌شده. |
| **Monolith / یکپارچه** | برنامه‌ای که به‌صورت یک واحد اصلی build یا deploy می‌شود؛ می‌تواند داخلی ماژولار یا درهم‌تنیده باشد. |
| **Modular monolith** | یک واحد deployment با ماژول‌های دارای مالکیت، قرارداد و dependency rule قابل‌اعمال. |
| **Microservice** | سرویس مستقل پیرامون قابلیت دامنه که تیم می‌تواند با مالکیت داده و عملیات روشن جداگانه منتشر کند. |
| **Microkernel** | هستهٔ نسبتاً پایدار با قابلیت‌های افزوده‌شده از طریق plugin یا extension point. |
| **Bounded context** | محدوده‌ای در DDD که در آن مدل و زبان دامنه معنای سازگار و مالکیت مشخص دارد. |
| **Ubiquitous language** | واژگان مشترک متخصصان دامنه و تیم برای توضیح یک bounded context. |
| **Entity** | مفهوم دامنه با هویت پایدار که در طول زمان تغییر می‌کند. |
| **Value object** | مفهوم تعریف‌شده با مقدار و ویژگی‌هایش، معمولاً بدون هویت مستقل. |
| **Aggregate** | خوشه‌ای از اشیای دامنه با یک aggregate root و مرز invariant/تراکنش مدل. |
| **Invariant** | قاعده‌ای که سامانه باید در همهٔ حالت‌های معتبر حفظ کند؛ مانند منفی‌نشدن تعداد موجودی. |
| **CQRS** | جداسازی مسیر یا مدل نوشتن از مسیر یا مدل خواندن؛ لازم نیست دو دیتابیس یا event sourcing داشته باشد. |
| **Event sourcing** | ذخیرهٔ رخدادهای تغییر به‌عنوان منبع حقیقت و ساخت وضعیت/نمایش از آن‌ها. |
| **Projection / نمای مشتق‌شده** | داده‌ای که برای خواندن یا گزارش از منبع اصلی/رویدادها ساخته شده و باید قابل‌بازسازی یا همگام‌سازی باشد. |

## داده و تراکنش

| اصطلاح | توضیح |
| --- | --- |
| **ACID** | Atomicity، Consistency، Isolation و Durability؛ مجموعهٔ ویژگی‌های متداول تراکنش رابطه‌ای. |
| **Atomicity / اتمی بودن** | تراکنش کامل اعمال می‌شود یا هیچ‌کدام از آثار محلی آن اعمال نمی‌شود. |
| **Consistency / سازگاری** | تراکنش قیود تعریف‌شدهٔ مدل را حفظ می‌کند؛ این معنی با consistency در CAP یکی نیست. |
| **Isolation / جداسازی** | تعیین می‌کند تراکنش‌های هم‌زمان چه اثرهایی از هم ببینند. |
| **Durability / ماندگاری** | تغییر commitشده پس از failure قابل‌بازیابی باقی می‌ماند، مطابق تضمین موتور. |
| **CAP** | هنگام partition شبکه، تضمین‌های consistency و availability میان گره‌های توزیع‌شده با محدودیت روبه‌رو می‌شوند. |
| **Partition / بخش‌بندی** | تقسیم داده یا workload بین nodeها؛ کلید و توزیع نابرابر می‌تواند hotspot بسازد. |
| **Replication / تکثیر** | نگهداری نسخهٔ داده در چند node برای خواندن یا دسترس‌پذیری؛ به‌تنهایی backup نیست. |
| **Eventual consistency / سازگاری نهایی** | replicaها ممکن است موقتاً متفاوت باشند و اگر تغییرات متوقف شوند سرانجام همگرا شوند. |
| **Index / نمایه** | ساختار کمکی برای دسترسی سریع‌تر به الگوی query مشخص؛ storage و هزینهٔ نوشتن دارد. |
| **N+1 query** | یک query برای مجموعه و سپس یک query جدا برای هر ردیف؛ تعداد تماس‌ها با اندازهٔ مجموعه رشد می‌کند. |
| **Migration / مهاجرت schema** | تغییر ساختار یا داده؛ باید با نسخه‌های هم‌زمان، rollback و حجم واقعی سازگار باشد. |
| **Expand/contract** | اضافه‌کردن ساختار سازگار، انتقال تدریجی، تغییر مصرف‌کننده و حذف دیرهنگام ساختار قبلی. |
| **RPO** | Recovery Point Objective؛ حداکثر بازهٔ داده‌ای که پس از بازیابی از دست‌رفتنش پذیرفتنی است. |
| **RTO** | Recovery Time Objective؛ هدف زمانی برای بازگرداندن خدمت پس از رخداد. |
| **ETL / ELT** | استخراج، تبدیل و بارگذاری؛ تفاوت اصلی زمان/محل تبدیل نسبت به مقصد تحلیلی است. |
| **Fact / Dimension** | در انبار داده، fact رخداد/اندازه را در grain مشخص ثبت می‌کند؛ dimension زمینهٔ تحلیل مثل زمان یا محصول را می‌دهد. |
| **Grain** | دقیقاً مشخص می‌کند هر ردیف fact نمایندهٔ چه چیز یا چه رخدادی است. |
| **Lineage / تبار داده** | مسیر منشأ، تبدیل و مصرف داده که برای توضیح metric و تحلیل اثر تغییر لازم است. |
| **Watermark** | مرزی زمانی برای تشخیص پیشرفت یا میزان پذیرش دادهٔ دیررس در پردازش جریانی. |
| **Backfill** | اجرای دوبارهٔ pipeline برای بازهٔ تاریخی مشخص جهت بازسازی یا اصلاح داده. |

## API، پیام و سامانهٔ توزیع‌شده

| اصطلاح | توضیح |
| --- | --- |
| **API contract / قرارداد API** | تعریف پایدار ورودی، خروجی، خطا، امنیت، نسخه و رفتار مورد انتظار دو طرف. |
| **REST** | سبک معماری مبتنی بر منابع و semantics پروتکل؛ هر JSON endpoint الزاماً RESTful نیست. |
| **SOAP** | پروتکل پیام XML با قراردادها و استانداردهای سازمانی مرتبط. |
| **GraphQL** | زبان query و runtime مبتنی بر schema که client شکل فیلدهای پاسخ را انتخاب می‌کند. |
| **gRPC** | framework فراخوانی remote با قرارداد Protocol Buffers، تولید کد و پشتیبانی streaming. |
| **Idempotency / تکرارپذیری بی‌اثر** | اجرای دوبارهٔ همان درخواست اثر منطقی اضافه‌ای ایجاد نمی‌کند؛ دامنه و مدت کلید باید روشن باشد. |
| **Timeout / مهلت** | بیشترین زمانی که caller منتظر می‌ماند؛ پایان مهلت به‌تنهایی ثابت نمی‌کند عملیات سمت server انجام نشده است. |
| **Retry / تلاش دوباره** | ارسال دوباره پس از شکست احتمالی؛ باید محدود، زمان‌بندی‌شده و برای اثر کسب‌وکار امن باشد. |
| **Backoff و jitter** | افزایش فاصلهٔ retry همراه پراکندگی زمانی برای جلوگیری از هجوم هم‌زمان درخواست‌ها. |
| **Circuit breaker** | پس از failureهای تعریف‌شده تماس را موقتاً متوقف می‌کند و recovery را مدیریت می‌کند. |
| **Bulkhead** | محدودکردن منابع/هم‌زمانی برای جلوگیری از سرایت خستگی یک وابستگی به کل برنامه. |
| **Queue / صف** | نگهداری کار برای مصرف‌کننده‌ها؛ غالباً کار را میان اعضای یک گروه تقسیم می‌کند. |
| **Pub/sub** | انتشار رخداد به چند subscription مستقل. |
| **Event stream / جریان رویداد** | log مرتب و پایدار در محدودهٔ partition با offset و امکان replay طبق retention. |
| **Command / فرمان** | درخواست انجام عملی توسط گیرنده. |
| **Event / رخداد** | گزارش چیزی که رخ داده؛ گیرنده می‌تواند مستقل واکنش نشان دهد. |
| **Outbox pattern** | ثبت تغییر محلی و event در یک transaction و انتشار بعدی برای کاهش گم‌شدن پیام. |
| **Dead-letter queue (DLQ)** | نگهداری پیام‌های ناموفق پس از policy retry برای تحلیل و بازیابی کنترل‌شده. |
| **Backpressure** | محدودکردن تولید/مصرف برای جلوگیری از انباشته‌شدن کار بیش از ظرفیت سیستم. |
| **Saga** | فرایند چندمرحله‌ای بین مرزهای مستقل با state، retry و عملیات جبرانی. |
| **Compensation / جبران** | عملیات تجاری برای اصلاح اثر مرحلهٔ قبلی؛ الزاماً rollback کامل و اتمی نیست. |
| **Reconciliation / تطبیق** | مقایسهٔ سیستم‌ها یا وضعیت بیرونی برای کشف اختلاف و رساندن فرایند به نتیجهٔ سازگار. |

## امنیت و هویت

| اصطلاح | توضیح |
| --- | --- |
| **Authentication / احراز هویت** | بررسی هویت actor یا سامانه. |
| **Authorization / مجوزدهی** | بررسی اینکه actor می‌تواند عملی را روی resource مشخص در context فعلی انجام دهد یا نه. |
| **RBAC** | Role-Based Access Control؛ policy دسترسی بر اساس نقش‌ها. |
| **ABAC** | Attribute-Based Access Control؛ policy بر اساس ویژگی subject، resource، action و context. |
| **IDOR** | دسترسی ناامن به object با تغییر شناسه به‌دلیل نبود بررسی مجوز مالکیت/tenant سمت server. |
| **OAuth 2.0** | چارچوب واگذاری دسترسی (authorization)، نه به‌تنهایی استاندارد احراز هویت کاربر. |
| **OpenID Connect (OIDC)** | لایهٔ هویت روی OAuth 2.0 برای login و ادعای هویت. |
| **Session** | وضعیت ورود و شناسهٔ نشست که server می‌تواند نگه دارد و revoke کند. |
| **JWT** | قالب claim امضاشده یا رمزگذاری‌شده؛ وجود امضا به معنای محرمانگی نیست. |
| **Hash** | digest یک‌طرفه برای اثرانگشت یا تمامیت؛ hash ساده برای ذخیرهٔ password مناسب نیست. |
| **Salt** | مقدار یکتای غیرمخفی برای هر password hash که استفادهٔ مجدد از جدول hash را سخت‌تر می‌کند. |
| **Encryption / رمزگذاری** | تبدیل داده با کلید برای محرمانگی و بازیابی توسط دارندهٔ کلید. |
| **Digital signature / امضای دیجیتال** | سازوکار کلیدعمومی برای سنجش اصالت و تمامیت؛ به‌خودی‌خود محرمانگی نمی‌دهد. |
| **PKI** | زیرساخت گواهی و اعتماد برای پیوند کلید عمومی به هویت و مدیریت زنجیرهٔ اعتماد. |
| **TLS** | پروتکل حفاظت کانال ارتباطی؛ مجوزدهی API یا امن‌بودن business rule را تضمین نمی‌کند. |
| **STRIDE** | راهنمای طبقه‌بندی تهدید: جعل، دستکاری، انکار، افشا، محروم‌سازی خدمت و ارتقای دسترسی. |
| **Least privilege** | دادن حداقل دسترسی لازم، برای کمترین مدت و scope ممکن. |
| **Threat model** | ثبت دارایی، مرز اعتماد، actor، سوءاستفاده، کنترل، آزمون و ریسک باقی‌مانده. |

## عملیات و تحویل

| اصطلاح | توضیح |
| --- | --- |
| **Container** | بستهٔ برنامه و وابستگی‌ها که معمولاً kernel میزبان را به‌اشتراک می‌گذارد. |
| **Virtual machine (VM)** | ماشین مجازی با سیستم‌عامل مهمان و abstraction سخت‌افزاری. |
| **Orchestration** | زمان‌بندی و نگهداری وضعیت مطلوب workload در چند node. |
| **Service mesh** | زیرساخت ارتباط سرویس‌به‌سرویس برای هویت، ترافیک و telemetry؛ هزینهٔ proxy و کنترل‌پلین هم دارد. |
| **IaC** | Infrastructure as Code؛ تعریف و تغییر زیرساخت از فایل‌های نسخه‌دار و قابل‌مرور. |
| **CI/CD** | یکپارچه‌سازی پیوسته و تحویل/استقرار پیوستهٔ تغییرات از طریق pipeline قابل‌اعتماد. |
| **Blue/green** | نگهداری دو محیط و جابه‌جایی ترافیک؛ rollback ساده‌تر، ولی مصرف ظرفیت بیشتر. |
| **Canary** | ارائهٔ نسخه به بخشی از ترافیک و ارزیابی آن با metric و guardrail. |
| **Feature flag** | جداکردن فعال‌سازی قابلیت از انتشار کد؛ نیازمند owner و پاک‌سازی flag است. |
| **Observability / مشاهده‌پذیری** | توان استنتاج وضعیت درونی سامانه از metric، log، trace و context. |
| **Metric** | اندازه‌گیری عددی در طول زمان مانند latency، نرخ خطا یا مصرف منابع. |
| **Log** | رخداد ثبت‌شده با زمان و context؛ ممکن است دادهٔ حساس افشا کند. |
| **Trace** | مسیر یک درخواست در spanهای مرتبط در چند جزء و مرز شبکه. |
| **SLI** | Service Level Indicator؛ شاخص اندازه‌گیری‌شدهٔ تجربهٔ خدمت. |
| **SLO** | Service Level Objective؛ هدف داخلی برای یک یا چند SLI در پنجرهٔ مشخص. |
| **SLA** | توافق سطح خدمت با پیامد یا تعهد قراردادی. |
| **Error budget** | مقدار شکست/نقض مجاز برآمده از SLO که trade-off سرعت انتشار و reliability را هدایت می‌کند. |
| **Readiness probe** | اعلام اینکه instance برای دریافت کار جدید آماده است. |
| **Liveness probe** | بررسی اینکه process زنده و پاسخ‌گوست؛ نباید هر failure گذرای وابستگی را به restart storm تبدیل کند. |
| **Graceful shutdown** | توقف پذیرش کار جدید، تخلیهٔ کار جاری و خروج پیش از deadline. |
| **Drift** | تفاوت وضعیت واقعی زیرساخت با تعریف موردنظر در IaC. |
| **Rollback / forward-fix** | بازگشت به نسخهٔ قبلی یا اصلاح رو به جلو؛ تغییر schema ممکن است rollback ساده را ناممکن کند. |

## مدیریت و سازمان

| اصطلاح | توضیح |
| --- | --- |
| **WIP limit** | سقف کارهای هم‌زمان در جریان برای کاهش چندوظیفگی و آشکارشدن گلوگاه. |
| **Lead time** | زمان از ثبت درخواست/آغاز کار تا تحویل، با تعریف متناسب سازمان. |
| **Cycle time** | زمان اجرای یک قلم پس از شروع واقعی آن تا تکمیل. |
| **Backlog** | فهرست اولویت‌دار کار/نیاز؛ به‌تنهایی تضمین ارزش یا کیفیت نیست. |
| **Business capability** | توان پایدار سازمان برای ارائهٔ نتیجهٔ کسب‌وکار، مستقل از شکل فعلی پیاده‌سازی. |
| **System of record** | مرجع authoritative برای تغییر و وضعیت معتبر یک داده یا entity. |
| **Enterprise architecture** | نگاه به پیوند راهبرد، قابلیت، داده، برنامه، فناوری و گذار در سطح سازمان. |
| **BPMN** | نشانه‌گذاری مدل فرایند کسب‌وکار برای نمایش فعالیت، رویداد، نقش و تصمیم. |
| **Technical debt / بدهی فنی** | هزینهٔ آینده‌ای که از میان‌بُر یا انتخاب قبلی و نیاز به اصلاح/نگهداری باقی مانده است. |
| **Runbook** | راهنمای اجرایی برای تشخیص و اقدام در رخداد یا کار عملیاتی تکراری. |
